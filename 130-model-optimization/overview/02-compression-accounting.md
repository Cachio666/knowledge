# 五本账与三种峰值：报「省了多少显存」之前必须先答的两个问题

> 六族优化的「省」必须落到**五本账**（权重 / 梯度 / 优化器状态 / 激活 / KV cache）中的某一本；
> 而这五本账**不同时到达峰值**——同一个模型在训练 / prefill / decode 三个阶段的峰值是
> **105.99 / 17.34 / 14.55 GiB**（示例配置的推导值）。所以「省了多少显存」这句话在答出
> **「哪一本账」「哪个阶段」**之前，**没有真假**。

## 0. 背景与动机

同一个 7B 量级的模型，同一句「int4 量化能省很多显存」，在两个场景里给出**两个差得很远的数**：

| 场景 | 基线峰值 | int4 权重后 | 降幅 |
|---|---|---|---|
| **训练**（示例：`B=8, S=4096`） | 105.99 GiB | 96.58 GiB | **8.88%** |
| **decode**（示例：`B=1, S=4096`） | 14.55 GiB | 5.14 GiB | **64.65%** |

两个数都是 `code/02_accounting.py` 算出的**推导值**（C.1 与归因表），**都对**。
它们不矛盾，因为它们说的不是同一件事：前者动的是「五本账里占 1/8 的那一本」，
后者动的是「decode 阶段的两本账里占 86% 的那一本」。

这就是本题的全部动机：

> **「省了多少显存」不是一个数，而是一个函数**——它的自变量是
> **哪一本账**与**哪个阶段**。不把这两个自变量写出来，任何数字都无法核对。

## 1. 原理

### 第一步：先把账列全——**五本**，不是一本

| # | 账 | 表达式 | 谁活着 |
|---|---|---|---|
| ① | **权重** | `Ψ · w/8` | 训练 / prefill / decode **都活着** |
| ② | **梯度** | `Ψ · g/8` | **只有训练** |
| ③ | **优化器状态** | `Ψ · K`（Adam + fp32 主权重：`K = 12`） | **只有训练** |
| ④ | **激活** | 与 `batch × seq × 层数` 相关 | 训练与 prefill 显著；decode 极小 |
| ⑤ | **KV cache** | `B · S · k_KV(b)` | **只有推理**（prefill 边写边用、decode 全量读） |

★ `Ψ` 是参数量；`K = 12` 与 `2Ψ + 2Ψ + KΨ = 16Ψ` 的**分解与逐项字节的正文**在
`90-training/checkpointing/01-state-and-bytes.md` §1.3，本文**只消费、不重推**。
★ 每 token KV 字节 `k_KV` 的正文在 `130-model-optimization/quantization/18-kv-cache-basics.md`，
本文同样只消费（A.3 会用六项乘积独立复算一次做跨域对拍）。
★ **激活那一本本文不推导**：它的正文在
`90-training/autograd-and-backward/02-gradient-checkpointing.md`（`O(√n)` 那条链）。
本文把训练 / prefill 的激活量当作**两个给定的示例输入**（`specs.py` 里标为**示例假设**），
因为本题的对象是**归因**，不是激活公式。

### 第二步：哪些账**同时**活着——阶段矩阵

| 账 | 训练 | prefill | decode |
|---|---|---|---|
| 权重 | ✅ | ✅ | ✅ |
| 梯度 | ✅ | — | — |
| 优化器状态 | ✅ | — | — |
| 激活 | ✅ | ✅ | （极小，本文不计） |
| KV cache | — | ✅（写） | ✅（全量读） |

⇒ 三个阶段的峰值（示例工作负载，`B=8/S=4096`、`1/4096`、`1/4096`）：

```
train    105.99 GiB = weights 12.55 + grads 12.55 + optimizer 75.30 + activations 5.59
prefill   17.34 GiB = weights 12.55 + activations  2.79 + kv  2.00
decode    14.55 GiB = weights 12.55 + kv  2.00
```

### 第三步：峰值是 `max`，不是 `sum`

这是本题要证明的第二件事。把五本账**各自的最大值**加起来：

```
五账加总 = 12.55 + 12.55 + 75.30 + 5.59 + 2.00 = 107.99 GiB
真实峰值 = max(105.99, 17.34, 14.55)         = 105.99 GiB
```

**加总比峰值大 2.00 GiB**（A.3；差额恰是「只有别阶段才活着」的那本账——
这里就是 prefill/decode 的 KV）。「把账加起来」是规划显存时最常见的错误做法，
它给出一个**永远偏大**的数，而偏大的方向会让本来能装下的配置被误判为装不下。

### 第四步：把六族的「省」归因到五本账

六族各自动哪几本？程序 B 类把八个档位逐一算出来（示例配置，**推导值**）：

| 族 / 档位 | 训练峰值 | 降幅 | decode 峰值 | 降幅 | 动到的账 |
|---|---|---|---|---|---|
| 量化 · 权重 W4 | 96.58 GiB | 8.9% | 5.14 GiB | 64.7% | 权重 |
| 量化 · KV4 | 105.99 GiB | 0.0% | 13.05 GiB | 10.3% | KV |
| 稀疏化 · 2:4 结构化 | 100.50 GiB | 5.2% | 9.06 GiB | 37.7% | 权重 |
| 剪枝 · 50%（**稀疏存储**） | 99.72 GiB | 5.9% | 8.28 GiB | 43.1% | 权重 |
| 剪枝 · 50%（**稠密存储**） | 105.99 GiB | **0.0%** | 14.55 GiB | **0.0%** | **一本都没动** |
| 低秩分解 · `r=256` | 19.03 GiB | 82.1% | 3.68 GiB | 74.7% | 权重 + 梯度 + 优化器状态 |
| 蒸馏 · 学生 50% | 55.79 GiB | 47.4% | 8.28 GiB | 43.1% | 权重 + 梯度 + 优化器状态 |
| PEFT · `ρ=0.002` | 18.31 GiB | 82.7% | 14.55 GiB | **0.0%** | 梯度 + 优化器状态 |

这张表有三格是本主题的**核心结论**：

1. **六族里没有一族同时动到五本账**（B.1）——所以「某族优化能省 X%」这句话
   必须带上是哪一本账。
2. **稠密存储下的剪枝一本账都没动**（B.2）。剪枝减少的是**参与计算的元素**，
   但如果权重仍按稠密张量存，**字节数一点没变**。「剪枝省显存」这个说法
   隐含一个前提：**改成稀疏存储**（并按硬件粒度表编码 metadata）。
3. **PEFT 对 decode 峰值的影响恰好是 0**（表里那一行），因为它动的是训练专属的两本账。
   ★ 反过来，**量化对优化器状态的影响也恰好是 0**（C.4 把这条逐位断言出来）。

### 第五步：为什么 PEFT 能把训练峰值压到 1/6

`ρ = 0.002`（LoRA 常用的 0.2%，**引用值**，见 `specs.QLORA_LORA_PARAM_FRACTION`）时：

```
基线     16Ψ + 激活 = 105.99 GiB
PEFT 后  2Ψ（冻结权重）+ 2ρΨ（梯度）+ 12ρΨ（优化器状态）+ 激活 = 18.31 GiB
```

**训练峰值里最大的一本账是优化器状态（75.30 GiB，占 71%）**，而 PEFT 动的正是它。
这就是为什么「训练大模型」的显存瓶颈**通常不在权重**，也解释了
`16Ψ` 里 `12Ψ` 那个系数为什么值得单独记住。

## 2. 执行映射

账是纸上的，落到系统里由这些组件兑现：

- **优化器状态**：PyTorch 的 `torch.optim.Adam` 为每个参数维护 `exp_avg` 与
  `exp_avg_sq` 两个张量；在 AMP/混合精度下它们通常是 **fp32**，
  于是就是 `2 × 4 = 8` 字节/参数，加上 fp32 主权重 `4` 字节 ⇒ `K = 12`。
  **PEFT 之所以有效，是因为它让这个张量表只覆盖 `ρ` 比例的参数。**
- **显存读数**：`torch.cuda.max_memory_allocated()` 与 `memory_reserved()` 是
  **两个不同的口径**（allocated 是张量实际占用，reserved 是缓存分配器向驱动要的池）。
  再乘上「峰值」这个词本身——它是一个**按时间取 max** 的量，
  所以「峰值读数」与「某时刻的账」可以差出很多。
- **KV cache**：推理引擎侧由 block manager 管（vLLM 的 PagedAttention 块表），
  容量规划的那条链是 `可用显存 // (块大小 × 每 token 字节)`（正文在
  `120-inference/kv-cache/01-capacity-planning.md`）。
  **它的输入是「每 token 字节」，也就是本文第五本账的单位。**

**一个数值量级**：示例配置下优化器状态是 **75.30 GiB**（`12Ψ`），
而整个 decode 峰值只有 **14.55 GiB**。**训练的一本账比推理的峰值还大 5 倍**——
这就是「训练显存」与「推理显存」不能互相换算的算术原因。

## 3. 实现与演进

**朴素做法：打印一张张量表。** 手工加 `sum(p.numel() * p.element_size() for p in model.parameters())`
——它只给出第一本账，而且漏掉优化器状态。

**主流做法：问运行时要峰值。** `torch.cuda.max_memory_allocated()` 给出**真实峰值**
（它按时间取 max，正是 §1 第三步要求的那个 `max`），配合 `reset_peak_memory_stats()`
就能做分段测量。这一步的必要性在于：**纸上的账会漏项**（临时张量、通信缓冲、碎片），
而运行时读数不会。

**为什么还需要下一步：读数不告诉你「为什么」。** 峰值超了，是权重、激活还是优化器？
`torch.cuda.memory._record_memory_history()` 的 memory snapshot 能给出分配栈，
把每一笔分配归到具体的算子或模块——这才把「读数」变回「账」。

**前沿方案：把账当约束做搜索。** 当六族的档位可选时，「在给定显存约束下选档位」
是一个带约束的优化问题；`accelerate` 一类的 `estimate` 工具做的是它的查表近似。
框架内的自动分片（ZeRO/FSDP 的 `16/N` 那一族）则是把第三本账**按卡数切**——
切法的正文在 `100-parallelism/zero-fsdp/`。

## 4. 踩坑与失败模式

### 4.1 现象：规划时把五本账加起来当峰值，结果按这个数选卡永远不够

**成因**：五本账**不同时**到达峰值（§1 第二步的阶段矩阵）。加总比真实峰值大——
示例配置下大 `2.00 GiB`（A.3）。偏大的方向会让可行的配置被误判为不可行，
更糟的是它会掩盖**真正的**峰值来源。

**规避**：报峰值时一律写**阶段**：`phase=train` 的峰值、`phase=decode` 的峰值。
判据：如果一句话里的峰值不是「某个阶段在某一时刻同时活着的账之和」，它就不是峰值。

### 4.2 现象：说「剪枝 50% 省一半显存」，实测显存没变

**成因**：剪枝减少的是**参与计算的元素**；dense 存储下张量形状不变、字节不变
（归因表里那一行降幅**恰好 0.0%**）。要真的省，必须改成稀疏存储，
并按硬件粒度表付 metadata：2:4 在 16-bit 下的整块宽度是 `36/64`（省 43.75%，
**不是** 50%，正文在 `sparsity/01-sparsity-granularity.md`）。

**规避**：把「剪枝」与「稀疏存储」当两个独立决定。报省字节时，先写明存储格式。

### 4.3 现象：拿训练态的 `16Ψ` 估检查点文件大小，存档比预期大

**成因**：`16Ψ` 是**训练显存**口径、**含梯度 `2Ψ`**；检查点只有参数与优化器状态，
是 `14Ψ`。程序 C.3 把这条差**逐位断言**出来：`(16 − 14)Ψ = 2Ψ`。
分解的正文在 `90-training/checkpointing/01-state-and-bytes.md`，本文只消费。

**规避**：报「显存」用 `16Ψ`、报「文件」用 `14Ψ`，并在同一段写出这句限定语。

### 4.4 现象：把「量化省显存」与「量化省训练显存」当成同一句话

**成因**：量化只动**权重**那一本。在训练态里权重只占 `2/16 = 1/8`，
所以降幅 `< 10%`（C.1 用 8.88% 这个推导值把它钉住）；
而在 decode 里权重占 86%，降幅 64.65%。同一句话在两个阶段差 7 倍。

**规避**：任何「省显存」的声明后面跟一个括号写明 `(账=权重, 阶段=decode)`。
判据见 §5 的第一行。

## 5. 判据表

| 条件（可机械判定） | 结论 |
|---|---|
| 一句「省了 X% 显存」没写**账**与**阶段** | **无法核对**：同一次量化在训练态降 `8.88%`、在 decode 降 `64.65%` |
| 要估峰值 | `max` over 阶段，**不是**五账相加；相加会偏大（示例：`107.99` vs `105.99` GiB） |
| 声称「剪枝省显存」 | **前提是稀疏存储**；dense 存储下归因表的降幅**恰好 0.0%** |
| 声称「量化省优化器状态」 | **假**：差**恰好为 0**；要动这一本只能走 PEFT 或蒸馏 |
| 声称「PEFT 让推理更省显存」 | **假**：decode 峰值降幅 **0.0%**（它只动训练专属的两本账） |
| 报训练显存 | `2Ψ + 2Ψ + 12Ψ = 16Ψ`（含梯度）；**优化器状态占 12/16 = 75%** |
| 报检查点文件大小 | `2Ψ + 12Ψ = 14Ψ`；与 `16Ψ` 差 `2Ψ`（一份梯度） |
| 要动训练峰值的**大头** | 动优化器状态（PEFT / 蒸馏）；只压权重最多降到 `14.5Ψ` |
| 要动 decode 峰值的**大头** | 先看 KV 占比 `B·S·k_KV / (W + B·S·k_KV)`；`S` 越长它越大 |
| 见到「六族之一能省全部显存」 | **假**：六族里没有一族同时动到五本账（B.1） |

## 6. 小结与延伸

- 五本账：**权重 / 梯度 / 优化器状态 / 激活 / KV**。它们的**峰值时刻不同**。
- 峰值是 `max` over 阶段，**不是** `sum`；示例配置下两者差 `2.00 GiB`。
- 六族里**没有一族**同时动五本账；**量化不碰优化器状态**、**PEFT 不碰推理**，
  这两条各是一个「恰好为 0」的断言。
- 训练峰值的大头是**优化器状态**（`12Ψ`，占 75%），不是权重。
- **剪枝省显存以稀疏存储为前提**；dense 存储下降幅恰好 0。
