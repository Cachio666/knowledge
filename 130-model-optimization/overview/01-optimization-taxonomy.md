# 优化技术的六个自由度：压缩率与加速率之间那道墙

> 六族优化不是六个并列的技巧，而是对同一个模型动**六种不同的自由度**；而「压到 1/4 就快 4×」
> 在**任何一族**上都不普遍成立——墙由三件事砌成：**账不同时到顶**、**阶段不同瓶颈不同**、
> **能被这一族动到的份额小于 100%**。

## 0. 背景与动机

先摆一个具体的对照场景，它是本题全部推导的起点。

取一个 32 层、`d_model = 4096`、`d_ff = 11008`、32 个 KV 头、`head_dim = 128` 的
MHA 模型（**本文构造的示例假设**，形状取 7B 量级，不是任何已发布模型的规格声明）。
fp16 下它的权重是 **12.551 GiB**（`code/01_taxonomy.py` 的 A.2）。

现在把它放到一张 24 GB 卡上做 decode。有人会说：

> 权重占了大头，那就把权重压到 4 bit——`16/4 = 4`，**推理快 4 倍**。

这个推理链有两处断裂，本题把它们逐一量出来：

| 环节 | 朴素预期 | 本程序算出的**推导值** |
|---|---|---|
| 权重字节（全部参数） | 12.551 GiB → 3.138 GiB（4×） | 成立（纯载荷口径） |
| decode 每步读的权重 | 同上 | **12.307 GiB**（少掉的 `0.244 GiB` 是 embedding 查表：它每步只读 `d` 个数，不读整表——见 §1 第二步） |
| decode 端到端加速（`S=1`） | 4× | **3.999524×** |
| decode 端到端加速（`S=4096`） | 4× | **2.818×** |
| decode 端到端加速（`S=131072`） | 4× | **1.138×** |
| prefill 端到端加速（W4A16） | 4× | **1.000×**（FLOPs 一点没变） |
| 训练显存降幅 | 50% | **9.38%** |

同一句「压 4×」，在六个格子里给出**六个不同的数**。差异不是测量噪声，而是三件事：

1. **压缩率压的是某一本账，不是「显存」**——权重、梯度、优化器状态、激活、KV cache
   是五本独立的账，各有各的峰值时刻（正文在 [02](02-compression-accounting.md)）。
2. **同一本账在不同阶段的瓶颈不同**——decode 是 memory-bound，prefill 是 compute-bound
   （roofline 的判据见 `10-foundations/performance-models/01-roofline-model`）。
3. **一族优化只能动到自己那本书的一部分**——剩下那部分按 Amdahl 留在原地
   （见 `10-foundations/performance-models/02-amdahl-and-scaling`）。

## 1. 原理

### 第一步：先把「模型」拆成四个可动的自由度

不提「量化 / 剪枝 / 蒸馏」，先问：**一个已训练好的模型，有哪些东西是「可以被改小」的？**

| 自由度 | 含义 | 改它意味着 |
|---|---|---|
| **表示精度** | 每个数用多少位存 | 同一个张量，字节数变、数值略变 |
| **参与计算的位置** | 哪些元素/通道**参与** | 张量变大变小（dense 存储下**字节不变**，见第四步） |
| **表示的秩** | 权重矩阵是满秩还是低秩 | 参数量变、表达能力的上界变 |
| **可训练量** | 训练时哪些参数需要梯度与优化器状态 | 训练态的五本账里**只有两本**随之变 |

六族优化就是这四个自由度上的六种动作，**没有第七种**：

| 族 | 动哪个自由度 | 动的是谁的字节 | 光靠它能减少 FLOPs 吗 |
|---|---|---|---|
| 量化 | 表示精度 | 权重 / 激活 / KV 的字节 | **不能**（除非同时降激活位宽） |
| 剪枝 | 参与计算的位置 | 参数量（**前提是改成稀疏存储**） | 能（稀疏算力档） |
| 稀疏化 | 参与计算的位置**的粒度与编码** | metadata 开销 | 能（但在硬件粒度表内才换得到吞吐） |
| 蒸馏 | 换一个更小的模型 | 全部五本账 | 能 |
| 低秩分解 | 表示的秩 | 权重与 FLOPs | 能 |
| 参数高效微调 | 可训练量 | 梯度与优化器状态 | **不能**（推理侧完全不动） |

★ 这张表有两格是反直觉的，它们各自是 §4 的一条失败模式：
**量化不减少 FLOPs**、**参数高效微调对推理毫无帮助**。

### 第二步：decode 一步搬多少字节

decode 每生成一个 token，需要把**整个权重**读一遍，再把这个请求的**整个 KV cache** 读一遍
（注意力的算术强度在 `S=1` 时收敛到 `1 FLOP/字节`，推导在
`130-model-optimization/quantization/18-kv-cache-basics.md`，本文不重推）。于是

$$
\text{bytes}_{\text{step}} \;=\; \underbrace{\Psi_{\text{decode}} \cdot \frac{w}{8}}_{\text{权重}}
\;+\; \underbrace{B \cdot S \cdot k_{\text{KV}}(b_{\text{kv}})}_{\text{KV cache}}
$$

其中 `Ψ_decode` 是**每 token 真正参与矩阵乘**的参数（**不含** embedding 查表），
`k_KV(b)` 是每 token 的 KV 字节（位宽 `b`），`B` 是 batch，`S` 是上下文长度。

**要点一**：这一步是 memory-bound，所以

$$
T \;=\; \frac{\text{bytes}_{\text{step}}}{\text{BW}} \quad\Longrightarrow\quad
\frac{T_{16}}{T_{4}} \;=\; \frac{\text{bytes}_{16}}{\text{bytes}_{4}}
$$

**带宽在比值里约掉了。** 于是本题关于「加速比」的结论**与 GPU 型号无关**——
它只由「权重字节」与「KV 字节」的**占比**决定。这一点值得单独记住：
一个不依赖任何硬件常量的加速比结论，是很难用「换卡就好了」搪塞过去的。

### 第三步：把占比代进去，得到那道墙

示例配置下 `Ψ_decode = 6.607B`（A.4），fp16 权重 `= 13.214 GB`；
每 token KV `= 512 KiB`（A.3，**取自** `18-kv-cache-basics`，本文不重推）。于是

| `S` | KV 字节 | KV 占比 `f_kv` | 权重压 4× 后的字节比 |
|---|---|---|---|
| 1 | 0.5 MiB | 0.00004 | **3.999524×** |
| 1024 | 0.5 GiB | 0.039 | **3.581×** |
| 4096 | 2.0 GiB | 0.140 | **2.818×** |
| 32768 | 16.0 GiB | 0.565 | **1.484×** |
| 131072 | 64.0 GiB | 0.839 | **1.138×** |

把它写成权重的**字节占比** `f_w = 1 − f_kv` 的 Amdahl 形式：

$$
\text{speedup} \;=\; \frac{1}{(1-f_w) + f_w/4}
$$

`S=4096` 时 `f_w = 0.860` ⇒ `1/(0.140 + 0.215) = 2.818`，与表逐位吻合（B.1/B.2）。
**这就是那道墙的解析形式**：只要 `f_w < 1`，加速比就严格小于压缩率；
而 `f_w → 0`（长上下文）时加速比 `→ 1`（C.2）。**下界是 1，不是 0**——
权重压缩在长上下文下「白做」，但它不会变成负收益。

### 第四步：prefill 那一侧，位宽根本不进算力账

prefill 是 compute-bound，它的账是 FLOPs：

$$
\text{FLOPs/token} \;=\; 2\,\Psi_{\text{token}} \;=\; 26.43\ \text{GFLOP}
$$

（A.4；`S` 个 token 的 prefill 是它的 `S` 倍）。**这个数与权重位宽无关**：
`W4A16` 只是把权重用 4 bit *存*、用 16 bit *算*——矩阵乘的乘法次数一次都没少。

⇒ 在 compute-bound 阶段，**只压权重带来的加速恰好是 `1.000×`**（C.3 的反面）。
要在这条账上拿到收益，只有三条路：

1. **降激活位宽**（W8A8 / FP8）：让 tensor core 走更快的档位；
2. **减少参与计算的元素**（剪枝 / 稀疏化）：FLOPs 真的变少；
3. **减少参数量本身**（低秩分解 / 蒸馏）：FLOPs 真的变少。

而且即便走了第 1 条，还有一层 Amdahl：算力档位提升 `k` 倍，
只有当**矩阵乘占满全部时间**时才拿到 `k` 倍。`f = 0.85` 时 int8 的 2× 只换来
`1/(0.15 + 0.85/2) = 1.739×`（C.3）。

### 第五步：训练那一侧，权重只占 1/8

训练态的账是 `16Ψ`：`2Ψ`（fp16 权重）+ `2Ψ`（fp16 梯度）+ `12Ψ`（fp32 主权重 + `m` + `v`）。
它的**分解与逐项字节的正文**在 `90-training/checkpointing/01-state-and-bytes.md` §1.3，
本文**只消费、不重推**。

把参数代进去（B.3）：训练态 `= 100.406 GiB`，其中 fp16 权重 `= 12.551 GiB`，
占比**恰好 `2/16 = 0.125`**。于是

> 把权重从 16 bit 压到 4 bit（纯载荷 4×），训练峰值从 `16Ψ` 降到 `14.5Ψ`，
> **只降 9.38%**——因为 `12Ψ` 的优化器状态一点没动（C.4）。

这解释了为什么「量化让大模型训练更省显存」是一个**弱断言**：
它动的是那本**只占 1/8** 的账。要动大账，只能动优化器状态那一本，
而那正是**参数高效微调**的位置（归因表见 [02](02-compression-accounting.md)）。

### 第六步：三件事合成的判据

把上面五步合起来，六族优化的「加速声明」必须先回答三个问题：

| 问 | 答「否」的后果 |
|---|---|
| **哪一本账？** | 「省了显存」这句话没有真假——五本账的峰值时刻不同（§1 第五步、[02](02-compression-accounting.md)） |
| **哪个阶段？** | decode 的收益不能搬到 prefill；反之亦然（§1 第三、四步） |
| **动到了该账的多大份额？** | 占比 `f` 决定加速上限 `1/((1-f)+f/k)`（§1 第三步、第五步） |

## 2. 执行映射

上面全是账。这些账在真实系统里由**具体的组件**兑现或落空：

- **量化**：`torch.ao.quantization` 侧由 observer 定 scale、`convert` 换实现；
  推理引擎侧由 `quant_config`（vLLM 的 `--quantization`）**dispatch 到不同的 kernel**——
  同一个 4-bit 权重，走 Marlin / Machete / ExLlamaV2 的吞吐可以差出成倍。
  ★ **量化格式与 kernel 的配对是运行时决定的一等公民，不是权重文件里的属性。**
- **稀疏化**：`mma.sp` 与 `cuSPARSELt` 只认硬件粒度表里的档位（1:2 / 2:4 / 4:8-paired），
  非结构化稀疏**不在表里**（正文在 `sparsity/01-sparsity-granularity.md`）。
- **KV cache 量化**：引擎侧是一个独立的开关与独立的一组 kernel（`CacheDType`），
  它**不与权重量化解锁同一段加速**——它解锁的是 §1 第三步里那个 `f_kv`。
- **参数高效微调**：它落在 `torch.optim` 的**状态张量**上。以 Adam 为例，
  每个参数带两个 fp32 矩估计 ⇒ **8 字节/参数**，加上 fp32 主权重共 `12` 字节/参数——
  这就是 `16Ψ` 里那 `12Ψ` 的来源（分解正文在 `90-training/checkpointing/01-state-and-bytes.md`）。
  冻结主体后这部分按可训练比例 `ρ` 缩，而**推理侧的权重一个字节都没少**。

**一个数值量级**：示例配置下，decode 一步要搬 `12.307 GiB + 2.000 GiB = 14.307 GiB`
（`S=4096`）。KV 那 `2.000 GiB` 是 `4096 × 512 KiB`——**它自己就是一次全量读**，
与权重读同一条带宽。这就是为什么 §1 第三步里 `f_kv` 涨得那么快：
**KV 字节随 `S` 线性增长，权重字节不随 `S` 变。**

## 3. 实现与演进

**朴素做法：把「压缩率」当「加速率」。** 这是 2023 年前后大量博客的做法——
算一遍「16/4 = 4」，写成「快 4 倍」。它错在把某一本账的字节比当成了端到端时间比。

**主流做法：分阶段、分账地报数。** 今天的引擎与论文至少把三件事分开写：
batch 大小、上下文长度、以及测的是 prefill 还是 decode。本库 `120-inference` 的
kv cache 与调度两题就是这个视角的产物。

**为什么还需要下一步：把「组合」也纳入进来。** 六族可以叠加，而叠加有两种做法：
一种是**独立叠加**（先 W4，再 KV4，互不相干），另一种是**互相改变输入**的叠加
（剪枝改变量化 scale 所依赖的分布；量化的并列改变剪枝的支撑集）。
后者的结果**依赖顺序**，而判据不是「看情况」——它有一条可机械判定的边界条件，
这在 [03](03-composition-and-selection.md) 里推导并用程序搜证。

**前沿方案：把「自由度」交给搜索。** 当六族的档位（位宽、粒度、稀疏度、秩、`ρ`）
都可选时，问题变成「在给定的账约束下选一组档位」。这一步的正文不在本题——
它属于 `50-performance` 的判据方法论与各族的实现细节。

## 4. 踩坑与失败模式

### 4.1 现象：W4A16 量化后，prefill 吞吐没涨，甚至掉了

**成因**：prefill 是 compute-bound，而 W4A16 的**乘法次数不变**（§1 第四步）。
更糟的是 int4 权重在矩阵乘前要**反量化**——独立的反量化 pass
读 `K·N/2` 字节却写 `K·N·2` 字节（**写是读的 4 倍**），被写侧带宽卡住
（正文在 `quantization/15-w8a8` 与 `quantization/16-w4a16-packing`，此处回链）。

**规避**：把「权重压缩」与「算力提升」当作两件独立的事来报数。
要在 prefill 拿收益，必须动**激活位宽**（W8A8 / FP8）或**结构**（剪枝 / 低秩）。
判据：如果权重文件小了 4× 而 prefill 的 FLOPs 没变，那么 prefill 的加速预期**就是 1×**。

### 4.2 现象：长上下文下，权重压缩的收益趋近于零

**成因**：`f_kv → 1`（§1 第三步的表）。`S=131072` 时 KV 占 83.9%，
权重那条账再小也只剩 16% 的可压缩空间，把 4× 压进这部分最多拿到 `1.138×`。

**规避**：**权重压缩与 KV 压缩是两笔独立的交易**，必须分别报价、
分别验证。看到一个「端到端 4×」的数字时，先问它的上下文长度与 batch。

### 4.3 现象：把 2:4 稀疏写成「省 50%」，账对不上

**成因**：2:4 的 metadata 是 **4 bit/组、一组 4 个元素**（PTX ISA 的稀疏存储一节），
它**不随载荷一起缩**。16-bit 数据下含 metadata 的整块宽度是 `36/64`（省 43.75%），
**不是** `1/2`。程序 A.4 用这条复算并与 `sparsity/01` 的结论对拍。

**规避**：报压缩率时一律写**整块宽度**（载荷 + metadata），并写明 metadata 的分母是
「原始数据」还是「压缩后载荷」——同一个 4 bit 在这两个分母下差一倍。

### 4.4 现象：用 `16Ψ` 估检查点文件大小，存档总是比预期大

**成因**：`16Ψ` 是**训练显存**口径，**含梯度 `2Ψ`**；检查点里的 `state_dict`
只有参数与优化器状态，是 `14Ψ`。两者差**恰好一个梯度项**（正文在
`90-training/checkpointing/01-state-and-bytes.md`，本文只消费）。

**规避**：报「显存」时写 `16Ψ`、报「文件大小」时写 `14Ψ`，并在同一段里写出
这一句限定语。程序 `02_accounting.py` 的 C.3 把这条差**逐位断言**出来。

## 5. 判据表

| 条件（可机械判定） | 结论 |
|---|---|
| 加速声明只给了一个倍数，没写上下文长度 `S` 与 batch | **信息不全**：decode 的倍数随 `S` 单调下降（`3.9995× → 1.138×`），无法判定 |
| 声称「权重压 `k` 倍 ⇒ 端到端 `k` 倍」，且 KV 未压缩 | **假**：加速 `= 1/((1-f_w) + f_w/k) < k`，只要 `f_w < 1` |
| 要估 decode 的字节账 | `Ψ_decode·w/8 + B·S·k_KV`；带宽在比值里约掉 ⇒ 结论与 GPU 型号无关 |
| 声称 prefill 因权重量化而提速 | **假**：`FLOPs/token = 2Ψ` 与权重位宽无关；除非同时降激活位宽或减参数量 |
| 声称「4-bit 权重 = 4 bit/参数」 | **假**：含常量后 NF4 的整块宽度是 `4.127` bit/参数（qLoRA §3 的 `8/64 + 32/(64·256)`） |
| 声称「2:4 稀疏省 50%」 | 若指**整块**宽度则**假**：`36/64`（省 43.75%）；若指**载荷**则对，须写明 |
| 声称「量化让训练更省显存」 | 只压权重时降幅 `< 10%`（`16Ψ → 14.5Ψ`）；要大降必须动优化器状态（PEFT / 蒸馏） |
| 要报「省了多少显存」 | 先答三问：哪一本账 / 哪个阶段 / 动到了该账的多大份额（§1 第六步） |
| 报检查点文件大小 | 用 `14Ψ`；用 `16Ψ` 会**恰好多算一份梯度** |
| 见到「剪枝省显存」 | **前提是改成稀疏存储**；dense 存储下剪枝一个字节都不省（[02](02-compression-accounting.md) 的归因表） |

## 6. 小结与延伸

- 六族优化 = 四个自由度（**表示精度 / 参与位置 / 秩 / 可训练量**）上的六种动作。
- 压缩率 ≠ 加速率。三件事砌成那道墙：**账不同时到顶**、**阶段不同瓶颈不同**、
  **可动份额 < 100%**。
- `speedup = 1/((1-f_w) + f_w/k)` 是这道墙的解析形式；
  **带宽在比值里约掉**，所以它是结构性的，不靠换卡。
- 量化不减少 FLOPs；PEFT 不改善推理。这两条各自是一条失败模式。
