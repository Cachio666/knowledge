## 六族的统一视角

六族不是六个并列的技巧，而是**对同一个模型动六种不同的自由度**。`overview/` 把这张表推导成账，这里只列骨架：

| 族 | 动的是哪个自由度 | 直接省的是哪本账 | 换来的新代价 |
|---|---|---|---|
| 量化 | 每个数的**表示精度** | 权重 / 激活 / KV 的**字节** | 精度损失；低精度 kernel 的硬件支持面 |
| 剪枝 | 哪些参数**参与计算**（选谁） | 参数与 FLOPs | 精度恢复训练；判据本身的校准成本 |
| 稀疏化 | 保留下来的参数**怎么被硬件消费**（粒度） | 只在硬件粒度表内的档位才换得到吞吐 | metadata 开销；档位与精度分布不匹配 |
| 蒸馏 | **学生**的容量与训练信号 | 参数量与推理成本 | 需要教师；训练算力 |
| 低秩分解 | 权重矩阵的**秩** | 参数与 FLOPs | 秩预算决定表达能力上限 |
| 参数高效微调 | **可训练**的参数量（主体冻结） | 优化器状态与训练显存 | 下游任务的可达容量上限 |

**剪枝与稀疏化是两件事**：剪枝回答「去掉哪些」（判据），稀疏化回答「剩下的怎么表示给硬件」（粒度与 metadata）。
两者的正文因此分开：判据在 [pruning](pruning/)，粒度在 [sparsity](sparsity/)。

## 写作约定

1. **代码形态按主题声明（CONTRIBUTING §2 判定表）。** 本域**并存两种**形态，因为各主题的编号程序对运行环境的要求不同：

   | 主题 | 形态 | 编号程序跑在 | 三类断言落在 |
   |---|---|---|---|
   | `quantization`（20 篇，`code/` 内含 6 组 `verify_*.py` 辅助模块） + `sparsity` / `pruning` / `distillation` | **第三种**（需真系统） | 装了 `torch` 的非默认解释器 | **B 在编号程序**（代价模型的参照是真系统）；**A / C 在 `verify.py`**（默认 `python3`，**永不 import torch**） |
   | `overview` / `low-rank`（及后续 `peft`，视其程序是否需真系统而定） | **第二种**（本机可跑） | 默认 `python3` + `numpy` | **三类全在编号程序内部**，失败以非零码退出 ⇒ **不需要 `verify.py`** |

   `make verify` 与 `make run` 是两个不同解释器下的两个入口，不得混用；`verify.py` 的产出**一律是推导**，不得标成本机实测值。

2. **`§5 实测数据` 的形态也按主题声明。** `quantization`（20 篇）与 `sparsity` / `pruning` / `distillation` 用**实测数据**形态（真 `torch` 本机实测，**必须写明解释器与 torch 版本**）；`overview` 与 `low-rank` 用**判据表**形态——它的知识对象是**方法**（选型与账），本机无 GPU，且其编号程序**不依赖真系统**，故「实测数据」与「整节省略」两种形态都不适用。

3. **压缩率 ≠ 加速率。** 凡「压到 1/4」这类断言，必须写明压的是哪本账（权重字节 / KV 字节 / FLOPs / 可训练参数），以及加速受什么约束（带宽、Amdahl、kernel 支持面）。两者**不得互相背书**。

4. **组合的顺序有判据，不是「看情况」。** 先量化后剪枝与先剪枝后量化是否同解，由 **scale 的作用域**（逐张量 / 逐组）与 **top-k 边界是否出现并列**共同决定；正文须给出**可机械判定的条件**，而不是「两者可以组合」这类无信息量的句子（判据与它的失效边界见 [overview/03](overview/03-composition-and-selection.md)）。

5. **引用值与本机实测值分档。** 厂商与论文的倍率标为**引用值**并附其测量条件（硬件 / batch / 精度）；本库程序算出的标为**推导值**；真 `torch` 上跑出的标为**本机实测值**并写明版本。三档不得混用。
