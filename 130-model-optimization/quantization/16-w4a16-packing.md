# W4A16 的打包布局：一个字节装两个值，换来了什么

> int4 省下的是**载荷**（每个权重 0.5 字节），但这份节省被两样东西吃掉：**元数据**（每 `gs` 个权重一个 fp32 scale + 一个 fp32 zero-point）和**打包布局**——一个字节装两个值，于是**每个元素的读取都多了一次 `& 0xF` 与一次 `>> 4`**。★ 本篇的核心是**把本机 CPU 上那个 int4 kernel 的布局逐字节反解出来**：低/高半字节**沿 N（输出通道）配对，不是沿 K 相邻配对**——这一条换两种解释会给出不同的字节，而实测能判出胜负。还有那条最硬的反证：**喂给转换器的必须是「有符号值 + 8」；不 +8 时 maxdiff 从 0 跳到 10²–10³ 量级，且不崩、不 NaN。**

## 0. 背景与动机

### 0.1 一个具体的对照场景

一个 `[4096, 4096]` 的权重层：

| 精度 | 载荷 | 相对 fp16 |
|---|---|---|
| fp16 | 32 MiB | 1× |
| int8 | 16 MiB | 0.5× |
| **int4** | **8 MiB** | **0.25×** |

int4 看起来是最划算的。但「每个权重 0.5 字节」这个数**只是载荷**——真实的存储还要加上：

| 项 | 判据 | gs=32 | gs=128 | gs=256 |
|---|---|---|---|---|
| group scale（fp32） | 4 B / gs | 0.125 B/元素 | 0.031 | 0.016 |
| zero-point（fp32） | 4 B / gs | 0.125 B/元素 | 0.031 | 0.016 |
| **元数据合计** | 8 B / gs | **0.25 B/元素** | **0.0625** | **0.031** |
| 相对载荷（0.5 B/元素） | — | **+50%** | **+12.5%** | **+6.25%** |
| 等效位宽 | `8 × (0.5 + 8/gs)` | 6.0 bit | 4.5 bit | 4.25 bit |

**⇒ 「int4」这个名字在 gs=32 时其实是 6 bit/权重。** 这就是本主题主线（**省下的字节去哪了**）在这一篇里的第一笔账。

### 0.2 第二笔账：一个字节装两个值，读的时候要还回去

`wp` 的形状是 `[N, K/2]`——**每字节两个 nibble**。要取出一个元素，得先算它在哪个字节、以及取低半字节还是高半字节：

```
byte = wp[i, j]
q    = byte & 0xF          # 低半字节
q    = (byte >> 4) & 0xF   # 高半字节
```

**省下的是存储字节，不是索引次数。** 元素总数一个不少（`N×K` 个），每个元素都多了一次位运算。而且——见 §1——**「哪个元素装在哪个 nibble 里」这件事不是显而易见的**。

## 1. 原理

### 第一步：调用契约（本机在 torch 2.11.0 上完整跑通）

```python
v   = torch.randint(-8, 8, (N, K), dtype=torch.int32)               # 有符号 int4 权重
wp  = torch.ops.aten._convert_weight_to_int4pack_for_cpu(v + 8, 2)  # uint8 [N, K//2]  ★ 必须 +8
qsz = torch.stack([scales, torch.zeros_like(scales)], -1).contiguous()  # [K//gs, N, 2]
out = torch.ops.aten._weight_int4pack_mm_for_cpu(x, wp, gs, qsz)    # [M, N]
```

四个实参各自的口径：

| 实参 | 形状 / 类型 | 含义 |
|---|---|---|
| `x` | `[M, K]` fp32（或与 `qsz` 同 dtype） | 激活，**必须 2D** |
| `wp` | `[N, K//2]` **uint8** | 打包后的权重 |
| `qGroupSize` | int，∈ `{32, 64, 128, 256}` | 量化粒度 |
| `qsz` | `[K//gs, N, 2]` | 最后一维 = `(scale, zero_point)` |

### 第二步：解包数学

```
dequant = scale · (q − 8) + zero_point          q ∈ [0, 15] 是无符号 nibble
```

本机实测（判据：`zp ~ randint(-3,4)`、形状 `[K//gs, N]`）：输出与这个**逐元素**形式的 maxdiff = **3.814697e-05**；而与「zp 每组只加一次」形式的 maxdiff = **1.48e+02**——**差 6 个数量级**。

> ★ **这是 W4A16 的 zero-point 用法：逐元素 `(q − z)`。**
> 而 `15-w8a8` §1 第四步那个「`Σx` 列和修正」的形式，**在官方文档里只有 W8A8 的激活侧版本**。
> **不得把「Σx 列和修正」写成 W4A16 的标准做法。**
> 独立的源码证据（**逐字读到**，见「参考」）：vLLM 的 machete `Readme.md` 写着
> `out = (w_q.to(scale_type) * w_s - w_z.to(scale_type)) @ a`——也是逐元素。

### 第三步：为什么要先 `+8`

这是本篇最容易写错的一步，也是**判据最硬**的一步：

- **转换器**只做 `输入 & 0xF`——它把输入的**低 4 位**当作 nibble 存下去，不关心符号；
- **mm 算子**在解包时**减 8**——它假定 nibble 是「有符号值 + 8」得到的无符号偏移。

两者合起来，**喂进转换器的必须是有符号值 + 8**。

**不 +8 会发生什么**：对每个有符号值 `v ∈ [−8, 7]`，读回来的是 `(v & 0xF) − 8`。逐项看：

| `v` | `v & 0xF` | 读回 `(v&0xF)−8` | 偏差 |
|---|---|---|---|
| −8 | 8 | 0 | **+8** |
| −1 | 15 | 7 | **+8** |
| 0 | 0 | −8 | **−8** |
| 7 | 7 | −1 | **−8** |

**偏差恒为 ±8**，而且**它是一个双射**（16 个取值 ↦ 16 个不同结果）——所以**不崩、不 NaN、不报错，只是每个权重都错了 8**。

这正是它危险的地方：误差按 `K` 累积（`|Δout| ≤ 8·Σ_j |x_j|·s`），在大矩阵上是 10²–10³ 量级。

### 第四步：打包布局——低/高半字节沿哪个方向配对

`wp[i, j]` 一个字节装**两个**权重元素。问题是：**哪两个？**

两个候选解释：

| 解释 | 配对方向 | 直观程度 |
|---|---|---|
| **A** | 沿 **K 相邻**配对：`wp[n, k//2]` 装 `k` 与 `k+1` | 直觉上最自然（一个字节管两个相邻的输入通道） |
| **B** | 沿 **N** 配对：低/高半字节落在**相邻的两个输出通道**上 | 本机实测的这一个 |

**两者都是合法的双射**（都能把 `N×K` 个元素恰好放满 `N×K/2` 个字节）——所以「自己跟自己自洽」**判定不了**。必须拿**事实**去判。

**本机逐字节反解出来的公式**（判据见 §5.2）：

```
wp 的形状是 [N, K//2]。下标 (i, j) 处的字节装两个元素：
  低半字节 ←  n = 16·(i//16) + 2·(j%8) + 0,   k = (K//16)·(i%16) + (j//8)
  高半字节 ←  n = 16·(i//16) + 2·(j%8) + 1,   k = (K//16)·(i%16) + (j//8)
```

反过来的（解包方向）：

```
i = 16·(n//16) + k // (K//16)
j = 8·(k % (K//16)) + (n%16)//2
nibble = n % 2                  # 0 = 低半字节，1 = 高半字节
```

**结构上在说什么**：`k` 被切成两组——`i % 16` 走的是 `k // (K/16)`（**K 方向按 16 块跨步**），`j // 8` 走的是 `k % (K/16)`。而 `i // 16` 与 `j % 8` 一起决定 `n`。用一句话说：**这个布局是按「16 个输出通道一组、每组内 8 个元素一包」重排过的**。

> ★ **这就是权重预重排（weight pre-shuffling）在 CPU 侧的最小对应物。**
> 主流 GPU kernel 的 prepacking 是为了让 tensor core 的 `ldmatrix` 能 128-bit 加载
> （**4-bit 没有 `ldmatrix` 指令**，见 `17-kernel-design`）；这里没有 tensor core，但
> **「把数据重排成硬件要的样子」这件事是一样的**——代价是**离线的一次重排 + 一个不直观的索引公式**。

## 2. 执行映射

### 2.1 三个组件名与一个数值量级

- **转换器 `_convert_weight_to_int4pack_for_cpu(w, innerKTiles)`** —— 离线跑一次，产出 `[N, K//2]` 的 uint8。它只做 `& 0xF`。
- **`qsz`（`[K//gs, N, 2]`）** —— 每组一个 `(scale, zero_point)`。`gs=128`、`N=4096`、`K=4096` 时是 **131 072 组 × 2 × 4 B = 1 MiB**。
- **mm 算子 `_weight_int4pack_mm_for_cpu`** —— 解包 + 逐元素 `(q − 8)` + 乘 scale + 累加，一次调用完成。
- **量级**：一个 `[4096, 4096]` 层的 int4 载荷是 **8 MiB**；若把它反量化成 fp16 写回，是 **32 MiB**——**写是读的 4 倍**（与 `15-w8a8` §2.2 同一笔账）。

### 2.2 「省下的字节」与「付出的运算」

| | int4 打包 | fp16 |
|---|---|---|
| 存储 | 0.5 B/权重 | 2 B/权重 |
| 取一个元素 | **1 次 `& 0xF` 或 1 次 `>> 4` + 1 次 `& 0xF`** | 直接读 |
| 索引 | **一次公式换算**（§1 第四步） | `w[n, k]` |
| 额外元数据 | `8 B / gs` | 无 |

**⇒ 「一个字节装两个值」省的是存储，不是运算。** 这笔交易的收益取决于**这个 kernel 是存不下还是算不动**：
W4A16 的 decode 阶段是**访存受限**的（**引用值**：attention 的算术强度 `ST/(S+T)`，
decode 时 `S ≫ T = 1` ⇒ 趋近 **1**；**这是 attention 部分的结论，不能直接外推到整个模型**），
所以用存储换运算是划算的——**但它是有限的划算**。

## 3. 实现与演进

**第一代：`[N, K]` 的 int8 张量 + 逐元素反量化。** 不打包，每个权重占一整个字节。取元素没有任何位运算。

- 代价：存储是 int4 的两倍。收益：布局直观，任何人看一眼就懂。

**第二代：nibble 打包（沿 K 相邻）。** `wp[n, k//2]` 装 `k` 与 `k+1`——这是「最自然的」打包方式，很多手写实现就这么做。

- 代价：无。收益：存储减半。
- 为什么不够：它**没有为硬件的加载指令做重排**。GPU 上 `ldmatrix` 不支持 4-bit，naive 布局要让每个线程做多次 8-bit load 才能拼出 tensor core 要的寄存器布局。

**第三代：面向硬件的 per-shuffle 布局（本机实测的这一种）。** 把权重按「硬件要的样子」重排——本机 CPU 这个 kernel 选的是**沿 N 配对**，并把 `k` 按 16 块跨步。

- 收益：一次 128-bit 加载就能填满一个 tile（GPU 侧；CPU 侧的好处是同一份数据被多个输出通道复用）。
- 代价：**索引公式不再直观**，而且离线要跑一次重排（转换器）。

**第四代：把 scale 也融进去。** `qsz` 把 `(scale, zero_point)` 和权重分开存，但**在 kernel 内部**逐元素应用（§1 第二步）。

- 这一步与 `15-w8a8` 的 epilogue 融合是同一个思路：**反量化后的权重不落回 HBM**。

## 4. 踩坑与失败模式

### 4.1 不 `+8`

**现象**：`maxdiff` 从 **0** 变成 **10²–10³ 量级**，程序不崩、不 NaN、不报错。

**成因**：转换器只做 `& 0xF`，而 mm 算子解包时减 8。直接喂有符号值时，每个元素读出的偏差恒为 **±8**（§1 第三步的表）。

**规避**：**喂 `v + 8`**。判据（本机实测，判据是把参照钉死的那三条）：

| `(N, K, gs)` | `+8` 的 maxdiff | 不 `+8` 的 maxdiff |
|---|---|---|
| (16, 32, 32) | **0.0** | 263 |
| (64, 128, 32) | **0.0** | 656 |
| (128, 256, 128) | **0.0** | 1048 |
| (256, 512, 256) | **0.0** | 1648 |
| (64, 1024, 256) | **0.0** | 2209 |

> ⚠ **计划基线写的「不 +8 时 maxdiff = 3.389e+01」是另一组 `x`/`scale` 下的值**（本表用的是整数值的 `x`，量级更大）。**两者都对，但不是同一个量**——判据不同 ⇒ **不得并列**。

### 4.2 把 `maxdiff = 0` 当成「这个算子更准」

**现象**：文档里写「实测 maxdiff 恰好为 0，说明这个 kernel 是精确的」。

**成因**：这个 **0 是「输入挑得好」的结果，不是算子的性质**。判据必须一起写出来：

1. `x` 是**整数值** fp32（`randint(-4, 5, (4, K)).float()`）；
2. `scale = 1.0`、`zero_point = 0.0` ⇒ 反量化后的权重是小整数；
3. 参照 = **int64 精确值**，不是 fp32 matmul。

此时每一项乘积与**每个部分和**都是绝对值 < 2²⁴ 的整数，在 fp32 里**逐位精确** ⇒ **任何累加顺序都给出同一个结果**。所以 0 与形状无关。

**规避**：把判据写出来，并**再跑一次反证**——同一个算子、换成 `randn` 的 `x` 与 fp32 的逐组参照，maxdiff 立刻变成 **~1e-6**（本机实测 2.384186e-06）。

> **⇒ 三个数（0 / 2.4e-06 / 656）都能在同一个算子上复现，区别只在判据。**

### 4.3 把 `qsz` 的主维当成有校验的

**现象**：以为「`qsz` 必须是 `[K//gs, N, 2]`」这条约束和另外几条一样会抛异常。

**成因**：**它不抛。** 本机实测：主维**过短**（1 组而实际需要 4 组）不报错，结果要么是 NaN 要么是错值（取决于读到的越界内容）；主维**过长**（多 3 组）不报错，给出静默错值。

**规避**：把这条单列成**「错了不报」**的一类。被校验的只有 `qsz` 的 **ndim** 与第 2 维：

```
RuntimeError: _weight_int4pack_mm_cpu: expect qScaleAndZeros to be 3d tensor with sizes [:, 32, 2]
```

> ⚠ 注意这句里的 `[:, 32, 2]` 是**把实际 N 代进去打印的**。把这个 `32` 当成字面量引用，就是 P9 的形状（同一句话里两个 N 不是同一个量）。

### 4.4 以为五条约束是一起出现的

**现象**：写「违反约束会抛异常」，一条一句带过。

**成因**：`K` 被 `gs` 整除这一条**是版本相关的**——本机实测：**torch 2.6.0 上不抛、静默跑过**；2.7.1 起抛
`expect K to be divisible by qGroupSize, got K:192, qGroupSize:128`。

**规避**：写「约束会抛异常」时**带上版本**，或把每条约束的实测原文抄下来（本文 §5.4 就是）。

### 4.5 把「沿 K 相邻配对」当成唯一可能的布局

**现象**：反解布局时直接从「相邻两个 k 装一个字节」出发。

**成因**：这个解释**自洽**（它也是双射），所以写代码时不会报错——只是解出来的权重全错。本机实测：对 `N=64, K=256`，这种解释有 **7663 / 8192** 个字节对不上。

**规避**：**用真数据判**。`verify_kernels.py` 的 A.1 把「从真 torch 抄下来的 512 字节」与文档公式逐字节比；A.1c/A.1d 专门断言**另一种解释也是合法双射但与事实不符**——**这就是「这份样本集能区分两种解释」的判据本身**。

## 5. 实测数据

**测量条件**：Apple M1 Pro（10 核）/ macOS / **CPU-only，无 GPU 数字**；python 3.12.9；**torch 2.11.0**。五个解释器（2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 / 2.13.0）都跑过本篇的程序；`2.9 / 2.10 / 2.12` 本机无解释器。数值逐条记在 `code/specs_kernels.py`。

### 5.1 完整调用契约（判据：`N=32, K=128, gs=32, M=4`）

| 量 | 实测 |
|---|---|
| `wp` 形状 / dtype | `[32, 64]` / `torch.uint8` |
| `qsz` 形状 | `[4, 32, 2]`（= `[K//gs, N, 2]`） |
| `out` 形状 / dtype | `[4, 32]` / `torch.float32`（与 `x` 同） |
| 约束 | `N % 16 == 0`、`gs ∈ {32,64,128,256}`、`K % gs == 0`、`w` 是 uint8、`x` 是 2D、`qsz` 与 `x` 同 dtype |

### 5.2 ★ 逐字节布局反解（本篇的核心实测）

**判据**：造一张 `q = (v + 8) & 0xF` 的 `[N,K]` nibble 表，与 `wp` 的**每个字节**对比。

| `(N, K)` | 错字节数 | 覆盖元素数（应 = `N×K`） |
|---|---|---|
| (32, 32) | **0 / 512** | 1024 / 1024 |
| (64, 256) | **0 / 8192** | 16384 / 16384 |
| (16, 128) | **0 / 1024** | 2048 / 2048 |

**两种候选解释的对比**（`N=64, K=256`）：

| 解释 | 错字节数 |
|---|---|
| 沿 K 相邻配对 | **7663 / 8192**（在 `N=64,K=256` 上） |
| **沿 N 配对（文档这一种）** | **0 / 8192** |

> **⇒ 这份样本集有区分力**：两种解释给出不同答案，实测判出胜负。

### 5.3 ★ 「不 +8」的反证（判据：整数 `x`、`scale=1`、`zp=0`、int64 精确参照）

| `(N, K, gs)` | `+8` | 不 `+8` |
|---|---|---|
| (16, 32, 32) | **0.0** | 2.63e+02 |
| (64, 128, 32) | **0.0** | 6.56e+02 |
| (64, 128, 64) | **0.0** | 6.56e+02 |
| (128, 256, 128) | **0.0** | 1.048e+03 |
| (256, 512, 256) | **0.0** | 1.648e+03 |
| (64, 1024, 256) | **0.0** | 2.209e+03 |

**闭式解释**：偏差恒为 ±8（§1 第三步），误差上界 `8·Σ_j |x_j|·s`。

> ⚠ **反证一：同一个算子、换成 `randn` 的 `x` 与 fp32 的逐组参照 ⇒ maxdiff = 2.384186e-06 ≠ 0。**
> ⇒ 上面那一列 0 是**输入的产物**，不是算子的性质。

### 5.4 五条约束的异常原文（本机逐条抄下）

| 违反 | 2.11.0 的异常原文 | 2.6.0 |
|---|---|---|
| `N = 24`（非 16 倍数） | `_convert_weight_to_int4pack_cpu : expect N to be dividable by 16` | 同 |
| `gs = 48` | `_weight_int4pack_mm_cpu: expect qGroupSize to be 32, 64, 128 or 256, got 48` | 同 |
| `K = 192` 不被 `gs = 128` 整除 | `expect K to be divisible by qGroupSize, got K:192, qGroupSize:128` | **不抛** |
| `qsz` 是 2D | `expect qScaleAndZeros to be 3d tensor with sizes [:, 32, 2]` | 同 |
| `w` 是 int32 | `_weight_int4pack_mm_cpu : expect B to be uint8 tensor.` | 同 |
| `x` 是 1D | `IndexError: Dimension out of range (expected to be in range of [-1, 0], but got 1)` | 同 |
| **`qsz` 主维不对** | **不抛**：过短出 NaN 或错值（取决于数据），过长给出静默错值 | 同 |

### 5.5 `innerKTiles` 这个实参

判据：`v = randint(0, 16, (64, 256))`，`innerKTiles ∈ {1, 2, 4, 8}`。

| `innerKTiles` | 输出形状 | 与 `t=2` 逐字节相同？ |
|---|---|---|
| 1 | `[64, 128]` | **是** |
| 2 | `[64, 128]` | — |
| 4 | `[64, 128]` | **是** |
| 8 | `[64, 128]` | **是** |

**⇒ 本机这四档给出逐字节相同的输出**（在这一个形状上）。文档沿用 `2` 是**取这个值**，不是「只有它可用」。

### 5.6 zero-point 的用法（判据：`zp ~ randint(-3,4)`、形状 `[K//gs, N]`）

| 解释 | maxdiff |
|---|---|
| **逐元素 `s·(q−8) + zp`** | **3.814697e-05** |
| zp 每组只加一次 | 1.48e+02 |

**⇒ W4A16 用逐元素、不用列和修正。** 独立的源码证据（**逐字读到**）：vLLM 的 machete `Readme.md` 写着 `out = (w_q.to(scale_type) * w_s - w_z.to(scale_type)) @ a`，并注明 *"`w_z` is added after the scales so we can use FMA operations"*（**⇒ zero-point 必须预先乘过 scale**）。

### 5.7 引用值

| 项 | 值 | 出处 |
|---|---|---|
| 元数据的等效位宽 | `8 × (0.5 + 8/gs)` bit | **推导值**（本仓库算术） |
| 独立反量化 pass 的写/读比 | 4× | **引用值**（0.5 B/元素读 → 2 B/元素写） |
| 4-bit 没有 `ldmatrix` 指令 | —— | **引用值**：Red Hat Developer 的 Machete 官方介绍（本实现者**逐字读到**：「However, this instruction isn't available for 4-bit types」） |
| Machete 的 zero-point 形式 | 逐元素 | **引用值**：vLLM `csrc/quantization/machete/Readme.md`（**逐字读到**，2672 字节） |

## 6. 小结与延伸

- **int4 省下的是载荷（0.5 B/权重）**，但元数据（`8 B / gs`）把它吃回去一部分：**gs=32 时等效 6.0 bit/权重**，gs=256 时 4.25 bit。**判据：`8 × (0.5 + 8/gs)`。**
- **一个字节装两个值省的是存储，不是运算**：元素总数不变，每个元素多一次 `& 0xF` / `>> 4`，还要一次索引换算。
- ★ **打包布局是「沿 N 配对」，不是「沿 K 相邻配对」**——低/高半字节落在**相邻的两个输出通道**上。本机在三个形状上逐字节验证（错字节 0 / 512、0 / 8192、0 / 1024），而另一种解释错 7663 / 8192。
- ★ **必须喂 `v + 8`**：转换器只做 `& 0xF`、解包时减 8 ⇒ 不 +8 时每个元素偏差恒为 **±8**，`maxdiff` 从 **0** 跳到 **10²–10³**，而且**不崩、不 NaN、不报错**。
- ⚠ **那个 `maxdiff = 0` 是判据的产物，不是算子的性质**：整数 `x` + `scale=1` + `zp=0` + int64 精确参照 ⇒ 所有部分和在 fp32 里逐位精确，**任何累加顺序都一样**。换成 `randn` 的 `x` 与 fp32 参照，同一个算子给 **2.384186e-06**。
- **W4A16 的 zero-point 是逐元素的**（maxdiff 3.8e-05，而「每组加一次」是 1.48e+02）。**「`Σx` 列和修正」只有 W8A8 的版本，不得写成 W4A16 的标准做法。**
- ⚠ **`qsz` 的主维没有校验**：过短出 NaN 或错值、过长给静默错值。它是这套契约里**唯一一条「错了不报」的约束**。
- ⚠ **`K % gs` 这条校验是版本相关的**：2.6.0 不抛，2.7.1 起抛。

**延伸**：

- `scale` 在粒度上的取舍（per-tensor → per-channel → per-group 各自换回多少精度）在 `130-model-optimization/quantization/06-granularity`。
- 这些 int4 组是**怎么算出来的**（GPTQ 的逐列补偿、group size 对输出误差的影响）在 `130-model-optimization/quantization/09-gptq`。
- 这份布局在真实 GPU kernel 上对应的是什么（pre-shuffling / `ldmatrix` / TMA）在 `17-kernel-design`。
- GEMM 本身的 tiling 与流水线在 `40-kernels/gemm`（**正文在本域，回链 `40-kernels`**）。
