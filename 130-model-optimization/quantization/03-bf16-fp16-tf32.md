# bf16 / fp16 / tf32 的量化视角：为什么浮点量化不需要 clipping

> 定点量化的第一课是「**要裁剪**」——不裁的话一个离群值就能把 scale 撑大，让其余值掉进个位数的有效级数里。而浮点量化**不需要**这件事，理由不是「clipping 在浮点上没用」，而是**浮点的相对误差与数据尺度无关**：同一批数据换成重型长尾，SQNR 只掉 1 dB 左右。这个对照正是本文的主线。

## 0. 背景与动机

**本文不复述位域表。** bf16 / fp16 / fp8 / tf32 的位域、范围与**累加器宽度**，正文在 [10-foundations/floating-point/04-low-precision-formats](../../10-foundations/floating-point/04-low-precision-formats.md)；按 CONTRIBUTING §7「一个知识点只有一处正文」，判据是「去掉量化层，位域定义还成立吗」——**成立**，所以位域归那一篇。本文从这里开始回链，只讲**量化视角**的东西。

**两篇讲的是两个不同的误差来源，不是同一件事的两个深浅：**

| | 那一篇 | 本篇 |
|---|---|---|
| 讲什么 | **累加误差**：同一个格式算得越多、误差怎么涨（`√K·u`） | **量化误差**：把连续值压到有限个格点上，误差有多大 |
| 自变量 | `K`（归约长度） | 数据的**分布**与格式的**尾数位数** |
| 典型结论 | 误差 ≲ `√K · u`；`u` 差 8192 倍 | SQNR ≈ `6.02 · (M+1) + 7.78` dB；跨分布极差 ≈ 1 dB |
| 修法 | 换累加器宽度、分块、补偿 | 换格式、调粒度、裁剪 |

**把这两条混在一起，就会在一个来源上调参去修另一个来源的问题**（那一篇 §4.1 把这条写成了失败模式）。本文一个累加都不做。

**一个具体的对照场景。** 有一批激活值，量级分布是重型长尾（§1 第三步用的 `StudentT(3)` 就是这一类），要把它压到 8 位。定点做法的第一反应是「先找 `max`，再决定裁多少」——因为**在定点上，`max` 直接决定 `Δ`，而 `Δ` 直接决定所有值的误差**。本文要给出的结论是：**在浮点上这个动作可以省掉**，因为浮点的误差主要由**尾数位数**决定，不由 `max` 决定。

## 1. 原理

### 第一步：浮点的量化误差长什么样

浮点格式的绝对误差**不是常数**，它随数值的指数走：设尾数 `M` 位，则

```text
在区间 [2^e, 2^(e+1)) 内：  ulp = 2^(e − M)
                            |误差| ≤ ulp / 2 = 2^(e − M − 1)     （RNE）
```

**关键性质是「相对误差与数值大小无关」**：把上式除以 `x`（`x ∈ [2^e, 2^(e+1))`）：

```text
|误差| / x  ≤  2^(e − M − 1) / x    ≤  2^(e − M − 1) / 2^e  =  2^(−M−1)
```

上界只依赖 `M`，**不依赖 `e`**。也就是说，**无论一个数落在 `1e-30` 还是 `1e+30`，它的相对误差上界都是同一个 `2^(−M−1)`**。这正是浮点与定点的分水岭——定点格式的 `Δ` 是**绝对**步长，`|误差| ≤ Δ/2` 这个界与数值大小无关，于是「一个大值」会把 `Δ` 整体推高、把「小值」的相对误差推爆。

**推论（本文的主线）**：如果在浮点上先裁剪到某个 `α` 再量化，`α` 变小只会让**大值的相对误差变大**（因为它们被裁掉了），而不会让**小值的相对误差变小**——因为小值的相对误差本来就已经在 `2^(−M−1)` 量级了。**浮点上没有「牺牲尾部换分辨率」这笔交易可做**，这笔交易的前提（步长是绝对的）在浮点上不成立。

### 第二步：解析式——一位尾数值多少 dB

设信号 `x`，量化误差 `e`。定义 `SQNR ≜ 10·log10(Σx² / Σe²)`。

假设尾数在 binade 内均匀（`x = u · 2^e`，`u ~ U[1,2)`）、误差在 `±ulp/2` 内均匀：

```text
RMS 绝对误差   RMS(e) = ulp / √12 = 2^(e−M) / √12

相对误差取 RMS（e 与 x 独立，可分开取）：
  RMS(e/x) = RMS(e) / 2^e · sqrt( E[1/u²] )
           = (2^−M / √12) · sqrt( ∫_1^2 u^−2 du )        ← ∫_1^2 u^−2 du = 1/2
           = 2^−M / √24

SQNR = 20·log10( 1 / RMS(e/x) )
     = 20·log10( √24 · 2^M )
     = 13.80 + 6.0206 · M
     =  7.78 + 6.0206 · (M + 1)          ← 两种写法完全等价
```

**结论：一位尾数值 6.02 dB，常数项约 7.78 dB。** 与定点那条著名的 `6.02B + 1.76` 相比，**斜率相同、常数不同**——差在「浮点的误差是相对步长、定点的误差是绝对步长」。这一点在 §4.1 会救一次命。

代入三个格式（`M` = 尾数位数）：

| 格式 | `M` | 解析 SQNR | 本机实测（`N(0,1)`） |
|---|---|---|---|
| `float8_e4m3fn` | 3 | 31.86 dB | **31.52 dB** |
| `bfloat16` | 7 | 55.95 dB | **55.59 dB** |
| `float16` | 10 | 74.01 dB | **73.65 dB** |

**实测与解析差都在 0.4 dB 以内，而且实测一律略低。** 这是合理的：解析式假设尾数在 binade 内均匀，真实数据的尾数分布不是均匀的。**这条只作量级校验，不是同一个量的两种测法。**

**与论文印值的交叉验证。** Kuzmin et al.（arXiv:2208.09225）Table 1 印的是 "BFloat-16 **55.6** dB / IEEE float-16 **73.7** dB"。本机 torch 2.11.0 在 `N(0,1)`、2×10⁶ 样本上测到 **55.59 / 73.65 dB**——**吻合到 0.1 dB 以内**。

> ⚠ 该论文的 SQNR 定义（信号/误差比的分母、样本集、分布）**本仓库未逐字核实**。所以这是「两个来源给出同一量级」的旁证，**不是「定义相同」的证明**。

### 第三步：★ 浮点 SQNR 与分布几乎无关

把同一套测量在四个分布上跑一遍（2×10⁶ 样本，torch 2.11.0）：

| 分布 | bf16 | fp16 | `e4m3fn` | tf32（仿真） |
|---|---|---|---|---|
| `N(0,1)` | 55.59 | 73.65 | 31.52 | 73.65 |
| `U(-1,1)` | **56.62** | 74.68 | **32.53** | 74.68 |
| `Laplace(0,1)` | 55.61 | 73.67 | 31.52 | 73.67 |
| `StudentT(3)`（截 ±1e3） | 55.61 | 73.69 | 31.51 | 73.69 |
| **跨分布极差** | **1.04 dB** | **1.03 dB** | **1.02 dB** | 1.03 dB |

**判据**：SQNR = `10·log10(Σx²/Σ(x−x̂)²)`；分布集就是上表四行（每行都带参数与截断）；`torch.manual_seed(20260918)`。

三件事值得说清：

1. **极差约 1 dB，不是 0 dB。** 从 `N(0,1)` 到 `U(-1,1)` 差 1.03–1.04 dB。原因是 `U(-1,1)` 里 |x| 更接近 1，落在 binade 的上半段（相对误差更小），而 `N(0,1)` 有大量小值落在各 binade 的下半段。**这是一个真实的、可解释的偏移，不是噪声。**
2. **⚠ 不要写「< 1 dB」。** 55.59 → 56.62 就是 1.03。**也不要给一个笼统区间。** 两个端点（`N(0,1)` 与 `U(-1,1)`）是稳的——控制者与审查者独立复现一致；**中间值随分布集变化**。引用时**给端点 + 说明分布集**。
3. **跨版本一致。** 这张表在 torch **2.6.0 / 2.11.0 / 2.13.0** 三个解释器上**逐格相同**（同一 seed、同一 RNG 流）。这是「换一个版本同一个数还是同一个数」的一个正面例子——与 [01-fp8-family](01-fp8-family.md) 那个溢出断点恰成对照。

**对照定点：同一格式跨场景可差 20+ dB。** 定点格式的 SQNR 强相关于分布——[06-granularity](06-granularity.md) 那张粒度表里，同一个 8-bit 格式在不同场景下差到 20 dB 以上。**所以讨论「`6.02n + 1.76` 适不适用」之前，必须先说清是定点还是浮点，否则两个结论会打架。**

### 第四步：★ 这就是「浮点量化不需要 clipping」的答案

把第二步与第三步合起来：

```text
定点：|误差| ≤ Δ/2，Δ = (b − a)/2^B  ← a、b 是数据的 min/max
      → 一个离群值把 (b−a) 撑大，Δ 变大，**其余所有值**的误差一起变大
      → 所以要做「最优 clipping」：牺牲尾部、换更小的 Δ

浮点：|误差|/x ≤ 2^(−M−1)  ← 只跟 M 有关，与数据的 min/max 无关
      → 一个大值不会影响小值的相对误差
      → **没有「牺牲尾部换分辨率」这笔交易可做**
```

第三步的实测表就是这句话的数值形式：**换成重型长尾（`StudentT(3)`）之后，bf16 的 SQNR 只从 55.59 掉到 55.61**（`U(-1,1)` 那 1 dB 的偏移来自 |x| 的位置，不来自尾部）。如果换成定点，同一批数据会掉 20 dB 以上。

> **⚠ 准确的说法是「浮点量化不需要 clipping」，不是「clipping 在浮点上没用」。** 后者是错的：`x = ±inf` 或超出格式范围的值仍然要被处理（`clamp` 到格式的 `max`）。**不需要的是「最优 clipping 那套『用一个低于 max 的阈值换取更小的步长』的逻辑」**——因为浮点上不存在「更小的步长」这个可调的旋钮，步长已经由指数自动定好了。

### 第五步：四个格式在量化场景下的取舍

位域与范围见 [10-foundations/floating-point/04](../../10-foundations/floating-point/04-low-precision-formats.md)，这里只从**量化**的角度排一遍：

| 格式 | `M` | 实测 SQNR（`N(0,1)`） | 作为**存储格式**用于量化时 |
|---|---|---|---|
| `float8_e4m3fn` | 3 | 31.52 dB | 主要选择。范围 ±448 够 WL 场景的权重与激活 |
| `float8_e5m2` | 2 | 25.55 dB | 少 6 dB，换来 9 个数量级的范围；**溢出不落 NaN**（它有 Inf） |
| `bfloat16` | 7 | 55.59 dB | 与 fp16 同为 16 位，少 3 位精度（18 dB）、**量程跨度多 67.5 个数量级** |
| `float16` | 10 | 73.65 dB | 精度最高，范围最窄（±65504） |
| tf32 | 10 | 73.65 dB（**仿真**） | **不是存储格式**，只在矩阵乘输入端截尾数 |

**三条来自这张表的取舍规则**：

1. **`bfloat16` 与 `float16` 的取舍是「范围 vs 精度」，而且天平明显偏向前者。** 同样是 16 位容器，fp16 精度高 **18.06 dB**（3 位 × 6.02），bf16 的**量程跨度宽 67.5 个数量级**（76.5 vs 9.0；`2^-126` vs `2^-14` 只是其中「最小正规数」那一段的 33.7 个数量级，两个数**不是同一个量**，不要混用）。对**权重与激活**（量级集中在几十分贝内）fp16 明显更好；对**梯度**，**归零下限那 33 个数量级的差距**是决定性的——这是 loss scaling 存在的全部理由，正文在 [10-foundations 那一篇](../../10-foundations/floating-point/04-low-precision-formats.md) §3。
2. **`e4m3fn` 与 `e5m2` 的取舍在小数点后另一位。** 差 6 dB 对量化结果通常可接受，而 9 个数量级的范围差在「一个张量里混着多个量级」时是救命的。**这也是 MX 规范同时保留两个元素格式的理由**（[02-e8m0-and-mx](02-e8m0-and-mx.md)）。
3. **tf32 不能当存储格式用。** torch 里根本没有 `torch.tf32` 这个 dtype——它是「fp32 矩阵乘在输入端截到 10 位尾数」的**行为**，不是一个可以分配的格式。**所以「把权重存成 tf32」这件事不存在**；tf32 的量化讨论只在「矩阵乘的输入精度」这一层。

### 第六步：一个实现细节——bf16 与 fp16 的入口精度不同

这一条是本仓库实测发现的，写在原理节里是因为它**改变数值结果**：

- `float64 → float16` 是**单次舍入**：与「按 10 位尾数直接 RNE」逐元素相同（20 万样本，含 9 个次正规样本，**0 处不一致**）。
- `float64 → bfloat16` 是**双重舍入**：它与「先转 fp32、再转 bf16」逐元素相同；而与「按 7 位尾数直接 RNE」有 2 处不一致。

**具体反例**（`code/03_bf16_fp16_tf32.py` §A4 打印）：

```text
x = 1.4257812575996542392
  float64 → bf16 直转     = 1.421875
  float64 → fp32 → bf16   = 1.421875
  单次 7 位 RNE（手写）    = 1.4296875     ← 不同

x = -2.1953125050592809941
  同理，直转与经 fp32 都是 -2.1875，单次 RNE 是 -2.203125
```

机理：`x` 的**第 8 位尾数是 1、其余全 0**——在 float64 里它不是平局（`x · 2^7 = 182.50000097275574`），但在 **float32** 里它恰好被截成 `1.01101101₂`（8 位尾数），于是对 7 位 RNE 来说**变成了精确平局**，取偶后向下。

**所以「fp32 → 16bit 是 RNE」这句话里的「中间精度」也要写清**：bf16 的入口是 **fp32**，fp16 的入口是 **fp64 → fp16 单次**。对从 fp32 出发的实际训练/推理负载，这条差异不存在；但对从 fp64 生成测试数据的实验，它会让「手写参考实现」与 torch **差几个元素**——排查时值得先想到这里。

## 2. 执行映射

**这一节的落点是「这个 cast 在 ATen 里走哪条路、以及它的中间精度从哪来」。** §1 第六步的差异根源就在这里：

| 转换 | ATen 路径 | 中间精度 |
|---|---|---|
| `float64 → bfloat16` | 经 **fp32** cast kernel | **fp32**（7 位尾数的入口是 23 位） |
| `float64 → float16` | 直接 cast | **fp64**（单次舍入） |
| `float32 → bfloat16/float16` | 直接 cast | fp32 |
| tf32（矩阵乘输入） | **不存在 cast 路径** | 由 GEMM kernel 内部截断 |

**判据**：`x.to(torch.bfloat16)` 与 `x.to(torch.float32).to(torch.bfloat16)` 在 20 万样本上**逐元素相同**；`x.to(torch.float16)` 与 `x.to(torch.float32).to(torch.float16)` **有 11 处不同**。这说明 bf16 的入口是 fp32、fp16 的不是。

**tf32 的落点完全不同，而且本机测不了。** tf32 是「fp32 矩阵乘在**输入端**把尾数截到 10 位」，累加仍在 fp32 里做——这句话的两个动作在**两个不同的时刻**发生，而文档里经常被合并成一句「tf32 的精度是 10 位尾数」。

> **★ 一个必须如实留下的空格：tf32 的输入转换舍入模式。** 两处来源冲突，且「输入转换的舍入」与「累加过程的舍入」**可能就是两件事**；torch 里**没有 tf32 存储 dtype**，本机又只有 CPU，**跑不了真 TF32**。
> **这一格写「未解决」，不给一个看起来合理的答案。** 篇名里带着 `tf32` 不等于它必须有结论——**「这一格我们不知道」本身就是可交付的内容。**

**数值量级：**

| 量 | 数值 | 来源 |
|---|---|---|
| `bf16` 尾数位 | **7**（不是 8） | 本机 `finfo`，五个版本一致 |
| `bf16` 的 eps | `2^-7` = 0.0078125 | 同上 |
| `fp16` 的 eps | `2^-10` = 0.0009765625 | 同上 |
| `bf16` / `fp16` 的 SQNR 差 | **18.06 dB**（3 位 × 6.02） | 实测 18.06 / 18.04 dB |
| 跨分布极差 | **≈1 dB** | 实测 1.02–1.04 dB |

## 3. 实现与演进

**float32 全精度。** 没有量化误差，只有 fp32 自己的舍入（`u = 5.96e-08`）。代价是存储与带宽。

**fp16 存储。** 精度足够（73.65 dB），但范围只有 ±65504 与 `2^-14` 的最小正规数。用在**推理的权重与激活**上通常足够；用在**梯度**上会下溢——那属于累加/混合精度那条线（[10-foundations 那一篇](../../10-foundations/floating-point/04-low-precision-formats.md) §3），本文不展开。

**bf16 存储。** 用 3 位精度（18.06 dB）换 67.5 个数量级的量程跨度。**从量化视角看这是一次「精度换范围」的干净交易**，而且在**量化**场景下它有一个额外优势：bf16 的 `M = 7` 已经比任何 fp8 都宽，所以 bf16 量化通常不需要再叠一层块缩放——这正是 MX 这套东西存在的理由（[02](02-e8m0-and-mx.md)）。

**fp8 + 微缩放。** 走到 8 位，`M` 掉到 2–3 位，全局 scale 盖不住张量内的量级跨度，于是引入**块级共享指数**。**这一步是「格式设计对象从『一个数』变成『一组数』」的转折点**——量化误差的分析对象不再是单个元素，而是「块内相对最大值」的分布（[02](02-e8m0-and-mx.md) §1 第四步那 17%–30% 的溢出率就是它）。

**tf32。** 它不在这条演进线上——它不改变存储，只改变**矩阵乘输入端的精度**。代价是 fp32 矩阵乘的精度静默掉到 10 位尾数，收益是零代码改动就能用上 Tensor Core。

**前沿：浮点量化与定点量化正在合流。** MX 的元素格式里既有 `E4M3`（浮点）也有 `INT8`（定点），它们**共用同一个 E8M0 的块 scale 机制**。也就是说「浮点 vs 定点」这个二分在微缩放这一层已经被绕开了——**scale 的粒度成了更基本的变量**。

## 4. 踩坑与失败模式

### 4.1 拿定点的「6.02n + 1.76」去算浮点的 SQNR

**现象**：给一个 8 位的浮点格式估 SQNR，顺手用 `6.02 × 8 + 1.76 = 49.9 dB`，算出来的比实测高 **18 dB**。

**成因**：那条公式的 `n` 是**总位数**（定点上每一位都是有效位），而浮点的 `n` 里有一部分被指数占掉了。正确做法是把它换成**尾数位数**，并把常数换成浮点的那一个：

```text
定点：SQNR ≈ 6.02 · B        + 1.76     （B = 总位数）
浮点：SQNR ≈ 6.02 · (M + 1)  + 7.78     （M = 尾数位数）
```

**斜率相同（6.02 dB/bit），常数不同（1.76 vs 7.78）。** 对 `e4m3fn`（`M = 3`）：`6.02 × 4 + 7.78 = 31.86 dB`，实测 31.52 dB。**用错公式会得到 49.9 dB，差 18 dB。**

**规避**：**先说清是定点还是浮点，再选公式。** 更稳的做法是记住公式的**来源**：定点那条来自「误差在 `±Δ/2` 内均匀、信号是满量程正弦」；浮点这条来自「相对误差在 `±2^(−M−1)` 内、尾数在 binade 内均匀」。**两个前提不一样，公式就不能互换。**

### 4.2 把「浮点不需要 clipping」读成「浮点的 clip 阈值随便设」

**现象**：既然结论是「不需要 clipping」，于是把 clip 阈值设成一个很大的数（或者干脆 `clamp` 到格式的 `max`），结果发现量化质量反而比调过的阈值差一点点。

**成因**：§1 第四步的结论是**「没有『牺牲尾部换分辨率』这笔交易」**，不是「阈值完全无关」。实际还在起作用的是另一件事：**格式本身的范围边界**。把阈值设成 `448`（`e4m3fn` 的 `max`）在多数情况下没问题；设得更大则**越界**，而越界在 `e4m3fn` 上的后果是 `NaN`（[01](01-fp8-family.md) §1 第四步）——**`NaN` 不是「差点」，是「全废」**。

**规避**：把两件事分开。**「最优 clip」（牺牲尾部换更小步长）在浮点上无效**；**「范围 clip」（把值夹进格式的可表示区间）仍然必需**。前者可以省，后者不能省——而且后者的阈值就是格式的 `max`，不需要搜索。

### 4.3 用 fp64 生成测试数据，然后拿手写参考去对拍 torch

**现象**：写一个「独立参考实现」验证 torch 的 bf16 转换，用 `torch.randn(..., dtype=torch.float64)` 造数据，对拍发现**有几个元素对不上**（20 万个里 2 个）。于是以为自己或 torch 有问题，开始逐位排查。

**成因**：**两个都不是错**。`float64 → bfloat16` 在 torch 里**经过 fp32**（§1 第六步），而手写参考是「对 fp64 值直接做 7 位 RNE」。在「fp64 值恰好能被 fp32 截成平局」的那些点上，两者必然不同。20 万分之 2 正好是这个概率量级。

**规避**：三条。① 手写参考若要模拟 torch，**先按 fp32 取整**；② 用 `x.to(torch.float32).to(torch.bfloat16)` 作为对照通道，它能一眼区分「双重舍入」与「实现写错」；③ **别用 `fp64` 造数据去测 `fp32` 的行为**——如果测试目的是验证 bf16 的量化误差，直接用 fp32 输入更贴近真实负载。

## 5. 实测数据

**测量条件**：CPU 型号 **Apple M1 Pro（10 核）**；macOS；`python3` 版本与 `torch` 版本**逐表注明**；**CPU-only，无 GPU 数字**。

**覆盖范围**：四个分布的 SQNR 表在 **torch 2.6.0 / 2.11.0 / 2.13.0** 三个解释器上**逐格相同**（同一 `torch.manual_seed(20260918)`、2×10⁶ 样本）。其余实测在 torch 2.11.0 上。**未覆盖 2.9.x / 2.10.x / 2.12.x**（本机无解释器）。

**表 1：RNE 的中点判别**（判据：中点 = 相邻两个可表示数的算术中点；RNE 取偶尾数）

| 转换 | 输入 | 输出 | 说明 |
|---|---|---|---|
| → bf16 | `1 + 1/256` = 1.00390625 | **1.0** | 1.0 与 1.0078125 的中点，取偶 → 向下 |
| → bf16 | `1 + 1/256 + 2^-15` | 1.0078125 | 确实按最近 |
| → bf16 | `1 + 1/256 − 2^-15` | 1.0 | 同上 |
| → fp16 | `1 + 1/2048` | **1.0** | fp16 的同一判据 |

⚠ 扰动必须**大于 fp32 的 ulp**（约 1.19e-7），否则它会先被 bf16 转换里那一步 fp32 取整吃掉、又变成精确平局（§4.3）。

**表 2：★ 四分布 × 四格式的 SQNR**（2×10⁶ 样本，`torch.manual_seed(20260918)`）

| `N(0,1)` | 55.59 | 73.65 | 31.52 | 73.65 |

## 6. 小结与延伸

三个可复用的结论：

1. **浮点的相对误差上界只由尾数位数决定**（`2^(−M−1)`），与数值的指数无关。这条直接给出 **SQNR ≈ `6.02(M+1) + 7.78` dB**，也直接给出本文的主线结论：**浮点量化不需要 clipping**——因为「牺牲尾部换更小步长」这笔交易的前提（步长是绝对的）在浮点上不成立。
2. **浮点 SQNR 与分布几乎无关，极差约 1 dB**（bf16 1.04 / fp16 1.03 / `e4m3fn` 1.02）；而定点格式跨场景可差 20+ dB。**讨论 `6.02n + 1.76` 适不适用之前，必须先说清是定点还是浮点。**
3. **`float64 → bfloat16` 是双重舍入（经 fp32），`float64 → fp16` 不是。** 这一条会让「手写参考实现」与 torch 差几个元素——不是谁写错了，是入口精度不同。

**这条主线在 §0.8 的三角上是哪条边**：**范围 vs 精度**——与 [01-fp8-family](01-fp8-family.md) 是同一条边，只是容器从 8 位换成了 16 位。`bf16` 与 `fp16` 用同样的 16 位，把 3 位从尾数移给指数，换来 67.5 个数量级的量程跨度、丢掉 18.06 dB 精度。

延伸有三条。**往误差界**：`σ² = Δ²/12` 与 `±Δ/2` 界是**定点**的结论，四条经典假设（平稳、不相关、样本不相关、均匀）在浮点上不成立——正文在 [05-error-bounds](05-error-bounds.md)。**往粒度**：`per-tensor → per-group` 这条线上，「定点格式的 SQNR 强相关于分布」是它的全部动机，正文在 [06-granularity](06-granularity.md)。**往微缩放**：8 位以下必须引入块共享指数，格式设计的对象从「一个数」变成「一组数」，正文在 [02-e8m0-and-mx](02-e8m0-and-mx.md)。
