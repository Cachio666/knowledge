# FFN 的形态：从两层到 GLU 变体，d_ff 怎么定

> **`d_ff = 8d/3` 不是论文里的话，是一条推导**：它来自「GLU 变体有三个矩阵、朴素 FFN 有两个」
> 加上一条**论文之外的约定**（朴素 FFN 取 `d_ff = 4d`）。
> 而两个真实模型的 `intermediate_size / hidden_size` 是 **3.5 与 3.0** —— 既不是 4，也不是 `8/3`。

## 0. 背景与动机

一个 block 里有两个子层：attention 与 FFN。**参数的大头在 FFN**——
Llama-3-8B 上它一项占 `70.2%`（这笔分布的账在 `03-depth-and-width`；本文只讲**它的形态**）。

「形态」这个词在这里指的是一个很具体的取舍：**FFN 用几个矩阵、`d_ff` 取多大**。

| 形态 | 矩阵个数 | 参数个数（一层） |
|---|---|---|
| 朴素两层（`W1: d→d_ff`，`W2: d_ff→d`） | **2** | `2·d·d_ff` |
| GLU 变体（多一个门控矩阵） | **3** | `3·d·d_ff` |

**两个形态之间怎么比较**？直接比 `d_ff` 是没有意义的（矩阵个数不同）。有意义的比较方式是：
**让两者的参数量持平，再看 `d_ff` 该取多少**。这就是本文那条式子的全部来历：

```
3·d·d_ff^{GLU}  =  2·d·d_ff^{两层}       ⇒   d_ff^{GLU} = (2/3)·d_ff^{两层}
若两层取 d_ff = 4d                      ⇒   d_ff^{GLU} = (2/3)·(4d) = **8d/3**
```

★ **那个 `4` 不在 SwiGLU 论文里**（见 §1.2 的原始字节计数）——它是**这条推导的前提**，
写成正文时必须一并写出来，否则读者无法复核 `8d/3` 这个数从哪来。

## 1. 原理

### 1.1 参数个数的式子（两条路径：公式 vs 枚举）

一层的朴素 FFN 就是两个矩阵：`W1 ∈ R^{d×d_ff}`、`W2 ∈ R^{d_ff×d}`，
所以权重元素个数是 `d·d_ff + d_ff·d = 2·d·d_ff`。GLU 变体多一个（门控）矩阵，
两个 `d×d_ff` 加一个 `d_ff×d` ⇒ `3·d·d_ff`。

本程序用**两条独立路径**核对这个式子：一条是上面的乘法式，另一条是**真的
`numpy.zeros` 出两个矩阵、数它们的 `.size`**（`A.1`）。两条路径给出同一个整数
（`d=64`、`d_ff=256` 时都是 `32768`）——整数计数**没有舍入**，所以这里用 `==` 是对的。

### 1.2 `8d/3` 的来历：论文只给了 `2/3`，没给 `8d/3`

**SwiGLU 论文（arXiv 2002.05202）逐字只有：**

> "All of these layers have three weight matrices, as opposed to two for the original FFN.
> To keep the number of parameters and the amount of computation constant, we reduce the
> number of hidden units `d_ff` (the second dimension of `W_1` and the first dimension of `W_2`)
> **by a factor of `\frac{2}{3}`** when comparing these layers to the original two-matrix version."

**原始字节计数**（`raw.count`，即**在原始字节上数**，不是先转文本再数）：

```bash
curl -sS -o /tmp/swiglu.html "https://ar5iv.labs.arxiv.org/html/2002.05202"
python3 -c "raw=open('/tmp/swiglu.html','rb').read(); print(len(raw), [(p, raw.count(p)) for p in (b'8d/3', b'\\\\frac{8d}{3}', b'8d', b'\\\\frac{2}{3}')])"
# 实跑输出：141834 [(b'8d/3', 0), (b'\\frac{8d}{3}', 0), (b'8d', 0), (b'\\frac{2}{3}', 2)]
python3 -c "import hashlib;print(hashlib.sha256(open('/tmp/swiglu.html','rb').read()).hexdigest()[:16])"
# 实跑输出：54d6e4f552c74d53（与计划 §C.2 记的值一致）
```

⇒ **`8d/3` 在论文里出现 0 次**；**`\frac{2}{3}` 出现 2 次**（对照检验：一个已知存在的
字符串计到非 0，一个待证否的计到 0 ⇒ 「0」可信）。**`4d` 也出现 0 次。**

| 这个数 | 它是什么 | 来源等级 |
|---|---|---|
| `2/3` | 论文逐字给的**缩小因子** | **[C]**（★ 未确认同行评审：arXiv abs 页**没有** venue 线索，按页面实测填） |
| `4` | 「朴素 FFN 取 `d_ff = 4d`」——**论文之外的约定** | **无等级**：它是约定，不是来源 |
| `8d/3` | `(2/3) × 4`，**推导值** | — |

### 1.3 论文自己的实验恰好落在「精确持平」的点上

论文 §3.1 逐字给出了它自己的配置：

> "The encoder and decoder each consist of 12 layers, with `d_{model}=768` … `d_{ff}=3072`.
> As we describe above, for the GLU-variant-based FFN layers, which have thee weight matrices
> instead of two, we reduce the hidden layer to `d_{ff}=2048`, so as to maintain the same
> parameter and operation counts as the base model."

（★ 「thee」是**论文原文的拼写**，不是本文的笔误。）

**可手算的整数恒等式**：

```
GLU 变体：3 · 768 · 2048 = 4,718,592
两层基线：2 · 768 · 3072 = 4,718,592        ← d_ff = 3072 = 4 × 768，即那条约定成立
且 8 × 768 / 3 = 2048 —— **整除**（768 被 3 整除）
```

⇒ **论文选的数字使「参数持平」这条论证精确成立**（不是近似）。这是一个可以写进正文的巧合：
`8d/3` 只在 `d` 被 3 整除时是整数，而论文的 `d_model = 768` 恰好被 3 整除。

### 1.4 一般 `d` 上的比值：d 被 3 整除才是精确的

比值定义为 `3·(8d/3)·d ÷ 2·(4d)·d`（**取整**后的 `d_ff`），本机实测：

| `d` | `(8d)//3` | 比值 | 说明 |
|---|---|---|---|
| 768 | 2048 | **1.0000000000** | 被 3 整除 |
| 3072 | 8192 | **1.0000000000** | 被 3 整除 |
| 4098 | 10928 | **1.0000000000** | 被 3 整除 |
| 6144 | 16384 | **1.0000000000** | 被 3 整除 |
| 4096 | 10922 | 0.9999389648 = `16383/16384` | `4096 mod 3 = 1` |
| 8192 | 21845 | 0.9999847412 = `65535/65536` | `8192 mod 3 = 2` |

★ 计划 §0.7-D 的 **D19** 用的正是 `4096 / 8192` 两个点 —— 它们**都不被 3 整除**，
所以 D19 给出的 `0.9999 / 1.0000` 里那个 `0.9999` **不是**「持平」，而是**取整**
造成的 `1/16384` 偏差。⇒ 凡引用「`8d/3` 让参数持平」，**必须说明 `d` 是否被 3 整除**。

### 1.5 前提敏感度（`4` 是前提，不是可调参数）

同一个 `8d/3`，换掉基线比例，比值立刻变成别的数：

| 基线 `d_ff` | 比值（GLU 三个矩阵 ÷ 两层两个矩阵） |
|---|---|
| `3d` | `4/3` |
| **`4d`** | **`1`**（这就是「持平」） |
| `5d` | `4/5` |

比值 = `4 / base`，可手算。⇒ 「持平」这件事**只在 `d_ff = 4d` 这条前提上成立**；
把 `8d/3` 当成一条与前提无关的定理，是本文 §4 第 1 条要防的错。

## 2. 执行映射

**三个矩阵叫什么**（HuggingFace 的命名）：`mlp.gate_proj`（`d → d_ff`）、
`mlp.up_proj`（`d → d_ff`）、`mlp.down_proj`（`d_ff → d`）；门控用的激活函数由
config 的 **`hidden_act`** 给出 —— 本域两个模型都是 **`silu`**（即 SwiGLU 里的 `Swish`）。

★ **限定语**：`hidden_act` **不在** `45-kernel-lifecycle/requirement-discovery/code/specs.py` 里
（逐词频核实：该字段在那份文件中出现 **0** 次）。本域经 **`hf-mirror.com` 镜像**取得，
**未与官方 repo 比对 sha256**。所以本文引用它时**必须带上这句限定语**。

**量级**（本机推导值，`python3 3.13.5`，纯整数运算）：

| 量 | Llama-3-8B | Qwen3-30B-A3B |
|---|---|---|
| `hidden_size`（`d`） | 4096 | 2048 |
| `intermediate_size`（真实 `d_ff`） | 14336 | 6144 |
| `8d/3` | 10922.67 | 5461.33 |
| `4d` | 16384 | 8192 |
| 一层的 FFN 权重元素个数（`3·d·d_ff`） | **176,160,768** | **37,748,736** |
| `intermediate_size / hidden_size` | **3.5**（= `7/2`，精确有理数） | **3.0**（= `3`） |

⇒ **没有一个是 `4`，也没有一个是 `8/3 ≈ 2.667`**。两个真实模型都落在「比 `8/3` 宽一点」的地方，
但它们**彼此也不同**（3.5 vs 3.0）——说明这个比值是被别的约束（总深度、总宽度、训练配方）定出来的，
不是由那条「参数持平」的式子定出来的。

## 3. 实现与演进

| 阶段 | FFN 的形态 | 它换来了什么 |
|---|---|---|
| 原版（2017） | 两个矩阵 + ReLU/GELU | 每层 `2·d·d_ff`；`d_ff = 4d` 是那个时代的常规选择 |
| GLU 变体（2020） | 三个矩阵，多一个**门控**（`gate_proj ⊗ up_proj` 再 `down_proj`） | 论文的主张是「**在参数量与计算量持平的前提下**更好」——注意这个「持平」是**论证的前提**，不是结论（§1.2/§1.3） |
| 现代主流（Llama 一族） | `SwiGLU`（门控 + `silu`） | `hidden_act = silu`；但真实 `d_ff` **不从 `8d/3` 来**（见表：3.5 / 3.0） |

**演进的方向不是「矩阵越多越好」**，而是「同样的参数预算，花在哪更值」：
加一个门控矩阵 = 把原来给 `d_ff` 的那部分预算挪一部分去换**乘性交互**。
⇒ 这正是本域主线说的「每个选择都在别处付账」：**多出来的那个矩阵，是从 `d_ff` 里偷的**。

> ⚠ **本文只算参数（矩阵个数 × 形状），不算 FLOPs。**
> 「系数 4 vs 6」那一套（每 token 的 FLOPs 系数）的正文在
> `40-kernels/moe-kernels/01-moe-compute-pattern.md:72,278` 与
> `40-kernels/moe-kernels/code/verify.py:443`（正文在彼，此处回链）。
> **两者长得很像（`2` 与 `3` 都出现），但一个数的是权重元素，一个数的是每次前向的乘加** ——
> 混起来就是把「显存账」和「算力账」搞成了一本账。

## 4. 踩坑与失败模式

**① 把 `8d/3` 当成论文的结论引用。**

- **现象**：正文写「SwiGLU 论文把 `d_ff` 取成 `8d/3`」，读者去论文里搜 `8d/3` **搜不到**。
- **成因**：论文只有 `by a factor of 2/3`（原始字节计数 `\frac{2}{3}` = **2** 次，
  `8d/3` = **0** 次）；`8d/3` 是 `(2/3) × 4` 的**推导**，而那个 `4` 是**论文之外的约定**。
- **规避**：引用时写全三件东西 —— 「论文的 `2/3`」+「朴素 FFN 取 `d_ff = 4d`（约定）」+「⇒ `8d/3`（推导）」。

**② 拿 `8d/3` 去解释真实模型。**

- **现象**：用 `8d/3` 反推 Llama 的 `intermediate_size` 得到 `10922.67`，与真实值 `14336` 差 **23.8%**；
  对 Qwen3 得到 `5461.33`，与真实值 `6144` 差 **11.1%**。（换成 `4d` 也一样错：`16384` 差 14.3%、
  `8192` 差 33.3%。）
- **成因**：`8d/3` 是「**在参数持平的前提下**」的 `d_ff`，而真实模型是**先定总规模、再分配**的
  —— 两者回答的不是同一个问题。
- **规避**：把三个数**并列写出来**（真实 `d_ff` / `8d/3` / `4d`），让读者一眼看到它们都不相等。

**③ 忘了取整。**

- **现象**：`d_ff` 算出来是小数 (`10922.67`)，或者断言「比值精确等于 1」在 `d=4096` 上失败。
- **成因**：`d_ff` 是权重矩阵的宽度，**必须是整数**。取整之后，「持平」只能**近似**成立
  （`1/16384` 的偏差）；而且 `d` 很小时取整的误差**不再可忽略** —— 本机实测 `d = 1,2,3,4,5`
  上的比值是 `0.7500 / 0.9375 / 1.0000 / 0.9375 / 0.9750`。
- **规避**：把取整方向写进代码（本域用 `//`，与 `probes/probe_80.py` 的 `int(8*d/3)` 同口径）；
  断言写成**区间**；且只在 `d` 被 3 整除时断言「精确」。

**④ 把「参数持平」读成「计算量持平」。**

- **现象**：说「SwiGLU 与两层 FFN 的计算量一样」（论文的逐字是 "the same parameter **and operation**
  counts"，但那是在**它自己那组数**上成立的）。
- **成因**：参数量与 FLOPs 是两本账；本文只算前者，后者属 `40-kernels/moe-kernels`（回链见 §3 的注）。
- **规避**：本文正文只出现「参数个数 / 权重元素个数」这两个说法，**不出现 FLOPs**。

## 6. 小结与延伸

**一句话**：`d_ff` 不是「取 4 倍」或「取 `8/3` 倍」这样的常数，而是一条**在给定前提下的推导**
——换掉前提（矩阵个数、基线比例），它立刻变成另一个数；而真实模型用的是**第三个**数。

- **本文的账是「参数在 FFN 这一层里怎么花」**：多一个门控矩阵 = 从 `d_ff` 里偷预算换乘性交互。
- **FFN 在整机参数里的占比**见 `03-depth-and-width`（同一主题的下一个编号）。
- **专家（MoE）那条路**是「加宽 FFN 但不激活它」——它的形态取决于本文的 FFN 结论，
  正文在 `80-model-architectures/moe/01-gating-and-routing`（此处回链）。
- **输入/输出维度与头数**：`03-depth-and-width` 的规格表（逐字段标注「config 原生 / 推导」）。
- **从 config 反算算子清单**：正文在 `45-kernel-lifecycle/requirement-discovery/01-model-to-operator-inventory.md`
  （正文在彼，此处回链）。
