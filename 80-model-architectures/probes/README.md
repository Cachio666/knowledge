# 80-model-architectures/probes —— 探测脚本与它们的口径

这 7 个脚本是 `docs/superpowers/plans/2026-09-22-model-architectures-domain.md`
**§0.7-D「本机实测值」那张表（D1–D21）的唯一口径记录**。

它们原先只存在于 `/tmp`（**不入版本控制**，随时会被清掉），Chunk 0 把它们收进仓库。
**种子、初始化分布、重复次数、判据式都在脚本里**——读数字之前先读那一行是怎么算的。

- **不是编号程序**，不在任何主题的 `code/` 下，**不参与「文档数 = 编号程序数」的核对**
  （`CONTRIBUTING` §2：只有形如 `NN_*` 的文件才计入）。
- 它们是**探测**：**只打印、不断言、没有非零退出码**。可证伪的断言属于各主题 `code/`
  下的编号程序，不属于这里。
- 运行环境（本机实测，即这些数字的测量条件）：**python3 3.13.5 + numpy 2.4.4**，macOS arm64。

```sh
cd 80-model-architectures/probes
python3 probe_80.py        # 其余同理：probe_80b.py … probe_80g.py
```

## 入仓前的两处修正（计划 §0.7-D 末尾、§4 R9）

1. **`probe_80.py` 的 Q5 原先是恒真断言。** `out_shared` 与 `out_naive` 在初版里是
   **逐字符相同的同一行代码**（`attn(Q[i], K[i//group], V[i//group])` 写了两遍），
   所以它报出的 `0.000e+00` 是**构造出来的、不是测出来的**（计划 §0.1 的 **P17**）。
   现在改成**两条真正不同的路径**：① 共享 KV + **物化完整分数矩阵**的稠密 softmax；
   ② 把 KV **物化复制**成 `h_q` 份 + **online softmax 流式**实现（两者不共享任何辅助函数）。
   并加了一条**反恒真自检**：`inspect.getsource(attn_naive) == inspect.getsource(attn_online)`
   必须为 `False` —— 为 `True` 时那个差就是构造出来的，这一行会当场揭穿。
   （先例：`40-kernels/attention/code/verify.py` 的 A4 `:508-531` 用 `attn_naive` vs
   `attn_online` 两条不同实现比同一组 (Q,K,V)。）

   **实测**：`h_q=8 h_kv=4 r=2` 时最大差 `8.882e-16`，输出量级 `2.010`（相对 `4.42e-16`），
   源码同一份 = `False`。★ **注意它不是 `0.0`** —— 见下方「缺口」的第 3 条。

2. **`probe_80g.py` 的「显式」路径原先只旋转了 `k` 没旋转 `q`。**
   初版写成 `scores_rope = Q @ K_rope.T`（用的是**未旋转的 `Q`**）⇒ 那个对象
   **不是任何合法的注意力分数**，拿它和「错误吸收」作差得到的是**两个都不合法的对象之差**
   （计划原稿报的 `18.90` 由此而来）。现在按正确形式改成 **`q` 与 `k` 都被旋转**：
   `scores[t,s] = (R_{pos_t} q_t)·(R_{pos_s} k_s)`。

   另加一行**参照量级**（`max|score|`），避免读者拿一个孤立的差值去猜它算大还是小。

## 顺带清掉的两处噪音（计划 §4 R9）

- `probe_80d.py` 的 `residual_growth(seed, mode="pre", scaleF=1.0)`：`mode != "pre"`
  那一支**从不更新 `h`** ⇒ 范数数组恒为 `x_0`，是一支**死代码**（且该参数从未被传过别的值）。
  已删除该参数与那一支；`scaleF` 保留（它在 `F` 里真的被用到）。
- `probe_80.py` 的 Q8：删掉一行**从未被使用**的 `ff_plain`。

## 缺口与不可用的数（**引用前必读**）

1. **D2 在本组脚本里没有口径记录。** 「`I(half(x,pos)) == adj(I(x),pos)` 差恒为 `0.0`」
   这一条出自事实层审查者的**另一次独立测量**（`d=8`、`pos ∈ {0, 1.3, 5.0}`），
   脚本**没有**收进 `/tmp/probe_80*.py`，因此**不在本目录**。
   （控制者复核过该恒等式，三个 `pos` 上差都是 `0.000e+00`；★ 它的**精确为零是预期的**——
   两边做的是**同一批标量运算**，只是结果的索引摆放不同。）

2. **D21 的 `8.030 B` 不能由 `probe_80g.py`【C】复现。** 那一行现在给出的是
   **`7.505 B`**，因为它的 `param_split(..., tie_embed=True)` **默认为 tied**
   （嵌入与 `lm_head` 只算一次），而 D21 的 `8.030 B` 是 **untied** 口径
   （`tie_word_embeddings=False`，两个矩阵各算一次）。**两个口径不可混用**；
   用哪一个必须写在数字旁边。

3. ★ **两个「差 == 0」的断言口径要分开看。**
   `D13` 修正后得到的是 **`8.882e-16`（机器精度）**，不是 `0.0`：只要参考实现与被测实现
   **真的是两条独立路径**，逐元素差就不可能恒为精确的 `0.0`。
   ⇒ 计划 §3 Chunk 2 表 A ① 现写的判据「最大逐元素差 **== 0.0**，且参考实现独立」
   **两者并存时不可满足**（这正是它同时要求 M6 的独立性所导致的）。
   本机实测的对应阈值是**机器精度档**（先例：`40-kernels/attention/code/verify.py` 的
   A4 用 `< 1e-14`）。

4. **`probe_80g.py`【C】 的 `Qwen3-30B-A3B` 那一行是 P15 的现场，不得当参数量用。**
   它把**dense FFN 公式**套在一个 **MoE** 上（`d_ff` 填的是 `768`），于是得到 `1.444 B`——
   而真值 ≈ `30.5 B`，**差约 20 倍**（计划 §0.1 的 **P15**：MoE 的参数量按 `E` 算）。
   该行还是**手填的结构参数**（脚本自己写着「不是从官方 config 读的」），
   `Llama-2-70B` 那一行同理。**这两行只作为「公式长什么样」的演示，不作为任何模型的规格。**

5. **`probe_80c.py` 是 `probe_80d.py` 的「错误版」**，保留它是为了留下
   §0.1 里两类错误模式的现场（`n=1` 的熵非单调、把两个都每层归一化的实验当成「深度放大」）。
   **新工作请用 `probe_80d.py`，不要引用 `probe_80c.py` 的结论。**
