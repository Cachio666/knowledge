# 跨 block 归约与确定性

> 跨 block 归约只有两条路：`atomicAdd` 直接收尾，或者写 workspace 再由第二个 kernel 按固定顺序归约。**两条路线的部分和字节数完全相同**（都是 `2·G·4`）——差别在一次 kernel 启动，和**结果能不能复现**。判据只有一条：**加法树形写死在代码里 = 确定；顺序由运行时调度决定 = 不确定**。

## 0. 背景与动机

单块的归约在 [02 篇](02-warp-shuffle-and-hierarchy.md) 讲完了：warp 内 shuffle、跨 warp 一次块级屏障、每块一个局部和。**块数多于 1 时，局部和还要再归一次**——这一次没有块级屏障可用了，因为 `__syncthreads()` 的作用域就是块内。

对照场景：**把 N = 2^24 = 16777216 个 fp32（64 MiB）归约成一个标量**。

```text
全局读字节 = N × 4 = 67108864 B
内核时间   ≈ 67108864 / 3350e9 = 20.03 µs     （按 H100 的 3350 GB/s）
```

（推导值，`make verify` §B6。）而如果把「第二级归约」放进**第二个 kernel**，要多付一次启动：

| N | 内核本身 | 多一次启动的相对开销 |
|---|---|---|
| 2^18（1 MiB） | **0.31 µs** | **958% ~ 1597%** |
| 2^20（4 MiB） | 1.25 µs | 240% ~ 399% |
| 2^24（64 MiB） | 20.03 µs | 15% ~ 25% |

（推导值，`make verify` §B6；启动开销是**引用值** 3.0~5.0 µs，**本仓库不复核其测量口径**。）

**第一行是关键**：N = 2^18 时，内核本身只要 0.31 µs，而多一次 kernel 启动要 3~5 µs——**固定开销是内核时间的十倍以上**。这就是「小规模归约不要用两级 kernel」的定量依据。

但**第二条路不是白拿的**：`atomicAdd` 的那条路虽然只启动一次，却有一个更麻烦的性质——**同一个输入、同一份代码、同一张卡，两次运行的结果可能不同**。这个性质在 [gemm/06](../gemm/06-split-k-and-stream-k.md) §2.1 的 split-K 里出现过，在 [attention/03](../attention/03-flash-attention-backward.md) §2 的 `dQ` 累加里又出现过一次。本文是这条线的收束处：给出**判据**，说明**哪些归约是确定性的、哪些不是**。

## 1. 原理

### 1.1 两条路线

**第一步：把跨 block 归约拆成「局部和 + 收尾」。**

```text
第 1 级：每个 block 归约自己负责的那一段 → 一个局部和
第 2 级：把 G 个局部和归成一个标量
```

第 2 级怎么做，有两种选择：

| 路线 | 怎么做 | 部分和流量 | 启动次数 | 确定性 |
|---|---|---|---|---|
| **A `atomicAdd`** | 每个 block 直接原子加到全局累加器 | `2·G·4` B（每次原子操作是一次读改写） | **1** | **不确定** |
| **B workspace + 第二个 kernel** | 写进 `partials[blockIdx.x]`，第二个 kernel 按固定下标顺序累加 | `G·4`（写）+ `G·4`（读）= `2·G·4` B | 2 | **确定** |

**第二步：先看清一个反直觉的事实——两条路线的字节数完全相同。**

```text
G = 132：atomic 路线 2 × 132 × 4 = 1056 B
         两级路线  132 × 4 + 132 × 4 = 1056 B
```

（推导值，`make verify` §B6 断言了这两个数**相等**。）`atomicAdd` 不是「省了一次写」，它是一次**读改写**——读回旧值、加起来、写回，两倍流量。所以两条路线的差别**不在流量上**，在两件事上：

1. **一次 kernel 启动**（§0 的表：N 小时压倒性地贵）；
2. **确定性**（§1.2）。

这与 [gemm/06](../gemm/06-split-k-and-stream-k.md) §2.1 的三条归约路线是同一个结论（那里的第三条「信号量自旋」省掉了第二次启动，但顺序仍然是写死的）。**归约路线之间的差别从来不在字节数上。**

**第三步：部分和的字节数在什么情况下才值得算。**

上面 `2·G·4` 是「归约成一个标量」的情形——G = 132 时只有 1 KB，可以忽略。**但二维（每行一个结果）时它不再可忽略**（推导值，`make verify` §B6）：

| 形状 | 部分和 | 输入 |
|---|---|---|
| `nrows = 4096`、`G = 132` | **2.06 MiB** | 64 MiB（每行 4096 个 fp32） |
| `nrows = 4096`、`G = 1024` | **16.00 MiB** | 64 MiB |

**G 每翻一倍，部分和的流量就翻一倍，而输入流量不变。** 这是 segmented 归约（[01 篇](01-reduction-algorithms.md) §1.2）跨 block 化之后的真实代价：**切分换来并行度，代价是归约**——与 [attention/03](../attention/03-flash-attention-backward.md) §2 的 `n_split` 表格是同一笔账。

### 1.2 确定性的判据

**第一步：浮点加法不满足结合律。**

这不需要演示就能接受，但有两件事必须说清楚（推导值，`make verify` §C1）：

- **量级相当时，换序的差异落在最后几位。** 4096 个 fp32、各量级约 45：顺序、逆序、树形三种累加给出三个**不同的位模式**，而相对参考（fp64）的偏差都在 **1e-7 量级**。**精度没问题，只是不可复现。**
- **量级悬殊时，差异是肉眼可见的绝对误差。** 第 0 个数 = `1e8`、其余 127 个 = `1.0`：fp32 在 `1e8` 处的 ulp 是 **8.0**，所以先加 `1e8` 会把后面 127 个 `1.0` 全部吞掉——两种顺序给出 `100000000` 与 `100000128`，差 **128.0**。

**第二步：给出判据。**

> **确定性 = 加法的树形固定。**
>
> | | 判据 | 例 |
> |---|---|---|
> | **确定** | 谁和谁先加**写死在代码里**，与运行时的调度时序无关 → 同输入必得同 bit | workspace + 固定下标归约；三段式扫描；固定的树形归约；warp 内 shuffle 归约 |
> | **不确定** | 加法顺序由**运行时调度**决定 | `atomicAdd`；动态领号 / 工作窃取（Stream-K）；按到达顺序触发的信号量归约 |

**注意判据里没有任何「性能」或「精度」的字眼**——它只问一件事：**这个加法的左右操作数是谁，是在编译期就确定的，还是要等到运行时才知道？**

- `partials[blockIdx.x]`：下标是 `blockIdx.x`，**编译期就知道**这个 block 的局部和会落在哪个槽位；第二个 kernel 的 `for (b = 0; b < G; ++b)` 更是把顺序完全写死。
- `atomicAdd(total, acc)`：这个 block 的加法**排在第几个**，取决于它什么时候到达——由 block 调度、SM 占用、内存系统时序共同决定，**编译期无从得知**。

**第三步：证据。**

`make verify` §C7 用纯 numpy 把两条判据都做成了断言（推导值）：

```text
132 个 block 的局部和（各量级约 45），只改累加顺序：
  50 个随机排列 → 12 种不同的位模式        ← 「不确定」这一侧成立
  量级悬殊的构造（1e8 + 131 个 1.0）：先加 1e8 与先加小量相差 128.0

固定树形归约跑两遍 → 位模式完全相同        ← 「确定」这一侧成立（这一半是必然的）
```

**第四步（⚠ 这一条最容易搞错）：反过来不成立。**

```text
132 个量级相当的局部和，**正序与逆序恰好得到相同的位模式**（本例）
```

（推导值，`make verify` §C7。）同一批数据上 50 个随机排列才给出 12 种不同位模式——**「换顺序」只是让结果*可能*变，不是*必然*变。**

所以：

> **「把同一个输入跑两遍、结果一样」既不能证明确定性，也不能证明不确定性。**
>
> 判据看的是**代码里的加法树形是否固定**，不是一次观察。这一条是本文最实用的一句，因为它直接否掉了一种很常见的自检方式（§4.3）。

同样地，**改划分就是换一棵树**：同一份输入、只把 block 数从 4 改成 8，位模式就变了（推导值，`make verify` §C7：敏感输入下 4 block 给 `100000096`、8 block 给 `100000112`）。**「确定性」是「给定同一份代码与同一份输入」的确定性，不是「不管怎么切都一样」。**

### 1.3 三段式跨 block 扫描

扫描跨 block 时多一层结构：每块的输出不仅依赖自己的输入，还依赖**前面所有块的总和**。

```text
第 1 阶段：每块对自己那块做**块内 inclusive 扫描**，写出结果，
          并把本块的**总和**写进 block_sums[blockIdx.x]（下标固定）
第 2 阶段：对 block_sums 做 **exclusive** 扫描 → block_off[b]（每块的偏移）
第 3 阶段：每块把自己的块内结果加上 block_off[b]
```

（推导值，`make verify` §A6：三段式扫描在 4 / 16 / 33 个 tile 上都与 `np.cumsum` 逐元素相等。）

**这条路线是完全确定的**：第 2 阶段的顺序写死（`b = 0, 1, 2, …`），第 3 阶段的偏移是一个**查表**。给定 tile 数，结果逐位可复现。

两个细节：

- **第 2 阶段必须是 exclusive**。用 inclusive 会把本块的总和也算进去，于是每块整体偏一个块——**首个不符处就是索引 0**（推导值，`make verify` §A6）。这类错是「整体平移」而不是「小误差」，所以自检容易抓到（对比 §4.2 里真正难抓的那类）。
- **块数往往不是 2 的幂**（例如 132 个块扫 1024 个 tile）。若第 2 阶段用 Blelloch（[03 篇](03-scan-algorithms.md) §1.5），要把 `block_sums` **补到 2 的幂**，补在尾部——补零在末尾不改变前面任何一项的前缀和。

**代价**：三段式要读两遍输入（第 1 阶段读一遍、第 3 阶段要么重算要么从 workspace 读一遍）。**这个代价可以用单遍的 decoupled look-back 消掉**（§3），代价是引入运行时的顺序依赖。

## 2. 执行映射

### 2.1 三个部件的量级

| 部件 | 在跨 block 归约里做什么 | 量级 |
|---|---|---|
| L2 cache | `atomicAdd(float)` 的落点（不在 HBM 上做） | H100 的 L2 容量本仓库未收录规格值（上游 `architecture-evolution` 把 B200 的 L2 列为 `UNSOURCED`），正文只做机制陈述 |
| 全局原子单元 | 同一地址的原子操作**串行化** | 每次读改写 = 2 次访存 |
| kernel 启动 | 那条「第二条路线」的固定成本 | **3~5 µs**（**引用值**，本仓库不复核其测量口径） |
| HBM | 第一趟读 N 个元素 | 3350 GB/s（H100）、400~800 周期延迟 |
| `gridDim` 上限 | 第二级塞进 grid 的 y/z 维时 | x = 2^31−1，**y = z = 65535** |

（规格值，来源见 `code/specs.py`。）

**最后一行值得单独说**：`gridDim.y` 与 `gridDim.z` 的上限只有 **65535**，而 `gridDim.x` 是 2^31−1——**差 5 个数量级**。把「按块切 K」放在 y 维、把大维度放在 x 维是常见做法，反过来会直接被 launch 拒绝。这个限制与输出尺寸耦合之后，就是 §4.2 那条失败模式的一部分。

### 2.2 `atomicAdd` 的到达顺序为什么不可控

`atomicAdd` 保证的是**原子性**（不会有丢失的更新），**不保证顺序**。第 `b` 个 block 的加法排在第几位，取决于：

- 它什么时候被调度到 SM 上（取决于此时哪些 SM 有空槽）；
- 它什么时候读完自己那一段数据（取决于内存系统的时序）；
- 它对同一个地址的原子操作什么时候排到队首（取决于其他 block 在同一时刻的竞争）。

这三件事没有一件是确定的。**同一份代码、同一份输入、同一张卡，两次运行给出不同的位模式**，这不是 bug，是「并行归约 + 浮点」的必然结果。完整机制与另一个出口（split-K 的部分和累加）在 [gemm/06](../gemm/06-split-k-and-stream-k.md) §2.1 与 [attention/03](../attention/03-flash-attention-backward.md) §2，此处只回链，不复述。

### 2.3 二级 kernel 的代价为什么常常被低估

因为它**不是一个常数，而是与规模成反比的一项**（§0 的表）：

| N | 内核时间 | 多一次启动 |
|---|---|---|
| 2^18 | 0.31 µs | 958%~1597% |
| 2^24 | 20.03 µs | 15%~25% |

所以「两级归约还是原子归约」这个问题**没有全局答案**：大 N 时两级几乎免费（15%~25%），小 N 时两级贵十倍以上。而**确定性的需求是另一根轴**——它与 N 无关：

> **两个问题要分开问**：这次归约**需不需要确定性**（契约问题）、这次归约**的规模有多大**（性能问题）。前者的答案决定选哪条路线，后者的答案决定这个选择值不值。

## 3. 实现与演进

按「跨 block 的通信方式」这条线：

1. **单块搞定**。N 小到能塞进一个 block 时不需要跨块（[02 篇](02-warp-shuffle-and-hierarchy.md)）。深度受限：单块最多 1024 线程、共享内存 228 KB/SM。
2. **两级 kernel（本文路线 B）**。局部和落 workspace，第二个 kernel 顺序归约。**确定**，代价是一次启动（N 小时压倒性地贵）。
3. **`atomicAdd` 收尾（本文路线 A）**。少一次启动，换来**不确定性**。适合「只要数值上够准」的调用方。
4. **三段式扫描**。把扫描拆成「块内扫描 → 块总和扫描 → 加回偏移」三段（§1.3）。**完全确定**，代价是输入要读两遍。
5. **单遍 look-back 扫描**。把三段合并进一个 kernel：每块先算出自己的局部扫描与总和，再**回看**前面各块的前缀（用全局内存里的状态字 + 标志位做生产者-消费者）。消掉了第二遍读，代价是引入了**运行时的顺序依赖**——它比 `atomicAdd` 弱（顺序由回看的推进顺序决定，而推进顺序受「先算完的先发布」影响），但**仍然不是「写死的树形」**。判据（§1.2）在这里的应用：**看回看循环里的加法树形是否固定**。若某块的前缀是「把自己看到的已发布前缀按到达顺序加起来」，那它就和 `atomicAdd` 同类。
6. **对确定性有硬要求的场景**：回到第 2 / 4 两条路线，把顺序彻底写死。

这条线的方向与 [gemm/06](../gemm/06-split-k-and-stream-k.md) §3.1 的「把网格描述问题的方案换成网格描述机器的方案」是同一个方向——**每一步都在削弱确定性，而确定性是可以单独买回来的**（[gemm/06](../gemm/06-split-k-and-stream-k.md) §3.3）。

## 4. 踩坑与失败模式

### 4.1 用 `atomicAdd` 做跨 block 归约 → 每次运行结果都不同

**现象**：内核的正确性检查「有时过有时不过」。把同一个输入跑两遍、**逐位**比较输出，发现有相当比例的元素不同。难度在于它**在开发时常常看不出来**——单跑一次与参考实现比对是「在容差内」的。

**成因**：`atomicAdd` 的执行顺序由硬件决定（§2.2）。浮点加法不满足结合律，顺序一变结果就变。量级相当时差异落在最后几位（相对误差 1e-7 量级），量级悬殊时是**可观的绝对误差**（推导值，`make verify` §C1：`1e8` 与 127 个 `1.0` 的两种顺序相差 **128.0**）。这个现象在两个地方已经分别出现过：split-K 的部分和累加（[gemm/06](../gemm/06-split-k-and-stream-k.md) §4.1）与 flash attention 反向的 `dQ` 累加（[attention/03](../attention/03-flash-attention-backward.md) §4.1）——**同一机制的三个出口**。

**规避**：先确定调用方要的是「在容差内正确」还是「逐位可复现」。前者用 `atomicAdd`（省一次启动）；后者必须用 workspace + 固定顺序归约。判定方法是**逐位**比较两次运行的输出——`code/04_multi_block_scan.cu` 就是这么做的。**注意「在容差内一致」不等于「可复现」**：测试里写 `allclose` 抓不到这条。

### 4.2 grid 的遍历顺序改变累加顺序

**现象**：把「哪个维度对应哪个下标」调换一下（例如第二级归约从遍历 x 维改成遍历 y 维），结果变了；或者某个形状下 `gridDim.y` 直接超限。

**成因**：grid 是多维的，而「第二级归约按什么顺序累加局部和」取决于**遍历的顺序**。`for (b = 0; b < G; ++b) partials[b]` 与「先 y 后 x」的二维版本是**两棵不同的加法树**——即使两者的下标集合完全相同。再加上 `gridDim.y` / `gridDim.z` 的上限只有 **65535**（x 维是 2^31−1，差 5 个数量级），把「按块切」的那一维放到 y 上还会遇到第二类问题：**维度顺序不只是性能问题，它同时改变了数值结果**。

**规避**：把第二级的遍历顺序**显式写死**，并且与第一级的写入下标一一对应（`partials[blockIdx.x]` ↔ `for (b = 0; b < G; ++b)`）。写下标时优先用扁平化的一维编号（`b = blockIdx.x + gridDim.x * blockIdx.y`），不要依赖「编译器会按我期望的顺序遍历」。**改网格形状就是改加法树**——按 §1.2 的判据，改完之后必须重新确认「树形是否仍然固定」。

### 4.3 用「跑两遍结果一样」证明归约是确定性的

**现象**：为了验证某个跨 block 归约可复现，把同一个输入跑两遍、比较输出，结果完全一致，于是判定它确定性。上线后换一个数据分布、换一张卡，或换一个 block 数，两次运行开始不一致。

**成因**：**「换顺序」不保证改变位模式。** 132 个量级相当的局部和，正序与逆序累加在本例里**恰好得到完全相同的位**（推导值，`make verify` §C7）——因为两条舍入路径落在同一个可表示数上。同一批数据上，50 个随机排列才给出 12 种不同的位模式。所以「跑两遍一样」是一个**没有信息量**的观测：确定的和不确定的实现都可能通过它。

这个坑最阴险的地方在于它**给出的是一个假阳性**：观察支持了「确定性」这个结论，而观察本身不具备区分能力。

**规避**：判据看**代码**（§1.2），不看观察。要检验确定性，问三个问题：

1. 累加的**左右操作数**是编译期确定的，还是运行时才知道的？
2. 有没有 `atomicAdd`、动态领号、按到达顺序触发的信号量？
3. 改一个 block 数 / tile 数，是不是就换了一棵加法树？（如果是，那么「确定性」要连划分一起声明。）

配套程序 `code/04_multi_block_scan.cu` 会打印两次 `atomicAdd` 路线的结果，并在输出里**显式提醒**：两者相同**不能**证明它确定。

### 4.4 把「数值契约」当成性能问题处理

**现象**：某层的输出与参考实现（或另一台机器上的同一模型）比对时超差；排查很久找不到「错误」。训练里表现为「同一份数据、同一份代码，两次跑出的梯度不一样」——复现实验、对拍、调试全部变难。

**成因**：切分改变了累加的树形。误差量级仍然是 `γ·Σ|x|` 那一套（正文在 [10-foundations/numerical-linear-algebra/02](../../10-foundations/numerical-linear-algebra/02-gemm-rounding-error.md)，本文只回链），量级变化不大——但**结果的具体数值变了**，而且（`atomicAdd` 路线下）每次运行还不一样。如果下游做了「与上一次输出逐位比较」这类检查，就会报出并不存在的 bug。

**规避**：把「本层是否允许非确定性归约」当成**数值契约**问题与调用方明确约定，而不是纯性能问题。训练（需要可复现的梯度）与推理（只要数值够准）在同一份代码上会选**不同**的路线。这条取舍在 [gemm/06](../gemm/06-split-k-and-stream-k.md) §3.3 与 [attention/03](../attention/03-flash-attention-backward.md) §4.1 已经分别给出过结论，本节是把它收束成一个判据。

## 6. 小结与延伸

本文一条主线：**跨 block 归约的两条路线字节数完全相同（`2·G·4`），差别在一次启动与确定性；而确定性只有一条判据——加法树形是否写死在代码里。** 围绕它有三个可独立复用的中间结论：

1. **两条路线的选择是两个独立问题的乘积。** 「需不需要确定性」是**契约**问题（决定选哪条路线），「规模有多大」是**性能**问题（决定这个选择值不值）。N = 2^18 时多一次启动贵 958%~1597%，N = 2^24 时只贵 15%~25%——**同一笔开销，差 60 倍**。
2. **判据：固定树形 = 确定；`atomicAdd` / 动态调度 = 不确定。** 具体到代码：`partials[blockIdx.x]` + `for (b = 0; b < G; ++b)` 是确定的（下标与顺序都在编译期确定），`atomicAdd(total, acc)` 不是（排第几由运行时决定）。三段式扫描是三段都确定的形态。
3. **⚠ 反过来不成立：换顺序不保证改变位模式。** 132 个量级相当的局部和，正序与逆序**恰好**给出相同的位（50 个随机排列才给出 12 种位模式）。所以「跑两遍一样」既不能证明确定性、也不能证明不确定性——**判据看代码，不看观察**。这一条同时否掉了「用一次对比测试验证确定性」这个很常见的做法。

三篇的收束：这条主线的三个出口到这里合上了——**split-K 的部分和累加（[gemm/06](../gemm/06-split-k-and-stream-k.md) §2.1）**、**flash attention 反向的 `dQ` 累加（[attention/03](../attention/03-flash-attention-backward.md) §2）**、以及**跨 block 归约（本文）**，三者的机制完全相同：**浮点加法的结合顺序决定结果，而顺序由「归约路线」而不是「切分方式」决定**。切分只决定代价，路线决定可复现性——这是本主题四篇要说的最后一句话。
