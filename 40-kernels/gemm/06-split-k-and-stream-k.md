# split-K 与 Stream-K

> M/N 小、K 大时并行度可以少到个位数个 block，132 个 SM 里 128 个空转——而算力需求一点没变。split-K 把 K 切给额外的 block 来填机器，代价是**归约顺序不确定 → 结果逐位不可复现**。Stream-K 把同一件事做得更平滑，但它并没有变回确定。

## 0. 背景与动机

先看对照场景：**`M = N = 256`、`K = 65536`，FP32，`BM = BN = 128`**。

```text
block 数 = (M/BM)·(N/BN) = 2 × 2 = 4
机器 SM 数（H100）= 132
```

**4 个 block 要喂 132 个 SM**——128 个 SM 全程空转，利用率 **3.03%**（推导值，`make verify` §C4）。

而这道题的**算力需求一点没变**：`FLOPs = 2MNK = 8.5899e9`。作为对照，`M = N = 4096、K = 256` 的方阵题也是 `8.5899e9`，但它有 `(4096/128)² = 1024` 个 block 去分。**同一个计算量，一个是 4 个 block、一个是 1024 个 block。**

这就是瘦高 GEMM 的困境：并行度由 `(M/BM)·(N/BN)` 决定，而这个乘积只依赖 M 和 N，**与 K 无关**。K 很大只是让每个 block 干得更久，不会多出任何 block。

减小 tile 也救不了：`BM = BN = 64` 给出 16 个 block，`BM = BN = 32` 给出 64 个——但块级算术强度同步下降（`AI_block = BM/esize`：32 → 8.0、64 → 16.0），**两者都低于 `I*(FP32) = 20.0`**，越切越 bandwidth-bound（`make verify` §C4）。这是个死结：tile 小了并行度上去、AI 下来；tile 大了 AI 上去、并行度下来。

本文讲的两条路都是绕开这个死结的：**不切 tile，改切 K**。

## 1. 原理

按五步推导。

**第一步：split-K 的并行度收益。**

把一个输出 tile 的 K 循环切成 `S` 段，每段交给一个独立的 block：

```text
并行度 = (M/BM)·(N/BN) · S
```

对照场景里 `(M/BM)(N/BN) = 4`，`S = 32` 时并行度变成 **128**，正好填满 132 个 SM。（`make verify` §B6 的表逐行打印。）

| `S` | block 数 | 占用 SM | 计算时间 | 加速比 | 归约字节 | 归约时间 | 归约/计算 |
|---|---|---|---|---|---|---|---|
| 1 | 4 | 4 | 4230.9 µs | 1.0× | 0.5 MB | 0.16 µs | 0.00% |
| 8 | 32 | 32 | 528.9 µs | 8.0× | 4.2 MB | 1.25 µs | 0.24% |
| 16 | 64 | 64 | 264.4 µs | 16.0× | 8.4 MB | 2.50 µs | 0.95% |
| **32** | **128** | **128** | **132.2 µs** | **32.0×** | **16.8 MB** | **5.01 µs** | **3.79%** |
| 64 | 256 | 132 | 128.2 µs | 33.0× | 33.6 MB | 10.02 µs | 7.81% |
| 256 | 1024 | 132 | 128.2 µs | 33.0× | 134.2 MB | 40.06 µs | 31.25% |
| 512 | 2048 | 132 | 128.2 µs | 33.0× | 268.4 MB | 80.13 µs | 62.50% |

（推导值。计算时间 = `FLOPs / (占用 SM 数 × 每 SM FP32 速率)`，每 SM 速率 = `67.0e12/132 = 5.0758e11 FLOP/s`；归约字节 = `2·S·MN·esize`，即 atomicAdd 的读改写各一次；归约时间按 3350 GB/s 折算。）

**加速比在 `S = 33` 处到顶**（`4 × 33 = 132`，恰好填满），之后归约开销线性上涨、加速比不再增加。

**第二步：split-K 的代价——C 的部分和搬运。**

注意第一列到最后一列：**主循环的访存并没有变多**。第 `s` 个分段块读的是 `A` 的 `BM×K/S` 与 `B` 的 `K/S×BN`，`S` 个分段加起来仍是整条 `A` 边与整条 `B` 边——split-K **不增加主循环的 HBM 流量**（前提是分段之间不重复读）。

多出来的是 `C` 的**部分和**：每个分段块都要把自己那份 `BM×BN` 的部分和交出去。`atomicAdd` 口径下是「读改写各一次」：

```text
归约流量 = 2 · S · MN · esize
```

`S = 32` 时是 16.8 MB，占 `S = 32` 那一档计算时间（132.2 µs）的 **3.79%**。这是一个规模不大但**随 S 线性增长**的量——`S = 512` 时归约时间 80.13 µs，已经是计算时间的 **62.5%**。

**第三步：有用的 `S` 窗口。**

把两个条件并起来解：

```text
填满机器：        S ≥ ⌈132 / 4⌉ = 33
归约 ≤ 10% 计算： S ≤ 81
```

**窗口是 `[33, 81]`，宽度只有 49 档**（推导值，`make verify` §B6）。两端都很硬：`S < 33` 时机器填不满，`S > 81` 时归约开销开始吃掉收益。而窗口的宽度随 K 变小而收窄——K 越小，同样的 `S` 切出来的分段越短，而归约流量 `2·S·MN·esize` 与 K 无关。

**第四步：split-K 与 Stream-K 的区别。**

两者都切 K，但**切法不同**。

**split-K** 把每个 tile 的 K 切成固定的 `S` 段，网格大小是 `T·S`（`T = (M/BM)(N/BN)`）。这个数**是量化的**——`S` 只能取整数，所以 `T = 4` 时网格只能是 4、8、16、…，**永远不等于 132**（`make verify` §A3 逐档打印）：

```text
S = 16 → 网格  64 个 block（填不满 132 个 SM）
S = 32 → 网格 128 个 block（差 4 个填满）
S = 64 → 网格 256 个 block（填满，但不是 132 的倍数 → 有余数波）
```

**Stream-K** 换一个做法：**先定网格，再分工作**。工作单元是 `(tile, k-chunk)` 对，总共

```text
U = T · (K / BK_chunk)
```

个，把全局序号 `0 … U−1` 切成 `P` 段（`P` 是机器的槽位数），第 `b` 个 block 拿第 `b` 段连续的号。于是：

- **网格严格等于 `P`**，不受 `T` 的整除性影响；
- **负载不均 ≤ 1 个工作对**（`make verify` §A3：`P = 132` 时每 block 拿 1~2 个）；
- 一个 tile 可能被**多个 block** 拥有：`P = 132`、`U = 256` 时，每个 tile 的 owner 数是 **33**。

第三点是 Stream-K 的代价。分段的粒度越细（`BK_chunk` 越小），负载越平滑，但每个 tile 的 owner 数越多、归约流量越大。而且这个代价**随 `T` 变小而上升**——`T = 4` 时每个 tile 有 33 个 owner；换个形状 `T = 1024`，`P/T < 1`，多数 tile 只有一个 owner，Stream-K 就退化成一个「尾部更平滑的静态划分」，几乎不付归约的钱。

**一句话的区别**：**split-K 是「把 K 切成固定的 S 份，网格大小由 S 决定」；Stream-K 是「把全部 `(tile, k-chunk)` 工作对均匀分给固定的 block 数，网格大小由机器决定」。** 后者更平滑，但**仍然不是确定性的**。

**第五步：为什么两者都不确定。**

浮点加法不满足结合律。部分和以什么顺序累加，结果就不同。`make verify` §A2 在 `256×256×65536` 上把三种归约顺序打印出来（推导值）：

| 归约顺序 | `max\|Δ\|` | 相对**量级**误差 | 相对**元素**误差 |
|---|---|---|---|
| 顺序累加 | 9.336e-04 | 9.131e-07 | 3.332e-02 |
| 逆序累加 | 9.336e-04 | 9.131e-07 | 3.290e-02 |
| 树形累加 | 9.924e-04 | 9.706e-07 | 3.198e-02 |

三个结果的**位模式互不相同**。整体精度没问题（相对量级误差 1e-6 量级），但逐位不可复现。

`atomicAdd` 的执行顺序**由硬件决定**：哪个 block 先加到那个地址上，取决于调度时序。于是「同一个输入、同一份代码、同一张卡」两次运行会给出不同的 bit。这不是 bug，是「并行归约 + 浮点」的必然结果——同一现象在跨 block 归约里普遍存在（另一处正文在 [40-kernels/reduce-scan/04-multi-block-and-determinism](../reduce-scan/04-multi-block-and-determinism.md)，此处回链）。

## 2. 执行映射

### 2.1 三条归约路线与它们的确定性

| 路线 | 怎么做 | 归约流量 | 确定性 |
|---|---|---|---|
| **第二个 kernel** | 部分和写进 `workspace[S][M][N]`，再由一个独立 kernel 按固定的 `s = 0,1,…` 顺序累加 | `2·S·MN·esize`（写一遍 + 读一遍）+ `MN·esize`（最终写） | **确定**（顺序写死在代码里） |
| **信号量自旋** | 每个 tile 配一个计数器与信号量；每个分段块把部分和写进 workspace 后原子递增计数器，**最后一个到达的** block 负责归约 | 同「第二个 kernel」，但没有第二次启动 | **确定**（谁做归约不确定，但**按什么顺序加**是写死的 `s` 序） |
| **`atomicAdd`** | 直接把部分和加到 `C` 上 | `2·S·MN·esize`（每次原子操作都是一次读改写） | **不确定**（顺序由硬件决定） |

第二行值得单独说：**「谁来做最后那一步」不确定，不代表「结果」不确定**。只要最后那个 block 是**按 split 序号**读 workspace 并累加，结果就与「谁最后到」无关。信号量方案省掉了一次 kernel 启动，代价是自旋等待与一个全局计数器。

`make verify` §C3 用纯 numpy 把「顺序决定结果」这件事演示了两遍（推导值）：

- **量级相当**：32 段、每段 4096 个 fp32 值、各段量级约 45、总和约 255。正序与逆序的结果有 **3305/4096 个元素位模式不同**。
- **量级悬殊**：第 0 段 = `1e8`、其余 127 段 = `1.0`。此时 fp32 在 `1e8` 处的 ulp 已经等于 **8.0**，所以先加 `1e8` 会把后面 127 个 `1.0` 全部吞掉——两种顺序的结果相差 **128.0**。

第二个构造说明的是：**归约顺序的影响不是「只在最后一位」**，当分段量级差得远时会变成可观的绝对误差。`K` 大、分段多、每段量级相近时，差异通常落在最后几位；但「通常」不是「总是」。

### 2.2 分段块的两个固定开销

切 K 之后，每个分段块的**有用计算**正比于 `K/S`，而两项开销是**固定的**：

- **`C` 的部分和**：`BM·BN·esize`（H100 的 `128×128` 是 64 KB），与 `K/S` 无关。`K/S` 越小，这一份搬运占该 block 工作量的比例越高。
- **流水线填充与 SMEM 分配**：一次填充的延迟是几百个周期（[04 篇](04-tensor-core-and-async-pipeline.md) §1 第四步量级），与 `K/S` 无关。`S = 512` 时每个分段块的 K 循环只有 128 次迭代、计算时间 8.26 µs 量级，而填充延迟 0.3~0.5 µs 占了 4%~6%。

这两项加起来，就是「**分段越多，每个 block 的 K 循环越短、固定开销占比越高**」的准确形态——注意**变多的不是 `A`/`B` 的访存**（分段之间读的是不同的 K 区间，总量不变），而是 `C` 的部分和与每块的启动项。

### 2.3 具体的部件与量级

| 部件 | 在 split-K 里做什么 | 量级 |
|---|---|---|
| 全局原子计数器 | Stream-K 领号 | 每 block 一次 |
| `atomicAdd` | 直接归约到 `C` | 每输出元素 `S` 次读改写 |
| workspace | 存部分和 | `S·MN·esize` 的显存 |
| 第二个 kernel | 按固定顺序归约 | 一次额外启动 + `2·S·MN·esize` 流量 |
| 信号量 / mbarrier | 「最后一个到达者」判定 | 每 tile 一个计数器 |
| HBM | 所有部分和的往返 | 3350 GB/s（H100） |

`S = 32`、对照场景下的具体数字：workspace 是 `32 × 256 × 256 × 4 = 8.4 MB`（一个方阵 `4096³` 的 `C` 是 67.1 MB，所以 workspace 的量级完全可控）；归约流量 16.8 MB，在 132.2 µs 的计算时间上占 3.79%。

## 3. 实现与演进

### 3.1 从「切 tile」到「切 K」再到「切工作对」

| 阶段 | 网格 | 每个 block 的工作 | 尾部 | 确定性 |
|---|---|---|---|---|
| 常规 tiling | `(M/BM)(N/BN)` | 一个完整 tile 的 K 循环 | 波次量化 | 确定 |
| split-K | `(M/BM)(N/BN)·S` | 一个 tile 的一段 K | 量化到 `T·S` 的倍数 | **不确定**（`atomicAdd` 路线） |
| persistent + split-K | 槽位数 | 领号循环，多个分段块 | 最后一个工作对 | 取决于归约路线 |
| **Stream-K** | **槽位数** | 领号循环，工作对是 `(tile, k-chunk)` | 最后一个工作对 | 仍不确定 |

这条线的每一步都在把「网格描述问题」改成「网格描述机器」（[05 篇](05-persistent-kernel-and-tcgen05.md) §3.1），同时**每一步都在削弱确定性**——除了归约那一步之外，切 K 的每一刀都把「一个输出元素的累加」拆到了多个执行单元上。

### 3.2 什么时候值得切 K

判据可以写成一个不等式。设 `T = (M/BM)(N/BN)`、槽位数 `P`：

```text
T ≥ P     ⟹  不需要切 K（已经有足够并行度，切了只增加归约开销）
T ≪ P     ⟹  切 K 是唯一能填满机器的手段
```

对照场景 `T = 4`、`P = 132`，属于后者。这是「瘦高」的典型形态：**推理的批量维小、`d_model` 大、权重矩阵的 K 很大**——也就是 decode 阶段大权重矩阵乘小 batch 的形状。反过来说，**`T ≥ P` 时切 K 纯粹是净损失**。

一个常被忽略的中间形态：如果 `T` 略小于 `P`（比如 `T = 100`、`P = 132`），切 K 的收益（把 100 个 SM 补到 132）远小于它的代价（归约流量），此时更应该考虑的是调 tile 大小让 `T` 接近 `P`，而不是切 K。

### 3.3 确定性是可以买回来的

三条路线的确定性差异（§2.1）说明：**不可复现不是切 K 的必然属性，而是「用 `atomicAdd` 做归约」这个选择的属性**。要确定的结果就用 workspace + 固定顺序（第二个 kernel 或信号量自旋），代价是一次额外的显存与流量。这个取舍在训练（需要可复现的梯度）与推理（只要数值上够准）之间完全不同——同一份代码，两种调用方会选不同的路线。

## 4. 踩坑与失败模式

### 4.1 用 `atomicAdd` 做 split-K 归约 → 每次运行结果都不同

**现象**：内核正确性检查「有时过有时不过」；把同一个输入跑两遍、逐位比较 `C`，发现有相当比例的元素不同。难度在于它**在开发时常常看不出来**——单跑一次的结果与参考实现比对是「在容差内」的。

**成因**：`atomicAdd` 的执行顺序由硬件决定。哪个分段块先把自己的部分和加到 `C` 上，取决于 block 调度、SM 占用、内存系统的时序——这些都不是确定的。浮点加法不满足结合律，顺序一变结果就变。`make verify` §C3 的构造（32 段、各段量级约 45）显示 **3305/4096 个元素的位模式不同**；量级悬殊的构造（`1e8` 与 127 个 `1.0`）差值可达 **128.0**。

**规避**：先确定调用方要的是「在容差内正确」还是「逐位可复现」。前者用 `atomicAdd`（最省显存与流量）；后者必须用 workspace + 固定顺序归约（第二个 kernel 或信号量自旋）。判定方法很直接：**把同一个输入跑两遍，逐位比较两次的输出**——`code/06_split_k_gemm.cu` 就是这么做的（它同时跑 `atomicAdd` 与固定顺序两条路线并打印位模式对比）。顺带注意：**"在容差内一致" 不等于 "可复现"**，测试里写 `allclose` 是抓不到这条的。

### 4.2 分段数取太大，收益被归约开销吃掉

**现象**：为了「充分利用并行度」，把 `S` 从 32 加到 256 甚至 512。并行度确实上去了（block 数 1024、2048），但耗时不再下降，甚至变长。

**成因**：`S > 33` 之后机器已经填满，**加速比的分子不再增长，而分母在涨**。归约流量是 `2·S·MN·esize`，与 S 成正比、与 K 无关。`make verify` §B6 的表：`S = 32` 时归约占 3.79%，`S = 512` 时占 **62.50%**。同时每个分段块的 K 循环被切短，`C` 部分和的搬运与流水线填充这些**固定开销**占该 block 工作量的比例同步上升（§2.2）。

**规避**：先算 `S` 的下界（`⌈P/T⌉`，填满机器）与上界（让归约开销不超过计算时间的某个比例，比如 10%），在窗口里取值。对照场景的窗口是 `[33, 81]`——注意它**很窄**，而且**随 K 变小而收窄**。`S` 取 2 的幂（32、64）是工程习惯，但要确认它落在窗口里：`S = 32` 在窗口内，`S = 128` 已经超出（归约占 15.62%）。

### 4.3 把 split-K 当成「白拿的并行度」

**现象**：看到一个 `T = 4` 的瘦高 GEMM，直接上 split-K，并预期加速比接近 `P/T = 33`。真机上的加速比远达不到。

**成因**：加速比的上界不是 `P/T`，而是 `P/T` 与「归约开销占比」共同决定的结果，而且还有三项本文没细算的代价：(a) `C` 部分和的搬运（§1 第二步）；(b) 每块的流水线填充与 SMEM 分配（§2.2）；(c) 分段块之间的 **L2 复用被拆散**——原方案里同一 block 行的 block 会共享 `A` 的那一列块，切 K 之后这些共享关系在时间上被拉开，L2 命中的机会变少。第三项在本文的零缓存口径里看不见（因为口径假设零缓存），但真机上它会吃掉一部分预期收益。

**规避**：把 split-K 的收益算成「`min(P/T, 1/归约占比)` 量级的一个数」，而不是 `P/T`。先做一次小规模的对照（同一个形状，`S = 1` 与 `S = 32` 各跑一遍）确认收益存在，再往上加 `S`。`make verify` §B6 的表可以直接当预期的上界用。

### 4.4 用 split-K 修并行度，却忘了它改变了数值结果

**现象**：某层的输出与参考实现（或者另一台机器上的同一模型）比对时超差；把 `S` 从 1 改成 32 之后误差变大，排查了很久却找不到「错误」。

**成因**：split-K 把一次长度为 `K` 的累加拆成了 `S` 段部分和再相加。误差的量级从「一条 `K` 长的链」变成「`S` 条 `K/S` 长的链 + 一次 `S` 项求和」。误差界仍然是 `γ_K·Σ|x·y|` 那一套（正文在 [10-foundations/numerical-linear-algebra/02](../../10-foundations/numerical-linear-algebra/02-gemm-rounding-error.md)），量级变化不大——但**结果的具体数值变了**，而且（`atomicAdd` 路线下）每次运行还不一样。如果下游做了「与上一次输出逐位比较」这类检查，就会报出并不存在的 bug。

**规避**：把「是否允许切 K」当成一个**数值契约**问题而不是纯性能问题，与调用方明确约定。训练里要求可复现实验时，必须用确定性路线（§2.1）；推理里只要误差在容差内即可。同时注意 `K/S` 变小会改变累加的树形结构——如果下游对某几个特定的、接近 0 的输出元素敏感（[01 篇](01-naive-gemm-and-roofline.md) §4.2 讲的那种），`S` 的变化可能在那些元素上放大相对误差。

## 6. 小结与延伸

本文一条主线：**瘦高 GEMM 的并行度由 `(M/BM)(N/BN)` 决定、与 K 无关，切 K 是唯一填满机器的手段；而切 K 的代价是归约，`atomicAdd` 路线的归约顺序由硬件决定、结果逐位不可复现。** 围绕它有三个可独立复用的中间结论：

1. 并行度收益是 `×S`，代价是 `2·S·MN·esize` 的归约流量。对照场景（`M=N=256, K=65536`）的有用窗口是 `S ∈ [33, 81]`——下界由机器填满决定，上界由归约开销吃掉收益决定。**窗口很窄，且随 K 变小而收窄。**
2. **split-K 与 Stream-K 的区别在切法**：split-K 每个 tile 固定切 `S` 段、网格是 `T·S`（量化）；Stream-K 把全部 `(tile, k-chunk)` 工作对均匀分给固定的 `P` 个 block（网格严格等于机器槽位数，负载不均 ≤ 1 个工作对）。**Stream-K 更平滑，但仍不确定。**
3. 确定性是**可选的**：workspace + 固定顺序归约（第二个 kernel 或信号量自旋）给出逐位可复现的结果，`atomicAdd` 不给。这不是切 K 的属性，是归约路线的属性。

确定性这条线在本域还有另一个出口：[40-kernels/reduce-scan/04-multi-block-and-determinism](../reduce-scan/04-multi-block-and-determinism.md) 讲的是同一个机制在跨 block 归约里的形态（同样的「顺序决定结果」+ 同样的「两条路线」），两者互为印证。而「什么时候需要确定性」是一个**契约**问题而不只是性能问题——训练需要，推理通常不需要，同一份内核会被两类调用方以不同的方式使用。

到这里，本主题的六篇走完了 GEMM 的完整路径：**朴素（[01](01-naive-gemm-and-roofline.md)）→ HBM 分块（[02](02-shared-memory-tiling.md)）→ 寄存器分块与占用率（[03](03-register-tiling-and-occupancy.md)）→ tensor core 与异步流水（[04](04-tensor-core-and-async-pipeline.md)）→ persistent 与 TMEM（[05](05-persistent-kernel-and-tcgen05.md)）→ 并行度不足时的切 K（本文）**。六步里每一小步都在回答同一个问题：**这一层的复用，够不够把下一层的带宽喂饱。**
