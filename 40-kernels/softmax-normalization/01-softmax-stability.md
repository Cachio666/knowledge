# softmax 的数值稳定性

> 减 max 在实数域**恒等**，它只把 `exp` 的输入从 `(−∞, +∞)` 挪到 `(−∞, 0]`。这个改动的全部价值可以压成一行：**fp16 的 `exp` 在 `x > 11.0901` 时变成 `inf`，而 `x − max ≤ 0` 时永远不变。** `88.72` 是 fp32 的阈值，不是 fp16 的。

## 0. 背景与动机

先给一个具体场景：**fp16 的 attention logits，序列长度 4096，logit 的量级到 ±30**。

一个刚学 CUDA 的人会这样写内核：算出 logits 向量，然后每个位置 `y_i = exp(x_i) / Σ_j exp(x_j)`。这份代码在 fp32 下跑了半年没出过问题——数学上它也确实没问题。换成 fp16 之后，4096 个输出里出现了 **372 个 `nan`**（推导值，`make verify` 的 §C1 在 logits ~ N(0,1)×8 上打印的就是这一行），其余位置也全乱。

他的第一反应是「fp16 精度不够」，于是去查 fp16 有多少位有效数字、去算 `2^-11` 的舍入误差、去考虑要不要上 bf16。**方向全错。** 出问题的不是有效位数，是**可表示范围**：`exp(32.7) = 1.6e14`，而 fp16 能表示的最大有限数是 `65504`。`exp` 的结果在存进 fp16 的那一刻就已经是 `inf`；`inf` 加起来还是 `inf`；`inf / inf = nan`。整行失效的**起点是 372 个 logit 越过了 `11.0901`**，与精度无关。

本文要做三件事：

1. 把「减 max」这个恒等变形写清——它为什么不改变数学结果；
2. 把**溢出与下溢的边界算准**，给出 fp16 / fp32 的四个数字，并把「同一精度在两个不同计算域下阈值不同」这件事讲明；
3. 把「减 max 之后还剩哪些数值问题」交代干净——减 max 解决的是范围，不是全部。

第三步尤其重要：减 max 之后 `l = Σ exp(x_i − max)` 仍然要累加，而**这个累加的格式**才是剩下的那个真问题（§4.3）。

## 1. 原理

按六步推导。前三步是恒等变形与边界的定义，后三步把数字算出来。

### 第一步：恒等变形

设 `m` 是任意**有限**常数。分子分母同乘 `exp(−m)`：

```text
y_i = exp(x_i) / Σ_j exp(x_j)
    = [exp(x_i)·exp(−m)] / [Σ_j exp(x_j)·exp(−m)]
    = exp(x_i − m) / Σ_j exp(x_j − m)
```

最后一步用了 `exp(a)·exp(b) = exp(a+b)`。**这一步对任意 `m` 成立**，不要求 `m = max x`。取 `m = max x` 只是为了让指数落在 `(−∞, 0]` 这个最好用的区间里。

`make verify` 的 §A1 把这件事直接跑了出来：`n = 4096`、`logits ~ N(0,1)×8` 的输入上，**不减 max 的 fp64 实现**与 `scipy.special.softmax` 的最大绝对误差是 `1.110e-16`——在 fp64 里，不减 max 完全正确。所以「减 max」不是算法修正，是**数值工程**。

### 第二步：它改变的是可表示范围

| 写法 | `exp` 的输入 | `exp` 的输出 |
|---|---|---|
| 不减 max | `x_i`，理论范围 `(−∞, +∞)` | `(0, +∞)` |
| 减 max | `x_i − max`，范围 `(−∞, 0]` | `(0, 1]` |

上界从「无界」变成 1，下界不变。`make verify` 的 §C1 断言了这条：减 max 之后 `exp` 的最大值**恒为 `1.0`**（max 那一项是 `exp(0)`），而且与 logit 的绝对大小无关——`scale = 4 / 8 / 11 / 12` 四组输入下它都是 `1.0`。

### 第三步：定义「溢出边界」——是舍入，不是解析值

「`exp` 在什么时候溢出」这句话必须先定口径，否则会得到两个都对但不同的答案。本文用的口径是：**把 `exp(x)` 的结果舍入到目标格式，看它变成什么。**

- **上溢边界** `x_ovf` = 使得舍入结果为 `inf` 的最小 `x`。
  在不考虑舍入时，`exp(x) > M`（`M` = 最大有限数）就会溢出。但**加上了舍入**，真正的门槛是 `M` 与它上方最近的那个可表示值的**中点**：低于中点的值会向**下**舍入到 `M`，仍然安全。

- **下溢边界** `x_unf` = 使得舍入结果为 `0` 的最大 `x`。
  同理，门槛是**最小次正规数的一半**——低于它才舍入到 0。注意这里是「次正规」，不是「正规」：正规数下面还有一整段可以用，`exp(x)` 落在次正规区时值仍然存在，只是精度掉了。

### 第四步：把四个数字算出来

**fp16，上溢。** 最大有限数是 `65504 = (2 − 2^-10)·2^15`。它在 `[2^15, 2^16)` 这一档里，档内步长 `2^15 · 2^-10 = 2^5 = 32`，所以「上方最近的可表示值」是 `65504 + 32 = 65536`——而 `65536 = 2^16` 在 fp16 里**就是 `inf`**。中点：

```text
x_ovf(fp16) = ln[(65504 + 65536)/2] = ln 65520 = 11.090110718526951
```

**fp16，下溢。** 最小次正规数是 `2^-24 = 5.960464e-08`，它的一半是 `2^-25`：

```text
x_unf(fp16) = ln(2^-25) = −25·ln 2 = −17.328679513998633
```

**fp32，同两步：**

```text
x_ovf(fp32) = ln(FLT_MAX)         = 88.72283905206835
x_unf(fp32) = ln(2^-149 / 2)      = −150·ln 2 = −103.97207708399179
```

四个数合起来：

| 精度 | `exp` 上溢（→ `inf`） | `exp` 下溢（→ `0`） |
|---|---|---|
| fp16 | `x > 11.0901` | `x < −17.3287` |
| fp32 | `x > 88.7228` | `x < −103.9721` |

`make verify` 的 §B1 用**二分搜索**把这四个数重新扫了一遍（判据是「舍入后的结果是不是 `inf` / `0`」，不是「超过某个解析值」），与上面的解析值逐条吻合，相对差在 `3.36e-10` 以内。

**这张表里有两处必须写清，否则数字就错了。**

**其一：`ln 65504 = 11.089866`，不是 `11.0938`，也不是阈值。** 前者是「最大有限数」本身的对数，后者是在 **float16 域里算 `log`** 被舍入污染的产物：

```text
math.log(65504)                    = 11.089866488461016   ← 正确（输入先转 float64）
np.log(np.finfo(np.float16).max)   = 11.09375             ← 污染（在 fp16 域里取 log）
```

`np.log` 拿到一个 fp16 标量，就在 fp16 域里算：它先把结果舍到 `11.09375`，再返回。两个数差 `3.884e-3`——比本文全部其它误差都大。`make verify` 的 §B1 把这条做成了断言（防坑断言 1）。

而 `11.089866` 本身也**不是**阈值：阈值是它上方半个 ulp 处的 `ln 65520 = 11.0901`。两者差 `2.44e-4`，正好是一整段 logits 的宽度。

**其二：fp32 的下溢不是 `−88.03`。** `−88.03` 对应的是 `2^-127`，那是**最小正规数**的一半，不是最小次正规数的一半。在 `x = −88.03` 处：

```text
exp(−88.03) 在 fp32 里 = 5.875661e-39     ← **非零**
```

它是一个次正规数（fp32 的最小正规数是 `2^-126 = 1.1755e-38`），好好地在 fp32 里待着。把 `−88.03` 当阈值会把边界写早 16 个数量级。**两个精度的下溢判据必须同一口径**，`make verify` 的 §B1 把这条做成了断言（防坑断言 3）。

### 第五步：同一精度、两个计算域，阈值不同

上面那张表用的是「**在 fp32/fp64 域里算 `exp`，结果再舍入存进 fp16**」的口径。这是最常见的工程情形：数据以 fp16 存在显存里，读进来先转 fp32 做计算，算完转回 fp16 存出去。本文把这个口径记作 **HOST**。

另一种口径是全程 fp16（输入先量化到 fp16，`exp` 也在 fp16 域里算），记作 **NATIVE**。此时**阈值不再是 11.0901，因为它根本不是一个可表示的点**。fp16 在 `[8, 16)` 这一档的格宽是 `2^15 · 2^-10 = 2^-7 = 0.0078125`，这一段里可表示的点是：

```text
11.0859375   11.09375   11.1015625   11.109375   ...
```

`11.089866`（`ln 65504`）和 `11.0901`（`ln 65520`）都**落在这条格缝里**，取不到。NATIVE 口径下能说的是：

```text
x = 11.0859375  →  exp = 65248.0   （安全，fits in fp16）
x = 11.09375    →  exp = inf       （溢出）
```

`np.float16(11.09)` 实际取到的是 `11.09375`，`exp` 就是 `inf`——所以「fp16 的阈值是 11.09」这句话在 NATIVE 口径下意味着「**11.09 已经在死的那一侧了**」。`make verify` 的 §B1 把这两行都断了出来（防坑断言 2）。

**写文档时必须两个口径都写。** 本文后面讨论「logit 越过阈值」时用的是 HOST 口径（因为 logits 通常是 fp32 算出来再存 fp16 的），并明确标注。

### 第六步：减 max 之后还剩什么

减 max 把上溢彻底消掉了（输出区间是 `(0, 1]`），但留下两件事：

**(a) 下溢丢掉小项。** 若 `x_i − max < −17.3287`（fp16 口径），`exp` 舍入后是 `0`，这一项被**静默丢弃**。它是良性的，因为可以界定：丢掉的一项 < `2^-25`，而分母 `l ≥ 1`（max 那一项贡献 `exp(0) = 1`），所以整行的相对误差上界是

```text
n · 2^-25   （fp16）        n · 2^-150   （fp32）
```

`n = 4096` 时 fp16 的界是 `1.2207e-4`，`n = 16384` 时是 `4.883e-4`（`make verify` §B2）。

**(b) `l` 本身的累加。** 这是真问题：`l = Σ exp(x_i − max)` 是 `n` 个正数求和，如果累加器是 fp16，误差会到 `1e-2` 量级。这不是「减 max 没做对」，而是「做对了之后还剩的那部分」（§4.3）。

顺带一条常被写错的：**`max` 本身不需要特别的精度处理**。它是输入里的一个值，原样存下来不引入新误差；即便向下舍入半个 ulp，`x − max` 的上界也只有 `ulp/2`，`exp` 不可能因此上溢。真正存在的混合精度陷阱是**累加 `l` 时的精度**，不是 `max` 的存储格式。

## 2. 执行映射

### 减 max 的代价是一次额外的归约

朴素 softmax 只需要一遍：读 `x`、算 `exp`、累加、再除。减 max 之后先要知道 max，而 max 必须看完整行才能定——所以至少**多一遍对 `x` 的读**。

这一遍在现代 GPU 上不是「再读一遍显存」那么简单，它是一次 **block 级归约**。4096 个元素、256 个线程的内核里，这个归约走两条路：

- **warp 内**：`__shfl_down_sync` 五步（`32 → 16 → 8 → 4 → 2 → 1`），每步一条 shuffle 指令；
- **warp 间**：每个 warp 的 lane 0 把局部和写进 shared memory，再让第一个 warp 读出来做一次同样的五步归约。中间两次 `__syncthreads()`。

数字量级（规格值）：shared memory 命中延迟 **20~30 周期**，一次片外访存往返 **400~800 周期**，每个 SM 最多每周期发射 **4** 条指令（4 个 warp scheduler）。所以跨 warp 那一步的真正成本不是两条 shared memory 指令，而是**生产者 warp 与消费者 warp 之间的两次同步**——它把整块线程拴在一起，Warp 级并行的松弛度被这一段收紧。

### 归约本身不贵，字节数贵

把 4096×4096 的 fp16 矩阵跑一遍 softmax（行内 softmax，共 16.777M 个元素）的访存账（推导值，`make verify` §B5）：

| 写法 | 每元素字节 | 总量 | HBM 时间 @ 3350 GB/s |
|---|---|---|---|
| 两遍法（max 一遍 + exp/和一遍 + 写回） | `3·esize` | 100.7 MB | 30.0 µs |
| 融合成一遍（在线 softmax，02 篇） | `2·esize` | 67.1 MB | 20.0 µs |
| 最差写法（exp 结果落回显存再读回来除） | `4·esize` | 134.2 MB | 40.1 µs |

`3350 GB/s` 是 H100 SXM 的 HBM 带宽（规格值，`specs.py`）。这个表里两遍法比融合版多 **33.6 MB**、多 **10.0 µs**——**这就是「减 max」在工程上的全部代价**，也是 02 篇要把它省掉的东西。

### 为什么「多算一点」几乎不要钱

softmax 的算术强度（非超越部分）大约是每元素 2 个浮点操作（一次比较/减、一次乘/除），而 fp16 下每元素要过 4 个字节（读 1 次 + 写 1 次）：

```text
I    = 2 / 4            = 0.5   FLOP/byte
I*   = 67.0e12 / 3350e9 = 20.0  FLOP/byte     （H100，FP32 向量）
I/I* = 0.025            → 带宽受限
```

可达算力只有 `3350e9 × 0.5 = 1.675 TFLOPS`，是 FP32 峰值 `67 TFLOPS` 的 **2.5%**。**这是 softmax 的瓶颈判定**：它在 roofline 上深在带宽区，此时「多算一点」不花钱，「多搬一个字节」才花钱。把 `exp`、减 max、多一次比较全塞进去，只要不增加访存，时间几乎不动。

反过来解一下这个判据：每元素的 FLOP 预算是

```text
I* × 每元素字节 = 20.0 × 4 = 80 FLOP/元素
```

也就是说，**只要 `exp` 的等效代价不超过每元素 80 个 FLOP，softmax 就还是带宽受限的**。（本仓库**不给出** `exp` 在 CC 8.0/9.0 上每 SM 每周期的确切吞吐——编程指南那张表在各版本间口径差异很大，本次未能核实到当前版本的值，已记进 `specs.py` 的 `UNSOURCED`。所以上面这个 `80` 是一个**条件判据**，不是「`exp` 只花 80 FLOP」的结论。）

## 3. 实现与演进

softmax 的实现史可以只用**自变量 `x` 被读了几遍**讲完。本文只完成前两档，后两档留给 02 与 attention 主题。

1. **朴素实现**（本文 §0 的起点）。读 1 遍，`exp(x)` 直接算。范围溢出，fp16 下整行 `nan`。
   对应 `code/01_softmax_stable.cu` 的 `softmax_naive_kernel`。

2. **减 max 的两遍法**（本文的落点）。读 2 遍（max 一遍、`exp`+和一遍）+ 写 1 遍。范围问题解决，剩下 `l` 的累加精度问题（§4.3）。
   对应 `code/01_softmax_stable.cu` 的 `softmax_stable_kernel`。归约用 warp shuffle + shared memory 两级。

3. **融合成一遍**（[02-online-softmax](02-online-softmax.md)）。用在线递推把「先求 max 再求 exp」压成一遍：`(m, l)` 随着数据一块一块地往前滚，新块来了就重标定一次。字节数从 `3·esize` 降到 `2·esize`。

4. **去掉写回与第二遍读**（attention 主题）。`y = exp(x − m)/l` 这一步还要回看 `x`。在 attention 里它被省掉，靠的是同时维护输出累加器 `o`——那是第三条递推，正文在 40-kernels/attention（此处只回链）。

**本文只完成第 1、2 档**，这一篇建立了三样后面要反复用的东西：恒等变形的形式、四个阈值的确切值、以及「softmax 是带宽受限算子」这个判定。

## 4. 踩坑与失败模式

### 4.1 不减 max：fp16 下 `exp` 变成 `inf`，输出出现 `nan`

**现象**：fp16 的 softmax 在 logits 幅度稍大时，输出里出现成片的 `nan`；换成 fp32 就好了。`make verify` 的 §C1 在四组输入上把这条跑了出来（下表是**推导值**，不是 GPU 上的测量）：

| logit 幅度 | max logit | 朴素 `exp` 的 `inf` 数 | 输出 `nan` 数 | 稳定版的 `l` |
|---|---|---|---|---|
| ×4 | 15.180 | 14 | 14 | 2.484375 |
| ×8 | 32.719 | 372 | 372 | 1.010742 |
| ×11 | 39.875 | 644 | 644 | 1.093750 |
| ×12 | 44.125 | 711 | 711 | 1.024414 |

幅度只有 ×4 时就已经有 14 个位置出问题——**门槛比直觉低得多**，因为 fp16 的上溢阈值只有 `11.0901`。

**成因**：`exp` 的输出是 `(0, ∞)`，而 fp16 的上界是 `65504`。对数到 `11.0901` 就够不着了（HOST 口径）。溢出之后：单个 `exp` 是 `inf` → 分母 `Σ exp` 是 `inf` → 每个位置算的都是 `inf/inf = nan`。注意**分母被污染之后，整行 4096 个位置全废**，不只是越界的那 14 个。

**规避**：减 max。这是唯一的手段，也是本文的全部内容。自检办法：在 `exp` 之前断言 `max(x) ≤ 阈值`，或者更彻底——**只要 logits 是 fp16 存的，就不要算 `exp(x)`，永远算 `exp(x − max)`**。

### 4.2 `exp(x − max)` 下溢到 0：项被静默丢弃

**现象**：某个 logit 比 max 低 18 以上时，它对应的输出精确等于 0（`make verify` §C2 的表：`x − max = −17.3287` 时 fp16 的 `exp` 就已经是 `0.0`）。没有报错，没有警告，那个位置的概率就是 0。

**成因**：`exp(x − max)` 的值落到最小次正规数 `2^-24` 的一半以下，舍入到 0。这是**格式的下界**，不是算法错误——那个项的真实权重本来就只有 `1.5e-8` 量级。它在 fp32 里不会发生（fp32 的下溢边界是 `−103.9721`；同一个 `−18` 在 fp32 里是 `1.523e-08`，一个正常的次正规数）。

**规避**：**不要修**。这是良性丢弃，有明确的上界：丢掉一项 < `2^-25`，而 `l ≥ 1`，所以整行相对误差 ≤ `n·2^-25`（§1 第六步）。`n = 4096` 时是 `1.2207e-4`。真正需要警惕的是**当这个「丢」不是发生在 `l` 上、而是发生在别处的累加器上时**——那时它不再是「一个计数少了一点」，而是「一段已经算好的结果被整体抹掉」，见 [02-online-softmax](02-online-softmax.md) §4。

### 4.3 `l` 用 fp16 累加：误差到 1% 以上

**现象**：减 max 做对了，`exp` 也正常，但把 `l` 的和用 fp16 存，输出仍然肉眼可见地偏。`make verify` 的 §C3 扫出来（推导值，fp16 **顺序**累加 vs fp64 参考）：

| `l` 的量级 | `l` 的 fp16 `ulp/2` | 平均项 `l/n` | fp32 顺序累加 | fp16 顺序累加 | fp16 树形归约 |
|---|---|---|---|---|---|
| 549.4 | 0.2500 | 0.13412 | 5.444e-07 | **6.712e-02** | 2.274e-04 |
| 2959.5 | 1.0000 | 0.18063 | 1.048e-06 | **6.205e-01** | 1.622e-04 |
| 95.0 | 0.0312 | 0.02319 | 1.281e-06 | **1.359e-01** | 3.089e-04 |
| 1.41 | 0.0005 | 0.00034 | 6.404e-08 | 2.462e-04 | 2.462e-04 |

**成因**：机制就在第三、四列里。`l` 涨到 `549` 时，fp16 在这一档的 `ulp/2` 是 `0.25`，而每一项平均只有 `0.134`——**项比半个 ulp 还小**，加进去就被舍掉了。`l` 越大越糟：`l ≈ 2960` 时 `ulp/2 = 1.0`，而没有任何单项能超过 1（`exp(x−max) ≤ 1`），于是**每一项都被吞掉**，误差到 `62%`。这不是「精度不够」，是「累加器的分辨率已经被自己的和撑爆了」。

**规避**：`l` 用 fp32 累加（表中每一行的 fp32 误差都 `< 1.6e-5`）。这条规避不需要额外的访存，只是让累加器占 4 字节而不是 2 字节——**在带宽受限的算子里，这几乎不要钱**（§2 的判据）。

**一条必须一起给出的限定**：上表里「fp16 顺序累加」是**一种归约拓扑**。如果换成树形归约（warp shuffle + shared memory，也就是 §2 描述的那套真实内核做法），fp16 的表现好 2~3 个数量级——`l ≈ 549` 那行从 `6.712e-02` 降到 `2.274e-04`（好 295 倍），`l ≈ 2960` 那行从 `6.205e-01` 降到 `1.622e-04`（好 3825 倍）。树形归约的误差按 `u·√(log n)` 涨，顺序累加按 `u·n` 涨。**所以「`l` 不能用 fp16」这句话要带上拓扑才准确。**

即便如此，工程上仍然推荐 fp32 累加器，理由有两个：（a）它同时消掉了 02 篇 §4 那个「整段丢弃」的失败模式；（b）`l` 一旦越过 `65504`，**树形归约也救不回来**——`float16(70000.0)` 直接就是 `inf`，再好的归约树也无从下手。

## 编译与运行

配套程序是 **`code/01_softmax_stable.cu`**，内含三个内核：

- `softmax_naive_kernel` —— 不减 max，对应本文 §0 的起点与 §4.1；
- `softmax_stable_kernel` —— 减 max 的两遍法，warp shuffle + shared memory 两级归约；

它需要 `nvcc` 与 GPU：

```bash
cd code

程序会做四件事：在**运行时**从 `65504`、`FLT_MAX`、`2^-24`、`2^-149` 现算 §1 那四个阈值并打印（这部分是纯 host 算术，与 `make verify` 的 §B1 是同一批数）；统计输入里越过阈值的 logit 个数；分别跑两个内核并统计 `inf` / `nan` 的个数；最后用「不减 max 的 CPU 参考」与稳定内核比对。

- 阈值、字节数、算术强度、以及本文全部表格里的数——**推导值**，由算术得到，可用 `make verify` 的 §A1 / §B1 / §B2 / §B5 / §C1 / §C2 / §C3 逐条复核；

```

## 6. 小结与延伸

全文一条主线：**减 max 是一个恒等变形，它不改变数学结果，只把 `exp` 的输入挪到 `(−∞, 0]`。** 围绕它有三个可独立复用的结论：

1. **四个阈值**：fp16 的上溢/下溢是 `11.0901` / `−17.3287`，fp32 是 `88.7228` / `−103.9721`。上溢判据是「最大有限数与其上方可表示值的中点」，下溢判据是「最小**次正规**数的一半」——两个精度必须同一口径。
2. **两套口径**：fp16 域里不存在 `11.0900` 这个点。`11.0859375 → 65248.0` 与 `11.09375 → inf` 是相邻的两个可表示点，`11.0901` 属于「fp32 域算 `exp` 再舍入存 fp16」的口径。`ln 65504 = 11.089866` 是表观值，不是阈值；在 fp16 域里取 `log` 会得到 `11.09375`。
3. **瓶颈判定**：softmax 的算术强度是 `0.5 FLOP/byte`，`I* = 20`，深在带宽区。**多算不花钱，多搬一个字节才花钱**——这是本文之后每一篇优化的前提。

后面两篇：

- [02-online-softmax](02-online-softmax.md) 解决本文 §2 那笔「多读一遍」的账：把 `3·esize` 降到 `2·esize`，代价是状态重标定。**在线 softmax 的 `(m, l)` 更新公式的正文在那里**，attention 主题回链该处；
- [03-normalization-fusion](03-normalization-fusion.md) 换一类算子——LayerNorm 与 RMSNorm 也需要均值与方差，但它们要的是**整个一行的两个统计量**，而不是逐元素的归一化因子，于是 Welford 单遍 / 两遍 / `Σx² − nμ²` 三种写法摆上台面。

本文**只推导了「减 max 为什么有用、边界在哪」这一条线**，在线递推、Welford、`eps` 的位置这三条都不在本文。
