# 在线 softmax 与重标定

> 减 max 需要先看完整行——这在 attention 里做不到，而且要多读一遍显存。在线 softmax 把「先求 max 再求 exp」压成一遍：维护一对 `(m, l)`，新块来了就重标定一次。**本文是 `(m, l)` 更新公式的正文**：`m_new = max(m_old, max(块内 x))`，`l_new = l_old·exp(m_old − m_new) + Σexp(x − m_new)`。

## 0. 背景与动机

[01 篇](01-softmax-stability.md) 的落点是两遍法：先归约出 `max`，再算 `exp(x − max)` 与它的和。它解决了范围问题，但留下两笔账。

**第一笔是访存。** 4096×4096 的 fp16 矩阵上，两遍法是 `3·n·esize = 100.7 MB`，融合成一遍是 `2·n·esize = 67.1 MB`——按 H100 的 `3350 GB/s` 折算，`30.0 µs` 对 `20.0 µs`（推导值，`make verify` §B5）。softmax 是带宽受限算子（`I = 0.5 FLOP/byte`，`I* = 20`），省下 33.6 MB 就是实打实省下 10 µs。

**第二笔更硬：有些场景根本不允许两遍。** attention 里 softmax 的分母要跨越整条 KV 序列求和，而 KV 是一块一块流过芯片的——你不可能先把长度为 `seq_len` 的所有 logits 都留住。同理，`seq_len` 到 `1e5` 量级时，一行 logits 本身就装不下。**两遍法要求「先看完全部数据，再从头算一遍」，这在流式场景里是不成立的。**

在线 softmax 用一个观察把这两笔账一起消掉：**归一化的基准 `m` 不必一开始就取到最终值，它可以随着数据推进一步步抬高，每抬高一次就把已经累积的结果重标定一次。** 最终基准必然收敛到全局 max，因为数据是有限的。

本文只交付一件事：**把 `(m, l)` 的更新公式逐项推出来，并说清它为什么正确。** 这条递推是 attention 主题的正文来源（那边会回链此处）。至于 attention 里同时维护的输出累加器 `o` 的第三条递推，正文在 40-kernels/attention（此处只回链）。

## 1. 原理

### 记号与不变量

把长度为 `n` 的输入 `x` 切成 `T` 块 `B₁, …, B_T`（大小任意，只需覆盖全部元素）。记 `S_t = B₁ ∪ … ∪ B_t` 为前 `t` 块的并集，约定 `S₀ = ∅`。定义一对状态：

```text
m_t = max{ x_j : j ∈ S_t }                       （m₀ = −∞）
l_t = Σ_{j ∈ S_t} exp(x_j − m_t)                 （l₀ = 0）
```

**不变量**是：`l_t` 等于「把**已经见过的全部元素**按**当前的** `m_t` 归一化之后的 exp 之和」。

这个不变量正是我们要的东西。取 `t = T`：`S_T` 是全体的下标集合，所以 `m_T = max_j x_j`，`l_T = Σ_j exp(x_j − m_T)`——**与两遍法要算的两个量逐字相同**。

于是问题变成：能不能在**只读一遍**、且**不回看旧元素**的前提下，把 `(m_t, l_t)` 推到 `(m_{t+1}, l_{t+1})`？答案是能，而且只用一个恒等式。

### 递推的推导

**第一步：`m` 的更新。** 新集合 `S_{t+1} = S_t ∪ B_{t+1}`，所以

```text
m_{t+1} = max(m_t, max{ x_j : j ∈ B_{t+1} })
```

右端只用到 `m_t`（一个标量）和新块本身。这一步不需要旧元素。

**第二步：拆开 `l_{t+1}` 的定义式。** 把求和按「旧元素 + 新元素」分成两段：

```text
l_{t+1} = Σ_{j ∈ S_{t+1}} exp(x_j − m_{t+1})
        = Σ_{j ∈ S_t}      exp(x_j − m_{t+1})        ← 旧元素，归一到**新**基准
        + Σ_{j ∈ B_{t+1}}  exp(x_j − m_{t+1})        ← 新元素，同样归一到新基准
```

第二项只用得到新块——它已经可以直接算了。第一项是问题所在：它要对一堆**已经流过去的**元素重新算 `exp`。如果不做点什么，这就退化成两遍。

**第三步：把「基准的移动量」从求和号里提出来。** 对任意 `j ∈ S_t`，把指数拆成两段：

```text
x_j − m_{t+1} = (x_j − m_t) + (m_t − m_{t+1})
```

注意后一段 `m_t − m_{t+1}` **与 j 无关**，是一个标量。用 `exp(a + b) = exp(a)·exp(b)`：

```text
exp(x_j − m_{t+1}) = exp(x_j − m_t) · exp(m_t − m_{t+1})
```

**这一步是整条推导唯一的支点。** 它把「按新基准归一化」换成了「按旧基准归一化，再整体乘一个常数」。

**第四步：代回求和号。** 那个常数与 `j` 无关，可以提到求和号外：

```text
Σ_{j ∈ S_t} exp(x_j − m_{t+1})
  = exp(m_t − m_{t+1}) · Σ_{j ∈ S_t} exp(x_j − m_t)
  = exp(m_t − m_{t+1}) · l_t
```

右边的 `l_t` **就是旧状态本身**——「旧元素按旧基准归一化之和」这件事，在 `t` 时刻已经算完并压成了一个数。求和号里对 `j` 的依赖消失了。

**第五步：合起来。** 记 `α = exp(m_t − m_{t+1})`：

```text
l_{t+1} = l_t · α + Σ_{j ∈ B_{t+1}} exp(x_j − m_{t+1})          （★）
```

这就是全部的更新公式。写成算法：

```text
m_new = max(m_old, max(x ∈ 本块))                        （1）
l_new = l_old · exp(m_old − m_new) + Σ exp(x − m_new)    （2）
```

### 为什么这个递推正确

用归纳法。**基例**：`t = 0`，`S₀ = ∅`，`m₀ = −∞`，`l₀ = 0`，不变量成立（空和是 0）。**归纳步**：设 `l_t = Σ_{j∈S_t} exp(x_j − m_t)`，代入第三步与第四步的变形即得 `l_{t+1} = Σ_{j∈S_{t+1}} exp(x_j − m_{t+1})`。所以对**任意**分块方式、**任意**块数 `T`，最终状态都等于两遍法的结果。

`make verify` 的 §A2 把这条断言跑成了表格：`n = 4096` 的输入，分块 `∈ {16, 32, 128, 1024, 4096}`、顺序 `∈ {原序, 递增, 递减}`、切法 `∈ {连续切片, 步长切片}`，共 30 种组合，fp64 状态下与两遍法的最大相对误差 **`3.456e-15`**。“步长切片”指的是让线程 `t` 处理 `x[t::block]`——这时每个线程自己维护一对 `(m, l)`，等价于把同一份数据用另一种分组方式喂给同一个递推。

### 一个可以手算的例子

`x = [2, −1, 4, 0]`，切成两块 `B₁ = [2, −1]`、`B₂ = [4, 0]`。逐项算（`make verify` 的 §A3 把每一步都打印了出来）：

```text
块 1：m₁ = max(2, −1) = 2
      l₁ = exp(2 − 2) + exp(−1 − 2) = 1 + exp(−3)
         = 1.0497870683678638

块 2：块内 max = 4
      m₂ = max(m₁, 4) = 4
      α  = exp(m₁ − m₂) = exp(−2) = 0.1353352832366127
      Σexp(x − m₂) 在新块上 = exp(4 − 4) + exp(0 − 4) = 1 + exp(−4)
                            = 1.0183156388887342
      l₂ = l₁ · α + 1.0183156388887342
         = 1.0497870683678638 × 0.1353352832366127 + 1.0183156388887342
         = 0.14207323023569815 + 1.0183156388887342
         = 1.1603888691244324
```

**验算**：直接按 `m = 4` 的两遍法算

```text
l = exp(2−4) + exp(−1−4) + exp(4−4) + exp(0−4)
  = exp(−2) + exp(−5) + 1 + exp(−4)
  = 1.1603888691244324
```

两者**逐位相同**。这不是巧合：`l₁ · α` 展开就是 `1·exp(−2) + exp(−3)·exp(−2) = exp(−2) + exp(−5)`——第三步那个「提公因子」正好把两块拼回了同一个基准。

### `α` 的方向：`m_old ≤ m_new` 恒成立

`m` 是 max，所以它**单调不减**：`m_t ≤ m_{t+1}` 对每个 `t` 成立。于是

```text
α = exp(m_old − m_new) ∈ (0, 1]
```

`α` **恒不大于 1**：它只会把已经累积的 `l` 缩小，绝不会放大。所以乘 `α` 这个动作本身**不可能造成上溢**——最坏情况是 `α` 下溢到 0，那是 §4.2 的话题。

方向写反（用 `exp(m_new − m_old)`）会立刻出事：那个因子可以是 `exp(+20)` 量级，在 fp16 里直接是 `inf`。这不是一个「数值差一点」的错误，是一个数量级级别的错误。

### 结合律：为什么分块方式无关

把状态写成一个二元组，并定义合并算子 `⊕`：

```text
(m_a, l_a) ⊕ (m_b, l_b) = ( M, l_a·exp(m_a − M) + l_b·exp(m_b − M) ),  M = max(m_a, m_b)
```

这个定义**就是**（1）（2）两式——把「旧状态」和「新块」都看成同一类对象。单位元是 `(−∞, 0)`（空集）。

`⊕` 满足**结合律**。验证的思路：两边最终算出的都是「按 `max(m_a, m_b, m_c)` 归一化的、三个集合全部元素的 exp 之和」——也就是 `l` 的定义式本身，而定义式与括号怎么加无关。这也解释了为什么最终结果必然是唯一的：**无论怎么分组，`(m_T, l_T)` 收敛到的都是同一个定义式。**

`make verify` 的 §A2 用两种切法（连续 / 步长）交叉验证了这一点；`code/02_online_softmax.cu` 的 `softmax_online_order_kernel` 更进一步——它接受一个块序数组，正序、逆序、随机置换各跑一遍，结果必须一致。

**这条性质是本文能落到工程上的全部依据**：它让一个 block 内的乱序归约（warp shuffle 的树形合并）成立，也让 attention 能把 KV 切成任意块流式推进。

## 2. 执行映射

### 一个 block 里怎么落地

两层结构，都用同一个 `⊕`：

**线程级**。每个线程用步长切分（`for i = tid; i < n; i += blockDim.x`）处理自己的那一段，在寄存器里维护自己的一对 `(m, l)`，逐条套用（1）（2）。这一步天然就是流式的——线程只看自己手里的元素。

**block 级**。归约时**不能**先各自算 `l` 再相加（那等于假设所有线程共享同一个 `m`，而它们各自的 `m` 不同）。要归约的是二元组 `(m, l)`，合并式就是 `⊕`：先 `__shfl_down_sync` 把两个 lane 的 `(m, l)` 并起来，五步之后每个 warp 得到一个 `(m, l)`；lane 0 写进 shared memory；第一个 warp 再做一次同样的五步。**与 01 篇的 max 归约相比，每一步从一条 shuffle 变成两条**（`m` 与 `l` 各一条），外加一次 `exp` 算 `α`；warp 间的 shared memory 阵列也从一份变成两份。

代价（规格值）：shared memory 延迟 **20~30 周期**，一次片外访存往返 **400~800 周期**，每 SM 每周期最多发射 **4** 条指令。归约这一步是三倍指令，但它是 `O(log n)` 的、只在行末发生一次，与逐元素的循环不是一个量级。

### 每元素多算了什么

重标定本身的开销是**每块一次**，不是每元素一次：

```text
每块：1 次 max（块内）+ 1 次 exp（算 α）+ 1 次乘（l·α）
```

一个 `n = 4096` 的行切成 32 块，摊到每个元素上是 `1/128` 次 `exp` 和 `1/128` 次乘。**相比省下的 33.6 MB 访存（10.0 µs），这点算术可以忽略。** 这正是 §0 说的「softmax 是带宽受限算子，多算不花钱」。

### 访存账

| 写法 | 每元素字节 | 4096×4096 fp16 总量 | HBM 时间 @ 3350 GB/s |
|---|---|---|---|
| 两遍法（01 篇） | `3·esize` | 100.7 MB | 30.0 µs |
| 在线（本文） | `2·esize` | 67.1 MB | 20.0 µs |

比值 `2/3`。这笔账成立的前提是**一个 block 能吃下一整行（或至少一段）并把它留在片上**：`n = 4096`、fp16 时一行是 `8.0 KB`，每 SM 的 shared memory 上限是 `228 KB`，放得下（推导值，`make verify` §B6）。行再长就得回显存读第二遍——那是 03 篇和 attention 主题各自要面对的形态。

### attention 里它长什么样

（本节只交代形态，正文在 40-kernels/attention，此处回链。）

attention 的每一行是「一个 query 对全部 key 的注意力分布」。KV 序列沿 `seq_len` 切成块流过来，每来一块：

```text
新块 logits = Q · K_blockᵀ          （形状 1 × block）
块内 max   = max(新块 logits)
m_new     = max(m_old, 块内 max)
l_new     = l_old·exp(m_old − m_new) + Σ exp(新块 logits − m_new)
```

到这里为止与本文的（1）（2）逐字相同。差别在于 attention 还要同时产出一个加权和 `o = Σ exp(x_j − m) v_j`，它**也要被同一个 `α` 重标定**：

```text
o_new = o_old·exp(m_old − m_new) + Σ exp(新块 logits − m_new) · v_block
```

**这第三条递推的正文在 40-kernels/attention。本文只推导 (m, l) 两条**，不在这里展开，也不留「见下篇」的悬空承诺——上面这一行是**结论**，它的推导过程在那边。

## 3. 实现与演进

按「`x` 被读了几遍、以及能不能流式」两个维度：

1. **两遍法**（01 篇）。读 2 遍，**不能流式**——必须先看完全部数据才能定 `m`。
2. **在线 softmax**（本文）。读 1 遍，**能流式**。状态是一对 `(m, l)`，每块重标定一次。数值上与两遍法一致（`make verify` §A2：fp64 最大相对误差 `3.456e-15`，fp32 状态最大 `9.788e-06`）。
3. **在线 + 输出累加器**（attention 主题）。把 `o` 也纳入重标定，于是连「回看 `x` 写 `y = exp(x−m)/l`」那一步也省掉——但代价是必须把 `o` 留在寄存器/片上，`o` 的大小与 `d_head` 成正比。这是 FlashAttention 那一系的形态。
4. **在线 + 更少重标定**（工程变体）。既然重标定是每块一次，增大块就能减少次数。但**减少重标定次数并不带来数值收益**（§4.3），它只影响指令数。

`code/02_online_softmax.cu` 里给了三个内核：`softmax_two_pass_kernel`（基准）、`softmax_online_kernel`（线程级在线 + block 级 `⊕` 归约）、`softmax_online_order_kernel`（块序可控，用来验证结合律）。

## 4. 踩坑与失败模式

### 4.1 把「`m` 单调递增」误读成「`m` 可以不更新」

**现象**：既然 `m` 只会往上涨，那就一次定下来——用第一块的 max，或者干脆预设一个上界（比如 `m ≡ 0`）。这样连 `α` 都不用算了，代码更简单，而且省掉了每块一次 `exp`。

`make verify` 的 §C4 在「前两块 logits 都在 0 附近、第三块里出现一个 20」的三块数据上跑了三种策略：

| 策略 | fp16 终态 `l` | fp32 终态 `l` |
|---|---|---|
| A 按递推更新 `m` | 1.000000（正确） | 1.000000 |
| B 冻结 `m = 0.1`（第一块的 max） | **inf** | 4.38996e+08 |
| C 预设 `m ≡ 0` | **inf** | 4.85165e+08 |

正确答案是 `1.0000000170054972`（`make verify` §C4 的 fp64 结果）——第三块的 `20` 是全局 max，所以 `l` 应该 ≈ 1。

**成因**：不更新 `m` 时，块内算的是 `exp(x − m_old)`，而 `m_old` 可以比块内 max 小很多，指数直接冲出格式范围。`exp(20)` 在 fp16 里是 `inf`（上溢阈值只有 `11.0901`，见 [01 篇](01-softmax-stability.md) §1）。注意 fp32 那一列：它**不溢出**，但结果是 `4.39e8`——错了 8 个数量级。**溢出只是这种错误里最显眼的一种，不溢出的时候它同样致命。**

**规避**：`m` 必须每块都更新。这条与「`m` 单调递增」是**两件事**：单调性是递推**保住**的性质（`m_old ≤ m_new` 是 max 的定义直接给的），而「延后/冻结更新」是主动放弃它。前者不需要规避，后者必须规避。

### 4.2 rescale 因子下溢：分块贡献被静默丢弃

**现象**：`α = exp(m_old − m_new)` 在 `m_new − m_old` 足够大时舍入到 `0`，于是 `l_old · α = 0`——**整段已累积的贡献在一次乘法里消失**。`make verify` 的 §C5：

| `gap = m_new − m_old` | fp64 的 `exp(−gap)` | fp32 状态 | fp16 状态 |
|---|---|---|---|
| 10.0 | 4.539993e-05 | 4.539993e-05 | 4.541874e-05 |
| 17.0 | 4.139938e-08 | 4.139938e-08 | 5.960464e-08 |
| **17.3287** | 2.980171e-08 | 2.980171e-08 | **0.000000e+00** |
| 20.0 | 2.061154e-09 | 2.061154e-09 | **0.000000e+00** |
| 104.0 | 6.813557e-46 | **0.000000e+00** | 0.000000e+00 |

**成因**：这是 [01 篇](01-softmax-stability.md) §1 的下溢阈值在这里的具体形态。fp16 的归零点在 `−17.3287`（`= −25·ln2`，最小次正规数的一半），fp32 在 `−103.9721`。**状态存 fp16 时，`m` 只要在某一跳里抬高 17.33 以上（这在 logits 幅度 ±30 的场景里很常见），前面所有块的贡献一起归零。**

丢掉的量有上界：`l_old` 本身受 fp16 上限 `65504` 约束，所以一次丢弃最多丢掉

```text
65504 × 2^-25 = 1.952171e-03
```

相对新块的 `l`（`≥ 1`）是 `0.1952%`，约等于 fp16 的 `4.0` 个 `u`。**可见，但不是灾难。** `make verify` 的 §C5 还给了一个能从头算到尾的两块例子：前段 60000 项都等于 0（`l_old = 60000`），后块只有一个 `20`——

```text
真值 l = 60000·exp(−20) + 1 = 1.0001236692
fp32 状态：α = 2.061154e-09，l = 1.0001236200，相对误差 4.918e-08
fp16 状态：α = 0，           l = 1.0000000000，相对误差 1.237e-04  ← 整段丢弃
```

**规避**：状态 `(m, l)` 用 **fp32**。这条不需要额外思考，只需要不要顺手把它声明成 `half`。fp32 的对应阈值是 `103.9721`，在真实 logits 范围内不可达。

**真正的灾难在另一处**：当 `l_old` 本身就超过 fp16 的上限 `65504` 时，状态在**累加阶段**就已经变成 `inf`，后面的 rescale 全是 `inf × 0 = nan`。这与 [01 篇](01-softmax-stability.md) §4.3 是同一个根因（`float16(70000.0)` 直接就是 `inf`）。

还有一处必须点名：**同一个 `α` 还要乘到 attention 的输出累加器 `o` 上**。那里丢掉的不是「一个计数」，而是已经算好的输出向量。fp32 状态同样能消掉这个问题。

### 4.3 为了「少 rescale」去预扫 max 或排序

**现象**：读完 §1 会得到一个很自然的推论——每次抬高 `m` 都要乘一次 `α`，那就引入一次舍入；`m` 抬高的次数等于「前缀 max 发生变化的次数」。于是有人会想去**减少抬升次数**：先扫一遍拿到全局 max（那就退回两遍法了），或者把数据排个序让 `m` 尽快升到顶。

`make verify` 的 §C6 把这条推论直接测了。同一份 `n = 4096`、`logits ~ N(0,1)×4` 的数据，用排序制造出完全不同的抬升次数：

| 输入顺序 | 分块 | rescale 次数 | fp32 相对误差 | fp16 相对误差 |
|---|---|---|---|---|
| 原序 | 128 | 3 | 4.363e-07 | 1.410e-03 |
| 递增 | 128 | **31** | 4.363e-07 | 8.017e-04 |
| 递减 | 128 | **0** | 2.136e-07 | 8.017e-04 |

**rescale 次数从 0 变到 31，误差没有随之单调增长**——递增序（31 次）的 fp32 误差与递减序（0 次）在同一个量级，甚至常常更低。

**成因**：每次 rescale 只引入**一次乘法舍入**，相对误差 `~u`；`k` 次就是 `~k·u`。而真正主导误差的是 **`l` 的逐项累加**（[01 篇](01-softmax-stability.md) §4.3），它的量级是 `u·√n` 或 `u·n`。`k`（块的个数）远小于 `n`（元素个数），所以 rescale 那一项被淹没。把 rescale 链单独摘出来量（`make verify` §C6）：连乘 `2048` 次 `exp(−1/k)` 与一次 `exp(−1)` 的相对差只有 **`7.620e-14`**——完全可以忽略。

**规避**：不要为这件事做任何工程改动。分块的依据是**访存与并行度**，不是「减少 rescale 次数」。为了少几次 rescale 去排序，等于花一遍 `n log n` 的代价换掉一个 `1e-14` 量级的误差项。

## 6. 小结与延伸

全文一条主线：**把「先看完全部数据再归一化」换成「边看边归一化，每看一块就把已有结果重标定一次」**。三条式子：

```text
m_new = max(m_old, max(x ∈ 本块))                        （1）
l_new = l_old · exp(m_old − m_new) + Σ exp(x − m_new)    （2）
```

其中（2）的推导只有一个支点：`exp(x_j − m_new) = exp(x_j − m_old)·exp(m_old − m_new)`——**基准的移动量是一个与 `j` 无关的标量，可以提到求和号外**，而剩下的那个求和号里装的正是上一步已经算好的 `l_old`。

围绕它有三个可独立复用的结论：

1. **`α = exp(m_old − m_new) ∈ (0, 1]`**，方向由 `m` 的单调不减保证。写反会溢出，不是精度问题。
2. **`⊕` 满足结合律**，所以分块大小、分块顺序、切法都不影响数学结果（fp64 上 `3.456e-15`，fp32 状态 `9.788e-06`）。这是块内乱序归约与 attention 流式推进的共同依据。
3. **状态必须住 fp32**。fp16 状态的 `α` 在 `gap > 17.3287` 时归零（整段丢弃），而且 `l` 越过 `65504` 就自己变成 `inf`。
