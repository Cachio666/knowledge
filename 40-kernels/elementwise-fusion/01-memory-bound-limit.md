# 访存受限算子的上界与有效带宽

> 一个处理 N 个元素的单目逐元素算子，**最少**要往返 HBM `2N·esize` 字节——读一次、写一次，两项都省不掉（就地写法也一样）。把这个数代进 [roofline](../../10-foundations/performance-models/01-roofline-model.md) 就得到可达时间的下界；而这个下界**是不是有意义的**，取决于三件事：分母用的是标称带宽还是可达带宽、规模够不够大（否则固定开销压倒一切）、以及估算时有没有把「写」算进去。

## 0. 背景与动机

同一张 H100 上放两个算子，它们落在 roofline 的两端：

| 算子 | FLOPs | 往返 HBM 字节 | 算术强度 `I` | 算力时间 | 访存时间 |
|---|---|---|---|---|---|
| prefill 大 GEMM `[4096×8192] @ [8192×8192]` | `5.498e+11` | `2.684e+08` | **2048.0** | 8.2 ms | 80.1 µs |
| `y = exp(x)`，`N = 2^26` | `6.711e+07` | `5.369e+08` | **0.125** | 1.0 µs | **160.26 µs** |

（推导值，`make verify` §B1；roofline 的参数与拐点回链 [10-foundations/performance-models/01](../../10-foundations/performance-models/01-roofline-model.md) §1，本域只做代入。）

第一行算力时间比访存时间大 **102 倍**，第二行反过来小 **160 倍**。`I*`（FP32 向量）= `67.0e12 ÷ 3350e9` = **20.0** FLOP/byte，于是两行的 `I/I*` 分别是 **10240%** 与 **0.625%**。

对照场景就落在这里：**为第二行这个算子做计算侧优化，动的是全部工作量的 0.6%。**

具体一点。有人为一个 `y = exp(x)` 型的 kernel 花了两天：把 `expf` 换成 `__expf`，block size 从 128 试到 1024，加 `__restrict__`，去 `-Xptxas -v` 里数寄存器。每一步都改不动什么，因为**它 99.4% 的时间在做的是把 512 MiB 读进来再写回去**（推导值，§B1：算力时间 1.0 µs ÷ 访存时间 160.26 µs = 0.625%）。那两天里被优化的是这 0.625% 里的一个因子。

**不知道上界，就不知道余量在哪，也不知道该往哪优化。** 本文只回答两个问题：这个算子的**地板**在哪（§1），以及为什么小规模下**地板根本不是访存**（§4.2）。

## 1. 原理

下面五步推导，每一步只引入一个量。第一步是本篇的全部地基——**它错一次，后面每一个数都跟着错一倍**。

### 第一步：数清一个单目算子必须往返 HBM 的字节

一个单目逐元素算子是 `y[i] = f(x[i])`。硬件层面它只有两件事必须做：

```text
读：把 x[i] 从 HBM 取进来      → N·esize 字节
写：把 y[i] 送出去              → N·esize 字节
合计                           → 2N·esize 字节
```

**这个 `2` 是不可省的**：输入住在 HBM 里，不读就没有数据；输出要能被后面的算子看见，不写就不存在。两者都是**运算符**，不是实现细节。

代入 `N = 2^26`、`esize = 4`（fp32）：

```text
N·esize    = 67108864 × 4 = 268435456 B = 256.0 MiB
2N·esize   = 536870912 B   = 512.0 MiB
```

（推导值，`make verify` §B1。）

**关键的一步：就地（in-place）写法不省这一半。** `y[i] = f(y[i])` 仍然要「把 `y[i]` 读进来、算完、写回去」——HBM 层面的流量还是 `2N·esize`。就地省下来的是另外两样东西：

- **容量**：不再需要一块同样大小的输出缓冲（`N = 2^26` 时是 256 MiB）；
- **地址足迹**：触及的 cache line 数减半（读和写落在同一批 line 上）。

但流量一分不少。§4.4 专门讲这个坑。

### 第二步：代入 roofline，得到时间下界

roofline 的时间式是 `t = max(W/P, Q/B)`，其中 `Q` 就是上面那个 `2N·esize`。对逐元素算子，`W/P` 小到可以忽略（第一步已经算过），所以

```text
t ≥ Q / B_peak = 2N·esize / B_peak
```

代入 H100 SXM 的标称带宽 `B = 3350 GB/s`：

```text
t ≥ 536870912 / 3350e9 = 1.6026e-04 s = 160.26 µs
```

（推导值，`make verify` §B1。）

### 第三步：区分「标称带宽」与「可达带宽」

`160.26 µs` 这个数用的是 **datasheet 上的标称带宽**。真实的**可达**带宽低于它，缺口有两个来源：

- **HBM 自身的效率损失**：ECC 开销、刷新、读写方向切换等，官方口径是「扣掉几个百分点」；
- **实现侧的损失**：占用率不足、在途请求不够、尾效应等，取决于 kernel 写得怎么样。

**这个缺口的分解不在本文的题目里**（正文在 [20-gpu-architecture/interconnect/04-measuring-bandwidth](../../20-gpu-architecture/interconnect/04-measuring-bandwidth.md) 与 [memory-system/01-hierarchy-overview](../../20-gpu-architecture/memory-system/01-hierarchy-overview.md) §2，本域**不重推**，只做代入）。本域需要的只是一个**口径**：把可达带宽写成 `η · B_peak`，`η` 取本仓库上游客径给出的量级。

代入三档（推导值，`make verify` §B1）：

| `η` | 口径 | 可达带宽 | 下界时间 |
|---|---|---|---|
| 1.00 | 标称（**乐观下界**，不是可达值） | 3350.0 GB/s | **160.26 µs** |
| 0.95 | 缺口 5% | 3182.5 GB/s | 168.69 µs |
| 0.90 | 缺口 10% | 3015.0 GB/s | 178.07 µs |
| 0.85 | 缺口 15% | 2847.5 GB/s | 188.54 µs |

**`η` 的取值范围来自上游**：本仓库 [10-foundations/performance-models/03](../../10-foundations/performance-models/03-measuring-roofline.md) §0 把它写成「boost clock 漂移、占用率不足、ECC 开销都会扣掉**几个到十几个百分点**」，本域把这句话区间化成 `η ∈ [0.85, 0.95]`——**这是引用值，本仓库不复核其测量口径**。

量级上：`η = 0.90` 时下界从 `160.26 µs` 抬到 `178.07 µs`，**多 11.1%**。缺口的全部影响是「百分之十几」，**不改变量级**——但它决定了「还差多少」这个问题的答案（§4.3）。

### 第四步：这个算子永远在 roofline 的斜线段上

算一下算术强度。按 [roofline](../../10-foundations/performance-models/01-roofline-model.md) §1 第一步的口径，`Bytes` 只统计必须往返 HBM 的那一份：

```text
I = FLOPs / Bytes = ops_per_element / (2·esize)
```

**`I` 与 `N` 无关**——这是逐元素算子的定义性质：每多一个元素，运算数和字节数按同一个比例涨。代入（推导值，`make verify` §B1）：

| 每元素运算 | FLOPs/元素 | `I` | `I/I*` |
|---|---|---|---|
| `y = a·x + b`（1 次 FMA 计 2 FLOPs） | 2 | 0.250 | 1.250% |
| `y = exp(x)`（计 1 次） | 1 | 0.125 | 0.625% |

要让逐元素算子翻到算力受限那一侧，需要

```text
ops_per_element > 2·esize·I* = 2 × 4 × 20.0 = 160 次
```

**每个元素 160 次浮点运算**——实际情况差 2~3 个数量级。所以「逐元素算子是不是访存受限」这个问题**不需要每次重新判断**：只要 `esize = 4` 且运算次数在两位数以内，答案永远是「是」。

（`exp` 计 1 次运算」是**本表的口径**。SASS 上它是 `MUFU.EX2` 加一次乘法，还要先把输入乘上 `log2 e`——真实运算数更多，而**只会让 `I` 更大**，结论方向不变。）

### 第五步：小规模下这个下界不成立

前四步都假设「时间由访存主导」。规模小到一定程度，另一项固定成本会接管。一个逐元素算子每处理一批数据都要付一次 kernel 启动：

| `N` | 数据 | `2N·esize` | 访存时间（`η = 1`） | 一次启动 / 访存时间 |
|---|---|---|---|---|
| 2^16（65536） | 0.2 MiB | 524288 | **0.16 µs** | **1917% ~ 3195%** |
| 2^18（262144） | 1.0 MiB | 2097152 | 0.63 µs | 479% ~ 799% |
| 2^20（1048576） | 4.0 MiB | 8388608 | 2.50 µs | 120% ~ 200% |
| 2^24（16777216） | 64.0 MiB | 134217728 | 40.06 µs | 7% ~ 12% |
| 2^26（67108864） | 256.0 MiB | 536870912 | 160.26 µs | 1.9% ~ 3.1% |

（推导值，`make verify` §B2；启动开销 **3.0~5.0 µs** 是**引用值**，本仓库不复核其测量口径。）

**第一行是关键**：`N = 2^16` 时，访存只要 `0.16 µs`，而一次启动要 `3~5 µs`——**固定开销是访存时间的 19~32 倍**。从第一行到最后一行，同一笔固定开销的相对占比差了 **1024 倍**（推导值，`make verify` §B2）。

所以「访存受限」这个判断带一个隐含条件：**规模足够大**。`N ≤ 2^18` 时，时间下界根本不由访存决定。

## 2. 执行映射

### 2.1 参与这个算子的部件与量级

| 部件 | 在这次访存里做什么 | 量级 |
|---|---|---|
| warp scheduler | 发射 `LDG` / `STG` / `MUFU` | 每 SM 4 个，各每周期 1 条 |
| LSU | 把一条 warp 访存拆成若干条请求 | 128 字节/请求（一条 cache line） |
| sector | **实际搬运**的最小单位 | **32 字节**；一次满合并的 32-lane fp32 读 = 4 个 sector |
| L2 | `N = 2^26` 的 256 MiB 装不进去 | H100 记为 50 MB（口径见 §2.3 的注） |
| HBM | 取数与写回 | 3350 GB/s、往返延迟 **400~800 周期** |
| SFU | `expf` 的 `MUFU.EX2` | 与访存**完全重叠**，不占关键路径 |

（规格值，来源见 `code/specs.py`；访存粒度与合并的完整推导在 [memory-system/02](../../20-gpu-architecture/memory-system/02-coalescing-and-cache-line.md) §1，**本域只代入**。）

**这张表里最容易被忽略的是「SFU 与访存完全重叠」这一行**：它意味着把 `expf` 换成更快的实现，不会让 kernel 变快——访存那侧一个字节都没动。这与 §0 那两天的优化方向是同一件事。

### 2.2 真正的约束是「在途请求数够不够」

带宽不是「每次访存变快」的结果，而是「同时在飞的请求足够多」的结果。由 Little 定律：

```text
在途字节 = 带宽 × 延迟
每 SM      = (3350 GB/s ÷ 132 SM) × 延迟
```

代入 `400 / 600 / 800` 周期的延迟（要用**由规格反推的时钟** `1.9827 GHz`，见 §2.3）：

| 延迟（周期） | 延迟（ns） | 在途字节 | 每 SM | 需要的 128 B 请求数（每 SM） |
|---|---|---|---|---|
| 400 | 201.7 | 660.0 KiB | 5.00 KiB | 40.0 |
| 600 | 302.6 | 990.0 KiB | 7.50 KiB | **60.0** |
| 800 | 403.5 | 1320.0 KiB | 10.00 KiB | 80.0 |

（推导值，`make verify` §B5。）

取延迟 `600` 周期（区间中点），每 SM 需要约 **60 条在途的 128 字节请求**——而每 SM 的 warp 上限是 **64**（= 2048 线程 ÷ 32）。**这个数在「每 warp 只挂一条在途请求」的假设下已经用掉 94% 的余量。**（真实硬件允许一条 warp 挂若干条在飞，所以这是一个**保守**的界；它给出的是方向，不是精确值。）

这个数是本主题三篇的枢纽：**02 篇**会说明融合链吃掉寄存器、把可以常驻的 warp 数压低，从而把在途请求打下去；**03 篇**会说明向量化把每条请求从 128 字节抬到 512 字节，于是需要的请求数掉到 1/4。

### 2.3 三处口径声明

1. **时钟 `1.9827 GHz` 是推导值，不是规格值。** 它由 `67.0 TFLOPS ÷ (132 SM × 128 lane × 2 FLOP)` 反推。官方**未公布** H100 SXM5 的 boost 时钟（这一项记在 `code/specs.py` 的 `UNSOURCED` 里）。它成立的唯一前提是「67 TFLOPS 是在 boost 时钟下测得」。凡是依赖它的结论（§2.2、§B4 的发射时间、§C3 的 occupancy）都带这一条。
2. **`η` 是从「几个到十几个百分点」区间化来的**，是**引用值**，本仓库不复核其测量口径。
3. **L2 容量 50 MB** 只用于「装得下 / 装不下」的量级判断。**本仓库对 L2 容量这一项内部口径不一致**（`20-gpu-architecture/architecture-evolution` 只把 **B200** 的 L2 列为 `UNSOURCED`），所以本文不据此下任何精确结论。

## 3. 实现与演进

按「这条算子还能往哪走」排列。每一层的收益来源不同，**把它们混在一起谈就会得出「调参能提速」这种错结论**。

1. **直接映射（标量）**：`i = blockIdx.x·blockDim.x + threadIdx.x`，每线程一个元素。对 `N = 2^26` 是 `262144` 个 block、每 block 256 线程。**这是基线，也是这一篇的全部内容**。
2. **向量化到 `float4`**：每线程 4 个元素、一次 16 字节。它把**访存指令数**降到 1/4，但**事务数、sector 数、传输字节一个没动**——收益在「填满带宽所需的在途请求数掉到 1/4」上（§2.2 的 60 → 15）。完整推导在 [03 篇](03-vectorized-and-grid-stride.md)。
3. **grid-stride loop**：把 grid 与问题规模解耦。**对本文这个规模没有收益**（`N = 2^26` 的直接映射只用 `262144` 个 block，离 `gridDim.x` 的上限 `2^31−1` 差 4 个数量级），它的适用场景与小规模下的代价也在 [03 篇](03-vectorized-and-grid-stride.md) §2。
4. **融合**：**这是唯一能改掉那个 `2N·esize` 的手段**。前三条改的都是「怎么搬」，只有融合改的是「搬多少」——它把「每个中间结果各读一遍写一遍」压成「读一次写一次」。上界是链长 `k`，但见 [02 篇](02-fusion-and-traffic.md) §1 的限定条件。
5. **到这一步就没有了**。一个单目算子的字节数下界是 `2N·esize`，而它是**算术事实**，不是工程水平问题。剩下的空间只有 §1 第三步那「百分之十几」的可达带宽缺口，以及写成什么样的访存模式。

**这条演进线的方向是「字节数恒定，优化的是怎么把带宽吃满」**——与 [gemm](../gemm/01-naive-gemm-and-roofline.md) 那条「提高算术强度」的线方向相反。判断一个算子该走哪条线，用的就是 §0 那次 `I` 与 `I*` 的比较。

## 4. 踩坑与失败模式

### 4.1 用 `N·esize` 估算，乐观整整一倍

**现象**：规划时按「数据量 ÷ 带宽」估时间——`N = 2^26` 的 256 MiB 数据，`256 MiB ÷ 3350 GB/s = 80.13 µs`。跑出来永远差一倍左右，于是去怀疑带宽是不是虚标、是不是有别的瓶颈，排查很久。

**成因**：`2N·esize` 里的那个 `2` 是「读一次 + 写一次」，**两项都不可省**（§1 第一步）。只数读，等于把写的那一趟当成免费的。`make verify` §B1 断言了这两个数的比值**精确等于 2.00**。

这个坑的常见触发形态是「从输入规模估算」：手上有 256 MiB 的激活张量，就顺手写了 256 MiB。**规模说的是数据有多大，不是要搬多少字节。**

**规避**：把估算写成两行，把 `2` 显式写出来——

```text
字节 = 2 × N × esize        ← 2 = 读一份 + 写一份
时间 = 字节 / B_peak
```

`code/01_elementwise_bound.cu` 的 §4 就是按这个格式打印的，把 `N·esize` 与 `2N·esize` 两行并排放在一起，让少算一倍的写法一眼可见。

### 4.2 忽略小规模下的 launch 开销

**现象**：一条几十个逐元素算子的链，在小张量上（`N ≈ 2^16`）融合、向量化、调参全都试过，端到端时间几乎不动。

**成因**：**规模小到一定程度，时间下界根本不是访存**（§1 第五步）。`N = 2^16` 时访存只要 `0.16 µs`，而一次 kernel 启动要 `3~5 µs`（引用值）——**固定开销是访存时间的 19~32 倍**。这时调访存相关的参数，动的是一份被固定开销淹没的成本。

**规避**：先算一次「访存时间 vs 一次启动」的比值，再决定优化方向。判据：

```text
2N·esize / B_peak ≫ 启动开销  → 访存侧值得优化
2N·esize / B_peak ~ 启动开销  → 先数 kernel 个数（那是 02 篇的题目）
2N·esize / B_peak ≪ 启动开销  → 减少启动次数是唯一有意义的动作
```

按 §1 第五步的表，这条分界线落在 `N ≈ 2^20` 附近（那里比值是 120%~200%）。**注意这条判据与「要不要融合」是同一个问题的两面**：小规模下融合省的是启动次数，不是带宽（推导值，`make verify` §C1：`N = 2^16`、`k = 4` 时省下的 3 次启动值 `9~15 µs`，而省下的 3 份中间张量流量只值 `0.47 µs`，差 19 倍以上）。

### 4.3 把标称带宽当可达带宽，于是「余量」是假的

**现象**：报告里写「160 µs（按 3.35 TB/s 算出的下界），还有 17% 的优化空间」。花时间去找那 17%，找不到。

**成因**：`160.26 µs` 用的是 **datasheet 的 3350 GB/s**。可达带宽低于它（§1 第三步），所以

```text
160.26 µs（η = 1）  →  188.54 µs（η = 0.85）
差值 = 28.28 µs = 17.6%
```

**这 17.6% 不是余量，是缺口。** 把它当成余量，等于凭空造出一块不存在的优化空间——而且这块空间的来源（ECC、boost 漂移、占用率）里有一半**不是 kernel 能改的**。（这一条与 [10-foundations/performance-models/03](../../10-foundations/performance-models/03-measuring-roofline.md) §0 是同一件事，正文在那里。）

**规避**：**分母永远写成 `η·B_peak`，并把 `η` 的口径注出来**。要判断「还有多少余量」，先量出这台机器上这个数据流形态的可达带宽（方法在 [interconnect/04](../../20-gpu-architecture/interconnect/04-measuring-bandwidth.md) 与 [performance-models/03](../../10-foundations/performance-models/03-measuring-roofline.md) 第六步），用它当分母；用标称值当分母得到的是**乐观下界**，只能用来判断「还有没有必要继续优化」这个定性问题，不能用来算百分比。

### 4.4 以为就地（in-place）写法省一半流量

**现象**：为了提速，把 `out[i] = f(in[i])` 改成 `buf[i] = f(buf[i])`，理由是「这样只碰一块内存，读写各减半」。结果耗时几乎没变。

**成因**：**就地省的是容量，不是流量。** `buf[i] = f(buf[i])` 仍然是「把 `buf[i]` 读进来」加「把结果写回去」——`2N·esize` 一个字节都没少（推导值，`make verify` §B1）。它真正省下的是两样东西：

- **容量**：不再需要一块同样大的输出缓冲。`N = 2^26`、fp32 时是 **256 MiB**——在显存吃紧时这是实打实的收益；
- **地址足迹**：触及的 line 数减半（读与写落在同一批 line 上），TLB 压力与 L2 的占用都跟着减。

**规避**：把「就地」的收益写在正确的账上——**它是显存优化，不是带宽优化**。判断依据只有一句：**HBM 层面「读一个字节、写一个字节」这件事有没有被取消？** 就地没有取消任何一次访存。要真正减少流量，只有 [02 篇](02-fusion-and-traffic.md) 那条路：**让中间结果不落 HBM**。

## 6. 小结与延伸

本文一条主线：**一个单目逐元素算子最少要往返 HBM `2N·esize` 字节，代入 roofline 就是它的时间地板。** 围绕它有三个可独立复用的中间结论：

1. **那个 `2` 是「读一次 + 写一次」，两项都省不掉。** 就地写法省的是容量与地址足迹，不是流量（§4.4）。少算一半是最常见的估算错误（§4.1，`make verify` §B1 断言比值精确 = 2.00）。
2. **`I = ops_per_element / (2·esize)` 与 `N` 无关，所以逐元素算子不需要逐个判断瓶颈类型。** 要翻到算力受限那一侧需要每个元素 160 次运算（`esize = 4`、`I* = 20.0`），实际情况差 2~3 个数量级。这条同时给出一条**否证**：为这类算子做的计算侧优化，动的是全部工作量的千分之几。
3. **地板是不是有意义，取决于规模。** `N = 2^16` 时一次 kernel 启动是访存时间的 **19~32 倍**；`N = 2^26` 时同一笔开销降到 **1.9%~3.1%**——同一笔钱差 1024 倍。分界落在 `N ≈ 2^20`。

**本文留下的两个问题，正好是后两篇：**

- **「能不能少搬字节？」** 前三条实现（直接映射、向量化、grid-stride）改的都是「怎么搬」，只有**融合**改的是「搬多少」——它把中间结果留在片上，只读一次、只写一次。上界是链长 `k`，但这个上界挂着一个容易漏掉的前提。见 [02 篇](02-fusion-and-traffic.md)。
- **「同一份字节，怎么搬得更有效？」** 向量化不改字节数、不改事务数，它改的是「填满带宽需要多少并发」。这条线与本文 §2.2 那个「每 SM 约 60 条在途请求」直接接上。见 [03 篇](03-vectorized-and-grid-stride.md)。
