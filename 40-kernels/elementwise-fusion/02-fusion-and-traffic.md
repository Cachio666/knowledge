# 融合与流量：上界是链长 k

> 一条 k 个算子的单目链，**不融合**时每个算子各读一遍写一遍 → `2k·N·esize`；**融合**成一个 kernel 后只读输入、只写输出 → `2·N·esize`。比值是 **k**——不是「趋于 2」，也不是任何小于 k 的常数。但这个上界挂着一个容易漏掉的前提：**每个中间结果都往返 HBM**。中间数组装得进 L2 时，不融合的流量本来就≈ `2N·esize`，收益趋于 **1×**。真实比值落在 `(1, k)` 之间，**这就是公开报道的端到端收益远低于 k 的原因**。

## 0. 背景与动机

一个 decoder block 里有这样一串逐元素算子（`k = 3`）：

```text
t1 = exp(x · 1.5 + 0.25)
t2 = t1 · 0.5 − 1.0
y  = tanh(t2)
```

两种写法，两笔账。取 `N = 2^24 = 16777216` 个 fp32（单份张量 64 MiB）：

| 写法 | kernel 数 | 往返 HBM 字节 | 时间（`η = 1`） | 临时张量 |
|---|---|---|---|---|
| 三个算子各一个 kernel | 3 | **384 MiB** | 120.19 µs | 2 × 64 MiB |
| 手工融合成一个 kernel | 1 | **128 MiB** | **40.06 µs** | 0 |
| （对照：`k = 6` 不融合） | 6 | 768 MiB | 240.39 µs | 5 × 64 MiB |

（推导值，`make verify` §B3。）

**流量比是 3×，时间比也是 3×。** 这不是巧合——[01 篇](01-memory-bound-limit.md) §1 第四步已经证明这类算子永远落在 roofline 的斜线段上，所以时间与字节数成正比。**融合改的是「搬多少」，而这是唯一能改这个量的手段**：向量化、grid-stride、调 block size 改的都是「怎么搬」。

本文要回答的是那条比值公式到底等于什么、它挂在哪一个前提上，以及**为什么它经常不兑现**。

## 1. 原理

### 第一步：把「链」写成一个数据流

一条单目链，第 `j` 个算子的输入是第 `j−1` 个算子的输出：

```text
x ──op_1──▶ t_1 ──op_2──▶ t_2 ──▶ … ──op_k──▶ y
```

每个 `t_j` 都是一个**与输入同形的中间张量**（`N·esize` 字节）。这个「同形」是关键——逐元素算子不改变形状，所以中间张量与输入一样大。

### 第二步：不融合的账——`2k·N·esize`

不融合时，第 `j` 个算子是一个独立的 kernel，它必须：

```text
读 t_{j-1}（或 x）   → N·esize
算 op_j              （在寄存器里）
写 t_j（或 y）       → N·esize
```

k 个算子加起来：

```text
字节_不融合 = Σ_{j=1..k} 2N·esize = 2k·N·esize
```

**逐项数一遍**（`N = 2^24`、`esize = 4`、`N·esize = 64 MiB`）：

| 算子 | 读 | 写 | 小计 |
|---|---|---|---|
| `op_1` | 64 MiB（`x`） | 64 MiB（`t_1`） | 128 MiB |
| `op_2` | 64 MiB（`t_1`） | 64 MiB（`t_2`） | 128 MiB |
| `op_3` | 64 MiB（`t_2`） | 64 MiB（`y`） | 128 MiB |
| **合计** | 192 MiB | 192 MiB | **384 MiB** |

**注意 `t_1` 与 `t_2` 各被搬了两遍**（一遍是上一个算子写出去，一遍是下一个算子读回来）。这 128 MiB × 2 = 256 MiB 就是融合要消掉的那一块。

### 第三步：融合的账——`2N·esize`

融合成一个 kernel 后，每个元素只被读一次、写一次：

```text
读 x[i]      → 1 次
t_1、t_2     → 全程住在**寄存器**里，一次 HBM 都不碰
写 y[i]      → 1 次
```

```text
字节_融合 = 2N·esize = 128 MiB      （N = 2^24 时）
```

### 第四步：比值 = `k`

```text
加速比 = 字节_不融合 / 字节_融合
      = 2k·N·esize / 2·N·esize
      = k
```

逐行核对（推导值，`make verify` §B3 断言了这一列的**精确相等**）：

| `k` | 不融合 | 融合 | 比值 |
|---|---|---|---|
| 1 | 128 MiB | 128 MiB | **1.00** |
| 2 | 256 MiB | 128 MiB | **2.00** |
| 3 | 384 MiB | 128 MiB | **3.00** |
| 4 | 512 MiB | 128 MiB | **4.00** |
| 5 | 640 MiB | 128 MiB | **5.00** |
| 6 | 768 MiB | 128 MiB | **6.00** |

**上界是 `k`，而且它是线性的、没有天花板。** 这里有两个常见的错法，方向相反，都要说清：

- ❌ **「上界趋于 2」**：抓的是 `k = 2` 这一个特例。`k = 2` 时比值确实是 2，但 `k = 6` 时是 6——把特例当通例。
- ❌ **「上界是 `2k/(k+1)`」**：这个式子的来历是把两个**口径不一致**的式子并列——分子用「不融合 = `2kN`」、分母用「融合 = `(k+1)N`」。而 `(k+1)N` 是**另一种拓扑**的融合字节数（见下面的模型丙），单目链融合后是 `2N`，不是 `(k+1)N`。两个式子各自都对，写成一个比值就错了。

### 第五步（⚠ 必须紧接着说）：上界 `k` 挂在一个前提上

> **`k` 只在「每个中间结果都往返 HBM」时成立。**

第二步那个 `2k·N·esize` 假设 `t_1 … t_{k−1}` 每一次都被写进 HBM 又读回来。如果某个中间张量**留在 L2 里**，这笔往返就被缓存挡住了：

```text
模型乙：中间结果命中 L2
  不融合：t_j 在 L2 里被写、被读，不回 HBM
          → 流量 ≈ 读 x 一次 + 写 y 一次 = 2N·esize
  融合：  与甲相同 = 2N·esize
  → 比值 = 1（**与链长无关**）
```

（推导值，`make verify` §B3：模型乙那一列恒为 1.00。）

**判据是「中间张量装不装得进 L2」**：

| `N` | 单份张量 | 结论 |
|---|---|---|
| 2^24（16777216） | **64 MiB** | **明显超过 L2**（本仓库记为 50 MB）→ 落在模型甲 |
| 2^22（4194304） | 16 MiB | 单份装得下，但输入 + 中间 + 输出同时在途时未必 |
| 2^20（1048576） | 4 MiB | 很可能被吸收 → 收益趋于 1× |

（张量大小是推导值；**L2 容量 50 MB 这一项本仓库内部口径不一致**——`20-gpu-architecture/architecture-evolution` 只把 **B200** 的 L2 列为 `UNSOURCED`，并未给 H100 的值。所以上表只给「装得下 / 装不下」的量级判断，**不据此下精确结论**。）

一个更严的口径是**同时在途的张量个数**：不融合时内存里同时活着输入、k−1 个中间张量、输出，共 `k+1` 份，所以判据其实是

```text
(k + 1) · N · esize ≲ L2 容量     ← 才可能落到模型乙
```

`k = 4`、`N = 2^20` 时是 `5 × 4 MiB = 20 MiB`，仍在 50 MB 以内；`N = 2^24` 时是 `5 × 64 MiB = 320 MiB`，差一个数量级。

### 第六步：真实比值落在 `(1, k)` 之间——这是「收益不兑现」的全部解释

模型甲与模型乙是**两个端点**，真实情形在中间：

- 大张量（`N ≳ 2^23`）：中间结果装不进 L2，**趋于甲**，比值接近 `k`；
- 小张量（`N ≲ 2^20`）：中间结果被 L2 吸收，**趋于乙**，比值接近 `1`；
- 中间地带：一部分中间张量命中、一部分没有，比值在两者之间。

这解释了那个常被提起的落差——**理论上收益随链长线性增长，实际观察到的却远低于 `k`**。两个原因叠加：

1. **中间结果常能留在 L2**（上面的模型乙），把比值从 `k` 拉向 1；
2. **端到端收益里还有别的部分**——没被融合的算子、通信、启动开销等等，它们不随融合变化，按 [Amdahl](../../10-foundations/performance-models/02-amdahl-and-scaling.md) 的形态把整体比值再稀释一次。

> **本文不给「实际收益是几倍」的具体区间——因为找不到可引的一手来源。**
> 检索到的说法从「编译器的 10~20%」到「匹配良好的 FFN 融合 1.5~2×」都有，
> 跨度大到不构成一个可引用的区间，且高度依赖工作负载与所用工具。
> 按本仓库的规则（`specs.py`：「找不到可靠来源的项不写进来」），
> 这一类数字记在 `UNSOURCED` 里，**正文只给可判定的判据**——
> 也就是上面那条：**比值落在 `(1, k)` 的开区间，位置由 `(k+1)·N·esize` 与 L2 容量决定**。
> 判据能算，区间不能算。
>
> ⚠ 另有一处**不能用**的类比：`20-gpu-architecture/tensor-core/05-structured-sparsity`
> 里有一个「1.2×~1.6×」的端到端区间，那是**2:4 结构化稀疏**的收益（有可定位的一手来源），
> 与融合**不是同一个机制**，两者的数字不可互换引用。

### 附：模型丙——另一种拓扑，另一个上界

上面全部推导都针对**单目链**（每层一个输入）。若拓扑换成「`k` 个输入 → 1 个输出」的二叉链，两边的字节数都变了：

```text
不融合：k−1 个算子，每个读两个输入 + 写一个输出 → 3(k−1)·N·esize
融合  ：读 k 个输入 + 写 1 个输出              → (k+1)·N·esize
比值  = 3(k−1)/(k+1)
```

| `k` | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|
| 模型丙比值 | 1.0000 | 1.5000 | 1.8000 | 2.0000 | 2.1429 |
| （对照）模型甲比值 | 2.00 | 3.00 | 4.00 | 5.00 | 6.00 |

（推导值，`make verify` §B3。）

**模型丙的比值永远小于模型甲**（`make verify` §B3 断言了这一点）：它的「不融合」一侧天然更贵（每个算子要读两个输入），而「融合」一侧也更贵（要把 k 个输入都读进来，`k` 个输入本身是必须的流量，融合消不掉）。**同一个「融合」动作，在不同拓扑上给出不同的上界**——所以谈融合收益时，**先说拓扑，再说比值**。

## 2. 执行映射

### 2.1 两个版本在硬件上分别发生了什么

| 部件 | 不融合（`k = 3`） | 融合 |
|---|---|---|
| kernel 启动 | **3 次** | **1 次** |
| 显存分配 | 2 块临时张量（各 64 MiB，共 128 MiB） | 0 |
| 寄存器文件 | 每线程约 `16 + 12k`（**含假设成分**，§4.1） | 同左——**这是融合代价的来源** |
| L2 | 每个中间张量经过时都要占一段容量 | 只经手输入与输出 |
| HBM | `2kN·esize = 384 MiB` | `2N·esize = 128 MiB` |
| 片上的中间值 | 无（全在 HBM 里） | 全程在寄存器 |

（推导值；寄存器的公式见 §4.1，**它含假设成分**。）

**三处代价要分开记：**

- **流量**：`384 MiB → 128 MiB`，这是收益（等价于 120.19 µs → 40.06 µs，推导值）。
- **启动**：`3 次 → 1 次`，省下 2 次启动 = **6~10 µs**（**引用值**，3~5 µs/次，本仓库不复核其测量口径）。对 120.19 µs 来说只占 **5%~8%**——**大 N 时融合省的主要是带宽，不是启动**。（小 N 时反过来，见 [01 篇](01-memory-bound-limit.md) §4.2。）
- **寄存器**：`0 → 56 个/线程`（`k = 3` 时按 §4.1 的模型：`r(3) = 52`，按 8 个一档取整到 56）。**这一项是负收益，且它压低 occupancy**——§4.1 的题目。

### 2.2 「把中间值放进寄存器」这句话的准确含义

一个融合 kernel 里，中间值不一定真的每次都待在寄存器：编译器可能把它溢到 local memory（那其实在片外），也可能在一条 FMA 链里直接折叠掉，根本不产生独立的存储。**判据不是源码里有没有变量，而是 `-Xptxas -v` 报告里的寄存器数与 spill 字节数**：

```bash
make regs T=02_fused_chain
```

非零的 spill 字节意味着有一部分「中间结果」实际走了片外——**那就不再是模型甲，而是退化成介于甲乙之间的一种形态**。（spill 与 local memory 的机制在 [20-gpu-architecture/memory-system/01](../../20-gpu-architecture/memory-system/01-hierarchy-overview.md) §4.3，正文在那里，本文只回链。）

### 2.3 融合的两种实现形态

| 形态 | 谁做的 | 判据 |
|---|---|---|
| **单 kernel 手工融合** | 程序员 | 链的语义写死在 kernel 里；链变则 kernel 变 |
| **编译器融合** | 图编译器（Inductor / TVM / XLA 的 fusion pass） | 生产者-消费者对**或水平/兄弟对**能不能合并进同一个 kernel；代价模型用的就是本文 §1 的字节公式（判据细节见 `60-compilers/inductor` 与 `60-compilers/xla`） |

编译器融合的**判据与代价模型**属于编译器那一层：正文在 [60-compilers/inductor](../../60-compilers/inductor) 与 [60-compilers/tvm](../../60-compilers/tvm)，**本文只回链，不复述**。本文对那一层唯一有用的一句话是：**融合的收益上界由「中间结果的字节数」决定，而这个量在单目链上恰好等于链长 `k` 乘以数据大小。**

## 3. 实现与演进

按「谁来负责融合」排列：

1. **逐算子一个 kernel**。基线。代价是 `2kN·esize` 的流量，外加 k 次启动与 k−1 块临时显存。
2. **手工合并相邻算子**。最常见的起点：把 `bias add` 与激活合成一个 kernel，把 `scale` 与 `residual add` 合成一个。收益可以直接用 §1 的公式算——**每次合并两个算子，流量从 `2·2N` 降到 `2N`，比值就是 2**（模型甲下）。
3. **整链手工融合**。把一条 k 算子的链收成一个 kernel。上界是 `k`，但**先查两件事**：链上有没有跨元素的依赖（softmax 的 `max`、LayerNorm 的 `mean`——那些是归约，不是逐元素），以及寄存器够不够（§4.1）。
4. **编译器自动融合**。图编译器按数据依赖做融合，代价模型按「省下的字节 vs 多付的寄存器」取舍。**它做的取舍与本文 §1 / §4.1 是同一件事的两个出口**：`k` 说收益有多大，寄存器说代价有多大。
5. **把归约也融合进来**。softmax / LayerNorm 这类算子的融合是另一条线：它的收益不来自「少搬中间结果」，而来自「一遍读完就把统计量算出来」（在线 softmax）。正文在 [40-kernels/softmax-normalization/03](../softmax-normalization/03-normalization-fusion.md)，本文不重推。

## 4. 踩坑与失败模式

### 4.1 融合导致寄存器压力上升 → occupancy 下降 → 反而更慢

**现象**：一条链从 `k = 1` 融合到 `k = 4`、`k = 8`，字节数按 §1 的公式掉了一大截，耗时却没跟着掉——**某一段之后甚至变慢**。而 `-Xptxas -v` 显示的寄存器数一路在涨，spill 从 0 变成非 0。

**成因**：**融合省掉的 HBM 流量，和融合吃掉的寄存器，来自同一个资源池。** 寄存器既是中间值的家，也是买「在途深度」的货币。

先把代价算出来。设每线程寄存器

```text
r(k) = 16 + 12·k        （16 = 索引/地址/循环控制，12 = 每层算子同时活着的中间值与常量）
```

按 [01 篇](01-memory-bound-limit.md) §2.2 的算法换成 occupancy（`block = 256`，规格：每 SM 65536 个寄存器、寄存器按 8 个一档取整、每 SM 至多 32 block / 2048 线程 / 64 warp）：

| `k` | `r(k)` | 取整到 8 | 常驻 block/SM | 常驻 warp/SM | occupancy | ≥ 标量所需 60 warp？ |
|---|---|---|---|---|---|---|
| 1 | 28 | 32 | 8 | 64 | 100.0% | 是 |
| 2 | 40 | 40 | 6 | 48 | 75.0% | **否** |
| 3 | 52 | 56 | 4 | 32 | 50.0% | **否** |
| 4 | 64 | 64 | 4 | 32 | 50.0% | **否** |
| 6 | 88 | 88 | 2 | 16 | 25.0% | **否** |
| 9 | 124 | 128 | 2 | 16 | 25.0% | **否** |
| 10 | 136 | 136 | 1 | 8 | 12.5% | **否** |
| 19 | 244 | 248 | 1 | 8 | 12.5% | **否** |
| 20 | 256 | **> 255** | — | — | — | **只能 spill** |

（推导值，`make verify` §C3；`16` 与 `12` 这两个系数是**假设**，实际值由编译器决定。）

**这张表里有两个数，任何一个单独看都不意外，放在一起才反直觉：**

- 限制融合链长的**不是**寄存器的硬上限。那个要到 `k = 20`（`r = 256 > 255`）才撞到，编译器在此之前一直有办法。
- **限制它的是 occupancy。** 在「每 warp 只挂一条在途请求」这个保守假设下，填满带宽需要约 **60 个 warp/SM**（推导值，[01 篇](01-memory-bound-limit.md) §2.2）。**`k = 2` 开始就不够了**——`48 < 60`。寄存器上限允许你写 `k = 19`，而带宽早在 `k = 2` 就掉队了。

于是存在一个**最优点**：链再往下融合，省下的字节（线性增长）开始被「在途请求不足导致的带宽损失」超过。**这就是「融合反而更慢」的算术形态。**

两条使用边界，说清楚才有可信度：

1. `16 + 12k` 是**假设的模型**，不是测量。实际寄存器数要读 `-Xptxas -v`（`make regs`）。本文用的是这条曲线的**形状**，以及「寄存器随链长线性涨」这个结构。
2. 「每 warp 只挂一条在途请求」是**保守假设**——真实硬件允许一条 warp 挂若干条在飞，所以 `60` 是需求的上界。判据因此是**方向性**的：链越长，可用的在途深度越小。**要拿到本机的确切数，方法在 [20-gpu-architecture/execution-model/03](../../20-gpu-architecture/execution-model/03-occupancy-and-latency-hiding.md) §2，本文不重推。**

**规避**：融合前先看两件事，而不是先看收益表——**(a) 这条链有多长（`k`）；(b) 目标机器的每 SM 寄存器预算够不够撑住这个 `k`**。预算不够时的三条出路：把链拆成两段（`k` 减半，流量翻倍但 occupancy 回来）、改用向量化（把每 warp 请求从 128 字节抬到 512 字节，需要的在途请求数掉到 1/4，等价于把这道墙往后推 4 倍——见 [03 篇](03-vectorized-and-grid-stride.md) §1），或者显式限寄存器占用（`__launch_bounds__`）。

### 4.2 把上界 `k` 当成一定会拿到的收益

**现象**：按 `k = 4` 规划了 4× 的收益，上线后端到端只快了几十个百分点，于是去怀疑 kernel 写错了。

**成因**：漏掉了 §1 第五步那个前提。`k` 只在「每个中间结果都往返 HBM」时成立；中间数组装得进 L2 时，不融合的流量本来就近 `2N·esize`，收益趋于 **1×**。判据是规模：`N ≲ 2^20` 时中间张量很可能被 L2 吸收（§1 第五步的表）。

而且端到端收益还要再过一次 Amdahl：融合只改了这一条链，模型里别的部分不受影响。**实际观察到的收益远低于 `k`，正落在这个解释里**——不是「融合没用」，而是「融合的收益本来就被 L2 和 Amdahl 各砍一刀」。

**规避**：写收益预期时**同时写出规模**。判据是两句话——

```text
N ≳ 2^23（中间张量明显超过 L2）  → 按模型甲估，比值接近 k
N ≲ 2^20（中间张量可能被吸收）    → 按模型乙估，比值接近 1
```

**同一个融合动作，在两种规模下的收益能差一个数量级。** 报告里只写「融合了 4 个算子，预期 4×」而没写规模，等于没写。

### 4.3 手工融合把语义耦合进 kernel

**现象**：为了把链收进一个 kernel，把整条链的公式写死在源码里。两周后有人要改链中间的一个常数、或插一个算子，改动面是**整个 kernel**（而不是一行调用），回归测试的范围也跟着变大。

**成因**：融合是一次**权衡**，不只是收益：它用「少搬字节」换「少一层抽象边界」。不融合时每个算子是一个独立函数，可以单独测、单独换、单独复用；融合后那层边界没了。对**编译器**做的融合这个问题不存在（它每次从图重新生成），对**手工**融合它才是真代价。

**规避**：把「要不要手工融合」和「要不要融合」当成两个问题。能交给图编译器的就交给它（正文在 [60-compilers/inductor](../../60-compilers/inductor)）；必须手工融合时，把链的**参数**（系数、常量、甚至算子序列）做成模板参数或 kernel 参数，让「改链」不必改结构。**判据是：改动这条链时，需要重新验证的范围有多大。**

### 4.4 融合把「物化」变成「重算」——下游可能因此变慢

**现象**：把一条前向链融合了，前向确实快了；但整个训练步反而变慢，或者显存峰值没降反升。

**成因**：不融合时，`t_1 … t_{k−1}` 是**物化**的——它们躺在显存里，随时可以再读一次。融合后它们不存在了，任何想要中间值的地方只剩两条路：**重新算一遍**（前向的流量省了，反向的算力又付回去），或者改结构。这在反向传播里是实在的账：如果某个中间张量正好是反向需要的激活值，融合就把它从「读一次」变成了「重算一次」。

另外，**显存峰值的变化不是单调的**：融合去掉了 k−1 块临时张量（峰值下降），但如果为了实现它而让编译器把某些值 spill 到 local memory，或者为了重算而保留了别的缓冲，峰值可能反而上升（机制见 [memory-system/01](../../20-gpu-architecture/memory-system/01-hierarchy-overview.md) §4.3）。

**规避**：融合的账要**按整张图算，而不是按一个前向 kernel 算**。判据是问一句「这个中间值除我之外还有没有别的读者」——没有读者就放心融合，有读者（反向、调试、多分支）就先算清那一位读者的代价。训练与推理在这一点上会给出**不同**的答案。

## 6. 小结与延伸

本文一条主线：**融合把「k 个算子各读一遍写一遍」压成「读一次 + 写一次」，上界是链长 `k`；但这个上界只在中间结果往返 HBM 时成立，中间数组进了 L2 就趋于 1×。** 围绕它有三个可独立复用的中间结论：

1. **上界是 `k`，线性、无天花板。** 错法有两个方向：「趋于 2」（把 `k = 2` 的特例当通例）与 `2k/(k+1)`（把口径不一致的两个式子并列——`(k+1)N` 属于另一种拓扑）。**谈融合收益前先说拓扑。** 报告里只写「融合 4 个算子、4×」而没写规模，等于没写（§4.2）。
2. **真实比值落在 `(1, k)` 之间，两个端点各有名字。** 模型甲（中间结果往返 HBM）给 `k`，模型乙（命中 L2）给 `1`，判据是 `(k+1)·N·esize` 与 L2 容量的比较。这解释了「理论上线性、实际远低于 k」。
3. **⚠ 融合有负收益的一侧，而且它比收益先到。** 融合省掉的流量和吃掉的寄存器来自同一个资源池；寄存器上限允许你写到 `k = 19`，而带宽所需的常驻 warp 数在 `k = 2` 就不够了（**公式判定**，`make verify` §C3）。存在一个最优点，越过它融合**反而更慢**。

**与前后两篇的接口：**

- 前一篇 [01](01-memory-bound-limit.md) 给出 `2N·esize` 这个地板；**融合是唯一能改掉它的手段**，另外两条实现（向量化、grid-stride）改的都是「怎么搬」。
- 后一篇 [03](03-vectorized-and-grid-stride.md) 给出本文那条最优点的一部分解法：**向量化把每 warp 请求从 128 字节抬到 512 字节，需要的在途请求数掉到 1/4**——等价于把 §4.1 那道 occupancy 墙往后推 4 倍。两篇合起来才是「一条链该写多长」的完整答案。
