# 实测 roofline：怎么在自己的机器上量出峰值

> [01-roofline-model](01-roofline-model.md) 里的 `P_peak` 与 `B_peak` 是规格表上的数字——那是**上限**，不是你的天花板。要判断一个 kernel 还有多少余量，必须把两个顶点换成自己机器上量出来的值；而这两次测量本身各有一套会静默出错的机制。

## 0. 背景与动机

`01` 给出的 roofline 用的是厂商规格表上的峰值。拿它去和实测性能比，会得到一个偏乐观的结论：规格上 BF16 dense 是 989.5 TFLOPS（来源见 `01` §5 表 1），如果实测到一个明显低于它的数，你会自然读成「达成了这么多百分比，还有多少空间」。但真实的**可达**峰值低于规格值——boost clock 漂移、占用率不足、ECC 开销都会扣掉几个到十几个百分点。**分母错了，余量就算错了**：把规格值当分母，等于凭空多出一块不存在的优化空间，而那块空间原本应该由可达峰值来划。

更麻烦的是带宽那一侧。H100 SXM 的规格带宽是 3.35 TB/s，但 L2 命中会把这个数字**往上抬**：一个反复读同一块数据的 kernel 能从 L2 拿到几倍于 HBM 的带宽。如果测带宽的探针本身规模太小、装得进 L2，你会量出一个远高于 HBM 上限的数，然后据此判断「这个 kernel 是算力受限的」——**判定方向直接反了**。

所以「实测 roofline」不是把 `01` 的两个数换成实测值那么简单，而是要保证两次测量各自量到的是它该量的东西：测算力时量到的是**吞吐**而不是延迟，测带宽时量到的是**HBM** 而不是 L2。这两条各有一个静默失效的模式，加上时钟漂移与死代码消除，一共四类陷阱，本文逐一拆开。

配套程序 `code/11_roofline_probe.cu` 把两次测量与属性推算都写进了一个可执行文件。**本文作者所在环境没有 CUDA 工具链，该程序从未被执行过**——因此本文只描述它**会**量什么、以及为什么那样量才对，不含任何实测数字（§5 留空待填）。

## 1. 原理

### 第一步：测算力时，瓶颈为什么必须是吞吐而不是延迟

FMA 指令有大约 4 个周期的延迟。如果写成一条依赖链：

```text
acc = fma(acc, a, b)     // 下一条 fma 必须等这一条的结果
```

那么每 4 个周期才能发出下一条 FMA，其余 3 个周期发射端口是空的。这时测到的是 FMA 的**延迟**，不是**吞吐**。用 `L` 表示延迟周期数（`L ≈ 4`），`U` 表示独立累加器的条数，每周期实际能发出的 FMA 数是：

```text
单链（U = 1）：   吞吐 = 1 / L  条 FMA/周期
多链（U ≥ L）：   吞吐 = 1      条 FMA/周期         ← 发射端口每周期接受 1 条
```

两者之比正好是 `L`。也就是说，**用单个累加器测算力，会低估到四分之一**。条件 `U ≥ L` 是充分条件：只要独立链不少于延迟周期数，发射端口就能被占满。程序取 `UNROLL = 16`，远大于 `L ≈ 4`，留足余量。

这个推导也顺带说明了为什么 `UNROLL` 不能盲目调大：`16` 条 `float` 累加器就是 16 个寄存器，再往上加会挤占占用率，甚至让 `ptxas` 把累加器 spill 到 local memory——那会把 FMA 退化成访存，数字**大幅偏低**。程序提供了 `make regs` 来看寄存器用量与 spill，就是为这一项兜底。

### 第二步：算力探针还要有足够的并发去填满 SM

单线程的 `UNROLL` 条链只能占满一个 lane 的发射端口。每个 SM 每周期要发 128 个 FP32 lane 的 FMA，所以必须同时有足够多的 warp 驻留在 SM 上。程序用的规模是

```text
blocks  = sm_count × 32      // 每 SM 32 个 block
threads = 256                // 每 block 256 线程 ⇒ 每 SM 8192 线程
iters   = 1 << 16            // 65536 次外层迭代，让 kernel 跑到几十毫秒量级
```

每个线程做 `iters × UNROLL` 次 FMA，总 FMA 次数 = `blocks × threads × iters × UNROLL`，FLOPs = 该数 × 2（一次乘加计 2 FLOPs）。**kernel 必须跑到几十毫秒量级**，否则几微秒的启动开销会占掉可观的比例。

### 第三步：测带宽时，规模为什么必须远大于 L2

带宽探针要量的是 HBM 的峰值。如果数据集装得进 L2，读请求会被 L2 服务，量到的是 L2 带宽——比 HBM 高好几倍。程序按 device 属性里的 L2 大小**动态**选规模：

```text
want_bytes = max( 8 × L2 大小 , 512 MiB )
per_buf    = min( want_bytes , 可用显存 / 5 × 2 )     // copy 要两条 buffer，占可用显存 80%
per_buf   &= ~4095                                    // 4 KiB 对齐
```

三个约束各有来由。`8 × L2` 是**确保命中率可以忽略**：以 H100 的 50 MB L2 为例，单条 buffer 是 400 MB，是 L2 的 8 倍，工作集不可能被 L2 兜住。`512 MiB` 是下界，兜住「L2 属性返回 0」的情况（无 L2 的设备或驱动不支持该属性）。`可用显存 / 5 × 2` 是上界——copy 需要两条 buffer（读一条写一条），合计占可用显存的 80%，留 20% 给上下文、驱动开销与碎片。

程序测两种口径，它们**不是同一个指标**：

| 口径 | kernel | 字节数 | 说明 |
|---|---|---|---|
| copy | `out[i] = in[i]` | `2 × per_buf` | 读一遍 + 写一遍 |
| read-only | `acc += v.x+v.y+v.z+v.w` | `1 × per_buf` | 只读一遍 |

两者都用 `float4`（128 位）访问，保证每个线程每次访存是一条完整的 cache line 请求；都用 grid-stride 循环，让访存地址在整个 buffer 上均匀铺开。

### 第四步：探针自身的算术强度必须远离 `I*`

`01` 的判据是 `I` 与 `I*` 谁大。这个判据也适用于**探针自己**：如果探针的算术强度恰好落在 `I*` 附近，`t_cmp` 与 `t_mem` 同量级，测得的时间是两者的混合，无法归因到任何一侧。设探针的算术强度是 `I_p`，则

```text
I_p ≥ 10 · I*   ⟹  t_cmp / t_mem ≥ 10  ⟹  t_mem ≤ 10% · t_cmp   （测到的是算力）
I_p ≤ I* / 10   ⟹  t_mem / t_cmp ≥ 10  ⟹  t_cmp ≤ 10% · t_mem   （测到的是带宽）
```

偏离一个数量级之后，`max` 里占优的那一项至少是另一项的 10 倍，污染不到 10%。这两个条件在实际探针里都是**轻松满足**的：

- 算力探针 `fma_peak_kernel` 的循环体只碰寄存器，一次 HBM 访存都没有 → `I_p → ∞`；
- 带宽探针 `copy_kernel` / `read_kernel` 只有搬运、几乎不做浮点运算 → `I_p ≈ 0`。

真正需要这个不等式的是**你自己的 kernel**：拿在目标机上量出的 `I*` 去判断它的落点时，如果它的 `I` 恰好落在 `I*` 附近（例如 `01` §5 表 3 里那些 `I ≈ 100～500` 的算子），那么它同时受两侧约束，任何单侧优化都拿不到线性收益——这不是测量误差，是模型本身的性质。

### 第五步：从 device 属性推理论峰值

实测之外，程序还从 device 属性算一组**理论值**作对照：

```text
FP32 理论峰值 = SM 数 × 每 SM 的 FP32 单元数 × 2 FLOP/FMA × SM 时钟
显存理论带宽  = 显存时钟 × 总线宽度(字节) × 2            ← ×2 是 DDR（上升沿+下降沿各传一次）
```

「每 SM 的 FP32 单元数」**没有对应的 device 属性可读**，程序里是硬编码假设：`sm_80`（A100 / GA100）按 64 算，`sm_86` / `sm_89` / `sm_90` 按 128 算，更老的架构一律按 64 估。架构换代时这一项必须人工核对——这也是「理论值」这一列最大的不确定来源。这个假设被单独写进口径声明，是因为它**猜错时不会报错**：把 128 猜成 64，理论值直接减半，达成率那一列会变成 200%，而你会先去怀疑测量代码。

### 第六步：为什么 FP32 与 FP64 两个精度都要测

程序对同一个 FMA kernel 各测一遍 FP32 与 FP64，理论值那边则是 `theo_fp64 = theo_fp32 / 2`（`sm_80` / `sm_90` 上 FP64 峰值是 FP32 的一半）。测两个精度的意义不在 FP64 本身，而在于**它是一次交叉验证**：

- 两个精度的实测达成率应该接近（同一个 kernel 骨架、同一份占用率）；若 FP64 的达成率显著低于 FP32，多半是寄存器压力或占用率的差异，而不是「FP64 单元少」——因为理论值里已经把 1/2 这个比例算进去了。
- 两个精度的耗时是同一量级（FP64 慢一倍），说明 `iters` 的选取对两者都合适；若某一个跑到微秒量级，说明它的规模需要单独调。

这也顺带提醒一件事：**FP32 是标量流水线的峰值，不是这张卡的算力峰值**。程序的口径声明把这一点放在最前面：FMA 密集 kernel 打的是标量 FP32 流水线，而 LLM 训练推理吃的 Tensor Core 峰值比它高一个数量级，**用本程序的 FP32 实测值去和 989.5 TFLOPS 比是错误的**。要测 Tensor Core 必须用 `mma` / `wgmma` 指令或 cuBLAS，那超出本程序的范围。

## 2. 执行映射

### 属性名：一个字母都不能错

程序读的是这些属性（`cudaDeviceGetAttribute`）：

| 属性 | 含义 | 陷阱 |
|---|---|---|
| `cudaDevAttrMultiProcessorCount` | SM 数 | — |
| `cudaDevAttrClockRate` | **当前** SM 时钟（kHz） | 受功耗/温度影响，会漂移 |
| `cudaDevAttrMemoryClockRate` | 显存时钟（**kHz**，不是 Hz） | 部分平台报 0 或报数据率的一半 |
| `cudaDevAttrGlobalMemoryBusWidth` | 显存总线宽度（bit） | **没有 `cudaDevAttrMemoryBusWidth` 这个属性**，写错会编译不过 |
| `cudaDevAttrL2CacheSize` | L2 容量（byte） | 无 L2 的设备返回 0，要靠规模下界兜住 |
| `cudaDevAttrComputeCapabilityMajor` / `Minor` | 计算能力 | 用来决定每 SM 的 FP32 单元数 |

两处最容易写错的地方值得单独说。第一，**显存总线宽度的属性名是 `cudaDevAttrGlobalMemoryBusWidth`**——凭直觉写的 `cudaDevAttrMemoryBusWidth` 不存在，编译器会直接报错，不会静默给错值。第二，**`cudaDevAttrMemoryClockRate` 的单位是 kHz**，把它当 Hz 用会让理论带宽小三个数量级。

### 理论带宽的算式与 DDR 口径

```text
理论带宽 = 显存时钟 × (总线宽度 / 8) 字节 × 2
```

末尾的 `×2` 是 DDR（Double Data Rate）的等效口径：一个时钟周期内上升沿与下降沿各传一次。这一项**最容易漏**——漏掉它，理论带宽正好差 2 倍，而达成率那一列会变成 200%，看起来像测量代码错了，其实是公式错了。另外注意 HBM 的「显存时钟」在规格表上通常已经按数据率给出（如 3.35 TB/s 这类整带宽），与 `cudaDevAttrMemoryClockRate` 报的值口径可能不一致——程序的口径声明里明确写着：**若实测带宽与理论值差得离谱，先怀疑这个属性，不要先怀疑测量代码。**

### 两个带宽口径为什么都要量

带宽不是一个单值，它取决于「怎么数字节」：

| 口径 | 计法 | 物理含义 |
|---|---|---|
| copy | 读 `per_buf` + 写 `per_buf` = `2 × per_buf` | 双向流（读写同时发生），最接近真实的训练/推理数据流 |
| read-only | 只读 `per_buf` | 单向流，排除了写路径的干扰，更接近 HBM 的读带宽上限 |

`copy` 的口径里，读与写在同一条总线上争用，两个方向都要占带宽。`read-only` 只有读，所以通常能测到比 `copy` 折算值更高的数。**两者不是同一个指标**：`01` 的 `I* = P_peak / B_peak` 里的 `B_peak` 指的是哪个口径，会直接改变拐点的位置。程序第 5 节统一用 **read-only** 那一列作分母（带宽与精度无关，这样处理是对的），并在输出里写明。

所以抄写实测结果时，**必须连同口径一起抄**。只写「实测带宽 X TB/s」而丢掉「copy 还是 read-only」，等于丢掉了这个数字一半的含义——尤其在拿它和规格表上的 3.35 TB/s 比较时：规格值通常按单向读带宽给出，拿 `copy` 口径的数去比会天然偏低，看起来像是「没跑满」。

### 数值量级

单位先算清楚：每 SM 128 个 FP32 单元、每个单元每周期一条 FMA、一条 FMA 计 2 FLOPs ⇒ **每 SM 每周期 256 FLOPs**。乘上 SM 数与时钟才是整卡峰值。

作为对照的标称值（来源：`code/09_roofline_model.py` 的程序输出，**该程序自己声明「全部是解析计算，没有在 GPU 上跑任何 kernel」**，所以下面这些是 NVIDIA datasheet 上的规格，不是本机 GPU 实测）：

| 量 | 规格值 | 来源 |
|---|---|---|
| H100 SXM BF16 dense 峰值 | 989.5 TFLOPS | NVIDIA H100 datasheet |
| H100 SXM 显存带宽 | 3.35 TB/s（80 GB HBM3） | NVIDIA H100 datasheet |
| H100 SXM 的 `I*`（BF16 dense） | 295.4 FLOP/byte | 989.5 ÷ 3.35，见 `01` §5 表 1 |
| H100 的 L2 容量 | 50 MB | `09` 的边界声明 |

程序第 5 节会打印一行 `H100 SXM BF16 dense（规格，本机未必是） 295` 作为对照。**那是源码里硬编码的规格常量**（与 `09` 的解析计算结果一致），不是本机的测量值——抄写结果时不要把它填进实测栏。

同一张表里还有三行 Tensor Core 的 `I*`（TF32 / BF16 / FP8），它们是拿「H100 规格表上该精度峰值 ÷ FP32 峰值」这个比值乘本机实测 FP32 峰值**外推**出来的，程序明确标注为「外推（H100 规格比值）」。它成立的假设是「本机各精度的峰值比例与 H100 相同」，对非 Hopper 的卡这个假设不成立，只能当量级参考。

## 3. 实现与演进

**第一层：理论峰值。**从 device 属性直接算（§1 第五步）。它的优点是零成本、随时可读；缺点是两个输入都不可靠——SM 时钟随功耗漂移，且「每 SM 的 FP32 单元数」根本读不到。所以它只能当**上界**用。

**第二层：微基准测可达峰值。**用两个专门的 kernel 分别量算力与带宽（§1 第一步到第四步）。这一层拿到的才是「我的机器在这一次运行中的表现」。它比理论值低是正常的：程序自己的口径声明列出可能偏低的原因（占用率不足、寄存器压力、boost 时钟回落），并指出**几乎没有可能偏高**的原因——唯一的例外是 `ptxas` 因 `UNROLL` 太大而 spill。

**第三层：加上 cache 分层。**单层 roofline 只承认 HBM 一条带宽。把 L2 带宽、共享内存带宽也量出来，才能判断一个 kernel 的瓶颈是否已经从 HBM 转移到了下一级。这一层的关键是规模必须**跨过 L2 的边界**：同一个 copy kernel，在「装得进 L2」的规模与「`8 × L2`」的规模上各跑一次，会得到两个完全不同的带宽数——前者是 L2 的，后者才是 HBM 的（以 H100 的 50 MB L2 为例，后者是 400 MB）。`11` 只做了 HBM 这一层，并在边界一节声明「没有测 L2 带宽、共享内存带宽、NVLink 带宽」。

**第四层：用 profiler 的计数器校准。**微基准给出的是整卡的峰值；要判断**某个具体 kernel** 离它的上限还有多远，需要 profiler 的硬件计数器（DRAM 吞吐、Tensor Core 活跃周期、L2 命中率）。这一步的正文在 [50-performance/profiling-tools/01-collection-mechanisms](../../50-performance/profiling-tools/01-collection-mechanisms.md)（正文在该域，此处回链）。微基准与 profiler 的分工是：前者给出**边界**，后者给出**当前位置**。

## 4. 踩坑与失败模式

### 4.1 测算力时用单累加器

**现象**：写一个 `for (i...) acc = fma(acc, a, b);` 的循环测量峰值算力，得到一个远低于规格的数，于是判断「这张卡的实现达不到标称峰值」。

**成因**：FMA 有约 4 周期的延迟，单条依赖链每 4 周期才能发一条指令。测到的不是吞吐而是**延迟**，低估的倍数正好等于延迟周期数（约 4 倍）。这个错误不会报错、不会崩溃，只会安静地给出一个偏小的数——而且偏小的倍数恰好落在一个「看起来像是占用率不足」的范围内，很容易被误诊。

**规避**：用多个互不依赖的累加器把依赖链打断，条数不少于延迟周期数（程序取 `UNROLL = 16`）。验证办法：把 `UNROLL` 从 8 改到 16 再到 32，如果结果**成倍上升**，说明还没到吞吐平台，说明链数不够；只有当继续加大 `UNROLL` 而结果不再上升（开始下降则说明寄存器压力上来了）时，读到的才是吞吐。同时用 `make regs` 确认没有 spill——spill 会让数字大幅偏低，方向与依赖链问题相反，两者可能同时存在。

### 4.2 测带宽时数据集装得进 L2

**现象**：用一个 `2048 × 2048` 的 fp32 矩阵（16 MB，装得进一张 H100 的 50 MB L2）做 copy 测带宽，得到一个**大到不合理**的数（远高于该卡的 HBM 规格带宽），于是认为「规格表低估了实际带宽」，并据此判断某个 kernel 是算力受限的。

**成因**：数据集装得进 L2 时，读请求由 L2 服务，量到的是 L2 带宽而不是 HBM 带宽。这个错误**不会让数字变小**，反而会让它变大好几倍——而一个偏大的带宽会直接把 `I* = P/B` 算小，把原本带宽受限的算子误判成算力受限，优化方向整个反过来。

**规避**：按 device 属性动态选规模，取 `max(8 × L2, 512 MiB)`，并在输出里**打印 buffer 相对 L2 的倍数**让读者能核对（程序的做法）。验证办法：把同一个 kernel 在「装得进 L2」和「远大于 L2」两个规模上各跑一次，后者才是 HBM 的数字；如果两者相同，说明规模根本没跨过 L2 边界。另注意两个已知会让实测**偏高**的因素：grid-stride 循环让相邻 block 的访问在时间上有局部性；写分配（write-allocate）让 copy 实际写出的字节多于理论值。

### 4.3 忽略 boost clock 漂移

**现象**：同一段测量代码，两次运行给出相差几个百分点的峰值；某次运行的数字明显偏低，重跑又正常了。

**成因**：GPU 的 SM 时钟是动态的，受功耗墙与温度影响。`cudaDevAttrClockRate` 读到的是**当前**时钟，不是规格上的最高频率；kernel 一开始跑，时钟可能先冲高再因功耗墙回落。所以「理论值」这一列本身就会漂移，而实测值会跟着漂。程序的口径声明把「所有数字来自一次进程运行。GPU 的时钟受功耗、温度、同机其他进程影响，换一次运行可能差几个百分点」列为已知边界。

**规避**：先做一次**预热**再把结果计入（程序对 FMA 测量跑两次，第一次丢弃，理由写明是「第一次包含上下文初始化与频率爬升」），并做多次重复取中位（程序对每个测量跑 5 次）。绝对不要把单次运行的某一个数字当作稳定值报出去。要做长期稳定性测试的话，程序明确说明它**没有**做（「只跑了 5 次取中位，但没有做长期稳定性测试」）。

### 4.4 编译器把测量循环优化掉

**现象**：测算力的 kernel 报出一个天文数字（或者耗时接近 0），远超任何规格。

**成因**：结果从未被读取。编译器发现 `out` 没被写过、`acc` 没被用过，就把整个循环当死代码删掉，测出来的「峰值」是「0 耗时 ÷ FLOPs」。这与 4.2 不同：4.2 是物理原因导致的偏高，这一条是**测量目标不存在**。

**规避**：给结果一个编译器无法静态排除的出口。程序用的手段是加一个几乎不可能成立的分支：

```cpp
if (s == 12345.678f) out[blockIdx.x * blockDim.x + threadIdx.x] = s;
```

编译器必须把 `s` 算出来才能做这个比较，于是循环保住了；而实际几乎从不写内存，不会污染带宽测量。另一种手段是把结果写回全局内存，但那会给带宽探针引入额外流量——这也是为什么程序选前者。**注意这个分支要真的几乎从不成立**：若 `s` 恰好等于那个魔数，写入会污染后续测量。

## 6. 小结与延伸

本文只有一条主线：**实测 roofline 的两次测量各自有一个静默失效的模式**。测算力的那次会退化成测延迟（4.1），测带宽的那次会退化成测 L2（4.2），两次都不会报错，只会给出一个看似合理的错数。挡住它们的分别是「多累加器」与「规模跨过 L2 边界」这两个具体手段。

围绕这条主线，有四个可独立复用的结论：

1. **延迟 ≠ 吞吐。** FMA 延迟约 4 周期，单条依赖链会让吞吐降到 1/4。用不少于延迟周期数的独立累加器（`UNROLL = 16`）打断依赖链，并用 `make regs` 确认没有 spill。
2. **规模决定你量到哪一级。** 带宽探针取 `max(8 × L2, 512 MiB)`，并打印 buffer 相对 L2 的倍数作为可核对证据。
3. **属性名与单位是硬性的。** 显存总线宽度是 `cudaDevAttrGlobalMemoryBusWidth`（`cudaDevAttrMemoryBusWidth` 不存在），`cudaDevAttrMemoryClockRate` 单位是 kHz，理论带宽算式末尾的 `×2`（DDR）不能漏。
4. **口径必须跟着数字走。** 标量 FP32 的拐点与 Tensor Core BF16 的拐点差一个数量级；`copy` 口径与 `read-only` 口径不是同一个指标。报任何一个 `I*` 都要带上精度与口径。

延伸阅读：`01` 那篇给出的规格表峰值与本文量出的可达峰值**不是同一个数**，前者是上限、后者是天花板；两者之间的差距正是「你的 kernel 还有多少余量」这个问题的分母。要继续往下走，下一步是把本文整卡级的峰值与具体 kernel 的实测做对比，那需要 profiler 的硬件计数器——正文在 [50-performance/bottleneck-diagnosis/01-latency-and-bandwidth](../../50-performance/bottleneck-diagnosis/01-latency-and-bandwidth.md)（正文在该域，此处回链）。
