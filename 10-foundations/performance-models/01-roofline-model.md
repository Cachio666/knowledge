# Roofline 模型：先判断瓶颈类型，再谈优化

> 一个算子受限于算力还是带宽，只由它的**算术强度** `I` 与机器的**平衡点** `I*` 谁大决定。`I` 是算子这一侧唯一的自变量，`I*` 是机器那一侧唯一的常数——而 `I*` 随精度变化极大，不注明精度口径的 roofline 论断没有意义。

## 0. 背景与动机

一个 `[4096 × 8192]` 的激活张量要做 LayerNorm。有人为这个 kernel 花了两天：block size 从 128 试到 1024，加 `__restrict__`，把访存向量化到 128 位，把 `rsqrt` 换成更快的内建函数，甚至去数了寄存器用量。每一步都测，每一步的耗时变化都埋在噪声里。

按本文的口径算（§5 表 3），这个算子的算术强度是 `I = 1.500` FLOP/byte，而 H100 SXM 在 BF16 dense 下的平衡点是 `I* = 295.4`。它落在斜线段上，可达算力是 `3.35 TB/s × 1.500 = 5.025 TFLOPS`，**只有峰值的 0.51%**。等价地看比值：`I/I* = 0.005078`，也就是**计算那一侧的总耗时不到访存耗时的千分之六**（§5 表 3 的 LayerNorm 行）。那两天里被优化的是这千分之六里的一个因子——而它 99% 以上的时间在做的是把 `1.342e+08` 字节读进来再写回去，一步都没被碰过。

这类无效优化的共同前置错误是：**在没判断瓶颈类型之前就选定了优化方向**。调 block size、加限定符、换向量化宽度，都是计算侧的杠杆；而对一个带宽受限的算子，计算侧唯一能影响的是「同一份数据算了多少遍」，不是「算得多快」。

Roofline 模型就是用来做这个判断的：把每个算子的算术强度算出来，跟机器的平衡点比一次大小，就知道它该被哪一侧卡住、以及理论上最多能跑多快。本文负责把这条判断链完整推出来——`I` 怎么算、`I*` 怎么来、两段线怎么推、LLM 的典型算子各自落在哪里。它**不**负责回答「我的 kernel 离那个上限还差多少」：那个差距取决于具体实现（占用率、启动开销、尾效应、L2 命中），在跑过之前任何具体数字都是编的——那是 [03-measuring-roofline](03-measuring-roofline.md) 的事。

## 1. 原理

下面按六步推导，每一步只引入一个量。

**第一步：定义算术强度，并锁定 Bytes 的口径。**

一个算子要做两类动作：做浮点运算，和搬字节。二者的比值就是算术强度：

```text
I = FLOPs / Bytes        （单位：FLOP/byte）
```

关键在 `Bytes` 的口径。它只统计**必须往返 HBM（高带宽显存，High Bandwidth Memory）的字节**——读输入、写输出。寄存器与共享内存里的中间累加、被 L2 缓存挡住的复用，一律不计。理由是这个模型描述的是「算力」与「HBM 带宽」这两条**硬件能力边界**，不是某个具体 kernel 的数据流：L2 命中率是实现的属性，不是算子的属性。一次乘加（FMA）计 2 FLOPs——`a·b+c` 里有 1 次乘、1 次加。

这条口径是全篇最容易被写错的地方，§4 第一条专门讲它的反面。

**第二步：证明「哪一侧卡住」只由 `I` 与 `I*` 的比决定。**

设一个算子总共做 `W` 次浮点运算、搬 `Q` 个字节。机器的峰值算力是 `P`（FLOP/s），峰值带宽是 `B`（byte/s）。两类动作各自的耗时是

```text
计算耗时  t_cmp = W / P
访存耗时  t_mem = Q / B
```

它们是**串行依赖**的（数据不到就算不了），所以总时间不是相加，而是取大：

```text
t = max(t_cmp, t_mem) = max(W/P, Q/B)
```

现在把 `I` 与 `I*` 引进来。先看两者之比：

```text
t_cmp / t_mem = (W/P) / (Q/B) = (W/Q) · (B/P) = I / I*
```

这个等式把四个量（`W`、`Q`、`P`、`B`）压缩成了一个比值。于是「谁大」的判定条件变成

```text
t_cmp ≥ t_mem  ⟺  I ≥ I*  ⟺  算力受限
t_cmp <  t_mem  ⟺  I < I*  ⟺  带宽受限
```

**没有第三种情形。** 与算子的绝对规模（`M`、`N`、`K`）、与 FLOPs 总量、与参数个数都无关——这就是为什么可以把形状天差地别的算子全画在同一张图上。

**第三步：平衡点 `I* = P_peak / B_peak`——由机器单独决定。**

令 `t_cmp = t_mem` 就能解出分界点：

```text
W/P = Q/B   ⟹   W/Q = P/B   ⟹   I* = P_peak / B_peak
```

`I*` 只含硬件常数，与算子无关。代入 NVIDIA H100 datasheet 规格表上的 H100 SXM（Hopper / sm_90 / 80 GB HBM3），逐精度算一遍（§5 表 1）：

| 精度 | dense TFLOPS | 含稀疏 TFLOPS | `I*` (FLOP/byte) | 相对 BF16 |
|---|---|---|---|---|
| FP64（非 Tensor Core） | 34.0 | 34.0 | 10.1 | 0.03 倍 |
| FP32（非 Tensor Core） | 67.0 | 67.0 | 20.0 | 0.07 倍 |
| TF32 TC | 494.5 | 989.0 | 147.6 | 0.50 倍 |
| **BF16 TC** | **989.5** | 1979.0 | **295.4** | 1.00 倍 |
| FP16 TC | 989.5 | 1979.0 | 295.4 | 1.00 倍 |
| FP8 TC | 1979.0 | 3958.0 | 590.7 | 2.00 倍 |

**同一台机器，换个精度，平衡点差 58 倍**（FP8 的 1979.0 对 FP64 的 34.0）。这就是第三步存在的理由：说「H100 的 roofline 拐点是 295」时，**必须同时说清是 BF16 dense**。换成 FP32 就变成 20.0，结论会直接反转——一个 `I = 100` 的算子，在 BF16 下是带宽受限（100 < 295），在 FP32 下却是算力受限（100 > 20）。

`dense` 这半边也不能省。规格表上 Tensor Core 的数字带 `*`，脚注写明 *with sparsity*（2:4 结构化稀疏），本表一律取**不含稀疏的 dense 值**，它是 sparse 值的一半。两者相差正好 2 倍，混用会让 `I*` 整体挪位。

**第四步：两段线——从时间式推出可达算力。**

从第二步的时间式出发，把 `W` 除过去：

```text
可达算力 = W / t
         = W / max(W/P, Q/B)
         = min( W·P/W , W·B/Q )        ← 1/max(a,b) = min(1/a, 1/b)
         = min( P , B·(W/Q) )
         = min( P_peak , B_peak · I )    ∎
```

这就是 roofline 的两段线。分界点正是两条线的交点 `B·I = P`，即 `I = P/B = I*`：

- **`I < I*`**：带宽线更低，可达算力 = `B_peak × I`，与 `I` 成正比。此时提高算术强度能**线性**换来性能，叫 **memory-bound（带宽受限）**。
- **`I > I*`**：算力线更低，可达算力封顶在 `P_peak`。此时再怎么提高算术强度也拿不到更多算力，只能换峰值更高的精度，叫 **compute-bound（算力受限）**。

**第五步：把 LLM 的典型算子逐个放上去。**

先把两个阶段说清楚：LLM 推理的 **prefill** 一次处理整段输入，矩阵乘的 `M` 维等于序列长度，是个大 GEMM；**decode** 一次只生成一个 token，`M = 1`，同一个矩阵乘退化成矩阵乘向量（GEMV）。两者用的是同一类算子，形状却差三个数量级——这正是下面要展开的。

取一组 Llama-3-70B 量级的超参：`d_model = 8192`、`n_layers = 80`、`n_heads = 64`、`n_kv_heads = 8`、`head_dim = 128`、`d_ff = 28672`。权重按 BF16 存（2 byte/元素）。

*（1）prefill 大 GEMM，`X[4096×8192] @ W[8192×8192]`*

```text
FLOPs = 2·M·K·N      = 2 × 4096 × 8192 × 8192                  = 5.498e+11
Bytes = 2·(M·K + K·N + M·N) = 2 × (33554432 + 67108864 + 33554432) = 2.684e+08
I     = 5.498e+11 / 2.684e+08                                  = 2.048e+03
```

`I/I* = 6.934`，算力受限，可达算力 `9.895e+02` TFLOPS，即峰值的 **100.00%**。

*（2）prefill 小 GEMM，`X[512×8192] @ W[8192×8192]`*

```text
FLOPs = 2 × 512 × 8192 × 8192                                  = 6.872e+10
Bytes = 2 × (4194304 + 67108864 + 4194304)                     = 1.510e+08
I     = 6.872e+10 / 1.510e+08                                  = 4.551e+02
```

`I/I* = 1.541`，仍是算力受限，可达 100.00%。

*（3）decode GEMV，`x[1×8192] @ W[8192×8192]`*

```text
FLOPs = 2 × 8192 × 8192                                        = 1.342e+08
Bytes = 2 × (8192 + 67108864 + 8192)                           = 1.343e+08
I     = 1.342e+08 / 1.343e+08                                  = 9.998e-01
```

`I/I* = 0.003385`，带宽受限，可达算力 `3.349e+00` TFLOPS，**峰值的 0.34%**。

*（4）（5）attention 的 QKᵀ 与 PV*

QKᵀ 的 `Q[4096×128] @ Kᵀ[128×4096] → scores[4096×4096]`：

```text
FLOPs = 2·S²·d = 2 × 16777216 × 128                            = 4.295e+09
Bytes = 2·(S·d + S·d + S²) = 2 × (524288 + 524288 + 16777216)  = 3.565e+07
I     = 4.295e+09 / 3.565e+07                                  = 1.205e+02
```

PV 的 `P[4096×4096] @ V[4096×128] → O[4096×128]` 分子分母都被同一个 `2·S²·d` 与 `2·(S² + 2·S·d)` 支配，数值完全相同：`I = 1.205e+02`，`I/I* = 0.4079`，带宽受限，可达 `4.036e+02` TFLOPS（40.79%）。

两者可以合并成一个解析式：

```text
I = 2S²d / 2(2Sd + S²) = S·d/(2d + S)  ⟶_{S→∞}  d = 128
```

分子上的 `S²` 只乘一次 `d`，分母上却带着一个不乘 `d` 的 `S²` 项——**序列越长，`I` 越趋近 `head_dim`，永远够不到 `I*`**。而且收敛慢：`S = 4096`、`d = 128` 时 `I = 120.5`，只有渐近值 128 的 **94%**，要到 `S ≈ 100·d = 12800` 才走到 98%。在实用序列长度范围内，`head_dim` 直接就是它的算术强度上限，而 `head_dim` 通常是 64～128。

只有把 `S×S` 中间矩阵留在片上（flash attention），分母里的 `S²` 项才消失。此时把两个矩阵乘一起算：`FLOPs = 4S²d`，`Bytes` 只剩读 Q/K/V 写 O = `2·4Sd`，于是

```text
I = 4S²d / 8Sd = S/2 = 2048   （S = 4096）
```

从带宽受限翻到算力受限。**flash attention 省下来的不是 FLOPs（一点没少），是那个 `S²×2 = 33.6 MB` 中间矩阵的往返搬运。**

*（6）（7）（8）softmax / LayerNorm / SiLU*

```text
softmax   FLOPs = 5·S² = 5 × 16777216              = 8.389e+07
          Bytes = 2 × (16777216 + 16777216)        = 6.711e+07
          I = 1.250e+00

LayerNorm FLOPs = 6·M·d = 6 × 33554432             = 2.013e+08
          Bytes = 2 × (33554432 + 33554432)        = 1.342e+08
          I = 1.500e+00

SiLU      FLOPs = 5·M·d = 5 × 117440512            = 5.872e+08
          Bytes = 2 × (117440512 + 117440512)      = 4.698e+08
          I = 1.250e+00
```

**所有 elementwise / 归约算子的 `I` 都挤在 1～2 之间**，因为每个元素只做常数次运算，却必须读一次写一次（4 byte/元素）。它们离 `I* = 295` 差 **2.4 个数量级**，可达算力不到峰值的 1%（softmax 只有 `4.19` TFLOPS，即 0.42%）。所以「把 LayerNorm 算得更快」这件事从 roofline 看是没有意义的；有意义的是**少搬一次**，也就是算子融合。

**第六步：decode 的定量账，以及它什么时候会翻转。**

decode 阶段每生成一个 token，做的运算是「权重矩阵 × 向量」。设模型有 `P` 个参数：

```text
· 每个参数恰好参与一次乘加  ⇒ FLOPs = 2·P
· 而没有任何复用：读进一个权重、用一次、丢掉
                            ⇒ Bytes ≥ 权重总量 = P × 2
```

两式相除，向量长度、层数、隐藏维全部约掉：

```text
I_decode = 2P / (2P) = 1.0 FLOP/byte
```

**这个 1.0 与模型大小无关、与精度无关**，是「权重每被读一次只用一次」的必然结果。用同一套口径算出的 decode GEMV 行是 `I = 0.9998`，比 1.0 略小，因为还要读写输入输出向量共 32768 字节——相对 `1.342e+08` 字节的权重矩阵可以忽略。

代入 H100 SXM 的硬件常数（`P = 7e+10`、BF16）：

```text
读一遍权重的字节数  = 70000000000 × 2 = 1.400e+11 byte = 140.0 GB
访存时间下限 t_mem  = 1.400e+11 / 3.35e+12 = 0.0418 s = 41.8 ms
计算时间        t_cmp = 2 × 70000000000 / 9.895e+14 = 0.0001 s = 0.1415 ms
比值 t_mem / t_cmp  = 295.4 倍
单 token 吞吐下限   = 1 / 0.0418 s = 23.9 token/s
算力利用率          = t_cmp / t_mem = 0.3386%
```

也就是说：H100 有 990 TFLOPS 的 BF16 算力，而 decode 一个 70B 模型只能用到其中的 **0.34%**，超过 99.6% 的 Tensor Core 在空转。这不是实现问题——只要权重必须以「读一次用一次」的方式过一遍 HBM，这个上限就搬不掉。

**但「decode 必然是带宽受限」这句话本身是错的。** 它漏掉了两项：KV cache 的读取（每 token 每层 `2 × 8 × 128 × 2 = 4096` byte，全模型 `0.3277 MB/token`），以及 decode 时注意力自身的 FLOPs（`4·S·d_model·n_layers = 2.621e+06 × S`；`S = 8192` 时是 `2.147e+10`，为线性层 `2P = 1.400e+11` 的 15.3%）。把两项都算进去，令 `B → ∞`：

```text
I_∞(S) = (2P + 4·S·d_model·n_layers) / (S·kv)
       = 2P/(S·kv) + 4·d_model·n_layers/kv
       = 52.2 + 8.0        （S = 8192）
```

前项随 `S` 缩小，后项与 `S` 无关，所以 `I_∞` 有**下限 8.0**。在 `S = 8192` 时 `I_∞ = 60.2 < I* = 295`，任何 batch 都是带宽受限。但 `S = 1024` 时 `I_∞ = 425.2 > I*`——**短上下文 + 大 batch 下 decode 会翻转成算力受限**。解 `I(B,S) = I*` 得到临界的 batch：

```text
B*(S) = I*·2P / ( 2P − (I*·kv − 4·d_model·n_layers)·S )
```

其中 `I*·kv − 4·d_model·n_layers = 9.417e+07`，分母在 `S = 1487` 处变号。正确的表述是：

- **`S ≳ 1487` 时，decode 在任何 batch 下都是带宽受限**——这是绝大多数长上下文推理服务的实际情况。
- **`S` 较短时存在一个有限的大 batch `B*(S)`**（`S = 512` 时是 451，`S = 1024` 时是 949），越过去就翻转成算力受限。**短上下文 + 大 batch 的 decode 会退化成 prefill**，这正是 continuous batching（不等整批请求结束就换入新请求，把 batch 撑大）与 chunked prefill（把长 prompt 切块、与 decode 混跑）在工程上成立的根据。

## 2. 执行映射

Roofline 的两条边界在硬件上各有主人。

**HBM 侧**由显存控制器（memory controller）与显存总线决定。H100 SXM 是 80 GB HBM3，总线带宽 `3.35 TB/s`（来自 NVIDIA H100 datasheet 规格表）。所有 `Bytes` 都要从这条总线上过一遍，没有第二条路——这也是 `Bytes` 只统计 HBM 流量的物理依据。

**L2 缓存**能在 HBM 与 SM 之间挡下一部分流量，从而改变**有效**算术强度。H100 有 `50 MB` L2（`09` 的边界声明）。它能影响的是「同一份数据被读几遍」：一个大 GEMM 的权重如果被 L2 兜住了一部分，实际 HBM 流量就低于 `Bytes` 的估算，实测性能因而**高于** roofline 给的线。反过来，L2 命中率是实现的属性，roofline 故意不把它算进 `I`——曲线给的是**上界**，不是预测值。

**算力侧**由执行单元决定，而不同执行单元的量级差异极大。Tensor Core 在 BF16 dense 下是 `989.5 TFLOPS`；而做 `exp` 的 SFU（special function unit）吞吐远低于 FMA。`09` 的 FLOPs 计数口径把「exp 等超越函数计 1 次运算」，硬件上 SFU 的 exp 吞吐远低于 FMA，所以 elementwise 算子的真实耗时会比按此口径估的更差。这不影响它们在 roofline 上被判为带宽受限，只影响可达算力的具体数值。

`09` 里那张 ASCII 双对数图把所有算子都落在一张图上（§5 表 5）：`D/S/E/N`（`I ≈ 1～1.5`）挤在斜线最下端，可达算力只有几个 TFLOPS；`Q/V`（`I = 120`）压在斜线中段，可达算力 404 TFLOPS；`p/P`（`I = 455 / 2048`）已经越过拐点，踩在水平段上。**这张图上唯一能吃到峰值算力的只有 prefill 的 GEMM。**

把这套映射翻译成一句可操作的话：**同一个矩阵乘 kernel，形状不同就是两种瓶颈**。这就是为什么推理引擎要为大 batch 和小 batch 准备不同的 kernel——它们的 `I` 相差三个数量级，优化方向完全不同。

## 3. 实现与演进

**纸面 roofline。** 最初的形式就是本文 §1 的两段线：一条斜线 `B_peak × I` 加一条水平线 `P_peak`，两者以 `I*` 为界取小。它的价值在于把「优化什么」变成一个可以纸笔算完的判断——不需要 profiler，不需要跑一遍。

**加上 cache 分层。** 单层 roofline 只承认 HBM 一条带宽。真实机器有 L1 / 共享内存 / L2 三层，每一层的带宽都比下一层高一个数量级。把每层各画一条斜线，就得到**多级 roofline**：一个算子的 `I` 落在哪两条线的交点附近，就说明瓶颈已经从 HBM 转移到了下一级。这一步的意义是它解释了「为什么 tiling 有效」——tiling 不改变 `I`（`Bytes` 口径不变），但把中间复用推给了更快的层级，等效于抬高了斜线的斜率。

**加上延迟约束。** 两段线全是**吞吐**边界，没有一条约束说「这些数据要在多久之内到」。带上一条 Little 定律，就能推出「需要多少常驻 warp 才能把这条线的带宽吃满」——那一步的正文在 [20-gpu-architecture/execution-model/03-occupancy-and-latency-hiding](../../20-gpu-architecture/execution-model/03-occupancy-and-latency-hiding.md)（正文在该域，此处回链）。这是 roofline 最常被忽略的一半：满足了 `I` 的判据，只说明瓶颈不在算力，不说明带宽一定吃得满。

**加上实测校准。** 纸面 roofline 的 `P_peak` 来自规格表，而实测峰值总是更低（boost clock 漂移、占用率不足）。把 `P_peak` / `B_peak` 换成自己机器上量出来的值，曲线才从「这条线理论上存在」变成「我的机器上这条线在这里」——这就是 [03-measuring-roofline](03-measuring-roofline.md) 的内容。

## 4. 踩坑与失败模式

### 4.1 把代码里的所有访存都算进 Bytes

**现象**：算一个 fused kernel 的算术强度，把循环体里每一条 `load` 都数进去，算出 `I` 远高于 `I*`，于是判定它算力受限，转头去优化指令选择，性能毫无变化。

**成因**：`Bytes` 的口径是**必须往返 HBM 的字节**，不是代码里出现的访存次数。被 L1 / 共享内存 / L2 挡住的复用一次 HBM 都不需要走。把命中的访存算进分母，会把 `I` 算大一到两个数量级，判定的方向可能整个反过来——`I` 恰好落在 `I*` 附近时尤其危险。

**规避**：按「每个张量被从 HBM 读了几遍、写了几遍」来数，而不是按指令数来数。一个 `tile` 在共享内存里被复用 N 次，在 `Bytes` 里仍然只算它从 HBM 进来的那一次。自检办法：把算出的 `Bytes` 乘以 `B_peak`，如果得到的时间比实测耗时**还小**，说明 `Bytes` 低估了（有额外的 HBM 流量）；如果远大于实测算出的流量，说明把命中算进去了。

### 4.2 不注明精度的 `I*`

**现象**：看到某个 kernel 的 `I = 100`，查到一个「H100 的拐点是 295」，判定它带宽受限，于是去做融合、量化、减少访存——但如果这个 kernel 跑在 FP32 上，它其实是**算力受限**的，该做的是换精度而不是省访存。

**成因**：`I* = P_peak / B_peak`，而 `P_peak` 随精度变化极大。同一台 H100 SXM，FP64 的 `I*` 是 10.1、FP32 是 20.0、TF32 是 147.6、BF16/FP16 是 295.4、FP8 是 590.7——**最大差 58 倍**。一个不带精度口径的 `I*` 是个无法使用的数。

**规避**：任何 `I*` 都写成「`<型号> <精度> <dense/sparse>` 下的 `I*`」三元组，例如「H100 SXM BF16 dense 295.4」。dense/sparse 这一项也不能省：2:4 结构化稀疏的峰值恰是 dense 的两倍，混用会让 `I*` 整体挪位一倍。

### 4.3 认为「算力利用率低就是 kernel 写得差」

**现象**：profile 一个 kernel，看到 Tensor Core 利用率只有 0.42%，认定实现有严重问题，投入大量时间重写。

**成因**：带宽受限的算子**本来就**用不到多少算力。softmax 的 `I = 1.25`，可达算力 4.19 TFLOPS，是峰值的 0.42%——这个 0.42% 是模型的结论，不是实现的缺陷。把 roofline 已经封好的上限当成优化空间，是在追一个不存在的东西。

**规避**：先看 `I` 落在哪一侧。`I ≪ I*` 时该做的是融合与量化（少搬一次）；`I ≈ I*` 时每一点算术强度才是真金白银；`I ≫ I*` 时该做的是换峰值更高的精度。只有在 `I` 明确大于 `I*` 的算子上，算力利用率的绝对值才有意义。

### 4.4 把「decode 必然是带宽受限」当成无条件结论

**现象**：拿 `I_decode = 1.0` 这个数推出「无论怎么加 batch，decode 都是带宽受限」，据此把 batching 的收益上限估得很低。

**成因**：`I_decode = 2P/2P = 1.0` 这个推导**只算了权重**，漏掉了 KV cache 与 decode 时注意力自身的 FLOPs。把两项补回去之后 `I` 变成 `(2P + 4·S·d_model·n_layers)/(W + B·S·kv)`，它是一个**随 batch 上升的函数**：KV 字节随 `B` 线性涨，权重 140 GB 是一次性的，越摊越薄。在 `S = 8192` 下它从 `B=1` 的 1.13 涨到 `B=256` 的 49.97（利用率 0.38% → 16.92%），虽然仍远低于 `I*`，但方向是涨的。

**规避**：把 `B` 与 `S` 都放进公式再下结论，并解出翻转条件 `B*(S)`。本例里 `S = 512` 时 `B* = 451`、`S = 1024` 时 `B* = 949`——这个量级在真实服务里是够得到的；而 `S ≳ 1487` 之后 `B*` 无解，「任何 batch 都带宽受限」才成立。**说「接受这个上限」，必须连同「在什么 `S` 与 `B` 范围里」一起说。**

## 6. 小结与延伸

全文只有一条主线：**瓶颈类型由一个比值决定**。`t = max(W/P, Q/B)` 里两个候选时间谁大，等价于 `I` 与 `I*` 谁大，与算子的绝对规模无关。围绕这条主线，有四个可独立复用的中间结论：

1. `I` 的分子是 FLOPs（FMA 计 2），分母是**必须往返 HBM 的字节**——不是代码里所有访存。
2. `I* = P_peak / B_peak` 由机器单独决定，但**必须带精度口径**：同一台 H100 SXM 上 FP64 与 FP8 的 `I*` 差 58 倍。
3. 两段线 `min(P_peak, B_peak·I)` 是可操作的：`I < I*` 时提高算术强度线性换性能，`I > I*` 时封顶，只能换精度。
4. decode 的 `I_decode = 1.0` 只在「不算 KV cache、不算注意力 FLOPs」的口径下成立。加上这两项之后它随 `B` 上升，`I_∞(S)` 有下限 8.0，翻转条件是 `S ≲ 1487` 时存在有限的 `B*(S)`。

接下来两篇各有分工。[02-amdahl-and-scaling](02-amdahl-and-scaling.md) 换一个维度：单机内的瓶颈类型判完之后，多机扩展的天花板在哪里——那里会出现一个与本文结论共振的事实，**数据并行的 all-reduce 通信量是一个与卡数无关的常数**，它正是 Amdahl 串行项在多机场景下的物理来源。[03-measuring-roofline](03-measuring-roofline.md) 则把本文用的规格表峰值换成自己机器上量出来的可达峰值——毕竟规格表上的数是上限，不是你的天花板。
