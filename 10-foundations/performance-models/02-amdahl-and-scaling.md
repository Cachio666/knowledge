# Amdahl 定律与扩展性：并行的天花板在哪

> 单机内的天花板由**串行分数** `s` 决定：加速比永远超不过 `1/s`。多机扩展的额外天花板由**通信的常数项**决定：数据并行的 all-reduce 每卡通信量饱和到 `2S`，与卡数无关。两者都不是「很难达到」，而是**数学上做不到**。

## 0. 背景与动机

一个 70B 模型的数据并行训练任务，全局 batch 400 万 token，节点间走 InfiniBand NDR（400 Gb/s）。任务在 64 卡上跑得挺好。现在要扩到 512 卡——**八倍的机器**——该准备几倍的预算？

直接乘 8 是错的。按本文的模型算（§5 表 3）：这个任务在 64 卡上的扩展效率是 `82.8%`，在 512 卡上是 `37.2%`。所以 64 → 512 的实际加速比是

```text
T(64) = 1697.83/64 + 5.513 = 26.53 + 5.513 = 32.04 s
T(512) = 1697.83/512 + 5.589 = 3.32 + 5.589 = 8.91 s
加速比 = 32.04 / 8.91 ≈ 3.6 倍        （8 × 0.372/0.828 = 3.6）
```

**八倍的机器换来 3.6 倍的加速**，剩下的 4.4 倍去哪了？

答案藏在第二项里：`5.513 s` 与 `5.589 s` 这两个通信时间几乎一样，而计算时间从 `26.53 s` 掉到了 `3.32 s`。也就是说，**加卡只摊薄了计算，一点没摊薄通信**。更反直觉的是：通信**数据量**并不随卡数爆炸——它饱和在一个与 `N` 无关的常数上（每卡 279.7 GB 左右，§5 表 2）。真正随卡数线性增长的是**通信步数**，而步数乘以每步的固定延迟，在本例里相对那个常数小了两三个数量级。

所以「加卡能快多少」这个问题有两个独立的约束：一个是 Amdahl 的串行分数，一个是通信的常数项。本文负责把这两个约束分别推出来，再回答一个更实用的、也更容易答错的问题：**存在一个「最佳卡数」 `N*` 吗？** 答案是：闭式解存在，但**它不是有效的工程拐点**，而且直接把它报出去会高估可用规模 43 倍。

## 1. 原理

### 第一步：Amdahl——串行分数给加速比封顶

把程序按「能不能并行」切成两块。用归一化的说法：串行部分占总时间的比例是 `s`，可并行部分是 `1-s`。

```text
单处理器：T(1) = s + (1-s) = 1        （把单处理器总时间归一化为 1）
N 处理器：T(N) = s + (1-s)/N          （只有可并行部分被摊薄）
```

加速比就是二者之比：

```text
S(N) = T(1) / T(N) = 1 / ( s + (1-s)/N )
```

推导到这里已经能看出上限了。把分母里的 `s` 单独拎出来：

```text
S(N) = 1 / ( s + (1-s)/N )  <  1 / s        （因为 (1-s)/N > 0）
```

`N → ∞` 时 `(1-s)/N → 0`，所以 `lim S(N) = 1/s`。**无论投多少处理器，加速比都超不过 `1/s`**；`s = 5%` 时上限是 20 倍——哪怕用一百万张卡。

这个上限不是「很难达到」，是**做不到**。给定目标加速比 `S_t` 反解需要的处理器数：

```text
由 S_t = 1/(s + (1-s)/N) 解出：
N = (1-s) / (1/S_t - s) = (1-s)·S_t / (1 - s·S_t)
```

`s = 0.05` 时想要 `S_t = 20` 恰好需要 `N = ∞`，想要 100 倍则分母 `1 - 0.05×100 = 0` 直接变号——**无解**。注意另一侧的荒谬：`s = 0.001` 时上限是 1000，想要 512 倍「只要」1048 张卡——看起来还行，但 `N = 4096` 时才跑到 `803.9`，只有上限的 80%，也就是说千分之一的串行部分吃掉了 80% 的潜在加速（理想 4096 倍，实得 804 倍）。

### 第二步：Gustafson——换个固定的量，结论就反过来

Amdahl 固定的是**问题规模**：机器变多，每个处理器分到的活变少。Gustafson 固定的是**单处理器的工作量**：机器变多，总问题规模一起变大。

推导。固定「并行执行时」的总时间为 1：串行部分耗时 `a`，可并行部分耗时 `1-a`。现在问：这同一个问题放到 1 个处理器上要多久？可并行部分在单处理器上要花 `(1-a)·N` 的时间（`N` 倍），串行部分不变：

```text
T(1) = a + (1-a)·N
S(N) = T(1) / T(N) = a + (1-a)·N
```

**这是一个关于 `N` 的线性函数，没有上限。**它不是对 Amdahl 的否定——两者**固定的量不同**：

| 参数 | `T(N)` 固定为 | `T(1)` | `S(N)` | 形态 |
|---|---|---|---|---|
| Amdahl | 问题规模 | 1 | `1/(s+(1-s)/N)` | 有上界 `1/s` |
| Gustafson | 单卡工作量 | `a+(1-a)N` | `a+(1-a)N` | 线性无界 |

这句话必须落到具体数字上才可信。同一个物理量（串行占比）、同一个 `N`，两个定律给出的答案差了几个数量级：

| 串行占比 | `N` | Amdahl `S(N)` | Gustafson `S(N)` | 差多少倍 |
|---|---|---|---|---|
| 0.050 | 16 | 9.14 | 15.25 | 1.7 |
| 0.050 | 256 | 18.62 | 243.25 | 13.1 |
| 0.050 | 4096 | 19.91 | 3891.25 | 195.5 |
| 0.100 | 4096 | 9.98 | 3686.50 | 369.5 |

**哪个对？取决于你在扩机器的时候有没有把 batch 一起放大。**固定 batch、只加卡，是 Amdahl 的处境，加速比封顶；加卡的同时把 batch 按比例放大，是 Gustafson 的处境，加速比线性。LLM 训练实际走的是后者（全局 batch 随卡数一起涨，这也是为什么要调 learning rate scaling），所以「训练任务能扩到几万卡」的答案比 `1/s` 乐观得多——**但前提是 batch 还能继续放大**，而 batch 放大会撞上收敛性上限，那是训练动力学的问题，本文不涉及。

### 第三步：把通信写进模型，解出 `N*`

前两步都假设并行部分免费扩展。现实里并行要通信，而通信开销随 `N` 增长。把时间写成三项：

```text
T(N) = t_s + t_p/N + t_c·f(N)

  t_s     ：完全不能并行的固定时间
  t_p/N   ：计算部分，随 N 摊薄
  t_c·f(N)：通信部分，随 N 增长
```

关键在于 `f(N)` 取什么，它对应两种不同的集合通信算法：

| `f(N)` | 对应算法 | 为什么 |
|---|---|---|
| `N` | ring all-reduce | 步数 = `2(N-1)`，每步有固定延迟 `α` ⇒ `2(N-1)α ∝ N` |
| `log N` | tree / recursive halving | 步数 = `2·log₂N` ⇒ 延迟 `∝ log N` |

本文用线性项。理由不是它更大，而是它**更对**：LLM 训练的梯度 all-reduce 是**大消息**，主路径是 ring；tree 的 log N 在 NCCL 里确实存在（小消息默认走 tree），但对大梯度不是主路径。**更要紧的是数据量项本身不是 `t_c·N`**——下一节专门论证这一点。

对线性模型求极小。记 `f(N) = N`：

```text
T(N) = t_s + t_p/N + t_c·N
dT/dN = -t_p/N² + t_c
令其为零：-t_p/N² + t_c = 0  ⟹  N² = t_p/t_c
N* = sqrt( t_p / t_c )
```

二阶导 `d²T/dN² = 2·t_p/N³ > 0`，所以这是极小点。代回去得到最小时间：

```text
T(N*) = t_s + t_p/sqrt(t_p/t_c) + t_c·sqrt(t_p/t_c)
      = t_s + sqrt(t_p·t_c) + sqrt(t_p·t_c)
      = t_s + 2·sqrt(t_p·t_c)
```

对照 `f(N) = ln N`：`dT/dN = -t_p/N² + t_c/N = 0 ⟹ N* = t_p/t_c`，`T(N*) = t_s + t_c·(1 + ln(t_p/t_c))`。**线性模型是平方根（增长慢），log 模型是线性**。取 `t_p = 1` 归一化，两个闭式解差 1.5～4 个数量级（`t_c = 1e-4` 时是 100 对 10000）。所以必须按实际用的是 ring 还是 tree 来选模型——**选错的代价不是小数点，是「能扩到 100 卡」和「能扩到 10000 卡」的区别**。

还有一个容易被当成笔误的细节：`N*` 的表达式里**没有 `t_s`**。这不是笔误——`t_s` 是与 `N` 无关的常数，平移整条曲线但不改变它的形状，所以最优 `N` 完全由 `t_p` 与 `t_c` 的相对大小决定。

### 第四步：all-reduce 的每卡通信量是一个与 `N` 无关的常数

这一步是全文最反直觉的地方。ring all-reduce 分两个阶段（reduce-scatter + all-gather），每个 rank 的收发量是

```text
V(N) = 2(N-1)/N × S        S = 梯度总字节数
```

把 `N` 提出来看：`2(N-1)/N = 2 - 2/N`，`N → ∞` 时它趋近 2。也就是说 `V(N) → 2S`，**是个常数**。表（§5 表 2，`S = 140 GB`）：`N=2` 时每卡 140.0 GB（占 `2S` 的 50.0%），`N=64` 时 275.6 GB（98.4%），`N=1024` 时 279.7 GB（**99.9%**）。**数据并行的通信数据量不会随卡数爆炸**——这一点常被说反。

但它也**不随 `N` 下降**。这正是第一步那个串行分数 `s` 在多机场景下的物理来源：计算时间 `t_p/N` 一路降到 0，通信时间却停在 `2S/BW` 不动。把这个饱和的通信时间记成 `t_s`：

```text
IB     : t_s = 2S/BW = 2.800e+11 / 5.0e+10  = 5.600 s
NVLink : t_s = 2S/BW = 2.800e+11 / 4.5e+11  = 0.622 s
```

`S = 140 GB` 时 `2S = 2.800e+11` 字节。这两个数就是数据并行的 Amdahl 串行项——与 `N` 无关，永远在那儿。

### 第五步：三项模型与它的存在性条件

既然饱和的通信量是个常数，它应该作为 `t_s` 而不是 `t_c·N` 进入模型。把两项通信都写进去（计算 + 步数延迟 + 饱和带宽项）：

```text
T(N) = t_p/N + 2(N-1)α + 2(N-1)/N · S/BW
dT/dN = -t_p/N² + 2α + 2S/(BW·N²)
令其为零：2α = (t_p - 2S/BW)/N²
N* = sqrt( (t_p - 2S/BW) / (2α) )
```

那个 `2S/BW` 从 `t_p` 里**减掉**——因为通信量本身不随 `N` 下降，它等效于把可摊薄的算力变小了。代入 `t_p = 1697.8`、`2S/BW = 5.60`、`2α = 1.000e-05`：

```text
IB : t_p - 2S/BW = 1697.8 - 5.60 = 1692.2 ⇒ N* = sqrt(1692.2 / 1.0e-05) = 13009
```

**修正只把 `N*` 从 13030 挪到 13009，改了 0.17%——微不足道。**修正量小这件事本身就是结论：它再次说明饱和通信量在这里远不足以改变延迟项给出的 `N*`。

三项模型真正给出的新东西是**存在性条件**：`t_p ≤ 2S/BW` 时 `(t_p - 2S/BW) ≤ 0`，`N*` 不存在，此时 `dT/dN > 0` 对所有 `N` 成立，`T(N)` 单调上升，**加卡永远不划算**。换算成 batch：在 IB 上跑 70B，全局 batch `B ≤ 13193` token 时，连第二张卡都不划算（NVLink 上这个阈值是 `B ≤ 1466`）。

### 第六步：`N*` 不是有效的工程拐点

现在把 `N*` 与实际测得的效率曲线摆在一起。线性延迟项的物理来源是 ring 的 `2(N-1)` 步延迟，每步 5 μs，所以 `t_c = 2α = 1.000e-05` s/rank：

```text
线性模型 N* = sqrt(t_p/t_c) = sqrt(1697.8 / 1.0e-05) = 13030
log  模型 N* = t_p/t_c      = 1697.8 / 1.0e-05      = 169782719
```

**两个 `N*` 都在一万卡以上（log 模型更是到了 1.7 亿）。但按扩展效率的判据，效率在 `N ≈ 305` 就跌破 50% 了。**

原因很直接：线性延迟项每次同步 0.01 ms（`N=1000` 时累计 10.0 ms），相对饱和的通信量 5.60 s 小了两三个数量级。**真正卡住扩展的是那个常数通信量，不是步数延迟。**把 `N* = sqrt(t_p/t_c)` 当成「最佳卡数」报出去，会高估可用规模 **43 倍**（13030 / 305）。**闭式解只对它基于的那个模型成立**——它假设 `t_c·N` 是主要通信开销，而本例里主要开销是一个与 `N` 无关的常数，所以这个 `N*` 约束不到任何东西。

因此本文给出的是**两个不同性质的数**，不能混用：

| 量 | 值 | 它回答的问题 |
|---|---|---|
| `N* = sqrt((t_p − 2S/BW)/(2α))` | 13009 | 「在只考虑步数延迟的模型里，总时间的最小点在哪」——**不是工程拐点** |
| `N₅₀`（η 跌破 50%） | 305（IB）/ 2730（NVLink） | 「加到多少卡，一半的算力被通信吃掉」——**这才是工程决策的依据** |

## 2. 执行映射

**ring all-reduce 的两个阶段。**NCCL 的 ring all-reduce 是 reduce-scatter 加 all-gather：先把 `S` 字节切成 `N` 份，绕环走 `N-1` 步做完分片归约，再绕环走 `N-1` 步把结果拼回来，合计 `2(N-1)` 步。每卡在这两阶段里发出的字节数正是 `(N-1)/N × S` 的两倍，即 `V(N) = 2(N-1)/N × S`——这就是第四步那个公式的来历。**注意它是一个「步数 × 每步固定延迟」的结构**：数据量那一项饱和，步数那一项线性增长，两者在不同规模区间主导。

**NVLink 与 InfiniBand 把扩展分成两个区间。**节点内走 NVLink 4，规格标 900 GB/s、每方向 450 GB/s；跨节点走 InfiniBand NDR，400 Gb/s = 50 GB/s 单向。**口径警告**：900 GB/s 是双向合计，50 GB/s 是单向，直接拿 900 比 50 得到 18 倍，同口径（每方向）比只有 9 倍。本模型一律用每方向带宽，因为 all-reduce 里每个 rank 的收发量相等，瓶颈在单向链路上。

这个 9 倍的差距直接决定了两个拐点：IB 上 `N₅₀ = 305`，NVLink 上 `N₅₀ = 2730`——**差了将近一个数量级**。也就是说同一个模型，跑在节点内和跑在跨节点，可扩展规模的量级完全不同。

**数值量级**：梯度 `140 GB`（70B 参数、BF16），饱和通信时间 `5.600 s`（IB）对 `0.622 s`（NVLink），`t_p = 1697.8 s`（全局 batch 400 万 token、H100 SXM BF16 dense 989.5 TFLOPS）。

## 3. 实现与演进

**纯数据并行。**梯度 all-reduce 是唯一的通信，每卡通信量饱和到 `2S`。显存占用是最大的问题：每个 rank 都要放完整的模型、梯度与优化器状态（fp32 的 Adam 状态是参数的 8 字节/参数，70B 模型光优化器状态就 560 GB），单卡装不下。

**ZeRO / FSDP。**把优化器状态、梯度、参数按 rank 切分，显存占用降到 `1/N` 量级，代价是**通信量上升**——ZeRO 三阶段把通信量从 `2S` 抬到接近 `3S` 以上（多一次 all-gather 参数）。所以这一步是拿扩展性换显存，不是双赢。`10` 的边界声明里明确把「优化器状态通信」列为未建模项，正是这个原因。

**张量并行。**把单层的矩阵乘切开，通信发生在**每一层内部**（attention 后、FFN 后各一次 all-reduce），通信量与激活成正比，而不是与参数量成正比。这使它对带宽极其敏感，因此只在高带宽互联（NVLink）上可用，通常限于单节点 8 卡。这也是为什么 TP 的规模上限由节点内互联决定。

**3D 并行（TP × PP × DP）。**把三种切法组合：TP 吃掉节点内带宽，PP 走点对点，DP 承担跨节点的大规模扩展。走在最外层的仍是数据并行，所以本文的结论——**跨节点规模由 `N₅₀` 决定，而 `N₅₀` 正比于 `t_p`、也就是正比于全局 batch**——直接决定了整个训练任务能铺到多少卡。

## 4. 踩坑与失败模式

### 4.1 把 `N* = sqrt(t_p/t_c)` 当成「最佳卡数」报出去

**现象**：规划集群规模时，把三项模型求导得到的 `N*` 当作应当采购的卡数，本例给出 13030——于是按一万卡的规模做预算与拓扑设计。

**成因**：闭式解只对它基于的那个模型成立。`N* = sqrt(t_p/t_c)` 假设主要通信开销是 `t_c·N`（步数延迟）。而 LLM 训练的大梯度 all-reduce 里，主要开销是**饱和的常数通信量** `2S/BW`，步数延迟比它小两三个数量级。真实效率在 `N ≈ 305` 就已经跌破 50%，闭式解给的 13030 高估了 **43 倍**。

**规避**：把两个数分开算、分开报。`N*` 回答「模型里的极小点在哪儿」，`N₅₀`（η 跌破 50% 的卡数）回答「加到多少卡就不划算」。工程决策只该用后者，而后者由带宽项决定：无重叠时 `η = 50%` 等价于 `t_comm(N) = t_p/N`，即 `2(N-1)·S/BW = t_p`，解出 `N₅₀ = 1 + t_p·BW/(2S)`——IB 上 304.2，NVLink 上 2729.7，与表里数出来的值一致。

### 4.2 用 Amdahl 的 `1/s` 预估 LLM 训练的扩展上限

**现象**：拿 `s = 5%`（对应上限 20 倍）当作训练任务能扩到 20 卡的依据，或者反过来，因为它「只有 20 倍」而判断大规模训练不可能。

**成因**：两个错误叠加。其一，`1/s` 里的 `s` 是**单机内**的串行分数，多机场景的对应约束是通信常数 `2S/BW`，来源完全不同——把它当同一个东西会算错量级。其二，LLM 训练实际走的是 **Gustafson** 而不是 Amdahl：全局 batch 随卡数一起涨，`N = 4096` 时 Gustafson 给 3891 倍而 Amdahl 给 19.91 倍，差 195.5 倍。用 Amdahl 的框架去回答一个 Gustafson 的问题，起点就错了。

**规避**：先问「扩机器时 batch 跟着涨吗」。涨，用 Gustafson 的线性式；不涨（强扩展），用 Amdahl 的 `1/s` 并且把 `s` 的物理来源换成通信常数。两者的正确关系是：**Amdahl 的 `s` 在多机数据并行里的具体数值就是 `2S/BW ÷ t_p`** 这个比值——它随 batch 增大而减小（因为 `t_p` 正比于 batch），这就是为什么大 batch 任务能扩得更远。

### 4.3 把弱扩展的漂亮曲线当成强扩展的证据

**现象**：看到「每卡 batch = 65536 时，NVLink 上效率仍有 97.8%」，得出「这个任务在强扩展下几乎不掉效率」的结论。

**成因**：弱扩展固定**每卡的工作量**，总 batch 随 `N` 一起涨——机器越多，每卡要干的活一点没变少。这时效率里根本没有 `t_p/N` 那一项在缩小，通信的常数项相对一个不变的 `t_p` 自然显得很小。而强扩展固定**总 batch**，`t_p/N` 一路降到 0，同一个常数项就变成主导。两者固定的是不同的量，曲线好看与否不能互证。

**规避**：报扩展效率时必须写明是强扩展还是弱扩展，并给出固定的量（总 batch 还是每卡 batch）。弱扩展的那一列还要注明它是**上界**：`10` 只算了 `N → ∞` 时 `2S/BW + 2α` 的带宽部分，没有算 `2(N-1)α` 的线性增长——`N` 大到步数延迟不可忽略时，效率仍会被拖下来。

### 4.4 小 batch 的任务也上数据并行

**现象**：一个全局 batch 只有几千 token 的训练或微调任务，为了「用满机器」而铺到几十卡上做数据并行，结果墙钟时间不降反升。

**成因**：计算时间 `t_p = 6·P·B/P_peak` 正比于全局 batch。batch 小到 `t_p ≤ 2S/BW` 时，`T(N)` 对 `N` 的导数恒为正——**加任何一张卡都在增加总时间**，因为通信的常数项已经超过全部计算时间。在 IB 上跑 70B，这个阈值是 `B ≤ 13193` token；`B = 1e5`（十万 token）时 `t_p = 42.4 s`，而 `2S/BW = 5.60 s`，`N₅₀` 只有 **9 卡**——第九张之后就有一半算力被通信吃掉。

**规避**：先算 `t_p / (2S/BW)` 这个比值再决定要不要并行。比值接近 1 时改做**梯度累积**（把 batch 攒大，不增加卡数）或换并行策略（TP/PP 的通信模式与 DP 不同）。另注意 `N₅₀` 正比于 batch：`B` 从 `1e6` 涨到 `4e6`，`N₅₀` 从 77 涨到 304——**想扩到更多卡，先想办法把全局 batch 放大**。

## 6. 小结与延伸

全文有两条独立的天花板，分别来自两个不同的「固定量」：

1. **Amdahl 的天花板是 `1/s`**，`s` 是串行分数。它固定问题规模，所以 `N → ∞` 时加速比停在 `1/s`。`s = 0.05` 时上限 20 倍，且 `N` 从 1024 涨到 65536（64 倍）只从 19.6 涨到 20.0。
2. **多机扩展的天花板是通信的常数项**。ring all-reduce 每卡通信量 `V(N) = 2(N-1)/N × S` 饱和到 `2S`——与 `N` 无关。计算时间降到 0，这一项不动。它正是第一条里 `s` 在多机数据并行场景下的物理来源。

由此得到四个可独立复用的结论：

1. Amdahl 与 Gustafson 不矛盾，因为固定的量不同（问题规模 vs 单卡工作量）。同一个 `a = 0.05`、`N = 4096`，两者给 19.91 倍与 3891.25 倍，差 195.5 倍。
2. 三项模型的 `N*` 有闭式解 `sqrt((t_p − 2S/BW)/(2α))`，但它**不是有效工程拐点**。在本例里它给 13009，而效率在 `N ≈ 305` 就跌破 50%——闭式解高估 43 倍。工程判断要用 `N₅₀ = 1 + t_p·BW/(2S)`。
3. 三项模型真正的新内容是**存在性条件**：`t_p ≤ 2S/BW` 时 `N*` 不存在，加卡永远不划算。IB 上对应 `B ≤ 13193` token。
4. 效率取决于**每卡算多少 token**，不取决于卡数。`N₅₀` 正比于全局 batch——想扩到更多卡，先想办法把 batch 放大。

本文只建模了数据并行的梯度 all-reduce。张量并行与流水线并行的通信模式完全不同（TP 每层两次 all-reduce，PP 是点对点），本文的结论**不能**直接套用；数据并行的完整工程形态（ZeRO / FSDP / 3D 并行）的正文在 [100-parallelism/zero-fsdp](../../100-parallelism/zero-fsdp/) 与 [100-parallelism/data-parallel](../../100-parallelism/data-parallel/)（正文在该域，此处回链）。另外，`10` 明确列出未建模项：优化器状态通信（ZeRO 会把通信量抬到 3 倍以上）、通信与计算的实际重叠效率、网络拓扑的收敛比（跨交换机时多跳链路能同时承载的带宽比例）、straggler（最慢的那个 rank 决定整批的完成时刻），以及 ring 之外的其他算法。

回看 [01-roofline-model](01-roofline-model.md)：那篇给出单机内的瓶颈判据，本文给出多机扩展的判据，两者的形式是同一个——**一个与规模无关的常数项决定了上限**。单机里那个常数是 `P_peak` 与 `B_peak` 的比，多机里那个常数是 `2S/BW`。
