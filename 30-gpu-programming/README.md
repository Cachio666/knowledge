# 30-gpu-programming GPU 编程模型

从 CUDA C++ 到 CuTe，指挥 GPU 的几套语言与抽象层次。

本域不回答「这个算子**怎么写快**」（那是 `40-kernels`），也不回答「硬件**是什么**」（那是 `20-gpu-architecture`）。
它回答：**每一层抽象向你承诺了什么，以及那个承诺在哪里断裂。**

## 本域覆盖什么

| 主题 | 内容 | 状态 |
|---|---|---|
| [cuda](cuda/) | 线程组织与同步契约 / 流与事件 / 内存管理与 CUDA Graph | **已完成**（3 篇） |
| [triton](triton/) | 块级程序模型 / 边界掩码 / layout 泄漏 / 归约的跨 warp 代价 | **已完成**（4 篇） |
| [ptx-sass](ptx-sass/) | PTX 作为虚拟 ISA / warp 级执行 / 访存计数与 PTX→SASS 落差 | **已完成**（3 篇） |
| [cutlass](cutlass/) | CuTe layout 代数 / 层次化 tiling / swizzle 与 collective | **已完成**（3 篇） |

**统一主线**：

> **你写的程序、编译器生成的东西、硬件执行的东西，是三个不同的程序。**

四个主题是这条主线的**四次穿越**，也正好构成「**控制权逐步让渡、抽象逐步升高**」的顺序：

| 主题 | 层 | 边界（泄漏点） |
|---|---|---|
| `cuda` | CUDA C++ / 宿主 API | 你写的线程组织与同步 → 运行时**实际**给的顺序与并发 |
| `triton` | Triton DSL | 你写的块级程序 → 编译器**替你选**的 layout 与掩码 |
| `ptx-sass` | PTX / SASS | 编译器生成的**虚拟** ISA → 硬件执行的**物理** ISA |
| `cutlass` | CuTe 模板 | 你写的类型 → **编译期算出**的布局与派发 |

**这条主线直接产出的一个推论**，四篇都要用到：

> **抽象层的价值与它的泄漏是同一件事的两面。** 一个没有任何泄漏的抽象之所以可能存在，
> 通常是因为它把代价藏在了**别处**——藏到编译期、藏到一次隐式的数据搬运、
> 藏到一个只有特定形状才会触发的慢路径。**每一篇都要指出那个「别处」在哪里。**

## 本域**不**做什么

本域上下都紧挨着已建成的域，边界必须写死，否则会与它们大量重复。

| 相邻域 | 它讲什么 | **本域不讲什么** |
|---|---|---|
| `20-gpu-architecture` | 硬件**是什么**（SM、存储层次、Tensor Core、互联） | 本域不讲硬件原理。本域讲**语言层如何暴露它**，原理**回链**该域 |
| `40-kernels` | **具体算子**怎么写快 | 本域**不出现任何算子的完整实现**。本域讲写算子的**语言与抽象层** |
| `45-kernel-lifecycle` | 做**哪一个**、**什么时候停** | 本域不讲流程与决策 |
| `50-performance` | profiling **工具**与瓶颈定位 | 本域不重复工具用法。`ptx-sass` 只讲**读 SASS 的方法与 ISA 语义**，不讲怎么用 `ncu` |
| `60-compilers` | 编译器**内部**（MLIR / TVM / Inductor / XLA 的架构） | 本域不讲编译器架构。`triton` 讲的是**语言模型与它的边界**，编译器内部**回链**该域 |
| `10-foundations` | 浮点与性能模型的**原理** | 本域不重推 roofline、不复述浮点格式 |

**特别提醒**：`20-gpu-architecture/memory-system/03-shared-memory-bank-conflict.md` **已建成**。
`cutlass` 与 `ptx-sass` 讲 swizzle 与 bank 冲突时，**只讲它作为一种 layout 代数 / ISA 级计数的构造**，
**bank 冲突的机制回链**该篇，不重复推导。

## 代码约定：**真值来自外部真实工件**

本机的硬约束（已实测）：**无 GPU、无 `nvcc`/`cuobjdump`/`nvdisasm`/`ptxas`/`ncu`，
`triton` 全机器不存在，`numba`/`cuda-python` 未安装，三个源仓库里 0 个 PTX/SASS/cubin 文件。**

因此本域的编号程序**不写 `.cu`**，也**不 import 装不上的东西**。

| 文件 | 性质 | 构建 |
|---|---|---|
| `NN_*.py` | 编号程序，**与文档一一对应** | `make run` |
| `specs.py` | 非编号辅助模块，**外部事实常量** | 被编号程序读 |
| 其他无编号 `.py` | 引擎 / 独立参照 / 元检验等**支撑代码** | — |
| `Makefile` · `requirements.txt` | 构建 | — |

**本域的代码形态**（定义在 `CONTRIBUTING.md`「本域的代码形态」一节，此处只回链）：

> 编号程序是 `.py`、本机默认可跑，**断言在程序内部**（同 `CONTRIBUTING` 表里的第二种情形）；
> 与既有情形的区别**不在断言怎么分**，而在**真值从哪来**——
> 既有情形的真值都是本仓库自己构造的（手算、numpy 参照、迷你实现），
> **本域的真值是外部工件的真实行为**（CUTLASS 源码树 / 它自带的参考实现 / 厂商的训练材料）。

**硬规则**：

1. 每个主题必须**有一份本仓库自己的参照实现**，与外部工件**对拍**；
   **两者不一致时不默认工件是对的**，把差异当成结论写进正文。
2. **必须写明工件的版本与文件路径**。不写版本的源码引用**视为无效引用**。
3. **最大的风险是退化成转述**——一个只把外部工件的输出复述一遍的程序，不算知识库的程序。

## 数字口径

沿用 `CONTRIBUTING` 的**四类**（规格值 / 推导值 / 引用值 / 本机实测值），并叠加
`45-kernel-lifecycle` 的**来源分级 A–E**（A 厂商官方 · B 产品官方 · C 论文 · D 社区项目 · E 本库推导）。
**分级定义在 `45-kernel-lifecycle/README.md`，本域不重写，只回链。**

**本域额外两条**：

1. **外部工件的常量要记版本**：写法是「CUTLASS `<version>`，文件 `<路径>`，第 `<行>`」。
2. **不得以「官方说」的口吻引用源码注释**——源码里的注释是**某个实现的作者写的**，不是规范。

**★ 一处例外逐主题写明**：`cutlass` 主题会**真的 import `pycute` 与 `cutlass_library` 并跑它们**。
那是 NVIDIA 自己的参考实现**在本机跑出的结果**，属**「本机实测值」**，
**必须写明测的是哪个实现、哪个版本**，且**只能支撑关于 layout 代数与生成器策略的结论，
不能支撑关于 GPU 硬件的结论**。

## 文档的 §5：**逐主题形态不同**

`CONTRIBUTING` 第 315 行把 §5 定义为「**实测数据**（可选章节）」。本域**无 GPU ⇒ 无实测**，
所以 §5 改为**判据表**。**先例已存在**：`45-kernel-lifecycle/README.md` 声明了同一偏离。
**本域照做，不修改 `CONTRIBUTING` 第 315 行。**

| 主题 | §5 形态 |
|---|---|
| `cuda` / `ptx-sass` / `cutlass` | **判据表**（每行「可机械判定的条件 → 结论」，表要闭合）。`cutlass` 另有**真跑 `pycute`/`cutlass_library` 的本机实测值**，须带版本 |
| `triton` | **判据表 + 「本主题无实测，只有模型值」**——这一条必须与判据表**同时出现** |

## 与其他域的关系

- **上游**：`20-gpu-architecture`（不讲硬件原理写不出好 kernel）、`10-foundations`。
- **下游**：`40-kernels`（用这些工具写算子）、`60-compilers`（Inductor 生成 Triton 代码，要读懂才能调优）。
- **横切**：`50-performance` 的瓶颈定位常需下钻到 SASS；`ptx-sass` 提供**读它的方法**。
