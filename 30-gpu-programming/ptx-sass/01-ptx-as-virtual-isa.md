# PTX 作为虚拟 ISA：寄存器是声明的，不是分配的

> **PTX 里 `.reg .b32 %r<8>` 是一个声明，不是一个分配。** 本篇用一套**自己写的 PTX 子集解释器**（`code/ptxsub.py`）
> 与它的第一个编号程序（`code/01_virtual_isa.py`）把这句话做成**可算的量**，并给出三条带数字的结论：
>
> 1. ★★ **同一段 PTX 里，「声明了多少个寄存器」与「实际碰到了多少个」是两个可以任意不等的数。**
>   本主题两个真实片段：`.reg .b32 %r<8>` 声明 **8**、实际触及 **6**（比值 **1.3333**）与 **8 / 4**（比值 **2.0**）；
>   `.reg .pred %p<4>` 在两个片段里各声明 **4** 个谓词，而**两段 PTX 里一条 `setp` 都没有** ——
>   合起来 **8 个谓词槽从来没被写过**。**多声明是免费的**，而「省寄存器」在 PTX 层唯一的手段是**少声明**。
> 2. ★★ **PTX 的寄存器数、与硬件上真正用掉的物理寄存器数，没有任何关系** —— 但这句话在本库只能主张**一半**：
>   本库能算的是 PTX **声明量**与 PTX **触及量**（都来自文本）；**第三个量（SASS 上的物理寄存器数）本机一个都没观测过**
>   （无 `nvdisasm`）。**这一条限定语不是客套，它是本篇最容易被越界引用的地方**。
> 3. ★ **「用到了没有声明的 `%r8`」这件事，真正的 `ptxas` 在汇编期就拒绝，而解释器只能在执行到那条指令时才发现**
>   ⇒ 一个写在**不可达分支**里的非法寄存器引用，会**一路潜伏**（程序 `C.2` 把这件事跑了出来）；
>   而**表外指令**的检查是**静态**的（`validate()` 扫全部指令，不可达位置照样报错，程序 `C.4`）。
>   **同一个「不可达」位置，两种检查给出相反的结论** —— 这是本篇最具体的一条机制。
>
> ★★ 本篇的反直觉量化结论就是第 1 条：**声明的寄存器数与用掉的寄存器数没有任何关系**。
> 它是 `03-memory-and-sass-gap` 里「寄存器分配」那一节的入口。

> ★ **本域的三条强制限定语，在本篇的落点**（域 README 规定逐篇写明，不得省略）：
>
> 1. **「不是硬件」**——本篇跑的是 `code/ptxsub.py`，一个**逐 warp 推进到阻塞点**的解释器，
>    **不是真实的 warp 交错调度**，更不是硬件。本篇**一个硬件数字都没有**（本机是 Apple M1 Pro，**无 GPU**）。
>    凡本篇给出「声明 8 / 触及 6」这类数，都是在**一段文本**上数出来的，不是在任何芯片上跑出来的。
> 2. **「按 PTX ISA `9.7.10.6` / `9.7.15.1` / `9.7.15.3` 等章节实现」**——引文与章节号逐字保存在
>    `code/specs.py` 的 `ISA` 表里，每条都带章节号；**没有一条引文不带章节号**。
>    ★ 且 `shfl.sync.up` 处**必须写明本库的实现是对 ISA 文本的有意偏离**（本篇 §4.4 与
>    `02-warp-level-execution.md` §4.1：逐字引原文、并列出三种可能）。
> 3. **「手写 PTX 的语法未经过任何工具验证」**——本机**无 `ptxas`**（也无 `nvcc` / `cuobjdump` / `nvdisasm`）。
>    本主题里每一段 PTX 都**只被 `ptxsub` 解释过**；`code/01_virtual_isa.py` 的 `C.7` 用 `ast` 断言
>    **这个程序在结构上没有 spawn 任何进程的能力** —— 所以这不是「我们忘了验证」，是**做不到**。

## 0. 背景与动机

### 0.1 两个具体的对照场景

**场景 A（同一个名字，两种意思）**。你在 PTX 里写下：

```ptx
.reg .b32 %r<8>;
```

然后写 `mov.u32 %r5, %tid.x;`。看起来像「用了第 6 个临时变量」。但 PTX 里这句话的含义只有一条：
**`%r5` 是本文本里 `%r0..%r7` 这 8 个名字之一**。「8」是你**声明**的上限，
不是硬件给你的配额，也不是编译器替你算出来的需求。同一段文本里：

- 可以声明 8 个、只用 4 个（本篇的两个真实片段就是这样）；
- 可以声明 4 个谓词、**一个都不用**（本篇的两个片段都是这样）；
- 一旦引用 `%r8`（第 9 个），这段 PTX 就**非法** —— 而**发现它的时机**取决于谁来读它（§0.2）。

**场景 B（同一段文本，两种读法给出不同的错误时机）**。把非法的 `%r8` 放在一条**永远不会被执行到**的路径上：

```ptx
.reg .b32 %r<8>;
    mov.u32 %r0, %tid.x;
    bra L_END;
    mov.u32 %r8, 7;      // ★ 未声明的 %r8，落在**不可达**分支里
L_END:
    ret;
```

- **真实的 `ptxas`** 在**汇编期**读完整段文本，它在**任何执行发生之前**就会拒绝这段代码；
- **本库的解释器**只能在**执行到那条指令时**才发现 —— 而那条指令**永远不会被执行** ⇒ **它一路潜伏**。

同一个「不可达」位置，换成一条**表外的指令**（例如 `popc.b32`），结论**反过来**：
`validate()` 是**静态**的，它在跑之前就扫完所有指令，**不可达也照样报错**。
**这两种检查的时机不同，是本篇 §4.2 的题材**（程序 `C.2` 与 `C.4` 就是这一对）。

## 1. 原理

### 1.1 PTX 的四条「虚拟」特征，逐条对照 SASS

| # | PTX 的特征 | 与本篇的关系 |
|---|---|---|
| 1 | **寄存器无上限**：`.reg .b32 %r<N>` 是**声明** | 本篇的主线（§1.2 / §2.2） |
| 2 | **指令是类型化的**：`add.u32` / `add.s32` / `add.f32` 是三条不同的指令 | 解释器照实现（`specs.PTX_SUBSET['supported']` 的 46 条里，光是 `setp.*` 就有 12 条） |
| 3 | **地址空间是显式的**：`.global` / `.shared` / `.const` / `.param` | 本子集**只有 `.shared` 一个**（表外清单里 `ld.global.u32` / `ld.param.u32` 两条就是另外两个空间的代表） |
| 4 | **控制流是显式标签 + 谓词** | `02` 篇的题材（`bra` 与 `@%p` 的代价差） |

**这四条在 SASS 上全部消失或被改写**：物理寄存器是有限的、指令的后缀是硬件编码的一部分、
地址空间由指令形式隐含、控制流被重排与谓词化。**VM 与真机的差别集中在这四处**。

### 1.2 ★ 多步推导：为什么「声明量」与「触及量」可以任意不等

**第一步（定义两个量）**。对一段 PTX 文本 $T$：

- **声明量** $D(T)$：`.reg` 行给出的槽位数。`.reg .b32 %r<8>` ⇒ $D_{b32} = 8$。
- **触及量** $U(T)$：出现在指令操作数里的下标集合的基数。本篇的两个片段分别是 $\{1,2,3,4\}$ 与 $\{0,1,2,3,4,5\}$。

**第二步（两个量之间只有一条不等式）**。程序里没有哪一步会去检查 $U \le D$——
**这是文本层的两条独立事实**。它们之间唯一的约束来自「越界引用会报错」：

$$U \subseteq \{0, 1, \ldots, D-1\} \quad\Longleftrightarrow\quad \max U < D$$

⇒ $U \le D$，而**等号可以严格不成立**：

| 片段 | $D_{b32}$ | $U_{b32}$ | $D-U$ | 比值 $D/U$ |
|---|---:|---:|---:|---:|
| `SHFL_BODY`（warp 内 bfly 归约） | 8 | 4 | **4** | **2.0000** |
| `BAR_BODY`（两阶段 + `bar.sync`） | 8 | 6 | **2** | **1.3333** |

两个片段多声明而从未触及的槽共 **6** 个（程序 `B.4`）；谓词侧更极端：`.reg .pred %p<4>` 各 4 个、
**两段里一个都没写**，共 **8** 个（程序 `B.4b`）。

**第三步（为什么这在 PTX 层是「免费」的）**。PTX 是**虚拟** ISA：那 6 + 8 个槽**在文本上存在**，
而它们是否变成 SASS 上的物理寄存器，**由 `ptxas` 决定，不由这段文本决定**。
⇒ 「多声明」在 PTX 层不花任何代价，**它花的是别处的代价**（汇编器的工作量、以及可能的分配压力）——
**而那个代价本库观测不到**（§4.5）。

**第四步（反过来说：错误的方式也不是「用多了」）**。既然 $U \le D$ 是唯一的约束，
那么**越界引用**（$U \not\subseteq \{0,\ldots,D-1\}$）不是「超支」，而是**引用了不存在的名字** ——
它的后果不是变慢，是**这段文本非法**。判别它的时机见 §4.2。

### 1.3 覆盖范围必须是一张**闭合**的表

「本解释器覆盖哪些 PTX 指令」这件事有**三种写法**，只有一种能用：

| 写法 | 为什么不成立 |
|---|---|
| 什么都不写，遇到不认识的指令就跳过 | **静默给出错误答案**（最坏的一种） |
| 在文档里列一张表 | 表会与实现脱节，且**没人能机械判定**它是否完整 |
| **表 + 引擎按表拒绝，且表可从实现导出** | ✅ 本篇采用 |

具体做法（`code/ptxsub.py`）：标量指令与 warp 级指令各登记在**一张分派表**里
（装饰器 `@scalar(...)` / `@warp(...)`），而

```python
SUPPORTED_OPS = frozenset(_SCALAR) | frozenset(_WARP)
```

⇒ 「加了实现却没进表」在结构上**不可能发生**；反方向（「进了表却没实现」）由
程序 `A.1` 做**双向集合相等**断言钉住：

```
ptxsub.SUPPORTED_OPS == set(specs.PTX_SUBSET['supported'])      # 46 条
```

在这条弧线之外**任意一条** PTX 指令都会被 `Sim.validate()` 拒绝（程序 `C.3` 用 `popc.b32` 试了）。
**表外清单（14 条）里的每一条都是真实 PTX** —— `make anchors` 会逐条断言它们出现在刚下载的 ISA 原文里，
**这一条挡的是「凭印象编一个像样的指令名」**（那样的名字在原文里出现 0 次，抽取器会当场报出来）。

## 2. 执行映射

### 2.1 解释器读一段 PTX 的五个阶段

| 阶段 | 做什么 | 本篇的落点 |
|---|---|---|
| ① 解析 | `.reg` 声明 / 标签 / `@%p` 守卫 / `op 操作数, …` | `Program.declared` 在这里产生 |
| ② **校验** | **表外 opcode 一律拒绝**（`Sim.validate()`，**跑之前**） | 程序 `C.3` / `C.4` |
| ③ 分配 | 按**声明量**开寄存器文件（`.reg .b32 %r<8>` ⇒ 8 个槽） | 程序 `B.1` / `B.5` |
| ④ 执行 | 逐 warp 推进到阻塞点；**未声明的寄存器在这里才报错** | 程序 `C.1` / `C.2` |
| ⑤ 记账 | 发射数 / 活跃 lane-指令数 / 发散步数 / 访存轨迹 | `02` 篇 |

**②与④的时机差异是本篇最具体的一条机制**：②是**静态**的（扫完所有指令），
④是**动态**的（只查执行到的那条）。程序 `C.2` 与 `C.4` 是同一个「不可达」位置上的**一对反例**。

### 2.2 真实的 `ptxas` 在这一步做什么（★ 只做描述，本机无法观测）

| 步骤 | 输入 | 输出 | 本库能观测吗 |
|---|---|---|---|
| 汇编 | PTX 文本 | SASS 文本 + cubin | ✗（无 `ptxas`） |
| **寄存器分配** | PTX 的虚拟寄存器 | 每线程 ≤ 255 个**物理**寄存器（放不下就 spill） | ✗（无 `nvdisasm`） |
| **指令调度** | 源码顺序 | 发射顺序（为掩盖延迟而重排） | ✗ |
| 反汇编 | cubin | SASS 文本 | ✗（无 `cuobjdump` / `nvdisasm`） |

**★ 这一栏的四个 ✗ 就是本篇的边界**：本库能算的只有 PTX 层的那两个数（$D$ 与 $U$），
**第三个（物理寄存器数）本库没有观测过，也不从 $D$ 或 $U$ 推**。
`code/01_virtual_isa.py` 的 `B.4c` 把这条写成断言：**表内 46 条 opcode 里没有一条与 SASS 有关**。

### 2.3 参与的对象与量

| 对象 | 本主题里的角色 |
|---|---|
| 一段 PTX 文本 | 唯一的输入。**它本身就是一篇文档**（所以引文与章节号在 `specs.py` 里） |
| `.reg` 声明行 | 决定解释器开多少槽；**与运行期无关** |
| `Program.used_regs()` | 文本层扫出来的触及集合（**词法级**，不是数据流） |
| `Sim.validate()` | 表外 opcode 的**静态**闸门 |
| `_ridx()` | 未声明寄存器的**动态**闸门 |
| **真实的 `ptxas` / `nvdisasm`** | **本机不存在** ⇒ 本篇不产生任何关于它们行为的结论 |

## 4. 踩坑与失败模式

### 4.1 手写 PTX 的语法**从未被任何工具验证过**（★ 本篇的第一条）

- **现象**：本主题里每一段 PTX 都是手写的。本机**没有 `ptxas`**，
  所以这些片段**是否合法**、`%r8` 到底是「未声明的寄存器」还是「合法的第 9 个」，
  **本库没有任何工具可以确认**。
- **成因**：这是**本机的硬约束**，不是疏忽（`nvcc` / `cuobjdump` / `nvdisasm` / `ptxas` / `ncu` 一个都没有）。
- **规避**：把这条写成**结构性断言**而不是免责声明 —— 程序 `C.7` 用 `ast` 断言
  **本篇的程序不导入 `subprocess` / 不调用 `os.system` / `os.popen`**：
  它在结构上**没有能力**调用任何外部工具。⇒ 「未验证」这件事是**可复现地成立**的，不是一句自嘲。
- **★ 这条管着本篇的每一条结论**：本库能说的是「**按 ISA 文档转述实现的语义，在一个明确的近似执行模型上自洽**」，
  **不能**说「验证了 PTX 语义」。

### 4.2 同一个「不可达」位置，两种检查给出相反结论

- **现象**：把非法的 `%r8` 放在 `bra` 跳过的分支里，程序**跑完且不报错**（`C.2`）；
  把一条表外指令放在**同样的位置**，程序**立刻报错**（`C.4`）。
- **成因**：两道闸门的**时机**不同 —— `validate()` 是**静态**的（跑之前扫全部指令），
  `_ridx()` 是**动态**的（只在那条指令被执行到时才查）。真实的 `ptxas` 与二者都不同：
  它在**汇编期**读完整段文本 ⇒ 上面那个 `%r8` **根本编不过去**。
- **规避**：① 不要以为「解释器没报错」等于「这段 PTX 没问题」——
  **不可达路径上的非法引用会一路潜伏**；② 要检查这种错误，只能**静态扫**（`validate()` 就是干这个的），
  动态检查抓不到没跑到的代码。
- **一般化**：这是「**检查的时机**决定了它能抓到什么」这一类错误的实例，
  与语言设计里的「编译期 vs 运行期」是同一件事。

### 4.3 ★★ 转写错误：工具输出是对的，**写进规格时抄错了**

这是本主题**最贵的一次错**，也是本篇必须写下来的原因。

- **现象**：规划阶段用 `curl` 取到了 ISA 一手原文（这是对的），
  抽取脚本打印的是 `maxLane`（**正确**），而**写进规格时被转写成了 `minLane`**；
  于是长出一条「**ISA 用 `minLane`、二手转述是错的**」的叙事，当作「一手原文定案」
  **扩散到三处**、写进记忆、并报告为旗舰发现。
- **成因**：**转写是独立的出错环节**。工具输出不是结论；把输出搬到一个新位置时，
  它重新变成了一段「凭印象写的文本」。
  ★ 而且这个错**长得像一个更权威的结论**：它借用了「一手来源更可信」这个**真命题**。
- **规避（三条，全部是机械的）**：
  1. **凡引用外部原文，把原文与断言写在同一个地方**（`specs.ISA[k]['quote']` 与它的 `must_contain` 在一起）；
  2. **在原始字节上做计数**（`raw.count('j &gt;= maxLane')`），**不要先转成文本再数** ——
     转写层是最容易出错又最难自查的一层；
  3. **凡「我读了 X 所以我对」的句式，都是高风险信号。**
- **★ 本篇把它落成了断言**：`A.4b` 断言 `raw.count('j &gt;= maxLane') == 2`、
  `A.4c` 断言 `raw.count('j &gt;= minLane') == 0`、
  `A.4d`–`A.4g` 断言**两节引文各自**的内部计数。
  把引文里的 `maxLane` 改成 `minLane`，`make run` 立刻失败 —— 这是**可复现**的。

### 4.4 反面教训：`.up` 的判据【未定案】，**不得写成已定案**

- **现象**：ISA 原文（`9.7.10.6`）的 `.up` 分支写 `pval = (j >= maxLane)`，
  而本库的实现取的是 `minLane`（§4.3 的教训**不是**这一条，两者是两件事：
  前者是**实现选择**，后者是**转写错误**）。
- **成因**：按 `maxLane` 那式，`.up` 在常见参数下会**退化**；
  而 ISA 自己的例子（`shfl.sync.up.b32 Ry|p, Rx, 0x1, 0x0, 0xffffffff`）**`cval = 0x0`**，
  此时 `maxLane == minLane`，**两式恰好重合** ⇒ 那个例子无法区分两者。
- **规避**：**写清「未定案」并列出三种可能**（`02-warp-level-execution.md` §4.1 逐字引原文）。
  **不得写「规范规定 `minLane`」「二手转述是错的」「已定案」** —— 那是**伪造引文**。
- **为什么值得单列**：它是「**取到了一手原文 ≠ 读对了一手原文**」的实例，
  而**具体的失败形态是：错的那一方长得更像权威结论**。

### 4.5 ★ 那个「别处」在哪里

本域主线说：**抽象层的价值与它的泄漏是同一件事的两面**。那么本篇的代价被藏到了哪里？

> **它被藏进了「汇编期」这一步。**
>
> PTX 文本里寄存器是**无限**的（`.reg` 只是声明）；SASS 里每线程最多 **255** 个物理寄存器。
> 这个转换发生在 `ptxas` 里，而它**不在你的源码里、也不在 profiler 的默认视图里**。
> 你在 PTX 层看到的「声明 8 个」与「触及 6 个」**都不等于**它最后分配了多少个 ——
> **两个可见的数都不能推出那个不可见的数**，而那个不可见的数直接决定占用率与 spill。
>
> **这就是那个「别处」**：本篇的两个量（$D$ 与 $U$）是**同一段文本的两个侧面**，
> 它们**都便宜**（数一数就有），所以人很容易以为「我已经知道寄存器用得怎么样了」。
> 真正贵的那一步（**活跃区间分析 + 分配**）需要**数据流**，而不是词法扫描 ——
> 它被整个让渡给了 `ptxas`，而 `ptxas` **不在本机上**。

同一条主线的第二种形态也在本篇里：**检查的时机**（§4.2）。
「未声明的寄存器」这件事在 PTX 规范里是**汇编期**的错误，在本库是**运行期**的错误，
而在**不可达代码**上两者给出相反的结论。⇒ 同一个抽象（「这段文本合法吗」）
在不同工具里有不同的**边界**，而**语言层的写法完全相同**。

本篇不越过这条线（本机没有 `nvdisasm`），但把它**标出来**：这是 `03-memory-and-sass-gap` §3 的入口。

## 6. 小结与延伸

- ★★ **声明量 ≠ 触及量**：`.reg .b32 %r<8>` 声明 8、触及 6（比值 **1.3333**）与 8、触及 4（比值 **2.0**）；
  `.reg .pred %p<4>` 声明 4、**触及 0**（两个片段合计 8 个从未被写的谓词槽）。
  **多声明在 PTX 层是免费的**，而「省寄存器」唯一的手段是少声明。
- ★★ **PTX 的寄存器数与硬件上的物理寄存器数没有关系** —— 但本库只主张**两个量**（都来自文本）；
  **第三个量本机没有观测过**（无 `nvdisasm`）。这条限定语是本篇最容易被越界引用的地方。
- ★ **检查的时机决定它能抓到什么**：表外 opcode 是**静态**拒绝（不可达也报错），
  未声明寄存器是**动态**报错（不可达就潜伏）。真实的 `ptxas` 在**汇编期**拒绝两者 ——
  **本解释器没有汇编期**。
- ★ **手写的 PTX 语法从未被任何工具验证过**，而这一点是**结构性成立**的
  （程序 `C.7` 断言它没有 spawn 能力），不是免责声明。
- ★★ **转写是最容易出错又最难自查的一层**：本主题的规划阶段把抽取脚本输出的 `maxLane`
  抄成了 `minLane`，并据此指控二手来源错误。`specs.RAW_COUNTS` + `A.4` + `make anchors`
  是这条教训的**机械载体**（改错它，`make run` 立刻失败）。
- ★ **表要闭合**：46 条表内 opcode 由**分派表导出**（不是手抄的第二份清单），
  14 条表外 opcode **全是真实 PTX**（在线逐条核对出现在 ISA 原文里），**遇到即拒绝**。
- ★ **残余（如实列出）**：① `ISA[*].slice` / `locate` 两个字段**只在 `make anchors` 里被消费** ——
  离线时 `make mutate` 会如实把它们报成**漏网**；② `A.3e` 的范围**只到 `ISA[*]`**，
  另外四个顶层条目（`RAW_COUNTS` / `UP_MODE_UNDECIDED` / `PTX_SUBSET` / `BANK_CONFLICT`）不受它管。

**延伸**：

- warp 级执行的代价（`bra` 与 `@%p` 的差、`shfl.sync` 的 clamp、`bar.sync` 的 warp 粒度）：
  `30-gpu-programming/ptx-sass/02-warp-level-execution`。
- 共享内存访存计数与 PTX → SASS 的两大落差：`30-gpu-programming/ptx-sass/03-memory-and-sass-gap`。
- SIMT 与发散的硬件原理（本篇不重复推导）：`20-gpu-architecture/execution-model/02-simt-and-divergence`。
- 「先有独立参照再谈验证」的方法论：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- 另一个域里「先跑再写」的正例（静态检查器与真实文件的成对判据）：`30-gpu-programming/cuda/01-thread-hierarchy-and-sync`。
