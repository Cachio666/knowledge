# 共享内存访存计数与 PTX→SASS 的落差

> **同一个 `+1` padding，在一份代码里有效、在另一份里完全无效 —— 而两份都是「按列取用」。**
> 本篇用自己写的 PTX 子集解释器（`code/ptxsub.py`）从 `ld.shared` 的**实际字节地址**上数 bank 冲突，
> 给出本域**最值钱的一条反直觉量化结论**：
>
> | 行距 | **模式 A**：warp 跨 8 行 × 4 列（R = 8） | **模式 B**：warp 跨 32 行 × 1 列（R = 32） |
> |---|---:|---:|
> | 8（无 padding） | 2 路 | 8 路 |
> | **9（+1 padding）** | **2 路 ← 无效** | **1 路 ← 有效** |
> | **12** | **1 路 ← 有效** | 4 路 |
> | 32 | 8 路 | **32 路** |
> | 33（+1 padding） | 4 路 | 1 路 |
>
> 1. ★★ **`+1` padding 在模式 A 下完全无效**（行距 8 → 9，冲突仍是 **2 路**）——
>    机制是：9 与 32 互质，但**四个列合起来只覆盖 29/32 个 bank**
>    （bank `{0,1,2}` 被两个列同时用到、且是**不同 word**），同时 bank 8/17/26 空着。
>    行距 **12** 才是模式 A 下的解（**恰好铺满 32/32**、零重叠 ⇒ 1 路）。
> 2. ★★ **冲突路数被「warp 跨的行数 R」封顶**：模式 A 的 R = 8 ⇒ 行距 32 时只有 **8 路**
>    （**不是 32 路**）；而同一个行距 32 在模式 B 下是 **32 路** —— **同 stride、同 tile，差 4 倍**。
> 3. ★★ **「列访问」不是一个良定义的词**：它的冲突路数**取决于 lane 模式**。
>    本库把两种模式的定义连同数字一起写（P9），并断言**换一个模式数字就变**。
> 4. ★ **既有文档（`20-gpu-architecture/memory-system/03`）的 `gcd(行距, 32)` 规则是模式 B 的特例**，
>    本篇**穷举行距 1..64 复核了它**（**闭式** vs **解释器地址**，两条独立路径）。
>    ⇒ **本篇不是对它的订正**（它第 358 行自己已声明前提「一个 warp 恰好铺满 tile 的一整行」= 模式 B）。

> ★ **本域的三条强制限定语，在本篇的落点**（域 README 规定逐篇写明，不得省略）：
>
> 1. **「不是硬件」**——冲突路数是**本解释器**从其 `ld.shared` 的**字节地址轨迹**上算出来的模型值
>    （32 个 bank × 4 字节；同一 word 是广播、不算冲突）。真实硬件上还有 **32-bit / 64-bit / 128-bit
>    访问的不同判定池**、以及跨请求的合并（`20-gpu-architecture/memory-system/03` §2 末三条讲的就是这个）。
>    本篇**一个硬件数字都没有**（本机 **无 GPU**）。
> 2. **「按 PTX ISA `9.7.10.6` 等章节实现」**——本篇用到的访存口径
>    （`bank = (字节地址 ÷ 4) mod 32`、同 word 是广播）来自**既有篇章**
>    `20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`，**回链不复述**；
>    ISA 引文与章节号保存在 `code/specs.py` 的 `ISA` 表。
>    ★ `shfl.sync.up` 的有意偏离与「未定案」状态见 `02-warp-level-execution.md` §4.1
>    （本篇不用到 `.up`）。
> 3. **「手写 PTX 的语法未经过任何工具验证」**——本机**无 `ptxas`**（也无 `nvcc` / `cuobjdump` / `nvdisasm`）。
>    §3 讲 PTX → SASS 的两大落差时**只做描述性介绍**，本库**一个 SASS 数字都没有**。

## 0. 背景与动机

### 0.1 两个具体的对照场景

**场景 A（同一个 `+1` padding，两种命运）**。你有一个 32×32 的 fp32 共享内存 tile，
想让一个 warp 的 32 个 lane「按列取用」其中的 9 个元素。怎么把 32 个 lane 映射到 tile 上？
至少有两种自然写法：

```ptx
// 模式 A：lane t 读 tile[t % 8][t // 8]  ⇒ 一个 warp 横跨 **8 行 × 4 列**
    and.b32  %r1, %r0, 7;              // row = t % 8
    mul.lo.u32 %r1, %r1, %r6;          // row * stride
    shr.u32  %r2, %r0, 3;              // col = t // 8
    add.u32  %r1, %r1, %r2;
```

```ptx
// 模式 B：lane t 读 tile[t % 32][t // 32]  ⇒ 一个 warp 横跨 **32 行 × 1 列**
    and.b32  %r1, %r0, 31;             // row = t % 32
    mul.lo.u32 %r1, %r1, %r6;
    shr.u32  %r2, %r0, 5;              // col = t // 32
    add.u32  %r1, %r1, %r2;
```

**两段都是「按列取用」，两段只差两条指令的立即数。** 给 tile 加一个 `+1` padding（行距 8 → 9）：

- **模式 B：8 路 → 1 路**（教科书式的胜利）；
- **模式 A：2 路 → 2 路**（**完全无效**）。

而模式 A 真正的解是行距 **12**（1 路）—— **不是 9**。

**场景 B（同一句话，两个数）**。同一段源码里写「按列取用时给行距加 1 就能消除 bank 冲突」，
在模式 A 与模式 B 下**一真一假**。⇒ 「列访问」这个词**必须连同 lane 模式一起定义**（§2.2）。

### 0.2 本篇覆盖什么、不覆盖什么

本篇落在 `code/03_smem_and_sass.py` 的 **28 条断言**里（A 7 / B 10 / C 11）：

| 组 | 内容 | 数量 |
|---|---|---|
| **A** | 三条**互不重叠**的冲突计数路径（解释器地址 + 字典统计 / numpy 分箱 / 纯 Python 闭式）、**模式 B == `gcd(行距, 32)`** 的穷举复核、既有文档规则的**作用域** | 7 |
| **B** | 两张表的逐格断言、模式 A 的覆盖数（29/32 与 32/32）、R 封顶、广播不算冲突 | 10 |
| **C** | `+1` padding 在两个模式下的相反结论、模式定义是数字的一部分、R 封顶的反例、既有规则的作用域是**可算的** | 11 |

**边界**：bank 冲突的**机制**（为什么是 32 个 bank、广播为什么免费、64 位访问为什么换一套判定池）

合并访存（global memory 的 128 字节事务）在该域的 `02-coalescing-and-cache-line`；

### 0.3 统一主线：那个「别处」在哪里

本域主线是「**你写的程序、编译器生成的东西、硬件执行的东西，是三个不同的程序**」。
本篇的两半各守这条主线的一次穿越：

> **前半（§1–§2）**：你在 PTX 里写「按列取用」，**但硬件看到的是 32 个字节地址**。
> 中间隔着一个你没写下来、却决定一切的东西：**lane 模式**。
> **后半（§3）**：你数出来的那几个冲突路数，**到了 SASS 层还会变** ——
> `ptxas` 会重排、会合并、会把 `ld.shared` 拆开或并起来，而**它看到的东西比 PTX 文本多**
> （它知道寄存器压力、知道后续有没有再用这个值）。

代价被藏到了哪里？

> **它被藏进了「同一个地址序列由谁产生」这个问题里。**
> `03` 篇的两张表的每一个数，都是从**字节地址**上算出来的；而**产生这些地址的是 lane 模式**，
> 不是那条 `ld.shared` 指令本身。⇒ 「这条 load 几路冲突」在没有 lane 模式时**不是一个问题**。
> 再往后一步，那个「别处」就是**寄存器分配与指令调度**（§3）：
> 你在 PTX 层数的访存次数，到了 SASS 层可能被消除（值还在寄存器里）、
> 也可能被拆开（为了掩盖延迟）——**两层之间没有一一对应**。

## 1. 原理

### 1.1 从字节地址到 bank：本篇的口径，逐字来自既有篇章（回链，不重推）

本篇用到的两条口径（**定义**在 `20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`）：

1. **`bank = (字节地址 ÷ 4) mod 32`**（32 个 bank、每个 4 字节宽）；
2. **同一个 bank 上落在同一个 word 的多个访问是广播，只算 1 路**；
   **落在同一个 bank 的多个不同 word 才算冲突**，路数取最大值。

⇒ 本库的候选实现只有一条：

```python
banks.setdefault(word % nbank, set()).add(word)   # ★ set：同一 word 去重（广播）
return max(len(v) for v in banks.values())
```

★ **判据必须能在两条独立路径上得到同一个数**（否则就是 P12：被测对象与参照是同一段代码）。
本篇的三条路径（程序 `A.1`–`A.3`，在**2 个模式 × 33 个行距 = 66 格**上逐格比对）：

| 路径 | 做什么 | 与其它路径的区别 |
|---|---|---|
| ① **被测口径** | 跑解释器，从 `sim.ld_shared_trace` 里取**真实的字节地址**，再用字典统计 | 地址来自**执行**，不是公式 |
| ② numpy 分箱 | `words = addr // 4`；`bank = words % 32`；逐 bank 数 `np.unique` 的个数 | 统计实现完全不同 |
| ③ **纯 Python 闭式** | 按模式定义算 `flat = row × stride + col`，**完全不看地址**、不用 numpy | 连「地址」这一步都没有 |

★ 一条硬纪律：**地址必须从解释器的访存轨迹里取**，不能另算一遍公式 ——
否则路径①与路径③就变成了同一段代码（P12 的教科书形态）。

### 1.2 ★ 多步推导：为什么模式 B 的冲突路数恰好是 `gcd(行距, 32)`

**第一步（模式 B 的地址序列）**。模式 B 里 lane $t$ 读 `(row, col) = (t % 32, t // 32) = (t, 0)`
⇒

$$\text{flat}(t) = t \cdot s + 0 = t\,s \qquad (t = 0,\ldots,31)$$

其中 $s$ 是行距（以 word 计）。

**第二步（bank 序列）**。$\text{bank}(t) = (t\,s) \bmod 32$。
映射 $t \mapsto t s \bmod 32$ 的**像集**是一个子群，其大小是

$$\left|\{\,t s \bmod 32 \,\right| t \in \mathbb{Z}_{32}\}| = \frac{32}{\gcd(s, 32)}$$

（$\mathbb{Z}_{32}$ 上「乘 $s$」的像就是由 $s$ 生成的子群，阶为 $32/\gcd(s,32)$。）

**第三步（每个 bank 上几个 lane）**。32 个 lane 均摊到 $32/\gcd(s,32)$ 个 bank 上 ⇒ 每个 bank 有

$$\frac{32}{32/\gcd(s,32)} = \gcd(s, 32)$$

个 lane，而它们的 $\text{flat}$ **两两不同**（因为 $t$ 不同、$s \neq 0$ ⇒ $ts$ 不同）
⇒ 落在**同一个 bank 的不同 word** 上 ⇒ **每个 bank 的冲突路数就是 $\gcd(s,32)$**，
最大值也就是它。**证毕**：

$$\boxed{\text{bank 冲突路数（模式 B）} = \gcd(\text{行距}, 32)}$$

**第四步（这就是既有文档的那条规则）**。程序 `A.4` **穷举行距 1..64**，用解释器的**实际地址**
复核了这条闭式（与 §1.1 的路径③独立）。而程序 `A.4c` 同时断言
`specs.BANK_CONFLICT['existing_doc_rule_scope'] == 'B'` ——
**那条规则只在模式 B 下成立**（模式 A 下行距 8..40 里 **25/33 个**不成立，见程序 `C.6`）。

**第五步（为什么模式 A 完全不是这个形状）**。模式 A 里 warp **只跨 8 行**，
于是一趟里最多只有 **8 个 lane** 落在同一列 ⇒ **冲突路数被 8 封顶**（程序 `B.5` 穷举验证）。
这不是「9 和 32 互不互质」的问题，而是**分母变了**：

$$\text{模式 A 的冲突路数} \le R = 8 \quad\text{（warp 跨的行数）}$$

**★ 这就是本篇与既有文档的关系**：既有文档的规则**正确、且已经写明前提**；
本篇给出的是**前提被放掉之后**（warp 跨多行）的形态。
**不是订正**（`CONTRIBUTING` 第 56 行：不要在不构成冲突的地方硬造冲突）。

### 1.3 为什么 `+1` padding 在模式 A 下无效：数 bank 的覆盖面

模式 A 的四个列（$c = 0,1,2,3$）各自的 bank 集合是

$$B_c = \{\, (r s + c) \bmod 32 \;:\; r = 0,\ldots,7 \,\}$$

对 $s = 9$：

| 列 | 覆盖的 bank |
|---|---|
| $c=0$ | {0, 9, 18, 27, 4, 13, 22, 31} |
| $c=1$ | {1, 10, 19, 28, 5, 14, 23, **0**} |
| $c=2$ | {2, 11, 20, 29, 6, 15, 24, **1**} |
| $c=3$ | {3, 12, 21, 30, 7, 16, 25, **2**} |

四个集合的并**只有 29 个 bank**（程序 `B.3` 钉住这个数）：
bank **{0,1,2}** 被两个列同时用到，**而且是不同的 word**（第 8 行那组的 31/32/33 与第 0 行的 0/1/2）
⇒ 这三处**恰好 2 路**，于是最大值仍是 **2**。同时 bank **8 / 17 / 26** 空着。

对 $s = 12$：

$$B_c = \{\, (12r + c) \bmod 32 \,\} = \{\, 4\cdot(3r) + c \,\}$$

$3r \bmod 8$ 遍历 $\{0,\ldots,7\}$ ⇒ $12r \bmod 32$ 遍历 $\{0,4,8,\ldots,28\}$，
再加上 $c \in \{0,1,2,3\}$ ⇒ **四个列恰好铺满 32/32、零重叠**（程序 `B.4`）⇒ **1 路**。

★ **一般规律**：模式 A 下要无冲突，需要 8 个行首 bank $\{rs \bmod 32\}$ **两两间隔 ≥ 4**
（这样四个连续列才不会重叠）。程序 `B.5b` 的对照给出了另一端：模式 B 能到 **32 路**
——**同一个 R 封顶机制的两端**。

## 2. 执行映射

### 2.1 两张表（本篇的核心数据）

**模式定义**（★ 必须连同数字一起给出，否则没有意义）：

- **模式 A**：lane $t$ 读 `(row = t % 8, col = t // 8)` ⇒ warp 覆盖 **R = 8 行 × 4 列**；
- **模式 B**：lane $t$ 读 `(row = t % 32, col = t // 32)` ⇒ warp 覆盖 **R = 32 行 × 1 列**。

| 行距（word） | 模式 A（R = 8） | 模式 B（R = 32） | 说明 |
|---|---:|---:|---|
| 8 | 2 路 | 8 路 | 无 padding |
| **9** | **2 路** | **1 路** | ★ `+1` padding：**A 无效、B 有效** |
| **12** | **1 路** | 4 路 | ★ 行距 12：**A 的解** |
| 32 | 8 路 | **32 路** | ★ 同 stride 差 **4 倍**（R 封顶） |
| 33 | 4 路 | 1 路 | `+1`（再 +1）：A 反而**升到** 4 路 |

**参与的对象与量**：

| 对象 | 本模型里的角色 |
|---|---|
| `ld.shared.u32` 的**字节地址** | 唯一的输入（从解释器的访存轨迹里取） |
| 32 个 bank × 4 字节 | 判定池（回链 `memory-system/03`） |
| **同一 word 的多个 lane** | **广播**，只算 1 路 |
| **lane 模式（R）** | **决定地址序列** ⇒ 决定一切（P9） |
| 行距（stride） | 决定同一列相邻行落在哪些 bank 上 |
| **真实硬件的判定池（32/64/128 位）** | **本模型没有**它们（§4.3） |

### 2.2 「列访问」为什么不是一个良定义的词

| 说法 | 缺了什么 | 后果 |
|---|---|---|
| 「按列取用会 bank 冲突」 | **lane 模式** | 模式 A 下 2 路、模式 B 下 8 路（行距 8）——**两个数** |
| 「加 1 个 padding 就消除冲突」 | **lane 模式** | 模式 B 下 8→1；模式 A 下 2→2（**假**） |
| 「行距与 32 互质 ⇒ 无冲突」 | **R** | 模式 A 下 $s=9$ 与 32 互质，仍 **2 路** |

程序 `C.3` 把这件事做成可判定的：**五个行距全部**两种模式给出**不同的**路数
（2 vs 8、2 vs 1、1 vs 4、8 vs 32、4 vs 1），并断言两个模式产生的**字节地址集合并不相同** ——
⇒ 差别不在「怎么数」，在「**读的是哪些地址**」。

### 2.3 PTX 层与 SASS 层不是一一对应（★ 只做描述，本机无 `nvdisasm`）

| 层 | 谁决定访存次数 | 本库能观测吗 |
|---|---|---|
| PTX | 你写的 `ld.shared` 的**条数**（含循环里重复执行的那些） | ✅ 手写片段 + `ptxsub` |
| **SASS** | `ptxas` 会**消除**冗余 load（值还在寄存器里）、**拆分**长延迟 load、**重排**顺序 | ✗（无 `ptxas` / `nvdisasm`） |
| 硬件 | 每个请求在 bank 阵列上的实际遍数（含 64/128 位访问的判定池变化） | ✗（无 GPU） |

⇒ **本篇的两张表的作用域到此为止**：它们是**PTX 层的字节地址序列**上的结论。
`ptxas` 完全可以把那几个 load 合并或拆开 —— **那一步本库看不到**。

## 3. 实现与演进：PTX → SASS 的两大落差（★ 描述性）

这一节**只做描述性介绍**，本机**没有 `nvdisasm`**，所以**没有一条 SASS 数字**。

### 3.1 落差一：寄存器分配（虚拟寄存器 → 有限的物理寄存器）

PTX 的寄存器是**声明的**（`01-ptx-as-virtual-isa` 的反直觉量化结论），
而 SASS 的物理寄存器是**有限的**：每线程最多 **255** 个。于是 `ptxas` 必须做分配：

| 步骤 | 发生什么 | 本库能观测吗 |
|---|---|---|
| 活跃区间分析 | 从 PTX 的 liveness 算出哪些虚拟寄存器同时活着 | ✗ |
| 分配 | 把虚拟寄存器映射到物理寄存器 | ✗ |
| **spill** | 放不下的写回 **local memory**（本质是 global 内存，**带缓存行**） | ✗ |

★ **本库能算的两个量（PTX 声明量 $D$ 与触及量 $U$）都不能推出这个数** ——
$D$ 是文本上的上限，$U$ 是词法上的触及集合，而分配取决于**活跃区间**（一个数据流概念）。
⇒ **本篇与 `01` 篇都在同一条边界上停住**：再往前一步就需要 `nvdisasm` 或 profiler。

### 3.2 落差二：指令调度（源码顺序 → 发射顺序）

| 现象 | 为什么 | 对「数数」的影响 |
|---|---|---|
| 指令被**重排** | 为掩盖访存/算术延迟，编译器把独立指令插到等待间隙里 | PTX 层相邻的两条 load 在 SASS 里可能相距很远 |
| 一条 PTX 指令**变成多条** SASS | 例如 64 位访存被拆成两条 32 位 | **发射数不可跨层比较** |
| 多条 PTX 指令**变成一条** | 常见于地址计算被折叠进访存指令的偏移字段 | 同上 |
| 冗余 load 被**消除** | 值还在寄存器里、且编译器能证明无别名 | PTX 层数出来的访存次数**偏多** |

⇒ **「PTX 层数出来的发射数 ≠ SASS 层的发射数」**（`02-warp-level-execution` §2.3 是同一个断层
在控制流上的形态）。本库因此**从不把 PTX 层的计数说成 SASS 层的计数**。

### 3.3 演进：从「两张表」到「可判定的作用域」

| 版本 | 做法 | 被什么逼着改 |
|---|---|---|
| 探针 | 只做**模式 A** 一种 lane 模式（tile 8×8、`COL` 模式） | 缺模式 B ⇒ 无法解释「为什么 `+1` 有时有效」 |
| 探针 v2 | 加穷举行距，发现无冲突的行距是 **12/20/28/36** | 得到「模式 A 的解不是 9」这个事实，但**没有机制** |
| **本篇** | ① **两种模式并列**（§2.1 的表）；② **机制**（R 封顶 + bank 覆盖面 29/32）；③ **既有文档规则的穷举复核**（`A.4`，闭式 vs 解释器）；④ **作用域写成常量**（`existing_doc_rule_scope = 'B'`）并让程序断言它 | 「不是订正」这句话如果只写在正文里就**不可证伪**；写成常量 + 断言之后，**改一下就失败** |

## 4. 踩坑与失败模式

### 4.1 ★ 执行模型是**近似的**：「缺 `bar.sync` 错 32 个元素」是本模型的产物

- **现象**：本主题的程序里有几条结论（`02` 篇的「错 32/64」）是**本解释器**跑出来的。
- **成因**：`ptxsub` **逐 warp 推进到阻塞点** —— 一个 warp 一路跑到 `ret` / 阻塞 / 结束，
  才轮到下一个 warp。**真实 SM 上多个 warp 是指令级交错的**，所以「warp0 必然先跑完」
  是**这个模型的性质**，不是硬件的性质。
- **规避**：凡引用这类数字，**必须带限定语**：「这是本模型在『逐 warp 推进到阻塞点』
  这个调度假设下的产物，**不是硬件上的必然**」。
  本篇与 `02` 篇的每一条此类结论都带这句（`02` 篇 §4.2 的星号段）。
- **★ 这一条与 P12 的关系**：模型的结论只能支撑**关于机制的结论**，不能支撑关于真实系统的结论。

### 4.2 ★ UB 情形**没有复现**，只是**报错**

- **现象**：`shfl.sync` 的源 lane 不在 `membermask` 内、在发散控制流里 shfl、`bar.sync` 不收敛地执行
  —— 这些 ISA 都只说 **undefined**。本库的做法是**抛 `PTXError`**。
- **成因**：UB 的定义就是「没有定义」，**无法复现**（复现出来的是某一个实现的某一次行为）。
- **规避**：**不得**把「本库报错」写成「本库复现了 UB」。
  `specs.ISA['P4']` 的引文只说 undefined；程序 `C.6`（在 `01` 篇）断言的也只是**报错**这件事。
- **★ 残余**：本库**不检查** `bar.sync` 的收敛性要求（IA 原文要求「in convergence」）——
  一个发散地执行的 `bar.sync` 在本模型里照样放行（`02` 篇 `B.6` 的例子正是这样）。

### 4.3 ★ 「同一 word 是广播」这条口径**换一个访问宽度就不成立**

- **现象**：你会很自然地把本库算出来的「N 路冲突」当成硬件会报的那个数。
- **成因**：本库的口径是 **32 位访问**下的
  （`bank = (字节地址 ÷ 4) mod 32`、同一 word 去重）。
  真实硬件上 **64 位访问被拆成两个 half-warp**（判定池从 32 个 lane 缩到 16 个），
  宽访问的最小遍数也被抬高 —— **那是另一套记账口径**。
- **规避**：引用本库的数字时**必须写明「32 位访问、4 字节 word」**；
  机制与另外两套口径（64/128 位）在 `20-gpu-architecture/memory-system/03` §2 末三条，**回链不复述**。
- **一般化**：这是「**记账口径的变化被读成了代价的变化**」这一类错误的实例（该篇 §4.3 讲过同款）。

### 4.4 ★ 那个「别处」在哪里

本域主线说：**抽象层的价值与它的泄漏是同一件事的两面**。本篇的代价被藏到了哪里？

> **它被藏在两次「你以为你在数同一个东西」里。**
>
> **第一次**：你在 PTX 里写「按列取用」，以为在描述一种访存；而硬件看到的是 32 个字节地址，
> 那些地址由**你没写下来的 lane 模式**产生。⇒ 「几路冲突」在没有 lane 模式时**不是问题**，
> 而 `+1` padding 这条「经验」正是在这个缺口里失效的（§1.3）。
>
> **第二次**：你在 PTX 层数出「这一趟有 2 路冲突」，以为在描述硬件的代价；
> 而 `ptxas` 会把那些 `ld.shared` **重排、拆分或消除**（§3.2），
> 它比 PTX 文本多知道两件事：**寄存器压力**与**后续还有没有人用这个值**。
> ⇒ 本库数的那个数**不能跨层引用**，而**它恰好是你能在本机数出来的唯一的数**。
>
> 那个「别处」就是**两次让渡**：一次把「地址怎么产生」让渡给了 lane 模式（你在源码里能写对），
> 一次把「访存做几次」让渡给了 `ptxas`（你**看不到**）。前半篇讲第一次，后半篇讲第二次。

## 6. 小结与延伸

- ★★ **同一个 `+1` padding 在两种 lane 模式下结论相反**：模式 B **8 → 1 路**（有效），
  模式 A **2 → 2 路**（**无效**）；模式 A 真正的解是行距 **12**（1 路）。**这是本域最值钱的一条。**
- ★★ **机制是两层**：① 冲突路数**被 R 封顶**（模式 A 的 R = 8 ⇒ 行距 32 时只有 8 路，不是 32 路）；
  ② 行距 9 下四个列合起来**只覆盖 29/32 个 bank**，重复的正是 `{0,1,2}`（不同 word）⇒ 仍 2 路。
- ★★ **「列访问」必须连同 lane 模式一起定义**（P9）：五个行距**全部**两模式给出不同的数，
  而两者产生的**字节地址集合**根本不同。
- ★ **既有文档的 `gcd(行距, 32)` 规则是模式 B 的特例**，本篇**穷举行距 1..64 复核了它**
  （闭式 vs 解释器地址，两条独立路径）⇒ **本篇不是订正**，是把规则推广到「warp 跨多行」的情形。
- ★ **PTX → SASS 的两大落差**：**寄存器分配**（虚拟 → 有限 + spill）与**指令调度**
  （源码顺序 → 发射顺序）。本库**只能描述**它们，**一个 SASS 数字都没有**（无 `nvdisasm`）。
- ★ **残余（如实列出）**：① 本库的口径是 **32 位访问 / 4 字节 word**，64/128 位是另一套判定池；
  ② UB 情形**只报错、不复现**；③ `bar.sync` 的收敛性要求本模型**不检查**。

**延伸**：

- bank 冲突的**机制**（32 个 bank、广播、64 位访问的判定池、padding 的容量代价）：
  `20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`（**本篇只回链，不重推**）。
- 合并访存与缓存行（global memory 一侧）：`20-gpu-architecture/memory-system/02-coalescing-and-cache-line`。
- 分块矩阵乘怎么用共享内存 tiling（本篇不讲算子）：`40-kernels/gemm/02-shared-memory-tiling`。
- PTX 的虚拟性与寄存器声明（本篇的前一篇）：`30-gpu-programming/ptx-sass/01-ptx-as-virtual-isa`。
- warp 级执行的代价（`bra` 与 `@%p`、`shfl.sync`、`bar.sync`）：`30-gpu-programming/ptx-sass/02-warp-level-execution`。
- 「先有独立参照再谈验证」的方法论：`45-kernel-lifecycle/implementation/02-verification-matrix`。
