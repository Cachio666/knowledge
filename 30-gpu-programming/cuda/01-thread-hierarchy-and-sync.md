# 线程层次与同步契约：编译器一条都不查

> **你写的线程组织要满足的约束，编译器一条都不查，运行时不报错，结果还可能是对的。** 本篇把这一类约束做成一个**静态检查器**（`code/01_sync_contract.py`），用**真实的成对文件**当判据，并给出四条带数字的结论：
>
> 1. ★★ **`blocks = (N + (threads - 1) / threads)` 在 C 的整型除法下退化成 `blocks = N`。** `N = 500000`、`threads = 512` 时它得到 **500000**，而正确值是 **977**。线程槽从 `977 × 512 = 500224` 涨到 `500000 × 512 = 256000000`——**超发 512.0 倍（线程口径）/ 511.77 倍（block 口径）**。**同一行表达式在 `cuda-training-series` 的 7 个文件里逐字相同，包括两份「参考解」。**
> 2. ★★ **结果仍然正确，只因为 kernel 里有 `if (idx < N)` 守卫。** 通过守卫的线程只占发射总数的 **0.1953%**。⇒ 「结果对」与「代价对」是**两件独立的事**，而这行代码把两者的距离拉到了 512 倍。
> 3. ★ **`max` 归约的幺元不是 0。** `cuda-training-series` hw5 的 **max 参考解**第 23 行写着 `sdata[tid] = 0.0f;`——与同一份材料的 **sum 版**逐字相同。对全负数输入它会返回 `0.0f` 而不是最大负数；它自带的测试数据**全为正**，掩盖了这一点。
> 4. ★ **同一个发散分支里的 `__syncthreads()`，在 Pascal 及更早的架构上可能侥幸不死锁，在 Volta 及以后必然死锁。** 出处逐字见 §2.1——这不是「一般会挂」，而是一个**有架构分界的机制**。
>
> 本篇的检查器**不是**完整的数据流分析（§4.7 写明它读不到什么），它的真值来源是**外部工件**：`cuda-training-series` 里**成对的「已知有问题 vs 已知参考解」文件**，加上指南的两条原文。

> ★ **本域的三条限定语，在本篇的落点**（域 README 规定逐篇写明，不得省略）：
> 1. **「不是硬件」**——本程序**不执行任何 CUDA**，也不执行任何 kernel。它读的是**文本**、产出的是**文本的结论**：一个 kernel 在硬件上会不会真的挂起 / 算错 / 慢下来，本仓库**一概没有验证**，也不声称。凡程序说「会」的地方，请读作「按 `<出处>` 的规定会」。
> 2. **「分层输出只能读作『允许并发』，不能读作『实际并发』」**——本篇**没有**分层输出（那是 `02-streams-and-events` 的依赖 DAG 模型的事），所以这一条在本篇**自动成立、无可主张**。但同源的结论在这里也成立：`code/01_sync_contract.py` 的 B 组算出「发射了 256000000 个线程槽」，**它不能推出任何关于这些线程槽在硬件上如何重叠的结论**——本机无 GPU。
> 3. **「所有时间数字本机不可得」**——hw13 的 7 个文件里没有任何计时；`cuda-training-series` hw10 的 readme 第 70 行有「about 2X faster」、hw13 README 第 74 行有「a small preformance increase」，**两个都没有倍数、都没有验证**，也不出现在本篇的任何结论里。

## 0. 背景与动机

### 0.1 两个具体的对照场景

**场景 A（代价错，结果对）**。`cuda-training-series` 的 hw13 里，`axpy` kernel 的启动配置是：

```c
#define N 500000                         // 第 21 行
...
int threads = 512;                       // 第 104 行
int blocks = (N + (threads - 1) / threads);   // 第 105 行
```

这段代码**能编译、能跑、算出来的结果逐位正确**。它的 `blocks` 是 **500000**，而按 `blockDim = 512` 覆盖 `N = 500000` 只需要 **977** 个 block。两者相差 **511.77 倍**（block 口径）或 **512.0 倍**（线程口径——因为每个 block 都按 512 个线程发射，`500000 × 512 = 256000000` 而有用的是 500000）。

结果之所以还对，是因为 kernel 内部有 `if (idx < N)` 守卫。**守卫救了正确性，但一点也没救代价。**

**场景 B（编译通过，运行期挂起或给错值）**：

```c
if (threadIdx.x < 32) {
    __syncthreads();          // 编译器不报错，运行时不报错
    buf[t] += 1.0f;
}
```

`__syncthreads()` 落在**依赖 `threadIdx` 的条件分支**里。这个条件在同一个 block 内对线程**不成立同一个值**（半个 warp 满足、半个不满足），于是这个 block 的线程**不会被同一组线程到达同一个屏障**。指南对这行代码只有一句要求（§1、§2.1 逐字引出），而**编译器和运行时都不会替你检查它**。

## 1. 原理

### 1.1 三个名字，三种「谁必须一起到达」

| 名字 | 由谁给定 | 「一起到达」的含义 |
|---|---|---|
| `threadIdx` | 硬件给每个线程一组**只读**的坐标（x/y/z） | 不适用——它是坐标，不是同步点 |
| `blockDim` | 你在 `<<<grid, block>>>` 里写的**每块线程数** | 一个 block 的线程**可能不同时驻留**，但**必须能同时驻留**才合法 |
| `__syncthreads()` | 你在代码里写的一个**块级屏障** | **整个 block 的所有未退出线程**都必须到达（§2.1 给出这条的架构分界） |

`__syncthreads()` 的语义不是「等一会儿」，而是**一个契约**：调用点之后的代码，看到的全局内存与共享内存写入，包含了**同一 block 内所有线程在调用点之前**的写入。指南对它的**可判定前提**只有一句（锚点 C1，§7.6）：

> "__syncthreads() is allowed in conditional code **but only if the conditional evaluates identically across the entire thread block**, otherwise the code execution is likely to hang or produce unintended side effects."

这句原文有两个部分——「允许」与「但只在……时」。检查器能机械判定的只是**后者的一个子集**：条件里出现 `threadIdx`（或由它算出的量）就报。**一个不含 `threadIdx` 却仍然发散的表达式，检查器报不出来**（§4.7 把这条写成已知局限）。

### 1.2 ★ 多步推导：`(threads - 1) / threads` 为什么恒为 0，以及正确写法为什么是上取整

**第一步（退化）**：C 的整型除法是**截断除法**（toward zero）。设 `T ≥ 1` 为 `threads`。则 `0 ≤ T − 1 < T`，按整型除法 `(T − 1) / T` 的商是 **0**、余数是 `T − 1`。⇒

```text
blocks = (N + (threads - 1) / threads) = (N + 0) = N
```

**这一步与 N 无关**：只要 `threads ≥ 1`，它就把 `blocks` 钉成 `N`。所以这**不是**「在某些配置下才错」，而是**在任何配置下都错**。

**第二步（正确写法）**：设 `N = q·T + r`，`0 ≤ r < T`，则 `⌈N / T⌉ = q + [r > 0]`（`[·]` 是 0/1 指示）。而

```text
(N + T − 1) / T  =  (q·T + r + T − 1) / T  =  q + (r + T − 1) / T
```

因为 `0 ≤ r ≤ T − 1`，所以 `T − 1 ≤ r + T − 1 ≤ 2T − 2 < 2T`，于是 `(r + T − 1) / T` 在整数除法下是 **1 当且仅当 `r + T − 1 ≥ T`，即 `r ≥ 1`**，否则是 0。⇒ 二者相等。代进 hw13 的常数：

```text
⌈500000 / 512⌉ = (500000 + 511) / 512 = 500511 / 512 = 977   （C 截断除法）
```

**第三步（代价）**：错误写法下 `blocks = 500000`，错误写法与正确写法的**发射量之比**：

| 口径 | 错误写法 | 正确写法 | 比值 |
|---|---|---|---|
| block 数 | 500000 | 977 | **511.77×** |
| 线程槽（block × blockDim） | 500000 × 512 = **256000000** | 977 × 512 = 500224 | **512.00×** |

**两个口径给出两个不同的数（511.77 与 512.00），而两个都对**——差的是 `⌈N/T⌉` 与 `N/T` 那一点点。这正是 §0.2 提示的「同名不同指」：写正文时必须写明是哪一个口径，否则「超发 512 倍」与「超发 511.8 倍」会被当成互相矛盾的两个说法。

**第四步（守卫的作用）**：通过 `if (idx < N)` 的线程数是 `N = 500000`，占发射总数的

```text
500000 / 256000000 = 1/512 = 0.1953125%
```

被守卫丢弃的线程槽是 `256000000 − 500000 = 255500000`。**结果正确性完全由这一步保证**，因为 `idx ≥ N` 的线程写的是越界地址——守卫把它们挡在外面。

### 1.3 归约的幺元：为什么 `0.0f` 对 `+=` 无害、对 `max()` 有害

归约的初值必须是一个**幺元**（identity）：`x ⊕ e = x` 对所有 `x` 成立。

- `+` 的幺元是 **0**：`x + 0 = x` ✓
- `max` 的幺元是 **−∞**：`max(x, −∞) = x` ✓
- **`max(x, 0) = 0` 当 `x < 0`** ✗ —— 只要输入里出现负数，初值就会**取代**它。

于是 `sdata[tid] = 0.0f` 后面跟 `max(...)` 的代码，在**全负数输入**上返回 `0.0f` 而不是最大负数。这不是精度的近似误差，是**语义错误**。

hw5 的成对文件把这件事钉死了——两个文件第 23 行**逐字相同**，只有第 27/34 行的**算子**不同：

| | `max_reduction.cu`（题目给的 sum 版） | `max_reduction_solution.cu`（参考 max 版） |
|---|---|---|
| 第 23 行 | `sdata[tid] = 0.0f;` | `sdata[tid] = 0.0f;` ← **逐字相同** |
| 第 27 行 | `sdata[tid] += gdata[idx];` | `sdata[tid] = max(gdata[idx], sdata[tid]);` |
| 第 34 行 | `sdata[tid] += sdata[tid + s];` | `sdata[tid] = max(sdata[tid + s], sdata[tid]);` |

⇒ **「初值是 0.0f」这一条本身不是判据**（它在 sum 版里完全正确）。判据是「**幺元与算子不匹配**」，而它要求**同时看**初值行与算子行。这就是为什么 C4 的判定必须两处都读，而它给出的严重等级是 **WARN 而不是 ERROR**：代码在它**自带**的测试数据上是正确的。

### 1.4 分块装填：为什么右值必须依赖分块号

分块（tiling）矩阵乘的外层循环是

```c
for (int i = 0; i < ds / block_size; i++) {   // i 是分块号
    As[threadIdx.y][threadIdx.x] = A[...];    // 把第 i 块装进共享内存
    Bs[threadIdx.y][threadIdx.x] = B[...];
    __syncthreads();
    /* 用这一块做累加 */
    __syncthreads();
}
```

「第 i 块」这个语义**只体现在右值的下标里**。如果右值不随 `i` 变化，那么**每一趟装填的都是同一块数据**——循环白跑 `ds/block_size` 遍，累加结果错，而**共享内存数组的声明、屏障的位置、循环的次数都完全正确**。这份起始代码里没有任何语法错误：

```c
As[threadIdx.y][threadIdx.x] = A[idy*ds+idx];                       // 漏了分块号
Bs[threadIdx.y][threadIdx.x] = B[idy*ds+idx];                       // 漏了分块号
```

参考解在第 40/41 行分别写成 `A[idy * ds + (i * block_size + threadIdx.x)]` 与 `B[(i * block_size + threadIdx.y) * ds + idx]`——**`i` 出现在两处**。检查器 C3 的判据就是这件事：**外层 `for` 的归纳变量（或由它算出的中间量）必须出现在右值里**。

## 2. 执行映射

### 2.1 `__syncthreads()` 在硬件上是什么：一个**有架构分界**的强制级别

这是本篇最重要的一条外部事实。指南 §16.6.2 Independent Thread Scheduling 逐字写道（锚点 C1b）：

> "Although __syncthreads() has been consistently documented as synchronizing all threads in the thread block, **Pascal and prior architectures could only enforce synchronization at the warp level**. In certain cases, this allowed a barrier to succeed without being executed by every thread as long as **at least some thread in every warp reached the barrier**. **Starting with Volta**, the CUDA built-in __syncthreads() and PTX instruction `bar.sync` (and their derivatives) **are enforced per thread** and thus will not succeed until reached by all non-exited threads in the block. Code exploiting the previous behavior **will likely deadlock** and must be modified to ensure that all non-exited threads reach the barrier."

把它拆成可操作的判断：

| 架构 | 强制的单位 | `__syncthreads()` 写在发散分支里会怎样 |
|---|---|---|
| Pascal 及更早（`sm_6x` 及以前） | **warp 级**：每个 warp 只要有**至少一个**线程到达屏障，这个 warp 就过关 | **可能侥幸不死锁**，但语义已经错了（未到达的线程没被同步） |
| Volta 及以后（`sm_70`+） | **线程级**：屏障要等**所有未退出的线程** | **必然死锁**（指南：will likely deadlock） |

**参与的部件**：PTX 指令 `bar.sync`、block 级的 barrier 资源、warp scheduler、以及 Volta 起引入的**逐线程程序计数器与调用栈**（independent thread scheduling 的前提）。一个 `blockDim = 512` 的 block 是 **16 个 warp**（512 ÷ 32）——`__syncthreads()` 要求这 16 个 warp 的**全部 512 个未退出线程**都到达同一个 `bar.sync`。

⇒ 这条外部事实把「发散分支里的 `__syncthreads()`」从一条「风格建议」变成了一个**有明确后果的行为**：它不是在旧卡上“没事”、在新卡上“偶尔挂”，而是**机制变了**。同一句代码在不同架构上的可观测行为不同，而**编译器一条都不查**。

### 2.2 超发的 256000000 个线程槽在硬件上变成了什么

| 量 | 值 |
|---|---|
| 要处理的元素 | `N = 500000` |
| hw13 的 `blocks`（退化后） | **500000** |
| 每 block 线程数 | 512 = **16 个 warp** |
| 被发射的线程槽 | 500000 × 512 = **256000000** |
| 相当于多少个 warp | 256000000 ÷ 32 = **8000000** |
| 真正做事的线程 | 500000（合 15625 个 warp） |

**参与的部件**：grid 的分发（GigaThread 引擎按 block 把工作派给 SM）、SM 里的 block 槽位、warp scheduler、以及守卫分支的**谓词化 / 早退**。被超发的 block 全部要走完「拿到 SM 槽位 → 派发 warp → 读 `blockIdx`/`threadIdx` → 算 `idx` → 求值 `idx < N` → 不成立 → 退出」这条路径。

**★ 这里必须克制**（`CONTRIBUTING` 对第四类数字的规则）：本仓库**没有测过**这 8,000,000 个 warp 的退出开销有多大，也**没有**任何 GPU。所以本篇**只主张一件事**：

> 被发射的线程槽是 `256000000` 而不是 `500224`（**这是从源码算出来的，可对着 hw13 第 21/104/105 行复核**）。

**本仓库不主张**「所以它慢了 512 倍」——发射代价、占用率与守卫分支的收敛行为，本机一个都没测。`code/01_sync_contract.py` 的 B 组把这几个数字逐条算出来并**明确写出它不主张什么**。

### 2.3 检查器读的是什么，读不到什么

检查器做三件事，全部是**文本层**的：

1. **符号表**：把 `#define N 500000`、`int threads = 512;` 之类的整型常量收起来，用 **C 的整型语义**求值（截断除法）。这一步是 C3/C5 的基础——它必须知道 `blocks` 到底等于几。
2. **结构扫描**：手写括号配平，给每个偏移量算出「它落在哪些 `if` / `for` / `while` 里」。
3. **共享数组的取用方式**：记录每个 `__shared__` 数组被 `threadIdx` 直接索引的**维**——C2 的维度契约**只对这样的维**成立。

**它读不到**：数据流（它不建 SSA、不做支配分析）、别名（`float* p = A + i*ds;` 这种指针运算传递的依赖看不出）、以及任何需要**执行**才能知道的东西（`__syncthreads()` 在真实硬件上会不会挂起——本机**无 GPU**，一个 thread 都没跑过）。§4.7 说明这个边界落在哪里。

## 3. 实现与演进

### 3.1 三对真实文件的逐字对照（判据的真值来源）

判据 C3/C4/C5 的规则不是本篇发明的，是**从成对文件里反推**出来的。三对都已逐字核对过：

| 对 | 「已知有问题」 | 「已知正确」 | 差异的位置与内容 |
|---|---|---|---|
| C3 | `exercises/hw2/matrix_mul_shared.cu` | `exercises/hw2/matrix_mul_shared_solution.cu` | 第 **40/41** 行：右值**缺 `i * block_size` 项**（两文件第 37 行的 `for` 头逐字相同，归纳变量都是 `i`） |
| C4 | `exercises/hw5/max_reduction.cu`（sum 版） | `exercises/hw5/max_reduction_solution.cu`（max 版） | 第 27/34 行的**算子**不同；第 **23** 行的**初值逐字相同**（这正是矛盾所在） |
| C5 | —— | `exercises/hw13/` 的 **7 个文件**（含 2 份参考解） | 第 91/104/105/97/93/92/76 行的 `blocks` 表达式**逐字相同** |

C5 这一栏的「对」是**不对称的**：这 7 个文件**全都写着同一个错误表达式**，没有「已知正确」的对照文件。它的真值来自**算术本身**（§1.2 的两步推导）以及**源文件里另一个正确的例子**——hw5 自己的启动配置用的是正确写法：

```text
hw5/max_reduction_solution.cu 使用 (N + BLOCK_SIZE - 1) / BLOCK_SIZE   →  blocks = 640   (N = 8388608, BLOCK_SIZE = 256)
```

**同一份材料里既有正确写法也有错误写法**——这让 C5 的判据有了内部对照。

### 3.2 检查器的三次迭代（每一次都是被一个真实误报逼出来的）

| 版本 | 做法 | 被什么逼着改 |
|---|---|---|
| v1 | C2 无条件比对共享数组维度与 `blockDim`；C3 只做**文本**匹配（右值里有没有出现归纳变量的名字） | 两个**误报**：`04_flash_attention/flash_attention.cu` 与 `02_gemm/gemm.cu`（§4.1、§4.2） |
| v2 | C2 加上**条件**：只有该维的下标表达式里**真的出现 `threadIdx`** 时才判；C3 改成**依赖感知**（把循环体内由归纳变量算出的中间量也算作依赖，传递 3 轮） | —— |
| v2 + 夹具 | C1 用一份**合成夹具**证明它「该报的时候才报」 | 只证明「能报」不构成证据（§5 的 C.1/C.2 是一对） |

**v2 依然不是完整的数据流分析。** 它只是**在文本匹配上加了一层中间量传递**。这条限制写在程序的 docstring 里，也写在 §4.7。

### 3.3 演进：从「检查约束」到「消灭约束」

三条路线，代价与适用范围都不同：

1. **静态检查（本篇的程序）** — 词法 / 结构层，**不执行**。能覆盖的只有可判定的子集；它抓到的是「写法」，不是「行为」。
2. **动态检查** — 指南 §16.6.2 末尾提到 compute-sanitizer 的 `racecheck` / `synccheck` 可以定位这类违规。★ 这是**引用值**：本机**没有** compute-sanitizer（无 CUDA 工具链），**本仓库不复核它的测量口径**。
3. **把边界假设消灭掉** — 用 **grid-stride loop** 代替「按 `N` 反推 block 数」：

```c
for (size_t idx = blockIdx.x*blockDim.x + threadIdx.x; idx < n; idx += gridDim.x*blockDim.x)
```

这一段在 `cuda-learning` 的 kernel 与 hw5 的归约里都出现过。它的价值在于：**启动配置不再依赖 `N`**，于是「`blocks` 写错」这一整类错误在结构上不可能发生。hw13 的 `blocks` 错误之所以能潜伏，正是因为它同时**有一个正确的守卫**——把守卫当成「所以没问题」的理由，就等于接受 `blocks` 可以随便写。

> ⚠ **`cuda-learning` 的目标环境是 Tesla T4 / sm_75（Turing）**（其 `README.md` 第 16–17 行）。它是**没有** bf16 / TF32 / `cp.async` / TMA / warp-specialization 的一代（第 22 行）。上面引它的 kernel 时**必须同时说明这一点**，否则读者会以为那是 Hopper/Blackwell 的写法。

## 4. 踩坑与失败模式

### 4.1 检查器把「数组从不被 `threadIdx` 直接索引」误报成维度不自洽

- **现象**：C2 对 `cuda-learning/04_flash_attention/flash_attention.cu` 报「`Ks[Bc][D]` 第二维 64 < `blockDim.x = 128`」。该数组的声明与启动配置都**没有问题**。
- **成因**：该数组的装填走的是**协作式循环** `for (int r = threadIdx.x; r < Bc; r += blockDim.x) Ks[r][j] = K[row*D+j];`——索引是 `Ks[r][j]`，`threadIdx` 只出现在**循环的步进**里，不在**下标**里。v1 无条件比对「维度 ≥ blockDim」，于是把「该维必须由 `threadIdx` 覆盖」这个**前提**当成了**结论**。
- **规避**：判据要**先问前提**——只有该维的下标表达式里**真的出现 `threadIdx`** 时，「维度 ≥ blockDim」这条契约才成立。修正后 C2 对该文件**0 命中**（程序 `A.4b` 钉住这条回归）。
- **一般化**：这是「**判据的适用前提**没写进判据」这一类错误的实例。

### 4.2 检查器把「依赖经中间量传递」误报成漏分块号

- **现象**：C3 对 `cuda-learning/02_gemm/gemm.cu` 报「右值不含归纳变量 `t`」。该文件的装填是**正确**的。
- **成因**：它的右值是 `A[row * K + kA]`，而 `kA` 在循环体内定义为 `int kA = t * TILE + threadIdx.x;`——**依赖经一个中间量传递**，文本上确实不含 `t`。只做文本匹配的 C3 看不出这条链。
- **规避**：把循环体内「由归纳变量算出的局部量」也算作依赖（`tainted` 集合，传递 3 轮）。修正后 C3 对该文件 **0 命中**（程序 `A.4` 钉住）。
- **残余**：这只加**一层**传递（3 轮），不建 SSA。一个经由**指针运算**传递的依赖（`float* p = A + i*ds;` 之后用 `p[j]`）它仍然看不出。

### 4.3 块数写错 511.8 倍，而程序的结果逐位正确

- **现象**：`blocks = (N + (threads - 1) / threads)` 得到 `500000` 而不是 `977`；结果仍然对。
- **成因**：C 的**整型除法**把 `(threads − 1) / threads` 变成 0，表达式退化成 `N`（§1.2 第一步）。结果对是因为 kernel 里有 `if (idx < N)` 守卫。
- **规避**：两条，**都要**——① 写成正确表达式的可读形式 `(N + threads - 1) / threads`，或者更彻底地改用 **grid-stride loop**（§3.3）；② 如果只能用「按 N 反推」的写法，把「守卫」当成**最后一道防线**而不是**唯一一道防线**。
- **为什么它值得单列**：**7 个文件逐字相同，含 2 份参考解**。这不是笔误，是写法习惯。

### 4.4 `__syncthreads()` 写在发散分支里：旧卡没事、新卡死锁

- **现象**：`if (threadIdx.x < 32) { __syncthreads(); ... }` 编译通过、运行不报错，程序**挂起**或给出错值。
- **成因**：屏障的强制单位在 **Pascal 及更早是 warp 级**（每个 warp 只要有**至少一个**线程到达就算过），**Volta 起改成线程级**（必须所有未退出的线程都到）。同一个 block 内条件取值不一致 ⇒ Volta 及以后必然死锁（§2.1 的逐字原文）。
- **规避**：把 `__syncthreads()` 移到**所有线程都执行**的位置；需要条件同步时，用「条件成立与否**都**执行一次屏障」的写法，或改用 `__syncwarp(mask)` 之类的 warp 级原语（它的 mask 是**显式**的，不依赖控制流收敛）。
- **★ 这条最容易被讲成「一般会挂」**——但它有一个**明确的架构分界**，而那正是「为什么这段代码在旧卡上一直没事」的答案。

### 4.5 `max` 归约用 `0.0f` 当幺元

- **现象**：max 归约对**全负数**输入返回 `0.0f` 而不是最大负数。
- **成因**：`0` 是 `+` 的幺元，不是 `max` 的（`max(x, 0) = 0` 对 `x < 0`）。而这一行是从 **sum 版**复制过来的——`cuda-training-series` hw5 的**参考解**第 23 行仍然是 `sdata[tid] = 0.0f;`。
- **规避**：用 `-INFINITY`（或 `-FLT_MAX`）；如果数据保证非空，用**第一个元素**初始化（`sdata[tid] = gdata[idx];` 之后再归约），这样连幺元的类型问题都不存在。
- **★ 为什么它藏得住**：该文件自带的测试数据**全为正**（`h_A[i]=1.0f`、`h_A[100]=5.0f`）。⇒ **测试数据的选择本身可能掩盖语义错误**——这也解释了为什么 C4 的严重等级是 WARN：代码在它**自带**的输入上是正确的。

### 4.6 协作式装填漏掉分块号

- **现象**：分块矩阵乘的结果错，但循环次数、屏障位置、共享内存声明、`__syncthreads()` 数量**全部正确**。
- **成因**：`As[threadIdx.y][threadIdx.x] = A[idy*ds+idx];` 的右值**不随分块号 `i` 变化** ⇒ 每一趟装填同一块数据（§1.4）。这个错误只体现在**右值**里，任何「看结构」的检查都发现不了。
- **规避**：右值必须含 `i`（或由 `i` 算出的量）。检查器 C3 就是这条判据；它只在「外层有 `for`、且 LHS 下标里出现 `threadIdx`」时适用。
- **为什么值得单列**：它证明「结构正确」与「语义正确」之间有一条检查器也**只能部分**覆盖的缝——C3 做的是**词法级依赖判定**，不是数据流分析（§4.2 的残余）。

### 4.7 ★ 那个「别处」在哪里

本域主线（§0.3）说：**抽象层的价值与它的泄漏是同一件事的两面**。那么这一篇里，代价被藏到了哪里？

> **它被藏进了「正确性」这个词里。**
>
> `blocks = N` 这行代码之所以能活下来，是因为**同一个文件里还有一行 `if (idx < N)`**。守卫把「代价问题」转化成了「已经不是问题了」——**只要结果对，就没人会去数发射了多少个 block**。于是代价被从**正确性**这一个抽象里漏出来了吗？恰恰相反：**代价被压进了正确性，看不见了。**
>
> 这就是那个「别处」：**代价没有消失，它被转移到了一个不在任何人视野里的账本上**（`256000000` 个线程槽），而唯一会看这本账的场合是**性能问题出现之后**——而到那时，这个表达式已经在 7 个文件里复制了 7 遍（含 2 份参考解），没有人会怀疑它。

同一条主线的第二种形态也在本篇里：`__syncthreads()` 的契约（「条件在整个 block 上取同一个值」）**编译器不查**，是因为它在一般情况下**不可判定**。抽象把这份检查工作留给了你，而它的代价在 **Pascal 与 Volta 上不一样**——同一个抽象（「块级屏障」）在两代硬件上的泄漏程度不同，而**语言层的写法完全相同**。

## 5. 判据表

> ★ 按本域约定（域 README），§5 的位置与编号保留，内容**不是实测数据**而是**判据表**。每一行是「**可机械判定的条件 → 结论**」。前提是本机无 GPU、无 CUDA 工具链，本主题**没有任何 GPU 实测数字**。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | `__syncthreads()` 落在含 `threadIdx` 的条件里 | **ERROR**——违反锚点 C1 的可判定子集；Volta 及以后**必然死锁**（锚点 C1b） |
| 2 | 该条件**不含** `threadIdx` 但仍可能发散 | **本检查器报不出来**——见 §4.7；必须人工判断 |
| 3 | 条件相同、但 `__syncthreads()` 落在统一控制流里 | **不报**——判据不是「见条件就报」（程序 `C.1`/`C.2` 是一对） |
| 4 | `__shared__` 某维的下标出现 `threadIdx`，且该维尺寸 < 对应 `blockDim` | **ERROR**——维度契约不满足 |
| 5 | `__shared__` 某维**从不被 `threadIdx` 直接索引**（走协作循环） | **该维无契约**，不报（§4.1 的误报回归） |
| 6 | 静态 `__shared__` 合计 > 48 KB | **ERROR**——按锚点 C2 必须改动态共享内存 + `cudaFuncSetAttribute()`。★ 该锚点的原句以「Compute capability 7.x devices …」开头，**作用域是 7.x 设备** |
| 7 | 静态 `__shared__` 合计**正好等于** 48 KB（49152 字节） | **不报**——判据是「**over** 48 KB」；边界落在**一个 `float`** 上（96×128×4 = 49152 不报，97×128×4 = 49664 报） |
| 8 | 外层 `for` 的归纳变量（或由它算出的中间量）**不出现在**共享内存写入的右值里 | **ERROR**——该次装填与分块号无关（§1.4 / §4.6） |
| 9 | 右值经**指针运算**（`float* p = A + i*ds;`）传递依赖 | **本检查器报不出来**——只有一层中间量传递，不做数据流分析（§4.2 的残余） |
| 10 | 归约算子是 `max`/`min`，而累加器初值是 **≥ 0** 的常量 | **WARN**——幺元与算子不匹配（§1.3 / §4.5）。对非负输入**结果正确**，所以不是 ERROR |
| 11 | 归约算子是 `sum`，初值 ≠ 0 | **WARN**——sum 的幺元是 0 |
| 12 | 同一个共享数组的初值行，在 **sum 版与 max 版**里逐字相同 | 判据**必须同时读初值行与算子行**；只看初值行会把 sum 版误判（程序 `C.5`/`C.6` 是一对） |
| 13 | launch 覆盖的线程数 > 4 × `N`，**且** kernel 内有 `if (idx < N)` 守卫 | **WARN**——超发但结果对（§1.2 第四步）；消息里给出**两个口径**的倍率 |
| 14 | launch 覆盖的线程数 < `N` | **ERROR**——会少算（守卫挡不住「没发射」） |
| 15 | 去掉那个守卫再检查 | **WARN 消失**——因为判据诊断的是「**靠守卫兜住**」这件事；**没有守卫的版本是另一种错**（程序 `C.9` 把这条做成反例） |
| 16 | 把 `blocks` 行换成正确写法再检查 | **WARN 消失**——程序 `C.8` 断言这一点，它证明 C5 钉的**就是那个表达式** |
| 17 | 判据 C6（设计了但没实现） | **不得声称覆盖**——程序 `C.14` 以反向断言钉住这条 |

**闭合性检查**：读完这张表能判完「一行 CUDA 代码在这 5 类契约上是不是有问题、以及哪几类本检查器判不了」。**唯一的表外输入**是「这段代码的意图」（例如那 7 个文件里 `blocks` 到底想写多少）——它必须**读源文件**，不能从写法上推出来。

## 6. 小结与延伸

- ★★ **`(threads - 1) / threads` 在 C 的整型除法下恒为 0**（`0 ≤ T−1 < T`），表达式退化成 `N`。`N = 500000`、`threads = 512` 时 `blocks = 500000` 而不是 **977**。
- ★★ **超发有量纲**：线程槽 **512.00×**（256000000 vs 500224）、block 数 **511.77×**（500000 vs 977）。**两个口径不同、都正确**——写的时候必须写明是哪一个。
- ★★ **「结果对」与「代价对」是两件独立的事**：通过守卫的线程只占 **0.1953%**，剩下 `255500000` 个线程槽被发射后立刻被守卫丢弃。这不是「慢了 512 倍」——**本机没有 GPU，那个结论本仓库不做**。
- ★★ **7 个文件逐字相同，含 2 份参考解** ⇒ 这是写法习惯，不是笔误。同一份材料里 hw5 用的是**正确**写法 ⇒ C5 的判据有内部对照。
- ★ **`max` 的幺元不是 0**：hw5 的 max **参考解**第 23 行仍是 `sdata[tid] = 0.0f;`，对全负数输入返回 `0.0f`；它自带的测试数据全为正，掩盖了这一点。
- ★ **`__syncthreads()` 的强制单位有架构分界**：Pascal 及更早是 **warp 级**，Volta 起是**线程级** ⇒ 同一个发散分支在这两代上的可观测行为不同（锚点 C1b 逐字）。
- ★ **检查器只能覆盖可判定的子集**：它不建 SSA、不做数据流分析，一个不含 `threadIdx` 的发散条件、一条经指针运算传递的依赖，它都报不出来。
- ★ **代码里有一处反向断言**（`C.14`）：C6 判据**设计了但没实现**，程序**不得声称覆盖**它。

**延伸**：

- 分块矩阵乘的完整推导（本篇只讲「装填的右值必须依赖分块号」这一条契约）：`40-kernels/gemm/02-shared-memory-tiling`。
- 归约算法本身（本篇只讲「幺元必须与算子匹配」）：`40-kernels/reduce-scan/01-reduction-algorithms`。
- 共享内存 bank 冲突的机制（本篇不重复推导）：`20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`。
- warp 内发散与独立线程调度的硬件原理：`20-gpu-architecture/execution-model/02-simt-and-divergence`。
- 「先有独立参照再谈验证」的方法论：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- 本域的下一个主题：宿主侧 API 的同步语义与依赖图 —— `30-gpu-programming/cuda/02-streams-and-events`。
