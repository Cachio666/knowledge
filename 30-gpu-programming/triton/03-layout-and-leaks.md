# layout 与它的泄漏：两次 load 只差一个关键字

> **块级程序里最贵的一处，往往不在你写的那一行，而在一个离得很远的关键字参数上。** 本篇用 `code/03_layout.py` 把这件事算到逐位，并给出五条带数字的结论：
>
> 1. ★★ **两次 `load` 只差一个 `order`，源码里 `a * b` 那一行看不出任何区别，而代价从 0 变成一次 131072 字节的共享内存往返**（2 个 barrier）。两张图的输出**逐位相同**（16384 个元素）——差别纯粹在布局，不在数学。
> 2. ★★ **`trans` 是免费的，但它一点没让归约变便宜。** 转置后的布局**参数逐项等于**目标布局（`spt/tpw/wpc/order` 全同），可是归约的代价完全对称：`ops 82432 vs 82432`、`smem 4096 B vs 4096 B`、`barriers 2 vs 2`。⇒ **`trans` 免费 ≠ 归约变便宜**（`B.5`，负面结论）。
> 3. ★★ **代价模型不能退化成「转换一律昂贵」。** 存在**真的免费**的转换：`(64,2)` 的那一对布局**属主逐位相同、寄存器编号不同** ⇒ **0 字节、0 barrier**。官方的锚点逐字支持这件事（`G3`：`which is free`）。★ 把免费判据往**两个方向**改错（一律免费 / 一律昂贵），断言**都会失配**（`C.2`/`C.2b`）。
> 4. ★ **同一次转换，「值不值」按两个口径给出两个不同的交叉点**：barrier 口径 `K* = 2`，字节口径 `K* = 64`（`4096 × 32 = 131072` 正好打平）。⇒ 它在模型里**根本不是一个数**（`B.10`）。
> 5. ★ **「layout 转换昂贵」与「归约跨 warp」的官方出处只有一页**——Gluon「Tensor Layouts」。**主 tutorial（`01-vector-add`）里 `coalesc` / `Layout conversions` / `warp` 的出现次数都是 0**（`B.11` 与 `make anchors` 的可复算口径）。
>
> ★ **★ 本篇的「反直觉量化结论」**：**同一个 `a * b`，两次 `load` 只差一个 `order`，源码里那一行看不出任何区别，而代价从 0 变成一次 131072 字节的共享内存往返**（2 个 barrier）——两张图的输出**逐位相同**（16384 个元素）。
>
> ★ 本篇涉及的两条机制**有官方逐字出处**（`G1`/`G2`/`G3`/`G4`/`G5`）；但**定价公式、摊维规则、属主算法、交叉点这几个数都是本模型自造的**（`code/specs.py` 的 `MODEL_OWN_RULES`）。**B 类全部是模型值，本机无 GPU，一条实测都没有。**

> ★ **本主题的三条限定语，在本篇的落点**（域 README 规定逐篇写明，不得省略）：
> 1. **「本模型的规则是自造的」**——本篇用得最重的正是这一条：**转换定价公式 `2 × numel × esize` 字节 + 2 个 barrier 是本模型自定的**（`R3`），**免费判据「逐元素属主相同」也是本模型自定的**。官方的 `G1` 只锚定「跨 warp 要走共享内存」这个**机制**、`G3` 只锚定「只重排线程内寄存器就免费」这个**充分条件**。
> 2. **「本主题无实测，只有模型值」**——131072 字节、2 barrier、82432 ops、交叉点 2/64 全是**本模型算出来的**。官方页面上的 `0.774 TB/s` 是**引用值**，本仓库**不复核**它的测量口径（那是官方在他们自己的机器上测的）。
> 3. **「不是硬件，也不是 Triton 编译器」**——本程序**不执行任何 GPU 代码**，也不调用任何 Triton 组件。★ 尤其：**「Triton 会为这段代码插一次转换」这句话本机无从验证**，本篇只主张「**按本模型的规则**它需要一次转换」。
> 4. ★ **一处已记录的简化**：本模型要求 `spt×tpw×wpc == shape`（精确切分），真实 Triton 允许覆盖不足——官方第一个例子 `gl.BlockedLayout([1,1],[1,32],[1,4],[1,0])` 在 128×128 上只覆盖 **1×128**。本模型的 `C.5` 把这种布局**直接拒绝**（抛 `LayoutError`），这是**简化而不是规定**。

## 0. 背景与动机

### 0.1 一个具体的对照场景：两次 `load` 只差一个 `order`

块级程序里最无害的一行是逐元素乘法：

```python
a = tl.load(ptr_a, ...)      # order=[1, 0]
b = tl.load(ptr_b, ...)      # order=[1, 0]   ← 与 a 相同
out = a * b                  # 这一行看不出任何差别
```

把第二次 `load` 的一个关键字改掉：

```python
b = tl.load(ptr_b, ..., order=[0, 1])   # ← 唯一的差别
out = a * b
```

**输出的 16384 个元素逐位相同**（`A.2`）——**数学完全没变**。代价却变了（`B.6`）：

| | 布局转换次数 | barrier | 共享内存 |
|---|---|---|---|
| `G_cheap`（两次 `order=[1,0]`） | 0 | **0** | **0 B** |
| `G_dear`（第二次 `order=[0,1]`） | 1 | **2** | **131072 B** |

**131072 字节 = 2 × 16384 个元素 × 4 字节**——写一遍、读一遍（`R3` 的定价公式）。

**场景的本质**：`order` 是一个**告诉编译器「哪条维最快变化」**的参数。它决定了「谁摊在哪一维」，而「谁摊在哪一维」决定了两个操作数的**属主是否相同**；不同就要有人把数据搬一次——**跨线程搬**（共享内存），因为不同线程的元素不能直接互相看见。

## 1. 原理

### 1.1 属主映射：blocked layout 的全部内容

给定四个参数，**每个元素的属主线程号**是算出来的（`R2`，本模型自定）。以 `Lrow`（官方字面量那条）为例：

```text
shape=(128,128)  spt=(1,128)  tpw=(32,1)  wpc=(4,1)  order=(0,1)
```

`axis_threads(0) = tpw[0] × wpc[0] = 32 × 4 = 128`，`axis_threads(1) = 1 × 1 = 1`。⇒ **第 0 维由 128 个线程分担，第 1 维完全在一个线程手里**。所以：

| 布局 | 一行的 128 个元素属于几个线程 |
|---|---|
| `L`（内维合并） | **128** 个 |
| `Lrow`（第 0 维合并） | **1** 个 |

（`B.2`）这一行差异就是**后面所有归约代价差异的根源**。

★ **`coalesced_layout` 的规则是本模型自造的**（`R1`）：先把 32 个 lane 尽量摊到 `order[0]`，摊完再摊到 `order[1]`……剩下的元素数全归 `sizePerThread`。它在 `shape=(128,128) / num_warps=4 / order=[0,1]` 上**逐参数复现**了官方那条字面量：

```text
本模型：spt=(1,128) tpw=(32,1) wpc=(4,1) order=(0,1)
官方  ：gl.BlockedLayout([1, 128], [32, 1], [4, 1], [0, 1])
```

**★ 「复现同一个结果」不等于「同一个规则」**，这一点写在 `B.1` 的断言里，也写进 `MODEL_OWN_RULES["R1"]` 的 `basis`。

### 1.2 ★ 多步推导：从「谁摊在哪一维」到「要不要搬数据」

**第一步（归约只需要一个方向的信息）**。归约 `axis=1` 要合并**同一行**的 128 个元素。这批元素的属主是 `axis_threads(1)` 个线程——它们是**一个**还是**一百二十八个**，决定了要不要通信：

```text
Lrow:  axis_threads(1) = 1    ⇒ 一行的 128 个元素全在同一个线程的寄存器里
                                ⇒ 相位 1（线程内）就能算完
L:     axis_threads(1) = 128  ⇒ 一行分散在 128 个线程上
                                ⇒ 相位 1 之后还有相位 2（warp 内蝶形）与相位 3（跨 warp）
```

**第二步（跨 warp 为什么必须走共享内存）**。warp 内的两个 lane 之间可以 `__shfl_xor_sync`（**蝶形**）；**跨 warp** 的线程之间**没有**这样的寄存器级通道——官方原文（`G1`）：

> 「Layout conversions are **potentially expensive** operations, because they often result in data movement across threads and warps. Data movement across warps also requires using **shared memory**, which is a precious resource on the GPU.」

⇒ 「跨 warp」与「必须经共享内存」在官方那页上是**同一句话**里的因果。本模型把这条机制实现为：跨 warp 相位 = **写一遍 + read 一遍 + 2 个 barrier**（`R3` 的定价）。

**第三步（`trans` 为什么免费）**。`tl.trans` 只改**维标签**，不改数据在寄存器里的位置。本模型里 `permute` 只重排 `shape/spt/tpw/wpc/order` 五个元组：

```text
L.permute([1,0]) = spt=(1,128) tpw=(32,1) wpc=(4,1) order=(0,1)   ==  Lrow  （参数逐项相等）
```

（`B.4`）**它不产生任何代价事件**。代价由**消费者**在需要「规范布局」时付出——这正是 `A.1`（G1 与 G2 输出逐位相同）与 `B.5`（G1 与 G2 代价完全对称）这一对的含义。

**第四步（为什么「加 trans 就能省」是错的）**。归约的代价由 `axis_threads(被归约的那条轴)` 决定。转置把「被归约的轴」从 `1` 换成 `0`，而**两条轴的 `axis_threads` 都是 128**——于是摊开量**一点没变**，代价自然一点没省：

```text
reduce(axis=1) on L     : ops 82432  smem 4096 B  barriers 2
reduce(axis=0) on L.perm: ops 82432  smem 4096 B  barriers 2
```

⇒ **要省掉跨 warp 相位，唯一的办法是让被归约的那条轴在跨 warp 方向上是 1 —— 而那由 `load` 的 `order` 决定，加 `trans` 改不了它。**

### 1.3 转换的定价：免费与不免费是**可判定**的

`Conversion._is_free` 的判据只有一条（`R3`）：**每个元素换布局后仍归同一个线程** ⇒ 只是线程内寄存器重排 ⇒ 零代价。本模型里它是

```python
np.array_equal(self.src.owners(), self.dst.owners())
```

| 对 | 属主 | 寄存器编号 | 判定 |
|---|---|---|---|
| `(64,2)` 的那一对（`free_conversion_demo`） | **逐位相同** | **不同**（穷举搜出来的） | **免费**：0 B / 0 barrier（`B.8`） |
| `L → Lrow` | 不同 | —— | **昂贵**：`2 × 16384 × 4 = 131072 B` / 2 barrier（`B.9`） |

**★ 为什么这一条必须有**：如果代价模型把「转换一律昂贵」，那它**错**（不是保守）——官方明写存在免费的转换（`G3`）。如果把它改成「一律免费」，那它也错——`B.6` 的 131072 字节就消失了。两个方向的错误都被 `C.2`/`C.2b` 抓住。

### 2.1 官方出处的**唯一性**（这一节是本篇最硬的事实）

「layout 转换昂贵」与「归约跨 warp」这两条机制的官方出处**只有一页**。本主题用 `curl -sSL` 取原始页面、按 `code/specs.py` 模块头写明的口径去标签后**逐数计数**（`make anchors` 可复算）：

|---|---:|---:|---:|

⇒ **主 tutorial 里 grep 不到 `coalesc`，也完全没有 layout 转换的说法。** 这句话的含义不是「文档不好」，而是：

> **官方教 Triton 的那一套材料里，根本没有「layout 会泄漏成代价」这一课。** 这一课只在 **Gluon**（Triton 的下一代、更底层的接口）的页面里。

★ **口径必须写下来**（这是计划 §0.7 F4 的教训）：`warp` 那一列在**大小写敏感**下是 `71`（去标签文本）/ `72`（原始字节），在**不敏感**下才是 `73`。`specs.py` 把 `warp_cs` 与 `warp_ci` **两个都记**、不合并成一个数——写成一个数会让复现的人得出「对不上」的结论。

### 2.2 参与的部件与量级（`128×128` tile、`num_warps=4`）

| 量 | 值 |
|---|---|
| tile 元素数 | `128 × 128 = 16384` |
| 线程数 | `32 × 4 = 128` |
| 每线程元素数 | `16384 / 128 = 128` |
| 一次昂贵转换的共享内存 | `2 × 16384 × 4 = **131072 B**` |
| 一次昂贵转换的 barrier | **2** |
| 一次归约的共享内存（`L` 上 `axis=1`） | `4096 B` |
| 交叉点（barrier 口径 / 字节口径） | `K* = 2` / `K* = 64` |

**参与的部件**：寄存器（免费的转换只在这里重排）、**共享内存**（昂贵的转换的通道，也是 `G1` 点名的「precious resource」）、**barrier**（写入与读出之间必须有一次同步，本模型按「写一遍 + 读一遍 = 2 个 barrier」计）、以及 `store` 侧的**合并访存**要求（`B.7b`）。

**★ 这里必须克制**：`131072 B` 是**模型值**。`B.7b` 说的是「把转过置的结果写回一个要求合并访存的位置，**按本模型的规则**必须付一次转换」——**不是**「真实 Triton 一定会付」。

### 2.3 交叉点：同一次转换，两个口径两个答案

`K` 次归约的循环里，可以选择「一开始做一次显式转换」或「什么都不做」：

| 口径 | 每次归约 | 一次转换 | 打平在 | 严格更省在 |
|---|---|---|---|---|
| barrier | 2 | 2 | `K = 1` | `K ≥ 2` |
| 字节 | 4096 B | 131072 B | `K = 32`（`4096 × 32 = 131072`） | `K ≥ 64` |

（`B.10`）**⇒ 「这次转换值不值」在模型里根本不是一个数。** 想让它变成一个数，必须先声明「barrier 与字节怎么换算」——**而那一层换算本模型没有给**（也不该给：真实硬件上它们的相对价格随架构变）。

## 3. 实现与演进

### 3.1 迷你 IR 与前向布局推断（`layout_pass`）

`code/minitriton.py` 里有一个只有 7 种算子的迷你 IR：`load` / `trans` / `reduce` / `broadcast` / `elementwise` / `convert` / `store`。`layout_pass` 做**前向布局推断**：

1. 每个算子的布局由生产者决定；
2. 消费者的要求不同时，**插入一次转换**并把它记进事件列表；
3. `allow_convert=False` 时，**任何**需要转换的位置都抛 `LayoutConflict`（不静默产出错计划）。

**★ 第 3 条是这套判定的可证伪性来源**：`C.1` 对 `G_dear` 声明「不许插转换」⇒ 抛错；`C.1b` 对 `G_cheap` 用**同一个声明**⇒ 通过。`C.1d` 再把两件事摆在一起：同一张图在 `allow_convert=True` 下产出 **1** 个转换、在 `False` 下**抛错**——两条分支真的分开了。

**★ `store` 的要求单独说**：`store` 要求布局在 `coalesced_dim` 上**连续**（`contiguous_along`）。不连续时要**重新构造**一个沿该维合并的布局再插转换——不能沿用源布局的 `order`，否则会算出一个与源**完全相同**的布局、转换退化成恒等，**非合并访存就被静默放过了**（`minitriton.py` 的 `layout_pass` 里有一段注释专门记这件事）。

### 3.2 三次迭代

| 版本 | 做法 | 被什么逼着改 |
|---|---|---|
| v1（探针） | 只有 `allow_convert=False` 与「一律免费/一律昂贵」两个方向的反例 | 缺**非退化性**的正例：没人证明「真的免费的转换」在模型里可达 |
| v2 | 穷举搜出 `(64,2)` 那一对（属主相同、寄存器编号不同） | 「免费判据」的锚点没落到官方原文上——`G3` 的括号里那句 `which is free` 是**唯一的**官方依据 |
| v3（本篇） | 补 `B.10`（两个交叉点）、`B.11`（页面级事实）、`A.9`（恒等转换返回 `None`）、`A.11`–`A.13`（布局代数自身性质） | 断言里有一处**恒真**：`MODEL_OWN_RULES[*]['rule']` 的「打印一致性」（打印列表由同一个常量拼出）——被变异测试抓出，改成只断言可判定的部分（`A.7`） |

### 3.3 演进：从「按布局写代码」到「让布局成为参数」

1. **手写布局**（本模型的做法）——你必须知道 `order`、`spt`、`tpw`、`wpc` 四个参数，并知道它们的代价含义。
2. **让编译器选**（Triton 的默认）——编译器替你推断 layout 并插转换。**代价被隐式地转移到了那些转换上**——这正是本篇 §4.5 要指出的「别处」。
3. **把布局提到语言层**（**Gluon** 的做法）——`gl.BlockedLayout(...)` 是**显式**的类型，`gl.convert_layout(x, layout, assert_trivial=True)` 可以在**编译期**断言「这次转换必须是免费的」（`G3`）。⇒ 它把「隐式的搬运」变成了**显式的、可断言的类型约束**：**如果转换不免费，编译直接失败**，而不是运行时慢。

★ **本主题不展开 Gluon 的语言设计**（那会滑进 `60-compilers` 的编译器架构）；这里只需要知道：**「免费/不免费」这件事有官方的、可断言的判据**，而本模型的 `_is_free` 是它的一份**自造**实现。

## 4. 踩坑与失败模式

### 4.1 ★★ 只差一个关键字参数的两次 `load`（泄漏 L3）

- **现象**：`a * b` 这一行源码**看不出任何差别**，输出**逐位相同**（16384 个元素），而代价从 **0 barrier / 0 B** 变成 **2 barrier / 131072 B**。
- **成因**：第二次 `load` 的 `order` 与第一次不同 ⇒ 两个操作数的**属主映射不同** ⇒ 逐元素算子必须先**统一布局**。跨线程统一只能走共享内存（`G1`），而它要**写一遍 + 读一遍 + 2 个 barrier**（`R3`）。
- **规避**：把**参与同一个逐元素算子的所有 `load` 写成同一个 `order`**。这条规约的代价是「不能对不同的输入用不同的最优访存模式」——**这就是它的全部代价**，而且它是**局部的**（只看一个表达式内部）。
- **为什么它值得单列**：**它的载体是一个离得很远的关键字参数**。审阅者读 `a * b` 时看到的是「一次乘法」；成本却在两次 `load` 的参数里。

### 4.2 `trans` 免费 ⇒ 「先转成高效布局再归约更便宜」

- **现象**：`load → trans → reduce(axis=0)` 看起来比 `load → reduce(axis=1)` 多一步，直觉上「先转成行内布局，归约就便宜了」。
- **成因**：归约的代价由 `axis_threads(被归约的轴)` 决定，转置把被归约的轴从 `1` 换成 `0`，而**两条轴的 `axis_threads` 都是 128** ⇒ 摊开量没变（§1.2 第四步）。**本机跑出**：`ops 82432 vs 82432`、`smem 4096 B vs 4096 B`、`barriers 2 vs 2`（都是模型值）。
- **规避**：**想省跨 warp 相位，改 `load` 的 `order`**（让被归约的那条轴在跨 warp 方向上是 1），而不是加 `trans`。★ 官方的 `G5` 从另一个角度说了同一件事：「先把 layout 转成高效的再做归约通常**更贵**」——本库这条是从**两个数**推出来的，`G5` 是官方的一句话，**方向一致但不同源**。
- **★ 这是一条负面结论，保留它**：它挡住的正是「多写一步就能变快」这种直觉。

### 4.3 把转换定价成「一律昂贵」（模型的非退化性）

- **现象**：如果 `_is_free` 恒为 `False`，那么形如「两个参数几乎相同、只是寄存器编号不同」的转换会被算成 131072 字节的搬运。
- **成因**：**免费的转换真的存在**（`G3` 括号里的 `which is free`）。把模型写成「一律昂贵」不是保守，是**错**。
- **规避**：`B.8` 用 `(64,2)` 那一对（属主逐位相同、寄存器编号不同）钉住免费那一支；`C.2b` 把判据改成「一律昂贵」⇒ `B.8` 失配。**两个方向都有判别力。**
- **一般化**：**代价模型必须至少在两个方向上都可证伪**——只能往一个方向证伪的模型，会把它的偏置伪装成结论。

### 4.4 「拒绝对拍」把非合并访存静默放过

- **现象**：`store` 的目标布局如果沿用源布局的 `order`，会算出一个**与源完全相同**的布局，转换退化成恒等 ⇒ 「把转过置的结果写回一个要求合并访存的位置」这件事**不需要付任何代价**。
- **成因**：目标布局必须**真的沿 `coalesced_dim` 合并**，所以 `order` 要**重排**，不能沿用源的。
- **规避**：`B.7b` 钉住「这次转换是 2 barrier / 131072 B」，`C.1c` 钉住「声明不许插转换时**拒绝**」。★ 这条与 `G4`（「内维不再连续 ⇒ 没有合并访存」）是同一件事的两面。

### 4.5 ★ 那个「别处」在哪里

本域主线说：**抽象层的价值与它的泄漏是同一件事的两面**。这一篇的答案最直白：

> **代价被藏进了一个离得很远的关键字参数里。**
>
> 「块级程序」这个抽象的卖点是：**你只描述数据的形状与运算，不描述线程**。这个卖点是真的——`a * b` 那一行确实只需要两个张量。代价是：**当两个张量的属主不一致时，必须有人搬一次数据，而这件事在你写的那一行里没有任何痕迹。** 它不是「藏起来了」，它是**被移到了另一行**：`load` 的 `order`。
>
> 而这正是「**抽象的价值与泄漏是同一件事**」的字面版本：**你之所以能只写 `a * b`，是因为编译器替你记住了「谁在哪一维上」。当它的记法与你的提示不一致时，这份「记住」就变成了共享内存往返。**
>
> 本域主线的推论说「代价通常藏在**别处**」——在这一篇里，那个「别处」的具体坐标是：**`order` 参数、以及 layout 转换的插入点**。`04-reduction-cost` 会指出另一个坐标：**`wpc[axis]`**。

## 6. 小结与延伸

- ★★ **两次 `load` 只差一个 `order`**：输出**逐位相同**（16384 个元素），代价从 **0 / 0 B** 变成 **2 barrier / 131072 B**。**载体是一个离得很远的关键字参数。**
- ★★ **`trans` 免费 ≠ 归约变便宜**：转置后布局参数逐项等于 `Lrow`，而代价完全对称（`ops 82432 vs 82432`、`smem 4096 B vs 4096 B`、`barriers 2 vs 2`）。想省跨 warp 相位，**只能改 `load` 的 `order`**。
- ★★ **代价模型不能退化成「转换一律昂贵」**：`(64,2)` 的那一对属主逐位相同、寄存器编号不同 ⇒ **0 B / 0 barrier**（官方锚点 `G3` 的 `which is free`）。**两个方向的错改都会被抓住**（`C.2`/`C.2b`）。
- ★ **同一次转换，两个口径两个交叉点**：barrier `K*=2`、字节 `K*=64`。**「值不值」在模型里不是一个数**——要变成一个数，得先声明 barrier 与字节怎么换算，而那层换算本模型没有给。
- ★ **官方出处的唯一性**：主 tutorial 里 `coalesc` / `Layout conversions` / `warp` 全是 **0** 次，只有 Gluon「Tensor Layouts」页有（5 / 1 / 73）。**官方教 Triton 的材料里没有这一课。**
- ★ **`G5` 末词的 `reeduction` 是官方页面的拼写错误**，本仓库**逐字保留**——把它「修好」会让 `A.5` 与 `make anchors` **同时**失败。
- ★ **本模型有一条已记录的简化**：`spt×tpw×wpc == shape`（`C.5` 直接拒绝非精确切分），真实 Triton 允许覆盖不足（官方第一个例子在 128×128 上只覆盖 1×128）。
- ★ **元检验对本篇的意义**：注入 **D2**（转换判成免费）/ **D3**（跨 warp 相位被抹掉）/ **D5**（lane 摊到错的维上）后，本篇**必须**失败——本机跑出：三者都退出 1。

**延伸**：

- 归约三相的完整代价表与 `wpc[axis] > 1` 这条判据：`30-gpu-programming/triton/04-reduction-cost`。
- 合并访存在硬件上为什么快：`20-gpu-architecture/memory-system/02-coalescing-and-cache-line`。
- 共享内存 bank 冲突的机制（本篇只把共享内存当「一次往返的通道」，不推导 bank）：`20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`。
- Triton 代码在编译流水线里的位置（本篇**不讲**编译器内部架构）：`60-compilers/inductor/03-codegen`。
- 本主题的第一篇（属主由编译器决定）：`30-gpu-programming/triton/01-block-program-model`。
