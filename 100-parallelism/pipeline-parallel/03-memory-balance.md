# 各流水线级的负载均衡：流水线的吞吐由最慢的那一级决定

> ★★ **一句话**：流水线一旦切成 `p` 个**流水线级**，**总时间就是 `max(各流水线级的负载)`** —— **不是 `mean`**。
> 于是「切得匀不匀」直接变成吞吐：实测 `[130, 100, 100, 130]` 的效率是 **`0.8846`（损失 `11.54%`）**。
> ★★★ **而把一个 transformer 切到 `p` 个流水线级，天然就不匀** ——
> **首尾两级各多一份 embedding / lm_head** ⇒ **瓶颈恒在 `0` 或 `p−1`**（把 embedding 去掉就变匀）。
> **第二笔账是 `L % p != 0`**：层数分不尽时，每级差一层；★ 而**`p` 越大，同样的余数摊出的相对波动越大**。

## 0. 背景与动机

[01](01-microbatches-and-bubbles.md) 与 [02](02-schedules.md) 算的是**时间轴上的空闲**。
本文算的是**另一笔账**：**同一时刻，`p` 级各自要干多少活**。

**为什么它是独立的第三笔账**：

- **气泡**是「有人在等」；
- **负载不均**是「有人干得多、有人干得少，而大家要一起结束」——
  ★ **即使气泡为 0，这一笔账仍然存在**。

★★ **而它的后果与气泡**不同：气泡是**时间**开销（可以被 `m` 稀释），
负载不均是**吞吐**开销（★ **加 micro-batch 不能缓解它** —— 每一级都要多干那一份）。

**一个最小的例子**：12 层切 4 个流水线级、每级 3 层 ⇒ 负载 `[30, 30, 30, 30]`（匀）。
但**首尾两级还要各自扛一份 embedding / lm_head** ⇒ `[130, 30, 30, 130]` ——
★ **瓶颈出现在两头，效率掉到 `0.6154`**（★ **订正 2026-10-08**：原写 `0.8846` ——
那是**另一组**负载 `[130, 100, 100, 130]` 的效率，**两个向量被并成了一个**；
`[130,30,30,130]` 的 `mean/max = (320/4)/130 = 80/130 = 0.6154`）。

## 1. 原理

### 1.1 ★★★ 总时间的口径：`max`，不是 `mean`

流水线的**稳态吞吐**由**最慢的那一级**决定：

```text
总时间 = max(各流水线级的负载)        （★ 不是 mean）
效率   = mean / max  ≤ 1
```

**本机实测**（`code/03_balance.py` 的 `A.2`）：

| 负载向量 | `max/mean` | 效率 `mean/max` | 损失 |
|---|---|---|---|
| `[130, 100, 100, 130]`（首尾重） | `1.1304` | **`0.8846`** | **`11.54%`** |
| `[100, 100, 100, 100]`（完美匀） | `1.0000` | **`1.0000`** | `0.00%` |
| `[130, 100, 100, 130, 100]`（5 级） | `1.1607` | **`0.8615`** | `13.85%` |

★ **「效率」这个量的定义就是 `mean/max`** —— 因为**理想时间**是 `mean`（大家并行、齐头并进），
**实际时间**是 `max`（最慢的那个定调）。

> ★★ **一处同名不同指（必须写明）**：本文的**「总时间」**指的是
> 「**一个 batch 走完一遍**时，**最慢那一级**要干的活」—— **稳态口径**（每一级都要干 `m` 遍）。
> ★ 它与 [01](01-microbatches-and-bubbles.md) 的**「总时间」不是同一个量**：
> 那里是**时序口径**（`(m+p−1)·(t_f+t_b)`，含头尾的填满/排空）。★ 两者只在
> 「**每个流水线级的负载**」这一笔账上对齐（那一笔与 `m` 无关）。

★★★ **`A.1` 的两侧都要**：`总时间 == max`（**4 组**）**且**「均衡时它降到 `mean`」——
★ 只写前半句的话，一个「`总时间 = mean + 常数`」的错实现也能通过。

### 1.2 ★★★ 切不匀的第一个来源：首尾的 embedding / lm_head

一个 transformer 的**第一级**要装 embedding（把 token id 变成向量），
**最后一级**要装 lm_head（把向量变回 logits）。★ 这两块**不在任何层里**，
但它们**占着首尾两级的负载**。

**本机实测**（`C.1`，`L = 12, p = 4`）：

| | 负载 | 瓶颈在哪 |
|---|---|---|
| **带 embedding** | `[130, 30, 30, 130]` | ★ **流水线级 `0` 与 `3`**（两个） |
| **去掉 embedding** | `[30, 30, 30, 30]` | ★ **没有瓶颈**（全同） |

⇒ ★★★ **「瓶颈恒在首尾」不是一句定性的话，它有一个可证伪的后果**：
**去掉 embedding 就变匀**。
★ 而 `C.2` 把它做得更细：**只给流水线级 `0` 加 embedding** ⇒
**瓶颈的【个数】从 `2` 变成 `1`**（★ `max` 相同、**个数不同**）。

★ **顺带的第二笔**：**首尾两级的【显存】也多**（embedding 的激活与 lm_head 的 logits
通常比一层 transformer 的激活大得多）⇒ **首尾是瓶颈，既在算力上也在显存上**。

### 1.3 ★★ 切不匀的第二个来源：`L % p != 0`

层数**分不尽**时，各流水线级的层数差 `1` ⇒ 负载差 `1` 个层的当量。

**本机实测**（`B.1`/`B.2`，`LAYER_COUNT_GRID` 四组）：

| `L` | `p` | 每级层数 | 负载 | `max/mean` |
|---|---|---|---|---|
| `12` | `4` | `[3, 3, 3, 3]` | `[30, 30, 30, 30]` | `1.0000`（**整除，匀**） |
| `13` | `4` | `[4, 3, 3, 3]` | `[40, 30, 30, 30]` | `1.2308` |
| `12` | `5` | `[3, 3, 2, 2, 2]` | `[30, 30, 20, 20, 20]` | `1.2500` |
| **`12`** | **`8`** | **`[2, 2, 2, 2, 1, 1, 1, 1]`** | **`[20, 20, 20, 20, 10, 10, 10, 10]`** | **`1.3333`** |

★★★ **最坏的一组是 `L=12, p=8`，不是 `L=12, p=5`** —— 这一点不直观，但**可解释**：

> **`p` 越大 ⇒ 每级分到的层数越少 ⇒ 同样的「差 1 层」占的比例越大。**
> `p = 5` 时是 `3 : 2`（差 `50%`），`p = 8` 时是 `2 : 1`（**差 `100%`**）。

★★ **这与 `expert-parallel` 的「EP 度越大 ⇒ 负载越不均」是同一个机制**（见 [../expert-parallel/02-load-imbalance](../expert-parallel/02-load-imbalance.md)）：
**并行度越高，每一份越小，波动越难被平均掉**。

★ **每级负载的【最大/最小】之比随 `p` 变**（**不是常数**，`code/03_balance.py` 实测，`L=12`、带 embedding）：
`p = 4` → `4.333333`、`p = 8` → `12.000000` ⇒ ★ **引这个比值必须带 `p`**。

> ★★ **一处口径必须写清**（订正 2026-10-08）：这里的 `4.3333`/`12.0000` 是 **`max/min`**，
> 与 §1.1/§1.3 表里的 **`max/mean`**（如 `1.3333`）**不是同一个量**。
> ★ 原先这里写的是 `p=4 → 1.083333`、`p=8 → 1.250000` —— **那两个数出自 `probes/probe_100g.py`
> 的 `G5`**，用的是**另一套模型**（`per_layer = 4·b·s·h`、embedding ≈ **0.25 个层当量**），
> **与本文的 `BALANCE_*` 不是一回事**（★ 它们也不是 `03_balance.py` 的输出）。
> 现在改成引**本文配套程序**的数。

### 1.4 ★★ 为什么这一笔账**不能**靠加 micro-batch 缓解

[01](01-microbatches-and-bubbles.md) 里气泡可以被 `m` 稀释（气泡占比精确是 `(p−1)/(m+p−1)`，
★ **只在 `m ≫ p` 时才近似 `∝ 1/m`** —— 订正 2026-10-08：原写「`∝ 1/m`」不精确）。
★ **负载不均不行**：每一级都要把它那份活干 `m` 遍 ⇒ **比值 `max/mean` 与 `m` 无关**。

⇒ ★★ **两笔账的正交性**：

| 账 | 由什么决定 | 怎么缓解 |
|---|---|---|
| **气泡** | `(p, m)` | **加大 `m`**、或 interleaved |
| **负载不均** | `(L, p, embedding 的归属)` | **改层的划分**（如把首尾的层数调少） |

### 1.5 ★★ 与「重算」的关系：**只引，不重写**

PP 里常用**重算**来压首尾那一级偏高的**显存**（把激活丢掉、反向时再算一遍）。
★ 而**重算换显存的【机制】**（`O(√n)` 内存 vs `≈2n` 前向次数、最优检查点数）**不在本文** ——
正文在 `90-training/autograd-and-backward/02-gradient-checkpointing.md`（**此处回链**）。

★ 本文**只引原文的那一句**（`specs.GPIPE_RECOMPUTE_MEMORY_QUOTE`）：

> `peak activation memory requirement is reduced to` `O(N + (L/K)×(N/M))`

★ **常量只取到 `…reduced to` 为止**（那个公式 `O(...)` 在 ar5iv 上是 `<math>` ⇒ **跨标记，常量不含它**；
它的形式由上文照抄、并在 `specs.py` 的口径注里写明）。

⇒ 它的作用是**说明「重算压的是【激活】那一项」** —— ★ 这正是首尾两级显存偏高的那一项。
★ **至于怎么压、压多少，本文一行都不写**。

## 2. 执行映射

### 2.1 本机构造的模型

`code/03_balance.py` 只做两件事，**且两者互相独立**：

| 步骤 | 是什么 | 独立性证据 |
|---|---|---|
| **分层** | 把 `L` 层**尽量均匀**分给 `p` 级（`L % p` 时前 `L%p` 级各多 1 层） | `D.2`（**源码级线索**）：`assign_layers()` 里**不调用**任何汇总函数（`max`/`min`/`sum`/`sorted`…，**AST 级**） |
| **负载** | `层数 × BALANCE_PER_LAYER`，**首尾各加一份 embedding 当量** | 见下 |

★★★ **本模型是【演示用】的，它的两个取值都不是真实比例**：

- `BALANCE_PER_LAYER = 10`（每层当量）；
- `BALANCE_EMB = 100`（embedding 当量）—— ★ **取 `10 ×` 是为了让效应显著**。

> ★★ **真实模型的 embedding 与层负载比【不是 10】** ⇒
> 本文的**比值**（`1.2500` / `1.3333` 等，见 §1.3 表）是**这组设计取值下的**，
> **不得**当作「真实模型的负载不均有多大」。★ 可引用的是**结构**（瓶颈在首尾、`p` 越大越不均）。

### 2.2 与 `expert-parallel` 的对照

`expert-parallel/02` 讲的是**专家级**的负载不均（路由是**数据依赖**的 ⇒ 每次都可能不同）。
★ 本文的负载不均是**静态**的（由 `L`、`p`、embedding 的归属**算得出来**，与数据无关）。
⇒ ★ 两者**机制不同**（一个统计、一个代数），但**后果同构**（都是 `max/mean` 那一笔）。

## 3. 实现与演进

### 3.1 三种「把首尾的账摊平」的做法

| 做法 | 一句话 | 代价 |
|---|---|---|
| **首尾少放层** | 给首尾两级各少分几层（把 embedding 的当量抵掉） | ★ 层数的分配不再是「尽量均匀」⇒ **中间级更重**（要重新平衡） |
| **把一个层拆开** | 把首尾的层切到两级上 | ★ 引入了**切层内部的通信**（那接近 TP 的形态） |
| **只重算首尾** | 首尾用重算压显存（★ 算力上仍不均） | ★ 只解决**显存**那一半，吞吐仍由 `max` 决定 |

★ 三者的共同点：**都承认「`max` 定调」这个事实**，区别是**在哪一侧付账**。

### 3.2 与 `performance-models/02` 的分工

`10-foundations/performance-models/02-amdahl-and-scaling.md` 写的是**多机扩展**的两个天花板
（`1/s` 与 `2S/BW`）。★ 本文写的是**切层之后**的那笔账，**两者不是一个东西**。

★ 但有一条**结构上同源**：那里「**一个与规模无关的常数项决定了上限**」，
★ 这里「**一个由 `L mod p` 与 embedding 归属决定的比值决定了吞吐**」——
⇒ ★★ **两处都是「有一个不随你加资源而消失的项」**。

## 4. 踩坑与失败模式

### 4.1 ★★★ 用 `mean` 报吞吐

- **现象**：算「`p` 级流水线的总时间 = 总负载 / `p`」。
- **成因**：★ 那是**理想时间**，而实际由**最慢的一级**定调。
- **规避**：**总时间 = `max(各流水线级的负载)`**；效率 = `mean/max`（实测 `[130,100,100,130]` ⇒ `0.8846`）。

### 4.2 ★★ 说「层数分不匀是 `L % p != 0` 的锅，`p` 越小越严重」

- **现象**：以为 `p` 接近 `L/2` 时最坏。
- **成因**：★ **反了** —— **`p` 越大、每级越少、相对波动越大**（实测最坏是 `p = 8`：`2 : 1`）。
- **规避**：把 `max/mean` **对每组 `(L, p)` 真的算一遍**（`B.2` 断言最坏是 `(12, 8)`）。

### 4.3 ★★ 忽略了首尾的 embedding

- **现象**：算完「每级 `L/p` 层」就收工，得到「很匀」的结论。
- **成因**：embedding / lm_head **不在层里**，但**占着首尾的负载**。
- **规避**：★ 把「embedding 归属」变成**可变化的量**：带它 ⇒ `[130,30,30,130]`（**两个瓶颈**）；
  只给一端 ⇒ `[130,30,30,30]`（**一个瓶颈**）⇒ `C.1`/`C.2` 钉住这个**变化**。

### 4.4 ★★★ 守卫选成「层数倒序」（恒真的守卫）

- **现象**：为了验证「瓶颈在首尾」这条断言能失败，把层数顺序**倒过来** ——
  ★ **比值完全不变**，因为 `stage_loads` 给**首尾都加** embedding ⇒ **倒序不改变任何东西**。
- **成因**：守卫选的错法**不改变被判量**（★ 与 [01](01-microbatches-and-bubbles.md) 的 §4.3 同款）。
- **规避**：换成**「embedding 的归属」**（`C.2`）：带两端 ⇒ `2` 个瓶颈、只带一端 ⇒ `1` 个 ⇒ **真的会变** ✓
- ★★ **这条坑在本域出现了两次**（`01` 的对调 `t_f/t_b`、本文的层数倒序）⇒
  **守卫的选法本身要过一遍「它改变被判量了吗」**。

### 4.5 ★ 把本文的比值当真实比例

- **现象**：引用「PP 的负载不均是 `1.33` 倍」并外推到真实模型。
- **成因**：`BALANCE_EMB = 10 × BALANCE_PER_LAYER` 是**本库的设计取值**。
- **规避**：★ 只引用**结构**（瓶颈在首尾、`p` 越大越不均），**不引用比值**。

## 5. 判据表

| 可机械判定的条件 | 结论 |
|---|---|
| 报 `p` 级流水线的总时间 | **`max`(各流水线级的负载)**；★ 均衡时才等于 `mean`（★ 两侧都要断言：均衡相等**且**不均衡不等） |
| 报「效率」 | `mean/max`；★ 实测 `[130,100,100,130]` ⇒ `0.8846`（损失 `11.54%`）；`[130,30,30,130]` ⇒ `0.6154` |
| 层数分不尽（`L % p != 0`） | 各流水线级的层数**最多差 1**；★ 断言「层数之和 `== L`」是**独立的**另一条 |
| 要判「哪一组最坏」 | ★ **`p` 越大越坏**（实测最坏 `L=12, p=8`：`2 : 1`）—— **不是** `p ≈ L/2` |
| 一个 transformer 切 `p` 级 | ★ **首尾各多一份 embedding / lm_head** ⇒ **瓶颈恒在 `0`/`p−1`**；去掉 embedding 就变匀 |
| 想验证「瓶颈在首尾」这条断言能失败 | ★ **不能**用「层数倒序」（恒真）；要用 **embedding 的归属**（两端 ⇒ 2 个瓶颈、一端 ⇒ 1 个） |
| 报「每级负载的最大/最小之比」 | ★ **必须带 `p`**（实测 `p=4 → 4.3333`、`p=8 → 12.0000`，**不是常数**；★ 这是 `max/min`，与表的 `max/mean` 不是同一个量） |
| 想说「加 micro-batch 能缓解负载不均」 | **错** —— 每一级都要多干那份活 ⇒ **比值与 `m` 无关**（与气泡正交） |
| 想算「首尾的显存怎么办」 | ★ 可以引重算，但**只引它压的【激活】那一项**；机制在 `90-training/autograd-and-backward/02` |
| 引用本文的比值（`1.2500` / `1.3333`） | ★★ **不行** —— 它们是**本库设计取值**（`BALANCE_EMB = 10×`）下的；**只引结构** |

## 6. 小结与延伸

**一句话**：切完 `p` 级之后，**吞吐由最慢的那一级定调**；
★ 而「切成 `p` 级」本身就制造了不匀（**首尾的 embedding** + **`L mod p`**）。

**三条可独立复用的结论**：

1. **总时间 = `max(各流水线级的负载)`** —— 实测 `[130,100,100,130]` 的效率 `0.8846`（损失 `11.54%`）；
2. **瓶颈恒在首尾**（embedding / lm_head），★ 且**去掉它就不匀消失** —— 这是可证伪的；
3. **`p` 越大、不匀越严重**（实测最坏 `L=12, p=8`）——
   ★ 与 `expert-parallel` 的「EP 度越大越不均」**同构**。
