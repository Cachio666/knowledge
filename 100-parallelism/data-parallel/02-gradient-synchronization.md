# 数据并行的梯度同步（梯度分桶：与参数对齐）

> **梯度规约不需要「一整张张量就绪」才能开始 —— 它可以分段搬。**
> ★★ 于是一个工程问题出现了：**怎么切这些段（桶）**。答案只有一条 ——
> **划分必须【完备且不重叠】**。**漏一个桶** ⇒ 那部分梯度不参与规约 ⇒ **各卡发散**；
> **重叠一个桶** ⇒ 那部分被**重复计数**，在求和口径下变成 **`N` 倍**（本机 `7.999999`）。
> ★★★ 而最自然的「分桶后的结果 == 单桶的结果」这条判据**是恒真的**（纯搬运）
> —— **它一条信息都没有**，本文的核心判据是**完备性**，不是等价性。

## 0. 背景与动机

### 一个具体的对照场景

`Ψ = 192` 个参数的梯度要规约。最朴素的写法是**把整张梯度张量发给集合通信**，
等它回来再更新。

问题在于**什么时候能发**：反向传播是**从后往前**算的，最后一个参数的梯度**最先**就绪，
而第一个参数（比如 embedding）的梯度**最后**才就绪。若必须等**全部**就绪，
那么**第一个就绪的梯度要白白等一整轮反向**。

**梯度分桶**就是解这一刀：把 `Ψ` 个参数切成若干**桶**，**某一桶的梯度全就绪了就可以发**。
本机玩具规模（`N = 8`、每卡 `8` 行、`Ψ = 192`、**fp32**）的三种切法：

```
1 桶：       [0 ....................................... 192)     峰值缓冲 768 B
8 桶等分：   [0 24) [24 48) ... [168 192)                        峰值缓冲  96 B
48 桶：      每桶 4 个元素                                         峰值缓冲  16 B
```

★ 桶越小，**通信能越早发起**、**峰值缓冲越低** —— 但**发起次数越多**。
★★★ **而这一切的前提是：桶的划分必须【完备且不重叠】**。这一条不是风格问题：

| 坏法 | 后果 | 本机实测 |
|---|---|---|
| **漏一个桶** | 那部分梯度**根本没参与规约** ⇒ 各卡保留各自的本地值 ⇒ **副本发散** | 漏掉段跨 rank 极差 **`2.392e-01`**（已同步段 `0.000e+00`） |
| **重叠一个桶** | 那部分被**重复计数**（`SUM` 口径下 ⇒ **`N` 倍**） | 该元素 **`7.999999`** 倍（`N = 8`） |
| **端点错一位** | **恰好一个元素**被重复计数 —— **不报错、不崩** | 不同的元素 **`1`** 个（下标 `[95]`） |

## 1. 原理

### 1.1 ★★ 为什么「分段搬运」是合法的：文档里的两段式分解

[B] NCCL 2.31.2 的用户指南在 `AllGather` 一节逐字写着：

> `Executing ReduceScatter, followed by AllGather, is equivalent to the AllReduce operation.`

★★ **这一句是「桶」的合法性来源**：all-reduce **本来就可以**被拆成
「先在每段上做归约（reduce-scatter）、再把结果拼回来（all-gather）」两步 ——
**桶不过是把这两步的颗粒度调到「段」这一级**。
★★★ **而这两个阶段的算法与复杂度（`V(N) = 2(N−1)/N × S`、饱和）不在本主题**
⇒ 回链 `110-communication`（域 README 的「本域不做什么」表第一行）。

★ 另一条同样重要的逐字语义（[B] NCCL）：

> `The AllReduce operation performs reductions on data (for example, sum, min, max) across devices and stores the result in the receive buffer of every rank.`

⇒ **结果写回每一张卡** ⇒ 分桶之后**每张卡各自**持有一份完整的、已规约的梯度
（这是 §1.3 那三种坏法能**同时**在各卡上看到的原因）。

### 1.2 ★★ 判据 ①：完备且不重叠 ⇒ 两个后果

设 `local` 是 `N × Ψ` 的矩阵（每行是一张卡的本地梯度），`{B_k}` 是一个桶划分。
本程序用的模型是**逐桶 in-place 归约**（与真实系统的 `SUM` 语义一致）：

```
out ← local                                # 缓冲初值 = 本地梯度
for (lo, hi) in 桶:                        # 桶【依次】发生
    out[:, lo:hi] ← Σ_rank out[:, lo:hi]   # ← 注意右端读的是 out，不是 local
out ← out / N                              # 统一除以 N（01 的口径）
```

**若划分完备且不重叠**，每个元素被归约**恰好一次**，于是：

| 结论 | 本机实测 |
|---|---|
| **每个元素在所有 rank 上完全相同**（跨 rank 极差 `max−min` == `0.0`） | **`0.000e+00`**（1 桶 / 8 桶 / 不等分 3 桶，全部） |
| 结果与**单卡大 batch** 的梯度一致 | `max|diff| = 6.147e-08`（`g` 量级 `0.280`，**fp32** 的机器精度档） |

★★★ **这里有一处必须写明的反例（本域的头号错误模式）**：最自然的写法
「**分桶后的结果 == 单桶（不再分桶）的结果**」**在这台机器上是恒真的**：
本机实测**三种划分（`1` 桶 / `8` 桶等分 / 不等分 `3` 桶）下的结果与「不再分桶」逐位相同**
（`max|diff| = 0.000e+00`）——
因为分桶**只是把同一批加法按另一种顺序分段**，而本程序里每个元素在桶内的加法顺序
与单桶时**完全相同**。⇒ **它只重述了「分桶是纯搬运」这个定义，一条信息都没有**
（本域的 `D22`：纯搬运型切分的等价性判据恒真）。
★ 本程序把这件事**打印出来**（`A.1` 里那一行 `与不再分桶的结果逐位相同 = True`），
**而不是把它当判据用**。

★★ **A 类判据的落点因此改在「完备性」上**，方向是**双向**的：

1. **完备且不重叠 ⇒ 极差为 `0` 且与单卡大 batch 一致**；
2. ★★★ **把划分改坏（漏一个桶 / 重叠一个桶）⇒ 同一个谓词必须失败**
   —— 这是 `CONTRIBUTING:235` 的守卫，也是本域对抗「模拟器同时是被测对象」（`P12`）的
   标准落法：**判据的信息量在 [2] 这一半**。

### 1.3 ★★★ 三种坏法的机制

**(a) 漏一个桶。** 未覆盖的元素**保持缓冲初值**（= 本卡的本地梯度）⇒
**各卡不再持有同一个梯度**。下一步 `w ← w − lr·g` 之后，**每个 rank 的参数都不同**
（副本发散）。本机：漏掉段跨 rank 极差 **`2.392e-01`**，而**已同步段 `0.000e+00`**
（⇒ 局部的、**可定位**的错误）。

**(b) 重叠一个桶。** 桶**依次**发生，第二次归约读到的是**已经归约过的值**
（每个 rank 上都是 `Σ`）⇒ 再求和一次 = **`N × Σ`**，最后统一除以 `N`
⇒ 那部分变成 **`N × 均值`**。本机：**`7.999999`**（`N = 8`）。

★★ **这一条依赖 `SUM` 口径**：若归约运算本身是 **average**，重叠就**没有后果**
（幂等）。⇒ **「重叠是错的」这句话的成立条件是 `ReduceOp.SUM`** ——
而 [B] PyTorch 2.14 的 `all_reduce` 默认值正是 `ReduceOp.SUM`
（逐字 `op: _ReduceOp = ReduceOp.SUM`）。

★ 还要注意 **重叠的两个后果与漏桶不同**：重叠时**各卡仍然一致**（本机极差仍 `0.000e+00`），
**所有副本一起朝错的方向走** —— 比漏桶**更隐蔽**（没有发散可以观测）。

**(c) 端点错一位。** 两个桶写成 `[0, 96)` 与 `[95, 192)`（差一位）⇒
**恰好一个元素**（下标 `95`）落进两个桶 ⇒ 本机实测**只有 `1` 个元素不同**。
★★ **它不报错、不崩、不发散**：桶的边界错位是**静默**的 ——
这正是「完备且不重叠」必须被**断言**、而**不能被指望**的原因。

### 1.4 ★ 桶的**大小**是自由的（判据 ②）

「完备且不重叠」**不要求各桶等大**。本机用一个**不等分**的划分
`[100, 60, 32]`（`Σ = 192 = Ψ`）实测：跨 rank 极差 **`0.000e+00`**、
与单卡大 batch 的差 `6.147e-08` —— **与等分划分完全同档**。

⇒ **桶的划分是「完备性」约束下的实现自由**：这正是 §3 的立足点
（为了峰值缓冲与**参数张量边界的对齐**去调桶的边界，是**允许**的）。

## 2. 执行映射

### 2.1 桶在真实系统上换到了什么

| 量 | 与桶数的关系 | 本机实测（`Ψ = 192`、**fp32**） |
|---|---|---|
| **峰值缓冲** | `= 最大桶的元素数 × itemsize` ⇒ 与桶数**成反比** | `1` 桶 → **`768 B`** · `8` 桶 → **`96 B`** · `48` 桶 → **`16 B`** |
| **通信启动次数** | `= 桶数` | `1 / 8 / 48` 次（★ 接口级） |
| **每次搬的元素数** | `= Ψ / 桶数` | `192 / 24 / 4`（★ `启动次数 × 每次元素数 == Ψ` 是**整数恒等**） |

★★ **「峰值缓冲」这一项是可算的、也是可判定的**（本程序的 `B.1`）：
`峰值 × 桶数 == Ψ × itemsize`（本机 `768 × 1 == 16 × 48 == 768`）。

### 2.2 ★★★ 一处**必须不给判据**的地方：通信能藏多少

桶的意义是让「某段梯度就绪就发」—— **它值多少**取决于**通信与计算的重叠**。
★★★ **那件事在本主题的形态下没有可跑的判据**：

- 通信-计算重叠需要**两个可以并行推进的时间轴**（通信引擎 + 计算引擎），
  本机**没有**（单进程、没有 NCCL、没有真实网络）；
- 硬写一条「桶数越多、暴露在外的通信越少」的判据，等于
  **要求实现者复现一个跑不了的东西**（本库的 `P3`）。

⇒ **本主题只写接口**：*桶的作用是让通信能尽早发起；桶数 `k` ⇒ 启动 `k` 次、
每次搬 `Ψ/k` 个元素*。**「能藏多少」的正文在 `110-communication` 的 `overlap` 主题
（未建成），此处回链。** ★ 本程序的 `B.2` 只断言那条**接口级的整数恒等**，
**不给任何关于重叠收益的判定**。

### 2.3 桶的边界与参数张量的边界

「梯度怎么与参数**对齐**」这句话有两层意思：

1. **形状上的对齐**：每个参数张量的梯度与它自己的形状一致（本程序用扁平化的
   `Ψ` 维向量表示，这是实现细节，不改变语义）；
2. **桶边界上的对齐**：桶的边界**尽量落在参数张量的边界上** ——
   一个桶**跨越两个参数张量**在语义上**完全合法**（§1.4 已证：桶的大小是自由的），
   但它会让「某个参数**完全**就绪」这个条件**不再与某个桶的边界重合**
   ⇒ 「某桶就绪就发」能覆盖到的**参数粒度**变粗。

★ **这一层是工程取舍，不是正确性约束**：本程序判据里**没有**「桶必须对齐参数边界」
这一条 —— 因为它**不可证伪**（跨越张量的桶**仍然正确**，只是择时没那么细）。
⇒ 本文只把它写成**取舍**，不写成判据（`CONTRIBUTING:399` 的「可证伪性」要求）。

## 3. 实现与演进

| 阶段 | 做法 | 它换来了什么、付了什么账 |
|---|---|---|
| **整张梯度一次规约** | 一个 `all_reduce` 覆盖全部 `Ψ` | 最简单；★ 必须等**全部**梯度就绪 ⇒ 反向的最后一段被卡住；★ 峰值缓冲 = `Ψ × itemsize` |
| **梯度分桶** | 切成 `k` 个桶，逐桶规约 | ★ 换到**更早发起**与更低的峰值缓冲；★★ 代价是**划分必须完备且不重叠**，而这个错误**是静默的**（§1.3） |
| **桶大小 / 边界调优** | 桶**不必等大**（§1.4），边界尽量对齐参数张量（§2.3） | ★ 把「就绪」的粒度做细；★ 代价是**配置项**增加，而**完备性**从此是**配置的责任**（⇒ 判据必须跟着进测试） |
| **（本文不写）通信-计算重叠** | 双缓冲、分块流水、异步发起 | ★ 这才是桶真正买到的东西 —— **正文在 `110-communication` 的 `overlap`**，本主题**只留接口** |

★ 演化方向很清楚：**桶把一个「正确性由数据结构保证」的问题，
换成了一个「正确性由配置保证」的问题** —— 而配置是**可以被改错的**。
这就是为什么 §5 的判据表里，**前四行全部在守「完备且不重叠」**。

## 4. 踩坑与失败模式

**① ★★★ 漏一个桶。**
- **现象**：训练**不报错**，但 loss 曲线与单卡不一致；**各卡的参数慢慢分叉**。
- **成因**：未覆盖的元素保持**本地梯度**（缓冲初值）⇒ 只有**一部分**梯度被规约了。
- **规避**：把「完备性」写成一条**可执行的谓词**：`Σ(桶的跨度) == Ψ` 且桶两两不交；
  ★ 并在**真跑**里量「跨 rank 极差 == 0」（本程序 `A.1`/`C.1`）。

**② ★★ 重叠一个桶。**
- **现象**：那部分梯度变成 **`N` 倍**，而**各卡仍然一致**（没有发散可以观测）。
- **成因**：桶**依次**发生，第二次归约读到的是**已经归约过的值** ⇒ `N × Σ`；
  在 `SUM` 口径下这就是**重复计数**。
- **规避**：把重叠也纳入完备性检查（`Σ(跨度) == Ψ` **且**桶两两不交 ——
  注意 `Σ(跨度) == Ψ` **推不出**「完备且不重叠」：取 `[0, 96)` 与 `[95, 191)`，
  两段跨度都是 `96` ⇒ `Σ = 192 = Ψ`，但它**既重叠了一个元素（`95` 被算两次）
  又漏掉了一个元素（`191` 没被覆盖）** ⇒ ★★ **完备性与不重叠必须分别检查**，
  不能靠「跨度之和等于 `Ψ`」这一条代替；本程序的 `PLAN_OVERLAP` 就是这条判据的靶子）。

**③ ★★ 端点差一位。**
- **现象**：**恰好一个元素**错，其余全对（本机 `1` 个元素，下标 `[95]`）。
- **成因**：桶的边界写成了 `[0, 96)` 与 `[95, 192)`（第二段从 `95` 起）。
- **规避**：把划分**当成数据**（本程序把五种划分写成模块级常量 `PLAN_*`）
  ⇒ 它可以被**变异测试**逐端点地改动，每改一个端点都必须有断言失败
  （本主题的 `make mutate` 正是这么做的）。

**④ ★★★ 用「分桶后的结果 == 单桶的结果」当 A 类判据。**
- **现象**：判据**永远通过**，看起来很稳。
- **成因**：那是**纯搬运** ⇒ 本机实测**四种桶数全部 `max|diff| = 0.000e+00`**
  （逐位相同）⇒ 它只重述了定义（本域 `D22`）。
- **规避**：A 类必须落在**改变了求值顺序**或**可被证伪的谓词**上 ——
  本例是「完备性」（`漏/叠 ⇒ 必须失败`）。

**⑤ ★ 把「桶必须与参数张量边界对齐」写成判据。**
- **现象**：写了一条通不过、也证伪不了的检查。
- **成因**：跨张量的桶**仍然正确**（只是择时粒度变粗）⇒ 它**不是**正确性约束。
- **规避**：写成**取舍**（§2.3），不写成判据；判据只保留「完备且不重叠」这一条。

## 5. 判据表

> ★ 本表是**闭合的**：每一行都是「**可机械判定的条件 → 结论**」，读完能照着做判断。
> 全部数值为**本机实测值**（`code/02_grad_sync.py` 的 `make run`，
> `python3 3.13.5` + `numpy 2.4.4`、macOS arm64、**无 GPU/无多卡/无 NCCL**）。
> ★★ **口径**：`N = 8`、每卡 `8` 行、`Ψ = 192`、梯度 **fp32**；

> **被归约的轴 = rank 轴**（桶内的参数轴只被切片）· **除法的位置 = 全部桶做完后统一除以 `N`**。

| 可机械判定的条件 | 结论 |
|---|---|
| 划分**完备且不重叠**时，每个元素的**跨 rank 极差** | **`0.000e+00`**（1 桶 / 8 桶等分 / 不等分 3 桶全部） |
| 划分**完备且不重叠**时，与**单卡大 batch** 的差 | `6.147e-08`（`g` 量级 `0.280`）⇒ **机器精度档** |
| 划分**完备且不重叠**时，与**不再分桶**的结果 | ★★ **逐位相同**（`0.000e+00`；`1` 桶 / `8` 桶等分 / 不等分 `3` 桶**三种划分都是**）⇒ **这一句是恒真的，不能当判据**（`D22`） |
| 桶**必须等大**吗 | **不必**：不等分的 `[100, 60, 32]` 同样给出极差 `0.000e+00` ⇒ 划分是**完备性约束下的实现自由** |
| **漏一个桶**（只同步前 `128/192`） | 已同步段极差 **`0.000e+00`**、漏掉段极差 **`2.392e-01`** ⇒ **各卡发散**（下一步参数就不同） |
| **重叠一个桶**（`[0,96)` 与 `[95,192)`） | 该元素 = **`7.999999` 倍**均值（`N = 8`）；★ **各卡仍一致**（极差 `0.000e+00`）⇒ **不靠发散暴露** |
| **端点错一位**（同上） | 与正确值不同的元素**恰好 `1` 个**（下标 `[95]`）⇒ **静默** |
| 重叠的后果依赖什么 | **依赖归约运算**：`SUM` ⇒ 重复计数（`N` 倍）；**average ⇒ 幂等、无后果**。默认值是 `SUM`（[B] PyTorch 2.14 的 `op: _ReduceOp = ReduceOp.SUM`） |
| 桶的**峰值缓冲** | `= 最大桶元素数 × itemsize`：`1/8/48` 桶 ⇒ **`768 / 96 / 16 B`**（`Ψ = 192`、fp32）⇒ `峰值 × 桶数 == Ψ × itemsize` |
| 桶数与通信**启动次数** | `启动次数 × 每次元素数 == Ψ`（本机 `48 × 4 == 192`，整数恒等）★ **接口级** |
| ★★★ **「通信能藏多少」** | **本主题不给判据**（单进程形态下没有可跑的量测）⇒ 只写接口，回链 `110-communication` 的 `overlap` |
| 「桶必须与参数张量边界对齐」吗 | ★ **不是正确性约束**（跨张量的桶仍然正确）⇒ 只作**取舍**，不作判据（`§2.3`） |
| 用 `np.std` 还是**极差**判「各卡是否一致」 | ★★ 用**极差**：`np.std` 在「全同」时仍给一个**非零值**（本机 fp32 `2.980e-08`，来自 `mean` 那一步的舍入）⇒ 判据会被迫加容差、「全同 / 不同」的分界变模糊（本程序 `D.8` 量它） |

> ★ 阈值与口径（`code/02_grad_sync.py` 的 `preflight()` 逐位钉住）：
> `SEED = 20260942`、`N_SYNC = 8`、`PER_RANK_ROWS = 8`、`DIM = 192`、`LR = 0.05`、
> `PLAN_FULL / PLAN_EQ8 / PLAN_UNEQ / PLAN_MISS / PLAN_OVERLAP`（五种划分，逐端点钉住）、
> `BUCKET_COUNTS = (1, 8, 48)`、`PEAK_BYTES_EXPECT = (768, 96, 16)`、
> `TOL_EXACT = 0.0`、`TOL_REL = 1e-6`、`TOL_GUARD = 1e-3`、`TOL_RATIO = 1e-6`。

## 6. 小结与延伸

**一句话**：桶把「规约」从一个**整体动作**拆成**分段动作**，换到更早的发起与更低的
峰值缓冲；★★★ **而它的正确性只有一条约束：划分必须【完备且不重叠】**。
这条约束的三种坏法里，**只有漏桶会发散**（可观测），
**重叠与错一位都让各卡一起朝错的方向走**（静默）——
所以它**必须被断言**，而不能被指望。

- **平均的语义（除数在哪一边、`loss` 的口径）** ⇒ `100-parallelism/data-parallel/01-gradient-averaging.md`。
- **DP 的冗余账（`N` 个副本用 `N × 16Ψ` 存 `16Ψ` 的状态）** ⇒ `100-parallelism/data-parallel/03-redundancy-and-limits.md`。
- **梯度规约的算法与复杂度（ring allreduce、`V(N)`、它的饱和）** ⇒
  `110-communication/collectives`（**未建成**）、`10-foundations/performance-models/02-amdahl-and-scaling.md:209`（**正文在彼**）。
- **通信-计算重叠（桶真正买到的东西）** ⇒ `110-communication` 的 `overlap`（**未建成**，本文只留接口）。
- **集合通信在拓扑上的行为**（bisection 下界、分层） ⇒
  `20-gpu-architecture/interconnect/03-collectives-on-topology.md`（**正文在彼**）。
- ★★ **一处必须写明的让步**：本文的判据**全部**是「本机玩具规模的真跑」
  （`python3 3.13.5` + `numpy 2.4.4`、**无 GPU、无多卡、无 NCCL**）
  ⇒ **不是 NCCL，也不是真机**；**不得支撑关于真实集群性能的结论**。
