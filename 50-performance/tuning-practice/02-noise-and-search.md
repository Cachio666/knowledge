# 噪声下的搜索：把测量噪声加回来，搜索会怎么选错

> **当测量噪声 σ 与配置之间的真实差异同量级时，搜索会稳定地选错，
> 而且「多测几次」不足以救回来 —— 因为**找最小值这个动作本身就系统性地偏向运气好的那次读数**。**
> **本机实测：顶部相邻两个配置的真实差只有 0.12%，而一次真实测量的 σ/中位是 2%–4%；
> 于是 40 次独立搜索里有 **38%** 选错，把预算加倍后仍是 **35%**。**

## 0. 背景与动机

### 0.1 `60` 域**主动冻结**了噪声，把这一块让给了本域

`60-compilers/auto-tuning/code/mini_autotune.py:610-612` **逐字**：

```python
# ★ 冻结：本迷你地形**关闭测量噪声**。真实调优里 do_bench 的中位数本身有抖动，
#   把它加进来会让「模型误导搜索」与「测量噪声」两件事混在一起，无法归因。
MEASURE_NOISE = 0.0
```

**这三行是一体的**：单看 `MEASURE_NOISE = 0.0` 不知道它为什么被冻结，
单看注释不知道它冻结成了什么。**两件事必须分开归因，所以才需要两篇文档**：
`60` 讲**无噪声**的搜索（搜索空间 / 代价模型 / 四类策略 / regret / Triton autotuner 的默认行为），
**本篇只讲把噪声放回来之后发生了什么**。

### 0.2 一个具体的对照场景

一个 20 个配置的搜索空间，真值由一个二次碗给出（`mini_search.landscape`）：

| 配置 | 相对参考最优的真实差 |
|---|---|
| x=7（参考最优） | 0.000% |
| x=8 | **+0.120%** |
| x=6 | +1.079% |
| x=9 | +1.439% |
| x=5 | +3.357% |

**顶部那两个配置的真实差是 0.12%。** 而同一台机器上，**一次真实测量**（约 0.4 ms 的工作量，
用 `time.perf_counter` 计时）的 **σ/中位 = 2%–4%**。

**⇒ 真实差异比噪声小一个量级。** 在这个条件下，「搜索找最小值」会做什么，就是本篇的全部内容。

> ★ **限定语（本篇强制）**：本篇所有数字都是**本仓库在本机
> （Apple M1 Pro / macOS / `python3 3.13.5` / `numpy 2.4.4`）跑出的**，
> **是 CPU 上的测量，不是 GPU、不是 Nsight Compute**。
> 它们支撑的是「**测量噪声怎么让搜索选错**」这类**机制**结论。

## 1. 原理

### 1.1 「找最小值」在噪声下有**系统性的方向**

设某个配置的**真实**代价是 `θ`、每次测量得到 `θ + ε`（`E[ε] = 0`）。
对同一个配置测 `m` 次取中位，得到一个估计 `θ̂`。搜索选 `argmin θ̂`。

- **单看一个配置**：`θ̂` 在 `θ` 附近无偏（中位数对一个近似对称的主体而言是无偏的）；
- **但搜索要的是 `min` 那个值**：`E[min_i θ̂_i] < min_i θ_i`。

这就是**赢家诅咒**：`min` 这个**非线性**操作把分布的下尾挑了出来。
**噪声不是「平均掉就没了」—— 它被 `min` 系统性地用上了。**

**量级**：若每个配置的 `θ̂` 都是同分布的高斯、真值全等，那么
`E[min θ̂] ≈ θ − σ·√(2 ln K)`（K = 配置数）。**K=20、σ=2.5% 时，这个「白捡的收益」是 −4.3%。**
——**你的搜索会报出一个 4% 的「改进」，而它的期望值正好是那个负号**。

### 1.2 分辨力：噪声地板 σ 与配置差 Δ 的比值

**要让搜索可靠地找出最优，需要 `Δ ≫ σ̂`**，其中 `σ̂` 是「m 次测量取中位」的误差，
`σ̂ ≈ 1.2533·σ/√m`（中位数的标准误）。

本程序的口径：

| 量 | 值 |
|---|---|
| `σ/中位`（一次约 0.4 ms 的真实测量） | **2%–4%** |
| `σ̂`（m = 5，取中位） | **1.1%–2.2%** |
| `σ̂`（m = 10，取中位） | **0.8%–1.6%** |
| **顶部两个配置的真实差 Δ** | **0.12%** |

**Δ / σ̂ ≈ 0.1** —— **差一个数量级**。所以「加倍预算」把 `σ̂` 从 1.5% 压到 1.1%，
**对分辨力几乎没有帮助**。这与 `45/02` 的 `n ∝ σ²` 是同一件事的两面：
**分辨率不足时加样本无用。**

### 1.3 预算怎么分

把 `N` 次测量分给 `M` 个配置、每个测 `m = N/M` 次。于是
`σ̂ ∝ 1/√(N/M) = √(M/N)`：**配置越多，每个配置能分到的测量越少，分辨力越差**。

**⇒ 搜索空间的规模与测量预算是一对矛盾**（`60-compilers/auto-tuning/03-search-algorithms`
讲的就是这件事的**无噪声**版本：预算的账怎么算；**正文在那边，本篇只回链**）。
本篇补的是：**有噪声时，这个矛盾里多了一个「地板」** —— 无论怎么分，
`σ̂` 都下不到 `σ` 以下，而顶部配置的真实差可能就在 `σ` 以下。

## 2. 执行映射

| 组件 | 它在这里的角色 | 数值量级 |
|---|---|---|
| **`time.perf_counter` + CPython 解释器** | 噪声的**物理来源**：本程序不设噪声参数，`measure()` 就是把那份工作量真的跑一遍 | 一次测量约 **0.40 ms**；`σ/中位 ≈ 2%–4%` |
| **操作系统的调度** | 它把「一次测量」变成一个**随机变量**，而且尾部很重（`03-ab-orchestration` 实测 `max/中位` 可达百倍量级） | 本程序 `p90/中位` 实测 **1.041–1.053** |
| **搜索空间（20 个配置）** | 它决定「要赢多少个对手才叫最优」。K 越大，赢家诅咒越强 | 顶部真实差 **0.12%**；`K = 20` |
| **`min` 算子** | 它是**系统性偏向的来源**（§1.1）。它不需要任何额外假设就能把下尾挑出来 | 本机实测：**100% 的试验里**，被选中配置的读数低于真最优的真值 |

## 3. 实现与演进

**朴素：每个配置测一次，选读数最小的。** 它**能跑**，而且**特别容易选错** ——
`m = 1` 时 `σ̂ = σ`（2%–4%），而顶部真实差只有 0.12%。

**第一步：把每配置的重复次数 `m` 显式化，取中位而不是均值。**
**为什么需要下一步**：`m` 不是一个可以随便调大的旋钮（§1.3 的预算账）——
你需要知道**它现在够不够**。

**第二步：把「真值」与「读数」分开。** 本程序的做法是：
`mini_search.landscape(x)` 给出**解析真值**，而 `measure(x)` **真的把那份工作量跑一遍**。
**为什么需要下一步**：只有当两者分开，你才能量出「读数说赢了、真值说输了」这件事
（§3.4 的假胜利）。

**第三步：把「加倍预算」这件事实测一遍。** 这就是 §3.3。
**为什么还需要一步**：预算加倍**看起来**总该有帮助 —— 必须实测它到底有没有。

### 3.1 ★★ 本程序与 `60` 在**实现上**的关键区别：噪声是**量出来的**

`60` 的 `measure()` 是 `true_cost × (1 + MEASURE_NOISE × rng.normal())` ——
**噪声由那个参数决定，而参数是我设的**。

本程序的 `mini_search.Measurer.measure()`：

```python
n = int(round(TRUE_UNITS[x]))
t0 = time.perf_counter()
atomic_batch(n)                 # ← 真的把那份工作量跑一遍
dt = time.perf_counter() - t0
return dt                       # ← 返回**真的秒数**
```

**⇒ 噪声的量级、重尾程度、时间相关性全部来自这台机器，本程序一个字都没有规定它。**
这是对 **P12（自造真值）** 的正面回答：若用 `random.gauss` 造噪声，
那么「噪声让搜索选错」这个结论就变成了「我造的噪声让我造的搜索选错」——
**一个不关于任何真实机器的结论**。

> ★ **代价**：每次「测量」真的要花 `landscape(x) × t_op` 的墙钟时间。
> 本机 `t_op ≈ 80 ns`，参考最优一次测量约 **0.40 ms**，一次搜索（20 配置 × m 次）约 40–80 ms。

### 3.2 本机实测：噪声有多大（本程序 `A` 类）

| 量 | 本机实测 |
|---|---|
| 一次真实测量的中位 | **0.39–0.46 ms** |
| **σ/中位** | **2.1%–3.8%** |
| **p90/中位** | **1.041–1.053**（机器安静时） |
| `max/中位` | 1.09–1.30（**只打印、不作断言**：它只由一个样本决定） |

**★ 与 §0.2 的「顶部真实差 0.12%」一比**：**噪声是真实差异的 17–32 倍**。

### 3.3 本机实测：零噪声 vs 真实噪声，以及「加倍预算」（本程序 `B`/`C` 类）

搜索只做一件事：**每个配置测 `m` 次取中位，选读数最小的**。

| 预算 | 选错率 | regret 中位 | **regret 均值** | regret 最大 |
|---|---|---|---|---|
| **零噪声**（= `60` 域的做法） | **0/1**（确定性） | 0.0000% | **0.0000%** | 0.0000% |
| **m = 5**（真实噪声） | **15/40 = 38%** | 0.0000% | **0.2548%** | 1.4386% |
| **m = 10**（加倍） | **14/40 = 35%** | 0.0000% | 0.0899% | 1.0790% |

（`regret` = 「选中配置的真实代价 ÷ 参考最优的真实代价 − 1」，用**真值**算。）

**读法（三句话）**：

1. **零噪声下搜索永远选对** —— 所以「选错」只可能来自噪声，不是搜索逻辑写错了。
2. **真实噪声下 40 次里有 15 次选错**，平均 regret **0.2548%**。而**顶部两个配置的真实差只有 0.12%** ——
   **regret 的量级正好就是那个「无谓的差别」**。
3. **★★ 选错率几乎不动（38% → 35%）** ⇒ **真实差异在噪声地板之下时，加预算买不到分辨力**。
   **换一个问法更清楚**（本程序 `C.2`）：用 `45/02` 的公式
   `n = 2·(2.8016·σ/δ)²`（**代入，不重推**）算，要让顶部那个 **0.120%** 的真实差可判定，
   每个配置要 **6244 次**测量（= 当前预算 m=10 的 **624 倍**），
   20 个配置合计约 **12.5 万次 ≈ 49 s 墙钟**。
   **⇒ 「加倍」离够用差两个数量级。**
   ★ 这个量由**实测 σ** 与**解析 δ** 推出，**不随会话抖动** ——
   而「regret 均值的比值」那种判据会（实测出过 **0.35 与 1.34** 两个相反的结果）。

### 3.4 本机实测：赢家诅咒与「假胜利」（本程序 `D` 类）

| 量 | 本机实测 |
|---|---|
| **赢家诅咒**：被选中配置的**读数**低于真最优的**真值** | **40/40 = 100%** |
| **假胜利**：读数说「有收益」而真实是「亏损」 | **14/40 = 35%** |
| 其中报出来的「收益」 | 中位 **0.47%**，最大 **1.19%** |

**⇒ 「报出来的收益」与「真实的收益」是两件事，而且它们**经常符号相反**。**

**★ 与本域 `03` 的关系**：`45/03-convergence` 讲过「假胜利」这个概念（正文在 `45`，
本篇不重讲它怎么算假阳性率）。**本篇补的是它的一个可机械数出来的形态**：
在**一次搜索**里就能造出假胜利，不需要 200 步。

## 4. 踩坑与失败模式

### 4.1 现象：把「搜索结果」当成「真实差异」

- **现象**：搜索报出「x=8 比 x=7 好 0.5%」，而两者的真实差是 **−0.12%**（x=8 更差）。
- **成因**：`min of K noisy samples` 的期望低于真值（§1.1）。本机实测：
  **100% 的试验里，被选中配置的读数低于真最优的真值**。
- **规避**：**用真值复核**。本程序的 `regret` 就是用**解析真值**算的 ——
  **只有当你手里有一个不经过测量的真值时，你才能区分「搜索赢了」与「搜索碰巧了」**。
  工程上做不到这一点时，退而求其次是：**用同一批测量算出的 `δ*` 去卡它**（回链 `45/02`）。

### 4.2 现象：以为「多测几次」能解决一切

- **现象**：把每配置的测量次数从 5 加倍到 10，选错率从 **38% 只降到 35%**。
  按 `45/02` 的公式算，要让顶部那个 0.12% 可判定，**每个配置要 6244 次**（= 预算的 624 倍）。
- **成因**：`σ̂ ≈ 1.2533·σ/√m`。m 翻倍只把 `σ̂` 压到 **0.71 倍**；
  而顶部真实差是 `σ` 的 1/17 – 1/32。**要让它可分辨，需要 `m` 大到不现实。**
- **规避**：**先看 Δ/σ**。若 Δ/σ ≪ 1，**该改的是降低 σ（更长的测量、更稳的机器），
  不是加预算**（本程序 §5 判据表最后一行）。

### 4.3 现象：用一个**造出来的**噪声去验证「噪声让搜索选错」

- **现象**：`measure = true_cost × (1 + MEASURE_NOISE × rng.normal())` ——
  把 `MEASURE_NOISE` 调到 0.02，搜索当然会选错。
- **成因**：**这是 P12（自造真值）**：模拟器同时是被测对象。
  「我造的噪声让我造的搜索选错」**不关于任何真实机器**。
  更隐蔽的是，`rng.normal()` 造出来的是**高斯**噪声，而真实测量噪声是**重尾**的
  （`03` 的 A 段实测 `max/中位` 可达数百倍）—— **你验证的是一个不存在的噪声模型**。
- **规避**：**让噪声从机器里来**（§3.1）。本程序 `make falsify` 的注入项 3 就是它的反面：
  **把噪声关掉**，`A.1`（σ/中位 的双向闸门）立刻叫。

### 4.4 现象：把 `max/中位` 当作噪声的刻画量写进判据

- **现象**：本程序实施者第一版把 `A.2` 写成「`max/中位 > 1.05`」。
  **它随机失败** —— 同一段代码两次跑出过 **1.30 与 1.04**。
- **成因**：`max` **只由一个样本决定**。在 150–400 个样本上，它是分布里最不稳的量。
- **规避**：把断言落在**由全部样本决定的量**上（这里换成 `p90/中位`，实测稳定在 1.041–1.053），
  **`max` 只打印、不判定**。这与 `bottleneck-diagnosis` 的「极差判据在正确实现下会随机失败」
  是同一类错，只是换了一个量。

## 5. 判据表

| 条件 | 结论 |
|---|---|
| 两个配置的实测差 < 由本批 σ 算出的 `δ*` | **不可判定**（回链 `45-kernel-lifecycle/convergence-and-tuning/02-significance`）。搜索会在这两者之间**随机**选择 |
| 搜索结果对「加噪 / 不加噪」**敏感** | 你的搜索被**噪声**驱动，不是被真实差异驱动（本机：零噪声 regret 恒 0，真实噪声平均 regret 0.15%） |
| **顶部两个配置的真实差 / σ < 0.2** | **搜索不可能可靠地找出最优**（本机：0.12% / 2%–4% ≈ **0.04**）。**这时该改的是降低 σ，不是加预算** |
| 把测量次数加倍后，结论**不变** | 噪声**不是**主导因素 |
| 把测量次数加倍后，结论**改变**，但选错率仍很高 | 噪声是主导因素，而**加倍不足以救**（本机：38% → 35%）。**量化它**：按 `45/02` 的公式，要让顶部那个 0.12% 可判定，每个配置要 **6244 次**（= 预算的 **624 倍**） |
| 你**没有**一个不经过测量的真值 | 只能退而用 `δ*` 卡；**必须声明这是退而求其次**，因为 `δ*` 本身也是从同一批带噪声的数据算出来的 |
| 被选中配置的读数**低于**参考最优的真值 | 这是**必然的**，不是好消息（本机 100%）。它是**赢家诅咒**，不是「搜索找到更好的了」 |
| 报出的收益 > 0 而真实 regret > 0 | **假胜利**（本机 35%）。回链 `45-kernel-lifecycle/convergence-and-tuning/03-convergence`（正文在那边，本篇只回链） |
| 想用一个「可调噪声参数」验证搜索的鲁棒性 | **不行**（§4.3）：那验证的是你造的噪声模型。**让噪声从机器里来** |
| 想用 `max/中位` 当噪声的判据 | **不要**（§4.4）：它只由一个样本决定。用**分位数**（`p90/中位`）或 `σ` 加**双向闸门** |

## 6. 小结与延伸

**一句话**：**「搜索结果」与「真实差异」之间隔着一个 `min` 算子 —— 它会把噪声的下尾挑出来，变成你的收益。**

本域主线在这里的形态：**搜索报出来的数，是关于你的程序的一次测量的最小值**，
不是关于你的程序的结论。

- **姊妹篇**：`01-measuring-sigma-and-tau`（那个 σ 从哪来、怎么测）、
  `03-ab-orchestration`（两个配置比较时，**两个时间段不可比**）。
- **往上游回链**：`60-compilers/auto-tuning`（搜索空间 / 代价模型 / 四类策略 / regret 的**定义与预算公式** /
  Triton autotuner 的默认行为 —— **全部在那边，本篇只回链**；
  以及它**主动冻结噪声**的那三行，见 §0.1）、
  `45-kernel-lifecycle/convergence-and-tuning/02-significance`（`δ*` 与 MDE 判据）、
  `45-kernel-lifecycle/convergence-and-tuning/03-convergence`（假胜利与停止判据）。
- **往下游**：任何「autotune 报出最好配置」的流程，都应当先问一句
  **「顶部几个配置的真实差，比我这次的 σ 大还是小？」**
