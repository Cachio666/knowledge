# replay 与多 pass：比值型指标的分子分母可能来自不同的执行

> **一次采集收不齐所有指标，所以要 replay 多遍。每一遍的执行条件都不同。**
> 于是「hit rate = hits / queries」这样的比值，**分子和分母可能来自两次不同的执行**——
> **那个比值不是任何一次执行的测量结果。**

## 0. 背景与动机

一个具体的对照场景。同一个「热点」的两份读数：

| 读数 | 值 | 它是什么 |
|---|---|---|
| 第一次执行测到的 hit rate | **28.5714 %**（4 / 14） | 一次**真实**执行的测量结果 |
| 第二次执行测到的 hit rate | **0.0244 %**（1 / 4100） | 另一次**真实**执行的测量结果 |
| 把两次**混起来**：分子取第一次、分母取第二次 | **0.0976 %**（4 / 4100） | **不是任何一次执行的测量结果** |
| 反向混：分子取第二次、分母取第一次 | **7.1429 %**（1 / 14） | 同上 |
| 再混一次：分子取第一次、分母取**最小的一次**执行 | **400 %** | **物理上不可能**，而工具**故意不 clamp** |

四个真实可得的数（28.5714 / 0.0244 / 0.0976 / 7.1429）**两两不同**，
两个「混起来」的值都**不在两次真实执行的测量结果集合里**。

**不用它的代价**：你会拿一个 400% 的命中率去驱动优化决策，
或者在一个**远短于 20 µs**的小 kernel 上读比值型指标并相信它——
而这两个数都不是「仪器坏了」，它们是**工具按设计给出的输出**。

## 1. 原理：一条因果链

本篇的主干是**六环**，每一环都有规格依据（括号里是 `code/specs.py` 的 `FACTS` 编号）：

> ① 硬件计数器**同时可读的数量有限**（**F1**）
> → ② 所以**一次 pass 收不齐所有 metric**（F1）
> → ③ 所以 kernel 要 **replay 多次**（F1）
> → ④ replay 之间要做 save/restore（**F4**）、**默认清 cache**（**F6**）、**默认锁时钟**（**F7**）
> → ⑤ 所以**每个 pass 的执行条件不同**（F4/F6/F7）
> → ⑥ 所以**跨 pass 取分子分母的比值是错的**（**F3**）

**第 ③–④ 环的代价是实打实的**（F4 逐字）：第一遍要保存
**kernel 可访问的全部 GPU memory**，之后每遍开始前**恢复「被写过的那部分」**；
F5 补一句边界——**若判定只需一遍，就完全不做 save/restore**。
所以「多跑几遍」不是免费的，「多要几个 metric」也不是。

**第 ⑥ 环是本篇的核心**，F3 的原文给出两个触发条件：

1. **hits 与 queries 在不同的 pass 上收集**，且
2. **kernel 没有把 GPU 跑到稳态**（F3 逐字：`generally > 20 µs`）。

任一条件不成立，误差就显著。F3 还点名第二类负载：
**「workload is inherently variable, as e.g. in the case of spin loops」**——
自旋循环每一次执行的工作量**本来就不同**，此时连**单次执行内部**的比值都不稳
（§3 本机实测的 B 段）。

**把它写成可判定的形式**：设第 $i$ 次执行的命中数与查询数分别是 $h_i, q_i$，
真实值是 $\rho_i = h_i/q_i$。跨执行组合得到的

$$\hat\rho_{ij} = \frac{h_i}{q_j}\quad (i \ne j)$$

一般**不等于任何 $\rho_k$**。只有当 $h_i/q_i$ 在两次执行间恰好相同、
或者某一侧退化（$h_i = 0$ 或 $q_j = q_i$）时才会撞上——**而那是巧合，不是保证**。
它甚至**不需要**超出 $[0,1]$ 就会出错（0.0976% 就在范围里）。

> ⚠ **v1 的教训（记在这里，因为它比数字抄错更隐蔽）**：
> v1 初稿让两个 pass 的 `hits` **都是 1**。于是交叉组合只能得到 $1/6$ 与 $1/4096$，
> **恰好等于两个真实值本身**——**数值都真跑过，但它们支撑不了要证的断言**。
> 这是「实验设计本身不成立」，不是「数字抄错」。本主题的程序把
> 「**四值两两互不相同**」和「**交叉值不等于任何真实值**」都做成了断言
> （`code/02_replay_multipass.py` 的 `A.4` / `A.5`）。

## 2. 执行映射

| 组件 | 它在这里的角色 |
|---|---|
| **GPU 的性能监视器**（HW performance counters） | 同时可读的数量有限 ⇒ 决定要几个 pass（F1） |
| **L2 cache** | ncu **默认在 replay pass 之间清空全部 GPU cache**（F6）；这是「每一遍执行条件不同」的主要来源之一 |
| **replay pass 调度器** | 决定哪些 metric 分到哪一遍、要不要 save/restore（F4/F5） |
| **SM 时钟域** | ncu **默认锁 SM 时钟**（F7）—— 与清 cache 的方向**相反**（见 `03-defaults-and-attribution.md`） |
| **workload duration** | **从不在 software-patching 的 pass 里收集**（F9）—— 所以「耗时」与「计数」天然来自不同的 pass |

**数值量级**：

- **稳态阈值一般 > 20 µs**（F3 逐字）——低于它就别读比值型指标；
- **save/restore 的显存 ≈ kernel 可访问的全部显存**（F4 逐字），
  之后每遍恢复的是**被写过的那部分**；
- **metric 超出逻辑范围时，工具故意不 clamp**（F10 逐字）——
  目的恰恰是**让报告的其余部分保持自洽**。

## 3. 实现与演进

**朴素：一次跑完，把所有计数器读出来。** 不可行——第 ① 环就说清了：
**硬件计数器同时可读的数量有限**，一次 pass 物理上收不齐。

**第一步，多 pass + replay。** 把 metric 分组，每组一遍；kernel 反复执行。
**为什么需要下一步**：kernel 有副作用（写显存），跑第二遍时内存内容已经变了。

**第二步，save/restore（F4）。** 第一遍保存 kernel 可访问的全部显存，
之后每遍恢复「被写过的那部分」。**为什么需要下一步**：恢复本身有开销，
而且它**只恢复显存，不恢复 cache**。

**第三步，把「每一遍的执行条件」也调齐。** 这就是 F6/F7/F8 那一组开关：
清 cache（默认 `all`）、锁时钟（默认 `boost`）、串行化 launch（默认开）。
**为什么还需要人管**：这组默认值**方向不一致**（见 `03-defaults-and-attribution.md`），
没有「调齐了就对」的单一答案——**得按被测 kernel 对什么敏感来决定**。

**第四步，软件打补丁的 metric 单独分 pass（F2）。** 它们「需要改 kernel、
所有被打补丁的指令都要执行额外的代码」，开销最大；
放进独立 replay pass 之后，**它们不干扰其它 metric 的正确性与精度，
而且它们自己的值也不受自己造成的开销影响**（F2 逐字）。

### 本机实测：把第 ⑥ 环的算术后果做出来

本机没有 GPU，所以这里**不试图复现 GPU 上的 replay**——复现的是**那条链的算术后果**。
被测负载是**真的状态依赖工作负载**：环形数组（4096 槽）上的**自旋查找**
（F3 逐字点名的那一类）。消费者按「路径位置」推进，每探一个位置记 1 次 query，
探到的值等于目标键记 1 次 hit。

| pass | 目标槽位 / 停止路径 / cap | hits | queries | **真实** hit rate |
|---|---|---|---|---|
| `hot` | `(3, 7, 10, 13)` / 13 / 4096 | **4** | **14** | **28.5714 %** |
| `cold` | `(4095,)` / **4099** / 4100 | **1** | **4100** | **0.0244 %** |
| `tiny` | `(0,)` / 0 / 1 | 1 | 1 | 100 % |

★ **`cold` 的停止路径 4099 越过了数组末尾（4096）**——消费者**转进了第二圈**。
这就是「自旋」的字面含义，也是这一段负载「工作量本身可变」的来源。

**按 F3 的机制跨执行组合**：

| 组合 | 值 |
|---|---|
| `hot` hits / `cold` queries = 4 / 4100 | **0.0976 %** |
| `cold` hits / `hot` queries = 1 / 14 | **7.1429 %** |
| `hot` hits / **最小 pass** 的 queries = 4 / 1 | **400 %** |

**三个断言**（`code/02_replay_multipass.py`）：

- `A.4` **四个值两两互不相同**（28.5714 / 0.0244 / 0.0976 / 7.1429）；
- `A.5` **两个交叉值都不等于任何一次真实执行的测量结果**；
- `A.6` 跨执行组合可以造出 **400% > 100%**，而程序**照原样打印、不做 clamp**。

**B 类：每个 pass 的执行条件都不同。** 本机实测三次执行的**时长**分别是
4.3 µs / 427.8 µs / 0.75 µs（`hot` / `cold` / `tiny`，CPU 上的读数）——
**相差五百多倍**。「同一个热点」的三次采集，执行条件根本不同。

**B 类还有 F3 的第二句。** 同一个 pass（同一份代码、同一个数组构造方式），
只让**目标槽位随运行变化**，跑 20 次：`queries` 取到 **20 个不同值**，
「真实」hit rate 的极差 **38.6 倍**。⇒ **「工作量本身可变」时，连单次执行内部的比值都不稳。**

> ★ **口径声明**：以上全部是**本机 CPU 上的实测值**（Apple M1 Pro / macOS / `python3 3.13.5`），
> **不是 GPU、不是 Nsight Compute**。**本仓库从未运行 `ncu`/`nsys`**：
> 凡出现它们的行为，一律是**规格引用**（F1–F15，A 级，带 URL + 章节 + 抓取日），
> **不是**本机实测值。两者**不得互证**。
> 本机三组 `(hits, queries)` 的绝对值由 `code/specs.py` 的 `PASSES` 参数决定（可复核），
> 与计划 §0.7 D-11(b) 记录的控制者实测一致。

## 4. 踩坑与失败模式

### 4.1 现象：拿一个跨 pass 的 hit rate 去驱动优化

- **成因**：F3——分子分母来自不同的 pass，且 kernel 没到稳态。那个数**不是任何一次执行的测量结果**。
- **规避**：**先查分子分母是不是同一次 pass 收集的**。做不到区分时，
  改用**同一次 pass 内自洽的**替代指标（例如直接用绝对计数，自己在同一遍里取比值）。

### 4.2 现象：看到一个 > 100% 的命中率，以为工具坏了

- **成因**：**F10 逐字**——超出逻辑范围时，工具「**故意不 clamp**，以保证报告的其余部分自洽」。
  它不是 bug，是**为了不掩盖上一个错误**。
- **规避**：看到超范围的值，**先怀疑 multi-pass（F3），再怀疑工作量可变（自旋循环），最后才怀疑硬件**。
  本机实测的 **400%** 就是这个形态的最小复现（`A.6`）。

### 4.3 现象：在一个 < 20 µs 的 kernel 上读比值型指标

- **成因**：F3 逐字——kernel 没有把 GPU 跑到稳态（`generally > 20 µs`）时，
  跨 pass 的误差**显著**。
- **规避**：**别在这个尺度上读比值**；要么把工作量做大到越过阈值，
  要么改读绝对值并自己交代口径。

### 4.4 现象：同一份代码，两次执行的「真实」hit rate 就不一样

- **成因**：F3 的第二句——工作量本身可变（`spin loops`）时，
  「工作量」是**状态**的函数，不是常数。
- **规避**：这类负载上，**先量清楚它的可变幅度**（本机实测极差 **38.6 倍**），
  再决定要不要用比值。

## 5. 判据表

| 条件 | 结论 |
|---|---|
| 报出的 metric 名形如 A/B（hit rate、efficiency、pipe utilization） | **先查 A 与 B 是否同一次 pass 收集**；不是则**可能超范围**，读到的不是任何一次执行的结果 |
| metric 值超出 [0,1] 或超出物理范围 | 工具**故意不 clamp**（F10）；**先怀疑 multi-pass（F3），不要先怀疑硬件** |
| 被测 kernel 时间 < 20 µs | 未达稳态，跨 pass 误差显著（F3 逐字）。**不要在这个尺度读比值型指标** |
| 工作量本身可变（自旋、worklist、数据依赖的控制流） | 每个 pass 的工作量都不同，比值**更不可靠**（F3）。先量它自己的可变幅度 |
| 采到的 metric 里有 software-patched 的那一类 | 它在**独立 replay pass** 里（F2）；它的值**不受自己开销影响**，但那一 pass 里**没有 duration**（F9） |
| 需要「耗时」与「某类计数」的比较 | **它们来自不同的 pass**（F9）——比较时必须声明这一点，不能当成同一次测量 |
| 只跑一遍就收齐了 | 工具**完全不做 save/restore**（F5）；此时没有跨 pass 问题，但也要意识到**你只要到了很少的 metric** |
| 看到 save/restore 的开销很大 | 它正比于**kernel 访问过的显存**（F4）；减小它的办法是少要 metric（少一遍）而不是别的 |

## 6. 小结与延伸

**一句话**：一次采集收不齐 ⇒ 要跑多遍 ⇒ 每一遍的执行条件不同 ⇒
**跨遍取分子分母的那个比值，不是任何一次执行的测量结果**。

本主题的主线在这里的形态：**你看到的不是你的程序，是关于你的程序的一次（或几次）测量**——
而这一次「几次」是**工具为了收齐指标而不得不做的**，不是你的选择。**你要做的是知道它发生了。**

- **姊妹篇**：`01-collection-mechanisms.md`（数与数之间怎么被拿到）、
  `03-defaults-and-attribution.md`（replay 之间的默认动作**方向相反**，归因还会失效）。
- **往上游回链**：`20-gpu-architecture/memory-system`（正文在该域，此处回链）
  ——L2 cache 与显存的层次结构是 F4/F6 的物理背景。
- **往下游**：`50-performance/bottleneck-diagnosis`（正文在该域，此处回链）
  讲拿到数之后怎么判「卡在哪」；本篇只讲**这个数可能是怎么被造出来的**。
