# 采集机制：插桩与采样是两条根本不同的路

> **插桩能看到函数名与精确调用次数，但它改变时序；采样不改变时序，但它只能看到栈上存在的符号。**
> 同一段程序，两条路报出来的「最热的东西」可以完全不同 —— **两个工具都没说谎**。

## 0. 背景与动机

同一段程序，两条采集路线，两份报告：

| | 报告里的第一名 | 报告里有没有 `spin_wait` |
|---|---|---|
| **插桩**（`cProfile`） | `spin_wait`，`cumtime = 0.600 s` | 有，而且带精确调用次数 |
| **采样**（`sample`，macOS 自带） | `_PyEval_EvalFrameDefault`（解释器主循环） | **一次都没有** |

被测程序只有两个函数：`compute_hot()`（纯计算）与 `spin_wait(0.6)`（用
`time.perf_counter` 自旋 0.6 秒）。**耗时最长的是 `spin_wait`，而采样器一次都没把它报出来。**

这不是 bug，也不是哪一方「不准」。它暴露的是这两条路的**结构性差异**：

- 插桩**改动被测程序本身**（在每次函数进入/退出处埋 hook）⇒ 它知道调用了谁、调了多少次；
- 采样**不改动被测程序**，只周期性地抓一次栈 ⇒ 它看到的是**此刻栈上有什么符号**；
- 而 `spin_wait` 的 Python 栈帧**不在机器栈上**：`time.perf_counter()` 一路调进
  `mach_absolute_time`，于是「自旋等待」这段时间被归给了**内核计时调用**。

**不用它的代价**：拿采样报告去优化「最热的那个东西」，你优化的是 `_PyEval_EvalFrameDefault`——
一个你根本改不动的解释器主循环。反过来，对**调用密集**的程序（每次迭代都调一次函数），
插桩后的程序会比原来慢两三倍（本机实测 **+210%**，见 §4.2），
而那个倍数**不是被测程序的性质**——对 **wall-bounded** 的程序它甚至是 0。

## 1. 原理

### 1.1 插桩：付一次「每次调用」的钱

插桩在**每次函数进入/退出**时记录时间戳与调用栈深度。设函数 $f$ 被调用 $n_f$ 次、
单次 hook 的成本是 $c_h$、函数体本身的时间是 $T_f$，则插桩后测得的时间是

$$T_f^{\text{inst}} = T_f + n_f \cdot c_h$$

**开销正比于调用次数**。这条式子后面要用两次：一次解释「为什么它精确」（调用次数是数出来的，
不是估出来的），一次解释「为什么它会被自己压垮」（$n_f$ 大时 $n_f c_h$ 支配一切）。

### 1.2 采样：误差随样本数收缩

采样每隔 $\Delta t$ 中断一次并抓栈。若程序总时长的 $\theta$ 比例花在函数 $f$ 上，
则 $N$ 个样本落在 $f$ 上的个数服从 $\mathrm{Binomial}(N,\theta)$，于是估计值的标准差是

$$\sigma_{\hat\theta} = \sqrt{\frac{\theta(1-\theta)}{N}} \;\propto\; \frac{1}{\sqrt{N}}$$

**代价与调用次数无关**（只与采样频率和程序时长有关）——这正是它对
「调用极多但每次极短」的程序比插桩合适的原因。$\theta$ 小的时候要抓很多样本才稳
（$\theta = 1\%$、$N = 200$ 时相对标准差约 $70\%$）。

### 1.3 三步推导的第三步：归因的前提是「符号在栈上」

前两步只说明「误差多大」，第三步说的是**采样的正确性前提**：

> 一个样本只能归给它**抓到的那个栈上的符号**。任何**不在栈上留下符号**的时间，
> 都会被归给**它在栈上的最近邻**。

这条前提有两种破法，本域两种都实测到了：

1. **解释型语言的帧不出现在机器栈上**（§2 的本机实测）——`spin_wait` 的时间被归给 `mach_absolute_time`；
2. **内联让函数边界消失**（§4.3 的 C 版本）——`-O2` 把小函数内联进调用者，符号**根本不存在**。

第 2 条与 GPU 上「内联使函数边界消失」「JIT 代码没有符号」是**同一类问题**：
采样器不是「没看见」，而是**看见了一个没有你名字的栈**。

## 2. 执行映射

以本机的这次实测为例，把两个工具报出来的名字落到具体组件上：

| 报告里的名字 | 它是什么 | 为什么出现在那里 |
|---|---|---|
| `_PyEval_EvalFrameDefault` | **CPython 的字节码主循环** | 解释器执行 Python 帧的地方；它出现在栈上**不代表**「它是热点」，只代表「采样时正处在解释器里」 |
| `mach_absolute_time` | **Darwin 内核的单调时钟调用** | `time.perf_counter()` 的实现；`spin_wait` 的自旋**每一次判条件**都要调它 |
| `cfunction_vectorcall_NOARGS` | CPython 调**无参 C 函数**的入口 | 每个 `time.perf_counter()` 调用都经过它 |
| `_lsprof` 的 hook | CPython `cProfile` 的**插桩后端** | 每次 Python 函数调用**与内建/C 函数调用**都经过它 —— 所以内建函数也有精确 `ncalls`（本机实测 `perf_counter` 的 `ncalls` = 3674856，`tottime` = 0.281 s） |

**数值量级**（本机实测；下表是**一次** `make run` 的输出）：

| 量 | 值 | 口径 |
|---|---|---|
| `perf_counter` 被调 | **3,674,856 次** | `cProfile` 数出来的**精确**次数（不是估计） |
| `cProfile` 报的总时间 | **0.678 s** | 同一次运行的墙钟也是 0.678 s |
| 同一段代码**不插桩**的墙钟 | **0.680 s**（7 次中位数） | 与插桩后的 0.678 s **几乎相同**——因为这段负载是 **wall-bounded** 的（自旋由墙钟定时返回） |
| 其中 `spin_wait` | `tottime 0.319` / `cumtime 0.600` | 它自旋了 0.6 s（设定值），剩下的是它自己的循环开销 |
| 其中 `compute_hot` | `tottime 0.078` | 纯计算 |
| `spin_wait` 的 `cumtime − tottime` | **0.281 s** | **恰好等于** `perf_counter` 的 `tottime`（0.281 s）——见 §4.1 |

> ★ **口径声明**：以上全部是**本机 CPU 上的实测值**（Apple M1 Pro / macOS /
> `python3 3.13.5` / `Apple clang 21.0.0`），**不是 GPU、不是 Nsight Compute**。
> 计划 §0.7 D-11(a) 记录的同口径样例是 `0.690 s / 0.314 / 0.600 / 3,556,568 / 0.286 / 0.090`；
> 实施者随后几次 `make run` 又得到 `0.678 s / … / 3,674,856 / 0.281` 与 `… / 3,656,355 / 0.284`。
> **结构与量级完全一致，绝对值每次不同** —— **`perf_counter` 的次数由自旋循环的速度决定，
> 随运行时序变化**（与 §0.7 D-13 对 `sample` 计数采用同一条纪律）。
> ⇒ 本主题的程序**只对结构下断言，不写死任何一个绝对值**；
>    **本节的任何具体数字都只表示量级，不是可复现的常量。**
> 关于 NVIDIA 工具本身的事实，只能引 §0.7 C 的规格事实（F1–F15），见 `code/specs.py`。

## 3. 实现与演进

**朴素：`print` 计时。** 在函数头尾各打一次时间戳。问题：只能测「整段」，
嵌套调用的时间会重复计入，而且 `print` 本身改变时序。

**第一步，插桩 profiler（`cProfile` / `gprof` 一派）。** 在每次调用处埋 hook，
于是拿到**精确调用次数**与 **inclusive / exclusive 两套时间**。
为此付出的代价由 §1.1 那条式子给出：开销正比于调用次数。
**为什么需要下一步**：调用次数大的程序会被自己的插桩压垮（本机实测见 §4.1）。

**第二步，采样 profiler（`sample` / `perf` 一派）。** 周期性中断 + 抓栈，
开销与调用次数**无关**。代价是它只能看见**栈上有符号**的东西（§1.3）。
**为什么需要下一步**：解释器 / JIT / 内联让「你的函数」在栈上没有名字，
于是报告里全是别人的符号。

**第三步，两条路混用。** 现代工具普遍同时提供两条路，或在同一条路里做混合：

- **Intel VTune** 的「Hardware Event-Based Sampling」与「Instrumentation and Tracing」是两条并列的路；
- **Nsight Compute** 侧，**PM Sampling**（周期采样硬件计数器）与**基于 replay 的逐 kernel 计数**
  也是两条路 —— 后者的默认行为见 `02-replay-and-multipass.md`；
- **归因的下钻**：采样给出「哪个符号」，插桩给出「调了多少次」，
  两者都对不上时下钻到 SASS —— 读 SASS 的方法在 `30-gpu-programming/ptx-sass`
  （正文在那边，此处回链）。

## 4. 踩坑与失败模式

### 4.1 现象：同一个函数的两个数不相等，看起来像「有个数错了」

`spin_wait` 的 `cumtime = 0.600` 而 `tottime = 0.319`，**差 0.281 s**。

- **成因**：`cumtime` **含子调用**（这里是被调 367 万次的 `perf_counter`），`tottime` 不含。
  **两个数都正确，但回答的是不同问题**——这是 inclusive / exclusive 的**同名不同指**：
  同一个函数名下有两个量，读者不区分就会把它们当成一个。判据很直接：
  `cumtime − tottime` 应当**恰好等于**子调的 exclusive 时间之和；某一次本机实测
  `0.600 − 0.319 = 0.281`，而 `perf_counter` 的 `tottime` = `0.281` —— 对得上
  （另一次是 `0.600 − 0.316 = 0.284` 对 `0.284`）。
- **规避**：**报时间占比前先确认手里拿的是哪一个**。报「热点」用 `tottime`，
  报「这个子树的代价」用 `cumtime`，两者不可互换。

### 4.2 现象：插桩之后程序「变慢了 15%」，于是把差值当成插桩开销

- **成因**：`cProfile` 报的**总时间**是**各函数 exclusive 时间之和**（本机实测占比 100.0%），
  它就是程序的墙钟。计划 §0.7 D-11(a) 记的 `0.690 = 0.600 + 0.090`
  **也是这种和**（`spin_wait` 与 `compute_hot` 的 `cumtime`），**不是开销**。
  v1 初稿把它读成「插桩开销 +15%」——那是一道**一致性检查**没做：
  **wall-bounded 循环下，插桩开销结构上不可能是 +15%**（墙钟把总时长钉死了，见下条）。
- **规避**：**要测真正的插桩开销，必须用「固定迭代次数」的循环**——本机实测：

  | 循环结构 | 不插桩 | 插桩 | 开销 |
  |---|---|---|---|
  | **定次数** `fixed_iters(40000)` | 0.0024 s | 0.0074 s | **+210.3%** |
  | **wall-bounded** `wall_bounded(0.10s)` | 0.1000 s | 0.1000 s | **+0.0%** |

  **两个循环共用同一个循环体函数**，唯一变量是**终止条件**。
  事实层审查者独立实测的定次数区间是 **+174% ~ +276%**，wall-bounded 读法是 **+0.1%**。
  **⇒ 「插桩开销」这个数要先说清是在哪种循环结构下量的**——否则它就是 P13（量法口径错）。

### 4.3 现象：采样报告里最热的是 `mach_absolute_time`，而你根本没写过这个函数

- **成因**：采样看到的是**机器栈**，Python 的栈帧在 C 栈上不可见（§1.3）。
  `time.perf_counter()` 调 `mach_absolute_time`，于是「自旋等待」被归给了内核计时调用。
- **规避**：**换采集路线**，或**让符号重新长出来**。本机实测的 C 版本给出了后者的完整证据：

  | 编译级别 | 采样报告里 `hot_loop` | 采样报告里 `main` | 报告里的机器栈符号 |
  |---|---|---|---|
  | `clang -O2` | **0 次** | **> 0 次** | `clock_gettime` 等，> 0 次 |
  | `clang -O0` | **> 0 次** | **> 0 次** | 同上 |

  （具体计数随采样窗口变化，故只写 0 / 非 0 —— 见 `03-defaults-and-attribution.md` §3
  末尾那一段「绝对计数不可照抄」。）

  **同一份源码、两个优化级别下热循环都按墙钟定界（1.2 s）跑**，所以差异不可能来自
  「跑得多快」；它只来自代码生成——`-O2` 把 `static` 的 `hot_loop` **内联**进了 `main`。
  两边都能采到 `main`，所以这**不是**「采样器没采到」，是「采到了、但归给了别人」。

### 4.4 一个容易弄反的地方：替换 `sample` 的**目标 pid** 会让整条断言变成空操作

- **现象**：`sample` 一旦打在**另一个进程**（或一个已经退出的 pid）上，
  输出仍然是一份像模像样的调用图，程序照样打印「通过」。
- **成因**：`sample <pid> <秒> -f <文件>` 的 `pid` 是**唯一**把「这份报告」和「被测程序」
  绑起来的东西；打错了，报告就不再是关于被测对象的测量。
- **规避**：**要求采样报告里出现一个「这段程序一定有、但你的代码没写」的符号**。
  本主题的程序用的就是这个（见 `code/01_collection_mechanisms.py` 的 `C.4`）：
  `C 类` 的 C 程序要求报告里出现 `main`、`A 类` 的 Python 程序要求机器栈符号 > 0
  ——**空报告不可能同时满足「自己的函数 0 次」和「`main` > 0 次」**。
  只断言「自己的函数 0 次」是不够的：**打错 pid 也能让它成立**。
  （`make falsify` 的 6 个注入项里**没有**「pid 写错」那一条——域 README 的列表是
  举例，逐主题的注入项表在计划 §1.5；**这一点是实施者核实后的偏差，已回报**。）

## 5. 判据表

| 条件 | 结论 |
|---|---|
| 工具报出的最热符号是 `_PyEval_EvalFrameDefault` / `PyObject_Vectorcall` / `cfunction_vectorcall_*` | 你看到的是**解释器骨架**，不是你的代码。**换用插桩路线**，或下钻到原生层 |
| 工具报出的最热符号是你**没写过的** C 函数（`mach_absolute_time`、`malloc`、`memcpy`） | 时间被归给了栈上的**最近邻**；你写的那一层没有在栈上留下符号。**结合插桩确定它在哪** |
| 工具能给出每个函数的**调用次数**（精确整数） | 这是**插桩**（内置 C 函数也会被计数）。采样的「次数」是估计值，本主题的程序不报它 |
| 同一个函数给出**两个不同的时间** | 先看字段名：`cumtime`（inclusive）与 `tottime`（exclusive）。**报时间占比前先确认是哪一种**；两者之差应当等于子调时间之和 |
| 插桩后的总时间 > 未插桩的墙钟 | 差值即**插桩开销** —— 但**只有在定次数循环下它才有意义**；wall-bounded 循环下它是 0，报它就是把口径搞错 |
| 同一个函数在 `-O2` 与 `-O0` 下的采样归因不同（一个有符号、一个没有） | 差异来自**内联**，不是来自程序行为。**采样归因的前提是「符号在栈上」** |
| 采样报告里**你自己的函数一次都没出现** | 先排除「打错了 pid / 采样窗口太短」，再按上两行处理。**不要据此断定该函数不耗时** |

## 6. 小结与延伸

**一句话**：插桩与采样不是「精确 vs 粗糙」的优劣关系，而是**两种不同的测量**——
一个知道「调了多少次」，一个知道「此刻在哪儿」。**任何一份报告都带口径**；
本主题的主线在这里的形态是：**你看到的不是你的程序，是关于你的程序的一次采集。**
