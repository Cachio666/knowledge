# 默认值与归因：工具的两处「不中立」

> **① 工具的默认配置不是中立的**：ncu 默认清 cache（结果偏**差**）、默认锁 boost 时钟
> （结果偏**好**）、默认串行化 launch（**并发结构直接消失**）。
> **两个默认值方向相反 ⇒ 无法笼统地说「ncu 的数是偏高还是偏低」。**
> **② 归因会失效**：采样器把时间归给了机器栈上的符号，**你写的函数可以一次都不出现**。

## 0. 背景与动机

同一件事的两个具体对照场景。

**场景一：同一个 kernel，`ncu` 与 `nsys` 报出的 duration 不同。** 两份文档逐字写着
**三处默认不同**（F6/F7/F8）与**一处方法相同**（F13）。所以「哪个数对」这个问题**问错了**——
它们是**在两组不同的默认条件下**量的。

**场景二：采样报告里全是你不认识的符号。** 被测程序只有两个函数，运行了 2.4 秒；
采样报告里**这两个函数各出现 0 次**，最热的是 `_PyEval_EvalFrameDefault`、
`PyObject_Vectorcall`、`mach_absolute_time`。**这些名字都在机器栈上，不在你的代码里。**

**不用它的代价**：拿场景一里的差值去「修正」你的性能模型，或者拿场景二的报告
得出「我的函数不耗时」——**两者都是把口径当成了结论**。

## 1. 原理

### 1.1 默认值为什么可能「不中立」

一个 profiler 要在**不改动被测程序**的前提下把数收齐，必须替用户做一批决定。
每一个决定都在**改变被测对象的执行条件**。判据是问一句：

> **这个默认动作，会让被测对象跑得和「它自己跑」时不一样吗？**

对 ncu（`Nsight Compute`）的三个默认值，答案都是「会」，而且**方向不一致**：

| 默认动作 | 出处 | 对结果的方向 |
|---|---|---|
| **replay pass 之间清空全部 GPU cache** | **F6** | 让 kernel **冷启动** ⇒ 结果偏**差** |
| **锁 SM 时钟**（默认锁到 boost） | **F7** / **F15** | 让 kernel 跑在**最高频** ⇒ 结果偏**好** |
| **串行化 kernel launch** | **F8** | 并发结构**消失** ⇒ 报告里根本没有「并发」这个量 |
| （对照）PM Sampling 的 Workload Execution 行 | **F13** | 这一处 ncu 与 nsys **方法相同** |

**两个方向相反的默认值合起来是一个强论断**：**无法笼统地说 ncu 的数是偏高还是偏低**——
它取决于被测 kernel 对 **cache 状态**与**时钟**哪一个更敏感。
这一条是本篇的承重结论之一，也是「默认值不中立」这句话的**具体**含义
（不是「默认值有影响」这种没信息量的话）。

### 1.2 归因为什么可能失效

一个采样样本只能归给它**抓到的那个栈上的符号**（`01-collection-mechanisms.md` §1.3）。
这条前提有三种破法，本篇管后两种（第一种在 `01` 里）：

1. **解释型语言的帧不出现在机器栈上**（`01` 的 A 类）；
2. **内联让函数边界消失**（`01` 的 C 类）；
3. **机器栈上的符号是别人的名字** —— 于是「耗时最长的那段」被归给了一个
   **你没有写、也无法修改**的函数。

第 3 种是最容易被读错的一种：报告**没有出错**，它只是**在回答另一个问题**——
「这台机器此刻在哪个符号里」，而不是「你写的哪个函数最耗时」。

### 1.3 观测者效应：一个**存在**、但本机**判不稳**的效应

profiler 要读硬件状态，而硬件状态被读的时候会被打扰——
这是「**测本身改变被测**」。它的大小应当能量出来。**本机实测的答案是：判不稳。**

**口径**：两组各 7 次重复，子进程每次跑 3.0 s 的固定工作量，比较中位数；
两组的**启动描述符完全相同**（唯一的差别是 attach 与否）；
编排是**交错**的（A/B/A/B…，不是先跑完 A 再跑完 B）。

**11 次独立测量的结果**（控制者 1 次、事实层审查者 1 次、实施者 9 次）：

| 量 | 实测区间 |
|---|---|
| **组间差 \|Δ\|** | **一直是正的**，5.8 % – 24.6 % |
| 合并组内 σ（相对量） | **1.50 % – 13.40 %**（差约 **8 倍**） |
| `δ* = 2.801585218112968·σ·√(2/7)` | **2.25 % – 20.07 %** |
| **`\|Δ\| / δ*`** | **0.30 – 5.12**，**随机器负载移动** |

| 机器状态 | `\|Δ\|/δ*` |
|---|---|
| **静息**（本机闲着） | **0.30 – 2.90** |
| **被占满**（8 个进程打满 CPU） | **3.73 – 5.12** |

★ **负载会放大这个效应本身**：`\|Δ\|` 从静息的 5.8 %–7.5 % 涨到 **22 %–24 %**
（`sample` 自己也要抢 CPU）。**这不是交错编排能消掉的东西**——
交错防的是**时间相关的漂移**，不是「负载影响」。

**读法**：

- **效应是真的**：九次里 `|Δ|` **没有一次是负的**，所以不能说「观测者效应不存在」。
- **但它判不稳**：`|Δ|/δ*` 跨越了 1（有时 > 1、有时 < 1），
  **而跨越的原因不是 |Δ| 变了，是 σ 变了** —— 合并组内 σ 在两次实验之间差约 8 倍。
- ⇒ **本机在 7 次重复下不能给出稳定的判定**。要判定它，**先要把 σ 稳定住**
  （固定机器负载、加大重复次数），而不是简单地多跑几轮。

> **★★ 这一节不写成「测不出来」，也不写成「测出来了」，更不得为了叙事完整性报一个 −8%。**
> 写成「测不出来」会与数据打架：有两次测量里 `|Δ| > δ*`，按 `45/02` 的判据那**是**可判定的。
> 写成「测出来了」同样不成立：另几次里它落在阈值以下，而且 `σ` 的批次间漂移
> 让这个判据本身不可复现。
> **诚实的表述是**：**这个差就在本方法的分辨极限附近，而本机当前的噪声水平不足以支撑一个稳定判定。**

**一处必须是「量法」而不是「结论」的偏差（★ 实施者实测，计划 §1.4 用的判据已换）**：

计划 §1.4 写的判据是「**组间差 ≤ 组内极差**」。实施者实测发现：
**极差（range）在 n = 7 时是一个极不稳定的估计量**——它只由两个端点决定，
本机连续三次静息测量给出 **2.41 % / 1.87 % / 8.44 %**；
而组间差是中位数之差，稳定得多。拿一个抖动的量当门槛，
这条断言会在**效应真实存在**时**随机假失败**（本机就红过一次：`5.83% > 5.67%`）。

⇒ 本篇的程序把门槛换成 `45/02` 的 **δ\***（**从 `45` 代入、本域不重推**），
噪声幅度用**合并组内 σ**（先把每组减掉自己组的中位数再合并，自由度 6+6 = 12）。
这一换**没有放宽门槛**，它把「随机撞离群点」换成了「按 σ 算出来的分辨极限」。
程序断言的是 **`0.1 ≤ |Δ|/δ* ≤ 8.0`**（11 次实测落在 0.30–5.12）。
**窗开得宽是有意的**：这一条是**冒烟检查**，不是精确判据——
真正防「对照结构被改坏」的是 `C.1`（两组启动描述符逐项相同），
那一条是**精确且与负载无关**的。
窗外即意味着这个差**远离**了分辨极限：**下侧**（把 attach 那一组去掉、或给两组都 attach）
会让 `|Δ| ≈ 0`；**上侧**（把 `sample` 的窗口从 2 s 拉到整个 3 s）会明显冲出。
两种情况下「判不稳」这句话都不再成立，**程序必须叫**。

**★ 一条实操结论**：这类**计时**实验必须**在空闲机器上跑**。
本机被占满时 `|Δ|` 涨到三倍、`σ` 也漂，读数就不再是关于「观测者效应」的了。

**为什么这一节是内容而不是实验失败**：它就是 `45-kernel-lifecycle/convergence-and-tuning/02-significance`
的最小可检出差异（MDE）判据在**本域真实测量**中的现身——
**你有一个想报的差异，而它落在你自己的分辨极限附近**。

**一处必须写清的边界**：本机 CPU 上的这条结论**不得外推**。
它测的是一个**约 3 秒的、被 `sample` 以 1 ms 间隔打扰的**计数器循环；
**更短的被测量、更稀疏的采样、或更长的窗口都会给出不同的 `|Δ|/σ`**。
这一节要给的是一条**方法**（先算 `σ`、再算 `δ*`、再看比值），不是一条普适常数。

## 2. 执行映射

| 组件 | 它在这里的角色 | 数值量级 |
|---|---|---|
| **L2 cache** | `--cache-control all`（默认）在**每次 replay 之前**清空它 ⇒ 每一遍都是冷启动；`none` 则保留状态，由应用自己预热（**F6 逐字**） | 本机 **cacheline = 128 B**（**不是 x86 的 64 B**）；本机 L2 = 4 MiB |
| **SM 时钟域** | `--clock-control boost`（默认）把 GPC 与显存时钟**锁到各自的 turbo 频率**（**F15 逐字**）；`base` 则锁到额定 TDP 频率 | 「boost」与「base」是同一个 kernel 的两个不同执行条件 |
| **warp scheduler** | `--replay-mode` 与 `--cache-control` 的交互决定每一遍看到的状态；stall 样本的归因规则也在这里（F11/F12，正文在 `bottleneck-diagnosis`） | `selected` / `not_selected` 是**调度器状态**，不是真 stall（**F12 逐字**） |
| **kernel launch 队列** | ncu **默认把 kernel launch 串行化**（**F8 逐字**：`serializes kernel launches, unless a dedicated replay mode is used`）；nsys 不串行化 | 并发结构一旦消失，报告里就没有它 |
| **稳态阈值** | 低于它就别读比值型指标（F3 逐字） | **一般 > 20 µs** |

**F15 的两个默认值（逐字）**：

| 选项 | 允许值 | **默认** | 逐字依据 |
|---|---|---|---|
| `--cache-control` | `all` / `none` | **`all`** | `All GPU caches are flushed before each kernel replay iteration during profiling.` |
| `--clock-control` | `base` / `boost` / `force-boost` / `none` / `reset` | **`boost`** | `GPC and memory clocks are locked to their respective turbo boost frequency during profiling.` |

> ★ **本节所有 GPU 侧的内容都是规格值。** 本仓库**没有 GPU、也没有 `ncu`/`nsys`**，
> **从未运行过这些工具**：上面每一个默认值、每一条逐字引文，都来自
> NVIDIA 官方文档（A 级，URL + 章节 + 抓取日见「参考」），
> **不是**本机实测。它们**不得**与本机的 CPU 实测互证。
>
> ★ **一次被推翻的预设**（记在这里，因为它是一个「编造冲突」的实例）：
> 计划写作期间曾**预设** CLI 的默认是 `base`，从而与 Profiling Guide 的
> 「锁 SM 时钟」说法**冲突**。读出 CLI 页的表格结构（选项名 → 描述 → **默认值独立一格**）
> 之后确认默认是 **`boost`**，**两份文档一致，不存在冲突**。
> 若当时凭记忆写下「两份文档矛盾」，那会是**编造一个不存在的冲突**。
> 附带的一条**抽取纪律**：该页的选项名在表格里写作 `cache-control`（**不带 `--`**），
> 所以在**原始字节**上 `count("--cache-control")` = **0** ——
> 据此断定「文档里没有这个选项」会是一次**完全的假发现**（详见 `code/specs.py` 模块头）。

### 本机实测：归因失效的现场

被测程序是**解释型语言**的程序：`hot_loop()` 与 `rarely_called_but_slow()`，
前者先自旋 0.8 s、后者跑 1.6 s。`sample <pid> 2` 的报告里：

| 类别 | 符号 | 出现次数 |
|---|---|---|
| **程序自己定义**的 | `hot_loop` | **0** |
| | `rarely_called_but_slow` | **0** |
| **机器栈**上的 | `_PyEval_EvalFrameDefault` | > 0 |
| | `PyObject_Vectorcall` | > 0 |
| | `mach_absolute_time` | > 0 |
| | `cfunction_vectorcall_NOARGS` | > 0 |

**同一批数据、两个方向**：`B.2` 断言自己的函数 **0 次**，`B.3` 断言机器栈符号 **> 0 次**——
只有后者成立，前者才不是「采样器什么都没采到」。

**跨语言同构**（本域的核心论点之一）：这与 GPU 上「内联使函数边界消失」
「JIT 代码没有符号」是**同一类问题**。那一半由 `01-collection-mechanisms.md` §4.3 的
C 版本复现（`-O2` 下 `hot_loop` 出现 **0** 次，`-O0` 下出现 **> 0** 次）。

> ⚠ **绝对计数不可照抄**：上面的具体次数**随程序与采样窗口变化**。
> 控制者与事实层审查者复跑同一实验，`mach_absolute_time` 分别是 136 与 468、
> `_PyEval_EvalFrameDefault` 分别是 102 与 249。⇒ **正文只写「0 次 / > 0 次」这个结论。**

## 3. 实现与演进

**朴素：直接读硬件计数器。** 把「看到的一切」当被测对象——
默认值、replay、归因，一个都没考虑。这一阶段的典型症状是**把工具的输出当程序的属性**。

**第一步，让默认值可配。** `--cache-control` / `--clock-control` / `--replay-mode`
这类开关出现，用户可以把执行条件调成自己想要的。**为什么需要下一步**：
「调成自己想要」的前提是**知道默认是什么**——而默认值常常方向相反（§1.1），
没有一个「调齐了就对」的答案。

**第二步，把「两组默认下量出来的数」并列报告。** ncu 与 nsys 的关系就是这种并列：
F6/F7/F8 三处默认不同、F13 一处方法相同。**为什么需要下一步**：
并列只给出「不同」，不给出「为什么不同」——归因链要一路走到符号层。

**第三步，把归因显式化。** stall 归因给**消费者指令**（F11 逐字：
`attributed to the consumer instruction that is waiting on a dependency, not the producer`）；
官方反模式明说目标是**提高 issue-slot 利用率**、不是把 stall 计数器压到 0（F12 逐字）。
**为什么还要人管**：归因规则再清楚，也管不到「符号根本不在栈上」的那些情况（§1.2）。

**第四步，承认观测者效应并**量它**。这就是 §1.3 那一段：
本机在 7 次重复下**判不稳**这个效应（`|Δ|/δ*` 在 0.36–2.90 之间漂，因为 σ 本身漂）
——**这一条本身就是结论**。

## 4. 踩坑与失败模式

### 4.1 现象：同一个 kernel 在 `ncu` 与 `nsys` 里 duration 不同

- **成因**：**F6/F7/F8 三处默认不同**（清 cache / 锁时钟 / 串行化）；
  **F13 是唯一一处两者方法相同**（PM Sampling 的 Workload Execution 行）。
  ⇒ 差异来自**执行条件**，不是「某个工具算错了」。
- **规避**：**F7 逐字建议**——外部用 `nvidia-smi` 锁频，再给 ncu 加 `--clock-control none`；
  两组测量要在**同一组时钟条件**下比较。并发结构要看，就得关掉串行化并意识到
  这会改变 replay 的行为。

### 4.2 现象：一个对 cache 友好的 kernel，在 ncu 下却很难看

- **成因**：`--cache-control all`（**默认**）在**每次 replay 之前**清空全部 GPU cache，
  于是每一次 replay 都是**冷启动**。对 cache 状态敏感的负载，这个默认值直接抹掉了它最大的优势。
- **规避**：**F6 逐字建议**——`--replay-mode application --cache-control none`
  让**应用自己**隐式预热 cache。注意这是一对参数：只改 `--cache-control` 而不改 replay mode
  可能不成立。

### 4.3 现象：采样报出的最热符号不是你写的函数

- **成因**：归因（§1.2）。采样看到的是**机器栈**。
- **规避**：**结合插桩**（拿到精确的调用次数与函数级 exclusive 时间，
  见 `01-collection-mechanisms.md`），或**下钻到 SASS**（读 SASS 的方法在
  `30-gpu-programming/ptx-sass`，正文在那边，此处回链）。
  **不要**据此断定「这个函数不耗时」。

### 4.4 现象：同一个观测者效应实验，今天判「有」、明天判「没有」

- **成因**：拿**极差**当噪声门槛（本域计划初稿的写法）。极差只由两个端点决定，
  n = 7 时它随「哪一轮恰好撞上离群点」剧烈变化——本机连续三次静息测量给出
  **2.41 % / 1.87 % / 8.44 %**。于是同一条「差 ≤ 噪声」的断言会**随机红绿**。
- **规避**：**门槛用 σ 写**（σ 是稳定估计量），并把噪声幅度**合并两组的自由度**
  （先把每组减掉自己组的中位数再合并）。判据本身也换成 `45/02` 的
  `δ* = 2.801585218112968·σ·√(2/n)`——它是**从 `45` 代入**的，本域不重推。

### 4.5 现象：`--cache-control` 在命令行里加了 `--` 却报「未知选项」

- **成因**：本文档引用的表格里选项名写作 `cache-control`；
  而**在原始字节上** `count("--cache-control")` = 0（见 §2 的抽取纪律）。
  这不是「文档里没有它」，是 HTML 标签把它切断了。
- **规避**：**先找连续锚点，再打印它周围的原始字节看真实结构**——
  「在原始字节上计数」必须与「先确认锚点在字节上是连续的」**配对使用**，
  否则「我核过了」本身会产生假结论。

## 5. 判据表

| 条件 | 结论 |
|---|---|
| 你打算用 `ncu` 的数做**绝对**性能结论 | **停下**：默认清 cache 让它偏差、默认锁 boost 让它偏好，**方向相反**。先说清被测 kernel 对哪一个更敏感 |
| 被测 kernel 对 **cache 状态**敏感 | `--cache-control all`（默认）会抹掉它的优势。用 `--replay-mode application --cache-control none`（F6 逐字建议） |
| 想比较**两个工具**报出的 duration | 先查三处默认：清 cache（F6）、锁时钟（F7）、串行化（F8）。**F13 那一处方法相同**，可以用它做交叉验证 |
| 需要稳定、可比较的数 | 外部 `nvidia-smi` 锁频 + `--clock-control none`（F7 逐字建议） |
| 采样报告里**你自己的函数一次都没出现** | 归因失效。**结合插桩**或下钻 SASS；**不要**据此断定该函数不耗时 |
| 报告里的最热符号是「你没写过的 C 函数」 | 时间被归给了栈上的**最近邻**。找它**上游**那个你写的入口 |
| 想做「测一下 profiler 本身的干扰有多大」 | **先算合并组内 σ，再算 `δ* = 2.801585218112968·σ·√(2/n)`**（从 `45/02` 代入），看 `\|Δ\|/δ*`。**这个比值在 1 附近时不可报**——本机九次实测落在 **0.36–2.90** |
| 两组比较只报了**极差**，没报 σ | **不要拿极差当门槛**：n = 7 时它只由两个端点决定，本机连续三次给出 2.41 % / 1.87 % / 8.44 %。**换 σ** |
| 同一实验两次跑出的 `σ` 差很多 | **先怀疑机器负载**：σ 本身不可复现时，由它算出的 `δ*` 也不可复现 ⇒ **判定不可复现**。这时该做的是稳定负载，不是加预算 |
| 报告里出现 `selected` / `not_selected` | 它们是**调度器状态**，不是真 stall（F12 逐字）。**目标不是把它们压到 0** |

## 6. 小结与延伸

**一句话**：工具的输出**带默认值**，默认值**改执行条件**，执行条件**换一个数**；
而工具报出的**符号名**也可能根本不是你写的函数。**三者都不报错。**

本主题的主线在这里收尾：**你看到的不是你的程序，是关于你的程序的一次测量**——
而这次测量**是在工具替你选好的条件下**做的。`01` 讲「数是怎么被拿到的」，
`02` 讲「同一次采集要跑几遍」，本篇讲「**拿到的数与那个名字，可能都不是你以为是的东西**」。
