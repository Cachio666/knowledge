# SIMT 执行模型与分支发散

> 写代码时像写标量程序，执行时却是向量化的——两者之间的落差全部由硬件承担，代价在分支发散时暴露出来。

## 0. 背景与动机

一份处理数组的 kernel，每个元素带一个标志位：标志置位的元素需要一段较重的计算（例如 32 次乘加，用来逼近一个多项式），否则只需加一个常数。

```cuda
float v = x[i];
if (heavy[i]) {
    #pragma unroll
    for (int k = 0; k < 32; ++k) v = fmaf(v, c[k], d[k]);   // 重路径：32 条指令
} else {
    v += 1.0f;                                              // 轻路径：1 条指令
}
z[i] = v;
```

现在用两种数据分布各跑一次：

- **分布 A**：`heavy` 标志随机分布，每个 warp 里平均一半 lane 置位、一半不置位。
- **分布 B**：同一批数据先按标志位排序（分桶），于是每个 warp 的 32 个 lane 要么全部置位、要么全部不置位。

两次运行的**元素总数相同、重路径的总执行次数也相同、kernel 二进制一个字节都没改**，预期耗时却相差约两倍。这个差异也无法用访存解释：两种分布下读写的地址范围、访存总量、合并模式完全一样。

「约两倍」这个数是可以当场算出来的（推导值）：分布 A 的每个 warp 都要把重路径的 32 条与轻路径的 1 条**各走一遍**，合计 33 条；分布 B 的每个 warp 全走同一条路径，平均 `(32 + 1) ÷ 2 = 16.5` 条。`33 ÷ 16.5 = 2`。§1 会把这个观察推导成公式，此处只需先记住它来自一个事实：**warp 分裂成两条路径后，两条要串行走完。**

> **全文的数字口径**：本文没有实测数据，所有时间与倍数都是**推导值**，由 §1 的模型与 §2 的延迟量级算出。验证它们的最小实验是配套程序 `code/02_divergence_demo.cu`（见文末「编译与运行」）。凡是引用本文数字的下游文档，请沿用这个口径。

问题就出在「同一个 warp 里的 lane 想做不同的事」上。本文要回答两个问题：

1. **为什么「发散」是一种免费的假象？** 教科书说 SIMT 把 32 个线程打包成 warp、共享一条指令流，听起来收益只是「省了 32 倍的取指开销」。但既然每个线程都有自己的 PC（Volta 之后确实如此），硬件为什么不能同时执行两条路径，而非要把它们串起来？

2. **发散的代价可以量化吗？减少它有哪些可操作的手段？** 每种手段在什么条件下有效、什么条件下反而更慢？

围绕这两问，本文只做三件事：在 §1 推导**有效并行度模型**，在 §2 说明**硬件用哪些部件实现它**，在 §3 给出**三条减少发散的手段**。§4 用三条「即便读完全文仍然会踩」的坑收尾。

## 1. 原理

先约定两个后文反复使用的词。

- **lane**：warp 内的一条数据通路，编号 0～31。一条 warp 指令发射一次，32 个 lane 用各自的数据执行同一条指令。lane 是「数据并行的那一维」。注意它不是线程：在 Volta 之后，一个 lane 可以有自己独立的 PC 和调用栈，但「一条指令覆盖 32 个 lane」这件事没有变。
- **SIMT**（Single Instruction, Multiple Threads）：程序员写的是**标量**代码——一个线程处理一个元素；由**硬件**在运行时把 32 个线程组织成 warp，让它们共享一条指令流。

下面分五步推导。

**第一步：厘清 SIMT 与 SIMD 的本质区别——向量化的决策发生在什么时候。**

| | SIMD | SIMT |
|---|---|---|
| 向量化由谁决定 | **程序员**显式使用向量类型（`float4`、`__m256`），或由**编译器**把标量循环自动向量化 | **硬件**在运行时把 32 个线程组织成 warp |
| 决策发生在何时 | 编写/编译期，静态且可见 | 运行时，由调度器当场决定 |
| 决策的粒度 | 定长向量，编译产物里能直接看出哪几条指令被合并 | warp = 32 lane，但**任一时刻哪些 lane 活跃**随数据变化 |

SIMD 的向量化在编译期就付清了：编译器要么证明循环的各次迭代互不相关、把它们合并成一条向量指令，要么放弃。SIMT 则把这件事推到了运行时——程序员写标量代码，硬件负责「凑够 32 个执行同一指令的线程」以及「在这 32 个里挑出此刻真正有效的那些」。

推迟的好处是程序员不必操心向量化；**代价是硬件必须在运行时表达「这 32 个 lane 此刻并不都在同一条路径上」这件事**，而这份表达的开销只有到运行时、拿到真实数据分布之后才知道。这就是 §0 里同一份代码跑出两倍差异的来源。

**第二步：硬件如何表达「只有一部分 lane 在干活」。**

每个周期，一个 warp 只发射**一条**指令，而一条指令只携带**一份** active mask（活跃掩码，32 位，一位对应一个 lane）。当 warp 内的 lane 想要执行不同的指令时，这一份掩码表达不了「一部分 lane 走这条、另一部分走那条」。硬件能做的只有：把这个 warp 拆成 `N` 条**互斥路径**，一条一条地串行执行；每次只把属于当前路径的 lane 放进掩码。

```
active mask = 0b0000_0000_0000_0000_1111_1111_1111_1111   // 低 16 个 lane 活跃
```

掩码与指令一起送到执行单元，决定这条指令的结果对哪些 lane 生效。**同一个 warp 的两种控制流不能在同一周期共存**——原因不是硬件缺一条通路，而是**每周期只有一次发射**：§2 会说明，调度器从 warp 里取走的是一条指令，这条指令带一份掩码，「它看到的是 warp，不是线程」。这也回答了 §0 的第一个问题：每个线程有独立 PC，只是说硬件**记录了**它们各自的位置，不等于硬件能同时执行它们；单周期内能被携带的控制流状态仍然只有一份。

**第三步：推导有效并行度。**

设当前 warp 分裂成 `N` 条互斥路径，第 `i` 条路径有 `n_i` 个 lane、需要执行 `L_i` 条指令，其中

```text
Σ n_i = 32        (i = 1 … N)
```

硬件逐条路径执行。执行路径 `i` 时，active mask 恰好覆盖它的 `n_i` 个 lane，另外 `32 − n_i` 个 lane 空转。于是：

```text
发射的指令总数（发射槽）  S = Σ L_i
完成的有效工作（lane·指令）U = Σ n_i · L_i
```

把有效并行度定义为「平均每一条发射出去的指令，携带了多少个真正在干活的 lane」：

```text
P = U / S = ( Σ n_i · L_i ) / ( Σ L_i )
```

**在假设各路径长度相当（`L_i = L`）的前提下**，分子分母同时约掉 `L`：

```text
P = ( L · Σ n_i ) / ( N · L ) = 32 / N
```

而发射的指令总数 `S = N · L`，正好是单路径（`N = 1`）时的 `N` 倍。即：

```text
执行时间 ∝ N
有效并行度 = 32 / N
```

**第四步：特例校验。**

| `N` | 各路径 lane 数 | 有效并行度 `32/N` | 发射指令数 | 含义 |
|---|---|---|---|---|
| 1 | 32 | **32** | `L` | 全 warp 同路径，零损失 |
| 2 | 16 / 16 | **16** | `2L` | 对半分裂，理论耗时翻倍 |
| 4 | 8 × 4 | **8** | `4L` | 四分叉 |
| 32 | 每条路径 1 个 | **1** | `32L` | 退化为串行 |

`N = 1` 与 `N = 32` 这两行值得各停一下。前者说明 SIMT 在「所有 lane 同路径」时是满效的——这不是特例，而是常态，绝大多数指令序列都不含分歧。后者说明：如果 warp 内 32 个线程偏要各走各的路，那么硬件花 32 倍的时间完成了一件本可以 1 倍时间完成的事，此时 SIMT 相对「32 个独立标量核心」没有任何优势可言——**共享指令流的收益被完全还回去了**。

**第五步：模型的边界——两个方向都要知道。**

边界一：**`32/N` 的成立条件比「长度相当」更宽——它真正要求的是「加权不改变平均值」。**

把第三步的精确式换一个写法：

```text
P = ( Σ n_i · L_i ) / ( Σ L_i ) = Σ ( L_i / Σ L_i ) · n_i
```

右边是**以路径长度为权重、对 lane 数 `n_i` 求的加权平均**；而 `32 / N` 是 `n_i` 的**普通平均**（因为 `Σ n_i = 32`）。两者相等，当且仅当加权不改变平均值。于是有两组**充分条件**——注意都是充分、都不是必要：

- **各路径长度相当**（`L_i = L`）：权重全部相等，加权平均退化为普通平均。
- **各路径 lane 数相当**（`n_i = 32 / N`）：被平均的数全部相等，怎么加权都一样。

**单说「长度相当」是错的**，反例就是 §0 的分布 A 自己：`N = 2`，`n_1 = n_2 = 16`，`L_1 = 32`、`L_2 = 1`——长度比 32:1 悬殊到极点，但

```text
P = ( 16 × 32 + 16 × 1 ) / ( 32 + 1 ) = 528 / 33 = 16 = 32 / 2
```

`32/N` **精确成立**。真正让模型失效的是 **lane 数倾斜**——拿同样这两条路径，只把 lane 的分配改成「1 个 lane 走长路径、31 个 lane 走短路径」：

```text
P = ( 1 × 32 + 31 × 1 ) / ( 32 + 1 ) = 63 / 33 ≈ 1.9   ，而 32 / N = 16
```

**偏差的方向取决于 `n_i` 与 `L_i` 的相关性**，所以 `32/N` 既不是上界也不是下界：

| 情形 | `n_i` / `L_i` | `P` | `32/N` | 模型 |
|---|---|---|---|---|
| 少数 lane 走长路径 | `n = [1, 31]`，`L = [32, 1]` | 1.9 | 16 | **偏乐观** |
| 多数 lane 走长路径 | `n = [31, 1]`，`L = [32, 1]` | 30.1 | 16 | **偏悲观** |

那有没有不受这些条件影响的东西？有，就是**耗时本身**：它始终正比于发射总量 `S = Σ L_i`，由最长的那条路径锁定。长路径执行期间，属于短路径的 lane 全程空转，空转量是 `(32 − n_长) × L_长`——**它与短路径占住了多少 lane 成正比，而与短路径自己有多短无关**。所以「短路径」不是免费的，但它的代价不来自「长度悬殊」这个事实，而来自「有多少 lane 被短路径占着、在长路径期间无事可做」。

§0 分布 A 的代价正好落在这里：16 个 lane 被一条只有一条指令的轻路径占着，却要陪重路径等满 32 拍——它的 `P` 恰好是 16（模型精确），但相对 `N = 1` 仍然损失了一半并行度。

边界二：**warp 被访存主导时，实际差异会小于模型预测。**

若这个 warp 的耗时本来就被一次全局访存（数百 cycle，见 §2）主导，而分裂出的轻路径只有一两条指令（几个 cycle），那么发散带来的额外发射几乎被完全吸收进访存等待里。此时把 `N` 从 1 变成 2，实际耗时可能只涨几个百分点，而不是模型给出的翻倍。**模型算的是发射侧的代价；当发射侧不是关键路径时，这笔代价不体现在墙上时间里。**

配套程序 `code/02_divergence_demo.cu` 的取样点覆盖的是**边界一**：它让每个 warp 的前 `active` 个 lane 走重路径（32 条展开的 FMA）、其余 lane 只做一次加法，并让 `active` 取 0、4、8、16、24、32。代入 `L = [32, 1]`、`n = [active, 32 − active]`：

| `active` | `n_i` | `P` | `32/N` | 模型 |
|---|---|---|---|---|
| 0 / 32 | 单路径 | 32 | 32 | 精确（`N = 1`） |
| 4 | `[4, 28]` | 4.7 | 16 | 偏乐观 |
| 8 | `[8, 24]` | 8.5 | 16 | 偏乐观 |
| 16 | `[16, 16]` | **16** | 16 | **精确**（lane 数相等） |
| 24 | `[24, 8]` | 23.5 | 16 | 偏悲观 |

两端是全 warp 同路径（第四步的 `N = 1`）；`active = 16` 恰好落在「lane 数相当」这条充分条件上，模型精确；`active = 4` 与 `24` 才是边界一的领地，而且**分居两侧**——同一个 kernel、同一段分支代码，仅因倾斜方向不同，`32/N` 一会儿高估一会儿低估。

中间取值的耗时有两个**不同**的性质，别混为一谈：发射总量 `S = 32 + 1 = 33` 与 `active` 无关，所以耗时近乎平坦；而这 33 条里轻路径只占 1 条，所以这个平坦值**逼近重路径的长度**。前者是「不随分布变化」，后者是「约等于长路径」。

取样覆盖的只是边界一。**边界二没有被专门构造**——它的条件是 warp 耗时本来就被一次全局访存主导，程序里只有 `active = 0` 这类极端点才可能让访存地板盖过发射侧。

那么什么时候 `32/N` 才给出一个可信的数字？**当「各路径长度相当」与「各路径 lane 数相当」至少满足其一时**（见边界一）。反过来说，只要 lane 的分配是倾斜的、且倾斜方向与路径长度相关，就必须回到精确式去算，不能拿 `32/N` 交差。§4 第三条是同一笔账在长分支上的反面用例：把大分支改成谓词，`N` 确实回到了 1，但 `S` 也翻了倍。

## 2. 执行映射

### 参与者

§1 的推导只用到「每周期发射一次、一次带一份掩码」这一条事实，但真实硬件要靠下面这些部件把它实现出来。

- **warp scheduler**（在 [01-sm-internals](01-sm-internals.md) §2 中介绍过）：每个周期从分配给自己的就绪 warp 中挑一条指令发射。它看到的是 warp，不是线程；当前这条指令覆盖哪些 lane，由随指令携带的掩码描述。
- **active mask**：32 位掩码，一位一个 lane。它随指令一起进入执行单元，决定结果对哪些 lane 生效。
- **reconvergence stack（重汇聚栈）**：记录「这组 lane 是从哪里分出去的、应该回到哪里合流」。进入一段可能产生分歧的区域时压栈，合流时出栈。
- **predication（谓词执行）**：指令前缀 `@P0` / `@!P0`。指令**照常发射给全部 32 个 lane**，但只有谓词为真的 lane 写回结果。它**不产生控制流分歧**——不压栈、不跳转、不改掩码。

### SASS 层面一次发散的实际形态

把 `if (p) A; else B;` 编译出来，典型的骨架是这样（Volta 及以后）：

```sass
BSSY  B0, _join        // 压入重汇聚点 _join，把进入时的 active mask 记在栈项 B0 上
@!P0  BRA _else        // P0 为假的 lane 跳去 else——分歧就发生在这条 BRA 上
      <A 分支的指令>
      BRA  _join
_else:
      <B 分支的指令>
_join:
BSYNC B0               // 等 B0 对应的 lane 全部到齐，合并 active mask，弹栈
```

三条指令的分工：

| 指令 | 全称 | 作用 |
|---|---|---|
| `BSSY` | Branch Synchronization（**Set**） | **压栈**：声明重汇聚点，记录进入时的 active mask |
| `BRA` | Branch | **跳转**：条件跳转处把 warp 分成两组，硬件为另一组另记一份掩码 |
| `BSYNC` | Branch Synchronization（**Wait**） | **合流**：在重汇聚点等待相关 lane 全部到齐，合并掩码并弹栈 |

两条指令同名不是笔误：它们是一对——`BSSY` 建立同步点，`BSYNC` 在该点等待，成对使用。

执行次序是 **`BSSY` → `BRA` → … → `BSYNC`**，一头一尾把整个分歧区域夹住。其中 `BRA` 是唯一真正制造分歧的那一条：执行到它时掩码一分为二，此后两条路径各用缩小后的掩码走完。`BSYNC` 则是代价的兑现点——先到 `_join` 的那批 lane 在这里空等，直到另一批到齐。§1 说的「串行」，在硬件上就是这个等待。

有一个容易忽略的点：`BSYNC` 是**编译器插进去的**，它标记的是编译器**期望**的重汇聚点，不是硬件强制的顺序。Volta 之后硬件为每个线程维护独立的 PC 与重汇聚状态，不保证按栈的次序锁步推进（详见 §3 的演进一节）。所以 `BSSY`/`BSYNC` 更像「给硬件的合流提示 + 给调度器的同步点」，而不是一条硬性的执行顺序。

这两处说法不冲突，因为它们约束的是不同的东西：`BSYNC` 确实定义了一个「到齐才能继续」的合流点，**该 warp 的发射总量 `S` 因此是确定的**；硬件能自由安排的只是**次序**——哪些 lane 何时推进、谁先到、这段等待能不能被别的 warp 填掉。所以 §1 的模型（它只依赖 `S`）不受影响，受影响的只是这些发射在时间轴上如何排布。

### 谓词与真分支的分界线

同一个小分支，编译器可能选谓词，也可能选 `BSSY`/`BRA`/`BSYNC`。判据是**分支体有多少条指令**，背后是一笔很简单的账：

- **谓词执行**：两条路径的指令**都发射**，全部 32 个 lane 各走一遍，但每个 lane 只对其中一条路径写回。发射量恒为 `L_A + L_B`，额外代价只有置谓词、压谓词这点常数项。
- **真分支**：发射量是**数据相关**的。全 warp 同路径（`N = 1`）时只发射 `L_A` 或 `L_B`，另一条被整个跳过；真的分裂（`N = 2`）时两条都要走，变成 `L_A + L_B`。此外还要付一次 `BSSY`/`BSYNC` 的固定开销，并在 `_join` 处等最慢的 lane。

两边的差别只在 **`N = 1` 的那些 warp 上**：真实分支在那里能整个跳过一条路径，谓词化则照单全收。于是「`L_A + L_B`」与「`L_A`（或 `L_B`）+ 分支常数」谁小，就决定了哪个更划算。分支体只有一两条指令时，常数项压过差额，谓词胜；分支体长时正好相反。**这就是「短分支用谓词、长分支别用」的全部理由**——§3 的改进一与 §4 的第三条分别从正反两面引用它。

值得留意的是，这个代价只在「本来跑得很好」的均匀 warp 上兑现：同一个 kernel 里 `N = 1` 的 warp 越多，谓词化的损失越大。这一点在 §4 第三条里会展开。

### 数值量级与由此得出的判据

| 操作 | 量级 | 说明 |
|---|---|---|
| 一条 warp 指令的发射 | 1 cycle / 调度器 | 每 SM 4 个调度器，故每 SM 每周期最多 4 条（见 01 §2） |
| 共享内存访问延迟 | 约 20～30 cycles | 无 bank 冲突时；冲突会按冲突路数成倍放大 |
| 全局访存延迟 | 数百 cycles | 未命中 L1 时，数百 cycle 起步（正文在 [01-hierarchy-overview](../memory-system/01-hierarchy-overview.md) §1、§2，此处回链） |
| `BSSY` / `BSYNC` 的固定开销 | 数 cycle | 相对分支体长度是一个固定项，不随分支体增长 |

这张表给出一条判据：**分支体的算量如果短到能与 `BSSY`/`BSYNC` 的固定开销相比，它就不值得一条真分支。**

但要注意，这只决定「该不该用谓词」，不决定「发散值不值得消除」。后者还要乘上第二个因子：**这个 warp 的墙上时间是不是被访存主导**。一次全局访存是数百 cycle，而整个分歧区域可能只发射几十条指令——此时发散在时间上几乎看不出来（§1 边界二）。所以判断一个发散热点是否值得动手，至少要问两件事：它省下的发射量相对于什么（几 cycle 的分支开销，还是数百 cycle 的访存等待），以及它占不占关键路径。**只看「有分支」就动手，是最常见的一类无效优化。**

## 3. 实现与演进

本节按「为什么需要下一步」给出**三步改进**（改进一 / 二 / 三），它们的目标都是减少发散。后面另有两节不属于这三步：**演进**讲硬件如何改变发散的行为与保证（它不减少发散），**前沿**讲分工如何让分歧根本不出现。

### 朴素做法：直接写 `if/else`

就是 §0 那段代码。它在 `N = 1` 时是最优写法：一次条件跳转，没有多余的发射；在 `N > 1` 时按 `32/N` 打折。

所以朴素做法的问题不在于「有分支」，而在于——**`N` 不是编译期常量，它随数据分布变化**。这就是 §0 里同一份二进制跑出两倍差异的原因：性能取决于运行时的数据分布，而编译器看不到它，程序员写代码时也未必看得到。

**需要下一步的理由**：如果有办法把「与数据分布相关的分支」换成「与数据分布无关的写法」，那么性能就不再随输入漂移。

### 改进一：别让编译器把短分支变成真分支

**先纠正一个常见误解。** `if (v < 0.0f) v = -v;` 这类**分支体只有一两条指令**的写法，编译器**本来就会**把它 if-convert 成谓词或 `SEL`（§2 的账：分支体短到可与 `BSSY`/`BSYNC` 的固定开销相比时，谓词胜）。也就是说，这段源码**大概率根本没有产生发散**——把它手写成 `fabsf` 之类的算术形式，SASS 往往**一模一样**，收益为零。

所以这一步真正有价值的不是「手写掉短分支」，而是**认出编译器没有 if-convert 的情形**，并让代码变得可 if-convert。编译器保留 `BSSY`/`BRA`/`BSYNC` 的典型情况有三种：

- 分支体的指令数超过它的阈值（经验上几条到十几条，随编译器版本变化）；
- 分支体内有访存、函数调用，或其他它无法证明安全的操作；
- 分支位于循环内部，它倾向于保留控制流。

这类分支里有一类可以低成本地改造：两条路径**只是给同一个变量赋不同的值**。把「先分支、再赋值」改写成「两个候选值 + 一次选择」，选择本身只占一条指令，控制流因此消失：

```cuda
// 可能被保留为真分支
float t;
if (cond) { t = /* 表达式 A */; } else { t = /* 表达式 B */; }
z += t;

// 候选值 + 选择：控制流换成一条选择指令
z += cond ? /* A */ : /* B */;
```

**但省下的只有控制流，不是算量**——A 与 B 仍然都要算一遍。所以它划算与否还是 §2 那笔账：两条路径的**发射量之和** vs「只走一条 + 分支开销」。分支体越长，后者越亏，这就是 §4 第三条的坑。

另一类更省事的做法是**源码层面干脆不写分支**。当你要表达的是「钳位」「取绝对值」「挑较大者」这类语义时，直接用对应原语，编译器就没有机会生成 `BSSY`：

```cuda
x = fminf(fmaxf(x, lo), hi);   // 钳位；两条 FMNMX，min/max 链不需要谓词
v = fabsf(v);                  // 取绝对值；一条指令
m = fmaxf(a, b);               // 挑较大者；一条 FMNMX
```

**但「短」不等于「可以随手替换」——必须核对边界。** 一个典型的陷阱：

```cuda
// 想写：s = (a > 0.0f) ? 1.0f : -1.0f;
s = copysignf(1.0f, a);                             // ✗ 不等价，别这么改
```

`copysignf(1.0f, a)` 与 `(a > 0.0f) ? 1.0f : -1.0f` **在 `a = +0.0f` 时结果相反**（前者 `+1.0f`，后者 `-1.0f`）；`a` 为 NaN 时结果取决于该 NaN 的符号位，不保证不同。原因是 `copysignf` 取的是**符号位**，而 `>` 做的是**数值比较**；`+0.0f` 的符号位是正的、但它不大于 `0.0f`，两者就在这里分道扬镳。

上面几个能用的例子也各有边界：`fabsf` 与 `if (v < 0.0f) v = -v;` 在 `v = -0.0f` 时位模式不同（数值上仍相等）；`fminf`/`fmaxf` 在 `x` 为 NaN 时与逐条 `if` 的走向不同（CUDA 的 `fminf` 返回两个操作数里非 NaN 的那个）。

于是得到一条通用规则：**算术选择类改写只在「原语取值的依据」与「被替换的比较语义」一致时才等价**。核对方法是把 `±0.0f`、`NaN`、`±Inf` 各代进去走一遍。这类改写很值钱，但值钱的前提是等价——不等价的改写换来的是测试用例覆盖不到的静默错误，而它恰恰出现在「本来只想优化一条小分支」的地方。

**这一步的适用面**：它要么是「确认编译器已经替你做掉了」（多数短分支），要么是「让它能做而它没做」（候选值 + 选择）。它**处理不了**的是两条路径做的事情本质不同——不同的访存模式、不同的循环、不同的函数调用——那时没有办法把它们压进一次选择；而硬改成「两条都算、最后选一个」会把两条路径的指令都发射一遍，**对长分支是净亏**（§2 的账，反例见 §4 第三条）。

**需要下一步的理由**：我们需要一种既不发射两条路径、也不产生控制流分歧的办法。这要求把「分歧」本身消掉，而不只是把它换个形式写出来。

### 改进二：用 warp 级原语把控制流变成数据交换

换个思路：既然分歧的根源是「不同 lane 要做不同的事」，那就**让所有 lane 做同一件事，但让它们操作的数据来自不同的 lane**。控制流的差异于是被转成 lane 之间的数据搬运，而搬运由硬件在一条指令内完成，不产生掩码分裂。

三件工具：

| 原语 | 语义 |
|---|---|
| `__ballot_sync(mask, pred)` | **投票**：返回一个 32 位掩码，第 `i` 位 = lane `i` 的 `pred` 是否为真 |
| `__shfl_sync(mask, v, srcLane)` / `__shfl_down_sync(mask, v, off)` | **取值**：把 lane `srcLane`（或 lane「本 lane + `off`」）的 `v` 取到本 lane，一条指令内完成 |
| `__any_sync` / `__all_sync` | 投票的两个特例：任意 lane 为真 / 全部 lane 为真。本文只用到前两件，这一件留给需要「提前退出」的场景 |

典型例子——**按条件累加到不同分量**：

```cuda
// 朴素：warp 在 if/else 处分裂成两条路径
if (v > 0.0f) { posSum += v; posCnt++; }
else          { negSum += v; negCnt++; }
```

无分支版本先把「哪些 lane 走哪条」问出来，再让两组各自归约：

```cuda
const unsigned FULL = 0xffffffffu;
bool  isPos = (v > 0.0f);

float a = isPos ? v : 0.0f;      // 正组的贡献，其余 lane 补 0（这是选择，无分歧）
float b = isPos ? 0.0f : v;      // 负组的贡献

#pragma unroll
for (int off = 16; off > 0; off >>= 1) {     // log2(32) = 5 步 warp 内归约
    a += __shfl_down_sync(FULL, a, off);
    b += __shfl_down_sync(FULL, b, off);
}                                            // 归约结果落在 lane 0

unsigned m = __ballot_sync(FULL, isPos);     // 一次投票直接得到两组的大小
int posCnt = __popc(m);                      // __popc = 数掩码里 1 的个数
int negCnt = 32 - posCnt;
```

关键在后半段：`isPos ? v : 0.0f` 是选择而非分歧；归约循环里所有 lane 执行的指令完全相同，掩码始终是满的；分组信息由 `__ballot_sync` 一次拿到。整段代码的执行路径与 `v` 的分布**完全无关**，这正是朴素做法缺的那个性质。

**但要说清一件事：这两段代码不是可以互换的等价改写。** 朴素版本里 `posSum` / `posCnt` 是**每线程各自的累加器**，每个线程各自持有一份；改写后的 `a` / `b` 是**整个 warp 的归约结果**，最终只落在 lane 0 上。也就是说，**统计口径从线程级升到了 warp 级**——`posCnt` 由「本线程碰到的正数个数」变成了「本 warp 32 个 lane 里的正数个数」。如果上游本来就要的是逐线程的结果（例如每个线程负责一个独立的输出），那么这次改写**改变了算法的语义，而不只是它的实现**，必须同时调整数据流：要么让 lane 0 承担整个 warp 的写回，要么先用另一轮 `__shfl_sync` 把结果派发回各个 lane。**「无分支」不是一次局部替换，它往往要求把计算重新组织成 warp 级。** 这也是它成本的一部分。

**代价必须讲清楚**，否则这条会变成新的坑：改写之后发射的指令数**与数据分布无关**，但它是一个不小的常数——两次归约共 10 条 `SHFL` 加 10 条加法，外加一次 ballot 与一次 `popc`，而最后只有 lane 0 的结果有意义。所以它划算的前提是：**被它替掉的那段发散代码更贵**，也就是两条路径各自的算量都不小。

上面这个例子自己就能划出边界：它的两条分支各只有一条指令，发散版本总共发射 2 条，改写后要发射 20 多条——**这个例子本身是亏的**，它只用来演示形态。而且这种极短的两路累加根本轮不到改进二出手：两条分支各只有两条语句（各自的累加器与计数器），谓词化后一共 4 条指令就消除了分歧，仍然远少于改写后的 20 多条。**改进二的地盘是「两条路径都很长、且输出可以合并」的情形**——那时谓词化的代价是发射量翻倍，而 ballot + `shfl` 用一个与路径长度无关的常数把分歧直接消掉。

§0 那段代码落在两者之间，两头都不讨好：改进二的常数开销（20 多条）比整条轻路径还贵，是亏的；谓词化则要把重路径的 32 条对全部 lane 再发射一遍，更亏。**这正是 §1 边界一的直接推论**——轻路径既然不额外增加时间，任何为它付出的开销都是纯亏。

**需要下一步的理由**：改进二治的是症状，而且要求两条路径的输出能合并成同一个归约或交换。更根本的是，分歧之所以存在，是因为同一个 warp 的 lane 拿到了不同类别的数据——要根治就得回到上游，让同类数据落在同一个 warp 里，也就是把这些 lane 整个从 warp 中挪走。

### 改进三：重排数据布局，让同一 warp 天然同路径

如果 §0 的数据先按 `heavy` 标志排序（分桶），那么每个 warp 的 32 个 lane 要么全部置位、要么全部不置位。此时 `N = 1`，`32/N = 32`，**§1 的模型给出零损失**——而且计算代码一行都不用改。这是三条路里唯一**根治**的一条：前两条都在「把已发生的分歧处理得更便宜」，这一条让分歧不发生。

代价被移到了别处，而且必须算清。一次全局分桶（例如 `cub::DevicePartition`）不是一趟访存，而是**至少三趟**：

| 阶段 | 访存模式 | 量级 |
|---|---|---|
| 直方图 / 计数 | 读 n 个元素，写远小于 n 的计数 | 一读一写，带宽受限 |
| 前缀和 | 在计数数组上做 scan，规模是**桶数**而非 n | 很小，可忽略 |
| 散射 | 读 n 个元素、写 n 个元素，且写地址由前缀和决定 | 一读一写，**写不合并** |

第三阶段是瓶颈：写地址由前缀和决定、互不相邻，**合并失效**——桶数越多越严重，**即使只有两个桶，也会把一次写拆成两次**（§0 的例子正是两个桶）。这一趟的实际代价因此高于一次顺序写。再加上一次额外的 kernel 启动，以及**分桶要读写的元素量本来就数倍于原计算**。

设 `p` 为**全体 lane 中重路径 lane 的占比**（等价于各 warp 内占比的平均）。发散版本要把两条路径都发射一遍，而分桶之后每个 warp 是均匀的、只走一条——两边一减：

```text
发散时每 warp 发射量   = L_重 + L_轻
分桶后每 warp 平均     = p · L_重 + (1 − p) · L_轻
省下的发射 = (L_重 + L_轻) − [ p · L_重 + (1 − p) · L_轻 ]
           = (1 − p) · L_重 + p · L_轻
```

代 §0 的数（`p = 0.5`、`L_重 = 32`、`L_轻 = 1`）：`0.5 × 32 + 0.5 × 1 = 16.5`，与 §0 算出的「33 − 16.5」一致。**但它的适用范围是 `0 < p < 1`，且假定每个 warp 都确实分裂了**：`p = 1` 或 `p = 0` 时整个 warp 本来就没有分歧，发散版本也只走一条路径、本来就不付另一条的钱，**省下的是 0**；`p` 很小时（例如 0.05）多数 warp 里一个重路径 lane 都没有，实际省下量同样低于上式。端点不是「省得最多」，而是退化点——代入前先确认 `p` 落在中间。

判别式因此是：上面这个「省下的发射」必须大于「分桶的三趟访存 + 一次启动」。左边**不等于「重路径比轻路径长多少」**——它衡量的是被浪费掉的发射，而这个浪费在 `p` 的两端都趋于零。**只有重路径足够重、`p` 又落在中间、且同一批数据会被反复处理（多轮迭代，或多个 kernel 复用同一份布局）时，右边才可能被摊薄到左边以下。** 数据只过一遍时，昂贵的分桶几乎总是亏的——这时该退回去考虑前两条路，或者接受发散。

有一个更轻量的变体：不做全局排序，只在 **block 内**用共享内存中转，让连续 32 个 lane 处理的元素从「连续下标」变成「同一类别的元素」。它的成本不是「一趟廉价访存」，而是**三轮共享内存操作**——block 内直方图、block 内前缀和、共享内存散射——外加一次 `__syncthreads()` 来敲定各段偏移。共享内存延迟约 20～30 cycles（§2），远低于全局访存，数据也不出 SM；但三轮操作本身是实打实的发射量，**仍然要和自己省下的那点发射比一比**。它的适用面也更窄：只对「类别数少、且每个 block 内各类别分布充分」的数据有效，否则移位之后每个 warp 里仍会混着不同类别的 lane——**分桶的意义在于填满整条 warp，填不满就等于没分。**

### 演进：Volta 起的独立线程调度

前面三步讲的都是「怎么绕开发散」。硬件这一侧也没有闲着，方向却不同。

Volta 之前，一个 warp 的 32 个 lane 是**锁步**的：共享一个 PC、一个栈指针，硬件按 SIMT 栈严格地一条路径一条路径推进。这带来一个著名的限制：若两条路径之间存在依赖（路径 B 的 lane 在等路径 A 的 lane 写出的值），而调度器只按栈的次序推进，就可能**死锁**。这在 Volta 之前是要靠编程规范绕开的坑。

Volta 引入**独立线程调度（Independent Thread Scheduling）**：每个线程有自己的 PC 和调用栈，硬件可以在比「一条路径」更细的粒度上交错推进不同 lane。直接后果有三条：

1. **前进保证（forward progress）变强**。warp 内的 lane 可以各自推进，不再存在「整个 warp 被栈次序卡死」的情形。这使得 warp 级的 producer-consumer 模式（一部分 lane 生产、另一部分消费）第一次可以安全地写。
2. **`__syncwarp()` 从可选变成必需**。锁步执行时，「warp 内所有 lane 隐含地停在同一处」是硬件给的；独立调度之后硬件不再保证这一点，两个 lane 之间要传递数据就必须显式同步。任何依赖 lane 间数据可见性的代码（尤其是配合 `__shfl_sync` 使用的）都要有明确的同步点。这条线的具体踩坑见 §4 第二条。
3. **重汇聚从「硬件强制」变成「编译器提示 + 硬件选择」**。§2 里的 `BSSY`/`BSYNC` 仍由编译器插入，但它标记的是期望的合流点；硬件可以在其间自由交错，实际的重汇聚时机与栈上的静态次序未必一致。

这条线的方向值得记下来：**硬件把「每个 lane 一个 PC」做得越来越真**，而软件侧（`__syncwarp()`、带 `_sync` 后缀的原语）则在补偿由此失去的隐式保证。SIMT 里的「T」（线程的独立性）在增强，而「SI」（指令流的单一性）必须靠程序员显式维护掩码与同步来守住。

### 前沿：分工，还是不分歧

上面两节给出了两个相反的方向——改进一/二/三在**一个 warp 内部**想办法消除分歧，演进一节则让 warp 内的 lane 越来越独立。近几代架构还给出了第三条线索：**让不同的 warp 承担不同角色，从而在更高的粒度上让分歧根本不存在。**

这就是 Hopper 与 Blackwell 上常见的 **warp specialization**（warp 特化，即生产者 / 消费者分工）：把 kernel 拆成若干组 warp，一组专职搬运数据（用 TMA），一组专职计算（用 `wgmma` / `tcgen05`）。关键在于——**每一组 warp 内部都是同路径的**：生产者的全部 lane 执行搬运，消费者的全部 lane 执行矩阵运算。角色差异发生在 **warp 之间**，而 warp 之间本来就不共享指令流，因此这里不存在 §1 意义上的发散。换句话说，改进三「让同类工作聚在一起」的原则被搬到了 warp 粒度上，代价是两组 warp 之间要靠 mbarrier 之类的原语同步。

一个更小、也更贴近本文主线的落点是 CC 9.0 起可用的 **`elect.sync`**（CUDA 侧为 `__elect_sync()`）：它直接在**当前的 active mask 上选举一个 lane**，让那一个 lane 去执行后续代码。这正是「掩码 + 独立线程调度」这条线的现代形态——过去要写 `if (lane == __ffs(mask) - 1)` 这类依赖 `__ffs` 与掩码的技巧，现在由一条指令表达，而且语义就是「从当前活跃的 lane 里选一个」，比 `__ballot_sync` 加 `__ffs` 的组合更贴近硬件的实际行为。当一段代码只需要一个 lane 执行时（发起一次 TMA、写回一个标量结果），这是开销最小的写法——**它把「只需要一个 lane」这件事明说出来，而不是让 31 个 lane 陪着走一条退化路径。**

## 4. 踩坑与失败模式

### 4.1 以为发散只来自 `if/else`

**现象**：代码里一处分支语句都没有（既没有 `if/else`，也没有三元运算符），性能却随输入数据变化——同样的元素总数，换个数据分布就慢一截，而且 `SASS` 里通常看不到 `BSSY`/`BRA`/`BSYNC` 那种醒目的骨架（不同编译器版本可能不同）。

**成因**：控制流的分裂不只由 `if/else` 产生，**循环的边界不齐**同样让 warp 分裂。考虑按每线程自己的数量遍历的写法：

```cuda
for (int k = 0; k < counts[tid]; ++k) { ... }   // counts 随数据变化
```

只要同一个 warp 内某些 lane 的迭代次数多于其他 lane，**多出来的那几轮就只有部分 lane 活跃**。硬件上仍然是 §1 第二步的串行推进，和前文的 `if/else` 完全等价，只是分歧点出现在循环回边而不是分支语句上；`SASS` 里它通常只表现为一条普通的 `BRA`，没有 `BSSY` 那种醒目的重汇聚标记可循（循环发散是否包裹 `BSSY` 依编译器版本而异）。这也解释了为什么「给每个线程分配不等量的工作」在 GPU 上比直觉更贵。

**规避**：让数据量对齐 warp 边界，使同一 warp 内所有 lane 的迭代次数一致（尾部零头交给掩码或单独处理）；若每线程的工作量天然不等（稀疏结构、可变长序列），要么在循环内用**统一的迭代次数 + 掩码**把多余迭代显式做掉，要么接受它，并把数据**按工作量分桶**（改进三），让工作量相近的元素落进同一个 warp。诊断手段是看循环相关的分支指令与 `__activemask()` 的取值是否在循环内发生变化——**掩码在循环内缩水，就是边界不齐的直接证据**。

### 4.2 `__syncwarp` 语义误解

**现象**：在 Volta 及以后的卡上，依赖 warp 内隐式同步的代码**随机出错**——同一份二进制有时对有时错，换个 block 大小或换张卡可能就好了，`compute-sanitizer` 也未必能稳定复现。

**成因**：这是 §3 演进第 2 点的直接后果——Volta 起 lane 独立推进，「warp 内所有 lane 隐含地停在同一处」这条硬件保证消失了，「lane A 写、lane B 读」的代码若没有同步点，读写次序就无法保证（正文在 §3「演进」，此处回链）。

真正让这个坑难缠的是它的**随机性**：读写次序取决于硬件实际怎么交错，而那是运行时行为——同一份二进制换张卡、换个 block 大小，交错方式就变了。所以它表现为「有时对有时错」，而不是一个稳定的错误。

**规避**：任何依赖 warp 内 lane 间数据可见性的代码，在使用 `__shfl_sync` 等原语之后都要有明确的同步点，并在读之前用 `__syncwarp()` 划界。另外两条同样容易被忽略的约束：

- **用带 `_sync` 后缀的版本**（`__shfl_sync` / `__ballot_sync` / `__any_sync`），不要用无后缀的旧版——无后缀版本在 Volta 上语义已经不同，编译器通常会给出警告。
- **掩码要传对**。参与交换的 lane 必须全部在掩码里，否则行为未定义。全 warp 参与时习惯写 `0xffffffffu`；只让部分 lane 参与时写由 `__activemask()` 得到的结果——但必须清楚 `__activemask()` 返回的是**此刻**活跃的 lane，它随发散状态变化，**不能被当作稳定的常量缓存复用**。把它的返回值存进变量、在分支合并之后再拿来当掩码用，是这类 bug 最隐蔽的形态。

### 4.3 用谓词改写长分支

**现象**：把一个大 `if/else` 改成三元运算符（或手写成「两条都算、最后选一个」），代码在源码层面看不到分支了，跑起来反而更慢。

**成因**：这是 §2 那笔账在长分支上的兑现——谓词化把发射量恒定为 `L_A + L_B`，而真实分支在 `N = 1` 的 warp 上能整个跳过一条路径（正文在 §2「谓词与真分支的分界线」，此处回链）。**「无分支」本身没有价值，省下的发射量才有价值。**

真正的损失因此**不在发散的那些 warp 上**——它们本来就两条都走——而在**没发散的 warp 上**：`N = 1` 通常是多数，发射量近乎翻倍，而省下的只是几 cycle 的固定项。

这个坑的阴险之处在于它的**观测时机**：你多半是在一个已经有发散的输入上做对比测试，那时两边开销接近，看不出问题；上线后换到分布均匀的数据上，`N = 1` 的 warp 变多，损失才显现出来。

它与 4.1 的方向相反、成因也不同：4.1 是「没写分支却产生了分歧」，这里是「写了无分支却亏了算量」。后者尤其容易在「无分支代码更快」这类经验法则的诱导下发生，因为那条法则默认的正是短分支场景。

**规避**：只对**极短**的分支（一两条算术）用谓词或算术选择；长分支保留真实控制流，改从数据布局上减少发散（改进三）或用 warp 级原语重写（改进二）。判断依据始终是那一笔账：**把两条路径的发射量加起来，与「只走一条路径 + 分支开销」比一比**。

配套程序 `code/02_divergence_demo.cu` 就是为检验这些推论设计的。它的 branchless 版本必须无条件把两条路径都算一遍，因此**按 §2 的账预期**：耗时基本恒定、与 `active` 无关，且不低于 divergent 版本。差距最明显的是 `active = 0`——此时全 warp 走轻路径，divergent 版本能整个跳过重路径那 32 条 FMA，而 branchless 照付；中间取值（如 `active = 16`）两者应非常接近，因为 divergent 此时也要付 `BSSY`/`BSYNC` 与合流等待，而 branchless 只多一条 `SEL`，量级上分不出胜负。

**验证方式**：跑该程序，看两列耗时之**差**随 `active` 的变化曲线——按上段预期，它应当在 `active = 0` 处最宽、中间收窄，并在 `active = 32` 处**再次收窄**：此时全 warp 走的就是重路径，重路径本来就非走不可，divergent 能省的只剩 `path_light` 那一条加法，而 branchless 照付两条。**这里给的是推导出的形状，不是实测结果**（口径见 §0 的说明）；形状若与实测不符，应当回头检查 §2 那笔账里哪一项估错了。

它的价值不在「谁更快」，而在于**把「发散的代价」和「两条路径的成本之和」解耦**：branchless 的耗时就是 `L_A + L_B` 加上常数，是一条与数据分布无关的基准线，divergent 与它的差距就是发散的真实开销。它是「发散有多贵」的**标尺**，而不是「改写成无分支就好了」的推荐写法——两者恰好是同一枚硬币的两面。

## 编译与运行

配套程序 `code/02_divergence_demo.cu` 打印 `active` 从 0 到 32 时 divergent 与 branchless 两版的耗时**及其差值**，对应 §1 边界一的整张表与 §4.3 的推论形状；它还会顺带核对两个变体的输出逐元素一致。

**预期量级**：按 §4.3 的形状，差值在 `active = 0` 处最大，但倍率只有约 **1.2 倍**——那一档的耗时地板仍是访存，branchless 只是刚好越过去，其余各档收窄到接近持平。**这是推导值而非实测结果，且依赖具体机器**：单次 kernel 只有约 1 µs，而启动的固定开销（主机侧 2～4 µs、GPU 侧 1～2 µs）与之同量级；若某台机器是主机侧供不上，两列都会被拉到同一个 `max(主机, GPU)`，`diff` 也随之归零。程序会把 L2 容量与工作集一起打印、前提不成立时显式提示；**首次运行时请对照自查**：若两列都很平坦，先怀疑工作集没有驻留 L2 或主机侧供不上，而不是先怀疑 kernel 写错了。

## 6. 小结与延伸

本文的主线一句话可以讲完：**SIMT 把向量化的决策推迟到了运行时，代价在发散时兑现**。围绕这条主线，有三个可以独立复用的中间结论：

1. **有效并行度 = `32 / N`**，`N` 是一个 warp 内互斥路径的条数；`N = 1` 时零损失，`N = 32` 时退化为串行。精确式是 `P = Σ n_i L_i / Σ L_i`，即**以路径长度为权重对 lane 数求的加权平均**，所以 `32/N` 只在**「各路径长度相当」或「各路径 lane 数相当」**满足其一时成立——注意这两条都是充分条件而非必要，`32/N` 也因此既不是上界也不是下界。它另有一处边界在反方向：warp 被访存主导时，实际差异会小于模型预测（代价被数百 cycle 的访存等待吸收了）。
2. **减少发散有三条路，每条都有明确的适用面**：短分支交给编译器 if-convert——它多数时候已经做了，手写改写往往零收益，真正要动手的是「它没做，而你改写成候选值 + 选择就能让它做」的情形（对长分支是净亏，因为谓词化把只在 `N = 1` 的 warp 上才存在的那次「跳过」也取消了）；路径较长且输出可合并时，用 `__ballot_sync` + `__shfl_sync` 把控制流换成数据交换（成本是一个与数据分布无关的常数，所以路径越长越划算，但它会改变统计口径）；分歧的根源在输入时，从数据布局入手分桶，让同一 warp 天然同路径（成本是至少三趟分桶访存，其中散射那趟写不合并）。三条用的是同一笔账：**省下的发射量 vs 付出的发射量**，而且这笔账必须在「有发散」和「没发散」两种输入上分别算一遍。
3. **`__syncwarp()` 是 SIMT 的现代前提**。Volta 起 lane 独立推进，掩码与同步从「硬件保证」变成了「程序员的显式责任」；带 `_sync` 后缀的原语与正确的掩码是这项责任的具体形式。

本文留下了一个没有回答的问题：既然一个 warp 因为发散慢了几倍，**为什么整机的吞吐不一定会跟着慢几倍？** 答案在 [03-occupancy-and-latency-hiding](03-occupancy-and-latency-hiding.md)——那一篇会把 [01-sm-internals](01-sm-internals.md) 的两条占用率约束补全为完整的四约束取最小，并从 Little 定律出发说明：只要同一个 SM 上还有足够的其他 warp 可以发射，某个 warp 在 `BSYNC` 处的空等就会被别人填掉。发散打折的是**单个 warp 的效率**，而整机吞吐取决于**所有常驻 warp 合起来能不能把发射槽填满**——两者之间隔着一个占用率。
