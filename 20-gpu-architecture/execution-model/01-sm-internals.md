# SM 内部结构

> GPU 的并行度不是「核心数」，而是「每 SM 能同时挂住多少个 warp」——而这个数由寄存器文件除以每线程寄存器用量决定。

## 0. 背景与动机

一个初学者拿到一张加速卡的规格表：132 个 SM，每个 SM 有 128 个 CUDA core。他做了一次乘法，132 × 128 = 16896，然后把待处理的 16896 个输出元素切成一元素一线程，指望它们「同时」开跑，并据此规划后续的数据划分与分块策略。跑出来的性能只有理论峰值的百分之几，而且把分块调大、调小都救不回来。

问题出在那个乘法上。16896 是 FP32 数据通路的**宽度**：它表示「一个周期内能同时流过多少个 lane 的 FP32 运算」，而不是「同一时刻有多少个线程处于活跃状态」。这张卡同一时刻能挂住的线程数其实是 132 × 2048 ≈ 27 万，比 16896 高一个数量级；而每周期真正能发射的指令，只有 132 × 4 = 528 条 warp 指令。三个数字各自回答不同的问题，混用其中任意两个都会得到错误的规划。

更关键的是，27 万这个数字只是**架构允许**的上限。真实 kernel 编译出来，每线程常用 30～48 个寄存器（经验区间，复核方法见 §1 第一步）。寄存器一紧张，常驻 warp 数立刻往下掉：每线程 64 个寄存器时，每个 SM 只能挂 32 个 warp，占用率——实际常驻 warp 数与架构上限之比——直接腰斩，延迟隐藏能力随之腰斩。而这件事在源代码里完全看不见——它发生在编译期的寄存器分配阶段，由编译器悄悄决定。

所以「这张卡能跑多少并行」不能靠数核心回答，也不能靠数 SM 回答。本文要回答的是一个更具体的问题：**给定一个 kernel，如何算出它的并行度上限？** 上限由多条约束取最小得到，而本文只推导其中两条——**架构规定的常驻 warp 上限**，与**寄存器文件预算**——因为这两条在实际 kernel 上最常起决定作用，也完全可以纸笔算出。另外两条（共享内存、每 SM 最大常驻 block（线程块）数）留到 [03-occupancy-and-latency-hiding](03-occupancy-and-latency-hiding.md) 补齐；在补齐之前，本文给出的上限始终是一个成立的上界。

## 1. 原理

下面按顺序推导，每一步只引入一个量，最后一步才给出结论。推导只用到三个名词：**warp**，32 个线程组成的调度单位；**block**（线程块），一组线程，必须整体调度到同一个 SM 上，其占用的资源在该 block 的全部线程结束之前不会释放；**SM**（流式多处理器，Streaming Multiprocessor），容纳并调度这些 warp 的硬件单元。

**第一步：确定「每线程寄存器数」`r` 从何而来。**

寄存器是 SM 内最快的存储，它就在执行单元的旁边，读写不需要走任何互联，因而不像 L1/L2 那样有命中率的概念。但它也不像内存那样可以按需申请：一个线程要用多少个寄存器，由编译器在**编译期**做寄存器分配时一次性算定，写进 kernel 二进制。运行时无法增加，也无法减少。所以 `r` 是一个静态常量，可以用 `--ptxas-options=-v` 从编译日志里读到（会打印形如 `Used 40 registers` 的一行）。

**第二步：把 `r` 从线程粒度放大到 warp 粒度。**

warp 是 32 个线程，它们共享同一条指令流，只是各自持有不同的数据。硬件按 warp 组织取指、译码与发射，也就必须按 warp 组织寄存器：一个 warp 需要的寄存器量是

```text
单个 warp 的寄存器占用 = 每线程寄存器数 × 32 = 32r
```

单位为 32-bit 寄存器。这一步是后面所有推算的支点——它意味着寄存器消耗是**以 32 为步长**跳变的。

**第三步：确认这份占用必须整份预留，不能按需换入。**

一个 warp 被调度上 SM 之后，它的 32r 个寄存器在整个生命周期内都必须同时可寻址。原因是寄存器文件没有「后备存储」：调度器可能在任意周期把这个 warp 从就绪切到发射，发射时要在一个周期内读完 32 个 lane 的操作数，此时如果某个操作数不在寄存器文件里，流水线无法停顿去取它——没有地方可以取。因此

```text
寄存器可容纳的 warp 数 = floor(寄存器文件大小 ÷ (每线程寄存器数 × 32))
```

取整方向必须是向下（floor），因为寄存器不能超售：装不下的 warp 不会被部分装入，而是根本不被调度。

**第四步：与架构上限取较小者。**

架构还规定了每个 SM 最多常驻多少个 warp，记作 `W_max`（下文 §2 给出的量级是 64）。这个上限来自线程数上限（2048 线程 ÷ 32）而不是寄存器，因此它与第三步的约束相互独立，真实的并行度上限是两者中的较小者：

```text
每 SM 常驻 warp 上限 = min( W_max , floor(寄存器文件大小 ÷ (每线程寄存器数 × 32)) )
```

**第五步：代入具体数值。**

设寄存器文件为 65536 个 32-bit 寄存器（256 KB，这是 Volta 之后所有数据中心 SM 的配置），`W_max` = 64：

| 每线程寄存器数 `r` | 单 warp 占用 `32r` | 寄存器文件可容纳 | 最终常驻 warp 数 | 常驻线程数 |
|---|---|---|---|---|
| 32 | 1024 | 65536 ÷ 1024 = 64 | min(64, 64) = **64** | 2048 |
| 64 | 2048 | 65536 ÷ 2048 = 32 | min(64, 32) = **32** | 1024 |
| 128 | 4096 | 65536 ÷ 4096 = 16 | min(64, 16) = **16** | 512 |
| 255 | 8160 | 65536 ÷ 8160 = 8.03 → 8 | min(64, 8) = **8** | 256 |

每线程寄存器数从 32 涨到 255（约 8 倍），常驻线程数从 2048 掉到 256（正好是八分之一）。两者严格成反比，因为分子固定：常驻线程数 = `寄存器文件大小 ÷ r`。**寄存器文件里没有可以「挤一挤」的余量**，这是它与缓存的根本区别。

**第六步：把公式反过来解，得到架构的设计点。**

把寄存器文件大小除以架构的线程上限，就得到那个让两条约束恰好相等的寄存器数：

```text
65536 ÷ 2048 = 32
```

也就是说 **32 个寄存器/线程恰好是两条约束的交点**。低于 32，先卡住的是架构的线程数上限（寄存器还有富余）；高于 32，先卡住的是寄存器文件（线程数上限用不满）。而编译器为真实 kernel 生成的用量通常落在 30～48 这个区间——注意这是**经验区间而非实测值**：用 `--ptxas-options=-v` 编译自己的 kernel 即可随时复核（配套程序按 16/24/32/40/64/128/255 取样，覆盖并跨越这一区间）。它正好压在上述边界上、且常常越过去——**这就是为什么寄存器几乎总是那个真正起作用的约束**，也是为什么「这个 kernel 的占用率算出来是 50%」的答案十有八九落在寄存器上而不是别处。

**第七步：一个必须补齐的细节——分配粒度。**

上面的除法假设 `r` 可以是任意整数，但硬件分配寄存器是按档位进行的：现代架构的粒度是 **8 个寄存器一档**（等价于每 warp 256 个），实际占用按档上取整。这里要先与第二步的「32 的倍数」划清界限，两者读起来很像，讲的却是两件事：32 是**算术结果**——一个 warp 有 32 个线程，每个线程各占 `r` 个，总量自然被 32 整除，它不带来任何取整损失；8 是**分配器的取整单位**，作用在每线程的 `r` 上，会让实际占用高于名义占用。**前者是恒等式，后者才是损耗的来源。** 这个细节制造了一个非线性：`r` = 32 得到 64 个 warp，而 `r` = 33 会先被上取整到 40，于是 65536 ÷ (40 × 32) = 51.2 → 51 个 warp。**多用一个寄存器，占用率掉了 20%**。这也是为什么两个看起来几乎相同的 kernel 会有明显不同的性能——它们的寄存器用量可能正好落在档位边界的两侧。

**第八步：结论——寄存器文件是预算，不是缓存。**

区别在于「能不能超额分配」。cache 是后备存储：容量不够时，cache line 被换出，程序的正确性不受影响，只是变慢，而且被换出的数据有机会再被换回来。寄存器是预算：线程一旦常驻，它的寄存器必须全程可寻址，硬件没有「把某个线程的寄存器换出到别处」这种状态——唯一的腾挪手段是把整个 warp 撤下 SM，而那要等到该 warp 所属的 block 整体结束、资源整体释放。因此寄存器无法超售：寄存器不够的 block 根本不会被调度上 SM，只会在队列里等待。

这解释了一件在直觉上反常识的事：**在 kernel 里多用几个临时变量不是零成本的**。它在编译期就固定地扣掉了一部分并行度，而且是不可逆的——只要那个变量还活着，那部分寄存器就回不来。

## 2. 执行映射

### 一个 SM 里有什么

以 Hopper 一代的数据中心 SM 为例，它的结构可以分成本地部分与共享部分。

本地部分按 4 个处理块（processing block，也称 sub-partition）划分，每块包含：

- **一个 warp scheduler**：负责从分配给自己的就绪 warp 中挑选下一个执行的 warp；
- **一个 dispatch unit**：把调度器选出的指令路由到具体执行端口；
- **一条 32 lane 宽的 FP32 数据通路**：就是规格表上被称作「32 个 CUDA core」的那个东西；
- **寄存器文件的一个分片**：每 SM 65536 个 32-bit 寄存器（256 KB）被 4 块均分，每块 16384 个，服务本块 32 个 lane 的读端口。

共享部分包括：

- **LSU（load/store unit）**：处理访存指令，把 warp 的 32 个地址合并成尽量少的请求（合并的判定规则与代价，正文在 [memory-system/02-coalescing-and-cache-line](../memory-system/02-coalescing-and-cache-line.md)，此处回链）；
- **SFU（special function unit）**：执行 `sin`、`cos`、`rsqrt`、`exp` 等超越函数，吞吐远低于 FP32 通路（通常每分片每周期 4 个 lane）；
- **常数缓存（constant cache）**：广播式读取 `__constant__` 与 kernel 参数，同一 warp 内地址相同时一次读取即可服务全部 lane；
- **共享内存 / L1**：同一块物理存储，按配置切分。Hopper 上这块存储**合计 256 KB**，其中至多 228 KB 可切给共享内存，其余作 L1 缓存——注意 228 KB 是共享内存的上限，不是这块存储的物理总量。

### 为什么 warp 是调度的最小单位

**第一，取指与译码按 warp 做一次，而不是 32 次。** 一条指令覆盖 32 个 lane，把取指、译码、发射的开销摊薄了 32 倍。若按线程调度，仅取指带宽一项就会吞掉全部收益。

**第二，寄存器文件与读端口按 warp 组织。** 上文把 65536 个寄存器分成 4 个分片，每个分片服务本块固定的 32 个 lane。硬件因此只需要按 warp 记录「这一份寄存器归谁」，而不必维护 2048 份独立的线程状态。

**第三，依赖跟踪与记分板按 warp 粒度。** 一个 warp 的 PC（或 Volta 之后每线程的 PC）与未完成的长延迟操作（记分板上的位）是整体管理的实体。调度器判断「这个 warp 能不能发射」，查的是 warp 级的记分板，而不是逐个线程判断。

**第四，也是最实际的一点：调度成本与 warp 数成正比，而不是与线程数成正比。** 一个 SM 只需跟踪 64 个 warp 就管住了 2048 个线程。这也是为什么占用率这个指标用 warp 计数而不用线程计数——它衡量的正是调度器的账本规模。

于是每个周期的动作是：每个 warp scheduler 从自己负责的就绪 warp 中挑出一个（策略上多为 round-robin 或 greedy-then-oldest），发射**一条**指令，这条指令的 32 个 lane 在同一周期并行执行各自的数据。这就是 SIMT：**指令流是 warp 级的，数据是 lane 级的**。

Volta 引入的独立线程调度（independent thread scheduling）没有改变这个基本单位。它给每个线程配了独立的 PC 与调用栈，使得同一个 warp 内的线程可以停在不同地址上；但调度器每个周期仍然只从 warp 中取一条指令，只是这条指令携带一个**任意的 active mask**——32 个 lane 里可以只有一部分是有效的。调度单位仍是 warp，变化的只是「一个 warp 能表示多少种控制流状态」。这条线的另一半（发散、重汇聚、谓词执行）属于 [02-simt-and-divergence](02-simt-and-divergence.md)。

### 数值量级

| 量 | 数值 | 说明 |
|---|---|---|
| 每 SM 的 warp scheduler 数 | 4 | 每周期每调度器最多发射 1 条 warp 指令，故每 SM 每周期最多 4 条 |
| 每 SM 寄存器文件 | 65536 个 32-bit 寄存器 = 256 KB | Volta 起定型，至 Blackwell 未变 |
| 寄存器分配粒度 | 8 个寄存器一档 | 实际占用按档上取整，见 §1 第七步 |
| 每 SM 最大常驻 warp 数 | 64（Volta / A100 / Hopper / Blackwell 数据中心线） | 即 2048 线程；Turing 与 Ampere 消费级线不是这个数，见 §3 |
| 每 SM 每周期 lane 操作数 | 4 × 32 = 128 | 与 Hopper 的 128 个 FP32 单元 1:1 配平 |

### 发射与分派的区别

这两个词在日常讨论里经常被混用，但它们约束的是流水线上相邻的两段。

**发射（issue）**是调度决策：调度器决定「本周期让这个 warp 走」，把一条指令从 warp 的指令流中取出、送到执行流水线的入口。约束来自调度器数量——每 SM 4 个，所以每周期最多 4 条，无论下面有多少执行单元空着。

**分派（dispatch）**是路由与占位：这条指令被送到具体的执行单元与端口，占用该单元的输入带宽，在这里读操作数、进入流水线。约束来自执行端口的数量与宽度——FP32 端口每周期接受 32 个 lane、LSU 每周期能接受的事务数有限、SFU 只有 4 个 lane 宽。

区别的实际意义是：**发射成功不等于开始执行**。一条 `LDG` 可以被成功发射，然后在 LSU 的输入队列里排队等好几拍；一条 `FFMA` 可以被成功发射，然后卡在操作数收集器（operand collector）等待一个寄存器读端口。所以「每周期最多 4 条指令」只是发射上限，真实 IPC 还要被端口竞争与依赖停顿打折。反过来，一个常见的误判——「这个 kernel 的 IPC 只有 0.5，说明调度器没喂饱」——可能完全不是因为调度器闲着，而是因为 4 条发射出去的长延迟指令全都在等 LSU。

## 3. 实现与演进

每一代 SM 的调整都是对上一代暴露出的瓶颈的回应。下面按代际展开，先给规格，再说明这一代解决了什么、又留下了什么问题。

### Volta（2017，GV100，CC 7.0）

每 SM 64 个 FP32 单元与 32 个 FP64 单元、64 个常驻 warp（2048 线程）、96 KB 共享内存、256 KB 寄存器文件。代表型号 V100 有 80 个 SM。

Volta 是本文这套框架的起点：**寄存器文件 256 KB、常驻 2048 线程这两个数字在这一代定下来，之后各代沿用**。它同时引入了独立线程调度，让 warp 内的线程拥有各自的 PC 与调用栈，代价是硬件需要维护一个重汇聚栈与每线程状态。

但它留下了两个问题。其一，整数运算与浮点运算共享同一条 32 lane 数据通路，地址计算与循环计数会直接抢占浮点发射槽——而在真实的混合负载里，整数指令的占比相当高。其二，SM 之间仍然完全孤立，共享内存只能被同一个 block 看到，任何跨 block 的数据交换都必须绕道 L2 或全局内存。

### Turing（2018，TU102，CC 7.5）

每 SM 64 个 FP32 单元**加上 64 个独立的 INT32 单元**、32 个常驻 warp（1024 线程）、64 KB 共享内存、256 KB 寄存器文件。代表型号 RTX 2080 Ti 有 68 个 SM。

Turing 回应了第一个问题：把 INT32 拆成独立数据通路后，整数与浮点可以在同一周期由不同 warp 并发执行，地址计算不再与算术抢发射槽——这对图形负载和访存密集 kernel 都是直接的收益。

代价是常驻 warp 数从 64 降到 32。这个数字可以用本文的公式反过来解读：Turing 把每 SM 的线程上限设为 1024，而寄存器文件仍是 65536，于是满占用率下的每线程寄存器预算变成 65536 ÷ 1024 = 64，比 Volta 的 32 宽一倍——单个线程因此可以持有更多寄存器而仍然住得下。但代价同样清楚：**常驻 warp 上限只有 32，占用率的可调空间随之减半**。同样掉到 50% 占用率，Volta 还剩 32 个 warp 在飞，Turing 只剩 16 个，延迟隐藏的余量更薄。**这一代也是「跨架构比 SM 数」最容易翻车的地方**（见 §4 第一条）：Turing 的 SM 数量与 Volta 接近，但每 SM 的线程容量只有一半，把 SM 数当作算力换算因子会直接高估一倍。

这个方案还有一个内在局限：两条通路的宽度是各自固定的。每 SM 的 64 个 FP32 单元与 64 个 INT32 单元被平均分配到 4 个处理块里，于是纯浮点负载最多只能用满 64 个 lane，另外 64 个整数 lane 全程闲置；反过来，地址计算密集的负载会让 FP32 lane 空转。**能并行多少，最终取决于负载的指令配比**，而编译器对配比几乎没有控制权。下一代需要的不是「多一条通路」，而是「宽度可以按负载重新分配」的数据通路。

### Ampere（2020，CC 8.0 / 8.6）

Ampere 分成两条线，规格差异很大，这正是本文反复强调「SM 数不可比」的实证。

**GA100（CC 8.0，数据中心）**：每 SM 64 个 FP32 单元、64 个常驻 warp、164 KB 共享内存、256 KB 寄存器文件。代表型号 A100 有 108 个 SM。

**GA10x（CC 8.6，消费级）**：每 SM **128 个 FP32 单元**、48 个常驻 warp（1536 线程）、100 KB 共享内存、256 KB 寄存器文件。代表型号 RTX 3090 有 82 个 SM。

FP32 单元数的翻倍正是对上一代那个局限的回应：Turing 上分离的 INT32 通路被并入 FP32 通路，使 128 个 lane 都能执行 FP32——但同一周期仍然只有 64 个 lane 能执行 INT32。**「128 个 CUDA core」是 FP32 的峰值宽度，不是 128 路独立整数并行**，这正是 §0 里那个乘法的另一层陷阱。

LSU 侧的增强是异步拷贝（`cp.async`）：把 global → shared 的搬运从「读寄存器再写共享内存」改成由硬件直接搬运，既不占寄存器，也省掉了一半指令发射。这一改动是后续 TMA 的雏形。

Ampere 留下了共享内存的隔离问题：block 之间依然无法协作，而流水线并行、跨 block 的规约等模式非常需要 SM 之间的直接通信。

### Hopper（2022，GH100，CC 9.0）

每 SM 128 个 FP32 单元、64 个常驻 warp、**228 KB 共享内存**、256 KB 寄存器文件。代表型号 H100 SXM 有 **132 个 SM**——132 × 128 = 16896，正是 §0 里那个诱人的乘法。

Hopper 回应了 Ampere 留下的问题，手段是**线程块簇（thread block cluster）**：一个 cluster 最多包含 8 个 block（可移植大小；使用非可移植大小可到 16），簇内的 block 被共同调度到同一个 GPC 内的一组 SM 上，并且可以互相读写对方的共享内存——这就是**分布式共享内存（DSMEM）**。SM 之间的协作第一次不再必须经过 L2。（DSMEM 的完整机制与它作为「扩大可控范围」这一步的意义，正文在 [20-gpu-architecture/memory-system](../memory-system/01-hierarchy-overview.md)，此处回链。）

第四代 Tensor Core（`wgmma` 指令族）与 TMA（张量内存加速器）进一步把矩阵运算的操作数准备与批量数据搬运从线程的指令流中剥离：`wgmma` 由整个 warpgroup 协作发射，TMA 则由单个线程发起一大块搬运，寄存器压力因此下降——这实际上扩大了能跑满常驻 warp 数的 kernel 范围。

不过 TMA 卸掉的只是操作数搬运那一部分压力，真正的大头是累加器——这就直接回到了本文的主线。`wgmma` 的累加器仍然住在寄存器文件里：一个 m64n256 的 FP32 累加器 tile 分摊到 128 个线程（一个 warpgroup）上，每个线程单是累加器就要占掉 128 个寄存器；而 65536 ÷ 128 = 512 个线程，正好是 4 个 warpgroup。也就是说，**寄存器文件最多只装得下 4 个 warpgroup 的累加器**，而且这还没算操作数、地址与循环变量。**在选定大 tile 的前提下**，tile 越宽、累加器越大，留给常驻 warp 的预算就越少，能用来隐藏访存延迟的并发也就越少——这个取舍是可以选掉的：改用 m64n64，每线程的累加器占用就降到 32 个寄存器。换句话说，**Tensor Core 的收益是从通用寄存器预算里借来的**，而寄存器文件自 Volta 起就是 256 KB，没有增长的余地。这条线索决定了下一代必须回答的问题。

### Blackwell（2024，CC 10.0）

第五代 Tensor Core，引入 `tcgen05` MMA 指令族与 TMEM（Tensor Memory，每 SM 256 KB 的专用累加器存储），原生支持 FP4/FP6（微缩放格式，MXFP4 / MXFP6 / MXFP8）。每 SM 128 个 FP32 单元、64 个常驻 warp、228 KB 共享内存、256 KB 寄存器文件。

注意 TMEM 的容量与寄存器文件同为 256 KB——它不是寄存器的扩展，而是**另一份独立的存储**，这正是对 Hopper 那个问题的正面回答：累加器从通用寄存器文件里搬出去之后，§1 的反比关系不再被矩阵 tile 的宽度直接牵动。`tcgen05` MMA 同时把矩阵指令改为由单个线程发射，不再需要整个 warp 参与，又省下一部分发射槽与寄存器。低精度（FP4/FP6）则从第三个方向减压：同样的 tile 用更少的位表示，操作数占用的寄存器随之减少。

这一代的走向很能说明问题：算力的增量几乎全部落在低精度矩阵运算上，而**寄存器文件与常驻 warp 数的量级自 Volta 起就没有变过**——始终是 64K 个 32-bit 寄存器、几十个 warp。也就是说，本文给出的并行度上限公式在八年间一直有效，变化的只是共享内存容量，以及「每个 lane 每周期能做多少事」，而不是「一个 SM 能挂住多少 warp」。

## 4. 踩坑与失败模式

### 4.1 跨架构比 SM 数量

**现象**：看到 A 卡 132 个 SM、B 卡 108 个 SM，便断言 A 卡算力更强，据此决定用哪张卡跑训练或推理。

**成因**：SM 数不是可比的算力单位。每 SM 的 FP32 宽度、整数通路是否独立、频率、每周期指令数都随架构变化，甚至同一代内都会分叉。同属 Ampere 的 A100（108 SM）与 RTX 3090（82 SM）就是反例：按 SM 数 A100 领先 32%，但按 FP32 峰值吞吐 RTX 3090 约为 35.6 TFLOPS、A100 约为 19.5 TFLOPS，胜负完全颠倒。再如 Turing 每 SM 只有 32 个常驻 warp，是 Volta 的一半，SM 数接近也没有可比性。

**规避**：以实测吞吐或规格表上的理论峰值为比较依据——FP32/TF32/FP16 的 TFLOPS、HBM 的 TB/s，且必须注明精度与稀疏性假设。若要比较「能不能把某类 kernel 跑满」，则比较每 SM 的常驻 warp 数 × SM 数（即总常驻线程容量）。任何以 SM 数为唯一自变量的结论都应视为未经验证。

### 4.2 把寄存器文件当缓存

**现象**：认为「寄存器多就是缓存大，多写几个临时变量没关系」，于是在 kernel 里展开循环、增加中间变量、把数组索引进寄存器，结果性能不升反降。

**成因**：寄存器是静态预算，不是缓存。它没有命中率的概念，也无法换入换出，用掉就是固定扣减并行度（§1 第八步）。每线程寄存器用量越过一档位边界，每 SM 可常驻的 warp 数就掉一档，占用率随之下降——而占用率正是延迟隐藏的本钱。于是同一份代码出现「少算了几个中间量，反而更快」的现象，因为省下的寄存器换回了更多并发 warp。

**规避**：把寄存器用量当成一个需要主动查看的指标，编译时加 `--ptxas-options=-v` 或 `-Xptxas -v` 看 `Used N registers`，并结合架构的档位粒度判断它落在哪一档；用 `__launch_bounds__`、`__restrict__`、减少活跃变量、把循环中的地址计算外提等方式压低用量。经验判据：由于粒度是 8，用量落在 33～40 时实际都按 40 计，把它压到 32 能立刻换回一整档常驻 warp 数——**优先消除「刚好越过档位边界」的那一两个寄存器**，收益通常远大于继续做等价变换。

### 4.3 `__launch_bounds__` 误用

**现象**：为了让占用率最大化，把 `__launch_bounds__(threadsPerBlock, minBlocksPerMultiprocessor)` 的 `minBlocksPerMultiprocessor` 设得很大（例如按「能塞多少 block 就写多少」），结果性能反而明显下降。

**成因**：这个参数不是一个可以被任意推高的目标，而是一条**硬约束**。编译器必须保证 `minBlocksPerMultiprocessor` 个 block 同时常驻时寄存器不超支，于是每线程可用寄存器被压到

```text
每线程寄存器上限 = 65536 ÷ ( minBlocksPerMultiprocessor × threadsPerBlock )
```

约束过紧时，编译器只能强行压低寄存器数（例如 `__launch_bounds__(256, 2)` 会把上限压到 128），压不下就把活跃变量溢出到 local memory——而 local memory 物理上位于**片外**，每次 spill 都是一次真实的全局访存，延迟比寄存器高两个数量级以上。于是出现自相矛盾的结果：占用率名义上提高了，每个 warp 的实际工作量却因为反复 spill 而暴涨，总吞吐下降。

**规避**：把它当作**上限保护**而不是优化目标——只在确认寄存器用量超出预期、需要压制时才设，且 `minBlocksPerMultiprocessor` 取「经过验证确实能达到」的值而不是理论上限。设置后必须用 profiling 验证是否发生了 spill（查看 local memory 的访存统计与 `STL/LDL` 指令是否出现），并在同一份代码上对比设置前后的实测耗时；若耗时变差且出现 spill，就放宽该参数。

## 6. 小结与延伸

本文只有一条主线：**寄存器文件是预算，不是缓存**。它必须为 SM 上全部常驻线程静态预留，无法超额分配，因此每线程多用一档寄存器，可常驻 warp 数就下降一档，并行度上限随之下降。围绕这条主线，有三个可独立复用的中间结论：

1. 本文推导出的两项约束：架构的常驻 warp 上限与寄存器预算（完整上限是四条取最小，另两条见下）。其中寄存器最常成为瓶颈，因为它正好卡在真实 kernel 的用量区间里。
2. 寄存器预算的推算只需要两个数：`寄存器文件大小 ÷ (每线程寄存器数 × 32)`，再与架构上限取较小者。别忘了分配粒度带来的上取整。
3. CUDA core 数是数据通路宽度，不是并发线程数。任何把 lane 数当作并行路数的规划都会高估一个数量级。

接下来两篇承接本文的不同侧面。[02-simt-and-divergence](02-simt-and-divergence.md) 讲清「一条指令发射给 32 个 lane」之后会发生什么——当 lane 之间的控制流分叉时，硬件如何用 active mask 与重汇聚栈处理，以及为什么发散会让并行度按路径数打折。[03-occupancy-and-latency-hiding](03-occupancy-and-latency-hiding.md) 把本文的两条约束补全为完整的占用率计算——补上共享内存与每 SM 最大常驻 block 数，凑齐四大约束取最小，并从 Little 定律出发推导「为什么需要这么多常驻 warp」——那将回答本文留下的一个问题：常驻 warp 数掉到多少才算太低。
