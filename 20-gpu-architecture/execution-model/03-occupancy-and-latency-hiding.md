# 占用率与延迟隐藏

> GPU 开那么多线程，主要目的不是并行计算，而是**用并发掩盖延迟**——理解了这一点，才知道占用率该追到多少、什么时候不该追。

## 0. 背景与动机

一个访存密集的 kernel：每个线程读入若干元素、累加、写回一个结果。第一轮调优把 block 从 128 线程改成 256 线程，**预期耗时几乎不变**；改成 512，**预期还会略慢一点**（本文无实测数据，数字口径见下）。**线程数翻了几倍，性能纹丝不动，继续加还会倒退。**

这与 [01-sm-internals](01-sm-internals.md) §0 的直觉相反：既然 SM 的价值在于「挂住更多 warp 来掩盖延迟」，线程越多、能掩盖的延迟就该越多，收益为什么会在某个点上饱和，甚至反转？

要回答它，得先回答一个更基本的问题：**掩盖一份延迟到底需要多少并发？** §1 要推导的式子会给出**两个**数——一个来自流水线（SM 想按多快的节奏发起访存），一个来自内存（HBM 每秒能供多少字节），两者取较小的那个才是有效目标。而**「哪一个更小」不靠比较这两个数，靠一条与延迟无关的判据**：请求宽到约 51 字节以上，内存侧就先饱和。

本算例的访存是 128 字节的合并访问，远超这条线。于是开头那个 kernel 的处境不是「并发不够」，而是它**已经在带宽受限区**——加线程自然没有用，加得不对还会因为多花寄存器而倒退。这也说明「占用率高不高」单独回答不了任何问题：得先知道约束落在哪一侧。

于是本文要回答两个问题，§1 各给出一处推导：

1. **需要多少**：从 Little 定律推出「掩盖一份延迟所需的在途请求数」。这条定律要用两次——一次算流水线的需求，一次算内存的供给，**取较小者**才是有效目标（推导一）。
2. **能给多少**：一个 kernel 实际能提供多少常驻 warp，由四项资源上限**取最小**决定——[01-sm-internals](01-sm-internals.md) §1 已推导其中两项（架构常驻 warp 上限、寄存器预算），本文补齐另外两项（共享内存、每 SM 最大常驻 block 数），凑成完整公式（推导二）。

> **全文的数字口径**：本文所有时间、倍数与占用率都是**推导值**，由 §1 的公式代入公开的硬件规格算出，没有任何一项来自本文的实测。延迟量级沿用 [02-simt-and-divergence](02-simt-and-divergence.md) §2 已给过的那一组。要复核这些数，最小实验是配套程序 `code/03_occupancy_probe.cu`（见文末「编译与运行」）。凡是引用本文数字的下游文档，请沿用这个口径。

## 1. 原理

本文引入一个定义与一对缩写。

**占用率（occupancy）**，即 [01-sm-internals](01-sm-internals.md) §0 用过的那个比例，这里把它写成定义：

```text
占用率 = 实际常驻 warp 数 ÷ 每 SM 最大常驻 warp 数
```

一对缩写是 **TLP（线程级并行，thread-level parallelism）** 与 **ILP（指令级并行，instruction-level parallelism）**——两者都是「让访存同时在途」的手段：**TLP 靠更多常驻 warp 提供并发，ILP 靠单个线程内多条互不依赖的访存同时在途**。它们此消彼长的关系是 §1 第六步的主题。

下面两处推导分别回答「这个比值该多大」（推导一，需要多少）与「分子从哪来」（推导二，能给多少）。先讲需求，因为不知道需要多少，就算不出多少才算够。

### 推导一：掩盖一份延迟需要多少在途请求

**第一步：写出 Little 定律。** 一个稳定运行的系统里，平均有多少「请求」正停在系统内部，等于请求的到达速率乘以每个请求平均停留多久：

```text
在途请求数 = 到达率 × 平均驻留时间
```

这不是近似，也不依赖任何 GPU 细节——它只是「数守恒」：若每秒进来 λ 个请求、每个待 L 秒，那么任意时刻平均有 `λ · L` 个还在里面。

**第二步：把三个量翻译成 GPU 语言。**

| Little 定律里的量 | 在 GPU 上对应什么 |
|---|---|
| 请求 | 一条已经发射、还没拿到数据的访存指令（在途 load） |
| 平均驻留时间 | 访存延迟 `L` |
| 到达率 | 每周期愿意发出的访存指令数 |

**第三步：需求侧与供给侧分别算一遍。**

*需求侧*——这个 kernel 的指令流平均每隔 `I` 个周期就有一条访存指令，所以它希望访存单元以 `1 / I` 的速率接收请求。`I` 由指令配比与发射率共同决定：若平均每 4 条指令里有一条访存、而 SM 平均每周期发射 1 条指令，则 `I = 4`；访存占比更高或发射率更高，都会把 `I` 压小。

这里的发射率取的是**满发射**口径（SM 每个周期都在发射指令），**这是最乐观的情形**：真实发射率更低时 `I` 会变大，算出的需求随之变小。所以下面得到的 `L / I` 是**需求的上界**——先按最乐观口径估，是保守的做法。

*供给侧*——一个「发射一条访存就停在那里等结果」的 warp，每条访存要占住它 `L` 个周期，所以单个 warp 能交出的访存速率只有 `1 / L`。

**第四步：配平。** 设常驻 `W` 个 warp，SM 级的总速率是 `W / L`；要求它达到需求侧的 `1 / I`：

```text
W / L = 1 / I        ⟹        W = L / I
```

**第五步：代入数值。** 取 `L = 600` 个周期（§2 给出的 400～800 的中点）、`I = 4`：

```text
W = 600 / 4 = 150
```

需求侧对 `I` 很敏感，把 `I` 变一变就能看出**流水线侧**的需求何时能被 TLP 满足：

| `I`（平均每几条指令一条访存） | 流水线侧所需 warp 数 `L / I` | 64 个 warp 够吗 |
|---|---|---|
| 4（访存密集） | 150 | 不够 |
| 8 | 75 | 不够 |
| 16 | 37.5 | **够** |

也就是说，**单看流水线这一侧，只有访存稀疏到平均每 16 条指令才有一条时，64 个 warp 才够**；访存密集的 kernel 需要的并发是架构上限的两倍以上。不过这只是问题的一半——下一步要问的是内存供不供得起这个节奏。

**第六步：把并发的两个来源拆开。** 上面的 `W = 150` 是「每个 warp 只挂 1 个访存」的口径。换成「跑满 64 个 warp 之后，每个 warp 还要挂几个」：

```text
150 ÷ 64 ≈ 2.3        ⟹   平均每个 warp 还要有约 3 个独立访存在飞行中
```

```text
在途访存数 = 常驻 warp 数 × 每 warp 平均在途访存数
                 ↑ TLP              ↑ ILP
```

（两个缩写见本节开头。）占用率只描述右边第一项。第二项靠指令级并行——同一线程里多条互不依赖的访存，编译器把它们连着排下去，硬件为每一条各占一个记分板位与一个目标寄存器，于是它们同时在途。**推导二的公式算不出 ILP，这就是为什么「占用率」永远只是并发的一个侧面。**

**但先别急着下「TLP 不够、必须 ILP」这个结论。** `150` 是**流水线侧**的需求，它问的是「要让 SM 按指令配比的节奏发起访存，得有多少请求在途」——而它默认了一件事：内存供得起这个节奏。这件事必须先查。

**第七步：用同一条 Little 定律查供给侧。** 把「请求」换成「字节」，公式照写：

```text
在途字节数 = 带宽 × 延迟
```

对 H100 SXM：每 SM 能分到的 HBM 带宽约 `3350 GB/s ÷ 132 ≈ 25.4 GB/s`，按 1.98 GHz 折算约 12.8 字节/周期；乘 600 个周期，得 **打满这份带宽需要约 7.5 KB 在途**——注意这是**需求量，不是硬件容量**：内存不限制在途请求的条数，它限制的是吞吐。而一条对齐且完全合并的 warp 访存取回 128 字节，折成请求数就是

```text
7.5 KB ÷ 128 B ≈ 60
```

**两个 Little 定律给出两个数：流水线侧要 150，内存侧的饱和点是 60。** 它们问的是两个不同的问题，而**实际起作用的是较小的那个**——到达率不可能超过内存能供的速率。

**要判断「哪一侧是约束」，不必比较这两个数——有一条不含 `L` 的判据。** 内存每周期供 12.8 字节，若一条请求要 `B` 字节，它能供出 `12.8 / B` 条请求/周期；流水线想发 `1 / I` 条。谁小谁就是约束：

```text
供给速率 ≤ 需求速率   ⟺   12.8 / B ≤ 1 / I   ⟺   B ≥ 12.8 × I = 12.8 × 4 ≈ 51 字节
```

**这个式子里 `L` 被约掉了**，阈值只取决于带宽、SM 数、频率与指令配比——都是稳的量。于是判据变得很干净：

- **每请求 ≥ 约 51 字节 → 内存侧先饱和。** 这个 kernel 是**带宽受限**的：加 warp 无用（§4.3），该做的是减少访存量。本算例一条合并访存取回 128 字节，远超这条线，直接落进这一侧。
- **每请求 ≤ 约 51 字节 → 流水线侧成为约束。** 散列访问会落到 32 字节的 sector 上，此时内存每约 2.5 个周期就能供一条，快于流水线想发的每 4 个周期一条——答案是 150，而 `150 > 64`，**必须靠 ILP**。

那个 `60` 只是给这条判据配的例证：**`60` 与 `64` 落在同一量级，即使按 128 字节这个最窄的口径估，64 个 warp 也只是刚够**。而 `L` 在 `400～800` 之间取值时这两个数会互换大小（取 700 就得 70，反而超过 64），**所以别把「60 < 64」当成一条硬结论——结论是不依赖它们谁大谁小的那一条**：请求宽到 128 字节，就是内存侧先饱和，加并发换不来吞吐。

**「需要多少并发」因此不是 kernel 的固有属性，而是「请求有多宽」与「延迟有多长」共同的结论**——这也是 §4.2 与 §4.3 的定量依据。

**第八步：换一档延迟做对照。** 把 `L = 600` 换成共享内存的 20～30（§2）：`30 / 4 ≈ 8`——**8 个 warp 就能掩盖共享内存延迟**，只占 64 的 12.5%；L1 命中的约 30 个周期同理。这一档的好处是两侧都不会成为约束：延迟短，流水线侧只要几个在途请求，内存侧也远没饱和。**只有全局访存这一档长延迟，才值得动用占用率去掩盖**；短延迟几个 warp 就填满了，把占用率推到 100% 换不到任何东西。

### 推导二：一个 kernel 实际能挂住多少 warp——四项约束取最小

**第九步：列出四条独立上限。** 常驻 warp 数不是可以任意设定的数字，而是四条上限的**最小值**。其中第一行（寄存器）与第四行（线程上限）在 [01-sm-internals](01-sm-internals.md) §1 已经推导过，本文补齐中间两行——共享内存与每 SM 最大常驻 block 数：

| 约束 | 上限（warp 数 / SM） | 为什么是这个式子 |
|---|---|---|
| 寄存器 | `floor(65536 ÷ (r × 32))` | 01 §1 第三步已推导：一个 warp 占 `32r` 个寄存器，不能超售 |
| 共享内存 | `floor(S_max ÷ S_b) × W_b` | 共享内存按 **block** 整块预留，故先算能放几个 block，再乘每 block 的 warp 数 |
| 常驻 block 数 | `B_max × W_b` | 硬件对每个 SM 能同时挂住多少个 block 另有独立上限 `B_max`。它不由寄存器或共享内存容量决定，而由 SM 要为每个 block 维护的状态（barrier 计数、退出与资源回收记录）决定；Hopper 数据中心线为 32 |
| 线程数 | `2048 ÷ 32 = 64` | 架构的每 SM 线程上限除以 warp 宽度 |

其中 `r` 是每线程寄存器数，`S_max` 是每 SM 可用共享内存字节数，`S_b` 是每 block 申请的共享内存字节数，`W_b` 是每 block 的 warp 数，`B_max` 是每 SM 最大常驻 block 数。

**注意四条约束的单位并不统一，这是本节最容易错的一步。** 后两行先得到「block 数」，必须乘上 `W_b` 才能与前面比较；而前两行的「warp 数」其实也只是一个上界——**寄存器与共享内存都是按 block 分配的，装不满一个 block 就不装**。严格地说，每条约束都要先算「每 SM 能容纳几个 block」，再乘 `W_b`。以寄存器为例，`r = 24`、`W_b = 8` 时每 block 要 `8 × 24 × 32 = 6144` 个寄存器，`floor(65536 ÷ 6144) = 10` 个 block，即 **80** 个 warp，而不是 `floor(65536 ÷ (24 × 32)) = 85`。[01-sm-internals](01-sm-internals.md) §1 用的正是未做这层取整的版本——它当时就给的是一个**成立的上界**，本文的算例里最小值不落在寄存器上，两者不会产生差别。

最后一行那个 64 就是 [01-sm-internals](01-sm-internals.md) §1 第四步里的 `W_max`——它来自线程数上限，两个名字指的是同一个数。四条合起来就是本文承诺补全的完整公式：

```text
每 SM 常驻 warp 数 = min( floor(寄存器文件 ÷ (r × 32)),
                          floor(S_max ÷ S_b) × W_b,
                          B_max × W_b,
                          每 SM 线程上限 ÷ 32 )
```

**第十步：算一个例子。** 在 Hopper（`S_max = 228 KB`、`B_max = 32`、每 SM 2048 线程）上启动一个 block = 256 线程（`W_b = 8`）、每线程用 32 个寄存器（`r = 32`）、每 block 申请 36 KB 共享内存（`S_b = 36 KB`）的 kernel：

| 约束 | 代入 | 上限（warp 数） |
|---|---|---|
| 寄存器 | `floor(65536 ÷ (32 × 32)) = 64` | 64 |
| 共享内存 | `floor(228 ÷ 36) = 6`，`× 8` | **48** |
| 常驻 block 数 | `32 × 8` | 256 |
| 线程数 | `2048 ÷ 32` | 64 |

四项取最小：**48 个 warp**，占用率 `48 ÷ 64 = 75%`。

**第十一步：反解第三项，看它什么时候才可能生效。** 把 `B_max × W_b` 与线程上限比一比：

```text
B_max × W_b ≥ 64     ⟺     W_b ≥ 64 ÷ B_max = 64 ÷ 32 = 2
```

也就是说：**每 block 有 2 个 warp（64 线程）时这一项恰好与线程上限相等（并列，还不是瓶颈）；有 3 个 warp（96 线程）以上时，它就恒大于线程上限，不可能再成为最小值。** 算例里它给出 256 纯属虚高，真正竞争的只有寄存器、共享内存与线程上限三项——能让它成为**唯一**最小值的只有 32 线程的极小块（`W_b = 1`，此时它给出 32）。这条结论依赖 `B_max`，而 `B_max` 随架构分档、不能想当然：Turing（CC 7.5）的 `B_max` 是 **16**，线程上限 1024（`W_max = 32`），饱和条件是 `16 × W_b ≥ 32`，即同样要 `W_b ≥ 2`——**并不比 Hopper 宽松**。数据中心线为 32，CC 7.5 / 8.6 为 16，CC 8.9 为 24；四个数必须在同一架构上取，不能混用。

**第十二步：换一个输入，看占用率的变化率。** 这一步说明为什么占用率适合当**约束**而不是**目标**：

| 改动 | 受影响的约束 | 新的最小值 | 占用率 |
|---|---|---|---|
| 起点 | — | 48 | 75% |
| `r` 从 32 压到 24 | 寄存器 64 → 80（按 block 取整，见第九步） | **48（不变）** | 75% |
| `S_b` 从 36 KB 降到 18 KB | 共享内存 48 → 96，被线程上限 64 截断 | 64 | 100% |

压寄存器**什么都没换到**，因为瓶颈根本不在寄存器；真正卡住占用率的是共享内存。所以顺序永远是：**先看最小值是哪一项，再决定动谁**——否则最自然的那个动作（压寄存器）恰好是无效的那个。

## 2. 执行映射

### 一次访存从发射到返回，硬件在做什么

参与者是 [01-sm-internals](01-sm-internals.md) §2 已经点过名的几个部件，这里关心它们在同一段时间里的分工：

- **warp scheduler**：每周期从分配给自己的就绪 warp 里挑一条指令发射（每 SM 4 个，故每 SM 每周期最多 4 条）。
- **记分板（scoreboard）**：为每个 warp 记录「哪几条在途指令还没回来」。一条 `LDG` 发射后，对应位被置起。
- **LSU（load/store unit）**：接受访存指令，把 warp 的 32 个地址合并成尽量少的事务（正文在 `20-gpu-architecture/memory-system`，此处回链）。
- **寄存器文件**：65536 个 32-bit 寄存器（256 KB）。在途访存的目标寄存器必须整份占在这里，不能挪走（01 §1 第八步）。
- **指令流水线**：执行单元本体。它不会因为某个 warp 缺操作数就整条暂停——流水线是分级的，堵住的是那个 warp。

一次典型的事件序列：

1. 调度器发射一条 `LDG`，同时把该 warp 的一个记分板位置起；
2. 此后这个 warp 不能被发射任何**依赖该结果**的指令。若它后续的指令全都依赖，调度器就把它视为 stall，本周期改选**别的就绪 warp**；
3. 数据从 L2 或 HBM（显存）返回，写进目标寄存器，记分板位清除，该 warp 回到就绪队列（L2 与 HBM 的延迟、带宽如何分级，正文在 `20-gpu-architecture/memory-system`，此处回链）。

**第 2 步是整套设计的核心：被等待的 warp 不是「阻塞」，而是「换掉」。** 而换掉之所以几乎免费，是因为**不需要保存任何上下文**——每个线程的寄存器从一开始就静态分配在寄存器文件里的固定位置（01 §1），换一个 warp 发射只是换一个指针。如果寄存器需要像 CPU 上下文那样换入换出，每次等待就要额外付一次内存访存，整套「靠多 warp 掩盖延迟」的设计立刻失效。

**这也是寄存器文件必须那么大的原因**（65536 个，自 Volta 至 Blackwell 未变）：它不是「缓存」，而是「全部常驻 warp 的状态必须都是常驻的」。01 §1 从占用率上限的角度推导过同一件事，这里是它的另一半——**同一份预算同时是 warp 切换免费的前提**。

### ILP 与 TLP 为什么互相替代

§1 第六步把并发拆成 `TLP × ILP`。两者不是可以同时加满的两个独立维度，因为它们从**同一份寄存器文件预算**里取用：ILP 要求一个线程里多条在途访存的目标寄存器**同时活着**（`k` 条在途就是 `k` 个寄存器同时被占用），TLP 要求更多 warp × 各自的 `r` 个寄存器。同一份 65536，多分给 TLP 就少分给 ILP，反之亦然。**这是「提高占用率」这个动作天然带着代价的硬件原因**——§4.1 会给出这笔交换的具体数字。（前提仍是 §1 第七步那条分界线：这笔交换只在延迟受限的那一侧才体现在性能上。）

### 四条延迟量级，与一条粗判据

| 延迟源 | 量级（cycles） | 掩盖它需要几个在途请求（流水线侧，`÷ I = 4`） |
|---|---|---|
| 共享内存访问 | 20～30 | 5～8 |
| L1 命中 | 约 30 | 约 8 |
| L2 命中 | 约 200 | 约 50 |
| 全局访存（未命中 L1） | 400～800 | 100～200 |

前两行只占 64 个 warp 预算的百分之十几。**这就是「只有长延迟值得用占用率去掩盖」的全部内容**：短延迟的洞几个 warp 就填满了，把占用率从 12% 提到 100% 换不到任何东西；而 400～800 那一行，64 个 warp 全上阵也只是流水线侧需求的**不到一半**（`64 ÷ 150 ≈ 43%`）——**要不要再借 ILP，取决于内存侧供得起多少**，那笔账在 §1 第七步已经算过：请求宽到约 51 字节以上时内存侧先饱和，加并发换不来吞吐。

把 §1 第七步的结论搬到 H100 SXM 上，得到一个值得记住的量级：`3350 GB/s ÷ 132 个 SM ≈ 25.4 GB/s`，按 1.98 GHz 折算约 12.8 字节/周期，乘 600 个周期——**打满本 SM 那份带宽需要约 7.5 KB 在途**（需求量，不是硬件容量），换成 128 字节一条的合并访存就是约 60 条；而「64 个 warp 各挂一条」是 8 KB。

`64` 与 `60` 落在同一量级，但**这是巧合而不是设计**：`64` 的真正来源是线程槽位上限（`2048 ÷ 32`，[01-sm-internals](01-sm-internals.md) §1），而上面这个式子里三个量每一代都在变；吻合也只在「恰好 128 字节一条请求」这一点上成立——换成 `float4` 访存（512 字节一条），凑满同一份带宽只需约 15 个 warp；换成散列访问（32 字节的 sector），则要约 240 个。**同一份带宽，请求越宽，需要的 warp 越少**：这既解释了向量化访存为什么能让低占用率打满带宽（§4.3），也解释了窄请求为什么反而会把约束推回流水线侧（§1 第七步）。

### 02 留下的那个问题

[02-simt-and-divergence](02-simt-and-divergence.md) §6 问：一个 warp 因为发散慢了几倍，为什么整机吞吐不一定跟着慢几倍？答案就在上面第 2 步：**那个 warp 在合流点（`BSYNC`）等另一批 lane 到齐时，它只是从「就绪」变成了「不就绪」，调度器下一周期就从别的就绪 warp 里挑一条发射。** 发射槽被填掉了，这个空洞没有传到墙上时间里。

代价因此是**有条件**的：只有当 SM 上还有别的就绪 warp 可挑时，空洞才会被填掉。**占用率在这里的作用不是「让单个 warp 变快」，而是「让填补空洞的候选者足够多」。** 一个发散的 warp 打了折，但它空出来的发射槽需要别人接住——这就是「单 warp 效率」与「整机吞吐」之间隔着的那道占用率。

## 3. 实现与演进

本节按「为什么需要下一步」给出**三步改进**（改进一 / 二 / 三），它们的目标都是把 §1 推导二算出来的占用率变成**可操作、可验证**的数。后面另有两节不属于这三步：**演进**讲调优目标如何从「追高占用率」转向「追求足够的延迟隐藏」，**前沿**讲两处正在松动本文前提的硬件特性。

### 朴素做法：凭经验试 block 大小

最常见的起手式是把 block 设成 128 或 256，跑一遍；再换个值跑一遍，挑快的。只调一个旋钮时这还行，但 §1 推导二说明结论由三个变量（`r`、`S_b`、`W_b`）与两个架构常量（`B_max`、线程上限）共同决定，而其中只有 `W_b` 跟着 block 大小走——`r` 由编译器在编译期定、`S_b` 由代码里的共享内存申请定，**两个都不在启动配置里**。所以「换几个 block 大小试试」是在一个多变量空间里沿一条线乱走；而且每改一次源码 `r` 就变，上一次的结论随之作废。

**需要下一步的理由**：应该有个工具，直接按 §1 的公式把四项算完，而不是靠试。

### 改进一：用 API 精确计算理论占用率

`cudaOccupancyMaxActiveBlocksPerMultiprocessor` 就是那个工具：给定 kernel、block 大小与每 block 动态共享内存字节数，它返回该配置下每 SM 最多能常驻几个 block。

```cuda
int blocksPerSM = 0;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &blocksPerSM,       // 出参：每 SM 最大常驻 block 数
    occ_kernel,         // kernel 指针（函数名本身，不是 <<< >>> 启动语法）
    kBlockThreads,      // 每 block 线程数
    kDynSmemBytes);     // 每 block 动态共享内存字节数

int warpsPerBlock = kBlockThreads / 32;
int residentWarps = blocksPerSM * warpsPerBlock;            // 就是 §1 推导二的「四项取最小」
float occupancy   = (float)residentWarps / maxWarpsPerSM;   // maxWarpsPerSM = 每 SM 线程上限 ÷ 32
```

**第 4 个参数必须与真正启动 kernel 时传的动态共享内存字节数完全一致**，否则算出来的不是你要跑的那个配置。这一点在本示例里被用来做文章：把 `kDynSmemBytes` 从 1 KB 扫到一个较大的值（kernel 至少要为自己的 tile 申请 `blockDim` 个元素的共享内存，低于 1 KB 会越界），就能看到占用率沿 §1 推导二里**共享内存那一行**逐级台阶式下降——其余三项不动，只有这一项在变。

配套程序 `code/03_occupancy_probe.cu` 做的就是这件事：扫共享内存、扫 block 大小、读设备属性，把四项约束与最终占用率一起打印出来。

**它是上界，不是预测。** 它算的是「架构允许挂住多少 warp」，不含任何运行时效应（warp 实际在访存上停了多久、grid 是否小到填不满 SM）。所以它回答的是 §1 推导二，不是推导一。

**需要下一步的理由**：它只能回答「能放几个」，不能回答「该放几个」——当编译器为了换 ILP 而多用寄存器、把第一行压低时，缺的是一个**反向**的、能直接约束编译器的旋钮。

### 改进二：用 `__launch_bounds__` 反向约束编译器

那个反向旋钮就是 `__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)`——**它告诉编译器「每 SM 至少要放下 `minBlocksPerMultiprocessor` 个 block」**，编译器据此反推每线程寄存器的上限，并在寄存器分配时遵守它。

它在 §1 那张表里的位置很明确：**它直接锁住第一行（寄存器）**。01 §1 说明过寄存器通常是真正起作用的那一项，所以这是四行里最对症的一个——当编译器为了 ILP 用了过多寄存器、把占用率压到需求以下时，用它把寄存器用量封顶，就能把第一行抬上去。**但前提是先确认卡住的就是第一行**（§1 第十二步算过：瓶颈在共享内存时压寄存器什么都换不到），否则这个旋钮同样是在空转。

`minBlocksPerMultiprocessor` 设得过大时的后果（寄存器被压得太狠 → 溢出到 local memory → 更慢）在 [01-sm-internals](01-sm-internals.md) §4.3 已经推导过，此处回链，不重复。

**需要下一步的理由**：它是闭着眼睛压的——压到多少只能事后看结果，压过头就是 spill。要把它用好，需要一个能看见 `r` 实际取值的入口。

### 改进三：把编译器报告代进公式

`-Xptxas -v`（等价于 01 §1 用的 `--ptxas-options=-v`）会打印每个 kernel 的 `Used N registers`。这个 `N` 就是 §1 推导二第一行的 `r`，代进去立刻得到寄存器约束的值；再与另外三项比，就知道当前的占用率被谁卡住、下一步该动哪一项（§1 第十二步算过：动错项可能什么都换不到）。它同时报告 spill 的字节数，那是「寄存器是不是被压过头了」的直接证据。**压低寄存器用量的具体手段**（`__restrict__`、减少活跃变量、外提循环中的地址计算、利用 8 个寄存器一档的粒度）属于 [01-sm-internals](01-sm-internals.md) §4.2，此处回链。

### 演进：从「追高占用率」到「追求足够的延迟隐藏」

早期的占用率调优把 100% 当成目标，理由是「越多越能掩盖延迟」。§1 的两处推导把这件事拆开了：**需要掩盖多少由延迟与指令配比决定（推导一），能提供多少由四项取最小决定（推导二），两者之间只有「够不够」的关系，没有「越多越好」的关系。**

- 越过需求之后，继续提高占用率只会消耗预算：寄存器预算被摊薄 → ILP 变少（§4.1 会算这笔账）；共享内存被摊薄 → block 级的复用变少。
- 有些 kernel 的占用率**天然很低，而且不该提**：Tensor Core 上的大 tile GEMM，单是 FP32 累加器就可能吃掉 128 个寄存器/线程（[01-sm-internals](01-sm-internals.md) §3 对 Hopper 的计算），`floor(65536 ÷ (128 × 32)) = 16` 个 warp，占用率 25%。这类 kernel 靠 ILP 与 TMA 掩盖延迟、靠 Tensor Core 把算力堆在少数 warp 上——**用占用率去评价它，评价的是错的东西。**
- 现代调优的表述因此是「占用率够用即可」：先由推导一算出需要多少在途请求，再检查当前配置能不能提供，而不是先定一个百分比目标。

### 前沿：正在松动的两个前提

上面三步都建立在一条前提上：**每线程的寄存器数由编译器在编译期定死，运行期不能变**（[01-sm-internals](01-sm-internals.md) §1 第一步）。§2 也正是靠这条前提才得出「warp 切换不需要保存上下文、因此几乎免费」——寄存器静态躺在文件里，换 warp 只是换指针。近两代硬件在这条前提上各开了一个口子。

**其一，寄存器额度可以运行期调配。** Hopper（CC 9.0）引入 PTX 指令 `setmaxnreg`（`.inc` / `.dec`，带 `.sync` 后缀）：一个 warpgroup 可以在运行期把寄存器额度交还到 block 级的寄存器池，或者从池里要回来（要不到时会阻塞），代价是一次 warpgroup 级的显式同步。可设的额度落在 24～256 之间、且必须是 **8 的倍数**——正是 [01-sm-internals](01-sm-internals.md) §1 第七步那个分配粒度。它改变的不是总量（65536 不变），而是**同一 block 内不同 warp 之间的分配**：第一行（寄存器）于是从一个编译期常量，变成了可以在时间轴上分时复用的预算。

它服务的正是 [02-simt-and-divergence](02-simt-and-divergence.md) §3「前沿」讲的 warp specialization：生产者 warp 只需要很少的寄存器来做 TMA 搬运，消费者 warp 需要很多来放累加器。让生产者在搬运阶段把额度交出去、消费者接过来，**两类 warp 于是能同时住在同一个 SM 上**——静态分配下这是做不到的：第 2 行（共享内存）与第 4 行（线程上限）都还有余量，唯独第 1 行两边都要。

**其二，分配的粒度从「每 SM」长到了「每簇」。** 01 §3 讲过线程块簇（thread block cluster）让簇内 block 能互访共享内存；在占用率这一侧，它的含义是**四约束取最小又多长出了一维**。一个簇的 block 必须同时落进同一个 GPC，于是「整只簇装不装得下」成了新的门槛，`cudaOccupancyMaxActiveClusters` 就是回答它的 API。**资源不再每 SM 独立结算，而是以簇为粒度成组分配**：先要装得下几个 SM 的簇，才轮到每个 SM 装几个 block。§1 的推导在这里仍然成立——它算的是每个 SM 的账——但它成了簇级分配的内层。

## 4. 踩坑与失败模式

### 4.1 占用率不是越高越好

**现象**：一个延迟受限的 kernel，把占用率从 50% 提到 100%（通常是靠 `__launch_bounds__` 把寄存器压下去），耗时反而变长。

**成因**：**占用率不是并发，它只是并发的一个因子。** §1 推导一已经把它拆开了：`在途访存数 = 常驻 warp 数 × 每 warp 在途访存数`。而提高占用率的手段（压寄存器）恰好砍掉第二个因子——寄存器少了，编译器能同时挂在飞行中的独立访存就少了。把两个配置并排看（注意：这笔交换只在 §1 第七步划出的**延迟受限**一侧才成立，下面会说）：

| 配置 | 每线程寄存器 | 常驻 warp（占用率） | 每 warp 在途访存 | 在途访存总数 |
|---|---|---|---|---|
| A：买 TLP | 32 | 64（100%） | 1 | **64** |
| B：买 ILP | 64 | 32（50%） | 5 | **160** |

两者的寄存器用量都是 `warp 数 × r × 32 = 65536`，把同一份预算花光了，只是花法不同。推导一算出需求是 150：**A 不够（即使把 ILP 记作 2 也才 128），B 够。占用率 50% 的那个配置，掩盖延迟的能力反而更强。**

**这笔交换有效的前提是「需求超过了内存能供的速率」**（§1 第七步的分界线）。只有当每请求字节数足够窄——约 51 字节以下——内存侧供得起流水线想要的速率时，150 这个需求才有意义，A 与 B 的差别才会体现在性能上。反过来，若请求是 128 字节的合并访存，内存侧的饱和点约 60 个请求：A 的 64 与 B 的 160 都越过了这条线，**两者都能打满带宽，那这笔交换换的就是空气**，此时该做的是 §4.3 的事。

另一条把性能拉低的路径是寄存器被压到 spill——那是 01 §4.3 的坑，代价由 local memory 的访存兑现（正文在 [01-sm-internals](01-sm-internals.md) §4.3，此处回链）。

**规避**：把占用率当**约束**而不是**目标**。可操作的形式是把评价指标换成**在途请求数**：由推导一算出需求（`L / I`），再检查当前配置的 `warp 数 × 每 warp 在途数` 够不够。这个量比占用率难测，但它才是与性能同向的那一个。

### 4.2 把 occupancy 当唯一指标

**现象**：两个 kernel 占用率都是 50%，耗时差几倍；于是拿占用率当筛选依据，挑出「理论最好」的那个，跑起来最慢。

**成因**：占用率只回答「有多少 warp 可用」，完全不回答**这些 warp 的访存长什么样**。§2 说过，与带宽同向的量是在途**字节数**（`在途字节数 = 带宽 × 延迟`），而占用率只管在途**请求数**。两者之间还夹着一个「每个请求搬回多少有用字节」，它由合并程度决定。以一次 warp 访存为例：32 个 lane 读连续排布的 4 字节元素时，硬件发 1 个 128 字节事务、占 4 个 32 字节的 sector（sector 是访存的最小传输单位），取回的 128 字节全部有用；若这 32 个 lane 散落在 32 条不同 cache line 上，硬件就要发 32 个请求、占 32 个 sector，而有用数据仍然只有 128 字节。**8 倍的差距落在在途字节数上，占用率这个数字却一个字都不变。** bank 冲突是同一件事在共享内存上的版本：占用率同样看不见它。（两条正文都在 `20-gpu-architecture/memory-system`，此处回链。）

**规避**：先用 profiling 确认瓶颈类型（计算受限 / 带宽受限 / 延迟受限），再决定动不动占用率——这一步不能靠猜，而要读计数器（profiling 的正文在 `50-performance`，此处回链）。**占用率只在「延迟受限」时才是可动的旋钮**；其余两种情况下它既不是原因也不是解法。

### 4.3 在带宽受限的 kernel 上追占用率

**现象**：一个纯拷贝类 kernel，算法一字不改，只调启动配置（block 大小、寄存器上限、共享内存占用），占用率在 50%～100% 之间变，耗时几乎不动。

**成因**：它就是 §1 第七步里「内存侧的数是较小的那个」那一类 kernel。§2 把这条线量化了：每 SM 约 8 KB 在途字节（约 60 个 128 字节的合并请求）就能打满 HBM。拷贝类 kernel 用向量化访存（一条 `float4` 就是 512 字节）配合循环展开，**在相当低的占用率下就已经越过这条线**。越过之后，再增加并发只是给一个已经饱和的队列排队——HBM 每秒能搬的字节数不会因此增加，而为了提占用率付出的寄存器或共享内存代价仍然要付。**延迟隐藏解决的是「访存单元空转」，带宽受限时访存单元根本没有空转。**

**规避**：先用 roofline 判断算子落在带宽侧还是计算侧（正文在 `50-performance`，此处回链）。带宽受限的算子的优化方向是**减少访存量**——算子融合、降低精度、提高数据复用——而不是增加并发（正文在 `20-gpu-architecture/memory-system`，此处回链）。

## 编译与运行

配套程序 `code/03_occupancy_probe.cu` 按 §1 推导二做三件事：打印本设备的 `S_max`、`B_max` 与线程上限（标题行）；给出该配置下每 SM 的常驻 block 数与占用率，**其中占用率一列取自 `cudaOccupancyMaxActiveBlocksPerMultiprocessor`**；再扫描每 block 动态共享内存字节数（从 1 KB 起），打印占用率沿共享内存那一行逐级下降的台阶（对应 §3 改进一的用法）。

**它没有手算列，验证方式是人机对照**：拿打印出来的三个设备常量，按 §1 推导二的四行公式在纸上各算一次、取最小值，再与程序给出的 `blocksPerSM × (blockDim ÷ 32)` 比。**两者相等，才说明四项约束确实找齐了**；不等就说明漏了一项（推导二那张表就是对照表）。这也符合 §0 的口径声明——程序给的是 API 的答案，手算那一列得由读者自己填。顺带还能复算推导二第十一步那个反解：把 block 调到 64 线程以下，看 `B_max × W_b` 是否开始成为最小值。

## 6. 小结与延伸

本文的主线一句话可以讲完：**占用率是延迟隐藏的一个来源，不是它的度量；它是约束，不是目标。** 围绕这条主线，有三个可独立复用的中间结论：

1. **需要多少并发，由 Little 定律给出——而且要算两次。** 一次算流水线的需求 `W = L / I`（`L` 是访存延迟，`I` 是平均每几条指令一条访存），一次算内存的饱和点 `在途字节数 = 带宽 × 延迟`。前者问「流水线想发多快」，后者问「内存供得起多快」，**取较小者才是有效目标**。要判断哪一个更小，有一条**不含 `L`** 的判据：每请求 ≥ 约 51 字节（`= 每周期带宽 × I`）时内存侧先饱和。算例的请求是 128 字节的合并访存，落在这一侧，所以它是**带宽受限**的——加并发换不来吞吐，该减少访存量（§4.3）；内存侧那条线约 60 个请求，与 64 落在同一量级，**别把它们谁大谁小当成硬结论**（`L` 取 700 就翻过来）。只有请求窄到 51 字节以下（散列访问的 32 字节 sector），`150` 才成为约束，才必须再借 ILP（跑满 64 个 warp 之外，平均每个 warp 还要有约 3 个独立访存在飞行中）。换成共享内存的 20～30 个周期，两侧都只要 8 个 warp 上下——这就是「只有长延迟值得动用占用率」的分界线。
2. **能提供多少并发，由四项约束取最小给出**：寄存器 `floor(65536 ÷ (r × 32))`、共享内存 `floor(S_max ÷ S_b) × W_b`、常驻 block 数 `B_max × W_b`、线程数 64。后两项的单位是「block 数」，必须乘 `W_b`；而第三项只要 `W_b ≥ 3` 就恒大于线程上限，永不可能成为最小值——实际竞争的通常只有三项。
3. **把占用率当约束、把在途请求数当指标**。§1 第十二步算过：瓶颈在共享内存时，压寄存器换不到任何占用率；§4.1 的算例更进一步——在延迟受限的那一侧，压寄存器的代价是 ILP，占用率从 50% 提到 100% 反而可能让在途请求数**减少**（64 对 160）。顺序永远是：**先算出需要多少（两侧各算一次、取较小者），再看现在有多少，最后才决定动哪一项**。

三篇之间的关系可以一句话收口。[01-sm-internals](01-sm-internals.md) 推导了四大约束里的寄存器与线程上限两条，并留下一个问题——**「常驻 warp 数掉到多少才算太低」**。本文对它的回答是：**没有单一阈值，要看约束落在哪一侧**（§1 第七步）。带宽受限时（每请求 ≥ 约 51 字节），64 个 warp 已经超过打满带宽所需的量，再高换不来吞吐；延迟受限且请求很窄时，64 个只有需求（150）的约 `43%`，掉到 32 就明显不够。[02-simt-and-divergence](02-simt-and-divergence.md) 留下的「单个 warp 慢了、整机不一定跟着慢」，答案在 §2——空等中的 warp 不再就绪，发射槽被别的 warp 接住，而候选者够不够就是占用率。再往上一步，[01-hierarchy-overview](../memory-system/01-hierarchy-overview.md) 会说明 `L` 本身是怎么被分级缓存改变的，那是本文把 `L` 当作一个常数的前提。
