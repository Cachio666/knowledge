# GPU 存储层次总览

> 存储必须分级，因为容量、带宽、延迟三者不可兼得。GPU 与 CPU 的分歧在于：CPU 靠大缓存降低平均延迟，GPU 靠大量并发线程把延迟藏起来。

## 0. 背景与动机

一段在 CPU 上跑得飞快的代码：顺序扫描一个 1 GB 的数组求和。它在桌面 CPU 上是秒级的事——CPU 的预取器认得出顺序模式，在数据被用到之前几百个周期就把它搬进了 L1；单次访存落在 L1 时只要 4～5 个周期，即使落到 DRAM，也不过两三百个周期（60～90 ns，按 3～4 GHz 折算）。

把这段代码**原样**搬到 GPU——"原样"取字面义，就是同一个循环、编译成 GPU 上的**一个线程**——同样的顺序扫描、同样的整数加，却慢得多。（先把这笔账的适用范围划清：它是**单线程**的账。GPU 要拿回它自己那份带宽，前提是有几千个线程同时在途，见 §1 第五步；一个线程只能一个接一个地等，带宽再宽也用不上。）原因不在算力，也不在带宽——GPU 的访存带宽比桌面 CPU 高一个数量级以上。原因在于一个反直觉的事实：**GPU 的单次访存延迟比 CPU 还长**。

```text
CPU 的 DRAM 延迟   ≈ 60～90 ns            （公开的典型量级）
GPU 的 HBM 延迟    ≈ 400～800 cycles
                   ÷ 1.98 GHz（H100 SXM 的时钟）
                   ≈ 200～400 ns           （推导值）
```

按同一口径折算成时间，GPU 的一次片外访存要 CPU 的 3～5 倍。这不是"没造好"，而是两边选了不同的优化目标：CPU 把晶体管花在预取、乱序执行和深层私有缓存上，赌"我能猜中你要什么"，用一个低得多的**平均值**掩盖了 DRAM 本身的长延迟；GPU 把晶体管花在并行度上，不做任何猜测，而是让几千个线程同时在途——**用一个长延迟恰好就不那么致命的并发池，把同一条延迟摊薄**。这是 [01-sm-internals](../execution-model/01-sm-internals.md) 与 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) 讲的那套机制所服务的目标；本文要回答的是它下面那一层的问题。

于是有两个自然的问题，它们看起来只是"把数据放得离计算更近一点"，但都会被同一个障碍挡住：

1. **既然寄存器最快（1 个周期），为什么不把数据全放进寄存器？**
2. **既然共享内存比全局内存快一个多数量级（25 对 600 个周期，约 24 倍），为什么不把它全放进共享内存？**

两个问题的答案都是"装不下"，但**装不下的原因不一样**：一个是静态预算不够分，一个是容量太小且搬运要付代价。把这两笔账算清楚，就得到了全文的主线：**每一级的容量与延迟都是物理决定的，程序员能动的只有"把哪些数据放在哪一级、以及怎么访问它"。**

> **全文的数字口径**：本文所有 cycles、ns、倍数与容量都是**推导值**——由公开发布的硬件规格（显存带宽、时钟频率、各级容量）与物理常数换算得到，**没有任何一项来自本文的实测**。每一步算术都写在正文里，读者可以自己复核。延迟量级沿用 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §2 已公布的那一组，两篇文档给出的是同一组数。要复核这些数，入口是配套程序 `code/01_bandwidth_probe.cu`（见文末「编译与运行」）。

## 1. 原理

下面按顺序推导，每一步只引入一个量。推导只用到三个名词：**SM**（流式多处理器，容纳并调度 warp 的硬件单元）、**block**（线程块，必须整体调度到同一个 SM 上）、**warp**（32 个线程组成的调度单位）——三者的定义与关系见 [01-sm-internals](../execution-model/01-sm-internals.md) §1。

**第一步：说清"存储"为什么不可以又大又快。**

一块存储的物理形态决定了三件事，而且它们由**同一个原因**——阵列的物理尺寸——牵动：

- **容量**由位单元的数量与面积决定。位单元越小、越多，容量越大。
- **延迟**由两条路径的长度决定。其一，寻址电路：容量每翻一倍，地址就多一位，译码树深一级。其二，阵列内部的行列线：一条分布式的 RC 线，延迟按 `0.38 · r · c · L²` 增长（`r`、`c` 是单位长度的电阻与电容，`L` 是线长；系数 0.38 来自对沿线均匀分布的 `r`、`c` 做 Elmore 延迟积分，是分布 RC 线的标准解）。容量翻倍让阵列边长大约涨 `√2` 倍，这条线的延迟就涨约 `2` 倍——**延迟随容量超线性增长**。
- **带宽**由并行读出通道（bank 数、端口宽度）决定。它与前两者相对独立：多开几条通道就能堆带宽，但每条通道的延迟一点没变。

寄存器的快正因为躲开了这三条：它的容量小到可以用一棵深度恒定的译码树加上最短的连线，读写不需要命中/未命中判断，也没有"阵列边长"这个变量。**但把它按在 256 KB 这个量级上的主要约束不是线长，而是端口**：寄存器堆每个周期要同时服务 32 个 lane 的多个操作数读出，每个 bit 单元因此必须做成多端口，而多端口单元的晶体管数与面积随端口数快速增长——这才是它做不大的主因。（`0.38·r·c·L²` 讲的是存储阵列里一条长线的 RC 延迟，套不到寄存器堆上：它的问题在端口数，不在线长。）

**第二步：因此不存在"三全其美"的单级存储。**

把上面三条放在一起看：要容量就必须大阵列，大阵列就必须长线，长线就必须接受长延迟。于是任何一种"只用一级存储"的方案都会撞墙：

- 全用寄存器：容量只有每 SM 256 KB（65536 个 32-bit 寄存器），连一个中等规模的工作集都装不下。
- 全用共享内存：每 SM 也只有 228 KB（Hopper）。
- 全用 HBM：容量有几十 GB，但每一次访问都付 400～800 个周期。

**唯一出路是分级**：把小的、快的放在离执行单元最近的地方，把大的、慢的放在外围，然后依赖**局部性**——程序在任一时段内反复访问的，往往是同一小片数据——让多数访问落在快的那一级。

**第三步：把"多数访问落在快的那一级"写成一个可计算的式子。**

设两级存储的延迟分别是 `L_fast` 与 `L_slow`，快的那一级命中率为 `h`：

```text
平均访问时间 = h × L_fast + (1 − h) × L_slow
```

代入 `L_fast = 30`（L1 命中）、`L_slow = 600`（HBM 的中位值，见第六步的表）：

| 命中率 `h` | 平均访问时间（cycles） |
|---|---|
| 1.00 | 30 |
| 0.99 | 0.99×30 + 0.01×600 = 35.7 |
| 0.95 | 28.5 + 30 = 58.5 |
| 0.90 | 27 + 60 = 87 |
| 0.50 | 15 + 300 = 315 |

这张表里藏着两条后面反复要用的结论。

**其一，命中率的边际代价是常数，而它等于两级延迟之差。** `h` 每掉 1 个百分点，平均时间就涨 `0.01 × (600 − 30) = 5.7` 个周期。命中率从 0.99 掉到 0.95 只差 4 个百分点，平均时间却涨了 64%——**这就是为什么"工作集稍微大一点，性能就断崖式下跌"**（§4 第二条）。

**其二，多一级缓存，收益是乘法性的，不是加法性的。** 现实里有三级，把它们一路写下来：

```text
平均访问时间 = h₁·L₁ + (1 − h₁)·[ h₂·L₂ + (1 − h₂)·L_HBM ]
```

| `h₁`（L1 命中率） | `h₂`（L2 命中率） | 落到 HBM 的比例 | 平均访问时间 |
|---|---|---|---|
| 0.9 | 0.8 | `(1−0.9)×(1−0.8) = 2%` | `27 + 16 + 12` = **55** |
| 0.9 | 0 | `10%` | `27 + 0 + 60` = 87 |
| 0 | 0.8 | `20%` | `0 + 160 + 120` = 280 |
| 0 | 0 | `100%` | 600 |

**落到 HBM 的那一份是各级未命中率的乘积，不是和**：L1 放走 10%，L2 再从放走的部分里抓住 80%，于是只有 `10% × 20% = 2%` 落到 HBM。命中率 0.9 与 0.8 单看都只是"大部分命中"，乘起来却把平均访问时间从 280（只有 L2 时）压到 55。这解释了存储层次为什么一层一层地加：每加一级，都是在给"落到最慢那一级的比例"再乘一个小于 1 的因子。

**第四步：账本的另一半——命中率由访问模式决定，不由硬件决定。**

上面那个 `55` 有个前提：`h₁`、`h₂` 真的能达到 0.9 与 0.8。而决定 `h` 的是**访问模式**，不是硬件。同样一块 L1，顺序扫描一个大数组时命中率趋近于 0（每个元素只用一次），而按 tile 复用时可以很高。**所以"哪一级存储"只是账本的一半，另一半是"你怎么访问它"。** 后半本的正文在 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md)——本文只负责前一半：把这一级的容量与延迟量级交代清楚。

**第五步：把带宽与延迟分开算——它们回答的是两个问题。**

延迟是"一个字节来回要多久"，带宽是"每秒能过多少字节"。二者的式子不同：

```text
延迟     = 数据从发出请求到可用所经过的时间
有效带宽 = 传输字节数 ÷ 时间
```

HBM 的做法是把并行通道堆到极致：H100 SXM 用 5 个 HBM3 stack，每个 1024 bit，合计 5120 bit 的总线，堆出 3350 GB/s。折算成每个周期能交付的字节数：

```text
3350 GB/s ÷ 1.98 GHz ≈ 1692 字节/周期
```

也就是整个存储系统**每周期能交付约 1692 字节**——约 13 条 128 字节的 cache line——而**每一条的延迟仍然是 400～800 个周期**。宽，但一点都不快。这就是"高带宽不代表单次访问快"的全部内容：带宽来自通道数，延迟来自路径长度，两者由不同的物理量决定，可以独立变化。

顺着这条线还能复核 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §1 第七步算过的那个数：要同时喂饱这么大的带宽与这么长的延迟，在途的数据量是

```text
在途字节数 = 带宽 × 延迟 ≈ 25.4 GB/s（每 SM 分到的份额）× 300 ns ≈ 7.5 KB
```

（推导过程在那里，此处回链，不重复。）这个数就是"GPU 为什么需要那么多常驻 warp"的物理来源——**长延迟 × 大带宽 = 在途数据量的需求大**，而承载在途数据的地方是寄存器文件。

**第六步：沿着这条线，给出量级对照表。**

下表的每一行都是**典型值**，随架构与型号变化（§3 给出逐代的实际数字）。延迟一栏沿用 03 篇的那一组，两篇一致。

| 层级 | 典型容量 | 典型延迟 | 谁可见 | 谁管理 |
|---|---|---|---|---|
| 寄存器 | 每 SM 256 KB | 约 1 cycle | 单线程 | 编译器（编译期静态分配） |
| 共享内存 | 每 SM 最多 228 KB（Hopper，自统一池切出） | 20～30 cycles | 单 block | 程序员 |
| L1 | 与共享内存共用同一块物理存储 | 约 30 cycles（取上一档上沿） | 本 SM 上的全部线程 | 硬件 |
| L2 | 数十 MB | 约 200 cycles | 全 GPU | 硬件 |
| 显存（HBM/GDDR） | 数十 GB | 400～800 cycles | 全 GPU | 硬件 |
| 主机内存 | — | 微秒级 | — | — |

几点必要的说明：

- **"共享内存"那一档的取值跨代很宽，而且不单调**：这里列的是统一池的大小——Fermi/Kepler/Pascal 是 64 KB，Maxwell/Turing 是 96 KB，Volta 是 128 KB，Ampere 是 192 KB，Hopper/Blackwell 是 256 KB；共享内存从池中切出，上限是池子减去留给 L1 的部分（Hopper 为 228 KB）。取哪一代的数值做规划，要看目标硬件（§3 末的表按型号给出实数）。
- **主机内存一栏特殊**：GPU 不能像访问显存那样直接寻址主机内存的任意位置，跨越它的每次访问都要走 PCIe / NVLink（PCIe 的往返延迟是微秒量级），所以那一栏的延迟由**互联**决定，而不是由 DRAM 决定。它的用途是数据进出，不是工作集存放。
- **"谁管理"是这张表里最有信息量的一列**。它是下一节的起点。

**第七步：结论——共享内存是"软件管理的缓存"。**

看表中最后两列：共享内存与 L1 是**同一块物理 SRAM** 的两种用法——它们共享容量，也共享延迟（所以上表把 L1 那一档写成"取上一档上沿"）。两者的区别不在硬件，只在**谁做替换决策**：

- **L1 由硬件管理**：硬件按 cache line 自动填充，按自己的替换策略换出。程序员看不见 tag、不知道哪条数据在不在里面、也无法命令它留哪一条。命中的收益是"白捡的"，但也只能靠改访问模式去间接影响命中率。
- **共享内存由程序员管理**：数据什么时候搬进去、放在哪个偏移、什么时候读出来，全都由源码里的显式 load/store 决定，地址是连续的、可预测的、没有 tag 比较。**你明确知道什么在片上、什么不在。**

这个可控性是整条链上唯一一处"决策权在程序员手上"的地方，因此它成了 GPU 编程里性能优化的主要空间——按 tile 复用的 kernel 本质都是把这份可控性变现（正文在 `40-kernels/gemm`，此处回链）。

**但可控性不是免费的**，这一点决定了它的适用边界。搬运的代价是三项之和：

```text
搬一次的代价 = 一次全局读的延迟（400～800 cycles，按带宽摊）
             + 一次 block 级同步（__syncthreads）
             + 每 SM 能常驻的 block 数可能下降（共享内存申请量是它的约束项之一）
```

假设一份数据要被用到 `k` 次。不用共享内存时，这 `k` 次都要各自付一次全局访存；用了之后，是 `1` 次全局读加 `k` 次共享内存读。**账面收益只有在 `k ≥ 2` 时才为正，且必须大于上面那三项代价。** 这就是 §4 第一条的定量依据。

回到开头那两个问题，现在都能回答了——但答案不同：

- **为什么不全部用寄存器**：容量的账。65536 个寄存器是**静态预算**，不是缓存；每线程多用一档（8 个一档），可常驻的 warp 数就掉一档，并行度随之下降。这是 [01-sm-internals](../execution-model/01-sm-internals.md) §1 的主线，此处回链。
- **为什么不全部用共享内存**：容量与搬运两笔账。容量上，每 SM 228 KB 连一个卷积层的输入 tile 都未必装得下；更重要的是，共享内存申请得越多，每 SM 能常驻的 block 就越少，用来掩盖延迟的 warp 也随之减少。**把数据搬上去这件事本身要花掉全局访存的时间与一次同步，只有复用次数足够高才回本。**

## 2. 执行映射

### 一次全局访存要过哪几道关

参与者是这几个具体部件：

- **LSU（load/store unit）**：接受 warp 的访存指令，把 32 个 lane 的地址合并成尽量少的事务。（合并的规则与代价是 02 篇的题目，见 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md)。）
- **L1（tag + data）**：每 SM 一份，与共享内存共用同一块 SRAM（Hopper 上合计 256 KB，其中至多 228 KB 可切给共享内存）。命中最快的一级。
- **L2 分区（L2 partition / slice）**：全 GPU 共享（H100 SXM 为 50 MB），数据按地址映射到某个分区。它是 L1 之间**唯一的交汇处**。
- **MSHR（miss status holding register）**：一条未命中的请求在这里挂账，等待下层返回，一个条目对应一条在途请求。
- **HBM 控制器（memory controller）**：把未命中的请求排进队列，按 bank/row 组织成突发传输。
- **寄存器文件**：在途访存的目标寄存器整份占在这里，不能挪走。这是"更换 warp 发射几乎免费"的前提（[03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §2，此处回链）。

一次全局读的路径是：

1. warp scheduler 发射一条 `LDG`，同时把该 warp 的一个记分板位置起；
2. LSU 把 32 个 lane 的地址**归并**成尽量少的 **line 请求**（归并只负责合并，对齐是程序员的事），每次请求只取回用到的 **32 字节 sector**（4 个 sector 组成一条 128 字节的 cache line）；
3. 查 L1 tag：命中 → 约 **30 cycles** 返回；未命中 → 分配一个 MSHR 条目，向 L2 发请求；
4. 查 L2 tag：命中 → 约 **200 cycles** 返回，并按策略决定是否回填 L1；未命中 → 向 HBM 控制器发请求；
5. HBM 返回 → 回填 L2（可能还有 L1）→ 写进目标寄存器 → 清除记分板位，该 warp 回到就绪队列。

**命中层级越靠后，延迟越长，而且相邻两级的差距是好几倍**：

```text
寄存器（1）→ L1 命中（30）     ：30 倍
L1 命中（30）→ L2 命中（200）  ：约 6.7 倍
L2 命中（200）→ HBM（600）     ：约 3 倍
L1 命中（30）→ HBM（600）      ：约 20 倍
寄存器（1）→ HBM（600）        ：两个数量级以上
```

（`600` 取 400～800 的中位值；共享内存的 20～30 与 L1 命中同档。）**所以"优化访存"的第一个问题永远是：这次访问落在哪一级？** 差一级就是好几倍，而改访问模式能改变的正是"落在哪一级"。

还有一点比延迟更值得留意：**未命中不只是慢，它还占资源。** MSHR 条目、L2 到 HBM 的请求队列都是有限的硬件结构。未命中率高到一定程度，这些队列会满，新的请求被背压挡住——**这就是"带宽受限"在硬件上的样子**：不是每条请求变慢了，而是根本发不出去。它解释了为什么带宽受限时堆并发毫无用处（[03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §4.3，此处回链）。

### L1 为什么不是"小一号的 L2"

两点结构性差异，都会在写代码时咬人。

**其一，L1 不做跨 SM 的一致性维护。** 一个 SM 上的写入，不保证被另一个 SM 的 L1 看到——L1 之间没有一致性协议。所以跨 block 的数据交换必须落到 L2（全局内存是唯一被所有 SM 共同看见的地方），由程序员用同步来保证顺序。这也说明为什么"多个 block 协作"在 Hopper 之前必须绕道全局内存：不是没有数据通路，而是**片上那一级没有做共享**。

**其二，L1 的容量可以被程序员调走。** 那块 SRAM 是共享内存与 L1 共用的：切给共享内存多一分，留给 L1 的就少一分。**"缓存命中率"和"共享内存容量"因此是同一份预算的两面**——这是 GPU 独有的特性，CPU 的 L1 大小是固定的。它是 §1 第七步那笔"搬运成本"里第三项的来源。

### local memory 的物理归属

这个名字有两处会骗人。**它叫 "local"，但它不在片上。** local memory 是**显存里的一块区域**，只是按"每线程私有"的方式寻址。于是它有两个后果：

1. **它与全局访存走同一条路径、也受同一条缓存规则照顾**（依计算能力缓在 L1/L2）。所以它并不是"每次都要走完 L1 → L2 → HBM"——命中的那一次就停在片上。但一旦未命中，付的是与全局访存同级的 400～800 个周期：**它的延迟是"片外存储的延迟"，而不是"片上存储的延迟"**。
2. **它的合并保证带一个条件。** 硬件并不为每个线程从头到尾划一个连续段，而是把局部数组按**线程交织**排布：同一个下标对应的 32-bit 字，由**连续的线程 ID** 依次访问。因此——**只要一个 warp 内所有 lane 访问同一个相对下标**（例如同一个数组的同一个下标、同一个结构体的同一个成员），这次访问就是**满合并**的，与一条理想的对齐全局访存没有区别。**只有各 lane 访问不同相对下标时，这条保证才失效**（见 §4.3）。

所以坑不在"天然不能合并"，而在"这条保证什么时候会断"——这正好又是 §1 第四步那句话：决定性能的是访问模式，不是"名字里写着 local 还是 global"。

什么东西会落到 local memory？两类：

- **寄存器分配的溢出（spill）**：寄存器不够分时，编译器把一部分活跃变量挪到 local memory。检测方法是看 `-Xptxas -v` 报告里的 spill 字节数（正文在 [01-sm-internals](../execution-model/01-sm-internals.md) §4.3 与 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §3 改进三，此处回链，不重复）。
- **编译器无法证明可以用寄存器静态寻址的数组**：被变量下标索引的局部数组、或尺寸过大的局部数组。**这一类在源码里完全看不出来**——你只是写了一个 `float buf[64];`，编译器却在显存里给你开了一块。

第二条正是 §4 第三条要展开的坑——而**打掉合并保证的并不是"落进了 local memory"，是"各 lane 的下标不同"**：第二类里若下标在运行期恰好统一（编译器只是证不出它是常量），访问照样是合并的。

## 3. 实现与演进

这一节按"为什么需要下一步"组织。主线接着 §1 第七步：**每一代的动作，都是在改变"程序员能控制的那块片上存储"——先让它存在，再让它可配置，再调整它的大小与可见范围，最后让它跨出 SM。** 这里的"调整"不是单调扩大：池子从 Fermi 起依次是 **64 → 64 → 96 → 64 → 128 → 96 → 192 → 256 KB**，中间回落过两次（Pascal、Turing；Blackwell 沿用 Hopper 的 256 KB，未单列）。每代的规格数字都给出可查证的型号与出处（见本节末的说明）。

### 早期：没有缓存，只有共享内存

Fermi 之前（G80 / Tesla 架构，2006），SM 里只有寄存器与 16 KB 共享内存，**没有通用的 L1 数据缓存**——全局读没有任何片上缓冲，只有一条只读的纹理/常量缓存路径可以用。

共享内存因此是**唯一**可编程的片上存储，程序员必须手工把数据搬进搬出，否则每次访问都直达片外。

**为什么需要下一步**：所有"复用"都得靠自己写搬运代码，临时数据也没有任何落脚处。而那块 SRAM 在不用作共享内存时本来也可以充当缓存——**缺的不是存储单元，是 tag、替换与命中判断这一整套硬件**，那正是 Fermi 要补的东西。

### Fermi（2010，GF100）：统一 L1 与共享内存

Fermi 把 L1 与共享内存**统一成一块 64 KB 的 SRAM**，并允许在启动时按 **48 KB 共享 + 16 KB L1**（或反过来）配置。L2 为 768 KB；代表型号 Tesla M2090 用 GDDR5 给出 177 GB/s。

这是本文主线的起点：同一块物理存储，两种管理模式第一次共存，程序员可以选择"这一块给谁"。

**为什么需要下一步**：切分比例是 kernel 启动时定下的，跑起来就不能改——而同一个 kernel 在不同阶段对 L1 与共享内存的需求往往不同（先是搬运阶段吃带宽，后是计算阶段吃缓存）。

### Kepler（2012，GK110）：切分比例可调

Kepler 把切分变成**三档可选**（48:16、16:48、32:32），并额外提供 48 KB 只读数据缓存。L2 从 768 KB 翻倍到 1536 KB；代表型号 Tesla K40 的 GDDR5 带宽为 288 GB/s。

**为什么需要下一步**：177 → 288 GB/s 的增量全部来自 GDDR5 的频率爬坡，而这条路的边际收益在下降。下一代没有再靠带宽换性能，而是把重点转向每瓦性能，并把片上池子从 64 KB 扩到 96 KB；**介质换代要再等一代，到 Pascal 才发生**。

### Maxwell（2014，GM204）：池子变大

Maxwell 把统一池从 64 KB 扩到 **96 KB**（每 block 的共享内存上限仍是 48 KB），L2 扩到 2 MB；代表型号 GTX 980 用 GDDR5 给出 224 GB/s。

**为什么需要下一步**：这一代的重点在能效，池子只涨了 50%；真正的跃迁要等显存介质换代。

### Pascal（2016，GP100）：HBM2 上卡

**HBM2 第一次上卡。** 代表型号 Tesla P100 用 16 GB HBM2、4096-bit 总线给出 **732 GB/s**——比同代的 GDDR5 型号高一倍以上，L2 也从 2 MB 扩到 4 MB。但统一 L1/共享内存只有 **64 KB，反而比 Maxwell 的 96 KB 小**：**片上池子并不逐代单调增长**（两代的 SM 设计目标不同），所以取值必须落到具体型号，不能按"代"推。

**为什么需要下一步**：片外带宽翻了几倍，片上那块 64 KB 的池子立刻成了新的瓶颈；而且 block 之间依然完全孤立，任何跨 block 交换都必须经过 L2。

### Volta（2017，GV100）：片上的那次跃迁

统一池从 64 KB 一跃到 **128 KB**（共享内存上限 96 KB），L2 翻到 6 MB；代表型号 V100 SXM2 用 HBM2 给出 **900 GB/s**。共享内存的容量在这一代翻倍，且 `__syncthreads()` 之外的同步原语（`__syncwarp` 等）与独立线程调度同时到位。

这一代也是**寄存器文件这一级定型的时刻**：256 KB、每 SM 2048 线程，从 Volta 起沿用至今（[01-sm-internals](../execution-model/01-sm-internals.md) §3，此处回链）。注意这里的"定型"只指寄存器这一级——**共享内存那一级此后还会涨（128 → 192 → 256 KB）也会落（Turing 96 KB，见下一节），而 65536 个寄存器的配额八年没动过**。从这一代起，容量的增长主要发生在 L2 与片外。

**为什么需要下一步**：池子大了，但它服务的范围仍然只是**一个 SM 上的一组 block**。跨 block 的交换依旧要经 L2，而 L2 的延迟是共享内存的近 7 倍（200 对 30）。

### Turing（2018，TU102）：池子回落的一代

统一池从 128 KB **回落到 96 KB**，每 block 的共享内存上限从 96 KB 砍到 **64 KB**（各缩 25% 与 33%）；L2 仍是 6 MB；代表型号 RTX 2080 Ti 用 GDDR6 给出 616 GB/s。

这一代把预算让给了别处——独立的 INT32 数据通路（[01-sm-internals](../execution-model/01-sm-internals.md) §3，此处回链），片上存储这一级因此原地踏步甚至后退。它给出一个直接的教训：**"代"不是比较存储规格的单位**。Volta 的 128 KB 到下一代只剩 96 KB，凭"更新的一代"去估容量就会估错——这是 §3 开篇那句"回落过两次"的第二次，也是 §1 那张表下面"取值必须落到具体型号"那个提醒的第二个数据点。

**为什么需要下一步**：跨 block 的隔离没变（交换仍要绕道 L2），而当时 L2 只有 6 MB——**要绕的那条路太窄**。下一代给出的回应正是把 L2 扩到 40 MB：不解决隔离，但让"绕道 L2"这件事本身变得可以接受。

### Ampere（2020，GA100）：L2 开始可以被"规划"

统一池扩到 **192 KB**（共享内存上限 164 KB），**L2 从 6 MB 跳到 40 MB**——这条线的意义与共享内存那条不同：L2 大到了足以被当成设计变量的程度。分块（tiling）策略从此可以按"让工作集装进 L2"来设计，而不是只按共享内存容量。代表型号 A100 80 GB 用 HBM2e 给出 **2039 GB/s**。

**为什么需要下一步**：block 之间的隔离还没有打破。同一个 GPC 内的 SM 本来就通过同一组 L2 分区与内部互联相连，但共享内存被设计成 block 私有，跨 block 只能用全局内存兜一圈。

### Hopper（2022，GH100）：共享的范围扩到 cluster

统一池 **256 KB**（共享内存上限 228 KB），L2 50 MB；代表型号 H100 SXM 用 HBM3 给出 **3350 GB/s**。真正的结构性变化是**线程块簇（thread block cluster）与分布式共享内存（DSMEM）**：簇内的 block 被共同调度到一个 GPC，可以用 `cluster.map_shared_rank()` 拿到**对端 block 的共享内存地址**并直接读写，配合簇级同步使用。

**"共享"的范围第一次从 block 扩到了 cluster**——同一块片上存储，现在能被一组 SM 共同可见，中间不再经过 L2。这与 §1 第七步的论断是同一件事的延伸：**共享内存的价值来自可控性，那么扩大可控范围就等同于扩大它的价值。**

（DSMEM 的正文在本文这一节；[01-sm-internals](../execution-model/01-sm-internals.md) §3 只作提要，不重复。）

**为什么需要下一步**：DSMEM 解决的是"数据放在谁的片上"，没解决"哪一级最挤"。而当时最挤的不是共享内存，是**寄存器文件**——Tensor Core 的累加器就住在那里（[01-sm-internals](../execution-model/01-sm-internals.md) §3 对 Hopper 的计算，此处回链）。

### Blackwell（2024，GB100）：再加一级，而不是把这一级做大

统一池仍是 256 KB（共享内存上限 228 KB）；代表型号 B200 用 HBM3e 给出 **8000 GB/s**，片间互联 NVLink 5 到 1.8 TB/s；L2 继续扩大。

这一代的动作不在本文这条线上（L1/共享内存），但它的**思路**值得记下来：寄存器文件不够放累加器，Blackwell 没有把寄存器文件做大，而是加了**另一份独立的存储**（TMEM，每 SM 256 KB，`tcgen05` MMA 的累加器专用）。**当一级存储不够用时，解法是再加一级——这正是本文 §1 第二步的结论在最新硬件上的重演。**

### 把这些规格代回去，得到一个可操作的数

上表还能兑现成一个具体约束。§1 第七步说共享内存是"软件管理的缓存"，但它的容量不只受物理限制——它同时决定了**每 SM 能常驻几个 block**。这件事有**两个独立的上界**，一个来自容量，一个来自硬件槽位：

```text
共享内存约束：每 SM 常驻 block 数 ≤ floor(S_max ÷ S_b)      （S_b = 每 block 申请的共享内存）
block 数约束：每 SM 常驻 block 数 ≤ B_max
```

Hopper 上 `S_max = 228 KB`、`B_max = 32`。**若想让 32 个 block 同时常驻（把 block 数这一项顶满），每个 block 就只剩 `228 ÷ 32 ≈ 7 KB` 共享内存可用**；反过来，若每个 block 申请 36 KB，`floor(228 ÷ 36) = 6`，常驻 block 数掉到 6。**共享内存从"给得多就命中率高"变成了"给得多就并发少"**——这正是 §4.1 那条坑的完整形态：它的每一次扩容都是从并发预算里扣的。

**"软件管理的缓存"这句话里的"管理"，管的不只是数据放哪儿，还有"拿多少容量去换多少并发"。**

（四约束取最小的完整推导在 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §1 推导二，此处回链，不重复。）

## 4. 踩坑与失败模式

下面三条都在"读完前几节"之后仍然会犯——它们不是本文主线的复述，而是把主线**过度应用**的三种方式。

### 4.1 把共享内存当通用缓存

**现象**：既然 §1 说共享内存是"软件管理的缓存"，那就把所有要用的数据都先搬进共享内存。结果性能反而下降，有时下降得比不用缓存还多。

**成因**：把"可控的缓存"读成了"免费的缓存"。§1 第七步算过这笔账：搬一次要付一次全局读的延迟、一次 `__syncthreads()`，还要占掉一块共享内存容量——**后者会直接压低常驻 block 数**（共享内存是每 SM 常驻 block 数上限里的一个约束项，[03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §1 推导二，此处回链）。而收益只有 `(k − 1)` 次全局访存，`k` 是这份数据被复用的次数。**若每个元素只读一次，`k = 1`，收益为零，三项代价全是净亏。**（第三项的账在 §3 末算过具体数字：想让 32 个 block 同时常驻，每 block 只剩约 7 KB 共享内存可用。）

更隐蔽的是中间地带：`k = 2` 时账面为正，但那点收益很容易被同步开销吃掉——如果搬运后的使用只发生在很少几个 warp 上，或者 block 太小导致同步代价占比高，`k = 2` 并不划算。

**规避**：搬运前先数复用次数，而不是先看数据大小。判据是 **`k` 是否显著大于 1**：矩阵乘法里的 tile 每个元素被复用 `O(tile 宽度)` 次，值得搬；逐元素的向量加法每个元素只用一次，不值得搬。当不确定时，先写"不用共享内存"的版本跑出基线，再加共享内存对照——**这一步不能靠推理，要靠对照**，因为 `k` 的分布往往取决于运行时的数据与调度。

### 4.2 忽略 L2 容量，工作集越线

**现象**：一个 kernel 已经调好了，只是把问题规模（batch、序列长度、矩阵宽度）稍微调大一点，性能断崖式下跌——不是慢 10%，是慢好几倍。

**成因**：工作集**越过了 L2 的容量线**，§1 第三步那个乘法结构随之失效。把数代进去看得最清楚：工作集装得下时，按 §1 第三步那张三级表的 `h₁ = 0.9`、`h₂ = 0.8` 一行算是 55；越线之后 `h₂` 掉向 0，落到 HBM 的比例从 2% 涨回 10%（L1 那一级还在），平均时间跳到 87；而工作集既然已超出几十 MB 的 L2，通常也早已超出百 KB 量级的 L1，于是 `h₁` 跟着塌，平均时间直接逼近 600。**55 → 87 → 600，中间没有过渡带**，因为缓存替换策略在容量边界附近会进入颠簸（thrashing）：每个新来的访问恰好把下一个要用的数据挤出，命中率不是缓降而是崩塌。

有一个粗判据可以提前估出这条线在哪：L2 被**全部常驻线程**共享，所以

```text
每线程可分的 L2 字节数 ≈ L2 容量 ÷ (SM 数 × 每 SM 线程上限)
H100 SXM：50 MB ÷ (132 × 2048) ≈ 190 字节/线程
```

也就是：如果全体常驻线程各自的工作集都超过约 190 字节，加起来就超过了 L2。这个数只给量级——实际可用量取决于访问的时空分布，而不是所有线程都同时压满——但它足以说明为什么"每线程几百字节"是一个需要警惕的门槛。

**规避**：把工作集大小当成一个需要主动算的量，而不是"数据有多少就处理多少"。手法是**分块（tiling）**：把问题切成多个阶段，每个阶段的工作集都落在 L2 能容纳的范围内，让相邻阶段的中间结果在 L2 里命中，而不是每次回 HBM。（如果瓶颈是带宽而不是命中率，先按 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) §4.3 的判据确认落在哪一侧——带宽受限时增大并发的方向本来就错了。）

### 4.3 混淆 local memory 与 global memory

**现象**：在汇编或 profiling 输出里看到 `local` 字样，第一反应是"片上存储，应该不慢"，于是把它当成寄存器/共享内存那一档来估开销，忽略了它。等到发现 kernel 慢，才开始查别处。

**成因**：**名字的误导，加上一条有条件的保证被破坏。**

前半是"名字骗人"：§2 说过 local memory 物理上位于片外显存——它叫 "local" 说的是**寻址方式**（每线程私有），不是**存储位置**。所以它的延迟按片外存储算，而不是按片上存储算。

但真正让这条值得写进失败模式的，是后半。§2 强调过 local memory 的合并**带一个条件**：一个 warp 内所有 lane 必须访问**同一个相对下标**。而"用变量下标去索引局部数组"恰好把这个条件打掉——各 lane 取到的下标不同，硬件只能按各自的下标去取，这次访问就退回成不合并的散列访问（代价见 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md)）。

于是同一个 `float buf[64];` 会有两种命运：`buf[0]` 是满合并的，**只付一份片外延迟**；`buf[i]` 不保证合并，**还要再乘上一份合并损失**。两笔账的差别，就是「一次满合并的片外访问」与「同一次片外访问再赔上一份合并损失」——**中间差着一个数量级，而它们在源码里只差一个下标。**

（顺带说清一处分寸：在同一下标那一档，local memory 并不比等价的全局写法差，反而更好——把每线程私有数据摊在全局内存里，需要程序员自己排 layout 才算得出合并，而这里的 layout 是硬件替你排好的。它的对手从来不是"写得好的全局访存"，而是"片上那一级"。）

**规避**：两条一起做。

1. **别在 kernel 里定义大数组**，也别用变量下标去索引局部数组——这两类都会被编译器放进 local memory。需要数组时，按用途改写成共享内存（block 内共享）或重新组织成寄存器变量（编译期可展开的固定下标）。
2. **主动检查有没有 spill**：编译时看 `-Xptxas -v` 报告的 spill 字节数，非零就说明有数据在走 local memory（正文在 [01-sm-internals](../execution-model/01-sm-internals.md) §4.3，此处回链，不重复方法）。**注意 spill 的触发条件通常与 register 用量有关**，所以这条坑与"压寄存器换占用率"是同一条绳上的——压过头就会掉进这里。

## 6. 小结与延伸

本文的主线一句话可以讲完：**存储必须分级，因为容量与延迟由同一个物理量——阵列尺寸——同时决定；而程序员唯一能控制的，是把哪些数据放到哪一级、以及怎么访问它。**

围绕这条主线，有三个可独立复用的中间结论：

1. **分级是物理必然，不是工程选择。** 存储阵列越大，行/列线越长，分布 RC 线的延迟按 `0.38·r·c·L²` 增长（容量翻倍 → 边长涨 `√2` 倍 → 延迟涨约 2 倍）；而寄存器堆是被**端口数与面积**按在 256 KB 量级上的。两条约束指向同一个结论：不存在"大容量 + 低延迟"的单级存储。
2. **多级缓存的收益是乘法性的。** 落到最慢那一级的比例是 `(1−h₁)(1−h₂)` 而不是 `(1−h₁) + (1−h₂)`。`h₂ = 0.8` 时，把 `h₁` 从 0 提到 0.9，落到 HBM 的比例就从 20% 压到 2%，平均访问时间从 280 降到 55；而命中率每掉 1 个百分点，平均时间就涨两级延迟之差（5.7 个周期）——这是"工作集越线就断崖"的定量来源。
3. **带宽与延迟独立，不能互相替代。** HBM 用 5 个 stack、5120 bit 堆出 3350 GB/s（约 1692 字节/周期），但每一条 cache line 的延迟仍是 400～800 个周期。宽而慢，所以必须在途量大；在途字节数 = 带宽 × 延迟 ≈ 7.5 KB/SM，这个需求落在寄存器文件上，也就决定了 GPU 为什么需要那么多常驻 warp。

**共享内存是这条链上唯一一块"软件管理的缓存"**——它和 L1 是同一块物理 SRAM，区别只在替换决策由谁做：硬件做时你看不见也管不着，你做时什么都确定，代价是搬运与同步必须由复用次数来摊平。这条线索从 Fermi 的一块 64 KB 可切分 SRAM 起步，中间几经涨落（Pascal 与 Turing 各回落一次），到 Hopper 变成 228 KB 加 DSMEM，再到 Blackwell 把累加器搬出寄存器文件——**每一代都在回答同一个问题：把更多东西放到程序员能控制的那一级；而"那一级"的容量本身并不逐代递增。**

下一篇 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md) 接着 §1 第四步留下的那半本账：既然"落在哪一级"由访问模式决定，那就把访问模式本身讲清楚——32 个 lane 的地址怎么被合并成事务、32 字节的 sector 与 128 字节的 cache line 是什么关系、以及一个不对齐或跨步的访问为什么会白白浪费掉大部分搬回来的字节。
