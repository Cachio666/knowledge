# 共享内存 bank 冲突

> 共享内存比全局内存快一个多数量级（25 对 600 个周期，约 24 倍），但它的交付率（`bank` 阵列每周期能交付的有用字节数，§2）是按 bank 算的——32 个 lane 撞进同一个 bank 时，一次访问要串行 32 遍，交付率跟着降到 1/32，降完反而低于这个 SM 分到的 HBM 带宽。

## 0. 背景与动机

一个用共享内存做分块（tiling）的矩阵乘法。每个 lane 负责 tile 的一行（`lane` 是 warp 内 0～31 的编号，见 [02-simt-and-divergence](../execution-model/02-simt-and-divergence.md) §1），内层循环沿列推进：

```cuda
__shared__ float tile[32][32];

// 行号 = lane，列号 = 循环变量 k（对整个 warp 是同一个值）
for (int k = 0; k < 32; ++k)
    acc += tile[lane][k] * rhs[k];
```

把数组声明从 `float tile[32][32]` 改成 `float tile[32][33]`——**多一列**，其余一行没改：

```cuda
__shared__ float tile[32][33];       // 只改了这一个数
```

预期耗时相差数倍（**推导值**；这个访问模式的吞吐损失上限是 32 倍，推导见 §1 与 §2——**仅就这一次访问而言**，实际差距取决于 kernel 是不是卡在共享内存端口上）。而多出来的那一列从头到尾没有被读过一次：它不产生任何数据，也不参与任何计算。

于是问题很具体：**一块永远用不到的存储，为什么能让程序变快？**

答案不在代码里，在硬件的地址映射里。tile 的**行距**（一行占多少个元素）决定了 32 个 lane 的地址会不会挤进同一个 bank：`[32][32]` 的行距恰好等于 bank 数 32，于是"按列取用"这一种读法会把 32 个 lane 全部塞进同一个 bank；多出来的那一列把行距从 32 推成 33，冲突就消失了。§1 把这套推理逐步推完。

> **全文的数字口径**：本文没有实测数据，所有 cycles、倍率与字节率都是**推导值**——由公开文档给出的 bank 划分规则（32 个 bank、每个 4 字节宽）、[01-hierarchy-overview](01-hierarchy-overview.md) §1 第六步已公布的延迟量级，以及同一篇 §1 第五步与 §3 末的带宽数字（3350 GB/s、132 SM、1.98 GHz）算出。每一步算术都写在正文里，读者可以自己复核。复核它们的入口是配套程序 `code/03_bank_conflict_demo.cu`（见文末「编译与运行」）。凡是引用本文数字的下游文档，请沿用这个口径。

## 1. 原理

先约定三个词，本文只用这三个。

- **lane**：warp 内的一条数据通路，编号 0～31（定义与 warp 的关系见 [02-simt-and-divergence](../execution-model/02-simt-and-divergence.md) §1）。一个 warp 的 32 个 lane 在同一时刻执行同一条访存指令。
- **bank**：共享内存地址空间的划分单位。一共 32 个，每个 4 字节宽，地址按 4 字节为单位轮流分配（§1 第一步）。
- **串行遍数**：一次 warp 访问被拆成几遍逐遍服务。它是本文衡量冲突代价的量。

（**一个用词上的界定**：共享内存的访问不查 tag、不产生 L1→L2 的请求，所以 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md) 篇用来记账的「事务」口径在这里用不上。上一条定义的「串行遍数」是另一回事——它数的是同一条指令在 bank 阵列上占了几个周期，不是发往下一级的请求条数。）

**第一步：bank 划分模型。**

共享内存的地址空间按 4 字节为单位轮流分配给 32 个 bank：

```text
bank(addr) = (addr ÷ 4) mod 32
```

也就是第 0 个字（字节 0～3）进 bank 0，第 1 个字进 bank 1，……第 31 个字进 bank 31，第 32 个字回到 bank 0。整张映射表以 `32 × 4 = 128` 字节为周期重复。

由这个定义直接得到一条硬件宽度：**32 个 bank 每个每周期能供 4 字节，合计 128 字节/周期**。它恰好是一个 warp 的 32 个 lane 各读一个 `float` 的宽度——这与 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md) §2 那条"32 个 lane × 4 字节 = 128 字节 = 一条 cache line"是同一个对齐值，两边的设计意图一致：**让"一个 warp 的一次满效访问"正好一遍做完。**

（bank 宽度在计算能力 3.x 上可以配置成 8 字节，5.0 起固定回 4 字节。本文按 4 字节推——5.0 之后的架构都是这个口径。别把 §2 末那段"64 位访问"当成这件事：那里换掉的是**元素宽度**（`double` / `float2`），bank 宽度仍然是 4 字节。）

**第二步：冲突判定——三条规则。**

把这条指令的 32 个 lane 的地址分别映射到 bank，看结果：

| 32 个地址的落点 | 判定 | 代价 |
|---|---|---|
| 落在 **32 个不同的 bank** | 无冲突 | 一遍完成 |
| 多个地址落在**同一个 32 位字**内 | 多播（broadcast） | 仍算无冲突 |
| 多个地址落在同一个 bank 的**不同** 32 位字上 | 冲突 | **取各 bank 上不同地址数的最大值**，按这个值串行化 |

第二条值得单独说一句：**广播的判定单位是一个 32 位字，不是"完全相同的地址"。** 两个 lane 分别读同一个 `float` 的第 1 和第 3 个字节，硬件同样只取一次，**再按 lane 抽取各自的字节**——它们在同一个字里。所以 `char` 数组按 `shared[base + lane]` 访问是无冲突的：4 个连续 `char` 共享一个字。

（写访问的判定规则与读相同，区别只在同一地址有多个写入者时：硬件只会让其中一个写进去，是哪一个未定义。这里谈的是代价，那一条是正确性问题，不在本文范围。）

**第三步：把"落在哪些 bank"写成一个可算的式子。**

最常见的一类访问是**线性寻址**——每个 lane 的地址是"基址 + 行距 × lane"：

```text
第 i 个 lane 的字地址 = base + s · i          （s = 行距，以 4 字节字为单位）
bank(i) = (base + s · i) mod 32
```

`i` 从 0 取到 31 时，集合 `{s · i mod 32}` 是**模 32 下由 `s` 生成的子群**，也就是 `d = gcd(s, 32)` 的全体倍数：

```text
{s · i mod 32 : i = 0 … 31} = {0, d, 2d, … , 32 − d}     其中 d = gcd(s, 32)
```

这个集合里有 `32 / d` 个不同的 bank，而 32 个 lane 均分到它们上面，每个 bank 分到 `d` 个不同地址。于是：

```text
串行遍数 = gcd(行距, 32) = 32 ÷ (32 个 lane 实际用到的 bank 个数)
```

**这一步是本文全部结论的来源**：它把"冲突"从一件要拿 profiler 看的事，变成了一次求最大公约数。两个直接推论——

- **行距是奇数 ⟹ 无冲突。** 32 是 2 的幂，所以 `gcd(s, 32) = 1` 等价于 `s` 是奇数。
- **行距是 32 的倍数 ⟹ 最坏情形。** `gcd(32, 32) = 32`，32 个 lane 全挤进同一个 bank。

**第四步：把冲突推出来——`float tile[32][32]`。**

32×32 的 tile，一行 32 个 `float` 正好占 32 个字（128 字节）。lane 读自己那一行在固定列 `c` 上的元素：

```text
地址 = (lane × 32 + c) × 4 字节
bank = (lane × 32 + c) mod 32 = c          （lane × 32 是 32 的倍数，模 32 归零）
```

**行距 32 在这里被整个消掉了**——不管 lane 是谁，`bank` 都等于列号 `c`。32 个 lane 因此全部落在 bank `c` 上，而它们要的是 32 个**不同地址**（同一列的不同行），于是：

```text
串行遍数 = gcd(32, 32) = 32        ← 32 路冲突
```

这个数是从第三步的式子直接代出来的，不是估的。

**第五步：把 padding 推出来——`float tile[32][33]`。**

多一列之后，一行占 33 个字，行距从 32 变成 33：

```text
地址 = (lane × 33 + c) × 4 字节
bank = (lane × 33 + c) mod 32 = (lane + c) mod 32
```

`lane` 每加 1，bank 就加 1；lane 从 0 走到 31，bank 从 `c mod 32` 走到 `(c + 31) mod 32`——**遍历全部 32 个 bank，一个不重**。所以：

```text
串行遍数 = gcd(33, 32) = 1         ← 无冲突
```

被加出来的那一列只是把行距从"32 的倍数"推到"与 32 互质"。它自己从头到尾没被访问过——**它起作用的方式是改变别的元素的地址，不是自己提供数据。**

**第六步：把 padding 的代价推出来。**

两笔。

```text
容量：32 × 33 = 1056 个字，对照 32 × 32 = 1024 个字
      多出 32 个字 = 1/32 ≈ 3.1%
对齐：一行 33 个字 = 132 字节，而 132 mod 16 = 4
      → 行首落在 0、132、264、396 … 字节，对 16 取模是 0、4、8、12、0、4 …
       只有每 4 行里的第 1 行落在 16 字节边界上
      而 128 位向量化读写要求 16 字节对齐（[02](02-coalescing-and-cache-line.md) §3 改进二，此处回链）
```

行距 32 时每行行首都落在 128 字节边界上，这条性质在改成 33 之后就没了。

**所以 padding 既不是免费的、也不是总划算的**：它拿"容量 +3.1%、行不再对齐"去换"冲突从 32 路降到 1 路"。这笔账在**确实存在冲突**时是压倒性划算的（32 倍换 3%），在**不存在冲突**时是纯亏——§4.2 就是后一种情形。

**第七步：判据与适用边界。**

把上面四步收成一句可操作的判据：

> **看行距（以元素计）与 32 是否互质。** 互质 ⟹ 无冲突；不互质 ⟹ 串行遍数 = `gcd(行距, 32)`。

三条边界，缺一条这套推导就不成立。

1. **它只对线性寻址成立。** 通式是第二步那条"数每个 bank 上有几个不同地址"，`gcd` 只是线性情形下的闭式解。地址一旦不再是 `base + s · i` 的形式（异或重映射、按索引间接寻址），就得回到通式去数——§3 的改进二落在这条边界之外。（**转置不在此列**：它不改变判据，只改变读、写两侧各自的 `s`，两侧仍然各自套同一个闭式解。）
2. **它讲的是"每个 lane 4 字节"的访问。** 宽度换成 64 位（`double` / `float2`）时判定规则换了一套，判定池不再是 32 个 lane，见 §2 末。
3. **它管的是同一个 warp 的一次访问。** 不同 warp 之间没有 bank 冲突可言——bank 阵列每周期只服务一条被选中的访存指令。

## 2. 执行映射

### 参与者

- **共享内存（32 个 bank × 4 字节）**：每 SM 一块，与 L1 共用同一块物理 SRAM（Hopper 上合计 256 KB，其中至多 228 KB 可切给共享内存）。**它不查 tag、不发 L1→L2 的请求**——这是它与 L1 访问路径的分岔点（[01-hierarchy-overview](01-hierarchy-overview.md) §2，此处回链）。
- **LSU（load/store unit）**：接受 warp 的访存指令。全局访存与共享内存访存从同一个入口进来，在 LSU 内分岔：全局那条要归并成 line / sector 请求（[02](02-coalescing-and-cache-line.md) §2），共享内存这条不归并——它按 bank 归类。
- **warp scheduler**：每周期挑一条指令发射。发射一条共享内存 load（SASS 里的 `LDS`）时它并不知道这次访问会不会冲突——冲突的代价在 LSU 与 bank 阵列那一侧付出。
- **bank 阵列**：一次能供 `32 × 4 = 128` 字节。

### 一次冲突访问实际发生了什么

1. warp scheduler 发射一条 `LDS`，32 个 lane 的地址一起进 LSU；
2. LSU 按 `(addr ÷ 4) mod 32` 把 32 个地址分进 32 个 bank 的桶；
3. **各桶里不同地址数的最大值，就是这条指令要串行多少遍**——任何一个桶里有两个不同地址，bank 阵列就要被访问两次，第二次才轮到另一批 lane；
4. 每一遍**只服务一个地址**，其余 lane 空等；
5. 全部遍做完，结果一起写回目的寄存器。

关键在第 3、4 步的形态：**冲突的主要代价不是"这一次访问多等了几拍"，而是把一条指令摊成了 N 条。** bank 阵列每周期只服务一遍，所以 32 路冲突要占住它 32 个周期、期间只交付 128 字节——而这段时间里，同一个 SM 的其它 warp 也在抢同一块 bank 阵列。**这笔账主要落在吞吐上，不在延迟上**：两者要分开算，具体数字见下一小节。

这与 [02-coalescing-and-cache-line](02-coalescing-and-cache-line.md) 篇那个"不合并"是同一类账：两者的主要代价都不是"这一次访问本身多等了多少"，而是**一次访问占用硬件的次数**变多——全局那一侧兑现在传输量与发射量上，共享内存这一侧兑现在 bank 阵列被占住的周期数上。区别只在判定对象——那边数"32 个地址盖住几个 sector"，这边数"32 个地址撞进几个 bank"；判定的方法却是同一个：**把 32 个 lane 的地址当一个集合来看**（[02](02-coalescing-and-cache-line.md) §2 末，此处回链）。

### 数值量级：延迟与吞吐要分开算

冲突同时踩到两个量，而它对这两个量的作用**完全不一样**——把两笔账混在一起，数量级就会错。

```text
延迟：这一次访问从发射到拿到数据要多久
吞吐：bank 阵列每个周期能交付多少有用字节
```

| 情形 | 量级 | 依据 |
|---|---|---|
| 共享内存无冲突访问（**延迟**） | 20～30 cycles | [01-hierarchy-overview](01-hierarchy-overview.md) §1 第六步 |
| 32 路冲突（**延迟**） | 25 + 31 ≈ **56 cycles** | 32 遍背靠背重发（推导，前提见下） |
| 32 路冲突（**吞吐**） | 128 ÷ 32 = **4 字节/周期** | bank 阵列被占住 32 个周期、只交付 128 字节（推导） |
| 本 SM 分到的 HBM 带宽份额（**吞吐**） | `3350 GB/s ÷ 132 ÷ 1.98 GHz` ≈ **12.8 字节/周期** | [01-hierarchy-overview](01-hierarchy-overview.md) §1 第五步与 §3 末 |
| 全局访存（**延迟**） | 400～800 cycles | 同 01 篇 |
| L1 命中 / L2 命中（**延迟**） | 约 30 / 约 200 cycles | 同 01 篇 |

（`25 + 31` 那一格的底数取的是 20～30 的**中位值 25**，与 [01-hierarchy-overview](01-hierarchy-overview.md) §2 取 400～800 的中位值 600 是同一个口径；换成两端会得到 51 与 61，不改变任何结论。）

两个结论，方向相反。

**其一，延迟上共享内存仍然赢。** 32 路冲突让这次访问多等约 31 个周期（每一遍按 1 个周期重发），25 变成约 56——**仍然远低于一次全局访存的 400～800**。（这一格有一个显式前提：这 32 遍是**背靠背重发**的，数据在返回路径上收集，硬件不等前一遍的数据回来才发下一遍。若某台硬件是"等数据回来再发下一遍"，这一格会变成 `32 × 25 ≈ 800`。**但下一格与这个前提无关**——"bank 阵列被占住 32 个周期"就是串行化的定义本身。）

**其二，吞吐上反被全局内存超过。** bank 阵列被占住 32 个周期、只交付 128 字节有用数据，也就是**每 SM 每周期 4 字节**；而同一个 SM 从 HBM 分到的份额是 `3350 ÷ 132 ÷ 1.98 ≈ 12.8` 字节/周期。`4 < 12.8`：**冲突打满的共享内存，稳态吞吐只有绕道 HBM 的三分之一左右。** 更一般地，N 路冲突时交付率是 `128 / N`，而它在

```text
128 / N < 12.8    ⟺    N > 10
```

时跌破 HBM 的份额——**冲突超过 10 路，共享内存这条路的稳态吞吐就不如直接读全局。**

这就是文首那句话的可复核版本，而它的**作用域要一并带走**：共享内存输给全局内存的是**吞吐**，不是单次延迟（延迟那一格仍差一个数量级）。所以它成立的前提是**这个 kernel 反复访问同一块 tile、瓶颈落在共享内存端口上**——§0 那个分块矩阵乘正是如此（内层 k 循环每一轮都读一遍 tile，同一个 SM 上几十个 warp 一起抢同一块 bank 阵列）。反过来，一份只会被读一次的数据本来就不该搬进共享内存（[01-hierarchy-overview](01-hierarchy-overview.md) §4.1 那笔账），那是另一个问题。

这条线还能接回 §0 的主线：共享内存无冲突时的交付率是 **128 字节/周期**，正好是本 SM 分到的 HBM 份额（约 12.8）的 **10 倍**——这就是那句"快一个多数量级"在吞吐上的对应物（延迟上则是 25 对 600，约 24 倍）。而 32 路冲突把它砍到 4 字节/周期，**从 10 倍优势翻成 3 倍劣势**。也就是说，`tile[32][32]` 那一版的共享内存，在稳态吞吐上还不如直接从 HBM 读同一个数；而它同时多占了一块 SRAM、多付了一次搬运与一次 `__syncthreads()`（[01-hierarchy-overview](01-hierarchy-overview.md) §1 第七步，此处回链）。**这就是 §0 那笔"什么都不干的改动"为什么值钱**：它拿掉的是一笔净亏。

### 64 位访问：判定池从 32 个 lane 缩到 16 个

到上面为止，模型都是"32 个 lane 的 4 字节访问"。把元素换成 `double` 或 `float2`，规则换三条：

1. **一条 warp 的 64 位访问会被拆成两个 half-warp 请求（各 16 个 lane），独立发出。** 所以冲突是在**半个 warp 内部**判定的，判定池从 32 个 lane 变成 16 个。
2. **冲突的判据没变**：同一个 half-warp 内，两个 lane 落在同一个 bank 的不同地址上，就是冲突。文档给的例子正是 `extern __shared__ double shared[]` 按 `shared[BaseIndex + tid]` 连续下标访问——它**没有冲突**，因为每个 half-warp 的 16 个 lane 恰好铺满 32 个 4 字节 bank（每个 double 横跨相邻两个）。
3. **每个 lane 的 8 字节横跨两个相邻 bank**，而 bank 阵列一次仍然只供 128 字节——所以一次 32 个 lane 的 64 位访问**至少要 2 遍**，不管有没有冲突。等价的说法是：可以**把 32 个 bank 看成 16 个"双字槽"**（每个槽 8 字节），同一个槽里出现两个不同地址就是冲突。

为什么这三条要一起看？因为第 1 条会让**冲突路数的数字变小**（池子小了一半），第 3 条会让**地板抬高**（最少 2 遍）。这是两笔方向相反的账，只读前一笔就会得出"改用 64 位访问能省一半冲突"的结论——§4.3 那条坑就是它的产物。

（再宽的访问还有另一套规则：128 位访问**多数情况下本身就带 2 路冲突**，即使 quarter-warp 内没有两个 lane 落在同一 bank 的不同地址上。宽度买到的东西和它新引入的约束要一起算。）

## 3. 实现与演进

本节按"为什么需要下一步"给出**三步改进**（改进一 / 二 / 三），目标都是让 32 个 lane 落在不同的 bank 上。后面另有一节**演进**讲 DSMEM——它不减少冲突，改变的是"谁和谁共享"。

主线接着 §1 第七步那句判据：**行距与 32 是否互质**。三步改进动的是同一件事的不同位置——改善行距（padding）、改善地址映射（swizzle）、改善访问方向（转置）。

### 朴素做法：`float tile[32][32]`

就是 §1 第四步那一版。按行取用（lane 沿列变化）时无冲突，按列取用（lane 沿行变化）时 32 路冲突。**行距 32 = bank 数 32，是冲突的唯一来源。**

**需要下一步的理由**：只要行距保持 32 的倍数，任何"lane 沿行变化"的访问都必然全撞在一个 bank 上；而"按列取用"在分块矩阵乘、矩阵转置、沿列归约里都是天然形态，躲不掉。

### 改进一：padding——把行距推离 32 的倍数

```cuda
__shared__ float tile[32][33];       // 行距 33，与 32 互质
```

原理在 §1 第五步推完了，这里只交代它的**位置**：padding 必须加在**决定行距的那一维**上。`[32][32]` 的行距是后一个 32（一行 32 个元素），所以要在**列**上加 1；加在行上（`[33][32]`）行距仍是 32，一条冲突都不会少。§4.1 是这条的失败模式。

**代价**：§1 第六步那两笔——容量 +1/32、行首不再 16 字节对齐。

**需要下一步的理由**：padding 是用容量和买到的对齐去买"没有冲突"，而这两样在共享内存上都有价格——容量直接进每 SM 常驻 block 数的账（[01-hierarchy-overview](01-hierarchy-overview.md) §3 末，此处回链），对齐则决定向量化访问还能不能用。有没有办法**不动行距**就达到同样的效果？

### 改进二：swizzle——不改行距，改行内的地址映射

把元素 `(i, j)` 存到本行的第 `j ⊕ f(i)` 列（`⊕` 是异或，`f(i)` 只取行号 `i` 的低若干位）。行仍然是 32 个元素，**容量一点没变**；变的只是行内元素的次序。

先看原来好的那一半有没有被破坏。按行取用 `tile[r][lane]` 时，实际读到的是第 `lane ⊕ f(r)` 列：

```text
bank = (r × 32 + (lane ⊕ f(r))) mod 32 = (lane ⊕ f(r)) mod 32
```

行距 32 让行号在 bank 上归零，剩下的 `lane ⊕ f(r)` 在 lane 遍历 0～31 时是 0～31 上的**一一映射**（异或同一个常数）→ **32 个 bank 各不相同，仍然无冲突**。

再看原来坏的那一半。按列取用 `tile[lane][c]` 时，实际读到的是第 `c ⊕ f(lane)` 列：

```text
bank = (c ⊕ f(lane)) mod 32
```

`f(lane) = lane`（取全部 5 位）时，`c ⊕ lane` 随 lane 遍历两两不同 → **无冲突，而且一个字节的容量都没多花**。`f(lane) = lane & 7`（只取低 3 位）时，bank 只剩 8 个取值，每 4 个 lane 撞一次：

```text
串行遍数 = 32 ÷ 2^m            （m = 掩码位数）
m = 5 → 1 遍（无冲突）      m = 3 → 4 遍      m = 0 → 32 遍（等于不做）
```

**所以 swizzle 给的不是"有冲突 / 无冲突"这个二值开关，而是一个可调的档位**：用几次异或把冲突路数从 32 一路拧到 1，代价按掩码位数付。

它换掉的正是 padding 的两笔代价：容量没涨（不碰常驻 block 数那笔账），行距仍是 32（行首仍落在 128 字节边界上，向量化访问不受影响）。**它自己的代价是地址计算多一次异或，以及行内数据不再按原次序存放**——这一点决定了实际实现里异或的最小单位不是单个元素，而是一个固定的**块**（典型 16 字节，对应一条 128 位访存；**这是据库实现的典型取值，本文未核对具体库的源码**）：块内保持连续，块之间被异或打散，这样"向量化读一整行"仍然成立。Hopper 起 TMA 的描述符里也把 swizzle 做成一个可选项——重排由描述符声明、由硬件执行，程序员不再手写异或（TMA 的机制在 [01-sm-internals](../execution-model/01-sm-internals.md) §3，此处回链，不重复）。

现代高性能 GEMM 库普遍用 swizzle 而不是 padding，理由就是上面这两笔账的差额（**据库实现，本文未逐字核对源码**，只作方向性陈述；正文在 `40-kernels/gemm/02-shared-memory-tiling`，此处回链）。

**需要下一步的理由**：padding 与 swizzle 动的都是"地址怎么排"。还有一维没动：**访问从哪个方向来**。

### 改进三：改访问方向——把列访问变成行访问

冲突的根源是"lane 沿行变化、列固定"。既然布局可以自己定，那就**换一个方向存**：把 tile 转置着写进共享内存，于是计算阶段那句"按列取用"变成了"按行取用"：

```cuda
__shared__ float tileT[32][32];
// 计算阶段：lane 沿列变化、行号 c 固定 → bank = (c × 32 + lane) mod 32 = lane
```

**但这份收益是借来的，不是凭空来的。** 转置只是把"按列访问"从读侧挪到了写侧：往 `tileT` 里写时，写下标是 `tileT[lane][c]`——lane 沿行变化、列固定——**32 路冲突原封不动地出现在写入那一侧**。所以这条改进划算的前提是：**两侧的访问模式不对称**，转置之后冲突的那一侧本来就是无冲突的（例如写入由寄存器重排或 `__shfl` 洗牌完成，或者写入时的 lane 映射恰好沿连续维变化）。

一般化的说法是：**让 warp 内的 lane 沿 tile 的连续维变化，而不是沿它的跨步维变化。** 布局、lane 映射、数据从哪来这三件事要一起看——转置、padding、swizzle 都是这条原则的不同实现，而它们都救不回一个"读和写都按列取用"的 kernel。

### 演进：DSMEM 把判定规则原样带到了跨 SM

Hopper 的线程块簇（thread block cluster）与分布式共享内存（DSMEM）允许簇内的 block 用 `cluster.map_shared_rank()` 拿到**对端 block 的共享内存地址**并直接读写（机制正文在 [01-hierarchy-overview](01-hierarchy-overview.md) §3，此处回链，不重复）。

对本文这条线，它只意味着三件事。

1. **判定规则一个字都没变。** 每一块被访问的共享内存仍然是 32 个 4 字节的 bank，`bank(addr) = (addr ÷ 4) mod 32` 仍然是那块 SRAM 自己的映射。**DSMEM 扩大的是"共享的范围"，不是"bank 的宽度"。** padding 与 swizzle 照旧按 §1 的判据用。
2. **判据要落到"落在同一个 SM 上的那一段"上。** 一个跨 SM 拼出来的逻辑 tile，逻辑行距是一回事，它在每个 SM 上实际占的那一段的行距是另一回事——pad 要按每一段自己的行距去 pad，只看逻辑行距会算错。
3. **同一个冲突在跨 SM 的路径上更贵——但贵多少，取决于串行化发生在哪一侧。** 远程访问比本 SM 多走一段 GPC 内的互联，而这 32 遍可能落在来回的两侧：若它们是在**对端 SM 的 bank 阵列上**串完的（请求侧只等一次往返），代价约是"一次远程往返 + 本地那 32 个周期"；若**请求侧要逐遍重发**，每一遍都要各付一次远程往返，代价就按 32 倍乘上去。两者差一个数量级，本文不判断具体硬件落在哪一侧——**能确定的只是方向**：跨 SM 的访问更值得提前消除冲突，因为远程多付的那一段互联**只会加不会减**，绝对代价不小于本地。（远程往返自身的周期数也不在本文范围内。）

## 4. 踩坑与失败模式

下面三条都在"读完前几节"之后仍然会犯——它们不是主线的复述，而是把主线**用错位置**或**读错了记账口径**的三种方式。

### 4.1 padding 加错了维度

**现象**：给 tile 加了 padding，冲突一点没少，profiling 里报的还是 32 路。回去看源码才发现，数组是从 `[32][32]` 改成了 `[33][32]`——多了**一行**，不是多了一列。

**成因**：**这条坑不在"不知道要加 padding"，而在"拿一条规则代替了判据"。** §3 改进一给出的是一条规则——"加在列上"；而规则只有在你知道"行距是方括号里的哪个数"时才执行得了。两个维度在源码里长得一模一样（都是一个数），C 的行优先布局又让**最后一个维度**才是行距。更麻烦的是改错的代价是零：程序编得过、跑得动、结果也对，只有性能不动——没有任何东西会报错。

**规避**：改用一条**可以回代的判据**——`gcd(行距, 32) = 1`，也就是行距必须是**奇数**。改完回代一次 §1 第三步的式子，而不是看代码里"有没有多出一个数"。这条判据还顺手给出两条光看代码看不出来的结论：

- **加多少就还剩多少路。** 把行距写成 `s = 32 + e`（`e` 是加的元素数），则 `gcd(s, 32) = gcd(e, 32)`。加 1 → 归零；加 2 → 还剩 2 路；加 4 → 还剩 4 路。
- **所以"加得越多越好"是错的**：加 4 的残留冲突是加 2 的两倍。

想一次归零，加的量必须是**奇数**，而 `e = 1` 是最省的。

### 4.2 给本来没有冲突的 kernel 加 padding

**现象**：一个按教科书写法组织的分块矩阵乘，加上 padding 之后反而慢了。

**成因**：**它本来就没有冲突。** 教科书写法里线程映射是"`threadIdx.x` 最快变化"，于是同一个 warp 的 32 个 lane 沿 tile 的**列**变化，读到的是 `tile[r][lane]`（行固定、列随 lane 变）：

```text
bank = (r × 32 + lane) mod 32 = lane        → 32 个 bank 各不相同，无冲突
```

而另一半访问 `tile[k][c]`（`k` 是循环变量，对整个 warp 同值）是 §1 第二步的**多播**，也不收费。**这个 kernel 从头到尾没有冲突**，于是 §1 第六步那两笔代价全是净亏：容量涨 3.1%，行首不再 16 字节对齐（向量化读写失效）。

（上面这条结论带一个前提：**`blockDim.x = 32`，也就是一个 warp 恰好铺满 tile 的一整行。** block 取成 16×16 时，一个 warp 会横跨 tile 的两行——那个"对所有 lane 同值"的下标就不再同值了，两半 warp 的地址相差一个行距（32 个字），落在同一个 bank 的不同地址上，于是它从多播变成 **2 路冲突**，"从头到尾没有冲突"也就不再成立。这也是 §3 改进三那句"布局、lane 映射、数据从哪来要一起看"的具体形态。）更重的一笔在容量上——共享内存申请量是每 SM 常驻 block 数的约束项。公式与"想让 32 个 block 同时常驻、每 block 只剩约 7 KB"那个例子在 [01-hierarchy-overview](01-hierarchy-overview.md) §3 末，此处回链、不重推；同一条公式换个数代入就能看到它的形态：每 block 申请 74 KB 时 Hopper 上 `floor(228 ÷ 74) = 3`，能常驻 3 个 block；加 1/32 的 padding 后变成 `74 × 33/32 ≈ 76.3 KB`，`floor(228 ÷ 76.3) = 2`——**容量只涨了 3%，常驻 block 数掉了三分之一**，用来掩盖延迟的 warp 跟着少掉一批。

**规避**：**只在确认存在 bank 冲突时才加。** 判据不是"这个 tile 是不是方阵"，而是"这一次访问的 lane 落在不同的 bank 上吗"——回代 §1 第三步的 `gcd`，或让 profiler 报一次冲突路数（profiling 的正文在 `50-performance`，此处回链）。加完之后再检查一遍占用率有没有掉档（占用率的完整判据见 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md)，此处回链）。

### 4.3 以为 64 位访问没有冲突

**现象**：把 tile 的元素类型从 `float` 换成 `double`（或改用 `float2`），profiler 报的冲突路数一下子掉了一半，性能却没怎么动。

**成因**：**64 位访问不是"没有冲突"，而是换了一套判定规则**（§2 末三条）。请求被拆成两个 half-warp（各 16 个 lane）独立发出，**判定池从 32 个 lane 缩到 16 个**——于是同一个"32 个 lane 撞一个 bank"的访问，现在被报告成两个各 16 路的 half-warp 请求，数字看起来减半。同时每个 lane 的 8 字节横跨两个相邻 bank，bank 阵列一次仍只供 128 字节，**一次 64 位访问的地板被抬到 2 遍**。

两笔账方向相反：判定池小了一半，最小遍数涨了一倍。**凭"括号里的数字小了"就断定冲突被解决了，是把记账口径的变化读成了代价的变化。** 真正该问的问题已经变了：不是"32 个 lane 有没有撞进同一个 bank"，而是"**16 个 lane 有没有在同一个 bank 上请求不同地址**"。

**规避**：用 64 位（或更宽）访问时，**按 §2 末三条规则重新推一遍**——把 32 个 bank 看成 16 个双字槽，问同一个槽里有没有两个不同地址；或者退回字节级的定义 `bank = (字节地址 ÷ 4) mod 32`，把每个 lane 的 8 字节当成"占两个相邻 bank"，再用 §1 第二步的通式数一遍。**不要直接读 profiler 的冲突路数**——那个数在 4 字节与 8 字节两种访问下不是同一个量。

## 编译与运行

配套程序 `code/03_bank_conflict_demo.cu` 做两件事。

1. **扫描行距。** 同一份 32 行的 tile，只改列数（行距取 32 / 33 / 34 / 36），跑同一个"lane 按列取用"的循环，打印每档耗时。把耗时与 §1 第三步的预测并列摆出来：`gcd(行距, 32)` 给出 32 / 1 / 2 / 4，也就是**预期耗时比约为 32 : 1 : 2 : 4**（这是**吞吐侧**的预测：该循环反复读同一块 tile、瓶颈落在共享内存端口上；**延迟侧**的比值要小得多，约 2.2 : 1——两笔账的区分见 §2）。它另跑一个"行距 32、行数改成 33"的配置（`[33][32]`），预期与行距 32 那一档**冲突形态与量级相同**——读循环按行数走，这一档每轮多读一行，所以耗时高 1/32（约 33 倍而非 32 倍，差 3.1%）。这是 §4.1 判据的直接演示：决定冲突的是行距，不是行数。
2. **换 64 位元素重跑。** 同样的按列取用，元素换成 `double`。用于观察 §4.3：这一版的耗时**不会**按 32 倍给出。

**它的用法是人机对照**：拿程序打出的四档耗时两两相除，与 `gcd` 的预测对照。**程序给的是耗时比值，验不出单次访问的绝对周期数，也验不出交付率**——20～30、56、4 与 12.8 字节/周期这些量级都是 §2 从公开规格推出来的，程序没有手段直接读出它们（单次延迟是 [01-hierarchy-overview](01-hierarchy-overview.md) §1 与 [03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md) 的题目）。它也**验不出冲突发生在哪条指令上**，那要看 profiler 的冲突计数（`50-performance`，此处回链）。绝对时间还取决于具体机器与时钟，可对照的只有同一台机器上几档之间的**比值**。

## 6. 小结与延伸

本文的主线一句话可以讲完：**共享内存的 32 个 bank 以 4 字节为单位轮流分配地址；一次 warp 访问的代价，等于这 32 个地址里撞进同一个 bank 的不同地址最多的那一个 bank 上，有几个地址。**

围绕这条主线，有三个可独立复用的中间结论。

1. **冲突判定式：线性寻址下，串行遍数 = `gcd(行距, 32)`。** 32 个 lane 的 bank 值构成模 32 下由行距生成的子群，含 `32/gcd` 个 bank、每个被 `gcd` 个 lane 命中。行距是奇数即无冲突（32 是 2 的幂，互质等价于奇数），行距是 32 的倍数即最坏（32 路）。**判据是"行距与 32 互质"，不是"数组是不是方阵"**——后者只看行数，前者只看一行多长。
2. **padding 的推导与它的代价。** `[32][32] → [32][33]` 把行距从 32 推到 33（`gcd = 1`），代价是容量 +1/32 与行首不再 16 字节对齐。**收益大于代价的前提是确实存在冲突**：没有冲突时它是纯亏，而那 3% 的容量在容量档位边界上可能整档吃掉常驻 block 数（§4.2）。swizzle 是同一目标的另一条路——不占容量、不动行距，代价换成地址计算与行内重排。**第三条路是改访问方向**：让 warp 内的 lane 沿 tile 的连续维变化（转置存储就是把冲突从读侧挪到写侧），它不改变判据，只改变读、写两侧各自的 `s`（§3 改进三）。
3. **冲突是一笔"占用硬件次数"的账，主要兑现在吞吐上。** 32 路冲突把一条指令摊成 32 条、每条只服务一个地址：bank 阵列被占住 32 个周期而只交付 128 字节，**每 SM 每周期 4 字节**——低于本 SM 分到的 HBM 带宽份额（约 12.8 字节/周期），`128 / N < 12.8` 即**冲突超过 10 路就跌破这条线**。单次**延迟**上共享内存仍然占优（约 56 对 400～800），所以"共享内存比全局内存慢"成立的作用域是**反复访问同一块 tile、瓶颈落在端口上的 kernel**。更宽的访问（64 位 / 128 位）换的是另一套判定规则，不是免费的豁免。

本文到此把"共享内存怎么访问"这本书算完了。[02-coalescing-and-cache-line](02-coalescing-and-cache-line.md) 是它的前半本（全局那一侧的同类问题：32 个地址盖住几个 sector），而 `40-kernels/gemm/02-shared-memory-tiling` 要把这两本账同时用到一个具体形状上——tile 取多大、padding 与 swizzle 选哪个、双缓冲怎么排，每一步都在同时付"容量换并发"与"冲突换容量"两笔账。
