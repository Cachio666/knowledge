# 跨代趋势：拐点为什么只在低精度轴上移动

> 算力涨得比带宽快——这句话只在低精度轴上成立。在 FP32 向量轴上，两者十年同步增长，**roofline 拐点从 17.4 走到 9.7 再走回 20.0，全程在原地打转**；而在低精度轴上它从 138.9 走到 1168.8，**移动了 8.42 倍**。这就是「必须换精度而不是换算法」的全部数字依据。

> **全文的数字口径**：本文的数字分两类——**规格值**（直接引自 NVIDIA 官方文档，见参考）
> 与**推导值**（由 `code/specs.py` 中的规格常量代入 §1 的公式算出）。**本文无实测数据。**
> 要复核，运行 `code/02_scaling_trends.py`，它会打印出本文引用的每一个数。
> §1 第五步引用的算子算术强度**引自 [10-foundations/performance-models/01-roofline-model](../../10-foundations/performance-models/01-roofline-model.md)
> §5 表3**，本文不重算它们，只做跨代分类。

## 0. 背景与动机

一个 BF16 的 GEMM：`X[256×8192] @ W[8192×8192]`。权重矩阵固定，只有激活的 batch 维在变。同一份代码、同一个形状，在 A100 与 H100 上的表现是这样的（推导值，`code/02_scaling_trends.py` §5）：

| | A100 80GB | H100 SXM5 |
|---|---|---|
| 这个算子的算术强度 `I` | 240.94 FLOP/byte | 240.94（同一份代码，形状没变） |
| 该精度的 roofline 拐点 `I*` | 153.0 | 295.4 |
| **判定** | **算力受限** | **带宽受限** |
| 可达吞吐 | 312.0 TFLOPS | 807.2 TFLOPS |
| 占该卡峰值 | **100.00%** | **81.57%** |

两列之间的差别不在代码里。`I` 一模一样，`Bytes` 口径一样，FLOPs 一样。变的是**硬件的那个比值**：`I* = P_peak / B_peak` 从 153.0 升到了 295.4（1.930 倍）——因为 A100→H100 这一段，BF16 的 tensor 峰值涨了 **3.17×**，而带宽只涨了 **1.64×**。算子被留在了原地，拐点越过了它。

这件事的实际后果不是「H100 更慢」——它的绝对吞吐仍是 A100 的 **2.59 倍**。后果是**优化方向反了**：在 A100 上该做的是「把这一步算得更快」，在 H100 上该做的是「少搬一次」或「换低精度」。而 2.59 倍这个数字本身也值得一提：峰值之比是 **3.17×**，可达之比只有 2.59×——**H100 的峰值里有 18.4% 在这个形状上永远拿不到**。

所以「下一代更快」这句话对优化没有指导意义；有指导意义的是「下一代在哪些算子上一侧翻了另一侧」。本文要做的五件事按顺序排在 §1 里：

1. **第一步**：从规格基线重算逐代增长率，回答「谁涨得快」。
2. **第二步**：推导拐点 `I* = P_peak / B_peak` 的逐代迁移，回答「拐点往哪走」。
3. **第三步**（多步推导）：给出「一个算子在哪一代翻转」的封闭形式，并换算成 batch 窗口。
4. **第四步**（多步推导）：用官方 FP32 峰值反推时钟，交叉验证 B200 的 SM 数——这一步不直接算拐点，但它决定了前两步用到的 `P_peak` 是否自洽。
5. **第五步**：把真实算子代进去看它们落在哪一侧。**这一步是应用而不是新推导**，但它的结论与直觉相反，值得单列。

**分工说明。** roofline 模型本身的推导（两段线、`I` 的定义、`Bytes` 的口径）正文在 [10-foundations/performance-models/01-roofline-model](../../10-foundations/performance-models/01-roofline-model.md)，**本文回链，不重推**。逐代存储层次与 HBM 带宽的由来在 [memory-system/01-hierarchy-overview](../memory-system/01-hierarchy-overview.md)。逐代 SM 内部规格在 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md)。本文只做横向比较与趋势归纳。

## 1. 原理

### 第一步：先看基线，再看增长率

> **边界**：本表只列**做横向对比所必需**的芯片级量（年份、SM 数、每 SM 的 FP32 lane、HBM 带宽、逐精度峰值）。
> 每 SM 的寄存器文件与占用率约束归 [execution-model](../execution-model/01-sm-internals.md)，
> 存储层次（L1 / 共享内存 / L2 的逐代容量）归 [memory-system](../memory-system/01-hierarchy-overview.md)——
> **本文不重复罗列那两类规格**，只在需要时回链。

逐代规格（数据中心 SXM 档，`code/specs.py`，程序 §1 打印）：

| | V100 SXM2 | A100 SXM4 80GB | H100 SXM5 | B200 SXM |
|---|---|---|---|---|
| 发布年份 | 2017 | 2020 | 2022 | 2024 |
| SM 数 | 80 | 108 | 132 | **148**（反推值，见第四步） |
| FP32 lane / SM | 64 | 64 | **128** | 128 |
| HBM 带宽 (GB/s) | 900 | 2039 | 3350 | 7700 |
| FP32 向量 (TFLOPS, dense) | 15.7 | 19.5 | 67 | 75 |
| FP16 TC (TFLOPS, dense) | 125 | 312 | 989.5 | 2250 |

三行增长率（程序 §2 重算）：

| 跃迁 | FP32 向量 | FP16 TC | HBM 带宽 | 谁涨得快 |
|---|---|---|---|---|
| V100→A100 | 1.24× | 2.50× | 2.27× | 带宽 ≈ tensor，FP32 向量被甩下 |
| A100→H100 | **3.44×** | 3.17× | 1.64× | **算力反超带宽** |
| H100→B200 | 1.12× | 2.27× | 2.30× | 带宽 ≈ FP16/FP8；FP32 向量几乎停滞 |

读这张表得到全篇的主线：

> **在 FP32 向量轴上，带宽从不落后。在低精度轴上，算力在 A100→H100 这一段反超一次，随后被带宽追平。**

「算力反超带宽」只有一次，而且只在低精度轴上。这句限定是必须的——去掉它就变成了错的陈述。

### 第二步：拐点 `I* = P_peak / B_peak` 的逐代迁移

模型的定义（`min(P_peak, B_peak·I)` 两段线与拐点的来历）在 [roofline 文](../../10-foundations/performance-models/01-roofline-model.md) §1，**此处只代入**。程序 §3 打印的结果（单位 FLOP/byte，dense）：

| 精度轴 | V100 | A100 | H100 | B200 |
|---|---|---|---|---|
| FP32 向量 | 17.4 | 9.6 | 20.0 | 9.7 |
| TF32 TC | — | 76.5 | 147.6 | 142.9 |
| FP16 TC | 138.9 | 153.0 | 295.4 | 292.2 |
| BF16 TC | — | 153.0 | 295.4 | 292.2 |
| FP8 TC | — | — | 590.7 | 584.4 |
| FP4 TC | — | — | — | **1168.8** |

（TF32 那一行与 [roofline 文](../../10-foundations/performance-models/01-roofline-model.md) §5 表1 给出的 H100 `I* = 147.6` 一致；FP16 那一行与它的 295.4 一致。这是一处独立的交叉核对。）

**FP32 向量轴的十年**：`17.4 → 9.6 → 20.0 → 9.7`。最低 9.6、最高 20.0，最大最小之比只有 **2.09 倍**，而且序列是**震荡**的（降、升、降），不是单调迁移。原因很直接：

```text
FP32 向量算力的十年涨幅 = 75 / 15.7  = 4.78×
HBM 带宽的十年涨幅      = 7700 / 900 = 8.56×
两者之比 = 8.56 / 4.78 = 1.79 —— 只差 1.79 倍，商自然就在原地打转。
```

**低精度轴的十年**：FP16 TC 的 `I*` 从 138.9 走到 292.2（2.10×）；再往低走，B200 的 FP8 是 584.4、FP4 是 1168.8。**从 V100 的 FP16（138.9）到 B200 的 FP4（1168.8），拐点移动了 8.42 倍。**

这 8.42 倍的来源可以拆干净：

```text
算力涨幅（V100 的 FP16 → B200 的 FP4）= 9000 / 125  = 72.0×
带宽涨幅                              = 7700 / 900 = 8.56×
商 = 72.0 / 8.56 = 8.42 —— 正是拐点的迁移倍数 1168.8 / 138.9。
```

> **迁移的全部来源是分子（精度阶梯），不是分母（带宽）。**

这就是「必须换精度而不是换算法」的量化依据。一个 `I = 150` 的算子，在 V100 上刚过拐点（138.9）属算力受限；到 B200 上它离 FP16 的拐点（292.2）差 1.9 倍，早已是带宽受限。同一条算法、同一份数据，换硬件的净效果是**把它推到带宽那一侧**。唯一能把它推回去的操作是换精度——FP4 那一档的拐点是 1168.8。

### 第三步：多步推导——封闭形式，一个算子在哪一代翻转

*（i）拐点怎么移。* 设两代的算力增长率为 `r_P = P₂/P₁`，带宽增长率为 `r_B = B₂/B₁`：

```text
I*₂ / I*₁ = (P₂/B₂) / (P₁/B₁) = r_P / r_B

记 ρ = r_B / r_P（带宽增长率 ÷ 算力增长率），则 I*₂ = I*₁ / ρ：
    ρ > 1（带宽涨得更快）  ⇒  拐点下降
    ρ < 1（算力涨得更快）  ⇒  拐点上升
```

**拐点的迁移方向只由 `r_P` 与 `r_B` 谁大决定，与绝对规模无关。**

*（ii）翻转写成区间。* 算子在某一代算力受限 ⟺ `I > I*`。所以要跨代翻转，`I` 必须落在两代拐点之间：

```text
翻转 ⟺ min(I*₁, I*₂) < I < max(I*₁, I*₂)
     ⟺ I / I*₁ ∈ ( min(1, 1/ρ) , max(1, 1/ρ) )

· ρ < 1（拐点上升）⇒ 窗口 (I*₁, I*₁/ρ)，方向  算力受限 → 带宽受限
· ρ > 1（拐点下降）⇒ 窗口 (I*₁/ρ, I*₁)，方向  带宽受限 → 算力受限
```

第三条是最有用的一句：

> **带宽涨得比算力快的那一代，会把一批算子从算力受限甩到带宽受限那一侧。**

*（iii）逐代核对。* 程序 §4 打印六个窗口：

| 跃迁 / 精度轴 | `ρ = r_B/r_P` | 拐点方向 | 窗口宽度 | 翻转后的方向 | 窗口两侧的 `I*` |
|---|---|---|---|---|---|
| V100→A100 FP32 | 1.8241 | 下降 | 1.824× | 带宽受限 → 算力受限 | (9.6, 17.4) |
| V100→A100 FP16 | 0.9077 | 上升 | 1.102× | 算力受限 → 带宽受限 | (138.9, 153.0) |
| A100→H100 FP32 | 0.4782 | 上升 | 2.091× | 算力受限 → 带宽受限 | (9.6, 20.0) |
| A100→H100 FP16 | 0.5180 | 上升 | 1.930× | 算力受限 → 带宽受限 | (153.0, 295.4) |
| H100→B200 FP32 | 2.0533 | 下降 | 2.053× | 带宽受限 → 算力受限 | (9.7, 20.0) |
| **H100→B200 FP16** | **1.0108** | 下降 | **1.011×** | 带宽受限 → 算力受限 | (292.2, 295.4) |

最后一行是**反例**：窗口宽度只有 1.011 倍，因为两代的 FP16 拐点几乎重合（295.4 对 292.2，差 −1.07%）。**几乎没有算子会在这个窗口里翻转。**

> **「新一代一定重排瓶颈类型」是错的**——重排只发生在拐点真的动了的那些跃迁上。H100 与 B200 在 FP16 这一档上，平衡点是一样的。

*（iv）把窗口换算成 batch。* 取一个具体的 GEMM 族：`X[M×8192] @ W[8192×8192]`，只有 `M` 变。由 `I = 2MKN / (2(MK+KN+MN))`，代入 `K = N = 8192`：

```text
I(M) = 4096·M / (M + 4096)    ⟶_{M→∞}  4096 = K 与 N 的调和平均
```

（核对：`I(4096) = 2048.0`、`I(512) = 455.1`，与 [roofline 文](../../10-foundations/performance-models/01-roofline-model.md) §5 表3 的 prefill 大 / 小 GEMM 两行一致。这两行是引用，不是本文算出来的新数。）

反解出每个窗口对应的 `M` 区间：

| 跃迁 / 精度轴 | 翻转的 `M` 区间 | 方向 |
|---|---|---|
| V100→A100 FP32 | M ∈ (9.6, 17.5) | 带宽受限 → 算力受限 |
| V100→A100 FP16 | M ∈ (143.8, 159.0) | 算力受限 → 带宽受限 |
| A100→H100 FP32 | M ∈ (9.6, 20.1) | 算力受限 → 带宽受限 |
| **A100→H100 FP16** | **M ∈ (159.0, 318.3)** | **算力受限 → 带宽受限** |
| H100→B200 FP32 | M ∈ (9.8, 20.1) | 带宽受限 → 算力受限 |
| H100→B200 FP16 | M ∈ (314.7, 318.3) | 带宽受限 → 算力受限 |

§0 那个例子（`M = 256`）落在这张表的第四行里。

### 第四步：多步推导——用官方 FP32 峰值反推时钟，交叉验证 SM 数

FP32 向量峰值有一个只用规格常量的解析式：

```text
P_FP32 = SM 数 × 每 SM FP32 lane 数 × 2 FLOP/lane × 时钟

反解：  时钟 = P_FP32 / (SM 数 × lane 数 × 2)
```

那个 `2` 来自 FMA 计 2 FLOP（一次乘、一次加），口径与 [roofline 文](../../10-foundations/performance-models/01-roofline-model.md) §1 第一步一致。四代代进去（程序 §6）：

| 代 | SM 数 | lane/SM | 官方 FP32 峰值 | **反推时钟** | 公开时钟对照 |
|---|---|---|---|---|---|
| V100 | 80 | 64 | 15.7 | **1.533 GHz** | 1.53 GHz |
| A100 | 108 | 64 | 19.5 | **1.411 GHz** | 1.41 GHz |
| H100 | 132 | 128 | 67.0 | **1.983 GHz** | NVIDIA 不公布 |
| B200 | **148** | 128 | 75.0 | **1.980 GHz** | 官方未披露 |

V100 与 A100 两代的反推值与公开的 boost clock 吻合到小数点后两位——这验证了公式与规格常量两边都没错。

**B200 那一行是本文用得上的一处交叉验证。** 官方技术简报**没有披露 B200 的 SM 数**，而官方 FP32 峰值是 75 TFLOPS。反解：

```text
取 148 SM：时钟 = 75e12 / (148 × 128 × 2) = 1.980 GHz —— 与 H100 的 1.983 GHz 几乎相同
取 132 SM：时钟 = 75e12 / (132 × 128 × 2) = 2.219 GHz —— 在 1000 W 的封装下不可信
```

两代同制程世代（TSMC 4N / 4NP）、同样的 128 lane 配置，时钟落在同一个点上才是合理的设计；2.219 GHz 则要求在一个 1000 W 的封装里跑出比 H100 高 12% 的频率。**所以本文的逐代表一律取 148，并标注为「非官方直述，由官方 FP32 峰值反推 + Hot Chips 2024 披露交叉验证」。**

*（附带得到一个与发射槽有关的恒等式。）* 每 SM 每周期最多发射 4 条 warp 指令、每条覆盖 32 个 lane，所以每周期最多 `4 × 32 = 128` 个 lane 操作。把 FP32 lane 数代进去：

| 代 | FP32 lane/SM | 达到峰值所需 | 占发射上限 |
|---|---|---|---|
| V100 | 64 | 2.0 条 FFMA/周期 | 50.0% |
| A100 | 64 | 2.0 条 FFMA/周期 | 50.0% |
| H100 | 128 | 4.0 条 FFMA/周期 | **100.0%** |
| B200 | 128 | 4.0 条 FFMA/周期 | **100.0%** |

A100 只需要 2 条 FFMA/周期就顶到 FP32 峰值，发射上限有 2 倍余量；**H100 / B200 需要 4 条，即把 4 个发射槽全部占满、一条别的指令都不能插**。换句话说，Hopper 的 FP32 峰值恰好等于发射上限，**零余量**。任何一条 `LDS`、地址运算或分支指令都会从峰值上扣掉一份。

这不是实现缺陷，是「128 lane/SM」与「4 发射槽/周期」这两个规格的算术后果——也是 **Hopper 把 FP32 向量通路从 64 加宽到 128** 这一动作的直接兑现：加宽让峰值翻倍，同时把余量从 2 倍压到 0。

### 第五步：把真实算子放上去——以及一个反直觉的结论

下表算子的算术强度**引自 [roofline 文](../../10-foundations/performance-models/01-roofline-model.md) §5 表3**，本文不重算（重算会得到第二份数字，违反「一个知识点一处正文」）。右四列是本文加的分类（程序 §5）：

| 算子 | `I` | V100 | A100 | H100 | B200 |
|---|---|---|---|---|---|
| decode GEMV（batch=1） | 1.000 | 带宽 | 带宽 | 带宽 | 带宽 |
| softmax（4096×4096） | 1.250 | 带宽 | 带宽 | 带宽 | 带宽 |
| SiLU（elementwise） | 1.250 | 带宽 | 带宽 | 带宽 | 带宽 |
| LayerNorm | 1.500 | 带宽 | 带宽 | 带宽 | 带宽 |
| attention QKᵀ | 120.471 | 带宽 | 带宽 | 带宽 | 带宽 |
| attention PV | 120.471 | 带宽 | 带宽 | 带宽 | 带宽 |
| prefill 小 GEMM（M=512） | 455.111 | 算力 | 算力 | 算力 | 算力 |
| prefill 大 GEMM（M=4096） | 2048.000 | 算力 | 算力 | 算力 | 算力 |

> **在 FP16 轴上，上表 8 个算子没有一个发生过翻转。**

这是一个必须说出来的负面结论。它的成因是分布的形状：

- elementwise / 归约一族挤在 `I ≈ 1 ~ 1.5`，离**最低**的拐点（V100 的 138.9）还差两个数量级；
- 两个 GEMM 在 `I = 455` 与 `2048`，离**最高**的拐点（H100 的 295.4）还高出一截；
- 而所有翻转窗口（§1 第三步的表）全都落在 9.6~20.1 与 138.9~318.3 这两段里。

**中间那一段是空的**——真实算子的算术强度分布是双峰的（`O(1)` 的访存型与 `O(10²~10³)` 的矩阵型），而翻转窗口落在两峰之间的谷里。所以「换了硬件瓶颈类型就变了」这句话，对绝大多数算子都不成立；它只对**恰好落在窗口里的那一小段形状**成立，比如 §0 那个 `M = 256` 的宽 GEMM。

这条结论对实践的意义恰好与直觉相反：**不要指望换代来改变你手上算子的瓶颈类型。** 换代能改变的是绝对吞吐（§0 里是 2.59 倍），改变瓶颈类型要靠改 `I`——也就是改精度或改数据流。

## 2. 执行映射

拐点迁移在 SM 上留下一个具体痕迹：**同样的指令组合，发射槽不再被算力占满。**

先把 §1 第四步那个恒等式说清楚。每 SM 每周期 4 个发射槽，每条 warp 指令覆盖 32 个 lane：

```text
每周期 lane 操作上限 = 4 × 32 = 128
一条 FFMA = 2 FLOP/lane  ⇒  FP32 峰值需要 128 × 2 = 256 FLOP/周期/SM
```

于是两侧的分工是：

- **算力受限时**，这 4 个槽被 FFMA 填满，FP32 达到 `128 lane × 2 FLOP × 时钟`；在 H100 上这是零余量的满配。
- **带宽受限时**，FFMA 流被操作数等待打断。**LSU**（load/store unit，处理访存指令、把 warp 的 32 个地址合并成事务的部件）发出的 `LDG` 占掉发射槽，但它在等 L2/HBM 时下游的 FP32 端口是空的。**发射槽还在被消耗，只是消耗在了等待上。**

具体的部件分工：

- **HBM 侧**由显存控制器与显存总线决定。所有 `Bytes` 都要从这条总线上过一遍，没有第二条路——这是 `Bytes` 只统计 HBM 流量的物理依据（正文在 [memory-system/01-hierarchy-overview](../memory-system/01-hierarchy-overview.md) §1 第五步）。
- **L2**（H100 为 50 MB）能挡下一部分流量，从而改变**有效**算术强度。roofline 故意不把它算进 `I`——曲线给的是上界。
- **Tensor Core 侧**由 Tensor Core 单元决定。把它与 FP32 通路放在一起看，就得到 §1 那个「每降一档翻一倍」的阶梯。

一个可以直接用来判断的数：**H100 全卡每周期 132 × 4 = 528 个发射槽**。一个 kernel 的 IPC 长期低于它对应的理论值，且 `LDG` 占比高，就说明发射槽消耗在了等待上——这正是「拐点越过了这个算子」在硬件上的样子。

## 3. 实现与演进

这一节的主线是**精度阶梯如何逐代把峰值推高**——因为 §1 已经证明，拐点的移动全部来自分子。

### 阶梯的形状（B200，程序 §8）

| 精度 | 首次出现 | B200 峰值 (dense) | 相对 FP32 向量 |
|---|---|---|---|
| FP32 向量 | P100 | 75.0 | 1.0× |
| TF32 TC | A100 | 1100.0 | 14.7× |
| FP16 TC | V100 | 2250.0 | 30.0× |
| BF16 TC | A100 | 2250.0 | 30.0× |
| FP8 TC | H100 | 4500.0 | 60.0× |
| FP4 TC | B200 | 9000.0 | 120.0× |

三条可以直接引用的量级：

1. **B200 的 FP4 相对 FP32 向量是 120 倍。** 这就是「精度阶梯」的全部内容。
2. **位宽精确减半的两档，峰值精确翻倍**：FP16→FP8 是 2.0×、FP8→FP4 是 2.0×。TF32→FP16 只是**约** 2 倍（2.05×，两边的官方数字各自取过整）。而 **FP32 向量→TF32 不是一档，是 14.7 倍的大跳**——「每降一档翻一倍」这句口诀只适用于 TF32 以下的阶梯，别套到 FP32 那一跳上。
3. **迁移的账**：算力涨 72.0×、带宽涨 8.56×，商 8.42× —— 正是拐点的迁移倍数。

### 逐代的两次提速，性质不同

- **V100（2017）**：FP16 tensor core 第一次出现，`I* = 138.9`。它是通过「加一个执行单元」实现的——FP16 的 125 TFLOPS 相对 FP32 向量的 15.7 是 8.0 倍，这个倍数来自「一条指令顶几十条」。
- **A100（2020）**：TF32 与 BF16 同时到位，`I*` 分叉成 `76.5 / 153.0` 两条。它们不是新单元，只是输入端口换了解码（正文在 [01-capability-breakpoints](01-capability-breakpoints.md) §2），**但换解码就换来了 2 倍的峰值与一条新的拐点**。
- **H100（2022）**：FP8 到位，`I* = 590.7`。这一次的提速里混了一部分「不是低精度」的成分——FP32 向量通路从 64 lane 加宽到 128（§1 第四步），使 FP32 峰值涨了 3.44×。
- **B200（2024）**：FP4 到位，`I* = 1168.8`。FP32 向量几乎停滞（1.12×），低精度继续翻倍。

### tensor core 相对 CUDA core 的比值——一个反例

| 代 | FP16/FP32 | FP8/FP32 | FP4/FP32 |
|---|---|---|---|
| V100 | 8.0× | — | — |
| A100 | 16.0× | — | — |
| **H100** | **14.8×** | 29.5× | — |
| B200 | 30.0× | 60.0× | 120.0× |

**H100 那一格是本节的重点。** FP16:FP32 的比值从 A100 的 16.0× **掉到** H100 的 14.8×，因为 Hopper 的 FP32 向量吞吐涨了 3.44×，快于 FP16 tensor 的 3.17×。

> **「tensor core 相对收益逐代单调增大」这句话是错的。**

它在 A100→H100 这一段是**下降**的，到 B200 才又跳到 30.0×。序列是 `8.0 → 16.0 → 14.8 → 30.0`——先涨、再跌、再涨。

这条反例有直接的实践后果：「用 tensor core 一定比 FP32 快 N 倍」里的 `N` 不是一个逐代变大的数，用上一代的 `N` 去估下一代会在 H100 这一代上估高。**每一代都要用规格表重算，不能外推。**

## 4. 踩坑与失败模式

下面四条都是**在已知本文全部内容的前提下仍然会犯**的——它们不是「混了口径」这种粗心错误，而是口径本身有陷阱。

### 4.1 把 SXM 档与 PCIe 档混进同一张趋势表

**现象**：从两份规格表里各抄一列，做出一条「带宽逐代增长」的曲线，结果某一代的增长明显偏慢或偏快，画出来的趋势是折线。或者更常见：拿 H100 PCIe 的 114 个 SM 去和 A100 SXM 的 108 去比，得出「Hopper 的 SM 数只涨了 5.6%」。

**成因**：**同代内的两个封装档不是同一台机器。** H100 SXM5 是 132 SM / 700 W / 3.35 TB/s；H100 PCIe 是 114 SM / 350 W / 2.0 TB/s——SM 数差 13.6%、带宽差 **40.3%**、TDP 差一倍。把 PCIe 档混进 SXM 序列，等于在一条曲线上换了一次机器。

这条陷阱之所以致命，是因为它**不会报错**：两个数都是真的、都来自官方文档、单位也一样。错误只体现在趋势的形状上。

**规避**：在表头显式写死档位，本文的口径是「数据中心 SXM 档：P100 SXM2 / V100 SXM2 / A100 SXM4 80GB / H100 SXM5 / B200 SXM」，`code/specs.py` 的每个逐代常量以**代号前缀隐含档位**——`P100_` / `V100_` / `A100_` / `H100_` / `B200_` 一律指上表中的 SXM 档；唯一的另一个封装档用显式的 `H100_PCIE_` 前缀，并在模块里注明「不进任何趋势表，只为让这条陷阱的差值可以被程序算出来」（见模块开头的口径约定）。任何一次引用前问一句「这一列是哪个封装」。**同时注意 Turing 没有数据中心 SXM 档**（只有 PCIe 70 W 的 T4），所以本文的每一张逐代表都**不含 Turing**——不是遗漏，是口径。

### 4.2 把晶体管数当容量指标读

**现象**：看到 V100 21.1 B、A100 54.2 B、H100 80 B、B200 208 B，算出 B200 一代涨了 2.6 倍，据此推断「Blackwell 的规模是 Hopper 的两倍多」，进而估错 die 面积、良率、成本。

**成因**：**晶体管数的口径在 Blackwell 这一代断了。** P100~H100 一栏是**单 die 数**，而 B200 的 208 B 是**双 die 封装的总数**（单 die 104 B）。把两类数放在同一列上，2.6 倍里有一半是「从 1 个 die 变成 2 个 die」的计数方式变化，不是密度或规模的变化。

**规避**：见到跨代的晶体管数，先问「这是 die 数还是封装数」。正确的读法是**先归一到单 die**：B200 取 104 B，对 H100 的 80 B 是 1.30 倍；再叠加制程（TSMC 4N → 4NP）与封装（双 die）两项分开记。本文的逐代表把这一格单独标注出来，就是为了不让它在同一列里被误读。

### 4.3 用 SM 数外推算力

**现象**：看到 H100 有 132 个 SM、A100 有 108 个，按 `132/108 = 1.22` 估算两代的算力比，得到一个「Hopper 比 Ampere 快 22%」的结论。

**成因**：**SM 数增长率 ≠ 算力增长率**，有两个独立的偏差来源。

其一，**每 SM 的 lane 数会变**：数据中心线在 Hopper 这一代从 64 lane/SM 跳到 **128** lane/SM（A100 是 64，GA100 的事实；「Ampere = 128 FP32/SM」是消费级 GA10x 的事实，两者不能混）。于是 H100 相对 A100 的 FP32 峰值涨幅是 `(132 × 128) / (108 × 64) = 2.44×` 再乘频率——而不是 1.22×。

其二，**每 lane 每周期做的事会变**：tensor core 的加入让一条指令顶掉几十条 FFMA，这部分完全不体现在 SM 数上。

**规避**：算力一律用**峰值**（TFLOPS）本身，并带上「精度 + dense/sparse + 封装」三元口径（§4.4）；SM 数只在需要算「总常驻线程容量」（SM 数 × 每 SM 常驻线程数）时才用。（这一条陷阱的完整版在 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md) §4.1。）

### 4.4 不带口径地引用 Tensor Core 数字

**现象**：在文档里写「H100 的 FP16 Tensor Core 是 1979 TFLOPS」，据此算出一个 roofline 拐点 590.7，然后判定某个算子是带宽受限。结论整个反了。

**成因**：**NVIDIA 用于宣传的那个数字是带 2:4 稀疏的。** 产品页写 `1979 TFLOPS*`，星号脚注是 *with sparsity*，而 dense 是 **989.5**。A100 同理（**312** dense / **624** sparse）。两者相差**正好 2 倍**，混用会让 `I*` 整体挪位一倍，判定的两侧随之反转。

同一类陷阱还有第二个变体：**累加器类型改变 TFLOPS**。同一个 FP8 Tensor Core，配 FP16 累加与配 FP32 累加，峰值可以差 2 倍（Ada 白皮书就把这两个数列成了两行：389.9 与 194.9）。所以「这个格式有多少 TFLOPS」这个问法**本身不完整**。

**规避**：任何 Tensor Core 峰值都必须写成四元组——**`<型号> <精度> <累加器类型> <dense/sparse>`**。本文与 `code/specs.py` 全程用 dense，且常量名带 `_TFLOPS_DENSE` / `_TFLOPS_SPARSE_2TO4` 后缀，让口径写在名字里。程序 §9 把这条陷阱做成了现场演示（A100 624/312、H100 1979/989.5 两行并排）。

## 6. 小结与延伸

全文只有一条主线：**算力涨得比带宽快，但只在低精度轴上。** 围绕这条主线，有四个可独立复用的中间结论：

1. **拐点的迁移方向只由 `r_P` 与 `r_B` 谁大决定**：`I*₂/I*₁ = r_P/r_B`。ρ = 带宽增长率 ÷ 算力增长率；ρ < 1 时算子从算力受限翻到带宽受限，ρ > 1 时反过来。翻转窗口是 `min(I*₁, I*₂) < I < max(I*₁, I*₂)`。
2. **FP32 向量轴上没有趋势。** 拐点 `17.4 → 9.6 → 20.0 → 9.7`，十年涨幅 4.78×、带宽 8.56×，两者只差 1.79 倍，商在 2.09 倍的范围内震荡。**真正的迁移是 FP16 的 138.9 到 FP4 的 1168.8，8.42 倍**——全部来自分子（算力涨 72.0×），不是分母。
3. **换精度而不是换算法**有了量化依据，但「换代重排瓶颈」并不普遍：H100→B200 的 FP16 窗口只有 1.011 倍宽；本文引用的 8 个真实算子**没有一个**在 FP16 轴上翻转过。真实算子的 `I` 分布是双峰的，翻转窗口落在两峰之间的谷里。
4. **每一代都要用规格表重算，不能外推。** tensor:FP32 的比值序列是 `8.0 → 16.0 → 14.8 → 30.0`——先涨、再跌、再涨。「相对收益逐代单调增大」是错的。

下一篇 [03-invariants](03-invariants.md) 把方向反过来：本文与 [01-capability-breakpoints](01-capability-breakpoints.md) 讲的全是「变」，而有些数字十几年没动——warp 大小 32、每 block 1024 线程、每线程 255 个寄存器、每 SM 256 KB 寄存器文件、32 个 bank。**知道哪些不动，才知道哪些代码能活得久**——那里还会有一条会让读者意外的失败模式：「每 SM 最大常驻 warp 数」**不是**架构不变量，只是数据中心 SXM 产品线的巧合稳定。
