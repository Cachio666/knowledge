# 架构不变量：哪些数字十几年没动

> warp 大小 32、每 block 1024 线程、每线程 255 个寄存器、共享内存 32 个 bank、每 SM 256 KB 寄存器文件——这五个数字从 CC 3.5 一路到 CC 12.x 没动过。而同一张官方规格表里紧挨着的另一栏（每 SM 最大常驻 warp / 线程 / block 数）**不是**不变量，它只是数据中心 SXM 产品线的巧合稳定。**分不清这两栏，就会把产品线的巧合当成架构的保证。**

> **全文的数字口径**：本文的数字分两类——**规格值**（直接引自 NVIDIA 官方文档，见参考）
> 与**推导值**（由 `code/specs.py` 中的规格常量代入 §1 的公式算出）。**本文无实测数据。**
> 唯一的例外是 §7 的访存延迟：那是**外部引用值**，本文只转述、不产出、也无法复核，已在原处单独标注。
> 要复核本文其余数字，运行 `code/03_invariants.py`，它会打印出本文引用的每一个数。

## 0. 背景与动机

一份 2012 年为 Kepler 写的 warp 内规约 kernel：`__shfl_down` 做 5 级（`32 → 16 → 8 → 4 → 2 → 1`），block 形状是 1024 线程，共享内存数组按 32 个 bank 做了 padding，寄存器预算按每线程 40 个设计。

这份代码今天**仍然能编译、能跑、资源账本一分不差**。它的每一处数字假设都还在——warp 大小、每 block 线程上限、寄存器分配粒度、bank 数，全部没变。

同一份代码里如果有一条注释写着「每 SM 挂 64 个 warp 就能占满」，那句话在 Turing 上错 **2 倍**、在 Ada 上错 **1.33 倍**。而它和上面那些数字**写在官方规格表的相邻两栏里**。前者跨 CC 不变，后者同一列逐 CC 不同——这就是本文要划开的那条线。

划开它有直接的工程收益：**知道哪些数字不动，就知道哪些代码能活得久。**反过来，把「本产品线稳定」读成「架构保证」，就会写出在开发机上永远正确、在交付目标上永远错的代码。

本文的组织与前两篇相反。[01-capability-breakpoints](01-capability-breakpoints.md) 讲「能不能表达」的断点，[02-scaling-trends](02-scaling-trends.md) 讲「能不能跑到峰值」的趋势——两篇都在讲**变**。本文讲**不变**：逐个给出这些数字（§1），推导它们为什么不动（§1 的三个多步推导），指出它们各自钉在 SM 的哪个部件上（§2），再从不变量的角度回看前两篇那些「变」发生在哪里（§3）。

**分工说明。** 逐代的 SM 内部规格（共享内存容量、常驻 warp 上限的逐代表）与占用率四约束的完整推导正文在 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md) 与 [execution-model/03-occupancy-and-latency-hiding](../execution-model/03-occupancy-and-latency-hiding.md)，本文只引用结论。逐代存储层次在 [memory-system/01-hierarchy-overview](../memory-system/01-hierarchy-overview.md)。

## 1. 原理

### 第一步：先列出不变量（程序 §1）

| 量 | 值 | 依据 |
|---|---|---|
| warp 大小 | **32** | CUDA 13.4 §5.1 表 **与** CUDA 11.8 归档版 §5.1 表，两代一致 |
| 每 block 最大线程数 | 1024 | CUDA 13.4 §5.1（CC 2.0 起即为 1024） |
| 每线程最大寄存器数 | 255 | CUDA 13.4 §5.1（CC 3.0 起即为 255） |
| 共享内存 bank 数 | 32 | CUDA 13.4 §5.1，**各 CC 恒为 32** |
| 每 bank 宽度 | 4 B（32-bit） | CUDA 13.4 §5.1 |
| 每 SM 寄存器文件 | **256 KB**（65536 个 32-bit 寄存器） | CUDA 13.4 §5.1（CC 3.5 起） |

**唯一的例外必须与它一起写出**：CC 3.7（GK210）的每 SM 寄存器文件是 **512 KB**，是标准值的 2 倍。不写出这一格，「256 KB 是不变量」就是一个假陈述。不过它是**孤例**——此后到 CC 12.x 再没有出现过 512 KB 的 SM。

时间跨度是十几年（CC 3.5 是 Kepler GK110，2012）。而同样跨度的两个增长量是：

```text
每 SM 的 FP32 向量峰值：15.7 → 75 TFLOPS   = 4.78×（V100 → B200，只算数据中心线）
每 SM 的 FP16 tensor 峰值：125 → 2250 TFLOPS = 18.0×
```

**增长全部来自「每 lane 每周期做多少事」，不来自「能装多少东西」。** 这条分工是本文与前两篇的连接点：前两篇讲的那些「变」全部发生在这条线**上面**那一侧；本节这些数在**下面**那一侧一动不动。

### 第二步：多步推导一——warp 大小为什么钉死在 32

*（i）warp 大小不是孤立参数，它同时是四个东西。*

| # | 它同时是 | 改它会动到什么 |
|---|---|---|
| 1 | **SIMT 的发射宽度** | 一条指令覆盖 32 个 lane；改了就改了数据通路宽度 |
| 2 | **寄存器分配的单位** | 每 warp 占用 = warp 大小 × 每线程寄存器数 |
| 3 | **调度器的记账单位** | active mask、PC、记分板位都是每 warp 一份 |
| 4 | **共享内存的冲突单位** | 32 个 bank 恰好让 stride-1 访问无冲突（见第一步推导三） |

*（ii）四条独立约束从不同方向给出 32。*

**约束一（发射宽度）。** 每 SM 有 4 个 warp scheduler，每周期各发射 1 条 warp 指令。若 warp 大小变成 64，这 4 条指令就要覆盖 256 个 lane，而每 SM 的 FP32 数据通路只有 **128** 个 lane（H100/B200）——要么把通路加宽到 256 lane，要么让一条指令占 2 个周期发射。两条路的代价都落在同一处：**每 SM 每周期能发射的 warp 指令数**（H100 全卡是 132 × 4 = 528）。

**约束二（寄存器读端口）。** 寄存器文件被 4 个处理块均分，每块服务本块的 32 个 lane，每周期读出一个 warp 的全部操作数。warp 变成 64 意味着每块的读端口数翻倍——而 [memory-system/01-hierarchy-overview](../memory-system/01-hierarchy-overview.md) §1 第一步已经论证过：**寄存器堆做不大的主因正是端口数与面积**。于是「warp 加倍」会反过来压小寄存器文件，直接打破上面那条 256 KB。

**约束三（分配粒度）。** 每线程寄存器按 8 个一档分配（正文在 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md) §1 第七步），所以每 warp 的分配粒度是 `8 × warp 大小`。warp = 32 时是 **256 个寄存器一档**，而 `65536 ÷ 256 = 256` 个 warp 槽位——这个整除是硬件按整档记账的前提。

**约束四（整除恒等式）。** 反解一次，看 warp 大小与寄存器文件的关系：

```text
65536 ÷ 32 = 2048    ← 寄存器文件 ÷ warp 大小

而数据中心线的每 SM 最大常驻线程数恰好也是 2048。
    ⇒  寄存器文件 = warp 大小 × 常驻线程上限   （该产品线上、二者都取满时成立）
```

这条恒等式把 warp 大小与寄存器文件钉在一起：换个 warp 大小，`65536 ÷ 新值` 就不再等于那条产品线选定的线程上限，于是要么改寄存器文件容量（打破第一步那张表里的不变量），要么改线程上限（那是产品决定，见第五步）。

**注意这条恒等式用到了一个产品量**（数据中心线的 2048）——所以它解释的是「warp 大小为什么与这条产品线配得这么整齐」，不是「32 是 32 的唯一原因」。**把产品线决策当论据用，正是 §4 第一条那个坑的雏形**；这里的结论只有当三个量同时摆出来时才成立。

*（iii）还有一条与性能无关、但有决定性的约束——二进制兼容。*

warp 大小是写进 ISA 与 ABI 的：

- `__ballot_sync` / `__activemask` 返回的是 **32 位**掩码；
- 所有 `*_sync` 原语的 mask 参数是 32 位；
- 每 block 线程数按完整 warp 切分，`1024 = 32 × 32` 恰好整除；
- 已经编译出的**每一份 cubin** 都按 32 编码。

warp 变成 64，上面四项要同时改成 64 位掩码与新编码。**这不是「新硬件加个特性」，是「让过去十几年的二进制全部作废」。** 这是 32 之所以能钉住的最强理由：它的代价不是性能，是生态。

### 第三步：多步推导二——寄存器文件为什么是架构量，线程上限为什么不是

这两个数看起来是一对（65536 个寄存器、2048 个线程）。但它们的性质完全不同。判别方法只有一个：**在规格变化时，哪个动了？**

*（i）取三个真实存在过的线程上限，各自反解出满额常驻时的每线程寄存器预算。*

| CC | 线程上限 | `65536 ÷ 线程上限` | 是否整除 | 按 8 一档可取 |
|---|---|---|---|---|
| 7.5（Turing） | 1024 | 64.00 | 是 | r = 64，用掉 65536 / 65536，**余 0.00%** |
| 8.9（Ada） | 1536 | **42.67** | **否** | r = 40，用掉 61440 / 65536，**余 6.25%** |
| 9.0（H100） | 2048 | 32.00 | 是 | r = 32，用掉 65536 / 65536，**余 0.00%** |

*（ii）三行的分母在变（1024 / 1536 / 2048），分子始终是 65536。* 这就是判别结果：**线程上限在动，寄存器文件没动。**

*（iii）第三列还暴露了一件事。*

- 2048 与 1024 都是 65536 的**因数**，整除后得到 32 与 64，**零浪费**；
- 1536 **不是** 65536 的因数，反解出 42.67 这个非整数。按 8 一档只能取到 `r = 40`，于是 `65536 − 40 × 1536 = 4096` 个寄存器用不上——占整个寄存器文件的 **6.25%**，也就是**每 16 个寄存器白扔 1 个**。

换句话说：**2048 与 1024 是与 65536 共同设计过的线程上限，1536 不是。** 1536 是把一个产品决定（「这个 SKU 给多少线程」）叠在一个架构常量上，叠的时候没有对齐——**这个不整齐本身就是它有别于寄存器文件的证据**。

*（iv）反证另一头。* 如果寄存器文件才是那个可动的量，我们会看到什么？会看到 1536 线程的产品配一份能让 1536 整除的寄存器文件（例如 61440 或 73728 个），而 2048 线程的产品配另一份。

**实际没有发生——所有 CC 都报 65536。** 一写就是十年。

*（v）结论。*

> **65536 个寄存器 / SM（256 KB）是架构常量；每 SM 最大常驻线程数是产品线决策。**

数据中心 SXM 线恰好稳定在 2048，但**那不是「架构规定的」**。这条区别是本文最需要记住的一条，它的后果在 §4 第一条。

### 第四步：多步推导三——bank 数为什么也等于 32

*（i）编号规则。*

```text
bank = (字节地址 ÷ 4) mod 32
```

一个 warp 的 32 个 lane 在同一周期各发一个地址；硬件按 bank 分拣，**一个 bank 一个周期只服务一个地址**。所以这次访问的周期数 = 这个 warp 触及的不同 bank 数。

*（ii）取最典型的访问——stride-1，lane `i` 访问 `base + 4i`。*

```text
bank(lane i) = ((base + 4i) ÷ 4) mod 32 = (base/4 + i) mod 32
```

`i` 从 0 走到 31 时，`(base/4 + i) mod 32` 恰好取遍 0..31 各一次。**32 个 lane 落在 32 个不同 bank 上，一个周期读完。**

*（iii）反解——如果 bank 数不是 32 会怎样？*

| bank 数 | stride-1 触及的 bank 数 | 周期数 | 代价 |
|---|---|---|---|
| 8 | 8 | 4 | 4 路冲突 |
| 16 | 16 | 2 | 2 路冲突 |
| **32** | **32** | **1** | **无冲突** |
| 64 | 32 | 1 | 无冲突，**但加倍硬件、收益为零** |

16 个 bank 会让**每一次** stride-1 访问都吃 2 个周期；64 个 bank 则是一个字节都不多读、却要付双倍面积。**32 是让规范访问恰好无冲突的最小值**——所以它也被钉住了。

*（iv）把这条与 warp 大小放在一起。*

```text
bank 数 × bank 宽度      = 32 × 4 B = 128 B
warp 大小 × 每 lane 字宽 = 32 × 4 B = 128 B
                          ↑ 两边相同
```

一次 stride-1 访问正好把一个 warp 的数据铺满全部 bank，**一个字节不剩、一个周期不等**。

所以「bank 数 = warp 大小」不是巧合同一个数字，而是**同一个约束的两种写法**：32 是那条「一次访问服务一个 warp」的宽度，写在调度器上叫 warp 大小，写在 SRAM 上叫 bank 数。**改其中一个，另一个必须跟着改。**

### 第五步：反面清单——哪些数字**不是**不变量

这是本节的另一半，也是最容易被漏掉的一半。官方规格表里紧挨着上面那张表的另一栏：

| CC | 代表（产品线） | 常驻 warp | 常驻线程 | 常驻 block |
|---|---|---|---|---|
| 6.0 | P100（数据中心） | 64 | 2048 | 32 |
| 7.0 | V100（数据中心） | 64 | 2048 | 32 |
| **7.5** | **Turing（消费级）** | **32** | **1024** | **16** |
| 8.0 | A100（数据中心） | 64 | 2048 | 32 |
| 8.6 | GA10x（消费级） | 48 | 1536 | — |
| **8.9** | **Ada（消费级）** | **48** | **1536** | — |
| 9.0 | H100（数据中心） | 64 | 2048 | 32 |
| 10.0 | B200（数据中心） | 64 | 2048 | 32 |
| **11.0** | — | **48** | **1536** | — |
| **12.x** | — | **48** | **1536** | — |

（`—` 表示该 CC 的每 SM 最大常驻 block 数未在本文采用的来源中逐条核对，不填一个猜的值。本表的结论只用到 warp / 线程两栏。）

数据中心 SXM 线（6.0 / 7.0 / 8.0 / 9.0 / 10.0）五代的取值**完全一致**：64 warp / 2048 线程 / 32 block。

**但这不代表它是架构不变量。** 五个反例就在同一张官方规格表里：Turing 三条全不一样；Ada 与 CC 11.0 / 12.x 是 48 / 1536。

所以正确的表述是：**「本产品线稳定在 2048 线程」，不是「架构规定 2048 线程」。**

还有一处容易混进来的量：常驻 warp 数与常驻线程数只差一个因数（`32 × 32 = 1024`，后者是前者的 32 倍），**它们不是两个独立约束**。真正独立的是**每 SM 最大常驻 block 数**那一栏——它决定的是「并发粒度」而不是「并发总量」，所以它可以单独变（Turing 的 16 对数据中心线的 32）。

## 2. 执行映射

每个不变量落在 SM 的一个具体部件上。这张表（程序 §2–§4 的部件与数字）回答了「它为什么不自由」：

| 不变量 | 钉在哪个部件上 | 具体数量 |
|---|---|---|
| warp 大小 32 | **warp scheduler + dispatch unit + 32-lane FP32 数据通路 + 寄存器文件读端口** | 4 个调度器/SM；每周期 4 条 warp 指令；H100 全卡 528 个发射槽 |
| 每 block 1024 线程 | **block 调度器与 SM 的 block 槽位** | 1024 = 32 个完整 warp 恰好整除 |
| 每线程 255 寄存器 | **指令编码里的寄存器号字段** | 255 = 2⁸ − 1，即 8 位字段留一格 |
| 共享内存 32 bank | **共享内存 SRAM 的物理组织** | 32 × 4 B = 128 B = 一个 warp 的 stride-1 宽度 |
| 每 SM 256 KB 寄存器文件 | **4 个处理块的寄存器分片** | 65536 ÷ 4 = 16384 个/块，即 64 KB/块 |

几处值得单独看：

**寄存器文件那一格。** 65536 个 32-bit 寄存器被 4 个处理块均分，每块 **16384 个 = 64 KB**，服务本块 32 个 lane 的读端口。配合每 warp 的分配粒度（`8 × 32 = 256` 个寄存器一档），整个寄存器文件切成 **256 个 warp 槽位**。这三个数（65536 / 16384 / 256）是同一份预算的三种切法，任何一处变动都会牵动另外两处。

**255 那一格。** 255 = 2⁸ − 1，与 8 位寄存器号字段的容量恰好差 1（留一格）。它是**每线程**的上限，与**每 SM** 的 65536 是两个不同层级的约束——两者的关系在 §4 第二条里会咬人。

**block 那一格。** 1024 = 32 个 warp 恰好整除，这不是数字上的巧合，而是「block 由完整 warp 组成」这条规则的直接后果。它把「线程数」这个连续量离散化成了「warp 数」，也就让注册在 `blockDim` 上的所有资源计算都按 32 的整数倍跳变。

## 3. 实现与演进：从不变量的角度回看「变」

前两篇讲的全是「变」。把它们与本文的不变量叠在一起，会看到一个很清楚的分工：

| 十年里变了的 | 涨幅 | 十年里没变的 |
|---|---|---|
| FP16 tensor 峰值（V100 → B200） | 18.0× | warp 大小 32 |
| HBM 带宽（V100 → B200） | 8.56× | 每 SM 寄存器文件 256 KB |
| FP32 向量峰值（V100 → B200） | 4.78× | 共享内存 bank 数 32 |
| FP32 lane / SM（A100 → H100） | 2× | 每 block 1024 线程 |
| 访存延迟（外部引用值，见 §7） | 约 1.0× | 每线程 255 寄存器 |

**所有的「变」都发生在「每 lane 每周期做多少事」这条轴上；所有的「不变」都发生在「一个 SM 装得下什么、怎么组织」这条轴上。**

这条分工解释了几件事。

**其一，为什么算力的增长必须靠精度。** 寄存器文件十年没涨，意味着「加大 tile、多存中间结果」这条路被堵死了。[02-scaling-trends](02-scaling-trends.md) §1 已经算出低精度轴的拐点移动了 8.42 倍，而那个 8.42 倍的分母（带宽）只涨了 8.56×、分子（算力）涨了 72.0×。**分子能涨，是因为它不占存储**——同样一个矩阵乘，用 FP4 表示的操作数占的寄存器是 FP16 的四分之一，而吞吐是四倍。

**其二，为什么 Hopper 要另开一份 TMEM。** 前面说过，一个 m64n256 的 FP32 累加器 tile 分摊到 128 个线程上，每线程单是累加器就要占 128 个寄存器（正文在 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md) §3）。而 `65536 ÷ 128 = 512` 个线程，正好 4 个 warpgroup——**寄存器文件最多只装得下 4 个 warpgroup 的累加器**，还没算操作数、地址与循环变量。Blackwell 的解法不是把寄存器文件做大（那会打破一条十年不变量），而是**另开一份 256 KB 的 TMEM**。

**其三，为什么「不变量」这个词值得单独一篇。** 因为它是唯一能预测「哪些代码能活得久」的工具。按不变量写的代码——warp 内规约、32 路 shuffle、1024 线程的 block 形状、按 32 bank 排布的 padding、每线程 40 个寄存器的预算——在 CC 3.5 与 CC 12.x 上**语义与资源占用都不变**。按产品线决策写的代码（「挂 64 个 warp 就占满」「按 2048 算占用率分母」「共享内存给到 228 KB」）会随着目标型号漂移。

**判据只有一句话**：

> **这个数在 CUDA Programming Guide 的哪一栏？**
> 「Compute Capabilities」表里**同一行跨 CC 不变**的 → 不变量；
> **同一列跨 CC 会变**的 → 产品线决策，必须查表。

第一步那张表的每一行都是前者；第五步那张表的每一行都是后者。**两张表在官方文档里挨着，这正是它们最容易混为一谈的原因。**

## 4. 踩坑与失败模式

先诚实交代一句：**「不变量」这个词的含义是「官方规格表跨 CC 取值相同」，不是「永远不会变」。** 本文列出的五个数里，寄存器文件就**被打破过一次**——CC 3.7（GK210）是 512 KB。那是个孤例，而且已经过去十几年；但它提醒我们，按不变量写的代码并不获得豁免权。获得了什么？获得的是**变化可预测**：不变量真要变，变的是整条 ISA / ABI / 生态（§1 第二步约束三），所以它不会悄悄变；而产品量可以悄悄变，且没有代价。下面三条都落在这个区别上。

### 4.1 把「每 SM 最大常驻 warp / 线程数」当成架构不变量

**现象**：一个跑在 A100 上的 kernel，按「每 SM 常驻 64 个 warp = 2048 线程」设计 block 形状与寄存器预算，`ncu` 上占用率显示 100%。同一份代码交付到 Ada（CC 8.9）上，占用率**还是显示接近 100%**——因为占用率的分母变了——但吞吐明显不如预期。作者查遍别处：bank 冲突、合并、寄存器用量、指令选择，全都没问题。

**成因**：这不是一个「记错了数字」的坑，而是一个**归纳偏差**的坑，而且它的形状很特别。

开发环境的样本是数据中心 SXM 线：6.0 / 7.0 / 8.0 / 9.0 / 10.0——**连续五代都是 64 / 2048 / 32**。在这条线上做归纳，会得到一个非常干净、看起来像架构规定的结论。但这个归纳的**样本全部来自同一条产品线**，结论其实是产品线的属性。

关键的三个事实：

1. **同一列在别的 CC 上确实会变**：Turing 是 32 / 1024 / 16，Ada 与 CC 11.0 / 12.x 是 48 / 1536。所以它不是不变量。
2. **变的那几个 CC 恰好是消费级 / 工作站**——也就是这个 kernel 最终大概率要跑的地方。开发在数据中心线上，交付在 Ada / CC 12.x 上，归纳样本与使用场景刚好错开。
3. **错误不会立刻暴露，因为占用率会「跟着变」**：占用率的分母本身就是那个会变的线程上限。同一个 kernel 搬到 Ada 上，分母从 2048 变 1536，而 `ncu` 照常给你一个百分比。**你看到的数字自洽，只是它衡量的东西换了。** 一个在 A100 上「占用率 100%」的 kernel，在 Ada 上是 `2048/1536` 的比例关系——如果它真的挂满了 2048 线程，那在 Ada 上根本跑不满，性能下降是对的；如果它只挂了 1024，那在两台机器上的**百分比**会不一样而**绝对并发量**一样。

这条之所以在读完本文前几节之后仍然会犯，是因为**前几节把「不变量」列成了表，而这张表的第一印象是「大多数数字都不变」**。真实情况是：规格表上最容易凭记忆引用的那几个数（每 SM 多少个 warp、多少个线程、多少个 block）恰恰**不在**不变量的名单里。

**规避**：三条一起做。

1. **把这两栏的归属记成一句话**：`warp 大小 / 每 block 线程上限 / 每线程寄存器上限 / bank 数 / 寄存器文件容量` 是架构量，**可以凭记忆**；`每 SM 常驻 warp / 线程 / block 数` 是产品量，**必须查目标 CC 的那一行**。
2. **占用率的分子分母都用绝对值算，不用百分比下结论**。写「这个 kernel 在目标 CC 上常驻 `N` 个 warp、占该 CC 上限的 `N/W_max`」，而不是写「占用率 100%」——把 `W_max` 显式写出来，错误就无处藏身。
3. **交付前在目标 CC 上跑一次**。本文能担保的只是「过去十年没变」，不变量与产品量都可能再变（§1 第一步那个 CC 3.7 = 512 KB 的孤例就是提醒）。查表的成本远低于查错。

### 4.2 由不变量推出「1024 线程/block 是最优的」

**现象**：因为「每 block 最大线程数 = 1024」是不变量，就把它当成最优值用：所有 kernel 的 block 都开 1024 线程。在数据中心线上跑得很好；换到 Ada 或者一块 1536 线程/SM 的卡上，占用率只能到 **66.7%**，怎么调都上不去。

**成因**：**「最大值」不是「最优值」，而这两者恰好只在一种线程上限下重合。**

```text
数据中心线（线程上限 2048）：
    block = 1024 线程  ⇒  1536 线程上限下需 2 个 block = 2048 = 100.0%
    （线程上限 1536）：
    block = 1024 线程  ⇒  1536 ÷ 1024 = 1.5  ⇒  只能放 1 个 = 1024 线程 = 66.7%
    block =  512 线程  ⇒  1536 ÷  512 = 3    ⇒        3 个 = 1536 线程 = 100.0%
```

问题在于 **1024 是否能整除目标 CC 的线程上限**。数据中心线是 2048，1024 整除它，所以「开满」与「占满」重合；Ada 是 1536，1024 **不整除**它，于是必然剩下 512 个线程装不下——这是 §1 第三步那个整除关系的另一个体现，只不过这次用的是线程上限而不是寄存器文件。

注意这里的推理链条：出发点是一个**真不变量**（warp 大小 32 ⇒ block 由整 warp 组成），结论却依赖一个**产品量**（线程上限）。**从真前提出发也能推出错的结论，只要中间夹了一个会变的量。**

**规避**：block 形状由「目标 CC 的线程上限的因数」决定，而不是由「最大值」决定。步骤是：先查目标 CC 的线程上限 `T_max`（本文第五步那张表）；再选一个能整除 `T_max` 的 block 大小（数据中心线的 2048 → 1024 / 512 / 256；Ada 的 1536 → 512 / 256 / 128）；最后用 `__launch_bounds__` 把占用率目标固定下来。**如果同一个二进制要跨 CC 跑，就不要把 block 形状硬编码成某个 CC 的最优值**——要么按最保守的那个 CC 选，要么针对不同 CC 编译不同的配置。

### 4.3 用「256 KB 总额」推每线程的寄存器预算

**现象**：反解出「256 个线程/block 满额常驻时，每线程可用 `65536 ÷ 256 = 256` 个寄存器」，于是把 tile 按每线程 256 个寄存器来设计。编译后 `-Xptxas -v` 报出 spill，性能掉一大截。

**成因**：**65536 是每 SM 的上限，255 是每线程的上限，前者先被算到、后者先被撞上。**

```text
每 SM 容量反解： 65536 ÷ 256 线程 = 256 个寄存器/线程
每线程硬上限：                        255 个寄存器/线程
                                      ↑ 差 1，而 1 个寄存器都拿不到
```

255 是**指令编码层面**的上限（255 = 2⁸ − 1，8 位寄存器号字段留一格），不是「资源不够」的结果。任何超出的部分由编译器 spill 到 local memory，而 local memory 物理上在片外——每次 spill 都是一次真实的全局访存（正文在 [memory-system/01-hierarchy-overview](../memory-system/01-hierarchy-overview.md) §2 与 [execution-model/01-sm-internals](../execution-model/01-sm-internals.md) §4.3）。

顺带一个更隐蔽的后果：256 个线程 × 255 个寄存器 = **65280**，也就是 **65536 里有 256 个寄存器（0.39%）永远用不上**。这不是浪费，是两条不同层级约束之间的缝隙：一个按 `每 SM 容量 ÷ 线程数` 做预算的人会算出 256，而硬件只能给 255。

**规避**：每线程寄存器预算一律按 **255** 封顶，而且实际设计时留出余量——分配粒度是 8（255 会被上取整到 256，实际占用与 256 相同），编译器还要为地址计算、循环变量与临时值留位置。经验做法是按 224 或 240 设计目标值，把它当成**上限**而不是目标，并用 `__launch_bounds__` 保护。更要紧的是把两条约束的层级记住：**「每 SM 多少」与「每线程多少」是两个独立的上限，做预算时要分别检查，不能用一个反解出另一个。**

## 6. 小结与延伸

本文只有一条主线：**分清楚哪些数字是架构不变量、哪些只是产品线的巧合稳定。** 围绕这条主线，有四个可独立复用的中间结论：

1. **不变量是这五个**：warp 大小 32、每 block 1024 线程、每线程 255 个寄存器、共享内存 32 个 bank、每 SM 256 KB 寄存器文件（**例外：CC 3.7 = 512 KB**）。它们跨 CC 3.5 → 12.x 没动过，而同期每 SM 的 FP16 峰值涨了 18.0×。
2. **warp = 32 与 bank = 32 是同一个约束的两种写法**：`bank 数 × 4 B = warp 大小 × 4 B = 128 B`，一次 stride-1 访问正好铺满全部 bank。所以这两个数字必须一起变——而改 warp 大小还要同时改数据通路宽度、读端口数、发射槽语义与全部二进制。
3. **判别方法只有一个：看哪个动了。** 三种线程上限（1024 / 1536 / 2048）下，寄存器文件始终是 65536；而且 2048 与 1024 能整除它、1536 不能（余 6.25%，每 16 个寄存器白扔 1 个）。**能动的是产品量，不动的是架构量。**
4. **「每 SM 最大常驻 warp / 线程 / block 数」不是不变量。** 数据中心 SXM 线连续五代都是 64 / 2048 / 32，但 Turing 是 32 / 1024 / 16、Ada 与 CC 11.0 / 12.x 是 48 / 1536。**「本产品线稳定」不是「架构规定」。**

三篇合起来是一条完整的链。[01-capability-breakpoints](01-capability-breakpoints.md) 讲**能不能表达**（断点落在 PTX 的 target 上），[02-scaling-trends](02-scaling-trends.md) 讲**能不能跑到峰值**（拐点只在低精度轴上移动 8.42 倍），本文讲**哪些假设能活多久**（五个不变量 vs 一组产品线决策）。三者共用同一个事实源 `code/specs.py`——那里的每一条规格都带一行 `# 来源：`，没有来源的数一律不写。

回到 §0 那份 2012 年的 kernel：它今天仍然能跑，是因为它只依赖了本文 §1 第一步那张表里的量。**这就是「知道哪些不变」的全部价值。**
