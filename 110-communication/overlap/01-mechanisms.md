# 重叠的三种机制：双缓冲、通信分块、异步发起

> **一段通信怎么才能「藏」在一次计算后面？**
> 本文讲**通信-计算重叠**的三种机制 —— **双缓冲**、**通信分块**、**异步发起** ——
> 以及它们**各自要求什么条件**。
> ★★★ **本层是【时间层】**：讲的是**两条时间轴排起来要多久**，不是算法的代数（那在 `collectives`），
> 也不是任何真实库的行为（那在 `nccl`），更不是拓扑（那在 `network-topology`）。

> **全库没有**「重叠的收益」的一手公式；★★ **不得写成「研究表明」**。
> 本主题的机制描述来自 **`[B]` 级产品文档**（PyTorch DDP / vLLM-Gaudi），**随版本变**。

## 1. 原理

### 1.1 三个机制其实是一个机制的三种叫法

★★★ **本文最要紧的一句话**：**双缓冲 / 通信分块 / 异步发起** 不是三套独立的技术，
而是**同一个时间轴模型的三个侧面**。

| 机制 | 它做的一件事 | 在本模型里的参数 |
|---|---|---|
| **异步发起**（async launch） | 通信**不等**全部计算就绪就发 —— **一块算完就发这一块** | 「通信引擎」**不等**「计算引擎」跑到尾 |
| **通信分块**（chunking） | 把**一段**通信切成 `K` 块（★ **不是** `bucket`；见 §4.4） | 块的个数 `K`（★ 默认 `K = 1` = **不做**） |
| **双缓冲**（double buffering） | 用**两块**缓冲乒乓：**一块在算、一块在传** | `K = 2` 的**特例** |

★★ **所以本文只需要一个模型** —— `K` 自由的那个（双缓冲是它的 `K = 2` 特例）。

★★★ **`[B]` 级的机制逐字**（vLLM-Gaudi，★ 一个 `RowParallelLinear` 层）：

> `This pipelining allows the all-reduce of chunk i to run concurrently with the matmul of chunk i+1, reducing idle time on both the compute engine and the network interface.`

★★ 注意它说的正是本文的模型：**第 `i` 块的通信**与**第 `i+1` 块的计算**并行 ——
★★★ **而它【没有】给出收益的公式**（★ 那是本库的 `[E]` 级推导，见 §1.3）。

### 1.2 两条时间轴：模型

**题设**（★ 全部是**无量纲的时间单位**，**不宣称对应任何真实硬件**）：

- 一次「计算」总耗时 `C`；一次「通信」总耗时 `T`；
- 把**两者各自**切成 `K` 块（★ **同一把刀** —— 第 `i` 块的通信**需要**第 `i` 块的计算结果）；
- **两条引擎**：**计算引擎**与**通信引擎**，各自**按块序串行**（一台机器一次只能算一块、传一块）；
- ★★★ **一条依赖**：**第 `i` 块的通信，必须在第 `i` 块的计算【做完】之后才能开始**。

```
计算引擎:  [块1][块2][块3] … [块K]                      → 到 C 结束
通信引擎:        [块1][块2][块3] … [块K]                → 到 C/K + T 结束
                 ↑
        ★★★ 通信引擎【最早】只能从 C/K 开始 ——
            因为第一块的计算没做完，【没有任何东西可传】
```

★★★ **这条依赖就是全部内容**：**「首项不可重叠」** ——
第一块的计算**无法**与任何通信重叠（**还没有数据**），
最后一块的通信**也无法**与任何计算重叠（**没有下一块了**）。

### 1.3 时间的闭式（★ `[E]` 级：本库推导）

★★★ **本条必须如实标级别**：**全库没有**这条公式的一手来源（计划 `§C.4`）。

**被测试的式子**（记作 `cf_pipeline`，本文档体系里它**只有这一处正文**）：

```
T(K) = (C + T)/K + (K − 1) · max(C/K, T/K)
```

★★ **逐项读法**：
- **`(C + T)/K`** —— **第一块**（它的计算与通信**无法**与任何东西重叠）；
- **`(K − 1) · max(C/K, T/K)`** —— 其余 `K − 1` 块**稳态**（每块被**较长的那条时间轴**决定）。

★★★ **它的等价写法**（★ **同一个式子的另一种展开**，可代数验证；★ **本文不拿它当判据**）：

```
T(K) = max(C, T) + min(C, T)/K
```

**读法**：**下界 `max(C,T)`，再加上「较短那条时间轴的 `1/K`」**。
★★ ★★★ **`K = 1` 时它就是无重叠值 `C + T`；`K → ∞` 时它压到物理下界 `max(C,T)`** ——
★★ 这两条**是本文 `A.2` 要断言的**「免费守卫」（见 [02](02-how-much-can-hide.md) 的 `P35`）。

★★ **非正式地**（★ 这句是**本库的读法**，不是文献的声称）：**当通信比计算长（`T > C`）时**，
`T − C` 那一段**永远暴露在外**（★ 本程序 `C.1` 会判这件事）。

### 1.4 ★★ 它们各自要求什么条件

★★★ **这是本节最接近「工程知识」的部分** —— 载体是 vLLM-Gaudi 的实现文档（`[B]`），
它把「分块流水**在什么条件下才启用**」逐条列了出来（**四条**）：

| # | 官方逐字 | 翻成本主题的话 |
|---|---|---|
| 1 | `num_chunks > 1` | **得真的分了块** —— ★ 默认是 `K = 1`（**不开**） |
| 2 | `reduce_results` | **那一层得真的需要一次集合通信**（否则**没有可重叠的东西**） |
| 3 | `tp_size > 1` | **得有多条时间轴**（`> 1` 才有「重叠」可言） |
| 4 | `total_tokens >= chunk_threshold` | **得足够大**（★ 太小的消息**分块只会加开销**；默认阈值 `8192`） |

★ 官方还写明：**任一条件不满足 ⇒ 退回单发**（`When any condition is not met, the layer falls back
to the standard single-shot computation.`）—— ★★ 这正是本文模型里 **`K = 1` = 无重叠** 的实现对应物。

★★★ **一条不能省的限定语**：**这四条是 vLLM-Gaudi 一个层的【实现约定】，不是普适规律** ——
其中的数值（尤其第 ④ 条的阈值）**随实现与硬件变**（本库 `P19` 的头号形态）。

★★ **PyTorch DDP 侧的同一件事**（`[B]`，★ 三句里两句是「它怎么分」、一句是「它怎么发」）：

> `To improve communication efficiency, the Reducer organizes parameter gradients into buckets, and reduces one bucket at a time. Bucket size can be configured by setting the bucket_cap_mb argument in DDP constructor.`
> `Model parameters are allocated into buckets in (roughly) the reverse order of Model.parameters() from the given model. The reason for using the reverse order is because DDP expects gradients to become ready during the backward pass in approximately that order.`
> `When gradients in one bucket are all ready, the Reducer kicks off an asynchronous allreduce on that bucket to calculate mean of gradients across all processes. When all buckets are ready, the Reducer will block waiting for all allreduce operations to finish.`

★★★ **三句的读法**（★ **缺一不可**）：
- 第 ① 句：**通信分块**（原文用 `buckets`）+ **块大小可配置**；
- 第 ② 句：**分块的顺序有理由** —— 按参数**逆序**分块，**因为梯度在反向传播里大致按那个顺序就绪**
  ⇒ 「一块就绪就发一块」能**尽早**发起（★ 原句的限定词是 **`(roughly)`** 与 **`approximately`**）；
- 第 ③ 句：★ **`kicks off an asynchronous allreduce`**（**发起**，不等待）**＋**
  **`will block waiting for all allreduce operations to finish`**（**最后才等**）。

★★★ **第三句的前后半句【缺一不可】**：只引前半句会把「异步发起」读成「**永不等待**」——
而官方明确说**最后要 block 等全部完成**（见 §4.2）。

★★★ **限定语**：**DDP 的「桶」是【PyTorch 的实现约定】，不是普适规律** ——
「分成 `K` 块」这件事**任何实现都可以不做**（`K = 1` 就是一次规约全部）。

## 4. 踩坑与失败模式

### 4.1 ★★★ 漏掉「首项」的错式：`C + T/K`（`P35` 的现场）

- **现象**：算出来的「时间」**比物理下界还小**，而程序**不报错**（那些式子都是合法表达式）；
- **成因**：把「**所有** `K` 块都能重叠」当成前提 ⇒ 漏了
  「**第一块的计算与通信无法与任何东西重叠**」这一项；
- **本机实测**（`code/` 的 `C.1`）：`(C,T,K) = (3, 10, 4)` 时错式给 **`5.5`**，
  而**物理下界 `max(3,10) = 10`** ⇒ ★★★ **它给出一个比下界还小的「时间」**（物理上不可能）；
- ★★★ **它为什么最难防**：★★ **错式在 `T ≤ C` 时【恰好是对的】**
  （那时真值也是 `C + T/K`）—— 它的错**只在通信主导（`T > C`）时显现**；
- **规避**：★★★ **任何流水化模型都要过三条【免费守卫】**（计划 `§D.3`）：
  ① `K = 1` ⇒ 等于无重叠值；② `K → ∞` ⇒ 等于下界；③ 中间值**不得小于下界**。
  ★ 详细正文在 [02](02-how-much-can-hide.md)（★ 这是**一条判据一处正文**）。

### 4.2 ★★ 把「异步发起」读成「永不等待」

- **现象**：以为「一块就绪就发」意味着**不需要在最后同步**；
- **成因**：★★★ DDP 的异步那句有**两个半句**，只引前半句就会读反；
- **规避**：★★ 引它**必须两句一起**（`kicks off an asynchronous allreduce …`
  **`When all buckets are ready, the Reducer will block waiting for all allreduce operations to finish.`**）。

### 4.3 ★★ 引文层：限定词被截断

- **现象**：引文看起来对，**结论**悄悄变强；
- **成因**：★★★ DDP 的原句自带限定 —— **`(roughly)`**、**`approximately`**；
  ★ 引用时**容易被当修辞删掉**；
- **规避**：★★ 本文的 `D.5` 把这些限定词**逐字钉住**（★ 这是 v1.7 那条硬伤的直接对策）。

### 4.4 ★★ 术语层：把「通信分块」写成 `bucket`

- **现象**：把本库的「通信分块（chunking）」写成 `bucket`；
- **成因**：★★★ 库内 `bucket` 已有**两个**含义（DDP 的**梯度桶**、JAX 的**形状桶**，见域 README 的
  「同名不同指」表）；★ 而 DDP 文档里那个词正是 `buckets`；
- **规避**：★★ **本库一律写「通信分块」**；★ **引文里出现 `buckets` 时**，
  是**照抄 DDP 的原文**，要**点明**那是 PyTorch 的实现约定。
  ★★ 同理 **`stage` / 阶段不得裸写**（库内已有四个含义）—— 本文一律写「**通信阶段**」或直言「块」。

### 4.5 ★★ 三个主题的 A 类【共用同一条调度规则】

- ★★ **本文的 A 类（`A.1` / `A.2`）与 [02](02-how-much-can-hide.md) / [03](03-async-io.md)
  的 A 类共用同一条调度规则**（本程序里是 `do_comm = (ki<K) and (comp_progress[ki] >= C)`）⇒
  **它们共享同一个潜在偏差**（★ 若调度规则本身错，三章会一起错）；
- ★ 缓解是**本文 `D.4` 的守卫实验**（改坏依赖后结果必须变）。

| 见到 `C + T/K` | ★★★ **漏掉首项的错式** —— 在 `T > C` 时**低于物理下界**（`C.1` / `P35`） |
| 见到「分块能无限提速」 | ★★★ **不能** —— `K → ∞` 只到 **`max(C,T)`**（`A.2` 守卫②） |
| 见到 `K = 1` | ★★ **无重叠值 `C + T`**（`A.2` 守卫①，**逐位**）；★ 也是「不做重叠」的默认（`K = 1`） |
| 见到「异步发起」 | ★★ 官方逐字是 **`kicks off an asynchronous allreduce`** **＋** **`will block waiting`**（两句，`D.5`） |
| 见到「DDP 分成桶」 | ★★★ 那是 **PyTorch 的实现约定**（`bucket_cap_mb`），**不是普适规律**（`D.5`） |
| 见到「分块流水总是更快」 | ★★★ **不成立** —— 官方条件表有**四条**（分块 / 需要通信 / 有并行度 / 足够大），任一不满足就**退回单发**（`B.2`） |
| 见到裸写的 `stage` / `bucket` | ★ ★★★ **本库不写** —— 写「**通信阶段**」/「**通信分块**」（域 README 的「同名不同指」表） |
| 见到「本机 socket 的吞吐」 | ★★★ **不得用于本域的任何性能讨论**（计划 `§0.3` 的 `P34`） |

## 6. 小结与延伸

**一句话**：**把一段通信切成 `K` 块、一块算完就发一块（异步发起），
于是后一块的通信与前一块的计算并行（双缓冲是 `K = 2` 的特例）；
总时间 `(C+T)/K + (K−1)·max(C/K,T/K)` —— 而它永远不低于 `max(C,T)`。**

**三条可独立复用的结论**：

1. ★★★ **首项不可重叠** —— 第一块的计算**没有数据可传**、最后一块的通信**没有下一块可算**；
   ★ 漏掉它就得到**比物理下界还小的时间**（`P35`）；
2. ★★★ **三个机制是同一个模型**：双缓冲 = `K = 2`、通信分块 = `K` 自由、异步发起 = 两条引擎不等；
3. ★★ **机制有前提**：官方四条条件（分块 / 需要通信 / 有并行度 / 足够大），
   且**默认是关的**（`K = 1`）—— ★ 任何一条不满足就**退回单发**。

**延伸**：

- ★★★ **「能藏多少」的判据**（可藏的上限是 `min(C,T)`）→ [02-how-much-can-hide](02-how-much-can-hide.md)；
- ★★ **异步落盘**（同一件事的另一面：与计算重叠的那一半）→ [03-async-io](03-async-io.md)；
- **本层不写、只回链的正文**：
  · `V(N)` 的推导与扩展效率模型 → `10-foundations/performance-models/02-amdahl-and-scaling.md`；
  · 异步落盘的**存储侧**机制 → `90-training/checkpointing/01,02,03`。
