# 稀疏粒度：硬件只定义三种 N:M，而非结构化不在表里

> 稀疏的「形状」不是软件想怎么定就怎么定的：**PTX 只定义了三种 N:M 粒度**——`1:2`（tf32）、`2:4`（f16/bf16/int8/e4m3/e5m2）、`4:8 paired`（u4/s4 与 e2m1/mxf4，零与非零**以 2 元素子块成簇**）。**非结构化（任意位置）不在那张表里**，这就是它在 GPU 上拿不到加速的原因；同一件事在 CPU 上不成立。而本机在真 torch 上量到一件更要紧的事：**同一个「稀疏」在不同 dtype 上落到不同粒度——`float32` 走的是 `1:2`，不是 `2:4`**，六种 2:4 模式里有两种会**静默丢数据**。

## 0. 背景与动机

[05-structured-sparsity](../../20-gpu-architecture/tensor-core/05-structured-sparsity.md) 算了「2× 承诺为什么拿不满」的**字节账与 roofline 账**。那篇的起点是一个更前置的问题：**什么样的稀疏形状硬件才认？**

这个问题不回答，后面的账都算不了：

- 一个 7B 模型的权重做 50% 剪枝，压缩后显存从 14 GB 降到多少？**取决于选哪种粒度**——`2:4` 在 16 位元素上留下的是 `36/64 = 56.25%`（不是 50%），而 `4:8 paired` 的元数据口径与它不同。
- 一个「任意位置剪掉一半」的非结构化掩码，能不能直接喂给张量核心？**不能**——而且失败方式不是报错，是**慢**。
- 同一份稀疏权重，fp16 与 int8 的 metadata 开销一样吗？**不一样**，差一倍。

三件事的答案都落在同一张规格表上，而那张表**只有三行**。本文要做的就是：

1. 把那张表**逐行**写出来（含每一档对应的 dtype），并说明**它为什么不包含非结构化**；
2. 把 `2:4` 的 metadata 开销算清楚——**两个分母不要混**；
3. 把 `4:8 paired` 的两种 bit/元素口径分开——**它们差 5 倍**；
4. ★ 用真 torch 的**内部**转换函数把 metadata 的位宽**量出来**，并发现一件规格表里看不出来的事：**`float32` 那一行走的是 `1:2`**。

落到本文档所属主题的交换三角上，本篇站在**「用 metadata 的比特换稀疏的粒度」**这条边上：**每省一分载荷，都要拿 metadata 的开销去换，而元素越窄、这笔开销越贵。**

## 1. 原理

### 第一步：硬件粒度表**只有三行**，且每行都是 N:M 形式

规格（PTX ISA 的稀疏矩阵存储一节，引法与核对范围见文末「参考」）：

| 粒度 | 对应 dtype | 含义 |
|---|---|---|
| **`1:2`** | **tf32** | 每 2 个相邻元素 1 个非零；只有非零元素进存储 |
| **`2:4`** | f16 / bf16 / int8 / e4m3 / e5m2 / f8f6f4 / mxf8f6f4 | 每 4 个相邻元素 2 个非零 |
| **`4:8 paired`** | u4 / s4 / **e2m1** / mxf4 | 每 8 个元素 4 个非零；**零与非零以 2 元素子块成簇** |

三条要点：

1. **粒度 = 子块内非零数 / 子块大小**，子块大小由形状决定。**表里没有第二个维度**——稀疏的「形状」是硬件定的，不是算法定的。
2. ★ **非结构化（任意位置）不在表里。** 这不是「没写」而是「没有」：硬件只按 metadata 取数，而 metadata 的编码方式本身要求固定的子块结构。
3. **同一个「50% 稀疏」在不同 dtype 上落到不同粒度**——cuSPARSELt 的 `CUSPARSELT_SPARSITY_50_PERCENT` 的映射是：**`float → 1:2`、`e2m1 → 4:8 paired`、half / bfloat16 / int8 / e4m3 / e5m2 → `2:4`**。这一条后面会直接解释一处实测到的意外。

### 第二步：`2:4` 的 metadata 是 **4 bit/组**，而它有**两个分母**

一组 `2:4` 是 4 个元素，其中 2 个非零。每个非零位置需要一个 **2-bit 索引**（4 个位置里选一个），所以：

```
metadata = 2 个 2-bit 索引 = 4 bit / 组
```

于是 16 位元素的一组是：

```
原始稠密   4 × 16 bit  = 64 bit
压缩载荷   2 × 16 bit  = 32 bit
metadata   2 个 2-bit  =  4 bit
合计                    36 bit   ⇒ 36/64 = 56.25%（省 43.75%）
```

⚠ **两个分母不要混**（这一条与 [05](../../20-gpu-architecture/tensor-core/05-structured-sparsity.md) 是同一个知识点，正文在那里，此处只回链）：

| 分母 | 值 | 用途 |
|---|---|---|
| **原始数据** | `4/64 = 6.25% = 1/16` | 说「metadata 占了多少额外空间」 |
| **压缩后载荷** | `4/32 = 12.5% = 1/8` | 说「相对压缩结果又多了多少」 |

**比值差 2 倍**——而两个数都「对」。混用的后果是容量规划差 2 倍。

**同法算 8 位元素**：`(2×8 + 4)/(4×8) = 20/32 = 62.5%`。⇒ **元素越窄，同一个 4-bit metadata 越贵**。这条在下面第四步会变成一张表。

### 第三步：`4:8 paired` 的两种口径差 **5 倍**（一个「同名不同指」的实例）

`4:8 paired` 的 metadata 是**每 8 元素组 4 bit**。于是一个很自然的说法是：

```
metadata 那一份 = 4 bit / 8 元素 = 0.5 bit/元素
```

**这句话是对的，但它不是「`4:8 paired` 的宽度」。** 整块的等效宽度要把载荷算进来：

```
4 个非零 × 4 bit（int4 载荷） = 16 bit
metadata（每 8 元素组）        =  4 bit
合计                           = 20 bit ÷ 8 元素 = 2.5 bit/元素
```

| 口径 | 值 | 它回答的问题 |
|---|---|---|
| metadata 那一份 | **0.5 bit/元素** | 「索引占了多大地方」 |
| **整块等效宽度** | **2.5 bit/元素** | 「一个元素平均背多少比特」 |

**两者差 5 倍，不得混称。** 把 0.5 说成「`4:8 paired` 是 0.5 bit/元素」，会与「int4 + `4:8` 相对 fp16 稠密是 6.4×」（= 16/2.5）**直接打架**——这就是 P9（同名不同指）：两个数都真、来源都可查，错在**它们不是同一个量**。

### 第四步：稀疏 × 量化的压缩率**不是简单相乘**

把粒度与位宽叠起来算，**含 metadata** 的 bit/元素：

| 组合 | bit/元素 | 相对 fp16 | 朴素相乘 | 朴素高估 |
|---|---|---|---|---|
| fp16 稠密 | 16 | 1.00× | — | — |
| int8 稠密 | 8 | 2.00× | — | — |
| int4 稠密 | 4 | 4.00× | — | — |
| fp16 + 2:4 | **9** | **1.78×** | 2× | 1.12× |
| int8 + 2:4 | **5** | **3.20×** | 4× | **1.25×** |
| int4 + 2:4 | **3** | **5.33×** | 8× | **1.50×** |
| int4 + 4:8 | **2.5** | **6.40×** | 8× | 1.25× |

**高估的那一列全部来自 metadata**：`fp16 + 2:4` 按朴素相乘是 2×，实际 1.78×（差 12%）；`int4 + 2:4` 差 **50%**。

★ 这里有一个**方向容易说反**的地方，必须分开写：

- **相对 fp16 稠密**：`int4 + 2:4` 的 5.33× 是**最大**的（压缩最多）；
- **相对同等精度的稠密**：`int4` 上稀疏这一步只能拿到 `4/3 = 1.33×`，而 `fp16` 上能拿到 `16/9 = 1.78×`（**稀疏的边际收益最小**）。

**两句话都对，方向相反，因为它们的分母不同。** 换句话说：**元素越窄，「量化」省得越多、「稀疏」省得越少**。

### 第五步：非结构化——**不在硬件表里**，但「拿不到加速」是分硬件的

| | GPU | CPU |
|---|---|---|
| 非结构化能否加速 | **不能**（cuSparse 的 EW 路径要到 **>95% 稀疏**才开始快于稠密） | **能**（DeepSparse 跑 OPT-2.7B：40/50/60% 稀疏 = **1.57× / 1.82× / 2.16×**） |
| 来源 | 引用值（SparseGPT 论文对 cuSparse 路径的说明） | 引用值（SparseGPT 附录 E 表 7） |
| 硬件/基线 | GPU | Intel Core i9-7980XE / 18 核 / 单批 400 token；基线 = 稠密 DeepSparse |

⚠ **这两行不在同一个硬件上，也不是同一个引擎**——它们**不得并列成一个「GPU 不行、CPU 行」的合成结论**，只能各自绑定自己的硬件与基线引用（CONTRIBUTING §2 的「跨 harness 不得并列」）。

### 第六步：★ 实测——metadata 位宽，以及 `float32` 走得**不是 2:4**

规格给了「4 bit/组」，但**规格是规范、torch 是实现**，两者要分开看（P8）。本机用 torch 的**内部**转换函数把布局量了出来（公开 API 在 CPU 上直接报错，见 §2）：

| dtype | `meta.dtype` | meta 形状（64×256 输入） | meta bit /「4 元素」 | meta/原数据 | 合计/原数据 |
|---|---|---|---|---|---|
| float16 | int16 | 64×16 | **4.0000** | 0.0625 | **0.5625** |
| bfloat16 | int16 | 64×16 | **4.0000** | 0.0625 | **0.5625** |
| int8 | int32 | 64×8 | **4.0000** | 0.1250 | **0.6250** |
| **float32** | int16 | 64×32 | **8.0000** | 0.0625 | 0.5625 |

前三行与规格推导**逐位吻合**（`4/64`、`(2×16+4)/64`）。**第四行不对**：

> ★ **torch 的 `float32` 路径用的是 `1:2`，不是 `2:4`。**
> 判据是源码里的分支：`sparse_semi_structured_from_dense_cutlass` 里
> `if dense.dtype != torch.float: ksparse = 4 else: ksparse = 2`
> ——**float 走 `ksparse = 2`**，即每 2 个元素一个非零。
> 所以那一行的「8 bit / 4 元素」其实是**两个** 2 元素编码单元，不能读成「float32 的 metadata 是 8 bit/组」。

而且这**不是矛盾**：`1:2` 正是 tf32 那一档的合法粒度，与 cuSPARSELt 的 `float → 1:2` 映射**一致**。PTX 的粒度表与 torch 的实现**在这里是自洽的**——只有把「4 bit/组」当成对所有 dtype 都成立的结论时，才会读错。

**怎么用实验区分「2:4」与「1:2」两个假设？** 不能靠随机矩阵（见 §4.3），要**设计判别样本**：在 32×64 的 float32 矩阵上造六种固定的 2:4 模式，每组 4 个元素里第 `p0`、`p1` 位非零（值分别 1.0 与 2.0），编码后解码，逐元素比对：

| 模式 `(p0,p1)` | 同对？ | 往返相等 | maxdiff | 假设 A（2:4）预言 | 假设 B（1:2）预言 |
|---|---|---|---|---|---|
| (0,1) | **同对** | **False** | **2.0** | True | **False** |
| (0,2) | 跨对 | True | 0.0 | True | True |
| (0,3) | 跨对 | True | 0.0 | True | True |
| (1,2) | 跨对 | True | 0.0 | True | True |
| (1,3) | 跨对 | True | 0.0 | True | True |
| (2,3) | **同对** | **False** | **2.0** | True | **False** |

**实测结果落在假设 B 上**：只有「同一对内两个都非零」的两种模式失败，失败时**丢掉恰好一个元素**（整块丢 `2048/4 = 512` 个，每行 16 个），**且不抛任何异常**。

> ★ 这张表是「**专门挑两种候选解释会给出不同答案的点**」的样本：假设 A 之下六种全过，假设 B 之下只有两种失败。**用一个随机矩阵是区分不出来的**（随机数据下两种假设都「失败」，失败本身不指向任何具体假设）。

## 2. 执行映射

### 2.1 torch 侧的三个具体组件

| 组件 | 是什么 | 本篇关心什么 |
|---|---|---|
| `torch.sparse.to_sparse_semi_structured` | **公开** API | ★ **在 CPU 上直接抛 `RuntimeError("Only CUDA tensors are currently supported")`**——所以本机要用内部函数 |
| `torch.sparse._semi_structured_conversions.sparse_semi_structured_from_dense_cutlass` | **内部**编码函数 | 压缩载荷的形状、metadata 的形状与 dtype、`ksparse` 分支 |
| 同上 `..._to_dense_cutlass` | **内部**解码函数 | 往返是否无损——**这是判别两个假设的唯一手段** |

**一个数值量级**：metadata 的**形状**决定了位宽。64×256 的 fp16 输入给出 `meta.shape = (64, 16)`、`int16` ⇒ 每行 `16 × 16 = 256 bit` 覆盖 `256/4 = 64` 组 ⇒ **4 bit/组**。

### 2.2 源码里的三条约束（不是文档写的，是代码里查出来的）

1. **`meta_dtype` 按元素类型选**：`int8 → int32`；`half/bfloat16/float → int16`。
2. **形状对齐**：int16 metadata 要求 `m % 32 == 0`；int32 metadata 要求 `m % 16 == 0`；列数要求 `k % (4 × quadbits_per_meta_elem) == 0`。
3. ★ **`ksparse` 按 dtype 选**：`float → 2`（即 `1:2`）、其余 → `4`（即 `2:4`）。

### 2.3 编码表只用到 6 个值

一个 4 元素组里「恰好 2 个非零」的模式数是 `C(4,2) = 6`；而 4 bit 的 metadata 有 16 个可用值。**够用，但不唯一**——源码注释里逐条列出了 6 种合法编码（`0b0100` / `0b1000` / `0b1001` / `0b1100` / `0b1101` / `0b1110`），**其余值是未定义行为**。

这也解释了 §1 第六步里失败的那两种模式为什么**不报错**：非法模式走的是编码表里的**退化分支**（源码注释：「不足两个 True 时，某些位置被当作 True；多于两个 True 时，多余的被当作 False」），于是错误静默地变成数据丢失。

## 3. 实现与演进

**第一代：稠密。** 没有稀疏，只有「跳过零」的软件分支——在 GPU 上体现为分支发散，通常更慢。

**第二代：非结构化稀疏 + 通用稀疏库。** `cuSPARSE` 的 SpMM 路径。它的问题是**内存访问不规则**：每行的非零分布不同，无法用固定的 MMA 形状摊薄。于是「稀疏度不高时反而不如稠密」——本机引用的门槛是 **>95%**。

**第三代：`2:4` 结构化。** 硬件把「每 4 个元素 2 个非零」写进指令：操作数 A 的寄存器数**不变**（4 个），但每个寄存器覆盖**一个 4 元素子块**，位置由 metadata 现场给出。这就是 A100 起的 `mma.sp`。代价是**编制约束**：算法必须剪成这个形状，且 metadata 要额外存。

**第四代：按类型分档。** 4 位元素在 `mma.sp` 上只定义了 `4:8 paired`（零与非零以 **2 元素子块**成簇），2:4 的 4 位（mxf4）只在 `tcgen05` 且 `SparsityVersion = v1`（sm_107a）上定义。于是同一套算法要**按 dtype 选粒度**——这一代里 `1:2`（tf32）与 `4:8`（e2m1）不是历史遗迹，而是**并在的选项**。

> ⚠ **演进不等于「粒度越来越细」。** 能确认的只是**档位在增加**：`1:2` 服务于 tf32，`2:4` 服务于 16/8 位，`4:8` 服务于 4 位。**没有一条「哪一种更省」的普适结论**——省多少取决于元素位宽（§1 第四步）。

## 4. 踩坑与失败模式

### 4.1 把「4 bit/组」跨 dtype 混用

**现象**：用 `4 bit/组` 去算 `float32` 的 metadata 开销，算出「8 bit / 4 元素 = 2 bit/元素」，然后发现与实测的存储量对不上。

**成因**：`float32` 的编码单元是 **2 元素对**，不是 4 元素组。用「4 元素」当分母会把两个编码单元合成一个，凭空多算一倍。

**规避**：先问「**这一档的编码单元是几个元素**」，再套 metadata 位宽。判据是源码里的 `ksparse` 分支；实测的判别手段见 §1 第六步的六模式表。**见 `code/01_sparsity.py` 的 C.1。**

### 4.2 把 `4:8 paired` 的「0.5 bit/元素」当成整块宽度

**现象**：文档写「`4:8 paired` 是 0.5 bit/元素」，读者拿去算压缩率，得到 `16/0.5 = 32×`。

**成因**：0.5 是**只算 metadata** 的口径，不是整块。整块要加 `4 × 4 bit` 的载荷：`(16+4)/8 = 2.5 bit/元素`。

**规避**：两个口径**各自写出来并标明它回答什么问题**（§1 第三步的表）。**判据没写出来的数字，不得与另一个数字并列。**

### 4.3 用「随机矩阵往返正常」当检查——或者用「随机矩阵往返失败」当结论

**现象**：拿一个随机稠密矩阵做一次编码-解码，看是不是还原了，并以此判断「这个 dtype 的粒度是 2:4 还是 1:2」。

**成因**：随机数据**必然违反** 2:4——本机实测在 32×64 的 float32 随机矩阵上失配 1044 个元素（其中「同对两非零」的对有 1024 个）。**失败是意料之中的，而失败本身不指向任何具体假设。**

**规避**：**判据必须用受控样本**（§1 第六步的六种模式）。这条与 [02](02-pruning-criteria.md) 里「别用随机 X 去验归约关系」是同一种方法论错误。

### 4.4 把「非结构化在 GPU 上拿不到加速」当成普适结论

**现象**：写「非结构化稀疏没有加速价值」，并引 GPU 侧的 >95% 门槛当证据。

**成因**：那句话有**硬件限定词**。CPU 侧的同一件事结论相反（DeepSparse 在 50% 上就有 1.82×）。

**规避**：**把硬件与引擎写进句子**：「在 GPU 上（cuSparse 的 EW 路径）…；在 CPU 上（DeepSparse）…」。两条数字**不构成一个区间**。

## 5. 实测数据

**测量条件**：Apple M1 Pro（10 核）/ macOS / **CPU-only，无 GPU 数字**；python 3.12.9；**torch 2.11.0**。五个解释器（2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 / 2.13.0）都跑过本篇全部断言，**逐格一致**；`2.9 / 2.10 / 2.12` 本机无解释器。数值逐条记在 `code/specs.py`。

> ⚠ 本章的数字**全部是本机实测值**。规格侧的表（粒度、cuSPARSELt 映射）与引用值（>95%、DeepSparse 的三个数）在 §1 里，**不属于本章**。

### 5.1 ★ metadata 位宽与压缩率（判据：`numel × element_size × 8` 为分母；64×256 输入；非零数据）

| dtype | `meta.dtype` | meta 形状 | meta bit /「4 元素」 | meta/原数据 | 合计/原数据 |
|---|---|---|---|---|---|
| float16 | int16 | 64×16 | **4.0000** | 0.0625 | **0.5625** |
| bfloat16 | int16 | 64×16 | **4.0000** | 0.0625 | **0.5625** |
| int8 | int32 | 64×8 | **4.0000** | 0.1250 | **0.6250** |
| **float32** | int16 | 64×32 | **8.0000**（= 两个 2 元素单元） | 0.0625 | 0.5625 |

**前三行与规格推导逐位吻合**；第四行的「组」是 2 元素对，**不得与前两列并列读**。

### 5.2 ★ 六种 2:4 模式的往返（判据：float32 / 32×64 / 值 1.0 与 2.0 / `torch.equal`）

| 模式 | (0,1) | (0,2) | (0,3) | (1,2) | (1,3) | (2,3) |
|---|---|---|---|---|---|---|
| 往返相等 | **False** | True | True | True | True | **False** |
| maxdiff | **2.0** | 0.0 | 0.0 | 0.0 | 0.0 | **2.0** |
| 丢失元素数 | **512** | 0 | 0 | 0 | 0 | **512** |

**对照组（判据相同、只换 dtype）**：同样的六种模式在 **float16 与 int8 上全部无损**（6/6）。

**随机矩阵的对照（判据：`randn` 后取 50% 非零位置）**：失配 1044 个元素 / 2048，其中「同一对内两个都非零」的对有 1024 个 ⇒ **随机数据下的失败不能用来判定粒度假设**。

### 5.3 压缩率算术（判据：`(非零数 × 位宽 + metadata) / (组大小 × 位宽)`）

| 组合 | 位宽 | 合计/稠密 | meta/原数据 | meta/载荷 |
|---|---|---|---|---|
| fp16 + 2:4 | 16 | **0.5625**（36/64） | 0.0625（1/16） | 0.1250（1/8） |
| int8 + 2:4 | 8 | **0.6250**（20/32） | 0.1250 | 0.2500 |
| int4 + 2:4 | 4 | **0.7500**（12/16） | 0.2500 | 0.5000 |

**两个分母差 2 倍，且元素越窄两者都越贵。**

## 6. 小结与延伸

- **硬件只定义三种 N:M 粒度**：`1:2`（tf32）、`2:4`（16/8 位）、`4:8 paired`（4 位，**以 2 元素子块成簇**）。**非结构化不在表里**——这是「非结构化在 GPU 上拿不到加速」的根因，但**不是**「非结构化不能加速」（CPU 上能）。
- **`2:4` 的 metadata 是 4 bit/组**，16 位元素下 `36/64 = 56.25%`。**两个分母（1/16 与 1/8）差 2 倍**；**元素越窄 metadata 越贵**（int8 是 12.5%）。
- **`4:8 paired` 的 0.5 bit/元素只是 metadata 那一份**，整块等效是 **2.5 bit/元素**——**差 5 倍，不得混称**。
- ★ **本机在真 torch 上量到 metadata 位宽与规格逐位吻合（4.00 bit/组）**，同时量到一件规格表看不出来的事：**`float32` 那一行走的是 `1:2`**（源码 `ksparse = 2`），六种 2:4 模式有**两种静默丢数据**。
- **方向容易说反的一条**：「`int4 + 2:4` 压缩最多（5.33×）」与「`int4` 上稀疏的边际收益最小（1.33×）」**都对**，因为分母不同。

**延伸**：[02-pruning-criteria](02-pruning-criteria.md) 接着讲**怎么决定哪些元素该被剪掉**——三条判据以及它们之间那条容易被写反的归约关系。[05-structured-sparsity](../../20-gpu-architecture/tensor-core/05-structured-sparsity.md) 是本文的前置：它把 36/64 与 roofline 三段闭式算完，本文只做「形状从哪来」这一半。[03-distillation](03-distillation.md) 走的是另一条主线（蒸馏），与本文没有直接的交换关系。
