# e8m0 与 MX：一个只存指数的格式，和围着它建的微缩放规范

> `e8m0` 是 8 位、**0 位尾数、0 位符号位**的纯指数格式——它只能表示 2 的整数次幂，**没有零、没有负数、没有 Inf**，而且 `0.0` 会被它读成 `2^-127`。它单独没有任何用处，全部价值在于**当一个块（32 个元素）的共享 scale**：这样 scale 的开销就只有 0.25 bit/元素。代价是这个 scale **不是**最近的——MX 论文的算法用 `floor`，于是块内最大值有 17%–30% 的概率越界。

## 0. 背景与动机

一个具体的对照场景。要把一个 `(4096, 4096)` 的权重张量从 fp16 压到 fp4：

- **元素本身**从 16 位降到 4 位——这是主要的收益，4×；
- 但 fp4（E2M1）只有 8 个幅值（`0, 0.5, 1, 1.5, 2, 3, 4, 6`），**一个张量里不同位置的量级差几个数量级**，全局一个 scale 根本盖不住；
- 于是要**分块共享 scale**。块越小越准，但 scale 本身要占存储。

这就是本文的主线：**用共享指数换 scale 的比特**。MX 规范的选择是「块 = 32 个元素、scale = E8M0」：

| | 元素位宽 | scale 开销 | 有效宽度 | 相对 fp16 的压缩率 |
|---|---|---|---|---|
| MXFP4 | 4 | `8 / 32` = **0.25** bit/元素 | 4.25 bit | **3.76×** |
| NVFP4 | 4 | `8 / 16` = **0.50** bit/元素 + per-tensor FP32 | 4.50 bit | **3.56×** |
| MXINT8 | 8 | `8 / 32` = 0.25 bit/元素 | 8.25 bit | **1.94×** |
| 对照：fp16 稠密 | 16 | 0 | 16 bit | 1.00× |

**朴素算法（「4 bit 就是 4×」）会高估压缩率**：MXFP4 的实际收益是 3.76×，不是 4×。而 NVFP4 比 MXFP4 **多花一倍的 scale 开销**——这笔钱买回来的是什么，是本文 §1 第五步要算的账。

第二类问题是**规范与实现的边界在哪**。MX 的文档里有两条规定经常被当成「规范规定」引用，而它们其实不在规范里：块 scale 用 `floor`（这是**论文** Algorithm 1 的做法）、块的存储布局（**规范明写不规定**，而 cuDNN 在 Blackwell 上强制）。**把论文当规范，与把规范当实现，是同一个错误的两个方向。**

## 1. 原理

### 第一步：e8m0 的 256 个码字，一次扫完

e8m0 的位域是 `S0 E8 M0`——**根本没有符号位与尾数位**，8 位全是带 bias 的指数。取 `bias = 127`：

```text
value(code) = 2^(code − 127)          code = 0x00 .. 0xFE
0xFF 是 NaN
```

本机把 256 个码字全扫了一遍（真 `torch.float8_e8m0fnu`，torch 2.8.0 / 2.11.0 / 2.13.0 三个版本逐格相同）：

| 量 | 结果 |
|---|---|
| NaN 码字 | **只有 `0xFF`**，1 个 |
| 等于 0 的码字 | **0 个** |
| 负值码字 | **0 个** |
| 有限值个数 | **255**（`0x00`..`0xFE`） |
| `0x00` | **`2^-127` = 5.87747e-39** |
| `0xFE` | **`2^127` = 1.70141e+38** |
| 随码字单调性 | 严格递增 |
| 是否都是 2 的整数次幂 | **全部都是** |

三件事因此被钉死（都是「无符号、0 尾数」的直接后果）：

1. **没有零。** `0.0` 无法表示——最近的码字是 `0x00`，读出来是 `2^-127`。
2. **没有负号。** 8 位全给了指数，符号位一个都没有。
3. **相邻可表示值至少差一倍**（`eps = 1.0`，本机 `finfo` 确认）。

### 第二步：e8m0 的取整——规范说 `up`，源码写「ties to even」，实测恒向上

规范侧（ONNX `Cast` 的 `round_mode` 属性，**默认值 `up`**）逐字给出三个取值的含义：

| 取值 | 逐字含义 |
|---|---|
| `up`（**默认**） | "round to nearest value **away from zero**" |
| `down` | "round to nearest value towards zero" |
| `nearest` | "round to nearest value and ties **round up**" |

**默认是 `up`，不是 RNE。** 而实现侧，torch 的源码注释写的是另一个东西——`torch/include/torch/headeronly/util/Float8_e8m0fnu.h`（226 行，2.11.0 与 2.13.0 逐行打印过，行号一致）：

```text
第 74–75 行  // next, we use guard, round, sticky bits and the LSB to implement round to
             // nearest, with ties to even
第 83–84 行  // in casting to e8m0, LSB is the implied mantissa bit. It equals to 0 if the
             // original float32 is denormal, and to 1 if the original float32 is normal.
第 85 行     uint8_t lsb = exponent > 0;
```

**`lsb` 取的是「源 float32 的隐含尾数位」，不是「e8m0 结果码字的 LSB」。** 对一切**正规** float32 输入，`lsb` 恒为 1，于是平局分支恒走 round up——**注释自称的 ties-to-even 被实现成了恒向上**。

本机把 10 个中点逐点打印过（`a = -4 .. +5`，中点 = `1.5 · 2^a`），**全部向上**；其中 5 个点上 ties-to-even 本应选**下**：

| `a` | 中点 `1.5·2^a` | 实测 | ties-to-even 本会选 |
|---|---|---|---|
| −3 | 0.1875 | 0.25 | 0.125（**不同**） |
| −1 | 0.75 | 1.0 | 0.5（**不同**） |
| +1 | 3.0 | 4.0 | 2.0（**不同**） |
| +3 | 12.0 | 16.0 | 8.0（**不同**） |
| +5 | 48.0 | 64.0 | 32.0（**不同**） |
| （其余 5 个） | — | 向上 | 恰好也是向上 |

**结果与 ONNX 默认的 `up` 一致，理由却与注释自称的 ties-to-even 不同。** 这不是 bug 意义上的「错」——是「两条路殊途同归」。**结果一致、理由不同，就是 P8 的实体。**

### 第三步：e8m0 的失败边界——两端**不对称**

规范把 e8m0 的越界行为列成两列（`saturate + up` 对 `non-saturate + nearest`），正文写：**"The current CUDA behavior is to round up and saturate."** 同页还逐字写着：

> **Casting negative values to FLOAT8E8M0 gives undefined behavior.**

本机实测（CPU-only，torch 2.8.0 / 2.11.0 / 2.13.0 三个版本一致）得到三件事：

**（1）负值：规范说未定义，实现给了确定行为——取绝对值。**

```text
-1.0  → 1.0        -1.5  → 2.0        -460.0 → 512.0
```

`-460.0 → 512.0` 是决定性的：它不是「对 0 饱和」，而是**先丢符号、再对绝对值做最近取整**。**规范说未定义、实现有确定行为**，所以这一格必须写成「**torch 的实现选择**」，不能写成「e8m0 对负数取绝对值」。

**（2）低频端饱和：**

```text
0.0 → 2^-127       -0.0 → 2^-127        2^-130 → 2^-127        2^-200 → 2^-127
```

**（3）高频端**不**饱和——阈值 `1.5 · 2^127`：**

| 输入 | 结果 |
|---|---|
| `1.0 · 2^127` | `1.70141e+38`（= `2^127`） |
| `1.2 · 2^127` | `2^127` |
| `1.499 · 2^127` | `2^127` |
| **`1.5 · 2^127` = 2.55212e+38** | **NaN** |
| `2.0 · 2^127` | **NaN** |

**判据**：e8m0 的尾数位是 0，所以 `2^127` 处的 ulp **就是 `2^127`**；阈值 = 上限 + ulp/2 = `1.5 · 2^127`。**这与 01 里那四个 fp8 变体是同一条规则。**

两端表现不同，但**不是两条规则**：那份实现里**没有任何显式饱和逻辑**，它只是「按最近取整、平局向上」然后让码字落到该落的地方——低频端落到 `0x00`（**合法值** `2^-127`），高频端落到 `0xFF`（**NaN**）。**两端的不对称来自码字空间的边界，不来自两条不同的规则。**

> **⚠ 这是本文最需要小心的一格。** ONNX 正文那句话描述的是 **CUDA** 的行为；而本机是 **CPU-only**，测到的是 **CPU 路径**。对 `x > E8M0_MAX`，ONNX 的 `saturate + up` 列写 `E8M0_MAX`、`non-saturate + nearest` 列写 `NaN`——**torch 的 CPU 路径落在后者那一列**。
> **不得写「ONNX 错了」，也不得写「torch 一律饱和」。** 正确写法是：**规范说的是 CUDA 的行为，本机测的是 CPU 的行为，两者不同。**

### 第四步：MX——块 32、scale E8M0、块 scale 用 `floor`

OCP MX 的正式名称是 **"OCP Microscaling Formats (MX) Specification"**，**Version 1.0**，2023-09-07。四种格式的**块大小一律 32 个元素共享一个 scale**，scale 格式一律 **E8M0**；元素格式分别是 MXFP8 = FP8（E4M3/E5M2）、MXFP6 = FP6、MXFP4 = **FP4（E2M1）**、MXINT8 = INT8。这三条由三方独立印证：MX 论文 arXiv:2310.10537v2 Table 1、vLLM 源码常量 `OCP_MX_BLOCK_SIZE = 32`、以及 ONNX Cast 文档 e8m0 段的 MX 链接。

**块 scale 怎么算？这是本主题最容易标错来源的一条。**

```text
论文 Algorithm 1 第 1 行：shared_exp ← floor(log2(max|V_i|)) − emax
                          scale = 2^shared_exp
```

MX **规范的 out-of-scope 清单里逐字包含「块 scale 的具体计算算法」**——**也就是说 `floor` 不是规范规定的，它是 MX 论文 Algorithm 1 的做法**。**必须写成「论文 Algorithm 1」，不能写成「MX 规范规定」。**

**两次取整是两件事，不要混**：**块 scale 用 `floor`**（论文 Alg.1），**元素取整才用 RTNE**（这是规范侧的舍入模式）。

**`floor` 的必然代价。** 设块内最大幅值为 `amax`，规约后的尾数 `m ≜ amax / 2^floor(log2 amax) ∈ [1, 2)`。块 scale 是 `2^(floor(log2 amax) − emax)`，所以规约后最大值是 `m · 2^emax`——**超过元素上限当且仅当 `m > elem_max / 2^emax`**：

| 元素格式 | 元素上限 = ?·2^emax | 阈值 | 均匀假设下 | N(0,1) 32 元素块 MC |
|---|---|---|---|---|
| **e4m3** | `448 = 1.75 · 2^8` | **`m > 1.75`** | **25%** | **16.9%** |
| **e2m1** | `6 = 1.5 · 2^2` | **`m > 1.5`** | **50%** | **29.6%** |

> **⚠ 这两列的「25%」与「16.9%」不是同一个量。** 左边是**均匀分布假设下的解析估算**（`P = 2 − 阈值`），右边是 **N(0,1) 数据、32 元素块的蒙特卡洛**。**两个阈值也不同（1.75 vs 1.5）、两个元素格式也不同。** 把它们并列成「估算 vs 实测」是 P9（同名不同指）。
> 更要紧的是：**「~29%」这个数只能在这里（e2m1）复现**，而它旁边的「25%」是 e4m3 的估算——**这两格属于不同的元素格式，从来不是同一个数**。

**不 clamp 会怎样？** 因为 `e4m3fn` 没有 Inf（01 §1 第四步），溢出的码字就是 NaN：本机在 4096 个块上实测，**1077 个元素越界**，不 clamp 时产生 **781 个 NaN**；clamp 之后 0 个。

**⚠ 但这一条在 torch ≥ 2.13 的部分路径上已经失效**——见 §4.1。

### 第五步：NVFP4——块 16、scale E4M3、再加一层全局 scale

NVFP4 的元素也是 **E2M1**（幅值上限 ±6），但结构不同：

```text
x = x_e2m1 · s_block · s_global
s_global = global_amax / (448 · 6)            ← FP32，整张量一个
s_block  = (block_amax / 6) / s_global        ← FP8 E4M3，每 16 个元素共享
```

**与 MXFP4 的三点区别**（每一点都直接改变量级）：

| | MXFP4 | NVFP4 |
|---|---|---|
| 块大小 | **32** | **16** |
| block scale 格式 | **E8M0**（纯指数，只能是 2 的幂） | **E4M3**（带 3 位尾数，**不是** 2 的幂） |
| 全局 scale | 无 | **多一层 per-tensor FP32** |

`E8M0` 与 `E4M3` 的差别是**量级性的**：`E8M0` 只能表示 2 的幂，所以它把块内最大值规约到的区间是 `[1, 2)`——**最坏情况下浪费了一倍的动态范围**；`E4M3` 能把 scale 定得更贴近 `block_amax`。

代价表（本机 10⁶ 样本，**仿真**，见 §5 的限定语）：

| 分布 | MXFP4 | NVFP4 | 差 |
|---|---|---|---|
| `N(0,1)` | 18.78 dB | 20.43 dB | **+1.65 dB** |
| `Laplace(0,1)` | 17.95 | 20.66 | +2.71 |
| `StudentT(5)`（截 ±1e3） | 17.98 | 20.70 | +2.71 |
| `StudentT(3)`（截 ±1e3） | 17.01 | 20.81 | +3.79 |
| `StudentT(1)`（截 ±1e3） | 14.30 | 28.13 | **+13.83** |
| **对照**：MXFP4 只把块改成 16 | 18.58 | — | （仅 +0.20，与 NVFP4 的 +1.65 不是一回事） |

**「重尾」不是一个数。** 上表每一行都是**具体分布 + 具体参数 + 具体截断**；把它们概括成「重尾 +2.97 dB」就会丢掉全部信息，而 +2.97 在任何一个具体分布上都复现不出来。**判据没写出来的数字，不得与另一个数字并列。**

顺带一个有用的**对照实验**：把 MXFP4 的块从 32 改成 16（其余不动）只涨 +0.20 dB，而 NVFP4 涨 +1.65 dB。**所以 NVFP4 的优势主要不来自「块更小」，而来自「scale 是 E4M3 不是 E8M0」。**

## 2. 执行映射

**这一节的落点是「块缩放发生在哪个 kernel 里」。** 一次 MX 量化的数据通路是：

```text
每个 32 元素块 → amax 归约 → floor(log2) → 减 emax → 转 e8m0 → 逐元素除 scale → RTNE 到元素格式
```

其中**前四步产生的是 e8m0**，也就是本文 §1 第一到三步描述的那个 dtype——**`torch.float8_e8m0fnu` 在这里是正经的存储类型**，不是仿真。第五步（逐元素除）与第六步（元素取整）在 GEMM 的 epilogue 内融合，反量化发生在寄存器里（详见 [quantized-kernels](../quantized-kernels/)）。

**规范与实现在「布局」这一格上的分工**：

- **规范不规定**块在内存里的存放位置。MX 论文正文逐字："The layout of an MX block is **not prescribed**"。
- **某实现强制**：Blackwell 的 cuDNN 要求 "128×4 tiled layout"。

> **「规范不规定 / 某实现强制」必须分开写。** 把 cuDNN 的要求写成「MX 规范规定 128×4」是 P8；反过来把「规范没规定」写成「随便怎么放都行」也是错的——**规范不管，不代表运行时不挑**。

**数值量级：**

| 量 | 数值 | 来源 |
|---|---|---|
| e8m0 的可表示范围 | `2^-127` .. `2^127` | 本机 256 码字全扫 |
| e8m0 的高频端溢出阈值 | `1.5 · 2^127` = 2.55212e+38 | 本机实测（判据：上限 + ulp/2） |
| MX 的 scale 开销 | **0.25** bit/元素（`8/32`） | 规范：块 32、scale E8M0 |
| NVFP4 的 scale 开销 | **0.50** bit/元素（`8/16`）+ global | NVFP4 定义 |
| MXFP4 的 e4m3 块溢出率 | 25%（均匀解析）/ 16.9%（高斯 MC） | 两种判据，**不得合并** |
| MXFP4 的 e2m1 块溢出率 | 50%（均匀解析）/ 29.6%（高斯 MC） | 同上 |

## 3. 实现与演进

**没有 scale 的 fp4。** 一个张量一个 scale（per-tensor FP4）：`E2M1` 只有 8 个幅值，一旦张量内量级跨度超过几十倍，小值全部落到同一个格点上。这是所有块缩放方案要解决的问题。

**MX：块 32 + E8M0。** 解决的问题是「scale 本身的存储开销」。选 E8M0 的理由很直接：**它是 8 位纯指数，能让 `scale` 恰好等于一个 2 的幂**——而块缩放的关键运算是「除以 scale」，除以 2 的幂在硬件上是**指数相减**，精确且免费。代价是 §1 第四步算出来的那 17%–30% 溢出率，以及那条 `floor` 规则（论文 Alg.1，不是规范）。

**NVFP4：块 16 + E4M3 + 双层。** 解决的问题是 E8M0 的浪费。换成带尾数的 E4M3 之后 scale 能更贴近 `block_amax`，SQNR 在 `N(0,1)` 上高 1.65 dB、在重尾上高得更多（§1 第五步）。代价是 **scale 贵一倍**（0.50 vs 0.25 bit/元素），并且多一层 per-tensor FP32 global scale —— 那 32 位在 10⁶ 个元素上摊到 3.2e-5 bit/元素，可以忽略，**但它不是 0**。

**前沿：规范与实现还在往两个方向走。** 规范侧（ONNX）已经把这些行为做成显式属性（`saturate` / `round_mode`）；实现侧（torch / cuDNN）则各自选了不同的默认与不同的强制布局。**这意味着任何一份「MX 的行为是……」的表述都必须同时说清是规范还是实现、是哪个实现、是哪个版本。**

## 4. 踩坑与失败模式

### 4.1 把「MX 必须 clamp，否则出 NaN」写成一个不变的事实

**现象**：文档写「MX 不 clamp 会直接出 NaN，这从数值上证明了规范要求 clamping 的必要性」，在 torch 2.11.0 上验证通过。换成 2.13.0，同一段代码**一个 NaN 都没有**。

**成因**：这条结论**依赖 `e4m3fn` 的溢出行为**，而那件事在 2.13.0 变了（[01](01-fp8-family.md) §3）。本机实测，同一批数据（4096 个块、1077 个越界元素）：

| torch | 元素 e4m3，不 clamp | 元素 e5m2，不 clamp |
|---|---|---|
| 2.8.0 | **781 个 NaN** | 490 个 Inf |
| 2.13.0 | **0 个 NaN**（饱和到 448） | 490 个 Inf |

**「MX 必须 clamp」这句话在 2.13.0 的 e4m3 路径上不再由 NaN 支撑**——因为 `e4m3fn` 现在会饱和。**但结论本身仍然成立**，只是证据要换：**换成有 Inf 的 `e5m2`，两个版本都给出 490 个 Inf。** 也就是说规范要求 clamp 的数值必要性**由 e5m2 那一列独立支撑**，它不依赖 01 那条版本断点。

**规避**：把这条结论的证据挂在**不随版本变的那个格式**上（`e5m2`），并把 `e4m3` 那一列作为**版本相关的补充**写清。这正是「同一条结论若两边都能给，两边都要给」的实际用法。

### 4.2 把块缩放写成「element scale」

**现象**：解释 MX 时写「MXFP4 的 scale 是每 32 个元素一个」，读者据此以为「scale 是给元素用的」。于是去算「每个元素的有效位宽」时得到 4 bit，而正确值是 4.25 bit。

**成因**：**MX 的块 scale 是「共享指数」，不是「逐元素 scale」**——它的语义是「一个块共用一个 2 的幂」，全部价值在于「除以 scale = 指数相减」。把它当成逐元素 scale 会丢掉两件事：① 0.25 bit/元素 的固定开销；② **整个块共用一个指数**这件事本身带来的越界率（`m > 1.75`）。

**规避**：凡是写「scale」这个词的地方，**同时写出它的作用域**（每张量 / 每通道 / 每 token / 每 32 个元素的块）与**它的 bit 开销**。缺了任一，读者就算不出有效位宽。

### 4.3 把 e8m0 当成「小号的 fp8」

**现象**：代码里需要把 `448.0` 之类的小整数量化掉，顺手用 `torch.float8_e8m0fnu` 试一下，结果 `460.0 → 512.0`、`1.0 → 1.0`、而 `0.0 → 5.877e-39`。

**成因**：**e8m0 的尾数位是 0**——它不是「精度低的浮点」，它是「只有指数」。`2^整` 之外的数一律取整到最近的 2 的幂；而 `0` 根本不在值域里（最近的码字是 `2^-127`）。它**只适合当 scale**，不适合当数据格式。

**规避**：把 e8m0 当**索引**用（`scale = 2^(code−127)`，存的是指数），而不是当数值用。另外记住三件事：**没有零、没有负数、取整是平局向上**——尤其「没有零」这一条，任何 `x == 0` 的判断在 e8m0 上都不成立。

## 6. 小结与延伸

三个可复用的结论：

1. **e8m0 的全部价值在「除以 2 的幂是免费的」。** 它是 8 位纯指数，所以 scale 恰好是一个 2 的幂；代价是它**没有零、没有负数**（`0.0 → 2^-127`）、并且**高频端不饱和**（`1.5·2^127` 及以上 → NaN）。**两端不对称来自码字空间，不来自两条规则。**
2. **`floor` 是论文的算法，不是规范的规定。** MX 规范的 out-of-scope 清单逐字包含「块 scale 的具体计算算法」；同样，规范也**不规定块布局**（"The layout of an MX block is not prescribed"），而 cuDNN 在 Blackwell 上强制 128×4 tiled。**这三处必须分开标注。**
3. **「不 clamp 会出 NaN」是版本相关的。** 它依赖 `e4m3fn` 的溢出行为，而那件事在 2.13.0 变了。**结论仍然成立，但证据要挂在 `e5m2` 那一列上**——那一列在两个版本上都给出 Inf。

**这条主线在 §0.8 的三角上是哪条边**：**粒度 vs scale 开销**。块从 32 缩到 16，精度涨了（+1.65 dB），但 scale 的开销涨了一倍（0.25 → 0.50 bit/元素）。NVFP4 的选择是「花更多 bit 存 scale，换更细的粒度 + 更贴合的 scale 格式」。

延伸有四条。**往训练**：块 scale 与各粒度进到训练循环里怎么用（哪个张量用哪个编码、scale 从哪来、溢出怎么办），正文在 [90-training/mixed-precision/03-fp8-training.md](../../90-training/mixed-precision/03-fp8-training.md)（本文不复述，此处回链）。**往旁边**：`per-tensor → per-channel → per-token → per-group` 这四种粒度里，**per-group 的「组」怎么切**在不同论文里并不统一（Q-BERT 沿输出维、GPTQ 沿输入维、Dettmers 把张量拉平），**引用 group 相关数字时不写这一维，数字就不可比**（正文在 [theory/02-granularity](../theory/02-granularity.md)，此处只回链）。**往上**：MX 的 epilogue 融合与块 scale 在 GEMM 内部的施加方式，正文在 [quantized-kernels](../quantized-kernels/)。**往格式**：e4m3 与 e5m2 之间的取舍、以及溢出行为的版本断点，正文在 [01-fp8-family](01-fp8-family.md)。
