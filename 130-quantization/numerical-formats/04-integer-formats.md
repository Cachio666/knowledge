# 整数格式：对称与非对称，以及「除以 127.5 还是 127」

> 定点量化没有「指数」这个自由度，只有**步长 `s`** 与**零点 `z`** 两个旋钮。对称是把 `z` 钉死成 0（省掉存它的比特），非对称是让 `z` 自由（多花一个参数、换来贴着数据范围的动态范围）。这笔交易的收益**完全取决于分布偏斜**：`N(0,1)` 上两者只差 0.50 dB，而单边分布上差 **6.01 dB**。另外，**torch 的对称量化除数是 127.5，不是 127**——这一条多数二手材料写错了。

## 0. 背景与动机

浮点格式靠「指数」自动适配数据尺度（[03](03-bf16-fp16-tf32.md)），定点格式没有这个机制，一切靠两个参数：

```text
量化：  xq = clip( round(s·x + z), 0, 2^b − 1 )        （无符号码字那一套）
反量化：x̂  = (xq − z) / s
```

- **`s`（步长）** 决定分辨率。`s` 越小越准，但能覆盖的范围也越小。
- **`z`（零点）** 决定「哪个实数被映射成整数 0」。它让量化区间可以**任意平移**，从而贴合数据的真实范围 `[a, b]`。

**具体对照**：一批 ReLU 之后的激活（所以全是非负），范围 `[0, 4]`，要压到 8 位。

- **非对称**：`s = 4/255`，`z = 0`。整个 `[0, 255]` 的码字空间都盖在 `[0, 4]` 上，有效级数 **256** 个。
- **对称**：`z` 必须为 0（这是「对称」的定义），范围必须对称地摆成 `[−4, 4]`。于是 `s = 8/255`，而数据只落在 `[0, 4]`——**一半的码字（负半轴那 128 个）全部浪费**，有效级数 **128** 个。

**级数减半 = `20·log10(2) = 6.02 dB`。** 本机实测（8 bit，20 万样本）：`U(0,1)` 上非对称 54.15 dB、对称 48.13 dB，差 **6.03 dB**——与理论值吻合到 0.01 dB。

反过来，如果数据本来就是零均值对称的（`N(0,1)`），非对称就没有优势：本机实测差 **0.50 dB**。**「对称 vs 非对称」的收益是一个由分布决定的量，不是一个定值。**

第二件事是**实现与规范的分工**。同一件事在两边都有定义，而它们**不一样**：对称量化的尺度公式在文献里有两支（一支除以 127、一支除以 127.5），torch 走的是哪一支只能**跑出来**——本文 §1 第三步给出这个数：**127.5**。

## 1. 原理

### 第一步：非对称（affine）的公式

出处：arXiv:2004.09602 Eq.1–5（NVIDIA 的写法）。

```text
s = (2^b − 1) / (α − β)                                ← α、β 是范围的上下端
z = −round(β · s) − 2^(b−1)
xq = clip( round(s·x + z), −2^(b−1), 2^(b−1) − 1 )
x̂  = (xq − z) / s
```

**⚠ 这套写法里的 `z` 已经含了 `−2^(b−1)` 的偏移**——它把 `[0, 2^b−1]` 的无符号码字映射回有符号区间。本仓库的程序按**无符号码字**那一套写（`xq = clip(round(s·x + z), 0, 2^b−1)`，`s = (b−a)/2^b−1`，`z = round(−a/s)`），两套约定**差一个常数偏移**。**比较任何两个 qparams 之前，必须先写死用的是哪一套**——这句话听起来像废话，但同一篇论文的公式与实际库的实现经常不是同一套，混起来就会得到「零点差 128」这种结论。

`s` 与 `z` 都是**从数据的 `min`/`max` 算出来的**，所以：

- **没有裁剪误差**（`[a, b]` 内的值全部落在量化区间里）；
- 但**一个离群值会同时把 `s` 撑大**——`a` 或 `b` 被拉远，`s` 变大，其余值的有效级数掉下来。这正是「最优 clipping」要解决的问题，本文不展开（正文在 [ptq/01-calibration](../ptq/01-calibration.md)）。

### 第二步：对称的公式，两支约定

出处：arXiv:2103.13630 Eq.2–5。**`Z = 0`**，尺度有两支：

```text
restricted range:  S = max|r| / (2^(n−1) − 1)        ← int8 时 = max|r| / 127
full range:        S = 2·max|r| / (2^n − 1)          ← int8 时 = max|r| / 127.5
```

**两支的分母只差 0.5，但含义不同**：

- `restricted range` 用 `[−127, 127]`——**把 `−128` 排除在外**，换来「`−127` 与 `+127` 关于零对称」；
- `full range` 用 `[−127.5, 127.5]`——**把 `−128` 用起来**，代价是端点不再是整数。

两组在整个 `[a, b]` 上的 SQNR 差异很小（本机实测三组分布上差 0.03–0.05 dB），**但对拍 qparams 时必须知道是哪一支**，否则会得到「差 0.8%」这种看着像 bug 的偏差。

### 第三步：★ torch 走的是哪一支——127.5，不是 127

这一条**只能实测**，因为两支在文献里都存在。判据：喂一个 `maxabs = 17.961498` 的张量给 `torch.ao.quantization.observer.MinMaxObserver`（`per_tensor_symmetric` + `qint8`），看它给出的 scale：

```text
maxabs                    = 17.961498
maxabs / 127.5            = 0.14087449
maxabs / 127.0            = 0.14142833
observer 给出的 scale      = 0.14087449
observer × 127.5 = 17.9614980     ← 与 maxabs 逐位一致
observer × 127.0 = 17.8962…       ← 对不上
```

**所以 torch 用的是 `full range` 那一支，除数是 `127.5`。** torch 侧的口径是 `(quant_max − quant_min)/2`，int8 时 `= (127 − (−128))/2 = 255/2`。本机在 **2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 / 2.13.0 五个解释器**上跑出同一个数。

> **多数二手材料写「除以 127」，是错的**（那是 `restricted range`）。**这一格的价值不在于 0.4% 的精度差，而在于它是一个「照抄文献就会与实现不符」的例子**——正是 P8 那种「规范规定一种、实现做另一种」的形状。

### 第四步：零点被约束为整数，代价有多大

`z` 在数学上不需要是整数（`z = −a/s` 一般是个小数）；但**整数格式的 `z` 必须是整数**（它就是码字空间里的一个位置）。这个约束带来什么？

设 `δ ≜ (−round(z)·s) − a`，即「实际的左端点」与「理想的左端点」之差。因为 `round(z)` 与 `z` 最多差 0.5：

```text
|δ| = |round(z) − z| · s ≤ s/2

而且两端点**同时平移 δ**：
  a_eff = −round(z)·s = a + δ
  b_eff = a_eff + (2^b − 1)·s = b + δ
  ⇒ b_eff − a_eff = b − a     ← **范围宽度不变**
```

**这是这条约束的关键性质：既不缩小也不扩大范围，只是整体平移不超过半个量化步长。** 本机实测（10 万样本，8 bit）：`|δ| ≤ s/2` 在三组分布上都成立，其中 `U(-1,1)` 那一组几乎顶到界（`|δ| = 3.9205e-3`，`s/2 = 3.9215e-3`）。

**数值影响很小，但不是零。** 本机在同一批 10 万样本上把 `z` 从整数释放为实数，MSE 从 `1.039422e-04` 变到 `1.040683e-04`（相对差 0.12%）——**同量级，但确实在变**。所以正确的表述是「影响很小」，不是「没有影响」。

### 第五步：★ 对称 vs 非对称，收益取决于分布偏斜

本机实测（8 bit，20 万样本，`torch.manual_seed(20260918)`）：

| 分布 | 非对称（`0..255`，`s=(b−a)/255`） | 对称（`full range`，`/127.5`） | 差 |
|---|---|---|---|
| `N(0,1)` | 39.77 dB | 39.27 dB | **+0.50** |
| `|N(0,1)|`（单边，模拟 ReLU 后激活） | **45.96** | 39.95 | **+6.01** |
| `U(0,1)`（单边） | **54.15** | 48.13 | **+6.03** |
| （对照）`restricted range`（`/127`） | — | 39.23 / 39.90 / 48.10 | — |

**判据写在表头里**：非对称用无符号码字 `0..255` 的仿射；对称用 `full range`（`S = max|r|/127.5`），第三行是 `restricted range` 的对照。

三件事：

1. **零均值分布上，对称几乎不亏**（0.50 dB）。因为此时 `[a, b]` 本来就近于对称，「把 `z` 钉死成 0」几乎不浪费码字。
2. **单边分布上，对称正好亏 6.02 dB**——实测 6.01 / 6.03。这就是 §0 那笔账：**一半的码字盖在数据根本不去的半轴上**。
3. **`restricted range` 与 `full range` 在这三组分布上只差 0.03–0.05 dB。** 也就是说，**「torch 用哪一支」这件事在精度上几乎看不出来**——它只能靠**读 qparams**（§1 第三步）来判别。**「两支的精度差」与「实现用哪一支」是两个不同的问题**，别指望用前者回答后者。

### 第六步：★ 但从这条公式推不出「非对称总是更好」

上面的表**很容易**被读成「非对称更好」。两件事要同时说：

- **非对称要多存一个 `z`。** per-tensor 时它是一个标量，可以忽略；但粒度细到 per-group（比如每 128 个元素一组）时，`z` 的开销就变成 `b/128` bit/元素——**与 MX 的块 scale 同一量级的固定开销**（[02](02-e8m0-and-mx.md) §0）。粒度越细，这笔账越不能忽略。
- **`z` 让「`s` 与 `z` 之外还有一个自由度」变成「还要学/存一个参数」**，而对称的 `Z = 0` 是白送的。

**所以正确的结论是**：**当数据明显偏斜、且粒度够粗（per-tensor / per-channel）时，非对称的 6 dB 是白拿的；当粒度细到 per-group 时，这笔账要重新算。** 「非对称总是更好」与「对称就够了」都是把条件丢掉之后的说法。

## 2. 执行映射

**这一节的落点是「qparams 是谁算的、算完之后 `z` 的整数约束在哪里施加」。**

在 torch 里，这条链是 `observer → qparams → FakeQuantize / 量化 kernel`：

| 环节 | 组件 | 发生了什么 |
|---|---|---|
| 收集统计量 | `torch.ao.quantization.observer.MinMaxObserver` | 前向时累积 `min`/`max`（或 EMA） |
| 计算 qparams | `observer.calculate_qparams()` | 施加对称/非对称的公式，**`z` 在这一步被取整** |
| 应用 | `FakeQuantize` / 后端 kernel | `round(s·x + z)`、`clip`、反量化 |

**`reduce_range` 这个参数改的是「哪一段码字可用」**：置真时把量化范围砍掉 1 bit（`quint8` 从 `[0,255]` 变 `[0,127]`）。它的存在理由**不是数值需要，是某个指令集的行为**——本机读到的源码注释逐字（**torch 2.11.0 的 `torch/ao/quantization/observer.py:528-532`**；⚠ **这一处的行号是版本相关的**：本机实测 **2.7.1 在 518、2.8.0 在 523**，2.11.0 与 2.13.0 在 528）：

> "For x86 quantized kernels, we need to ensure that the **vpmaddubsw** instruction does not overflow. We allow for a reduce_range argument to observers that reduces the quantized range to (0,127) or (-64, 63). ... **This is not an optimal choice for non x86 backends as it loses a bit of precision**"

**所以引用时不要把它写成「量化的一般最佳实践」。**（`reduce_range` 对 qparams 的具体影响、以及默认 qconfig 里哪些组合会抛异常，正文归 [ptq/01-calibration](../ptq/01-calibration.md)，本文只留这一处口径说明。）

**数值量级：**

| 量 | 数值 | 来源 |
|---|---|---|
| torch 对称量化的除数（int8） | **127.5** | 本机 observer 实测，五个版本一致 |
| 单边分布下对称的代价 | **6.01 / 6.03 dB** | 本机实测（`|N(0,1)|` / `U(0,1)`） |
| 零均值分布下对称的代价 | **0.50 dB** | 本机实测（`N(0,1)`） |
| `restricted` 与 `full range` 的精度差 | **0.03–0.05 dB** | 本机实测（三组分布） |
| 零点取整的界 | `|δ| ≤ s/2` | 推导 + 本机实测（`U(-1,1)` 上顶到界） |
| `torch.int4` 的 `element_size()` | 报 **1**（语义上应为 0.5） | 本机实测，五个版本一致 |

## 3. 实现与演进

**per-tensor 非对称。** 整个张量一组 `(s, z)`。`z` 的开销可以忽略，范围贴合数据。这是最早的做法，也是 `torch.ao.quantization` 的默认观察器算出来的东西。

**per-channel 非对称。** 每个输出通道一组 `(s, z)`。解决的问题是「不同通道的量级不同」——一个通道的离群值不再影响其他通道。代价是 `z` 的开销按通道数放大（但仍然是 per-tensor 量级的可忽略量）。

**对称 + per-channel（硬件侧的主流）。** 推理 kernel（尤其是 int8 GEMM）更偏好对称：`z = 0` 时 `x̂ = xq · s`，反量化退化成一次乘法；非对称则要先减 `z`，在 GEMM 的 epilogue 里多一项（那一项的融合方式见 [quantized-kernels](../quantized-kernels/)）。**所以「对称还是非对称」在工程上常常不是精度决定的，而是 kernel 决定的**——这就是 §1 第六步那笔账的另一半。

**低比特（int4 / 2-bit）。** 位数越低，同一个 `z` 占的相对开销越大，对称的吸引力越强——因为 `z` 的存储开销按 `b` 的倒数放大。

**前沿：`torch.int4` 目前还不是一个能用的存储格式。** 本机实测（五个解释器一致）：

| 操作 | 结果 |
|---|---|
| `torch.zeros(4, dtype=torch.int4)` | **成功**（只分配） |
| `tensor.element_size()` | 报 **1**（语义上应为 0.5——两个 4 位数装一个字节） |
| `torch.tensor([1], dtype=torch.int4)` | **抛异常**（2.8+ 为 `store_scalar: invalid type`） |
| `tensor.fill_(1)` | **抛异常**（`fill_cpu` not implemented） |
| `tensor.copy_(同 dtype)` | **抛异常**（`copy_kernel` not implemented） |
| `str(tensor)` / `tensor[0].item()` | **抛异常**（`_local_scalar_dense_cpu` not implemented） |
| `tensor.float()` / `tensor + 1` | **抛异常**（`copy_` not implemented） |

**结论：它目前只是「可分配的空壳 dtype」，不能承载数据。** 文档不得写成「torch 支持 int4 张量」。4 位权重的真实落地路径是**打包存储 + 专用 kernel**（`_weight_int4pack_mm_for_cpu` 那一类），而不是这个 dtype。

> **⚠ 异常的类型本身跨版本变了**：2.6.0 一律 `RuntimeError`；2.7.1 起 `fill_cpu` / `copy_kernel` / `_local_scalar_dense_cpu` 变成 `NotImplementedError`（而 `fill_cpu` 到 2.8.0 才跟上）。所以**断言只能断「抛了异常」，不能断具体异常类**——断具体类会在某个版本上假失败。

## 4. 踩坑与失败模式

### 4.1 照着文献写 `/127`，与 torch 的 qparams 对不上

**现象**：自己按对称量化的公式实现一遍，拿 torch 的 observer 对拍，发现 scale 差 **0.4%**、反量化结果差一点。因为差得不多，容易被当成浮点误差放过去。

**成因**：对称量化的尺度在文献里**有两支**（`/127` 与 `/127.5`，§1 第二步），而 **torch 用的是 `/127.5`**（§1 第三步实测）。两支在精度上只差 0.03–0.05 dB，**所以「多跑几个样本看 SQNR」根本分辨不出来**——只有直接看 qparams 才能判别。

**规避**：**用 qparams 对拍，不要用 SQNR 对拍。** 构造一个 `maxabs` 已知的输入，检查 `observer_scale × 127.5 == maxabs`。更进一步：**任何「实现用的是哪一支」的问题，都要找一个「两支的差被放大」的观测量**——精度差 0.4%、但 qparams 差的是**恰好 0.4% 的一个整数倍关系**，后者是可判别的。

### 4.2 把「对称省一个 `z`」当成「对称更省」

**现象**：设计一个 per-group 的量化方案，为了省掉 `z` 选了对称，结果发现精度掉得比预期多，而「省下的比特」也没有想象中多。

**成因**：两笔账要分开算，而它们的方向相反。

- **省下的**：`z` 的存储。per-tensor 时可忽略；per-group（每 `G` 个元素一组）时是 `b/G` bit/元素——**这是与 MX 的块 scale 同一个量级的东西**（[02](02-e8m0-and-mx.md) §0 那张表：块 32 的 E8M0 scale 是 0.25 bit/元素）。
- **付出的**：单边分布上 **6.02 dB**。**在低位宽下这 6 dB 比 `z` 的存储贵得多**——位宽越低，级数越少，减半越致命。

**规避**：把两笔账放在同一个尺子上——**「6.02 dB 的精度」与「`b/G` bit/元素的存储」哪个更值**。在 `G ≤ 128` 且位宽 ≤ 4 时，经验上**后者明显更便宜**（0.03–0.06 bit/元素换 6 dB）。**这也是为什么主流的 per-group 方案（GPTQ / AWQ / MX）都用非对称或带零点补偿**，而不是为了省那几比特回到对称。

### 4.3 以为 `torch.int4` 能用

**现象**：看到 `torch.int4` 存在、`torch.zeros(4, dtype=torch.int4)` 也能跑，于是写了一段用 `torch.int4` 存权重的代码，直到 `fill_` 或 `str()` 才炸——而且炸的位置离「我以为它能用」的地方很远。

**成因**：`int4` 与 `uint4` 在 torch 里只是**注册了 dtype 元数据**（所以 `zeros` 能分配、`element_size()` 还能错报成 1），**但没有实现任何承载数据的 kernel**。本机实测的 7 类操作里只有「构造」成功，其余全部抛异常（§3 那张表）。

**规避**：把它当**未实现的占位**。真正的 4 位存储走打包路径（一个字节装两个 nibble），`element_size()` 那个「1」是**错的**（语义上应为 0.5）——**连这个元数据都还没对**。要判断一个 dtype 能不能承载数据，最快的判据是 `torch.tensor([1], dtype=dt)`：它必须能真的存进去一个数。

**配套程序与 `verify.py` 的分工**（CONTRIBUTING §2 第三种形态）：编号程序在真 torch 上测**observer 的真实 qparams**、`z` 的取整效果、以及 `torch.int4` 的行为边界；`verify.py` 在默认 `python3` 下（**不 import torch**）独立实现同一套仿射/对称公式、复算 `|δ| ≤ s/2` 的界、并核对 `127.5` 这个除数（用的是 specs 里记的实测 maxabs 与 scale）。**两者不得互相背书**——数学成立不证明实现如此。

## 5. 实测数据

**测量条件**：CPU 型号 **Apple M1 Pro（10 核）**；macOS；`python3` 版本与 `torch` 版本**逐表注明**；**CPU-only，无 GPU 数字**。

**覆盖范围**：本机五个解释器（torch **2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 / 2.13.0**），**全部逐格一致**。**未覆盖 2.9.x / 2.10.x / 2.12.x**（本机无解释器）。

**表 1：torch 的对称量化除数是 127.5**（五个版本一致）

| 量 | 值 |
|---|---|
| 输入 `maxabs` | 17.961498 |
| `maxabs / 127.5` | 0.14087449 |
| `maxabs / 127.0` | 0.14142833 |
| **observer 给出的 scale** | **0.14087449** |
| `scale × 127.5` | **17.9614980** ← 逐位一致 |
| `scale × 127.0` | 17.8962… ← 对不上 |
| 另一条独立期望：输入 `[-5, 5]` | observer scale = 0.039215688，`5/127.5 = 0.039215686` |

torch 侧口径：`(quant_max − quant_min)/2 = (127 − (−128))/2 = 127.5`。

**表 2：对称 vs 非对称**（8 bit，20 万样本，`torch.manual_seed(20260918)`）

| 分布 | 非对称 | 对称（`/127.5`） | 差 | 对照：`/127` |
|---|---|---|---|---|
| `N(0,1)` | 39.77 dB | 39.27 dB | **+0.50** | 39.23 |
| `|N(0,1)|` | **45.96** | 39.95 | **+6.01** | 39.90 |
| `U(0,1)` | **54.15** | 48.13 | **+6.03** | 48.10 |

判据：非对称 = 无符号码字 `0..255` 的仿射（`s = (b−a)/255`，`z = round(−a/s)`）；对称 = `S = 2·max|r| / 255`（full range）；第三列是 `restricted range`（`S = max|r|/127`）的对照。
**6.01 / 6.03 dB 与理论值 `20·log10(2) = 6.0206` 吻合。**

**表 3：零点取整的 `δ` 界**（10 万样本，8 bit）

| 分布 | `s` | `z_real` | `z_int` | `|δ|` | `s/2` | 界成立 |
|---|---|---|---|---|---|---|
| `N(0,1)` | 3.4585e-02 | 123.07 | 123 | 2.575e-03 | 1.729e-02 | 是 |
| `U(-1,1)` | 7.8430e-03 | 127.50 | 127 | **3.9205e-03** | **3.9215e-03** | 是（**几乎顶到界**） |
| 单边 | 1.7320e-02 | 0.00 | 0 | 0 | 8.660e-03 | 是 |

**表 4：`δ` 的数值影响**（10 万样本，`N(0,1)`，8 bit）

| `z` 的处理 | MSE |
|---|---|
| 取整为整数 | **1.039422e-04** |
| 释放为实数 | **1.040683e-04** |

相对差 **0.12%**——**同量级，但确实在变**。

**表 5：`torch.int4` / `torch.uint4` 的行为边界**（五个版本一致）

| 操作 | 结果 |
|---|---|
| `torch.zeros(4, dtype=dt)` | **成功** |
| `element_size()` | 报 **1**（应为 0.5） |
| `torch.tensor([1], dtype=dt)` | 抛异常 |
| `fill_(1)` | 抛异常 |
| `copy_(同 dtype)` | 抛异常 |
| `str(tensor)` / `tensor[0].item()` | 抛异常 |
| `tensor.float()` / `tensor + 1` | 抛异常 |

**7 类操作里只有「构造」成功。** 异常类型随版本变（2.6.0 一律 `RuntimeError`；2.7.1 起部分变为 `NotImplementedError`），所以断言只断「抛了异常」。

## 6. 小结与延伸

三个可复用的结论：

1. **定点量化只有「步长 vs 零点」这一对旋钮**，而零点被约束为整数带来的误差是**有界的、且只平移不缩放**（`|δ| ≤ s/2`，两端点同时平移）。本机实测 `U(-1,1)` 上 `|δ| = 3.9205e-3` 对 `s/2 = 3.9215e-3`——**几乎顶到界**，这个界是实的。
2. **对称与非对称的收益完全由分布偏斜决定**：`N(0,1)` 上差 0.50 dB，单边分布上差 **6.01 / 6.03 dB**（= `20·log10(2)`）。**它不是「哪个更好」的问题，是「这笔 6 dB 值不值它多花的那点存储」的问题。**
3. **`127.5` 这个数只能跑出来。** 文献里两支都在（`/127` 与 `/127.5`），它们的精度差只有 0.03–0.05 dB——**用 SQNR 分辨不出来**，只有拿 qparams 对拍才能判别。**这是「规范与实现要分开」的一个具体落点。**

**这条主线在 §0.8 的三角上是哪条边**：**用比特交换**——具体是**「一个 bit 的偏置 vs 更宽的动态范围」**那一条。非对称把 `z` 这个参数存下来，换来贴着数据范围的动态范围；对称把 `z` 钉死成 0，省下这份开销、代价是范围必须对称。零均值数据上这笔交易几乎免费，单边数据上它值 6 dB。

延伸有三条。**往校准**：`min`/`max` 怎么来（min-max / EMA / percentile / entropy）决定了 `s` 与 `z`，也决定了离群值怎么处理，正文在 [ptq/01-calibration](../ptq/01-calibration.md)。**往粒度**：`z` 的开销随粒度变细而放大，这条线在 [theory/02-granularity](../theory/02-granularity.md)。**往格式**：把块 scale 换成共享指数（而不是逐元素的 `s`）就是 MX 那一步，正文在 [02-e8m0-and-mx](02-e8m0-and-mx.md)；对称/非对称在浮点上的对应物是「裁剪与否」，而那笔交易在浮点上不存在，正文在 [03-bf16-fp16-tf32](03-bf16-fp16-tf32.md) §1 第四步。
