# W8A8：int32 累加器、epilogue 融合，以及两个「不是精确整数累加」的 CPU 算子

> 量化省下的是**载荷**，但每一处节省都会被别的东西吃掉一部分。这一篇讲 W8A8 那一侧的两笔账：**累加器不是免费的**（int8×int8 的乘积上界 16129，让 int16 在 `K ≥ 3` 就溢出，所以硬件只能用 int32——而 int32 又必须在 epilogue 先转 fp32 再乘 scale）；**epilogue 融合省下的是中间结果的写回**。★ 而本机真跑的两个「整数量化」CPU 算子——`_weight_int8pack_mm` 与 `_weight_int4pack_mm_for_cpu`——**都不是精确整数累加**（K=2²⁰ 时精确和 3.33e8 远小于 int32 上限，实测却差了 5.5e5）。**规范说指令层面是 `.s32`，实测说这个实现不是——两件事，必须分开写。**

## 0. 背景与动机

### 0.1 一个具体的对照场景

一个 `[4096, 4096]` 的权重层，fp16 存要 **32 MiB**，int8 只要 **16 MiB**。省下来的是**载荷**。但「省下一半字节」不等于「快一倍」——至少有四笔账要算：

| # | 账 | 谁在付 |
|---|---|---|
| 1 | **累加器** | 乘积只有 8 位，但**乘积的累加**不能只有 8 位。这一篇 §1 的第一步 |
| 2 | **scale / zero-point 的存储** | 粒度越细，元数据越贵（`02-w4a16-packing` §B.1 把这条算成一笔字节账） |
| 3 | **中间结果的写回** | 若把「反量化」做成一个独立 pass，就要把 fp16 权重写回 HBM——§2 的账 |
| 4 | **epilogue 的舍入** | int32 累加器交出来的整数，必须在 epilogue 转成浮点再乘 scale；这一步有自己的上界（§1 第三步） |

本篇只讲第 1、3、4 笔。第 2 笔在下一篇。

### 0.2 不用 int32 会怎样：一个两行的计算

朴素想法是「乘积只有 8 位，累加器给 16 位够了吧」。**不够，而且差得很远。** 见 §1。

## 1. 原理

### 第一步：单乘积的上界决定累加器宽度

int8 的值域是 `[−128, 127]`，所以单个乘积的**最大绝对值**有两个候选：

| 取法 | 值 | 什么时候取到 |
|---|---|---|
| `127 × 127` | **16129** | 两个操作数都在正端 |
| `(−128) × (−128)` | **16384** | 两个操作数都在负端 |

**这两个数不是同一个量**（判据不同：一个假设操作数都取正上界、一个假设都取负上界），所以**它们各自的溢出阈值也不同**。下面按 **16129** 算（这也是计划基线用的判据），另一个在 `verify.py` 的 A.2 与 E.4 里对照。

累加 `K` 项，最坏情况（全部同号且都取到上界）是 `K × 16129`：

| 累加器 | 上界 | 最后一次安全的 `K` | 首次溢出的 `K` |
|---|---|---|---|
| int16 | `2^15 − 1 = 32767` | **2** | **3** |
| int32 | `2^31 − 1 = 2147483647` | **133144** | **133145** |

**`K ≥ 3` 就溢出**——任何真实的 GEMM 都不可能用 int16 累加器。而 int32 要 `K ≥ 133145` 才首次溢出。现实中的 K（4096 / 8192 / 16384）最坏只占 int32 上限的：

| K | 最坏累加值 | 占 int32 上限 |
|---|---|---|
| 4096 | 66 064 384 | **3.08%** |
| 8192 | 132 128 768 | **6.15%** |
| 16384 | 264 257 536 | **12.31%** |

> ⚠ **判据必须一起写**：这是**最坏情况**（假定全部乘积同号且都取到 16129），不是典型值。典型情况下随机符号会互相抵消，占用远低于此。**没有这个判据，「3.08%」这个数会被误读成「实测占用」。**

### 第二步：这不是本仓库的推导，是四条规范来源

「整数矩阵乘的累加器是 32 位」这件事**在指令层面就是被规定死的**，有四个互不依赖的出处：

| 来源 | 原文/常量 | 它规定了什么 |
|---|---|---|
| **PTX 规范** | 整数 `wmma.mma` 的 `.ctype` 与 `.dtype` 必须是 **`.s32`** | **指令集里根本不存在 int8 的 s16 累加变体**——不是「不建议」，是没有 |
| **cuBLAS** | `CUBLAS_COMPUTE_32I` | 计算类型枚举 |
| **cuSPARSELt** | `CUSPARSE_COMPUTE_32I` | 同上 |
| **DP4A** | `"with 32-bit integer accumulation"` | 文档明文 |

**第一条是最硬的**：如果累加器宽度只是个「建议」，硬件厂商会提供多个变体；而 PTX 里整数 MMA 的累加器**只有 `.s32` 一种**。

> ⚠ **这是「规范侧」的断言。** 本机 CPU 上那两个算子的实测（§5）是**另一件事**——它们**不是**精确整数累加。**两条都写出来，缺一条就是 P8**（把规范当实现，或把某个实现的偏离当成规范失效）。

### 第三步：int32 累加器必须在 epilogue 先转 fp32

int32 累加器交出来的是一串**整数**。要乘上 `scale`（一个浮点数），必须先转成浮点。用哪个浮点？

fp16 = `S1E5M10`，**11 位有效位** ⇒ 它能精确表示的整数上界是 **`2^11 = 2048`**。而 int32 在 `K = 133144` 时仍然精确——**两者的量级差 10 万倍**。

**⇒ epilogue 里的第一步必须是 `int32 → fp32`，然后才乘 scale。** 直接把 int32 塞进 fp16 会丢掉低位整数位；而 fp32 的 24 位有效位对 int32 累加结果的典型量级（§1 第一步的表，最多 12%）是足够的。

这不是「精度更好」，是**「不用 fp32 就直接错」**。本机实测（`code/01_w8a8.py` 的 C.7）：

| int32 里完全正常的整数 | → fp16 读出 | 失败形态 |
|---|---|---|
| 2048 | 2048 | —— |
| **2049** | **2048** | **舍入**（ulp = 2） |
| 4096 | **4096** | ——（**是原值**） |
| **100000** | **inf** | **溢出**（> 65504） |

> ⚠ **三行、三种不同的东西，不得混成一句「fp16 装不下 2048 以上的整数」**：
> - 「**连续整数能精确表示的上界是 2048**」说的是：`2048` 以下**每一个**整数都可表示；
> - 而 `4096` 在 2048 之上**仍然精确**（它是 2 的幂）⇒ 那个上界**不是「最大可表示整数」**；
> - `100000` 的失败是**溢出**（`inf`），`2049` 的失败是**舍入**（→ 2048）——**两种不同的失败**。
> **判据不同的三个数，并列就是 P9。**

### 第四步：W8A8 的 epilogue 长什么样

标准形式（**引用值**，见「参考」）是 scale 与 zero-point 在 GEMM 的 epilogue 内融合应用：

```
D = s_a · s_b · ( Â·B̂ − z_a · J_a·B̂ )
```

其中 `J_a` 是全 1 行向量，所以 **`J_a·B̂` 就是 `B̂` 沿归约轴的列和**。这里有三件事要分开看：

| 项 | 形状 | 关键性质 |
|---|---|---|
| `Â·B̂` | `M×N` | 真正的 GEMM |
| `J_a·B̂` | `1×N` | **与 batch（M）无关 ⇒ 可离线预计算** |
| `z_a` | `M×1`（per-token）或标量（per-tensor） | 见下 |

**两者都实现成了「修正项」而不是「逐元素减零点」**，但形态不同：

- **per-tensor 的 `z_a`**：整项 `z_a·(J_a·B̂)` 是一个 `(1,N)` 行向量，可以**折进 epilogue 或 bias**；
- **per-token 的 `z_a`**：`z_a`（列向量）与 `J_a·B̂`（行向量）的**外积 / rank-1 更新**——每个输出行要用一个不同的系数去乘同一个行向量。

★ **这是 W8A8 的版本。** 下一篇会说明：主流 W4A16 kernel **不用这个形式**，而是逐元素做 `(q − z)`。**两件事，不要混。**

### 第五步：这个形式为什么等价于「逐元素减零点」

代数上是一行：

```
(Â − z_a·J_a)·B̂ = Â·B̂ − z_a·(J_a·B̂)
```

本机在真 torch 上对拍过（`code/01_w8a8.py` 的 A.5，maxdiff = 0）。之所以写成右边那个形式，是因为右边把**与数据无关的部分**（`J_a·B̂`）分离了出来——一次预计算，之后每次 GEMM 只做一次 rank-1 更新。

## 2. 执行映射

### 2.1 四个组件名与一个数值量级

- **DP4A / IMMA 指令** —— 真正做 `int8×int8 → int32` 的点积累加的那条指令。它是「累加器 = int32」这条规范的物理承担者。
- **累加器 tile（寄存器/共享内存）** —— `M×N` 的 fp32 累加器。判据：**4·M·N 字节**。`M=128, N=11008` 时是 **5.4 MiB**——它**从不离开寄存器/共享内存**。
- **epilogue 阶段** —— CUTLASS 把它列为独立阶段（**引用值**，官方文档原文：*"It is also the phase in which linear scaling and other elementwise operations may be conveniently computed"*）；`LinearCombination` 即 `D = alpha·accumulator + beta·source`；per-channel 向量 scale 走 `EpilogueWithBroadcast`。
- **量级**：一个 `[4096, 4096]` 层的 int8 载荷是 **16 MiB**。若把它反量化成 fp32 写回，是 **64 MiB**——**多写 48 MiB，每个 batch 一次**。

### 2.2 「独立反量化 pass」的带宽账：写是读的 4 倍

这是本主题主线（**省下的字节去哪了**）在这一篇里的那一笔：

| | 每个权重元素 | `[4096,4096]` 一层 |
|---|---|---|
| 读（int4 载荷） | 0.5 字节 | 8 MiB |
| **写（fp16 权重）** | **2.0 字节** | **32 MiB** |

**写是读的 4 倍。** 所以一个独立的反量化 kernel **被写侧带宽卡死**，而不是被 int4 的读侧。融合进 GEMM 之后，反量化发生在寄存器里，**fp16 权重永远不落回 HBM**——省下的是**中间结果的写回**，不是载荷。

> ⚠ **判据**：这条账算的是**一个独立 pass**。它不适用于「已经融合」的实现，也不能反过来当成「融合一定快 4 倍」——融合的收益随 batch 增大而衰减（dequant 在总时间里的占比下降）。这是**引用值**的定性结论，本机无 GPU 无法量化。

### 2.3 本机 CPU 侧的对照观察

`_weight_int8pack_mm` 的输出**直接就是 float**（判据：`torch.ops.aten._weight_int8pack_mm(x, w_int8, scales)` 的 schema 是 `-> Tensor`，返回 fp32，没有中间张量交给调用方）。

**这个观察支持什么、不支持什么，必须写清楚**：

- ✅ 支持：**调用方拿不到**反量化后的权重——它是算子内部的事，没有「先物化 fp16 权重再 matmul」这一步。
- ❌ **不支持**：「融合发生在 epilogue 里」。那是 CUTLASS / vLLM 文档对 GPU kernel 的描述，**本机无法核实**。把一个 CPU 算子的 API 表面当成 GPU kernel 内部结构的证据，就是 P7（引文与断言的作用域不匹配）。

## 3. 实现与演进

**第一代：独立的反量化 pass。** 先把 int8 权重乘上 scale 变成 fp32（或 fp16），再走一个普通 GEMM。

- 代价：§2.2 的那笔账——**写是读的 4 倍**。
- 为什么会这样做：它**不需要任何新 kernel**，是最容易落地的版本，在权重量化刚出现时很常见。

**第二代：融合进 GEMM 的 epilogue。** scale 与 zero-point 在累加器上就地应用。

- 收益：反量化后的权重不落回 HBM（§2.2）。
- 代价：epilogue 不再是「直接写回」，多了几条向量运算；且**累加器的类型必须是 int32**（§1 第一步）。
- 这一步同时把 §1 第四步的列和形式带了进来：`J_a·B̂` 可以在权重加载时就预计算好。

**第三代：per-token / per-channel 的细粒度 epilogue。** `scale_a` 从 per-tensor 变成 per-token（列向量）、`scale_b` 从 per-tensor 变成 per-channel（行向量）。

- 收益：粒度更细 ⇒ 量化误差更小（这条换算在 `theory/02-granularity`）。
- 代价：epilogue 从「两个标量相乘」变成「一个列向量 × 一个行向量」；per-token 的 `z_a` 还要多一次 rank-1 更新。
- **引用值**：vLLM 的 W8A8 epilogue 文档把这件事写成 **4 个变体**——`scale_a` ∈ {per-tensor, per-token}、`scale_b` ∈ {per-tensor, per-channel}，而 `bias` **永远是 per-channel（行向量）**。

## 4. 踩坑与失败模式

### 4.1 把 int32 累加器直接塞进 fp16

**现象**：认为「反正要在 epilogue 乘一个浮点 scale，直接转 fp16 省一半带宽」。

**成因**：fp16 只有 11 位有效位，**连续整数能精确表示的上界是 2048**；而 int32 累加器在 `K = 133144` 时还精确（差 10 万倍）。本机实测（`code/01_w8a8.py` 的 C.7）：`2049 → 2048`（**舍入**）、`100000 → inf`（**溢出**），而 `4096 → 4096`（**是原值**——所以那个上界不是「最大可表示整数」）。

**规避**：epilogue 的第一步固定为 `int32 → fp32`，再乘 scale。**这不是优化选择，是正确性要求。**

### 4.2 断言「`_weight_int8pack_mm` 是精确整数累加」

**现象**：既然 `_weight_int8pack_mm` 是「int8 权重」算子，就假设它内部是 int32 累加、结果逐位精确。

**成因**：这个假设**看起来完全合理**（§1 第二步的四条规范都指向 int32），而它在小规模上**也确实看不出问题**——本机实测的偏差表里，K=32 时只有 1.9e-06。

**规避**：**把精确和推过 2²⁴ 再去测**。本机实测（判据：`x = randint(1,5,(1,K)).float()` 全正不抵消、`w ≡ 127`、`scale = 1`，比较对象是 `float32(int64 精确和)`）：

| `K` | 精确和 | 与 `float32(精确和)` 的差 | 相对偏差 |
|---|---|---|---|
| 2¹⁶ | 2.08e+07 | **0** | 0 |
| 2¹⁸ | 8.32e+07 | 4.8e+01 | 5.77e-07 |
| 2²⁰ | **3.33e+08** | **5.51e+05** | 1.66e-03 |
| 2²¹ | 6.66e+08 | 3.17e+06 | 4.77e-03 |

K=2²⁰ 的精确和 3.33e8 **远小于** int32 上限 2.147e9——**一个 int32 累加器在那里必然逐位精确**。实测差了 5.5e5 ⇒ **排除「精确整数累加」**。

> ⚠ **只排除得掉这一种。** 它究竟是 fp32 还是别的宽度，本仓库**没有独立通道**判定（这是 §3 残留）。**不得断言。**
> ⚠ 2¹⁶ 那一档偏差仍是 0（和已经超过 2²⁴）⇒ 「超过 2²⁴」只是**必要条件**，不是「必然出偏差」的充分条件。

### 4.3 把 maxdiff 当成一个常量引用

**现象**：写「`_weight_int8pack_mm` 与浮点参照的 maxdiff 是 3.8e-06」。

**成因**：这个数**随 setup 变化**——本机同一张表里就跨了三个数量级（K=32 的 1.9e-06 → K=131072 的 1.7e-03）。

**规避**：写**量级 + 判据**：「与浮点参照一致到 ~1e-3 量级（取决于 K 与 scale）」。

> ★ **本主题还实测到一个更强的形态**：这个 maxdiff **连换 torch 版本都会变**——而变的**不是被测算子**。
> 判据（同一种子、同一输入，**三步分别看**）：
> | 看哪一步 | 2.6.0 / 2.7.1 | 2.8.0 / 2.11.0 / 2.13.0 |
> |---|---|---|
> | `_weight_int8pack_mm` 的输出 `.sum()` | **20.066649161279** | **20.066649161279** |
> | 参照的反量化步 `wq = w.float()*scales` 的 `.sum()` | **3.714967675507** | **3.714967675507** |
> | 参照的**矩阵乘** `(x @ wq.T)` 的 `.sum()` | **20.066647015512** | **20.066647142172** |
>
> **⇒ 前两步逐位不变，只有第三步变了。断点在 2.7.1 与 2.8.0 之间，定位在 `torch.matmul` 的 fp32 累加。**
> 「maxdiff 随 setup 变化」这句话里，**setup 连 torch 版本都算**。
> ⚠ **这个「拆一步」不是可选的**：不拆只能说「参照那条路径变了」，拆了才能说清是**哪一步**变的。

### 4.4 fp8 的溢出发生在**输出**，不在累加器

**现象**：以为 fp8 的 GEMM 会像 fp16 那样在累加过程中溢出。

**成因**：本机实测 fp8 的 `torch.mm` 累加是**高精度**的——输出与「把已量化输入升到 fp64 精确累加、再舍回 e4m3」**逐元素 100% 相等**（specs 的 `out_exact_fraction = 1.0`）。溢出发生在**最后一步 cast 回 e4m3**。

**规避**：把这一条当成一条**独立的边界**来测。判据：`x = [448×8, −448×7, 100]`，精确和 = **548 > 448**（e4m3 的上限）。

> ⚠ ★ **这一格的形态是版本相关的**：本机实测 **2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 输出 `nan`**，而 **2.13.0 输出 `448.0`（饱和）**——断点在 **2.11.0 与 2.13.0 之间**。这与同域 `numerical-formats` 记的断点是**同一次变更**（那里是 `.to()` 转换，这里是 `mm` 的**输出 cast**）。**写「torch 的行为是 NaN」就是版本无关地陈述版本相关的行为。**

### 4.5 以为 fp8 能像 fp16 一样逐元素算

**现象**：想验算 `448 + 448` 会不会溢出，直接写 `a + b`。

**成因**：本机 CPU 上 fp8 的**逐元素加法根本没实现**——抛 `NotImplementedError: "add_stub" not implemented for 'Float8_e4m3fn'`（2.6.0 上是 `RuntimeError`）。

**规避**：本机 CPU 上碰得到 fp8 的入口只有 `torch.mm` 与 `.to()`。要验累加行为，只能设计成矩阵乘的形式（本文的探针就是把向量变成 `(1,16) @ (16,1)`）。

### 4.6 把「约束会抛异常」当成一句话

**现象**：写「`qsz` 必须是 `[K//gs, N, 2]`，否则报错」。

**成因**：`_weight_int4pack_mm_for_cpu` 的**约束并不是齐的**。本机逐条实测：

| 约束 | 2.8.0 起 | 2.6.0 |
|---|---|---|
| `N` 被 16 整除 | 抛 `expect N to be dividable by 16` | 同 |
| `gs ∈ {32,64,128,256}` | 抛 `expect qGroupSize to be 32, 64, 128 or 256, got X` | 同 |
| `K` 被 `gs` 整除 | 抛 `expect K to be divisible by qGroupSize` | **不抛，静默跑过** |
| `qsz` 的 **ndim** | 抛 `expect qScaleAndZeros to be 3d tensor with sizes [:, N, 2]` | 同 |
| `w` 的 dtype = uint8 | 抛 `expect B to be uint8 tensor` | 同 |
| **`qsz` 的**主维** = `K//gs`** | **不校验**——主维过短出 NaN、过长给出静默错值 | 同 |

**规避**：把「会抛异常」与「不抛」分成两组写。**尤其是最后一条：它错了不报，只会静默出错。**

## 5. 实测数据

**测量条件**：Apple M1 Pro（10 核）/ macOS / **CPU-only，无 GPU 数字**；python 3.12.9；**torch 2.11.0**。五个解释器（2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 / 2.13.0）都跑过本篇的程序；`2.9 / 2.10 / 2.12` 本机无解释器。数值逐条记在 `code/specs.py`。

> ⚠ **本机没有 GPU。** 下表里凡标「引用值」的，**本仓库不复核其测量口径**。

### 5.1 `_weight_int8pack_mm` 与逐元素参照的偏差（**判据：每个形状独立播种 `torch.manual_seed(K)`**）

参照 = 先物化 `w * scales`（fp32）再走 `torch.matmul` —— **另一条代码路径**。

| `(M, K, N)` | maxdiff | 相对 `max\|ref\|` |
|---|---|---|
| (4, 32, 32) | 1.907349e-06 | 9.29e-08 |
| (4, 128, 64) | 2.288818e-05 | 4.29e-07 |
| (4, 256, 128) | 3.051758e-05 | 4.61e-07 |
| (8, 512, 256) | 6.866455e-05 | 5.27e-07 |
| (4, 1024, 64) | 1.220703e-04 | 8.48e-07 |
| (2, 8192, 32) | 6.866455e-04 | 2.55e-06 |
| (1, 131072, 16) | **1.739502e-03** | 2.20e-06 |

**⇒ 同一张表跨三个数量级。** 文档里写「与浮点参照一致到 **~1e-3 量级**（取决于 K 与 scale）」，**不得给单一固定值**。

> ⚠ ★ **换 torch 版本也会变，而变的是参照那一侧**（判据见 §4.3）：三条形状在 ≤2.7.1 上是另一组值——(4,32,32) **2.861023e-06**、(2,8192,32) **4.730225e-04**、(1,131072,16) **2.304077e-03**；被测算子的输出五版本逐位相同。
> 再把参照**拆一步**就把断点定死了：反量化那一步 `wq = w.float()*scales` 的 `.sum()` = **3.714967675507**、**五版本一致**；而 `(x @ wq.T)` 的 `.sum()` 变了 ⇒ **断点在 `torch.matmul` 的 fp32 累加，不在反量化**。

### 5.2 「不是精确整数累加」的探针

**判据**：`x = randint(1,5,(1,K)).float()`（全正、不抵消）、`w ≡ 127`、`scales = 1`；比较对象 = `float32(int64 精确和)`。

| `K` | 精确和 | 与 `float32(精确和)` 的差 | 相对偏差 |
|---|---|---|---|
| 2¹⁶ | 2.083257e+07 | 0 | 0 |
| 2¹⁸ | 8.323694e+07 | 4.8000e+01 | 5.767e-07 |
| 2²⁰ | 3.328514e+08 | **5.5072e+05** | 1.655e-03 |
| 2²¹ | 6.658035e+08 | 3.1724e+06 | 4.765e-03 |

**`_weight_int4pack_mm_for_cpu` 在同一判据下也偏**：K=2²⁰ 差 420（相对 2.289e-05）、K=2²¹ 差 1.7456e+04（相对 4.757e-04）。

> ⚠ **结论只能到「不是精确整数累加」这一层。** 具体是 fp32 还是别的宽度，本仓库没有独立通道——**不得断言**。

### 5.3 fp8 的 `torch.mm`（判据：`a, b ~ N(0,1)` 的 256×256，输入先 `.to(float8_e4m3fn)`）

| 量 | 值 | 判据 |
|---|---|---|
| 输出 dtype | `torch.float8_e4m3fn` | 仍是 fp8，不是 fp32 |
| 与「fp64 精确累加后舍回 e4m3」逐元素全等比例 | **1.0000** | 累加不丢精度、输出只舍入一次 |
| 输出 vs 量化输入后的精确积（平均相对误差） | **0.022674** | 分母 = 量化输入后的精确积 |
| 输入 cast 到 e4m3 的逐元素平均相对误差 | **0.024157** | 分母 = 原输入 |
| 全链路 vs fp64 原矩阵（平均相对误差） | 0.323179 | **判据不同**——见下 |
| 对照：同矩阵的 fp16 `mm` | 0.002525 | 同样 vs fp64 原矩阵 |

> ⚠ **0.323179 与 0.022674 / 0.024157 不是同一个量，不得并列**（P9）。前者的分母是全链路输出（随机符号下有大量接近 0 的元素，相对误差在那里被放大），后两者要么以「量化输入后的精确积」为分母、要么是逐元素输入误差。**结论是前者大 14 倍，而两者都对。**

### 5.4 fp8 输出溢出的边界（**版本相关**）

| 输入 | 精确和 | 2.6.0 / 2.7.1 / 2.8.0 / 2.11.0 | **2.13.0** |
|---|---|---|---|
| `[448×8, −448×7, 100]` | **548 > 448** | `nan` | **448.0（饱和）** |

**e4m3fn 没有 Inf 编码**（`0x7F`/`0xFF` 都给了 NaN）——所以越界的失败模式是 NaN / 饱和，**不是 inf**（那条是 e5m2 的事）。

### 5.5 累加器的算术（推导值，可复核）

| 项 | 值 | 判据 |
|---|---|---|
| int8×int8 单乘积上界 | 16129 / 16384 | `127×127` / `(−128)×(−128)` |
| int16 首次溢出的 `K` | **3** | `3 × 16129 = 48387 > 32767` |
| int32 首次溢出的 `K` | **133145** | `133144 × 16129 ≤ 2^31−1 < 133145 × 16129` |

## 6. 小结与延伸

- **int8×int8 的单乘积最大 16129** ⇒ int16 在 `K ≥ 3` 就溢出、int32 要到 `K ≥ 133145`。现实 K 最坏只占 int32 上限的 **3.08%–12.31%**（**判据：全部乘积同号**）。
- **这不只是工程惯例**：PTX 在指令层面把整数 MMA 的累加器钉成 `.s32`，cuBLAS / cuSPARSELt / DP4A 各有一条同样的规定。**指令集里不存在 int8 的 s16 累加变体。**
- **int32 累加器必须在 epilogue 先转 fp32 再乘 scale**：fp16 只能精确表示 ≤ **2048** 的整数，而 int32 在 `K = 133144` 时还精确——差 10 万倍。
- **epilogue 融合省下的是中间结果的写回**：一个独立反量化 pass 的**写是读的 4 倍**；融合后 fp16 权重永不落回 HBM。
- ★ **本机两个「整数量化」CPU 算子都不是精确整数累加**：K=2²⁰ 时精确和 3.33e8 远小于 int32 上限，实测却差了 5.5e5。⇒ **规范（`.s32`）与这个实现的行为是两件事。**
- ★ **maxdiff 连换 torch 版本都会变，而变的是参照那一侧**：三步拆开后，输出与反量化两步**五版本逐位不变**，只有 `torch.matmul` 那一步变了 ⇒ 断点定位在那里。
- ★ **fp8 的溢出在输出 cast，不在累加器**（累加是高精度的，逐元素 100% 等于 fp64 精确累加后舍回 e4m3）。而且**这一格的形态是版本相关的**：≤2.11.0 是 NaN，2.13.0 起饱和。
- ★ **fp16 的「三个上界」判据不同，不得捏成一句**：`2048`（连续整数的精确表示上界）、`1 → 2`（ulp，`.5` 用到的）、`65504`（最大有限值）。本机实测 `4096` 在 2048 之上**仍然精确**，而 `100000` 是**溢出**成 `inf`——两种不同的失败。

**延伸**：

- 本文的列和形式只在 **W8A8 的激活侧**成立。W4A16 那一侧的官方做法完全不同——见 `02-w4a16-packing`。
- 累加器的**数值分析**视角（`√K·u` 为什么成立、随机符号假设失效时退化为 `γ_K ≈ K·u`）在 `10-foundations/floating-point/04-low-precision-formats`。**本文只问「这种累加够不够支撑这个量化 kernel」，不复述那条推导。**
- `scale` 的粒度换算（per-tensor → per-channel → per-token 各自换回多少精度）在 `130-quantization/theory/02-granularity`。
- GEMM 本身的 tiling / 流水线 / split-K 在 `40-kernels/gemm`（**正文在本域，回链 `40-kernels`**）。
