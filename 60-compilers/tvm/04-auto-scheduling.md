# 自动调度：规则式与搜索式

> v0.26.0 里产生调度有**两条并列的路**：DLight 按**预定义规则**确定性地排（秒级、不用调），MetaSchedule **搜索一个空间**挑最好的（质量高、编译要几分钟到几小时）。两者都是在同一份 `s_tir` 计算上产生调度原语调用——差别是「**编译时间换性能**」这笔交易做不做。

## 0. 背景与动机

本文是主线上「**物化粒度**」这一维的判据来源。搜索空间里的 `tile` 大小是什么？就是**一次物化多大一块**：[02](02-schedule-primitives.md) 说 `compute_at` 把中间结果缩到父循环一次迭代的切片，而**切片有多大由 tile 决定**。所以「谁来定 tile」这个问题等价于「谁来定物化的粒度」。

具体场景：`C = (A+B)×2`，形状 `500×500`，搜索空间是 `(ti, tj)` 的 24 个组合。三条路：

| 路径 | 选出的 `(ti,tj)` | 测量次数 | 真实代价 |
|---|---|---|---|
| 规则式（查表） | `(1, 32)` | **0** | 294400 |
| 搜索式，模型**缺「向量化宽度对齐」这一项** | `(1, 500)` | **24** | **361217** |
| 搜索式，完美模型 | `(1, 64)` | 24 | **256000** |

（这三个「真实代价」由本仓库的迷你实现按本仓库定义的解析式算出，见 §5 的限定语。）

第二行是本文的重点：**多花了 24 次测量，结果比不测量的规则式更差**。

## 1. 原理

### 1.1 两条路的官方定位

官方教程（`docs/deep_dive/tensor_ir/tutorials/dlight_gpu_scheduling.py`）逐字：

> **MetaSchedule**: explores a search space to find the best schedule. **High quality, but compilation takes minutes to hours.**
> **DLight**: applies pre-defined scheduling rules **deterministically**. **No tuning required, compilation completes in seconds.**

两句话里的对比项是**编译时间**，不是运行性能。这决定了它们的适用面：一次性交付、形状固定、值得等 → 搜索式；形状多变、编译延迟本身就是用户体验 → 规则式。

### 1.2 搜索式三步：空间 → 模型 → 搜索

搜索式 = 三个部件相乘：

```text
候选集（空间）  ×  代价模型（给候选打分）  ×  搜索策略（按分数挑、按预算停）
```

**决定结果的常常不是搜索策略，而是代价模型**。原因是搜索策略只能从候选里挑，而候选的排序**完全由模型给**——模型把顺序排错，再好的搜索策略也只是更快地走到错的那个点上。

### 1.3 模型的错误不是随机的，是**有方向的**

把模型的错误当成噪声，会得出「多测几次就平均掉」的乐观结论。真实情况是：**模型缺一项，它就朝一个方向偏**。

设一条简化的代价式（本文配套程序用的就是这个，四项）：

```text
cost(ti, tj) = N_total
             × waste(ti, tj)     # 边界填充：块向上取整带来的多余工作量
             × occ(ti, tj)       # 占用不足：块数少于目标并发时惩罚
             × vec(ti, tj)       # 向量化宽度偏离最佳值的惩罚
             × reg(ti, tj)       # 寄存器/局部存储压力
```

**让模型缺掉 `vec` 那一项**（一个非常典型的缺口：模型训练数据里向量化宽度天然对齐，于是它学不到这一维），会发生什么？本机实测（§5）：

| 模型 | 选出的 `(ti,tj)` | 真实代价 | 与规则式比 |
|---|---|---|---|
| 缺 `vec` | `(1, 500)` | **361217** | **更差**（规则式 294400） |
| 完美 | `(1, 64)` | **256000** | 更好 |

原因很直白：缺 `vec` 之后，模型把 `tj=500`（几乎不填充、块数也够）看成最优——它的真实劣势**恰好全在 `vec` 项上**（`tj=500` 相对最佳宽度 64 偏离 2.97 个 log2 步）。模型看不到这一维，就把它推到了第一。

**这条是本域主线上「判据决定结果」的一个干净例子**：同一个搜索算法、同一个空间，**判据换一项，结论反过来**。

### 1.4 模型的排序能力比它的绝对值重要

搜索只需要**排序**，不需要准确的绝对值——它要的是「A 比 B 好」这件事别错。所以衡量模型质量的正确指标是**成对排序一致率**（pairwise comparison accuracy），不是回归误差。

本机实测：完美模型 `276/276 = 1.000`；缺 `vec` 的模型 `148/276 = 0.536`。**0.536 意味着它排对和排反的次数差不多**——用它引导搜索，和抛硬币的期望差不多。

（代价模型的完整形态、训练数据规模、损失函数，以及 Ansor 论文报的模型质量实测数字，**正文在 `60-compilers/auto-tuning/02-cost-models`，此处回链、不复制**——CONTRIBUTING §7.1：一个知识点只有一处正文。）

### 1.5 「空间更大」不构成「更好」

搜索式给人的直觉是「空间大 → 上限高」。**上限**确实更高，但**实际拿到的结果**不一定更好：候选集变大之后，模型评错的**机会也变多**。

本机实测（同一个缺 `vec` 的模型）：

| 空间 | 选出的配置 | 真实代价 |
|---|---|---|
| 全空间 24 个配置 | `(1, 500)` | **361217** |
| 先验裁剪后 20 个配置（去掉 `tj=500`） | `(1, 16)` | **332800** |

**把空间做大了 4 个候选，结果反而更差。** 把模型换成完美的，这条差别就消失（两边都是 256000）。所以「空间更大」这件事的**收益取决于模型质量**——没有模型质量这个前提，「扩大搜索空间」不是一个可以单独做的决定。

> **注意一个容易混淆的对照**：在**同一个模型、同一个空间**下，多测几个候选**不会**让结果变差（候选集不变、只是测得更多，最小值只会更小）。上面那条说的是**改动候选集本身**。「预算」与「空间」是两件事，别混——前者单调、后者不单调。

## 2. 执行映射

**位置**：两条路都作用在 `s_tir` 轨的计算上，产出的是**调度原语调用**（[02](02-schedule-primitives.md) 的那些）。native 轨（[03](03-native-track-and-tile-primitives.md)）没有这一层——那里的映射是手写的。

**MetaSchedule 的默认组件**（控制者基线给出，未落到具体文件路径）：

| 环节 | 组件 |
|---|---|
| 空间生成 | `PostOrderApply` |
| 搜索 | `EvolutionarySearch` |
| 代价模型 | **`XGBModel`**（梯度提升树） |
| 数据库 | `JSONDatabase` |
| 调度器 | `GradientBasedScheduler` |

**DLight 的规则库**按算子名分文件，可见的几组：`matmul` / `gemv` / `low_batch_gemv` / `general_reduction` / `reduction` / `rmsnorm` / `transpose` / `fallback`。注意最后那个 `fallback`——**规则库是有限的**，覆盖不到的算子走兜底路径。

**量级**（本机算例，测量次数不是墙钟）：规则式 **0** 次测量；搜索式 **24** 次测量（= 空间基数）。真实系统里这个差别被放大到官方说的「秒级 vs 分钟到小时」——**那两个时间口径是官方引用，本仓库不复核**。

## 3. 实现与演进

**第一代：手工调优（AutoTVM，已删除）。** 人为模板化的调度空间写参数模板，然后跑测量搜参。`from tvm import autotvm` 在 v0.26.0 上是 `ModuleNotFoundError`——AutoTVM 整体删除。

**第二代 / 并列的第一条路：规则式（DLight）。** 把「这个算子该怎么排」写成规则，按算子名查表，确定性地排。官方定位是「no tuning required, compilation completes in seconds」。

**并列的第二条路：搜索式（MetaSchedule）。** 空间生成 + 演化搜索 + 学习出来的代价模型，在编译期现场搜索。官方定位是「high quality, but compilation takes minutes to hours」。

**Ansor 的历史地位——这里有一处必须写清楚的措辞**：

- **Ansor 从来不是 TVM 里的一个 Python 模块**（仓库里没有 `python/tvm/ansor/` 这个目录）。**它是论文**：*Ansor: Generating High-Performance Tensor Programs for Deep Learning*，OSDI '20。论文提出的**两级搜索空间**（sketch + annotation）成了后来工程化的骨架。
- **「MetaSchedule 是 Ansor 的实现」是推断，不是引文。** TVM 的源码里没有这句话。能查到的是：MetaSchedule 由一份独立的 RFC（AutoTensorIR）提出，第三方文献用「**absorbs / unifies**」这类**等价**表述——**不是「改名」，也不是「工程化」**。本文按推断标注它。
- 搜索空间的构造细节（sketch 阶段的 derivation rules、**以及「sketch 阶段已经包含 fusion 决策」这条容易记反的事实**）正文在 `60-compilers/auto-tuning/01-search-space`；代价模型的形态与实测质量在 `60-compilers/auto-tuning/02-cost-models`。**本文只回链、不复制。**

**演进的方向**可以概括成一句话：**把「人写规则」换成「机器搜参数」，再换成「机器按规则排、只在值得的地方搜」**。DLight 与 MetaSchedule 并存而不是替代，正因为编译时间与性能之间的最优取舍取决于场景。

## 4. 踩坑与失败模式

三条。

**失败模式 1：以为「自动搜索」天然优于「手工规则」。**

- **现象**：把算子交给搜索式路径就默认它比规则式快；或者反过来，看到搜索式的编译很慢就以为它一定更好。
- **成因**：搜索的**上限**由空间决定，**实际结果**由代价模型决定。模型缺一项时，搜索会**系统性地**朝错的方向走——本机实测：缺「向量化宽度对齐」这一项的模型，24 次测量选出的调度真实代价 **361217**，而 0 次测量的规则式是 **294400**（§5）。注释里那条对照同样关键：把模型换完美，同一判据不再成立（256000 < 294400）——说明**问题在模型，不在「搜索」这个做法**。
- **规避**：评估一条搜索路径时要问三件事：**空间**长什么样、**模型**缺哪一维、**预算**多大。缺了模型那一问，另两问的答案没有意义。模型的排序能力可以用成对排序一致率量（本机实测：缺一项的模型 0.536，满分 1.000）。

**失败模式 2：把 MetaSchedule 说成 Ansor 的「改名/工程化」。**

- **现象**：写「Ansor 后来改名成 MetaSchedule」，或「Ansor 工程化之后就是 MetaSchedule」。
- **成因**：Ansor 是**论文**（OSDI '20），不是 TVM 里的模块——**TVM 源码里没有这句话**。能核到的是两者在组件层面的**对应关系**（空间 / 模型 / 搜索），第三方文献用的是「absorbs / unifies」这种**等价**说法。
- **规避**：写成**推断**并注明依据。这类「把对应关系写成谱系」的错误在本域反复出现：它读起来像结论，实际是转述者的加工。

**失败模式 3：把「搜得多就更好」当成单调关系。**

- **现象**：调不动性能时加大预算/扩大搜索空间，认为「多搜总能更好或者一样好」。
- **成因**：分两件事，方向相反：
  - **同一空间、更多预算**：单调（候选集不变，最小值只会更小或不变）；
  - **改动空间本身**：**不单调**——本机实测，把空间从 20 个候选扩到 24 个（加入 `tj=500`），同一个模型的选出结果真实代价从 **332800 恶化到 361217**。
- **规避**：把「扩大空间」当成一次**与模型质量绑定的**决定，而不是免费的收益。另外，**「搜到多少个配置后收益饱和」这个问题在本仓库没有可引用的定论**——不要写区间、不要给拐点：能引的只有具体论文在其基准上的实验设置，那部分正文在 `60-compilers/auto-tuning/03-search-algorithms` §5，本文不复制。

## 5. 实测数据

**测量条件**：`code/04_scheduling_paths.py` 在本机 `python3 3.13.5` + `numpy 2.4.4` 上跑出的结果，`cd code && make run` 退出码 0，本篇 **19 条断言（A 4 / B 10 / C 5）**。

> **★ 限定语（本域强制）**：下面每一个数字都是**本仓库的迷你实现**跑出来的，**不是 TVM 的 DLight 或 MetaSchedule**。这里的「代价」是一个**本仓库定义的解析式**（四项相乘），「测量」是**函数调用计数**——**本程序不产出任何时间数字**。这些数字支持的是「代价模型的盲点会怎样改变搜索结果」这类**机制**结论。

**算例**：`C = (A+B)×2`，`500×500`；空间 `TI = {1,2,4,8} × TJ = {16,32,64,128,256,500}`，共 **24** 个配置（次序冻结）。

**三条路**（A 类：三条路选出的调度各自执行，与独立 numpy 参考的最大误差都是 `0.000e+00`；规则式两次调用给出同一配置）：

| 路径 | 配置 | 测量次数 | 真实代价 | 实测填充元素数 |
|---|---|---|---|---|
| 规则式（查表） | `(1, 32)` | **0** | 294400 | 256000 |
| 搜索式（缺 `vec`） | `(1, 500)` | **24** | **361217** | 250000 |
| 搜索式（完美模型） | `(1, 64)` | 24 | **256000** | 256000 |

「实测填充元素数」由 `run_tiled`（与参考实现代码路径完全不同的分块执行器）真的跑出来，与解析式 `bi·ti·bj·tj` 逐行一致。

**模型的排序能力**（276 对）：

| 模型 | 成对排序一致率 |
|---|---|
| 完美（按真值排序） | **276/276 = 1.000** |
| 缺 `vec` 项 | **148/276 = 0.536** |

**C 类**

| 检查 | 结果 |
|---|---|
| C1：缺 `vec` 的模型选出的真实代价 vs 规则式 | **361217 > 294400**（搜索更差） |
| C1 对照：完美模型 | 256000 < 294400（**同一判据不再成立**——C1 检验的是模型，不是地形） |
| C3：全空间（24）vs 裁剪后（20），同一模型 | **361217 > 332800**（空间更大反而更差） |
| C3 对照：完美模型 | 两边都是 256000（不成立） |
| C4：把搜索式的测量次数记成 1 | 1 ≠ 实测 24，**失配** |

> **C1 / C3 的对照栏是刻意加的。** 这两条断言的对象是**地形 + 模型**的组合，构造地形的人可以无意识地「造出会通过的地形」。按本域纪律（§0.4 第 5 条），这类断言**必须能因为「把被检验的那一方换成正确的」而失败**：
> **C1 在把模型换成完美模型后不成立**，**C3 同样在完美模型下不成立**——两条对照都跑出来了（见上表），所以它们检验的是**模型**，不是地形。

**第一版被推翻的两项**（一项在设计阶段、一项被实跑改写，分开标注——本项目要求「跑出来的」与「推出来的」不混）：

1. **（设计阶段推翻，没跑）「半预算 vs 全预算」那条对照逻辑上恒真。** 第一版想用「预算减半 vs 全预算」演示「搜得多 ≠ 更好」，写代码前就发现它**不可能失败**：同一个模型下，子集搜索的最小值不会优于超集搜索的最小值（子集 ⊆ 超集）。按本域纪律（§0.4 第 4 条：断言必须能因实现改错而失败），这条属于**恒真的假断言**，删掉换成「**空间扩大 vs 空间裁剪**」——改动的是候选集而不是预算，才有真实的非单调性。**这条虽然没跑，但它与 Chunk 5 C3 被审查推翻的是同一类错误。**
2. **（实跑改写）裁剪后空间会选中哪个配置，第一版猜错了。** 我预期裁剪掉 `tj=500` 之后，缺 `vec` 的模型会选中 `(1,64)`（真实代价 262144）。实跑选中的是 **`(1,16)`（真实代价 332800）**：模型对 `(1,16)`、`(1,32)`、`(1,64)`、`(1,128)`、`(1,256)` 这几项给出的分数**完全并列**（都缺 `vec`，都无额外惩罚），而 `min` 取的是**枚举次序在前**的那个——也就是 `tj` 最小的那个。C3 的结论（更大反而更差）仍然成立，但**成立的方式和我预想的不一样**：不是「模型偏好大 tile」，而是「模型在这一维上根本分不出好坏」。这条只能靠跑出来。

## 6. 小结与延伸

- v0.26.0 有**两条并列的自动调度路径**：DLight（规则、确定性、秒级）与 MetaSchedule（搜索、分钟到小时）。官方对比的是**编译时间**。
- MetaSchedule 的默认组件：`PostOrderApply` + `EvolutionarySearch` + **`XGBModel`** + `JSONDatabase` + `GradientBasedScheduler`。
- **Ansor 是论文不是模块**；「MetaSchedule 是 Ansor 的实现」是**推断**，不是引文。
- 搜索式的结果由**代价模型**决定；模型缺一项会**朝一个方向**偏。本机实测：缺「向量化宽度对齐」的模型，24 次测量比 0 次测量的规则式更差（361217 vs 294400），排序一致率 0.536。
- **扩大搜索空间不是免费的**（332800 → 361217）；而同一空间内加预算是单调的。两件事别混。

**延伸**：

- 搜索空间怎么被构造出来（Ansor 的两级结构、sketch 阶段已含 fusion 决策） → `60-compilers/auto-tuning/01-search-space`（**正文在那里，此处回链**）
- 代价模型的完整形态与模型质量实测 → `60-compilers/auto-tuning/02-cost-models`（回链）
- **Ansor 论文的全部可引数字（搜索成本表、加速比、模型质量）的唯一正文位置** → `60-compilers/auto-tuning/03-search-algorithms` §5（回链，本文不复制）
- 被这些调度作用的那两条轨道 → [03-native-track-and-tile-primitives](03-native-track-and-tile-primitives.md)
- 「人怎么找瓶颈、怎么定参、怎么测」属于测量方法论 → `50-performance/tuning-practice`（正文在上游，此处回链）
