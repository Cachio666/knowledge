# 迭代级调度：continuous batching 的机制与收益来源

> **一次调度决策的单位从「整批」缩到「一步」，就多出一样东西：一个可以被算出来的间隙。**
> 本文要论证的是 —— **`continuous batching` 的收益来自【长度方差】，不来自【到达过程】**；
> 而这两句话的分量不同：**前半句有公式，后半句是做实验才敢说的话**。
>
> ★★★ **定义不在本文**：`continuous batching` 与 `chunked prefill` 的**定义**在
> `10-foundations/performance-models/01-roofline-model.md:251`（括注定义），本文**只回链**。
> ★★ **prefill / decode 的 kernel 差异**（两者的 `AI` 差 120 倍）在
> `40-kernels/attention/05-decoding-attention.md:229-236` —— 也**只回链**。
> **本文写的是它们的【机制与收益来源】。**
> ★★★ **本层是【推理性调度器】**。**「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无 vLLM、无 ORCA**（实测，见计划 `§0.7 A`）。
> ORCA 是 `iteration-level scheduling` 这个术语的出处（OSDI '22，`[C]`）——
> ★ **本域**不得把「迭代级调度」写成 vLLM 造的词。

## 0. 背景与动机

### 一个具体的对照场景

`N = 200` 条请求、每条要生成 `L = 100` 个 token、批上限（**在飞请求数**）`B = 32`、
**同时到达**。两种调度：

- **静态批**：凑够 `B` 条一起跑，**整批等最长的那一条**，该批全跑完才换下一批；
- **连续批（迭代级）**：每**一步**重新填批 —— 谁跑完了，它的槽位**当步**就让给下一条。

`200` 条 `100` token 的请求，`32` 个槽位：

| 调度 | makespan | ★ 说的一句话 |
|---|---|---|
| **连续批** | **`700.0`** | 每步 32 条并发，共 `⌈200/32⌉ = 7` 批 |
| **静态批** | **`700.0`** | **等长时两者完全相同** |
| **逐条处理**（`B=1`） | `20000.0` | 一次一条 |

★★★ **等长这一档里，连续批**相对静态批的**收益是 `1.0000×`**（程序 `B.2` 第一行）。
⇒ **「连续批一定更快」在这里是假的** —— 收益要看下面 §1 的那个间隙。

### 为什么值得算这笔账

推理的时间表上，**请求是不断进出**的：这一层多出来的开销全部落在**调度**上。
而调度决策的代价是**可算的** —— 本文把它算成**一个闭式**，
★ 算出来的是**机制与上界**，不是任何真实系统的性能。

## 1. 原理

### 第一步：把「一步」写成一个式子

设：请求数 `N`、每条长度 `L`、批上限 `B`、**同时到达**。连续批的排程规则是：

- 每步开头，**在飞数 `< B`** 的请求按到达序填入；
- 每个在飞请求**每步恰好产出 1 个 token** ⇒ 长度为 `L` 的请求耗 `L` 步。

**等长 + 同时到达**时，前 `B` 条**同时开始、同时结束**（都耗 `L` 步），
于是它们**同时**腾出槽位 ⇒ 下一批 `B` 条**同时开始**。所以：

```
makespan = ⌈N / B⌉ × L                              (1)
```

### 第二步：把 (1) 重写成「总量 + 间隙」

`N` 条 × `L` 步 = `N·L` 个「槽位·步」的工作量，`B` 个槽位并行 ⇒ **理想耗时 `N·L/B`**。
而 (1) 通常比它大，**差的就是最后一批没填满的部分**：

```
记  r = N mod B
间隙 = 0                        （r = 0：最后一批刚好填满）
间隙 = (B − r) × L / B          （r ≠ 0：最后一批只装了 r 条）

makespan = N·L / B + 间隙                            (2)
```

★ **等价性**：`N·L/B + (B−r)L/B = ((N−r)L)/B + L = ⌊N/B⌋·L + L = ⌈N/B⌉·L`。
⇒ **(2) 不引入新假设，它只是 (1) 的另一种写法** —— 但这一写法**把间隙显式化了**。

### 第三步：为什么这一写法有用 —— 间隙是有名字的

**间隙的读法**：`B` 个槽位里**有 `B − r` 个在最后一步是空的**。

| 情形 | 间隙 | 程序里的值 |
|---|---|---|
| `N = 200, B = 32`（`r = 8`） | `(32−8)×100/32 = 75.0` | makespan `625 + 75 = 700.0` |
| `N = 1, B = 32`（一个请求占不满一批） | `(32−1)×100/32 = 96.875` | makespan `100.0`（= `N·L/B` + 间隙） |
| `B \| N`（如 `N=32, B=32`） | **`0`** | makespan `100.0` |

★★ **三行都被程序 `A.2` 逐字钉住**（含中间那一行 `N=200, B=32 ⇒ 75.0`；两端是**免费的守卫**：
`B | N ⇒ 间隙 0`、`N = 1 ⇒ 间隙 (B−1)L/B`）—— ★ 只钉两端会让中间行**无人看管**。
★ 程序在 `N ∈ {1,7,32,100,200}` × `B ∈ {8,16,32,64}` 的 **20 档**上，
**逐 token 步推进的模拟器**与闭式 (2) **逐位一致**（`A.1`）。

### 第四步：间隙是怎么变成收益的

★★★ 上面三行全部假设**等长**。**一旦长度不等，(1) 就不成立了** —— 因为一批里的 `B` 条
**不再同时结束**，腾出的槽位是**零散**的：

- **等长**：每批**只有最后一批**没填满 ⇒ 只**一个**间隙；
- **有方差**：**每一批**都可能没填满 ⇒ **间隙按批数累积**。

★★ 这就是 `B.2` 那张表的机理（下面 §5 有全部数字）：

| 长度分布（同均值 `110`） | 连续批 / 静态批 |
|---|---|
| **等长** `100` | **`1.0000×`** |
| **均匀** `20–200` | **`1.6460×`** |
| **指数**（重尾，均值 `110`） | **`2.8135×`** |

★★★ **读法**：**收益的【主因】是长度方差** —— 等长时连续批与静态批**没有差别**；
方差越大，静态批「等最长」浪费得越多。

### 第五步：那「到达过程」呢？—— ★★★ 这里必须做实验，不能推理

「连续批处理的是**到达**，不是一批固定请求，所以到达的**节奏**也该有影响」——
★ 这个推理**听起来对，实测不对**。程序 `B.3` 把长度**固定成等长**、只改到达过程：

| 到达过程 | 连续批 / 静态批 |
|---|---|
| **同时到达** | `1.0000×` |
| **泊松 `λ = 8`**（远快于处理：处理速率 ≈ `0.32` / 时间单位） | `1.0039×` |
| **泊松 `λ = 1.2`**（仍高于处理速率） | `1.0310×` |
| **突发到达**（每 `32` 条一波、周期 `32`） | **`1.0000×`** |

★★★ **四条全部 ≈ `1.00×`** —— 与长度方差那三个档（`1.65–2.81×`）**不在一个量级**。
⇒ **收益不来自到达过程。**

★ **一条反例、也是唯一的例外**（程序 `C.3`）：**突发的【粒度】小于批上限**时会出现 `> 1`
（`S = 16 < B = 32` ⇒ `1.0229×`，而 `S = 32 ≥ B` ⇒ `1.0000×`）。
★★ **但那是同一个间隙**：静态批要**等下一波突发**才凑满一批 ——
★ 它**不随「到达过程的方向」单调**，与长度方差的机理**不是同一件事**。

## 2. 执行映射

引擎层。**请求调度器**（`§2.2`：本域不裸写 `scheduler`）每一步做两个决定：
**谁能进**（`len(inflight) < B` 且已到达）与**谁能走**（本步产出 token 的请求）。

**（1）三个量级**（本文程序里的算例，`[E]` 级）：

| 组件 | 本文的量级 |
|---|---|
| **在飞请求数上限** | `B = 32`（模型的「批上限」） |
| **一步的代价** | 每步每请求推进 1 个 token（`dt=1.0`，模型单位） |
| **makespan 的两项** | `Σlen/B`（总量）+ 间隙（最后一批没填满） |

**（2）收益的**分母**不止一个 —— ★★★ 这是本文最要紧的一条**（程序 `B.4`）：

| 基线 | 连续批的加速比（同一组请求：均匀 `20–200`、`N=200`、`B=32`） |
|---|---|
| **逐条处理**（`B = 1`） | **`27.80×`** |
| **静态批**（`B = 32`） | **`1.65×`** |

★★★ **同一个 continuous batching，两个加速比差 `16.9` 倍。**
⇒ **不写基线，「提升 N 倍」没有信息量。**
★★ 文献里的两个数**同样**必须连出处与基线一起写：

| 数字 | 归属 | 级别 |
|---|---|---|
| **`36:9×`** | **ORCA（OSDI '22）论文** —— 对比 NVIDIA FasterTransformer；★ **原文如此**（**冒号**，非小数点，应读作 `36.9×`） | `[C]` |
| **`23x`** | **不是 ORCA** —— vLLM 首页「进一步阅读」引的一篇**博客** | ★ **双标注**（`F1`）：**数字出处 `[D]`** + **载体 `[B]`**（vLLM 官方文档首页） |

★★★ **它们是【引用值】：基线是各自论文/博客的条件，与本机模拟器无关，不得写成实测**（`F4`）。

**（3）★★ vLLM 的批参数【没有单一默认值】**（`[B]`）—— 类常量 `2048` / `128` 只是**兜底**，
真实默认由 `get_batch_defaults()` 按**设备显存档 × 场景**覆盖，`throughput` 模式再各自翻倍
⇒ ★★★ **引用时必须带设备与场景**（★ 只引 `128` 会把 A100 上 API server 的真实值 `256` 写成 `128`）。

★★★ **这张表的【正文】在** [120-inference/engines/01-vllm](../engines/01-vllm.md)`（**正文在彼处，此处只回链**，`CONTRIBUTING` §7）；
★★ 本主题仍保留一条**程序侧**的钉住（`D.6`），★ 但**表格正文不在此重复**（★ 收拢是**有意的**：它是 **vLLM 专有的配置面**，
去掉引擎层即消失 ⇒ 归**引擎层**）。

**（4）★★ 这条链的产物是「机制与上界」，不是「真实性能」。**
上面的数**没有一个**来自真实系统。★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：静态批。** 凑够 `B` 条一起跑，整批等最长。
★ 代价：**最后一批**（以及长度不等时的**每一批**）没填满的那些槽位。

**第二步：迭代级调度（continuous batching）。** 每步重新填批。
★ 本文的算例：等长时 **`1.0000×`**、有方差时 **`1.6460×`**、重尾时 **`2.8135×`**。
★★ **第一步是关键**：**收益不是来自「请求能进出」这件事本身**，
而是来自**腾出的槽位立刻被别人用上** —— 而**只有当长度不等时槽位才是零散腾出的**。

**第三步：chunked prefill。** 上面两步管的都是**一个 token 一步**的 decode。
**长 prompt 的 prefill** 与 decode **混跑**时，会**独占整步** —— 那是下一篇：
[02-chunked-prefill](02-chunked-prefill.md)。★ 它把「一步里放什么」写成一个**分块数 `k` 的权衡**（`k* = ⌈t_p/t_d⌉`）。

★ **一条同名不同指的消歧**（`§2.2`）：**「静态批的填充浪费」** ——
`1 − 均值/最大值` 这个**式子**在 `40-kernels/moe-kernels/02-grouped-gemm.md:89` 已经推过
（那是 MoE **一个批内的槽位/算力**浪费）。★★ **本文不重算它**，
只指出：**同一个式子描述的在这里是「静态批等最长」在【时间】上的浪费** —— ★ **同式不同指**。

## 4. 踩坑与失败模式

### 4.1 ★★★ 实验设计里，被测量的那个因素根本没有进入路径

- **现象**：一个「到达过程影响很大」的结论，重做实验后**不成立**；
- **成因**：参照实现（静态批）**忽略了到达时间** —— 它只按长度切批，
  ⇒ ★★ **「到达过程」在整个实验里从未被激活**，而实验者据此写出了关于它的结论；
- **本机实测**（`code/` 的 `C.1`）：**忽略到达**的静态批对**同时到达 / 突发 / 泊松**
  三种到达过程给出**同一个数**（`700.00 / 700.00 / 700.00`）；
  **尊重到达**的版本给出 `700.00 / 716.00 / 725.24` —— **因素这才被激活**；
- **规避**：★★★ **归因前先做消融** —— **把声称的原因关掉，看结论是否真的变**。
  ★ 这与「把参照故意改错、断言必须失败」（`CONTRIBUTING:235`）是**同一个操作**，
  只是对象从「断言」换成「实验因素」。★★ 这条在本库有编号：**错误模式 `P38`**
  （它是**错误模式 `P12`**「自证」在**实验设计层**的形态）。

### 4.2 ★★★ 不写基线就报加速比

- **现象**：「continuous batching 带来 `X` 倍提升」——而 `X` 可以是 `1.65` 也可以是 `27.80`；
- **成因**：加速比的**分母没写**。同一件事对**逐条基线**是 `27.80×`、对**静态批基线**是 `1.65×`；
- **本机实测**（`code/` 的 `B.4`）：两个**同一组请求**的加速比差 **`16.9` 倍**；
- **规避**：★ **凡「X 带来 N 倍」的句子，必须写明【基线】**；★★ 引用别人的数
  （ORCA 的 `36:9×` / `23x`）**还要写明出处与条件**。★ 本库编号：**错误模式 `P9`**。

### 4.3 把「到达过程」当收益来源

- **现象**：认为「请求是流进来的，所以到达的节奏影响很大」；
- **误用场景**：★ 压测里**只改到达速率 `λ`**（其余全不动），看到吞吐变化就归因给「流式到达」——
  ★ 而那个变化来自**系统饱和与否**，与到达的**过程**（同时 / 泊松 / 突发）**无关**（`B.3` 四档全 `≈1.00×`）；
- **成因**：★ 忽略了**只有长度不等时槽位才是零散腾出的**；
- **本机实测**（`code/` 的 `B.3`）：泊松两种速率与突发到达都在 `1.00–1.03×`；
- **规避**：★★ **一次只改一个因素**（本文的长度分布与到达过程是**分开测的**），
  ★ 并**用等长档做控制变量**（`1.0000×` 是那个「什么都没发生」的基准）。

### 4.4 认为「到达过程的方向」能解释突发粒度的 `> 1`

- **现象**：看到突发粒度小（`S < B`）时收益 `1.0229× > 1`，就把它归给「到达过程」；
- **成因**：它其实是**静态批要等下一波突发才凑满一批** —— ★ 还是**同一个间隙**；
- **本机实测**（`code/` 的 `C.3`）：`S ≥ B` ⇒ **恰好 `1.0000×`**；`S < B` ⇒ `1.0229×`；
- **规避**：★ **改一个因素时把另一个因素钉在极端** —— 这里把**突发粒度与批上限的关系**
  写成判据，`> 1` 立刻有了归属。

## 5. 判据表

| 可机械判定的条件 | 结论 |
|---|---|
| 见到「等长 + 同时到达」的调度时间 | ★★★ 直接用闭式 `makespan = N·L/B + 间隙`，`间隙 = (B − N mod B)·L/B`（`B∤N`；否则 0）；已在 **20 档**上与模拟逐位一致（`A.1`） |
| 见到「间隙」这个词 | ★★ **它来自「最后一批没填满」** —— **不是**到达过程（`A.3` 给出恒等式 `闭式 == ⌈N/B⌉·L`） |
| 见到 `B \| N` | ★ 间隙 **恰好 `0`**（免费守卫，`A.2`） |
| 见到 `N = 1` | ★ 间隙 **`(B−1)L/B`**（一批只装一个，`A.2`；`B=32` 时是 `96.875`） |
| 见到「任何调度器的 makespan」 | ★★★ 必须 **`≥` 下界** `max(Σlen/B, 最后到达 + 其长度)`（`B.1`；等长档：静态批 `700.0` vs 下界 `625.0`） |
| 见到「连续批比静态批快 N 倍」 | ★★★ 先问**长度有没有方差** —— 等长时是 **`1.0000×`**（`B.2`） |
| 见到「泊松 / 突发到达让连续批更快」 | ★★ **不成立**：`1.00–1.03×`（`B.3`）；★ 唯一的例外是**突发粒度 < 批上限**（`1.0229×`），而那**仍是间隙**（`C.3`） |
| 见到一个「加速比」 | ★★★ **必须写明基线**：逐条处理 `27.80×` vs 静态批 `1.65×`（差 `16.9` 倍，`B.4`）；★★ 引用 ORCA 的 `36:9×`（**原文如此**，应读作 `36.9×`）/ `23x` 还要写出处（ORCA `[C]` / 博客 `[D]`） |
| 见到「到达过程影响很大」的实验 | ★★★ 先做**消融**：把参照实现里的到达时间**关掉**，看输出**变不变**（`C.1`；**错误模式 `P38`**） |
| 见到 `B ≥ N` | ★ 一批装完 ⇒ `makespan == L`（`C.2`）；空输入 ⇒ `0.0` |
| 见到「vLLM 的 `max_num_seqs` 默认值」 | ★★★ **没有单一答案**（兜底 `128` 会被**设备/场景**覆盖）——**必须带设备与场景**；★★ **取值表的正文在** [engines/01-vllm](../engines/01-vllm.md)（**正文在彼处，此处只回链**；★ 程序侧 `D.6` 仍钉住） |

## 6. 小结与延伸

**一句话**：**迭代级调度把「调度单位」从整批缩到一步，多出来的那点东西叫【间隙】；
而间隙只在【长度不等】时才累积成收益 —— 到达过程几乎不起作用。**

**三条可独立复用的结论**：

1. ★★★ **间隙闭式**：`makespan = N·L/B + (B − N mod B)·L/B`（等长 + 同时到达），
   ★ **两端免费守卫**：`B|N ⇒ 间隙 0`、`N=1 ⇒ (B−1)L/B`；
2. ★★★ **收益来自长度方差**：等长 `1.0000×` / 均匀 `1.6460×` / 指数 `2.8135×` ——
   等长时**两者没有差别**；
3. ★★★ **基线必须写**：同一件事对**逐条**是 `27.80×`、对**静态批**是 `1.65×`（差 `16.9` 倍）。
