# 抢占与公平：换出还是 KV 重算

> **显存不够时要踢掉一个请求，踢的方式有两种：把它的 KV 搬出去、或者把它丢掉以后（需要时）走 KV 重算。**
> **两种都「可算」** —— 而它们的交点是一个**长度**，不是一句「视情况而定」。
> 而公平那一半的结论更反直觉：**「饥饿」是【动态到达】的属性，不是【排序】的属性。**
>
> ★★★ **术语（`§2.2` 的第三义）**：本域的 **`KV 重算`**（抢占时丢掉 KV、需要时把它重跑一遍）与
> **编译器**的「物化 vs 重算」、**训练**的「重算换显存」（gradient checkpointing）
> **同名不同指** —— 本文**一律写「KV 重算」全称**。
> ★★★ **本层是【推理调度器上的两笔账】**。**「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无引擎**（实测，见计划 `§0.7 A`）。

## 0. 背景与动机

### 一个具体的对照场景

显存被占满，**请求调度器**要腾出空间。它踢掉一条长度为 `s` 的序列，有两种做法：

| 做法 | 代价 |
|---|---|
| **换出（swap）** | 把这段 KV **搬出**到主机内存，以后**搬回** ⇒ `2 × s × bpt / BW` |
| **KV 重算（recompute）** | 把这段 KV **丢掉**，需要时把这段 prefill **重跑一遍** ⇒ `s·τ_lin + s²·τ_quad` |

★ 两者的**形状不同**：换出按 `s` **线性**涨，KV 重算里**自注意力那项按 `s²` 涨**。
⇒ ★★★ **两条线会交于一点**（本文算例：`s* = 4000`）：

| `s` | 换出 | KV 重算 | 谁更便宜 |
|---|---|---|---|
| `256` | `8.3886` | **`5.3292`** | **KV 重算** |
| `512` | `16.7772` | **`11.0768`** | **KV 重算** |
| `2048` | `67.1089` | **`54.3482`** | **KV 重算** |
| **`4000`** | **`131.0720`** | **`131.0720`** | **相等** |
| `8192` | **`268.4355`** | `378.0515` | **换出** |
| `16384` | **`536.8709`** | `1184.5260` | **换出** |

★★ **读法**：**短序列 KV 重算、长序列换出** —— ★ 因为 **KV 重算**的注意力项按 `s²` 涨，
而换出只按 `s` 涨。★ 全部数字由 `code/03_preemption_and_fairness.py` 算出并被断言钉住（`A.1`/`B.1`）。

### 公平那一半的对照场景

6 个作业同时到达，服务时间（按到达顺序）`(7, 2, 9, 4, 1, 5)`。
**FCFS**（按到达序）与 **SJF**（最短优先）两种顺序：

| 策略 | 平均完成时间 | 最大等待 |
|---|---|---|
| **FCFS** | `17.8333` | `23.0` |
| **SJF** | **`11.6667`** | **`19.0`** |
| **穷举最小**（`6! = 720` 个顺序） | **`11.6667`** | — |

★★ **SJF 恰好等于穷举最小值**（程序 `A.4`），而且**最大等待也不比 FCFS 差**。
★ **穷举用一份【独立】的目标函数**（`avg_completion_alt`），不与 SJF 共享 `avg_completion` ——
★ 于是「目标函数本身写错」不会让两者**一起错**（`D.8` 在源码层核）。

### 为什么值得算这两笔账

推理是**请求不断进出**的一层：**显存不够 ⇒ 必须抢占**；**多个租户 ⇒ 必须公平**。
★ 这两件事在别处常被写成「要视情况而定」—— 本文把它们**各写成一个可算的量**。

## 1. 原理

### 第一步：两笔代价

★★★ **模型假设（必须写明）**：

```
换出     swap(s)      = 2 · s · bpt / BW                (1)
KV 重算  recompute(s) = s · τ_lin + s² · τ_quad         (2)
```

- `bpt` = 每 token 的 KV 字节（**取用** `130-model-optimization/quantization/18-kv-cache-basics` 的 `512 KiB`，**不重推**）；
- `BW` = **单向、载荷口径**的搬运带宽（★ 三种口径的正文在
  `20-gpu-architecture/interconnect/01-bandwidth-conventions.md`，**本文只回链**）；
- ★★ **(1) 里的 `×2` 就是「搬出 + 搬回」两个方向** —— 这是本文最容易错的一处（§4.1）；
- `τ_lin` = 每 token 的**线性**成本（矩阵乘 / MLP）；`τ_quad` = 每 token² 的**自注意力**成本。

★★ **`(2)` 的第二项是「长度临界点」的唯一来源**：把它取 `0`，两条线就**不再交叉**（`D.5` 的守卫实验）。

### 第二步：解出临界长度

令 `(1) = (2)`（两端都有因子 `s`，约掉）：

```
2·bpt/BW = τ_lin + s·τ_quad
⇒  s* = (2·bpt/BW − τ_lin) / τ_quad                    (3)
```

本文算例：`2·512KiB / 32 GB/s = 0.032768`、`τ_lin = 0.02`、`τ_quad = 3.192×10⁻⁶`
⇒ **`s* = 0.012768 / 3.192×10⁻⁶ = 4000.0`**。

★★★ **方向**（程序 `A.2` 两侧都断言）：

| `s` | 结论 |
|---|---|
| `s < s*` | **KV 重算更便宜** |
| `s > s*` | **换出更便宜** |

★ 程序用**两条独立路径**验证 `s*`：闭式 `(3)`，以及**在账本上二分**找
「换出 − KV 重算」**变号**的地方（落点 `4000`，与闭式相差 ≤ 1）。

### 第三步：临界带宽 —— 另一个独立的旋钮

固定 `s`，反解 `(3)`：

```
BW* = 2·bpt / (τ_lin + s·τ_quad)                        (4)
```

本文算例（`s = 1024`）：**`BW* = 45,063,976 B/ms`**。
★★ **方向**（`A.3`）：带宽**减半 ⇒ KV 重算更便宜**；带宽**加倍 ⇒ 换出更便宜**。

★★★ **读法**：**「长度」与「带宽」是两个彼此独立的旋钮** ——
★ 一个改 `s`、一个改 `BW`，但**它们乘在同一个不等式里**（`(3)` 的分子）。
⇒ ★ **判断口径必须写清**：`BW` 是单向还是双向、是线速率还是载荷口径（三种口径差 `2` 倍）。

### 第四步：公平 —— 用一个最优性判据代替「视情况而定」

给一组**服务时间**和一个**处理顺序**，**平均完成时间**：

```
平均完成时间 = (1/n) Σ (第 i 条的完成时刻)
```

★★★ **SJF（最短作业优先）最小化平均完成时间** —— ★★ **前提有四条**（缺一不可）：
**非抢占** · **全部作业同时可用**（静态集合） · **单机** · **目标 = 平均完成时间**。
★ **有抢占时 SJF 不最优**（那是 SRTF 的地盘，见第五步；★ 而且它还会引入饥饿）。
程序 `A.4` 用**穷举**验证：`n = 6` 时 **`6! = 720` 个顺序**里，SJF 的结果**恰好是最小值 `11.6667`**。
★ **参照是穷举** —— 它**不共享任何启发式**（不排序、不贪心）。

★★ **一条容易误读的性质**（`B.2`）：在**静态集合**（同时到达、没有新请求）上，
**SJF 的最大等待也不比 FCFS 差**（`19.0 ≤ 23.0`）。
⇒ ★★★ **「SJF 会饿死长作业」在静态集合上不成立** —— 饥饿是**动态**属性（第五步）。

### 第五步：饥饿 —— 只在【持续到达】时出现

让**长作业**（服务 `100000`）在 `t = 0` 到达，**短作业**（服务 `3`）每单位到一条。
**抢占式最短剩余时间（SRTF）**下录长作业的**开始时刻**：

| 短作业条数 `K` | 长作业开始时刻 |
|---|---|
| `10` | `30` |
| `100` | `300` |

★★★ **长作业的开始时刻沿「每来一条短作业后移 `3`」线性增长** ⇒
★ **到达不停则等待无界** = **饥饿**。
★★ **而静态集合上完全看不到这个现象**（`B.2` 里 SJF 的最大等待反而更小）——
⇒ ★★★ **「饥饿」是【动态到达】的属性，不是【排序】的属性**。

## 2. 执行映射

引擎层。**请求调度器**面临三类决定，本文各给一笔账：

| 决定 | 本文的账 |
|---|---|
| **重排序**（谁能先跑） | ★ **SJF 最优**（`A.4`，穷举证明；★ 前提见 §1 第四步：**非抢占 · 同时可用 · 单机 · 平均完成时间**）—— ★ **重排序本身就是「按服务时间排序」** |
| **抢占谁 / 怎么踢** | ★★★ **换出 vs KV 重算** —— 临界长度 `s*`（`A.2`）与临界带宽 `BW*`（`A.3`） |
| **优先级与 SLO** | ★★ **持续到达下低优先级会饥饿**（`C.4`）—— 长作业的**尾延迟**因此**无界** |

**（1）三个组件**：

| 组件 | 动作 | 本文的量级 |
|---|---|---|
| **代价账** | 逐块累加搬运字节 / 逐 token 累加 **KV 重算** | `s* = 4000` |
| **重排序** | 按服务时间排序 | `6! = 720` 个顺序里取最小 |
| **抢占** | 按 `s*` 逐条选更便宜的那一边 | 总代价 `1030.96`（vs 固定策略 `1062.21` / `1788.23`） |

**（2）★ 三种抢占策略的总代价**（程序 `B.1`，同一组长度 `{256…16384}`）：

| 策略 | 总代价 |
|---|---|
| **always-换出** | `1062.21` |
| **always-KV 重算** | `1788.23` |
| **按临界点选** | **`1030.96`** |

★★ **读法**：**按临界点选严格优于任何固定策略** —— 因为固定策略**在某些长度上必然付更贵的那一边**。
★ 这个优势**只来自一件事**：两条代价曲线在 `s*` 处**交叉**。

**（3）★★ 优先级与 SLO 的账**。SLO 通常写在**尾延迟**上（如 `P99` 首 token 延迟）。
★ 本文的 `C.4` 给出它的**下界**：在**持续到达**下按优先级/最短作业排序，
**低优先级作业的等待会线性后移** ⇒ **尾延迟无界**。
⇒ ★ **凡 SLO 里有尾延迟约束，调度器就必须给长期等待的请求一个「老化」通道**
（提高其优先级），否则约束**在任何负载下都可能被击穿**。

**（4）★★ 这条链的产物是「代价的算术」，不是「真实抢占行为」。**
★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：FCFS。** 按到达序。★ 本文算例平均完成 `17.8333`、最大等待 `23.0`。
失败模式：**一个长作业排在前面就拖累所有人**。

**第二步：SJF / 重排序。** 按服务时间升序。★ 平均完成 **`11.6667`**（= 穷举最小，`A.4`）。
★ 这一步就是**重排序**：它**不改变有谁**，只改变**顺序**。

**第三步：抢占。** 新请求挤不进来时踢掉一个。★ 踢的方式有两种，**代价都可算**：
短序列 **KV 重算**、长序列**换出**（`s* = 4000`）。

**第四步：抢占式最短剩余时间（SRTF）。** 每一步重新选「剩余最少」的那个。
★★ **它把 SJF 的最优性推广到动态到达** —— 但**代价是饥饿**（`C.4`）：
★ 只要短作业**持续到达**，长作业**永远不是「剩余最少」**。

**第五步：老化（aging）。** ★ 给等待过久的请求**提升优先级** ——
这是**唯一**能同时保住「平均最优」与「尾延迟有界」的手法。★ 它把 §2(3) 的 SLO 约束接回来。

## 4. 踩坑与失败模式

### 4.1 ★★★ 换出只算了「出」，忘了「入」

- **现象**：换出的代价系统性地**低估一半**，于是「几乎总是换出」看起来总是对的；
- **成因**：搬家是**两个方向**（搬出 + 搬回），而写代码时**只写了一个方向**；
- **本机实测**（`code/` 的 `C.3`/`D.4`）：坏法的换出**恰好是正确值的一半**
  （`s = 16384`：`268.44 = 536.87 / 2`）⇒ ★★ **在整个长度网格上再没有任何长度适合 KV 重算**，
  结论从「短序列 KV 重算、长序列换出」**反转**成「**几乎总是换出**」；
- **规避**：★★ **`BW` 的口径必须写清**（单向 / 双向、线速率 / 载荷）——
  ★ 这正是 `20-gpu-architecture/interconnect/01` 那一篇要挡的 2 倍错误。

### 4.2 ★★★ 把「饥饿」归给排序

- **现象**：「用 SJF 会把长作业饿死」—— 而在一个**固定的**请求集合上测，**看不到**这个现象；
- **成因**：静态集合里**每个作业最终都会被服务**（总量有限），
  ★ 饥饿需要**持续到达**才有；
- **本机实测**（`code/` 的 `B.2` vs `C.4`）：静态集合上 SJF 的**最大等待反而更小**（`19.0 ≤ 23.0`）；
  而持续到达下长作业的开始时刻**沿每条约 `3` 线性后移**（`30 → 300`）；
- **规避**：★ **判据要区分「静态集合」与「动态到达」** ——
  前者有穷举最优可证，后者只能用「等待随到达量线性增长」来证**无界**。

### 4.3 ★★ 把「到达过程」之外的东西也塞进 `s*`

- **现象**：以为 `s*` 会随**并发数 / 批大小 / 到达节奏**变；
- **成因**：`(3)` 里 `s* = (2·bpt/BW − τ_lin)/τ_quad` —— ★ **它只依赖 `bpt`、`BW`、`τ_lin`、`τ_quad` 四个量**；
- **规避**：★★ **`s*` 只随【单位代价】变，不随【负载】变** ——
  ★ 于是它可以被**预先算出来**当成一条静态阈值；★ 而**带宽**与**长度**是两个独立的旋钮（`A.3`）。

### 4.4 ★ 把「按临界点选」当成「一定要动态决策」

- **现象**：以为必须每一步都**重新求一遍** `s*`；
- **成因**：`s*` 是**四个常量的函数**（§4.3），在硬件与模型不变时它是**常数**；
- **本机实测**（`code/` 的 `B.1`）：按固定阈值 `s*` 逐条选较小者，总代价 `1030.96` ——
  ★ 与「每条都用闭式比一遍」**完全等价**；
- **规避**：★ **先把它算成一个数**（`s*`），再决定要不要动态更新。

## 6. 小结与延伸

**一句话**：**「换出还是 KV 重算」有一个可算的交点（一个【长度】），
而「会不会饿死」只有【持续到达】时才问得出来。**

**三条可独立复用的结论**：

1. ★★★ **临界长度 `s* = (2·bpt/BW − τ_lin)/τ_quad`** —— 短序列 **KV 重算**、长序列**换出**；
   ★ 它**只依赖四个单位代价**，不随负载变（§4.3）；
2. ★★★ **`×2` 与口径** —— 换出是**两个方向**、`BW` 有**三种口径**；
