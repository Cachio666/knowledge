# chunked prefill：分块数的一个最优点

> **把一段长 prefill 切成的块数 `k` 不是「越大越好」也不是「越小越好」——
> 它有一个最优值 `k* = ⌈t_p / t_d⌉`，而那个值同时是两边代价的转折点。**
>
> ★★★ **定义不在本文**：`chunked prefill` 的**定义**在
> `10-foundations/performance-models/01-roofline-model.md:251`（括注定义），本文**只回链**。
> ★★ **prefill / decode 的 kernel 差异**（两者的 `AI` 差 120 倍）在
> `40-kernels/attention/05-decoding-attention.md:229-236` —— 也**只回链**。
> **本文写的是【分块数 `k` 的权衡】。**
> ★★★ **本层是【推理调度器上的一块账】**。**「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无 vLLM**（实测，见计划 `§0.7 A`）。

## 0. 背景与动机

### 一个具体的对照场景

一段 **prefill** 的工作量 `t_p = 400`（时间单位），一步里**并发的 decode** 合起来要
`t_d = 20`。把 prefill 切成 `k` 块、**逐步**与 decode 混跑。

`k = 1`（不分块）时，这一步里 prefill **独占整步** `400`；`k = 4` 时每步 `100`；
`k = 20` 时每步 `20` —— **正好与 decode 一样贵**；`k = 64` 时每步**还是 `20`**（prefill 早已不是瓶颈），
**但要把 `64` 步都走完**。

| `k` | 每步耗时 | TTFT | decode 最坏单步 |
|---|---|---|---|
| `1` | `400.0` | `400.0` | **`400.0`（被挡住）** |
| `4` | `100.0` | `400.0` | `100.0` |
| **`20`** | **`20.0`** | **`400.0`** | **`20.0`** |
| `32` | `20.0` | **`640.0`** | `20.0` |
| `64` | `20.0` | **`1280.0`** | `20.0` |
| `128` | `20.0` | **`2560.0`** | `20.0` |

★★★ **`k = 20` 这一行的两头都是最优的**（TTFT 最小、每步耗时最小）；
★ 往左（`k < 20`）**TTFT 一点没省而 decode 被拖慢**；往右（`k > 20`）**每步耗时一点没降而 TTFT 线性涨**。
★ 全部数字由 `code/02_chunked_prefill.py` 算出并被断言钉住（`B.1`）。

### 为什么值得算这笔账

★ **prefill 与 decode 混跑**是连续批（前一篇）之后绕不开的一步：
decode **一步一个 token**，prefill **一次吃一整段 prompt** ——
★ 两者的 kernel **形状差约两个数量级**（`40-kernels/attention/05:229-236`：两者的 `AI` 差 `120×`，约两个数量级）。
本文学的是：**一个长 prefill 该怎么与一堆 decode 排队。**

## 1. 原理

### 第一步：把模型写成两行

★★★ **本主题的模型假设（必须写明）**：

```
一步耗时  = max(t_d, t_p / k)          (1)   ← 该步里两个负载的【较大者】
TTFT      = k × max(t_d, t_p / k)      (2)   ← prefill 走完 k 步的那一刻
```

★★ **这是简化**：真实里 **prefill 与 decode 共享算力**（不是简单取 `max`），
且 `C` 个 decode 请求与 prefill 块的相对成本**随实现变**（`[B]` 级，本机**无引擎**）。
⇒ ★ **本文只在这个模型内作断言**，**不声称任何真实引擎的性能**（`§1.3.3`）。

### 第二步：解出最优点

`(1)` 是**两个函数取大**：`max(t_d, t_p/k)`。

- `t_p / k > t_d`（即 `k < t_p / t_d`）⇒ 每步耗时 = `t_p/k`，**随 `k` 下降**；
- `t_p / k ≤ t_d`（即 `k ≥ t_p / t_d`）⇒ 每步耗时 = `t_d`，**撞到地板，不再下降**。

⇒ ★★★ **最优分块数**：

```
k* = ⌈ t_p / t_d ⌉
```

★ 它是**最小的使每步耗时降到 `t_d` 的 `k`**。程序用**两条独立路径**验证它（`A.3`）：
闭式 `⌈·⌉`，以及**在模拟器上逐档扫描**（最小的使每步耗时 `≤ t_d` 的 `k`）——
★ 两条都给出 `20`（整除档）与 `21`（`t_p = 401` 的不整除档）。
★★ **A 类的重心在 `A.3`**：`A.1`（`sim_chunk` vs 闭式）**近乎恒等** ——
`sim_chunk` 把 `max` **重复相加 `k` 次**、与 `k·max(...)` 是**同一个式子**；
★ **真正的两条独立路径是 `A.3`**（闭式 vs **在模拟器上扫描**）。

### 第三步：`k*` 把 `k` 轴切成三段（★★★ 判据的核心）

| 段 | 每步耗时 | TTFT | 谁被浪费 |
|---|---|---|---|
| `k < k*` | `> t_d` | **恒为 `t_p`**（不变） | **decode 被拖慢** |
| **`k = k*`** | **`= t_d`** | **`= t_p`** | **都没有** |
| `k > k*` | `= t_d`（不再改善） | `= k·t_d`（线性上升） | **prefill 块空转** |

★★★ **读法**：**`k < k*` 时 TTFT 完全不敏感**（`k=1` 与 `k=20` 都是 `400.0`），
代价**全落在 decode 用户的每步延迟**上；**`k > k*` 时每步耗时完全不敏感**，
代价**全落在 TTFT**上。⇒ ★★ **`k*` 是这两条代价曲线的转折点**。

★ **在整除档（`t_d | t_p`，本文的 `t_p = 400`）里，`k*` 是唯一的帕累托最优点** ——
它**同时**取到两侧的最小值（程序 `A.2`）。★ **不整除档两个目标会冲突**（见 §1 第五步）。

### 第四步：两端都是免费的守卫

```
k = 1     ⇒ 每步耗时 = t_p ⇒ TTFT = t_p      （退化成「不分块」）
k → ∞     ⇒ 每步耗时 → t_d，TTFT = k·t_d → ∞ （每步都要等一个完整的 decode 步）
```

★ 程序 `A.4` 钉住两端：`k = 1 ⇒ TTFT = 400.0`（= `t_p`）；
`k = 10^6 ⇒ TTFT = 2×10^7`（= `k·t_d`，**线性无界**）。

### 第五步：不整除时会发生什么（★ 如实声明）

`t_p = 401`、`t_d = 20` ⇒ `k* = ⌈401/20⌉ = 21`，但**每步耗时 = `max(20, 401/21) = 20.0`**，
而 TTFT = **`21 × 20 = 420 > t_p = 401`**。同一档里 `k = 20` 的 TTFT = `401.0`（**更小**），
但每步耗时 = `20.05 > t_d`。

★★★ **两个目标冲突**：**没有任何 `k` 能同时取到两侧的最小值**。
⇒ ★★ **「`k*` 是帕累托最优」这句话只在整除档成立** ——
不整除时 `k*` 只是「**每步耗时先触底**」的那一点，而 TTFT 为此**多付** `(k*·t_d − t_p)`。
★ **程序 `C.4` 把这一段如实跑了出来**（`A.2` 的帕累托陈述也据此限定在整除档）。

## 2. 执行映射

引擎层。**请求调度器**每一步要决定：**这一步的批里放什么。**

**（1）三件东西**：

| 组件 | 动作 | 本文的量级 |
|---|---|---|
| **prefill 块** | 这一步推进一段 prompt 的一部分 | `t_p/k`（`k = 20` 时是 `20`） |
| **decode 组** | 这一步推进所有在飞请求各 1 个 token | 合起来 `t_d = 20` |
| **步长** | 两者**取较大者**（模型假设） | `max(t_d, t_p/k)` |

**（2）★★ 混跑批的构成**（程序 `B.3`）：每步的批 = **1 个 prefill 块 + `C = 32` 个 decode 请求**。

| `k` | prefill 负载 | decode 负载 | 谁支配该步 |
|---|---|---|---|
| `1` | `400.0` | `20.0` | **prefill**（decode 被拖慢） |
| `4` | `100.0` | `20.0` | **prefill** |
| **`20`（`k*`）** | **`20.0`** | **`20.0`** | **相等（平衡点）** |
| `40` | `10.0` | `20.0` | **decode**（prefill 块空转） |

★★ **读法**：`k = k*` 时**两侧都不浪费** —— prefill 没拖慢 decode，decode 也没浪费 prefill 的槽位。
★ 这就是 `k > k*` 时 prefill 块**空转**的机理。

**（3）★ vLLM 的 chunked prefill 默认开关**（`[B]`，程序 `D.6` 逐字钉住）：

- 源码常量：`enable_chunked_prefill: bool = True`；
- 文档逐字：**「In V1, chunked prefill is enabled by default whenever possible.」**

★★★ **「默认开启」必须带「V1 / whenever possible」两个限定** —— ★ 它们是**句子的一部分**，
不是可选的注释（encoder-decoder 模型会**禁用**它）。★ 本库编号：`F6`。

**（4）★★ 这条链的产物是「一块的账」，不是「真实调度器」。**
★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：不分块（`k = 1`）。** prefill 独占整步。
失败模式：**每一个 decode 请求都要等一整段 prefill**（本文算例：每步 `400`）。

**第二步：切块（`k < k*`）。** 每步耗时降下来，**但 TTFT 一点没省**。
★ 本文算例 `k = 4`：每步 `100`（decode 仍被拖慢 5 倍），TTFT **还是 `400`**。

**第三步：切到 `k*`。** `k = ⌈t_p/t_d⌉ = 20`：每步 `20`、TTFT `400` —— **两侧同时取到最小**。

**第四步：切过头（`k > k*`）。** 每步耗时**封顶 `t_d`**，而 TTFT **`= k·t_d` 线性上升**。
★ 本文算例 `k = 128`：TTFT `2560`（`k*` 的 **`6.4` 倍**），每步耗时**一模一样 `20`**。
★★ **这一步引入的唯一失败模式是「纯亏」**（§4.1）。

**第五步：前缀缓存与调度器的接口。** ★ 当一段 prompt 的前缀**已经**在 KV 缓存里，
要切的就**只剩增量**那一部分 —— 那套机制在
[120-inference/kv-cache/03](../kv-cache/03-prefix-and-eviction.md)（**正文在彼处，此处回链**）。
★ 它改变的是 `t_p` 的**值**，不改变本文的 `k*` **公式**。

## 4. 踩坑与失败模式

### 4.1 ★★★ 「分得更细」不等于「更快」

- **现象**：为了「让 decode 更顺」，把 `k` 调得很大 —— 结果 TTFT 变长了，decode 一点没变快；
- **成因**：`k > k*` 之后每步耗时已经**撞到 `t_d` 的地板**，多余的 `k` 只让 prefill **多走几步**；
- **本机实测**（`code/` 的 `C.1`/`B.1`）：`k` 从 `20` 涨到 `128`，**TTFT `400 → 2560`（不降反升）**，
  而每步耗时**都停在 `20`**；
- **规避**：★★ **先算 `k* = ⌈t_p/t_d⌉`**，**没有理由超过它**。

### 4.2 ★★ `k < k*`：代价落在别人身上

- **现象**：把 `k` 调小「让 prefill 更连续」—— TTFT 看着没变，但**每个 decode 用户都慢了几倍**；
- **成因**：`k < k*` 时每步耗时 `= t_p/k > t_d`，**这一步里所有 decode 都被挡住**；
- **本机实测**（`code/` 的 `C.2`）：`k = 1 / 4 / 20` 的 **TTFT 全等于 `400`**，
  而每步耗时 `400 / 100 / 20` —— ★ `k=1` 相对 `k=k*=20` 差 **20 倍**（=`400/20`），`k=1` 相对 `k=4` 差 **4 倍**；
- **规避**：★★ **TTFT 对 `k < k*` 完全不敏感** —— 拿它当判据会漏掉全部代价；
  ★ 要同时看**每步耗时**（它才是 decode 用户感受到的那个量）。

### 4.3 ★ 不整除时两个目标冲突

- **现象**：`t_p` 不被 `t_d` 整除时，按 `k*` 切发现 TTFT **比 `t_p` 大**；
- **成因**：此时**没有任何 `k`** 能让每步耗时**恰好**回到 `t_d` 且 TTFT 回到 `t_p`；
- **本机实测**（`code/` 的 `C.4`）：`t_p = 401` ⇒ `k* = 21`、TTFT `420`；
  而 `k = 20` 的 TTFT `401`（更小）但每步耗时 `20.05`（更差）；
- **规避**：★ **先问「整除吗」** —— 整除时 `k*` 是唯一的帕累托最优点；
  不整除时它是一个**取舍点**，**没有免费的午餐**。

### 4.4 ★ 把「默认开启」当成无条件

- **现象**：写「chunked prefill 默认开启」；
- **成因**：vLLM 文档的原句带**两个限定**（`[B]`，逐字）：
  「**In V1**, chunked prefill is enabled by default **whenever possible**.」——
  ★ **`V1` 与 `whenever possible` 是句子的一部分**；
- **规避**：★ **引默认值必须连限定词一起引**（本库编号：`F6`）。

## 6. 小结与延伸

**一句话**：**长 prefill 切成的块数有一个最优值 `k* = ⌈t_p/t_d⌉` ——
它左边白亏 decode、右边白亏 TTFT、它自己同时最优（整除档里）。**

**三条可独立复用的结论**：

1. ★★★ **`k* = ⌈t_p/t_d⌉`** —— 「最小的使每步耗时降到 `t_d` 的 `k`」，
   ★ 两条独立路径（闭式 / 扫描）都给同一个值；
2. ★★★ **三段性质**：`k<k*` TTFT 不变而 decode 被拖慢；`k=k*` 两侧同时最优；
   `k>k*` 每步耗时不变而 TTFT 线性涨（**纯亏**）；
3. ★★ **两端免费守卫**：`k=1 ⇒ TTFT = t_p`；`k→∞ ⇒ TTFT = k·t_d` **无界**。
