# serving 栈：前缀感知的路由、扩缩容与指标口径

> ★★★ **本文承接 `50-performance/README.md:49`** —— 那里逐字写「**不重讲 serving 栈**」，
> 而 serving 栈就是本主题：**把请求发到哪个副本**、**什么时候加副本**、**报哪几个数**。
>
> 三件事，都**可算**：
> 1. ★★ **路由**：**前缀感知的路由**在给定请求流下把命中率从 `0.26` 抬到 `0.99`；
> 2. ★★ **扩缩容与排队**：等待时间 `= ρ/(μ(1−ρ))`，副本数 `= ⌈λ/(μ·ρ_target)⌉`；
> 3. ★★ **指标口径**：那三个「延迟」在 vLLM 里**各算哪一段** —— 以及**谁都没算排队**。
>
> ★★★ **本主题【有真 A 类】**（两条）：**前缀感知路由的命中数**（逐请求模拟 vs 闭式 `N − 不同模板数`）·
> **排队模拟 vs `M/M/1` 闭式**。★★ **不能整主题标「无 A」**：排队与负载均衡本质是可独立参照的算法。
> ★★ **只有「真实网络 / 多机的行为」不可测**（本机单机、无真网络）。
> ★★★ **限定语**：**不是任何真实引擎，也不是真机**。

## 0. 背景与动机

一个 serving 栈在引擎之上又加了一层：**一堆副本 + 一个路由器 + 一个扩缩容器 + 一套指标**。

**一个具体的对照场景**（本文程序的真算例，`code/03_scaling_and_observability.py`）：
`4` 个副本、每个副本能缓存 `2` 条前缀、`800` 条请求、它们的前缀来自 `8` 个模板：

| 路由策略 | 命中数 | 命中率 |
|---|---|---|
| **前缀感知**（发给已经持有该前缀的副本） | **`792`** | **`0.9900`** |
| **随机**（轮转，与请求内容无关） | `209` | `0.2612` |

⇒ ★★ **同一批请求、同一批副本，命中率差 `3.79` 倍** —— 差别**只在「发给谁」**。

★★★ **但注意「命中率」这个词在这里是【另一个量】**：本文的**路由命中**是
「请求的前缀在**被分配到的那个副本**的 KV 缓存里」；
而 `kv-cache/03` 的**缓存命中率**是「缓存内部的查找结果」（分母是**块数**）。
★★ **同名不同指** —— 引用时必须写清是哪一个。

## 1. 原理

### 1.1 前缀感知的路由：被测（逐请求模拟）vs 参照（闭式）

```
前缀感知（被测）      : replica = 某个【已持有该前缀】的副本
                        （没有持有者时，发给缓存条目最少的那个）
随机（对照）          : replica = 轮转指针 % 副本数        ← 完全不看请求内容
```

★ 「谁持有」由一个**轻量查找**回答（路由器维护 `前缀键 → 副本集合`）——
★★ **那套 `hash → 块` 的机制正文在** [03-prefix-and-eviction](../kv-cache/03-prefix-and-eviction.md)，
**本文只把它当一个接口用**。

★★★ **为什么这能提升命中率**：副本数 `R` × 每副本容量 `C` = **总槽位数**。
- 随机路由把 `T` 个模板**均匀撒在** `R` 个副本上 ⇒ 单个副本只见过 `C` 个 ⇒ 命中率 ≈ `C/T`；
- 前缀感知**按内容归置** ⇒ 不同模板可以安定到**不同副本**上 ⇒ 命中率接近 `1`（只要 `R·C ≥ T`）。

★★★ **一条【可独立参照】的闭式**（`A.1` 的参照）：当 `R·C ≥ T` 时**永无驱逐** ——
★ 若 `R` 台副本都装满 `C` 个，则**已被持有的不同模板数 = `R·C ≥ T`** ⇒ **所有模板都有主**
⇒ 不会出现「无主的模板」触发**回退分配** ⇒ **不会挤掉任何条目**。
⇒ ★★★ 于是**每个模板的首次出现是唯一的缺失** ⇒ **前缀感知命中数 = `N − (#不同模板)`**。
★★ 这是**纯计数**（不含任何 LRU / 事件循环）—— 与逐请求模拟器构成**两条独立路径**（`A.1`）。

### 1.2 排队：等待时间的闭式

`M/M/1`（指数到达率 `λ`、指数服务率 `μ`）：

```text
ρ = λ/μ              利用率
W_q = ρ / (μ(1−ρ))   平均排队等待
W   = W_q + 1/μ      平均系统时间
L   = λ·W            队列平均长度（Little 定律）
P(W_q > t) = ρ·e^{−μ(1−ρ)t}     ★ 尾部分布（据此解出任意分位）
```

★ **本文算例**（`λ = 0.9`、`μ = 1.0`、`ρ = 0.9`）：`W_q = 9.0`；
★★ **离散事件模拟**（`120000` 样本）量出 **`9.0871`**，相对差 **`0.97%`**（判据容差 `3%`）。
★★★ **容差不是随便定的**：样本数 `120000` ⇒ 标准误 ≈ `1/√120000 ≈ 0.29%`，
**判据容差应当与它同量级**。

### 1.3 扩缩容：副本数是整数，所以它是保守的

```text
副本数 = ⌈ λ / (μ · ρ_target) ⌉
```

★ 因为它是**上取整**，**实际利用率 ≤ 目标**（本文算例 `λ = 3.6`、`ρ_target = 0.9` ⇒ `4` 个副本，
实际 `ρ = 0.9`；`λ = 1.8` ⇒ `2` 个）。★ 这也解释了**扩容是阶跃的** —— 副本数不能取小数。

### 1.4 ★★★ 指标口径：三个量，三段路

vLLM 的官方定义（逐字，`[B]`）把一条时间轴切成**三段**：

| 段 | 谁定义它 | 逐字 |
|---|---|---|
| **排队** | ★★ **谁都不算它** | —— |
| **TTFT** | `time_to_first_token_ms` | 「Time from when the request was **scheduled** until the first output token was generated (TTFT).」 |
| **自回归解码期** | `generation_time_ms` | 「Decode time: time from the first output token to the last output token. **Excludes both queue wait and prefill/TTFT.**」 |

★★★ **读法**：vLLM 的 TTFT **起算于 `scheduled`** ⇒ **它不含排队**；
而 `generation_time` **显式排除**排队与 prefill。
⇒ ★ **三个量加起来也不等于「用户看到的端到端时间」** —— **排队那一段没有任何指标认领**。

★ 另一个口径细节：`mean_itl_ms` 的说明末尾是 **`null for single-token responses`** ——
★★ **「每输出 token 时间」在单 token 响应上无定义**（分母为零）。

## 2. 执行映射

服务层。★ **真实网络/多机的行为本机测不了** ⇒ 下面每个量都是**算术**，不是实测。

**（1）路由器是一次「查表 + 决策」**：`前缀键 → 持有副本集合`。
★ 代价极低（一次查找），收益是**整个副本池的缓存效率**。
★★ 但它**依赖前缀共享这个前提** —— 反例见 §4。

**（2）副本的前缀缓存 = 上一层的机制**：容量、LRU、`ref` 过滤器 ——
★★ **正文在** [03-prefix-and-eviction](../kv-cache/03-prefix-and-eviction.md)，本文只数**路由命中**。

**（3）★★ 路由命中率 vs 缓存命中率（同名不同指）**：
- **缓存命中率**（`kv-cache/03`）：`Σ 命中块数 / Σ 总块数` —— 一次**查找**的结果；
- **路由命中率**（本文）：`命中数 / 总请求数` —— 一次**分配**的结果。
★★ 两者**分母不同、主语不同**，**不可互相套用**（`C.1` 与 `D.3` 把「路由命中」的定义逐字钉住）。

**（4）指标口径的三段**（§1.4）：★★ **报一个「延迟」前，先问它起算于哪一点**。

**（5）本文算例的实际数字**（`make run`，`code/03_scaling_and_observability.py`）：

| 量 | 值 |
|---|---|
| 前缀感知命中率 / 随机（`cap=2`） | `0.9900` / `0.2612` |
| 排队模拟 / `M/M/1` 闭式（`ρ=0.9`） | `9.0871` / `9.0000`（差 `0.97%`） |
| `ρ=0.9` 时的 `p95` | `28.9037`（是均值的 `3.21` 倍） |

**（6）★ 产物是「机制与上界」，不是真实部署的行为。** ★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：一个副本、没有路由。** ★ 吞吐不够就**加副本**，但请求**随便发给谁** ——
★★ 于是每个副本都要**各自**重新 prefill 一遍共同的前缀。

**第二步：加权 / 最少连接。** 解决了**负载不均**，★ 但**完全不看请求内容** ——
★★ **命中率不会因此变好**（本文算例：随机路由 `0.2612`）。

**第三步：前缀感知。** ★★ 路由器**按前缀归置请求** ⇒ 命中率 `0.9900`。
★★★ **代价是**：命中率与**负载均衡**不再是同一件事（见 §4.3 的反例）。

**第四步：把「等待」显式建模（排队）。** ★ 一旦有队列，`W_q = ρ/(μ(1−ρ))` 就把
「加副本」变成一道可算的题：`⌈λ/(μ·ρ_target)⌉`。

**第五步（本文停在哪）：可观测性。** ★★★ **先定义清楚「你在报哪一段」**，再谈优化 ——
§1.4 的三段是本文最后一块内容。

## 4. 踩坑与失败模式

### 4.1 以为「延迟」只有一个

- **现象**：拿 vLLM 的 TTFT 指标直接当「用户等了多久」，发现总也对不上体感；
- **成因**：★★★ **TTFT 起算于 `scheduled`（不含排队）**，而 `generation_time` 又**排除**了排队与 prefill
  ⇒ **排队那一段没有任何指标认领**；
- **本库算例**（`C.1`）：三条引文**逐字钉住**（含 `null for single-token responses`）；
- **规避**：★★★ **报一个延迟前，先写清它的起算点与终点点**。

### 4.2 以为「均值达标 = 达标」

- **现象**：SLO 写「平均 TTFT < `X` 毫秒」，看着达标了，用户仍在抱怨；
- **成因**：★★★ **等待分布是重尾的** —— 均值与尾部分位差得远；
- **本库算例**（`C.3`）：`ρ=0.9` 时**均值 `9.00`** 而 **`p95 = 28.90`**（**`3.21` 倍**），
  ★ 且**中位数 `5.88` 小于均值 `9.00`**（**右偏**的重尾 —— 长尾在右侧）；
- **规避**：★★ **SLO 一律带分位**（`p95` / `p99`），别用均值单独兜底。

### 4.3 以为前缀感知路由「总是更优」

- **现象**：上了前缀感知路由，某些工作负载下吞吐反而变差；
- **成因**：★★ 它有**两个前提**与**一个副作用**：
  - **前提 1（零共享时无收益）**：如果**每条请求的前缀都不同**，前缀感知**退化到随机**；
  - **前提 2（`R·C ≥ T`）**：总槽位不够时收益打折；
  - **副作用（负载集中）**：如果**所有请求共享一个前缀**，前缀感知会把它们**全打到同一个副本**；
- **本库算例**（`C.2`）：零共享时两策略命中数**都是 `0`**；单一前缀时
  各副本份额 **`[800, 0, 0, 0]`** —— ★★ **命中率 100%，但负载全压在一个副本上**；
- **规避**：★★★ **路由要在「命中」与「均衡」之间取折中**（真实系统常常两者都要）。

### 4.4 把「缓存命中率」与「路由命中率」混用

- **现象**：拿 `kv-cache/03` 的命中率数字去估路由收益；
- **成因**：★★★ **两个量的分母与主语都不同**（一个数**块**、一个数**请求**）；
- **本文判据**（`D.3`）：路由命中的定义**逐字钉住**；
- **规避**：★★ **引用命中率时写明「命中什么、除以什么」**。

## 5. 判据表

| 可机械判定的条件 | 结论 |
|---|---|
| 见到「前缀感知路由」 | ★★ 收益**依赖前缀共享**：零共享时**退化到随机**（`C.2`）；★ 单一前缀时**负载集中**（`C.2`） |
| 见到「路由命中率」 | ★★★ **不是**缓存命中率 —— 前者数**请求**、后者数**块**，两者**不可互换**（`D.3`） |
| 见到「平均等待」 | ★★ 用 `W_q = ρ/(μ(1−ρ))`；★★★ **均值达标 ≠ 尾部达标**（`C.3`：`p95/均值 = 3.21`） |
| 见到「要加几个副本」 | ★ 副本数 `= ⌈λ/(μ·ρ_target)⌉`（**整数** ⇒ 实际利用率 ≤ 目标）（`B.3`） |
| 见到 `ρ → 1` | ★★ `W_q` **发散**（`ρ=0.95` 时是 `ρ=0.5` 的 `19` 倍）（`B.2`） |
| 见到「vLLM 的 TTFT」 | ★★★ **不含排队**（起算于 `scheduled`）；★ `generation_time` **排除排队与 prefill**（`C.1`） |
| 见到「每输出 token 时间」 | ★ 单 token 响应上**无定义**（vLLM 逐字 `null for single-token responses`） |
| 见到「真实网络 / 多机的行为」 | ★★★ **本机测不了**（单机、无真网络）⇒ 只能用**规格带宽推导** |

## 6. 小结与延伸

**一句话**：**serving 栈把「引擎」变成「服务」—— 路由决定请求落到哪个副本（前缀感知把命中率从
`0.26` 抬到 `0.99`），排队公式决定要几个副本，而指标口径决定你「看到的」到底是哪一段。**

**三条可独立复用的结论**：

1. ★★★ **命中率要写清是什么命中**：路由命中（数请求）与缓存命中（数块）不是同一个量；
2. ★★ **均值不兜底**：重尾下 `p95 / 均值 ≈ 3`，SLO 必须带分位；
3. ★★★ **每个「延迟」都有起算点**：`scheduled` 起的不含排队 —— 不写清楚就会算错。
