## 0. 背景与动机

`100-parallelism` 的六条轴（数据 / 张量 / 流水 / 序列 / 专家 / 状态）**在推理里依然存在**，
但**有两条在训练与推理之间【实质不同】**，而这正是本文的全部内容：

| | 训练 | 推理 | 差异的后果 |
|---|---|---|---|
| **PP（流水线）** | 一级要做**前向 + 反向** | 一级**只做前向** | ★★ 时间表少一半；★ **气泡率的公式不变，但「`m` 能取多大」变了** |
| **TP（张量）** | 切**权重**与**激活** | 还要切**KV 缓存** | ★★ KV 是**跨请求、随序列增长**的状态 ⇒ 切分粒度有**下限** |

**一个具体的对照场景**（本文程序的真算例，`code/02_inference_parallelism_and_pd.py`）：

`p = 4` 级流水线、`m = 8` 个微批、一级前向 `t_f = 3.0`：

| | 总时间 | 气泡率（Megatron 口径） |
|---|---|---|
| **训练**（`t_f = t_b = 3.0`） | `(m+p−1)(t_f+t_b) = 66.0` | `(p−1)/m = 0.375` |
| **推理**（只有 `t_f`） | `(m+p−1)·t_f = 33.0` | `(p−1)/m = 0.375` |

⇒ ★★★ **气泡率的公式两边一样**（`0.375 == 0.375`），**绝对量差一倍**。
★★ **而真正拉开差距的不是这个** —— 是**「`m` 能取到多大」**（见 §1）。

## 1. 原理

### 1.1 ★★ PP：没有反向，气泡模型怎么变

★★★ **训练侧的气泡推导本文【不重推】** —— 它在
[01-microbatches-and-bubbles](../../100-parallelism/pipeline-parallel/01-microbatches-and-bubbles.md)
（含 `(m+p−1)(t_f+t_b)` 与 GPipe / Megatron 两个口径的分母）。**本文只写推理侧的差别**：

```text
训练： 总时间 = (m + p − 1)·(t_f + t_b)       理想 = m·(t_f + t_b)      气泡 = (p−1)·(t_f+t_b)
推理： 总时间 = (m + p − 1)·t_f               理想 = m·t_f               气泡 = (p−1)·t_f
```

★ **两个口径下的气泡率都是 `(p−1)/m`** —— ★★ **公式相同**。
但两件事变了：

1. ★ **绝对气泡**减半（`(p−1)t_f` vs `(p−1)(t_f+t_b)`）；
2. ★★★ **`m` 的上限完全不同**：训练要为**每个在飞微批存激活**（否则反向没得算），
   所以 `m` 被显存卡住；**推理没有反向、不必存激活** ⇒ `m` 可以**大得多**。
   ⇒ 由于气泡率 `(p−1)/m → 0` **只在 `m` 大时**发生，**推理侧才真正够得着「气泡可忽略」的区域**。

★★ **这就是「值得独立写」的理由**：**同一个公式，两个不同的可达区**。

**本文算例**（`p = 4`、`t_f = 3.0`）：

| `m` | 推理总时间 | 训练总时间 | 气泡率 `(p−1)/m` | 训练/推理 |
|---|---|---|---|---|
| `1` | `12.0` | `24.0` | `3.000000` | `2.0` |
| `2` | `15.0` | `30.0` | `1.500000` | `2.0` |
| `4` | `21.0` | `42.0` | `0.750000` | `2.0` |
| `8` | `33.0` | `66.0` | `0.375000` | `2.0` |
| `16` | `57.0` | `114.0` | `0.187500` | `2.0` |

★ `A.1` 断言：**离散事件模拟器**的总时间与闭式 `(m+p−1)·t_f` **逐位一致**（`5` 档）。

### 1.2 ★★★ TP：为什么「切 KV 缓存」是一件新事

`100-parallelism/tensor-parallel` 的正文管的是**权重与激活**怎么切。★ 推理多出的一样东西是
**KV 缓存** —— 它有**两个训练里没有的性质**：

- **它是【跨请求、持续存在】的状态**（不是一个 batch 的中间结果）；
- **它随序列长度【增长】**（★★ 那笔「**KV 缓存的账**」的正文在
  `130-quantization/kv-cache-quantization/01` —— ★★ **本文不重算它的式子，也不把它写出来**
  （本域 README 的硬边界明确把「六项乘积」划给那一篇））。

⇒ ★★★ **切分粒度有下限**：**一个 KV 头不可再分**。于是

```text
每设备 KV 头数 = h_kv / min(h_kv, t)          t = TP 度
```

★ 当 `h_kv ≥ t` 时它就是 `h_kv / t`（**按头切**）；★ 当 `h_kv < t` 时它**卡在 1 头/设备**（**只能复制** ——
★★ **复制 KV 头**给多台设备，**而不是**让设备闲置；程序 `assign_kv_heads` 的每设备头数列表**没有 0**）。

**本文算例**（`A.2` 逐头分配 vs 闭式，5 格逐格一致）：

| `(h_kv, t)` | 每设备头数 | KV 相对单卡 | 「假设线性 ⇒ `1/t`」会写成 |
|---|---|---|---|
| `(8, 8)` | `1` | `0.125` | `0.125` ✓ |
| `(8, 4)` | `2` | `0.250` | `0.250` ✓ |
| `(4, 2)` | `2` | `0.500` | `0.500` ✓ |
| `(2, 8)` | **`1`** | **`0.500`** | `0.125` ✗ |
| `(8, 16)` | **`1`** | **`0.125`** | `0.0625` ✗ |

⇒ ★★★ **最后两行是本文的要害**：`(2, 8)` 用了 **8 张卡**，KV 却只压到**一半**（不是 `1/8`）。
★ 极端地，**MQA（`h_kv = 1`）时 8 张卡也压不下去** —— 每设备必装那 1 个头。

★★ **这不是实现细节，是架构约束**：`80-model-architectures/attention-variants/01` 的 GQA/MQA 配比
**决定了 TP 度能开到多大**（在 KV 上）。

### 1.3 ★★★ PD 分离：为什么拆，以及临界在哪

**为什么拆**（★ 只引结论，**不重算** `AI` —— 正文在 `40-kernels/attention/05:229-236`）：
**prefill 与 decode 的算术强度差 120 倍**（`120.5` 对 `1.0`）。两者是**完全不同的负载**：
prefill 是 **compute-bound**、decode 是 **memory-bound**。★ 把两者塞进同一个引擎，就必须
在**每步**里做折中（chunked prefill 就是那种折中，正文在
[02-chunked-prefill](../batching-and-scheduling/02-chunked-prefill.md)）。

**PD 分离走的是另一条路**：把 prefill 挪到**另一个硬件池**上。

| | 代价（总用户延迟损失） |
|---|---|
| **耦合**（同一引擎） | prefill 长 `P` ⇒ **阻塞 decode 循环 `c_p·P`** ⇒ **每个** decode 用户都被推后 ⇒ `n · c_p · P` |
| **分离**（两个池） | decode 不受影响；但 KV 要**从 P 传到 D**：`P·b_kv/BW` **+ 一次性开销** ⇒ **只有一个**请求被推后 |

⇒ **分离更优 ⟺**

```text
n · c_p · P  >  P · b_kv/BW + overhead
⟺  n  >  ( b_kv/BW + overhead/P ) / c_p   ≡  n*(P)
```

★★★ **一条可证伪的结论**：
- **`overhead = 0` 时 `n* = (b_kv/BW)/c_p`，与 `P` 无关**（本文算例：恒为 **`2.5`**）；
- ★ 一旦有**一次性开销**，`n*` **随 `P` 上升而下降**（`4.0625 → 2.5244`，趋于 `2.5`）。

★★ **物理读法**：**「少阻塞 `n` 个人」换「多一次传输」** —— 被阻塞的人**不够多**时，这笔交换是**亏的**。

**本文算例**（`b_kv/BW = 0.05` ms/token · `c_p = 0.02` ms/token · 开销 `0.5` ms）：

| `P \ n` | `1` | `2` | `4` | `8` |
|---|---|---|---|---|
| `16` | 耦合 | 耦合 | 耦合 | **分离** |
| `64` | 耦合 | 耦合 | **分离** | **分离** |
| `256` | 耦合 | 耦合 | **分离** | **分离** |
| `1024` | 耦合 | 耦合 | **分离** | **分离** |

⇒ ★★ **`16` 格已逐格钉住**（程序 `B.3`）里 **`7` 格**分离更优；★ `n = 1` 与 `n = 2` 两列**全耦合**（反例）；
★ `n = 4` 时 `P=16` 耦合、`P=64/256/1024` 分离 ⇒ **临界随 `P` 移动**。

## 2. 执行映射

引擎层与通信层的**接口**。★ **通信的机制不在本文**（集合通信原语 / NCCL / 拓扑 / 重叠 →
`110-communication` 全域）；**并行策略本身也不在本文**（六轴 → `100-parallelism` 全域）。
本文只写**推理侧的需求**。

**（1）流水线的「填满」是推理特有的**：训练里最后一个微批的后向走完之前，第一阶段不能收新微批
（否则反向的激活还没算完）。★ 推理**没有反向** ⇒ 新请求可以**边流边走**地填进来 ——
★★ 这正是**连续批（iterative-level scheduling）与流水线的交点**（调度正文在
[01-iteration-level-scheduling](../batching-and-scheduling/01-iteration-level-scheduling.md)）。

**（2）KV 缓存的切分决定了「TP 度能开多大」**：★ 权重与激活可以切到 `t` 份，
但 **KV 的粒度下限是 `h_kv`** ⇒ ★★ **GQA/MQA 的架构选择直接限制了推理侧的并行度**。
★★ 这条**在训练里不存在** —— 训练不存 KV。

**（3）PD 分离的传输量是「一次 prefill 的 KV」**：`P` 个 token 的 KV，大小 `P · b_kv`。
★★★ **口径警告**：本文的 `b_kv/BW` 是**推导用的规格带宽**，
**不是本机 socket 的任何数字**（本机**单机、无真网络** —— `P34` / 残留 `T75`）。

**（4）本文算例的实际数字**（`make run`，`code/02_inference_parallelism_and_pd.py`）：
`p=4`、`t_f=t_b=3.0`、`m∈{1,2,4,8,16}`；KV 头网格 `(8,8)(8,4)(4,2)(2,8)(8,16)`；
PD 的 `P∈{16,64,256,1024}` × `n∈{1,2,4,8}`。

**（5）★ 产物是「结构与上界」，不是真实系统的性能。** ★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步（训练的形态）：前向 + 反向，气泡由 `(p−1)/m` 定。** ★ 正文在
[01-microbatches-and-bubbles](../../100-parallelism/pipeline-parallel/01-microbatches-and-bubbles.md)。

**第二步（推理的第一个差别）：去掉反向。** ★★ **气泡率的公式**不变，**绝对气泡减半**，
而**`m` 的上限松开**（不必为在飞微批存激活）⇒ **可达区变大**。

**第三步（推理的第二个差别）：TP 要切 KV。** ★★★ 由此出现一个**训练里没有的约束**：
**TP 度的上限被 KV 头的个数卡住**（`h_kv < t` 时只能复制）。★ 这与 GQA/MQA 的架构选择直接耦合。

**第四步：把 prefill 与 decode 拆到两个池（PD 分离）。** ★ 动机是**两者的 `AI` 差 120 倍**；
★★ **代价是一条 KV 传输**（`P · b_kv`）**+ 一次性开销**。
★ 于是分离**不是普适更优** —— 它的适用域由 `n > n*(P)` 给出（§1.3 的表）。

**第五步（本文停在哪）**：★ **本文没有实现任何引擎**。三个 A 类判据的对象都是**模型本身**
（流水线时间表 / 头到设备的分配 / 逐用户的时间线）—— ★★★ **不是任何真实引擎的行为**。

## 4. 踩坑与失败模式

### 4.1 把「气泡率相同」当成「推理的 PP 与训练一样」

- **现象**：看到两侧气泡率都是 `(p−1)/m`，就认为推理的流水线效率与训练相同；
- **成因**：★★★ **公式相同 ≠ 可达区相同**：训练要为**每个在飞微批存激活**，`m` 被显存卡住；
  推理**不必**存 ⇒ `m` 能大得多，而气泡率只在 `m` 大时才趋零；
- **本库算例**（`C.1`）：`(p,m)=(4,8)` 下气泡率**两边都是 `0.375`**，**绝对气泡之比 = `t_f/(t_f+t_b) = 0.5`**；
- **规避**：★★ **引用气泡率时必须写明「这是哪个器械、`m` 的上限由什么定」**。

### 4.2 用 `h_kv / t` 估每设备 KV

- **现象**：算容量规划时写「KV 除以 TP 度」，于是在 `h_kv < t` 的地图上**低估**了每设备 KV；
- **成因**：★★★ **一个 KV 头不可再分** ⇒ `t > h_kv` 时**只能复制**，每设备仍装 **1 个头**；
- **本库算例**（`C.2`）：`(2,8)` 的每设备头数是 **`1`**（不是 `0.25`），KV 只压到 **`0.5`**（不是 `0.125`）；
- **规避**：★★ **一律用 `h_kv / min(h_kv, t)`**；★ 容量规划时要先问「KV 头有几个」。

### 4.3 认为 PD 分离「总是更快」

- **现象**：看到「prefill 与 decode 是两种负载」就把它们拆开，结果 TTFT 反而变大；
- **成因**：★★★ 分离**买来的是「不阻塞 decode」，付出的是「一次 KV 传输 + 一次性开销」——
  **被阻塞的人不够多**时是**亏的**；
- **本库算例**（`C.3`）：`n = 1`、`P = 1024` 时耦合代价 `20.48` < 分离代价 `51.70`；
  ★ 全网格里 **`16` 格只有 `7` 格**分离更优；
- **规避**：★★ **先用 `n > (b_kv/BW + overhead/P)/c_p` 判一下**，再决定拆不拆。

### 4.4 把「并行策略」或「通信机制」搬进本文

- **现象**：在讲 PD 分离时顺手把 NCCL 的集合通信、或那条六轴切分写成正文；
- **成因**：★★★ **一个知识点只有一处正文**（`CONTRIBUTING` §7）；
  六轴的正文在 `100-parallelism`、通信机制的正文在 `110-communication`；
- **本文判据**（`D.3`/`D.8`）：**六条回链锚点逐字钉住**（`D.3`）；★ `D.8` 在源码层核**三条 A 的被测与参照

## 6. 小结与延伸

**一句话**：**推理侧的并行与训练共享概念，但有两处实质不同 —— PP 少了反向（气泡率公式不变、
可达区变大），TP 多切了 KV 缓存（切分粒度下限是 KV 头的个数）；而 PD 分离是把两种负载拆到
两个池，代价是一条 KV 传输，是否划算由一个临界 `n*(P)` 决定。**

**三条可独立复用的结论**：

1. ★★★ **公式相同 ≠ 可达区相同**：气泡率两边一样，但 `m` 的上限由「存不存激活」决定；
2. ★★★ **切分粒度有下限**：KV 头不可分 ⇒ `h_kv < t` 时 TP 度**换不来 KV 的缩小**；
3. ★★ **分离不是普适更优**：换的是「少阻塞 `n` 个人」对「一次传输」，`n` 不够大就亏。
