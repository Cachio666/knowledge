# 从「账」到「容量」：可用显存 → KV 块数 → 最大并发

> **KV cache 的「账」算的是「一个 token 占多少字节」；本文算的是「这块显存能同时开几条序列」。**
> 中间那条链是：**可用显存 → KV 块数 → 最大并发**，而它在两端都会退化 ——
> **块太小时「块表装不下」，块太大时「一个块就装不下」**。
>
> ★★★ **本文不写「账」本身**：六项乘积、`512 KiB`、`2 GiB`、GQA 的坑这些**正文在
> `130-model-optimization/quantization/18-kv-cache-basics`**，本文**只取用它算出的那个数**（`P37`）。
> ★★★ **本文也不写「预留式 vs 分页式的浪费对比」**（含「浪费 90% 以上」的定量）——
> 那条正文在 `130-model-optimization/quantization/18-kv-cache-basics:124`，本文只回链。
> ★★★ **本层是【系统侧（容量规划）】。** **「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无 vLLM / SGLang / TensorRT-LLM**（实测，见计划 `§0.7 A`）
> ⇒ 本文的一切数字是 **`[E]` 级**：**闭式的推导值**与**本机跑模拟器得到的实测值**
> （★ 两者都不是任何引擎的实测并发数）。

## 0. 背景与动机

推理有**三重约束**：显存、吞吐、延迟。它们互相交换，而**交换的枢纽是「同时能开几条序列」**——
这个数叫**最大并发**（在飞请求数）。它太小，显存闲着、吞吐上不去；它太大，显存爆掉、请求失败。

一个具体的对照场景：

- **不规划**：把 80 GiB 全当成「能放 KV cache 的内存」，于是按 `80 GiB` 去算能开多少条；
- **规划**：先减掉**权重**（Llama-2-7B 的 fp16 权重约 `13 GiB`）与**预留**
  （激活、框架缓冲），剩 `63 GiB` 才是 KV cache 的预算。

`80` 与 `63` 差 `27%`——同一个模型、同一块卡，**并发差一截**。这就是本文的第一条纪律：
**「可用显存」是一个必须写清算式的词**（§1 第一步）。

**为什么本文值得单独写。** `130-model-optimization/quantization/18-kv-cache-basics` 已经把「账」算到了极致
（每 token `512 KiB`、`4096` ctx 恰好 `2 GiB`），但它停在**账**上——它回答的是
「**一个 token 占多少字节**」，不回答「**这块显存能开几条序列**」。
★ 后者才是引擎启动时必须先算出来的那个数（本文 §2）。两者是**同一条链的上下游**，
不是同一件事：**账是乘法，容量是除法加取整**。

## 1. 原理

### 第一步：把「可用显存」写成算式

```
可用显存 = 总显存 − 权重 − 预留
```

- **权重**：Llama-2-7B 的 fp16 权重约 **13 GiB**（取自 `130-model-optimization/quantization/18-kv-cache-basics:37`）；
- **预留**：激活 + 框架缓冲 —— ★ **本文用一个模型假设值 `4 GiB`**（`KV_RESERVE_GIB`）。
  ★★ **真实引擎的预留量随实现与配置变**，本机**无引擎**给不出真值 ⇒ 本文**逐处标注它是假设**。

于是三档总显存给出：

| 总显存 | − 权重 | − 预留 | = 可用 |
|---|---|---|---|
| `24 GiB` | `13` | `4` | **`7 GiB`** |
| `40 GiB` | `13` | `4` | **`23 GiB`** |
| `80 GiB` | `13` | `4` | **`63 GiB`** |

### 第二步：可用显存 → KV 块数（**一条除法**）

KV cache **不是一整块**——它被切成**固定大小的 KV 块**（每块装 `B` 个 token）。
★ **块大小是引擎的选择**：本文取 **`16` token / 块**，它来自 **vLLM 的源码常量
`DEFAULT_BLOCK_SIZE`（`[B]` 级，`vllm/config/cache.py`，抓取日 2026-10-09）**。
★★★ **不得写成「业界通常 16」** —— ★ 块大小是**引擎的选择**：另一家（SGLang）的粒度不同，
两者的口径差**正文在** [engines/02 的 `C.1`](../engines/02-sglang-and-radix.md)
（**正文在彼处，此处只回链**，`D1` 订正）；★ 域 README 的「同名不同指」表也记着这一条。

每个块占的字节 = **块大小 × 每 token 字节**，于是：

```
KV 块数 = 可用显存 // (块大小 × 每 token 字节)
```

代入 `63 GiB`、`B = 16`、每 token `524288 B`（= `512 KiB`，**取自 130-01，本文不重推**）：

```
KV 块数 = 63 × 2³⁰ // (16 × 524288) = 67645734912 // 8388608 = 8064
```

★ **这个数纯粹是 2 的幂在约分**（`63 · 2³⁰ / 2²³ = 63 · 2⁷`）—— 和「账」那边的 `2³¹` 是同一种手感。

### 第三步：块数 → 一条序列占几块 → 最大并发

一条长度为 `S` 的序列占 `⌈S / B⌉` 块。★ **末尾不满一块也要占一整块**（这是取整方向的关键，见 §4.2）：

```
每序列块数 = ⌈S / B⌉
最大并发   = KV 块数 // 每序列块数
```

代入 `8064` 块、`S = 4096`、`B = 16`：每序列 `256` 块 ⇒ 并发 `8064 // 256 = 31.5 → 31`。

★★ **两个除法连着做，两次都向下取整** —— 这就是「容量」与「账」在数值手感上的分界：
**账是精确的整数（`2³¹`），容量是带余数的除法（`31.5 → 31`）**。

### 第四步：★★★ **两条独立路径**（本文的 A 类）

上面那条链是**闭式除法**。本文的程序还有**第二条完全不同的路径**：
**逐块填池 + 逐 token 取块**的**模拟分配**——

- **填池**：一块一块往池里放，放到**下一块放不下**为止（一个 `while`，**没有除法**）；
- **取块**：**逐条序列、逐 token** 地写；每写满 `B` 个 token 就**取走一个块**，池空了就停。

★★★ **两条路径必须会合**：「闭式除法给出的并发」**逐位等于**「模拟真的塞进去的序列数」。
★ 这不是恒真 —— 它**同时**校验了「取整方向」「末尾不满一块也占块」「池的容量怎么算」三件事。
★ 程序里 `A.1` 在 **24 档**（预算 × 块大小 × 序列长度）上判它，`D.4` 再把参照**故意改坏**，
证明这个等式**对分配规则是敏感的**（`CONTRIBUTING:235` 的守卫）。

★★★ **判据设计上最要紧的一条**：**参照的表达式与控制流都不得依赖被测的量**。
模拟里**没有** `avail // (B · t)` 这个除法，也**不调用**任何 `cf_*` 函数 ——
`D.8` 在**源码层**核这一点（★ 它只是**线索**，真正的保证来自 `A.1` 与 `D.4` 的行为）。

★★★ **如实声明（一条弱判据）**：程序里 `A.2`（`sim_fill_pool` vs 闭式除法）**很弱** ——
`sim_fill_pool` 是「**把一条除法写成重复加法**」（两者都会数到「放不下为止」），与闭式几乎**恒等**。
★ 它只钉住**边界那一块**（`<=` 还是 `<`）；★★ **有信息量的是 `A.1`**（逐 token 取块）与第六步的 `A.4`。

### 第五步：★★★ 两端的退化（本文的 C 类）

同一条链在两端都会**退化**，而且**退化的方式完全相反**：

| 块大小 | 会发生什么 | 看得见吗 |
|---|---|---|
| **极小（`B = 1`）** | 池要装 **`129024`** 个块（比 `B = 16` 多 **16 倍**）⇒ **块表装不下** ⇒ **计划不可实现** | ★★★ **并发数看不出来**（`B = 1` 与 `B = 16` 都给 `31`！） |
| **极大（`B = 2²⁰`）** | 一个块占 **`512 GiB`** > 全部预算 ⇒ **一个块都放不进池** ⇒ 并发 **`0`** | ★ 一眼就看出来（并发直接 0） |

★★★ **`B = 1` 那一行是本文最值钱的一条**：**代价不在并发上，在块表的条目数上**。
只看「最大并发」这个数，你**完全看不出** `B = 1` 的计划是跑不起来的。
★★ **这条也把「块大小」这件事的判据钉在了【系统侧】** ——
「块大小的**真正约束**是什么」在 kernel 侧有一份正文（页表延迟 / 碎片 / 布局），
**那份正文在 `40-kernels/attention/05:130-179,283-290`，本文只回链**，不重算。

### 第六步：★★★ **同时装下 prefill 与 decode**（两种请求的 KV 需求不同）

上面第三步假设**请求是同质的**。真实里至少有两类，而它们的 **KV 需求形状完全不同**：

| 请求类型 | 它要几块 | 什么时候要 |
|---|---|---|
| **prefill 请求** | **`⌈S_prompt / B⌉` 块** | ★★ **一次性** —— prompt 要**整段**前向才能出第一个 token，这些块**必须同时在场** |
| **decode 请求** | `⌈s_current / B⌉` 块（`s_current` = **当前**长度） | ★ **逐步增长** —— 每多写 `B` 个 token 才多要一块 |

★★★ **两者在【同一块池】里的准入边界不同**：一条 prefill 要先把 `⌈S_prompt/B⌉` 块**一次扣走**，
剩下的池才轮到 decode 分。于是池容量 `P` 下：

```
共存 decode 条数 = (P − ⌈S_prompt/B⌉) // ⌈s_decode/B⌉
```

★★★ **一条长 prefill 会挤掉若干条 decode** —— 挤掉的条数约 `⌈S_prompt/B⌉ / ⌈s_decode/B⌉`。
★★ **临界条件**：`⌈S_prompt/B⌉ + ⌈s_decode/B⌉ > P` 时，**prefill 与任何一条 decode 都不能共存**
（共存条数 `0`）—— 此时引擎只剩两条路：**让 prefill 等**，或**把在飞的 decode 全部 KV 重算 / 换出**
（★ **抢占的机制与代价账**——换出 vs KV 重算、临界长度 `s*`——**正文在** `batching-and-scheduling/03-preemption-and-fairness.md`，此处**只回链**）。

★ **它不是恒真**：程序 `A.4` 在 **`12` 档**上判「闭式 == 模拟」（模拟**先一次性占满 prefill、再逐条塞 decode**，
两条独立路径）；`A.5` 钉住单调性与上面那条**临界条件**（`⌈S_p/B⌉ + ⌈s_d/B⌉ > 池 ⇒ 共存 0`）。

## 2. 执行映射

引擎层。这条链在**引擎启动时**就算完了，它的产物是**一个数**（「最多同时在飞几条请求」的上限；
★ **各家引擎给它起的参数名与它的默认值都不同**，那是 `engines` 主题的正文，本文只写**这个数怎么来**），
之后**每一个调度步**都要遵守它。

**（1）三个组件**：

| 组件 | 在容量规划里的角色 |
|---|---|
| **显存预算器** | 把「总显存」减成「可用显存」（权重 + 预留）—— ★ 它决定 §1 第一步那个数 |
| **KV 块池** | 按「块」分配/回收；**池的容量**就是 §1 第二步算出的 `8064` |
| **请求调度器** | 每一步只看**还剩几个空块**决定接不接新请求 —— ★ 它读的是**并发上限**，不是字节数 |

**（2）数量级**（**本机实测值** —— ★ 本机 `python3 3.13.5` 跑本文的**容量规划模拟器**得到，
★ **不是任何真机、不是任何引擎**）：

| 量 | 值 |
|---|---|
| `80 GiB` 一档的 KV 块数 | **`8064`** 块 |
| `S = 4096` 时的最大并发 | **`31`** 条 |
| `S = 512` 时的最大并发 | **`252`** 条 |
| ★ 块表条目数（`B = 1`） | **`129024`** 条（★ 16 倍） |

**（3）★ 一条容易踩的量化事实**：**并发与序列长度近似成反比**——
`S` 从 `512` 涨到 `4096`（8 倍），并发从 `252` 掉到 `31`（约 8 倍）。
★ **不精确的唯一原因是每序列块数的向上取整**（§4.2）。

**（4）★★ 这条链的产物是「机制与上界」，不是「真实性能」。**
本机**无 GPU、无引擎** ⇒ 上面的数**没有一个**来自真实系统。
★★★ **限定语**：「不是任何真实引擎，也不是真机」。

**（5）★★ 请求【不同质】**：调度器每步同时面对 **prefill 请求（一次性要 `⌈S_p/B⌉` 块）** 与
**decode 请求（逐步增长）**；★ 二者的**准入边界**不同（§1 第六步）。⇒ ★★ 「池里还剩几块」这一个数
**不足以**决定接谁 —— 还要看**请求类型**（一条长 prefill 可能把在飞的 decode 全挤掉）。

## 3. 实现与演进

**第一步：一个数（离线估算）。** 人工按本文的链算一次，把并发写死成常数。
失败模式：模型一换、序列长度一变，这个数就过期（§1 第二步的输入变了）。

**第二步：一张表（敏感度）。** 把「预算 × 序列长度」都算出来（本文 `B.1` 的六格表）。
★ 它暴露了「并发与长度成反比」这条结构，于是**不必每次都重算**，读表即可。

**第三步：一个约束（块表上界）。** ★★ 到这里才发现，**并发不是唯一的约束**——
`B = 1` 那张计划表里并发**看起来**没问题（还是 `31`），但**块表装不下 `129024` 个条目**。
⇒ 容量规划必须**同时**盯「并发」与「块表条目数」两个量（§1 第五步）。
★ 这一步的判据是**本主题的增量**：`130-01` 停在「账」，`40-kernels/05` 讲 kernel 侧的页表代价，
**而「块表条目数随块变小而线性变大」这条系统侧约束，本文把它算出来。**

**第四步：共享（通往 02）。** ★ 上面所有算式都假设**每条序列独占自己的块**。
真实系统里**多条序列可以共享块**（共同前缀、或 fork 出多条），于是**同样的显存能装下更多序列**。
那条链的正文在 [02-block-management](02-block-management.md)，本文只留下接口：
**共享改变的是 §1 第二步的「块数 → 能开的序列数」这一步**。

## 4. 踩坑与失败模式

### 4.1 把「总显存」当成「可用显存」

- **现象**：一个**具体误用场景** —— 你要在 `80 GiB` 的卡上跑 `S = 4096` 的服务，按**总显存**算得
  **并发 `40`**，于是把并发上限定成 `40`；★★ 而**真实可用只有 `63 GiB`**（`80 − 权重 13 − 预留 4`），
  它只给 **`31`** ⇒ ★★ **多收的 `9` 条**在显存里放不下 ⇒ **请求被拒或 OOM**。
  ★ 「可用显存」被高估了 `27%`（`80` vs `63`），落到并发上就是这个差额；
- **成因**：漏了 `可用显存 = 总显存 − 权重 − 预留` 里的两个减项（§1 第一步）；
- **规避**：★ **「可用显存」这个词出现时，必须把算式与三个数一起写出来**。
  ★★ 本机**无引擎** ⇒ 预留量只能用**标注过的假设值**，不得装作知道某个引擎的真实预留。

### 4.2 末尾不满一块就不算块（`floor` vs `ceil`）

- **现象**：并发算**偏大**；长度不是块大小整数倍时，每序列块数少算一块；
- **成因**：把 `⌈S / B⌉` 写成 `S // B`；
- **本机实测**（`code/` 的 `D.4`）：把参照的分配规则改成「末尾不满的一块不取」后，
  模拟从 `1` 变成 `3`，**与闭式当场对不上** ⇒ ★★ 这说明 `A.1` 的等式**真的**在判这件事；
- **规避**：★★ **只有模拟路径能可靠地守住取整方向**（闭式写错方向时它也「自洽」）。
  ★ 这条正是「两条独立路径」的价值：**一条写错，另一条会对不上**。

### 4.3 块大小取极值时，计划**静默地不可实现**

- **现象**：`B = 1` 的容量规划表**看起来完全正常**（并发还是 `31`），但**跑不起来**；
- **成因**：块越小 ⇒ 池里条目越多（`129024`）⇒ **块表索引不下**（§1 第五步）；
  ★★ **代价不在并发上，所以只看并发数根本发现不了**；
- **规避**：★★ **容量规划必须同时输出「并发」与「块表条目数」两个量**；
  ★ 另**一个极端**（`B` 大到装不下一个块）会给出并发 `0`——那个**看得见**，
  ★★ 真正危险的是**看不见的那个**。

## 5. 判据表

| 可机械判定的条件 | 结论 |
|---|---|
| 见到「这块卡能开多少并发」 | ★★ 先问**「可用显存」的算式**：`总 − 权重 − 预留`（§1 第一步）；漏减项就偏大 |
| 见到「KV 块数」 | ★ 本文的链是 `可用显存 // (块大小 × 每 token 字节)`（`B.1`）；**每 token 字节**的正文在 `130-model-optimization/quantization/18-kv-cache-basics` |
| 见到「每序列几块」 | ★★ 是 **`⌈S / B⌉`**，**末尾不满一块也占一整块**（`D.9`）；写成 `S // B` 会偏大（`D.4`） |
| 见到「块大小是 16」 | ★★ **那是 vLLM 的源码常量**（`[B]`，抓取日 2026-10-09）；★ **同名不同指**（另一家粒度不同）—— ★★ 正文在 [engines/02](../engines/02-sglang-and-radix.md)（`C.1`） |
| 见到「块小一点没坏处」 | ★★★ **有**：块越小 ⇒ 条目越多 ⇒ **可能越出块表上界 ⇒ 计划不可实现**（`C.1`，而**并发看不出**） |
| 见到「块大到装不下」 | ★★ 一个块超过预算 ⇒ 池空 ⇒ **并发 `0`**（`C.2`） |
| 见到「并发与序列长度的关系」 | ★ 近似**反比**（`B.2`）；偏差全部来自**末尾不满块的取整** |

## 6. 小结与延伸

**一句话**：**把「账」变成「容量」只多做一步半 —— 先减出可用显存，再连做两次除法并取整**；
而这条链**两端都会退化**（其中**「块太小」那一端在并发上看不见**），
且**请求不同质时还要看准入边界**（prefill 一次占满、decode 逐步增长）。

**四条可独立复用的结论**：

1. ★★ **可用显存是一个必须写算式的词**：`总 − 权重 − 预留`；本主题的预留是**标注过的假设值**；
2. ★★★ **两条独立路径必须会合**：闭式除法 vs 模拟分配 —— ★ 它们同时守住取整方向与池容量；
3. ★★★ **容量规划要输出两个量**：**并发**（看得见）与**块表条目数**（看不见的那条约束）；
4. ★★★ **请求不同质**：prefill **一次性**要 `⌈S_p/B⌉` 块、decode **逐步**增长 ——
   ★★ **`⌈S_p/B⌉ + ⌈s_d/B⌉ > 池` 时二者无法共存**（§1 第六步），
   而「池里还剩几块」这一个数**看不出**这件事。
