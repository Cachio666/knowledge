# 系统侧的块管理器：块池、引用计数与 copy-on-write

> **上一类算出了「有多少块」；本文管的是「这些块怎么被分配、共享、回收」。**
> 核心只有一条不变量 —— **`Σ_块 引用计数 == Σ_活序列 该序列的块数`** ——
> 而它同时守着两件事：**多序列共享块**（共享时 `ref += 1`）与 **copy-on-write**
> （只在**写一个 `ref > 1` 的块**时才复制）。
>
> ★★★ **本主题不写「paged KV 的 kernel 侧」** —— 页表延迟（`400~800` 周期 vs tile 计算 `504`）、
> 碎片（`16/2 → 0.049%`）、布局必须「一行」连续、**块大小的双向权衡及其结论**
> （「页大小的真正约束是查表次数，不是碎片」）**全部**在 `40-kernels/attention/05:130-179,283-290`，
> 本文**只回链**（`P37` 的现场）。
> ★★★ **本层是【系统侧（块管理）】**。**「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无 vLLM / SGLang / TensorRT-LLM**（实测，见计划 `§0.7 A`）。

## 0. 背景与动机

上一类的链停在「**有 `8064` 个块**」。真正的问题从那里才开始：

**两个请求的 prompt 开头一样**（比如同一个系统提示词），**它们的块要不要存两份？**

- **不共享**：各存各的 ⇒ 显存翻倍 ⇒ 能开的序列数**砍半**；
- **共享**：两块序列指向**同一个物理块** ⇒ 省一半 —— 但接下来那个请求**要往后写**：
  **它一写，另一条序列的 KV 就被改了** ⇒ **共享块必须在写之前复制**。

这就是 **copy-on-write（CoW）**：**块只有在被写、且 `ref > 1` 时才复制。**
于是「共享」与「正确性」由**一个引用计数**同时管住。

**一个具体的对照场景**（本文程序里的真算例，块大小 `4` token、`300` 步随机操作）：

| | 一共创建过的块 | 期末活块 |
|---|---|---|
| **引用计数 + CoW** | **`199`** | `199` |
| **朴素深拷贝**（完全不共享） | **`442`** | `442` |

★ 那 `300` 步里有 **`92` 次 `fork`**，而 CoW **只复制了 `17` 次** ——
**差的 `243` 个块就是「共享」省的**（`243/442` ≈ **`55%`**）。★★ 而**两条实现的每序列内容逐字相同**：
省下来的每一个块，**没有一个是靠算错换来的**。

## 1. 原理

### 第一步：三件东西

| 名称 | 是什么 | 本文的模型 |
|---|---|---|
| **块池** | 空闲物理块的集合 | `pool_cap` 个槽；空槽不够就得**回收或等待** |
| **块表** | 每条序列持有一串**块号**（它自己的 KV 存在哪些块里） | 每条序列一个 `list` |
| **引用计数** | 每个物理块被**几条活序列**指着 | 每块一个整数 `ref` |

★ **实现口径**：本文的块号是**池内的下标**（不是显存地址）—— 这是**本主题的实现**，
**不是**任何引擎的内部结构。

### 第二步：★★★ 唯一的不变量

```
Σ_所有块 ref  ==  Σ_所有活序列 (该序列的块数)
```

★ 左边是「所有物理块被指了多少次」，右边是「所有活序列一共该有多少块」——
**它们必须相等**。这一条同时管住三件事：

- `fork`（子序列共享父序列的块）：每一块 `ref += 1`；
- `append`（往序列尾部写）：**只有 `ref > 1` 时才复制**（CoW），复制后**旧块 `ref -= 1`**；
- `remove`（序列结束）：每一块 `ref -= 1`，**减到 `0` 才回收**。

★★★ **`ref > 1` 这个条件是全部内容**：它是「**有没有别人也在用这块**」的判据。
去掉它，就是**直接改别人的 KV**；写错它（比如 `fork` 忘了 `ref += 1`），
就是**把还在被用的块当成没人用的回收掉**。本文 `C.1`/`C.2` 与 `D.4`/`D.5`
把这两种错误都**真的跑了出来**。

### 第三步：CoW 的时机（一个容易被忽略的细节）

序列的块是按 `B` 个 token 一块**惰性**分配的，**最后一块通常是「不满」的**。
于是 `append` 分两种情况：

- **`off == 0`**（已经对齐到块边界）：**要一块新的** —— ★ **此时不需要 CoW**
  （新块还没被人共享，直接写）；
- **`off > 0`**（还在写当前这最后一块）：**要写共享块了** —— ★ 此时才轮到 CoW。

★★★ **一条反直觉的结论**（本文 `D.4` 的现场）：**「不共享就写」这个错误，第一眼是看不出来的**。
因为 CoW 本该保护的是「**别人会读到的那一段**」，而**不共享直接写**，写的往往是
**共享块里已经超出别人长度的那个槽位**（别人按自己的长度截断，读不到那里）。
⇒ ★★ **必须让两条序列都往【同一个索引】写，差异才会暴露**。
本文的守卫实验就是这么构造的：`create(0, 12345) → fork → append(子, 9) → append(父, 7)` ——
**子序列会读到父写进去的 `7`，而不是自己写的 `9`**。

### 第四步：块池的开销账 —— ★★ **增量只有【条目数】这一个维度**

块池不是白来的：**块表每条要占字节**（本文的模型假设：**每条 `4 B`**）。

★ **块数是上一类算的**（`可用显存 // (块大小 × 每 token 字节)`，
正文在 [01-capacity-planning](01-capacity-planning.md)，★ **是同一条链，本文不重推**）。把 `63 GiB` 一档代进去：

| 块大小 | 块数（条目） | 块表字节（本模型） |
|---|---|---|
| `1` | **`129024`** | `516096 B` |
| `16` | **`8064`** | `32256 B` |
| `256` | **`504`** | `2016 B` |

★★ **读法（本文的增量在左列）**：**块越小 ⇒ 条目越多**（近似 `∝ 1/块大小`）——
★★★ **`40-kernels/attention/05:139` 给的是【一个实例】**（页表 `1024 项 × 4 B = 4 KB`，`S=16384`、页 16 token），
**本文给的是【缩放】**（同一个池，块小一半 ⇒ 条目多一倍）—— ★ 那是那**一个实例**没有的维度。

★★★ **右列必须带一条消歧**：`块表字节 = 块数 × 4 B` 与 `40k-05:139` 的 `页表 = 1024 项 × 4 B = 4 KB`
**是同一个式子，却是【同值不同指】** —— 那条管的是 **kernel 侧硬件页表**（device 上给 SM 查的），
本文这条管的是**系统侧的块号表**（scheduler 侧的簿记）；★ **两者不可互相套用**（回链 `40k-05`）。

★★★ **但「这点字节值不值得担心」不是本文的问题** ——
那笔账（页表占比、碎片、布局、**以及块大小的双向权衡**）在
`40-kernels/attention/05:130-179,283-290` 已经算完，**本文只回链，不重算**。
★ 本文只负责把**条目数**与**本模型的字节数**摆出来。

### 第五步：共享改变了什么（回到容量）

★ 上一类的容量公式假设「**每条序列独占自己的块**」。共享打破了这个假设：

```
能开的序列数  →  不再只由「池容量 // 每序列块数」决定，
                 而是由「池容量 // 每序列【独占】块数」决定
```

★★ **这就是共享的价值**：本文算例里 CoW 期末活块 `199`、朴素 `442`——
**同一个池，CoW 能多装 `243` 个块的量**。★ 注意措辞：
**共享提高的是「能并发多少」，不是「单条快多少」**。

## 2. 执行映射

引擎层。块管理器是**调度器**每次做决定时要问的那个组件。

**（1）三个组件**：

| 组件 | 动作 | 本文的量级 |
|---|---|---|
| **块池**（分配/回收） | `append` 取块、`remove` 还块 | 池容量 `4096` 块（模型假设） |
| **块表**（每条序列的块号串） | `fork` 时**复制块号串**（**不复制物理块**） | `8064` 条 × `4 B`（`B = 16` 一档） |
| **引用计数** | `fork` `+1` / CoW `旧块 -1` / `remove` `-1` | 每块一个整数 |

**（2）CoW 的代价被量出来了**：`300` 步里 `92` 次 `fork`，**CoW 只复制 `17` 次** ——
★★ **`fork` 是「不复制」的**（只加引用计数），**复制只发生在「写一个被共享的块」时**。
这是「共享省了 ≈ `55%`（`243/442`）的块」这条结论的机制来源。

**（3）★ 一条容易踩的量化事实**：**块大小直接决定块表的规模**——
`B` 从 `16` 掉到 `1`，块表条目 **`8064 → 129024`（16 倍）**。
★★ 这与上一类 `C.1` 是**同一件事的两面**：`B = 1` 时**并发看起来不变**，
**变的是块表**。⇒ **块管理器与容量规划必须一起看。**

**（4）★★ 这条链的产物是「不变量」，不是「真实性能」。**
本机**无 GPU、无引擎** ⇒ 上面的数**没有一个**来自真实系统。
★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：不共享（朴素深拷贝）。** 每条序列自己一份块；`fork` 复制**全部**块。
失败模式：**显存按「序列数 × 长度」线性涨**（本文算例里 `442` 块）。

**第二步：引用计数 + CoW。** `fork` 只加计数；写共享块时才复制。
★ 本文算例：块数 `442 → 199`（**≈ `55%`**，`243/442`），**内容逐字不变**。

**第三步：回收与复用。** 块减到 `ref == 0` 就进**空闲表**，下一条序列复用它。
★★ **这一步引入了两个新失败模式**（§4.3/§4.4）：
**泄漏**（永不回收 ⇒ 池假满）与**双重释放**（多减一次 ⇒ 引用计数转负、块被误复用）。

**第四步：前缀共享（通往 03）。** ★ 上面所有共享都靠 `fork`（**同一时刻**的两条序列）。
真实系统里还有**另一个来源**：两条**不相关**的请求**碰巧有共同前缀**。
它需要一套**按内容找块**的机制（`hash → 块`）—— 那是 [03-prefix-and-eviction](03-prefix-and-eviction.md)。
★ 但它**复用本文的同一套块管理器**：前缀命中一个块，就是给那个块的 `ref += 1`。

## 4. 踩坑与失败模式

### 4.1 写共享块时不复制 —— 而第一眼看不出来

- **现象**：去掉 CoW 之后，很多用例的内容**居然还是对的**；
- **成因**：★★★ 「不共享直接写」写坏的往往是**共享块里超出别人长度的槽位**，
  而别人**按自己的长度截断读取**，**读不到那里**（§1 第三步）；
- **本机实测**（`code/` 的 `D.4`）：构造「父、子都往**同一个索引**写」的序列后，
  子序列内容从 `(1,2,3,4,5,9)` 变成 `(1,2,3,4,5,7)`（读到父写的 `7`）⇒ **差异才暴露**；
- **规避**：★★ **构造守卫时必须让两条序列写同一个索引**；★ 否则你会得到一个
  「绿」的守卫，而它**什么都没测到**。

### 4.2 `fork` 忘了 `ref += 1`

- **现象**：`remove` 父序列之后，子序列的块**被当成没人用而回收**，下一条 `create` 复用它；
- **成因**：引用计数漏加，于是「还在被用」这件事**丢了记录**；
- **本机实测**（`code/` 的 `D.5`）：`create(0,1234) → fork(0→1) → remove(0) → create(2,9999)`，
  子序列内容**从 `(1,2,3,4)` 变成 `(9,9,9,9)`**；
- **规避**：★ **每条共享边都要有一条「加一次」的代码路径**；★★ 用不变量兜底（§1 第二步）。

### 4.3 引用计数泄漏 ⇒ 池**假满**

- **现象**：块明明没人在用，却**再也分不出去**；新请求被拒，而显存看起来没满；
- **成因**：`remove` 时**没减引用计数** ⇒ 块**永不被回收**；
- **本机实测**（`code/` 的 `C.1`）：泄漏版的 `Σ ref` 是 **`196`**，而它**应当是 `143`**
  （**不变量当场破**），且在小池（`32` 块）上**分配失败**；
- **规避**：★★ **`Σ ref == Σ 活序列的块数` 是一条可以随时断言的不变量**——
  把它放进每次分配/回收的对账里，泄漏**当场现形**。

### 4.4 双重释放 ⇒ 引用计数转负 + 块被误复用

- **现象**：一个块**被两条序列同时指着**，后写的那条把前一条的 KV 改坏；
- **成因**：`remove` 时**多减一次**：
  ★ `ref` 只有 `1` 时 ⇒ **转负**（本机实测最小 `ref = -1`，物理上不可能）；
  ★ `ref` 是 `2` 时 ⇒ **直接减到 `0` ⇒ 被回收**，下一条序列复用并覆写（本机实测内容 `(1,2,3,4) → (9,9,9,9)`）；
- **规避**：★ **回收前必须断言 `ref == 0`（而不是 `ref <= 0`）**——「小于零」是**不可能发生**的状态，
  把它当正常路径吞掉，就等于把错误藏起来。

## 6. 小结与延伸

**一句话**：**块管理器只有一条不变量 —— `Σ ref == Σ 活序列块数` ——
而它同时管住共享（`fork` 加计数）与正确性（写共享块前先复制）。**

**三条可独立复用的结论**：

1. ★★★ **`ref > 1` 才复制**：这是 CoW 的全部内容，也是「共享省块」与「内容正确」的**同一个开关**；
2. ★★★ **判据是「与朴素深拷贝逐字相同」**：`442 → 199` 块的节省，**没有一个块是靠算错换来的**；
3. ★★ **回收的两个反例（泄漏 / 双重释放）后果相反但都被不变量抓住**：
   **泄漏 ⇒ 池假满；双释放 ⇒ 引用计数转负 + 内容被改坏**。

**延伸**：

- ★ **容量规划**（块数从哪来）→ [01-capacity-planning](01-capacity-planning.md)；
- ★★ **前缀共享与淘汰**（另一条共享来源：`hash → 块` / LRU）→ [03-prefix-and-eviction](03-prefix-and-eviction.md)；
- ★★★ **块大小的 kernel 侧权衡 / 页表延迟 / 碎片 / 布局** →
  `40-kernels/attention/05:130-179,283-290`（**正文在彼处，本文一行都不重写**）；
- ★ **KDA（循环模型）下 vLLM 把「块 / 对齐 / 前缀匹配」三概念拆开 + copy-on-write** →
  `45-kernel-lifecycle/requirement-discovery/01:187`（**该处自标「经检索转述」，非逐字**）；
- ★ **KV cache 量化** → `130-quantization/kv-cache-quantization/02,03`（**正文在彼处**）。
