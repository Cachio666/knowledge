# 前缀共享与淘汰：hash → 块、命中率、LRU

> **上一类讲的共享来自「同一时刻的 `fork`」；本文讲另一条来源 ——
> 两条互不相干的请求，碰巧有共同的前缀。**
> 它需要一套「**按内容找块**」的机制：**把块（连同它前面的前缀）哈希成一个键，去缓存里查**。
> 命中就 `ref += 1` 复用，未命中就新建；缓存满了就**按 LRU 逐出 `ref == 0` 的块**。
>
> ★★★ **本文不写**「KV cache 量化」（正文在 `130-quantization/kv-cache-quantization/02,03`）、
> 也不写「paged KV 的 kernel 侧」（正文在 `40-kernels/attention/05:130-179,283-290`）
> —— 两者都**只回链**。
> ★★★ **本层是【系统侧（前缀共享与淘汰）】**。**「不是任何真实引擎，也不是真机」** ——
> 本机**无 GPU、无 vLLM / SGLang / TensorRT-LLM**（实测，见计划 `§0.7 A`）。

## 0. 背景与动机

**推理有大量重复的前缀。**

- 同一个**系统提示词**被所有请求共享；
- **多轮对话**里，第 `n` 轮的 prompt 是第 `n−1` 轮的 prompt **加几个 token**；
- few-shot 的**示例部分**在每一条请求里逐字相同。

如果这些前缀的 KV **能复用**，那就**不必 KV 重算**——这是三重收益：**省算力**（不用重新 prefill）、
**省显存**（不必存两份）、**降延迟**（TTFT 更短）。★ 注意：**省显存这件事与上一类的块管理器是同一个机制**
（命中一个块就是给它的 `ref += 1`），本文只新增**「怎么找到那个块」**这一步。
★★ **KV 重算的机制与代价账**（换出 vs KV 重算、临界长度 `s*`）**正文在**
`batching-and-scheduling/03-preemption-and-fairness.md`，此处**只回链**。

**一个具体的对照场景**（本文程序里的真算例，块大小 `4` token、`8` 条请求）：

| | 数值 |
|---|---|
| 全部块数 | **`22`** |
| 命中（可复用）块数 | **`14`** |
| **命中率** | **`14 / 22 = 0.6364`** |

★★ **定义先摆出来**：本文的**命中率** = `Σ_请求 命中块数 / Σ_请求 总块数`。
★★★ **分母是「全部块」而不是「请求数」** —— 换一个分母会得到**另一个数**：
`14 / 8 = 1.75`（**大于 1，显然不是命中率**）。这是本库「**报数必报口径**」的直接应用。

**一条必须先说清的口径**（`[B]` 级，vLLM 文档，抓取日 2026-10-09，逐字）：

> 「we **hash each kv-cache block** by the tokens in the block and the tokens in the prefix before the block」
> 「**We only cache full blocks.**」

★★★ **两条都要**：块的键**含前缀链**（同一个块内容在不同前缀下是**不同的键**），
而且**只有整块**进缓存（末尾不满一块**既不入缓存、也不参与命中**）。
★ 这是 **vLLM 的实现口径**，**不得**说成「前缀共享的通用规律」。

## 1. 原理

### 第一步：把「块」变成「键」

**键 = 一个哈希值**，它的输入是**两样东西**：**本块的 token** 与 **本块之前的前缀的键**。

```
键(第 i 块) = hash( 键(第 i−1 块), 本块的 token )
键(第 0 块) = hash( 空前缀, 本块的 token )
```

★★ **为什么键里要带前缀**：因为**同一个块的内容，在不同前缀下是不一样的 KV**。
序列 A 是 `[x][y]`、序列 B 是 `[z][y]`——两块 `[y]` 的**内容和它要 attend 的上下文都不同**，
**绝不能互相复用**。★ 把前缀链折进键，就是让它们**映到不同的键**。

### 第二步：命中与命中率（**两条独立路径**）

找到块有**两条完全不同的路**：

| 路径 | 怎么做 |
|---|---|
| **被测**：`hash → 块` | 逐**整块**算键、查缓存；键在 ⇒ 命中、复用；不在 ⇒ 新建并写入缓存 |
| **参照**：**逐 token 朴素比对** | 拿当前请求与**之前每一条**请求**逐 token** 比最长公共前缀（LCP），再 `// 块大小` |

★★★ **判据**：在**构造的前缀结构**上，两条路径给出的**命中块数必须逐条相同**。
★ 一面走**哈希表**、一面**逐 token 比**——**两条独立路径的会合**。
★★ 程序 `A.1` 判它，`D.4` 把哈希**故意改成常数**（所有块撞在一起）证明这个等式**对「键唯一标识内容」是敏感的**。

★★ **命中率的定义**（本文的分子分母口径）：

```
命中率 = Σ_请求 命中块数  /  Σ_请求 总块数
```

### 第三步：★★★ 驱逐 —— 只能逐出「没人在用」的块

缓存**不会无限大**，满了就要**逐出**。本文取 **LRU**（Least Recently Used）：
**逐出最久没被访问的块**。★★★ 但有一条**硬约束**：

> **只能逐出 `ref == 0` 的块。**
> 一个块只要**还被某条活序列指着**（`ref > 0`），逐出它 = **把那条序列的 KV 删了**。

★ 这与上一类的**引用计数**是**同一个数**——本文只是给它加了第二个用途（**驱逐的过滤器**）。
★★ **`C.2` 把这条约束的反例跑了出来**：忽略 `ref > 0` ⇒ **正在被用的块被逐掉 ⇒ 那条请求的块消失了**。

★★★ **驱逐策略不止「选哪个块」，还有「哪些块【不许被选】」** —— 一个真实实现（vLLM）在 KDA（循环模型）
那条路径上加了 `VLLM_PREFIX_CACHE_RETENTION_INTERVAL`，做**区间化保留**：把一段前缀的缓存**按区间**留住，
而不是交给 LRU 随意逐出。★ **它的正文在** `45-kernel-lifecycle/requirement-discovery/01:187`
（★ 该处自标「**经检索转述**」，非逐字）—— **本文只回链，不重写那一段**。
★★ 读法：**「保留区间」是驱逐策略的【另一个维度】** —— LRU / FIFO 决定**选谁**，
保留区间决定**谁在候选之外**；★ 本文的 `ref == 0` 过滤是最简单的一种「候选之外」（**在用的一律不选**）。

### 第四步：LRU 的收益账

命中率**随缓存容量单调不降**。本文算例（访问序列 `400` 步、去重键 `16` 个）：

| 缓存容量（块） | 命中数 | 命中率 |
|---|---|---|
| `2` | `136` | `0.3400` |
| `4` | `266` | `0.6650` |
| `8` | `350` | `0.8750` |
| `16` | **`384`** | **`0.9600`** |

★★ **同表还有一列 FIFO**（`B.1` 逐格钉住）：`2 / 4 / 8 / 16` 块上 FIFO 命中 = `138 / 250 / 327 / 384`
—— ★★★ **注意 `cap = 2`：FIFO `138` > LRU `136`**（★ 两者**无普遍次序**，见 §2（3））。

★★★ **与 `engines/02` 的 LRU【不是同一件事】**（`S3` 互指）—— 那里的缓存单位是**条序列**
（**数据结构层**，radix tree 判成员）；这里的单位是**块**（**系统侧块管理**，带 `ref == 0` 过滤器
与「保留区间」那一维）⇒ ★ **命中率口径不同、不可互相套用**。

★★★ **一个免费的下界**：容量 `≥` 去重键数（`16`）时，**唯一的缺失是每个键的第一次**（**强制缺失**）：

```
命中 = 长度 − 去重键数 = 400 − 16 = 384
```

★★ **这条下界与替换策略无关**——LRU 与 FIFO 给**同一个数**（本文 `B.2` 判它）。
⇒ ★ 所以容量够大时，**比策略好坏没有意义**；策略只在**装不下**时才开始起作用。

### 第五步：★★★ 前沿分支 —— 循环模型下，三个概念必须拆开

**上面整套机制有一个隐含前提**：**每个 token 有一对独立的 `(K, V)`**。
有一类模型**不满足**这个前提：**线性注意力 / 循环模型**（如 KDA、SSM 这一类）——
它们推进的是一个**矩阵状循环状态 + 一个短卷积状态**，**不存 per-token KV 对**。

★★★ 于是「块」这件事在它们身上**裂成三个原本绑在一起的概念**（`[B]`，**经检索转述**）：

| 概念 | 它原来的含义 |
|---|---|
| **物理块大小** | 一个物理存储块装多少个 token |
| **调度器对齐** | 调度器按什么粒度切分一批工作 |
| **前缀匹配单元** | 两个请求「前缀相同」的判据按什么粒度比 |

★ 在「每 token 一对 KV」的模型里，**这三者碰巧可以是同一个数**（vLLM 的 `16`）；
**在循环模型里它们必须分开**——因为**「KV」不再是逐 token 的**，
「前缀匹配单元」**不能**再等于「物理块大小」。
★ 该实现还规定：命中**部分块**时**先把缓存状态拷进私有目的地再扩展**（就是上一类的 **copy-on-write**）。

★★★ **来源级别**：这一条是 **`[B]` 且【经检索转述】** —— 本库
`45-kernel-lifecycle/requirement-discovery/01:187` 自己标注了「**经检索转述**」（**未逐字读到**），
★★ **本文照抄这一档**：**不得**写成逐字引文、**不得**升格为 `[A]`。
★ 该处的用途也值得记住：它是「**算子清单算不出什么**」的**边界声明**
（原文下一句：「从 config 推出的清单…**算不出『缓存层要重构成什么样』**」）。

## 2. 执行映射

引擎层。前缀缓存在**每一条请求到达时**被查一次，它的产物是「**这条请求的哪几块可以复用**」。

**（1）三个组件**：

| 组件 | 动作 | 本文的量级 |
|---|---|---|
| **键函数** | 把「前缀键 + 本块 token」混成一个整数 | 本文是**确定性**乘加（★ **不是** Python 的 `hash()`——后者对字符串随 `PYTHONHASHSEED` 变） |
| **前缀缓存**（键 → 块） | 查 / 插 / 逐出 | `22` 块规模（本文算例） |
| **驱逐器** | 选一个 `ref == 0` 的块淘汰（LRU） | ★★ **过滤器是 `ref == 0`**（§1 第三步） |

**（2）★ 一条容易踩的量化事实**：**命中率的分母口径**。
本文 `14 / 22 = 0.6364`；如果把分母写成「请求数」会得到 `1.75`。
★★ 同一份数据，**两个分母给出两个「都对」但不可比的数**——这是本库 `P9` 的形态。

**（3）★ 另一条**：**LRU 与 FIFO 【没有普遍次序】**——
容量 `4 / 8` 上 LRU 占优（`266 / 350` vs FIFO `250 / 327`），
★ 而 **`cap = 2` 上 FIFO 反超**（**`138` vs LRU `136`**）；容量够大（`≥` 去重键数 `16`）时二者**同值**（都 `384`）。
★★★ **所以「LRU 一定比 FIFO 好吗」是个错问题** —— 方向**取决于访问序列与容量**；
★★ 能确定的只有一条：**容量够大时二者相等**。★ 「用哪种策略」**先要回答「装不装得下」**。

**（4）★★ 本节产物是「机制与上界」，不是「真实性能」。**
本机**无 GPU、无引擎** ⇒ 上面的数**没有一个**来自真实系统（★ 更不是任何引擎的前缀缓存命中率）。
★★★ **限定语**：「不是任何真实引擎，也不是真机」。

## 3. 实现与演进

**第一步：无前缀缓存。** 每条请求从头 prefill。失败模式：**公共前缀被重复计算**——
多轮对话的每一轮都在对前面几轮做 **KV 重算**（★ **KV 重算**的代价账正文在
`batching-and-scheduling/03-preemption-and-fairness.md`，此处回链）。

**第二步：按内容找块（`hash → 块`）。** 把「前缀键 + 本块 token」变成键，去缓存里查。
★ 本文算例：`22` 块里 **`14` 块命中**（`0.6364`）。
★ 这一层的**新失败模式**是**哈希碰撞**（§4.1）。

**第三步：驱逐（LRU + `ref == 0` 过滤）。** 缓存满了逐出最久未用的**空闲**块。
★ 这一层的**新失败模式**是**逐出掉仍在用的块**（§4.2）。
★★ 注意：**驱逐是「另一个方向的复用」**——命中让 `ref` 上升，驱逐必须等 `ref` 归零，
**两件事由同一个引用计数管**（上一类的 `ref`，本文加了第二个用途）。

**第四步：前沿 —— 循环模型（通往 `engines`）。** 模型不再逐 token 存 KV 时，
**块 / 对齐 / 前缀匹配三个概念必须拆开**（§1 第五步）。
★★ 这条是**本主题的边界**，也是 `engine` 主题的入口（各家的选择差异）。

## 4. 踩坑与失败模式

### 4.1 哈希碰撞 ⇒ 命中到**错的块**

- **现象**：命中率**看起来更高**了，但**复用的内容是错的**；
- **成因**：`hash → 块` 的**全部前提**是「**键唯一标识内容**」；键撞了，就等于
  **把两条不相关的序列的 KV 当成同一个**；
- **本机实测**（`code/` 的 `C.1`）：把键改成**常数**后，某条请求「复用」到了
  `(10,47,31,20,32,24,15,21,45,31,26,11)`，而它真正的前缀是
  `(32,24,15,21,45,31,26,11,64,96,93,67)` —— **完全不同的内容**；
- **规避**：★★ **键必须包含【前缀链】而不只是本块**（§1 第一步）；★ 且生产实现要用**足够宽**的哈希
  （vLLM v0.11 起默认 `sha256`，`[B]`）。

### 4.2 逐出掉**仍在用**的块

- **现象**：某条**正在解码**的序列，它的块**突然不见了**（要么读到别的内容，要么崩溃 / 需 **KV 重算**）
  （★ **KV 重算**的代价与判据正文在 `batching-and-scheduling/03-preemption-and-fairness.md`，此处回链）；
- **成因**：驱逐器**只看 LRU 顺序**，**没看 `ref`**；
- **本机实测**（`code/` 的 `C.2`）：池容量 `4`、`K0` 的 `ref = 1`（正在被用）；
  正确驱逐**保留了 `K0`**（逐出的是已归还的 `F*`），**坏法把 `K0` 逐掉了**；
- **规避**：★★ **驱逐候选必须按 `ref == 0` 过滤**（与上一类的回收条件**是同一个条件**）；
  ★ 缓存全被占用时的**正确行为是「等」或「拒绝」，不是「逐一个正在用的」**。

### 4.3 把「末尾不满一块」也算进命中

- **现象**：命中率**虚高**，复用的块**多算了最后那半块**；
- **成因**：口径是「**只缓存整块**」（`[B]`，vLLM 逐字 `We only cache full blocks.`）；
  ★ 末尾不满一块的块**既不入缓存、也不参与命中**；
- **本机实测**（`code/` 的 `D.9`）：长度**不足一块**（`3` token < `4`）的请求**命中 `0`**；
- **规避**：★★ **命中口径必须写明「按整块」**，且**两边（分子与分母）用同一条口径**（§1 第二步）。

### 4.4 在循环模型上照搬「块」的三合一

- **现象**：把「物理块大小 = 前缀匹配单元」直接搬到线性注意力 / 循环模型上，
  结果**前缀匹配的粒度是错的**；
- **成因**：这类模型**不存 per-token KV 对**（推进的是循环状态），
  「前缀相同」**不再能按 token 粒度判**（§1 第五步）；
- **规避**：★★★ **在循环模型上，块 / 对齐 / 前缀匹配【三个概念必须拆开】** ——
  ★ 这是 `[B]`（**经检索转述**）的实现做法，**不是**普适规律。

| 见到「命中率的理论上限」 | ★★ 容量 `≥` 去重键数时，命中 `= 长度 − 去重键数`（**强制缺失**，`B.2`，**策略无关**） |

| 见到「fp8 下还能用前缀缓存吗」 | ★★ **不能** —— 量化后的 cache 不再与原始 token 一一对应；正文在 `130-quantization/kv-cache-quantization/01:138`，此处回链 |

## 6. 小结与延伸

**一句话**：**前缀共享 = 把「块 + 前缀链」哈希成键去缓存里查；命中就复用（`ref += 1`），
缓存满了就 LRU 逐出 `ref == 0` 的块 —— 而正不正确全看「键唯一标识内容」与「只逐空闲块」两条。**

**三条可独立复用的结论**：

1. ★★★ **键里必须带前缀链**（否则不同前缀下的同内容块会被误复用）—— `C.1` 是它的反例；
2. ★★★ **驱逐的过滤器是 `ref == 0`**（与上一类的回收条件是同一个条件）—— `C.2` 是它的反例；
3. ★★ **命中率是有口径的量**：`Σ命中块 / Σ总块`，且**只按整块**；容量够大时退化成「长度 − 去重键数」。
