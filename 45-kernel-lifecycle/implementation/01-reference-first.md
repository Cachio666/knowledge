# 参考实现先行：共享代码的参考实现，捕获率为零

> **参考实现必须与被测实现独立。共享代码的参考实现，对「两者共有的那部分错误」的捕获率是 `0`——而且它给出的对照结果会看起来完全正常。**
>
> **一条可机械判定的论断**：把被测实现与参考实现各拆成「共享部分」与「独立部分」。若 `F = S ∘ f`、`R = S ∘ r`（`S` 共享），那么在比对 **`S` 直接产出的量**时，`F` 与 `R` 的差值**恒为 0**——不是「很小」，是代数恒等。`code/01_reference_independence.py` 的 §C 把这件事跑了出来：捕获数 `0`、报出的最大误差 `0.0`，而同一次运行里独立版参考实现报出 `3.0`。
>
> **前提必须一起写**：零捕获成立要求 ① 比对的是 `S` 之后**未经独立处理**的输出；② 缺陷是**静默的**（不崩、不抛异常）。丢掉任一条，结论就不成立——本程序 §B 与 §C.5 各给了一个反例。

## 0. 背景与动机

### 0.1 「我有参考实现了」的两种含义

写完一个算子，最常见的下一句话是「我拿参考实现对过了，没问题」。这句话至少有三种强弱完全不同的形态：

| 说法 | 参考实现是什么 | 它能捕获什么 |
|---|---|---|
| 「我自己看着对」 | 没有参考实现 | 什么都捕获不了（不能失败的测试） |
| 「我写了个对照」 | 一份手写的、与被测实现**共用 helper** 的版本 | 只捕获「独立部分」的错误 |
| 「我有独立参考实现 + 明确容差」 | CPU fp64 / 框架内置 op / 朴素版，且**不共享任何代码** | 连「共享部分」的错误也能捕获 |

差别不在「写了没有」，而在**共享了多少代码**。

### 0.2 共享代码的隐蔽性：它不报错，它什么都测不出来

这是本篇要建立的最重要的一条直觉：

> **共享代码的参考实现不会「报错」，也不会「给出可疑结果」。它会给出一个 `maxdiff = 0.0`，然后一切照常。**

对照一下两种失败形态：

| | 参考实现写错了 | 参考实现与被测实现共享代码 |
|---|---|---|
| 你看到什么 | 大量红色、`maxdiff` 很大 | **绿色，`maxdiff = 0.0`** |
| 你会怎么反应 | 去查是谁错了 | **通过，继续** |
| 代价 | 一次返工 | 缺陷进入下游，且**测试记录上它是「验证过的」** |

第二种是**静默的**：没有任何信号提示你「这个 `0.0` 不可信」。

### 0.3 本篇在本域主线上的位置：它守的是**上界的前提**

本域的主线是「**到上界还有多远，以及那段距离值不值得走过去**」。四个主题各占一环：

| 主题 | 「上界」在这一环是什么 |
|---|---|
| `requirement-discovery` | roofline 给的理论上界——**上界在哪** |
| `operator-design` | 候选设计各自的上界——**怎么抬高上界** |
| **`implementation`** | **正确性门——上界只有在算对的前提下才有意义** |
| `convergence-and-tuning` | 剩余距离是工程能触及的，还是噪声 |

**本篇站的是「正确性门」这一环的第一格**，理由有三条：

1. **上界是一个数，而数必须挂在「哪一个实现」上。** roofline 算出的算术强度 `AI` 与 ridge point 描述的是**某个具体实现**。如果你的参考实现与被测实现共享了「输入怎么排布」这段代码，那么你验证过的是**两者共有的那一部分**——上界描述的那部分恰好没有验证。
2. **正确性门是唯一的「一票否决」**。前三段都在算「值不值得」，只有这一段问「做不做得到」。**算对之前，一切上界讨论都是空的**——这就是为什么验证必须**先于**性能测量，而不是并列。
3. **这一环的代价是非对称的**：写一个独立参考实现是几分钟的事；而一个没被捕获的缺陷会让**后面所有的性能数字都失去含义**（你在优化一个算错的算子）。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。下面所有函数都是**数组变换**——它们是「共享子表达式」这个代数结构的最小可运行模型，与 GPU 无关。

## 1. 原理：拆成「共享部分」与「独立部分」

### 1.1 记号

把被测实现拆成两段：

```text
F = S ∘ f          S = 与被测实现、参考实现**共有**的那段代码
R = S ∘ r          f = 只属于被测实现的那段
                   r = 只属于参考实现的那段
                   r' = 完全不经过 S 的另一份参考实现
```

`S` 是**任意**一段代码：一个 padding 函数、一个 padding 到 4 的倍数的 helper、一个形状规范化步骤、一个量化/反量化对、一个索引映射。它是「两边都调用的那个东西」。

### 1.2 定理（这一条是代数恒等，不是经验）

> 若 `F = S ∘ f`、`R = S ∘ r`，则在比对 **`S` 直接产出的量**时：
>
> ```text
> F(x) − R(x) 的「共有部分」 = S(x) − S(x) ≡ 0
> ```
>
> ⇒ **`S` 中的任何错误在 `F` 与 `R` 上同时出现**，差值恒为 `0`。**捕获率为零。**

**为什么这是恒等而不是「多半如此」**：`F` 与 `R` 的差异完全由 `f` 与 `r` 决定。`S` 只是一个共同的前缀，它出什么错，两边**同向**地错——而差分测试比的是**差**。

**前提（丢掉任一条，结论不成立）**：

1. **比对的是 `S` 之后未经独立处理的输出**。如果参考实现拿 `S` 的输出**再做一次独立变换**（例如自己重新算一遍索引），那么 `S` 的错误有可能被那个独立变换暴露出来。
2. **缺陷是静默的**。只改结果的值，不改控制流。若缺陷导致崩溃/异常，那不是「捕获」而是**假捕获**（§1.5）。

### 1.3 用本库的程序跑一遍

`code/01_reference_independence.py` 用最小的数组结构把这个定理跑了出来（`n = 13`，元素是 0–9 的随机整数，固定种子）：

```text
共享代码 S：把序列补到 4 的倍数（缺陷 = 用 1.0 而不是 0.0 填充）
F        = S 之后按 4 个一组求和            （被测实现）
R_shared = S 之后按 4 个一组求和（另一套写法）（共享 S 的参考实现）
R_indep  = 只对真实存在的元素求和            （完全不碰 S 的参考实现）
```

| | `F` vs `R_shared` | `F` vs `R_indep` |
|---|---|---|
| 无缺陷（对照组） | **0.0** | **0.0** |
| 缺陷在**独立部分**（分组丢最后一个元素） | **7.0**（捕获） | **7.0**（捕获） |
| 缺陷在**共享部分**（补位值 `1.0` 而不是 `0.0`） | **0.0 ⇒ 捕获数 0** | **3.0**（捕获） |

三行对照读出来的东西：

- 第二行证明**定理的作用域是「共享的那一部分」**，不是「共享代码版参考实现**整体**」——缺陷落在 `f`（两边各自的那段）时，它照样捕获。
- 第三行的 `3.0` 不是调出来的，是 `(-13) % 4`。换成别的 `n` 就换数——**所以它是可反驳的**：程序断言它恰好等于 `(-N) % 4`。
- 第三行的 `0.0` 是**恒等**：不是「小于容差」，是 `0.0` 本身。它**能通过本库收录的最紧那条容差**（`1e-8`）。所以它不是「差点没抓到」，而是**显示一切正常**。

### 1.4 「独立」是一个可以被机械判定的性质，不是一个态度

本节最重要的可操作结论：

> **给共享代码装一个调用计数器，参考实现跑完后计数必须恰好为 `0`。**

`code/01_reference_independence.py` 的 §D.1 就是这么做的：

```text
R_indep  调用 S 的次数 = 0     ⇒ 独立
R_shared 调用 S 的次数 = 1     ⇒ 确实共享了
```

⇒ 「我们的参考实现是独立的」这句话在本篇里**有判据**。这比任何自我声明都强：它把「独立性」从一个只能靠人自觉的约定，变成了一个**可以被测试钉住**的性质。

**第二条机械判据**（对应 §4 的坑 ③）：**参考实现不得比被测实现更复杂**。
本篇用**语句节点数**作为代理指标（`ast` 数 `stmt` 节点）。本程序里 `F = 7`、`R_indep = 4`。
⚠ 这是代理指标，不是「复杂度」的正确定义——**本篇明写它的局限，不假装它是定理**。

### 1.5 三态：捕获 / 漏网 / 假捕获

跑一次对照，结果必须落进三态之一。**把第三态并进第一态是变异测试最常见的自欺方式**：

| 态 | 形态 | 它证明了什么 |
|---|---|---|
| **captured** | 出错的值不相等 | 参考实现**测得出**这个缺陷 |
| **missed** | 值相等（本可以捕获却报通过） | 参考实现**测不出**这个缺陷 |
| **false_capture** | **抛异常/崩溃** | 只证明「有地方不对」，**不是**「这个缺陷被测出了」 |

第三态为什么危险：一个会崩的缺陷，在「跑一下看失败没失败」的粗略判据下**看起来是被捕获了**。但它没有告诉你**参考实现有没有能力捕获这个缺陷**——崩溃可能来自参考实现自己，也可能来自测试脚手架。

> ★ **本主题的第一版在这里踩过坑**（本域规格 §Chunk3 逐字记录）：设计 C 类时用的缺陷是「少补一个元素」，`reshape` 直接抛 `ValueError: cannot reshape array of size 15 into shape (4)`。脚本**崩了**，而当时的判据会把「崩溃」记成捕获。**缺陷必须是静默的：只改结果的值，不改控制流。**

## 2. 执行映射：一个工程把三份东西合成一份（**[B] 级 · vLLM 的做法**）

### 2.1 `@register_op` 的 native 实现：三个角色

vLLM 的 IR（`vllm.ir.op`）里，一个 `@register_op` 装饰的算子自带一份 **native 实现**，官方文档明确它承担**三个角色**：

| 角色 | 含义 |
|---|---|
| **semantic definition** | 它**定义**了这个算子的语义（形状、stride、边界行为） |
| **default implementation** | 没有别的实现可用时用它（provider 名 `native`，恒 `supported=True`） |
| **test baseline** | 别的 `register_impl` 注册的实现**必须与它一致** |

**这三合一解决的是「漂移」**：声明、默认实现、测试基线如果是三份东西，它们会各自演化、互相不一致。

> ⚠ **但它不解决本篇的问题（P7：引文与断言作用域不匹配）。**
> native 既是语义定义又是测试基线，意味着：**拿 native 当参考实现去测另一份实现时，参考的独立性来自「两份实现是不同的人写的」，不是来自「native 更正确」。** 如果两份实现共享了一段代码（例如同一个 layout 规范化 helper），本篇 §1 的定理照样成立。

### 2.2 强度是**两层**，而且都不判 batch size

`register_impl(provider, *, supported=True, supports_args=None, inplace=False)` 的两层检查分工明确：

- `supported` 是**静态布尔**（import 时求值一次）——只用于**平台/库是否存在**；
- `supports_args` 是**动态谓词**（按类型与形状判）——编译期拿 fake tensor 调，eager 路径拿真 tensor 调。

官方文档明确要求 `supports_args` **不得**检查 batch size、也不得加「基于取值」的守卫。这不矛盾：**batch size 不改变「构建出哪个 kernel」**，它只改变同一个 kernel 的调用参数。

**本主题关心的是它对本篇主线的意义**：支持性检查跑在**热路径**上，所以它的签名被限制（不许有关键字专用参数）。**一条性能考虑反过来约束了接口**——这与 `operator-design` 的 compile key 是同一件事的两面：**接口的形状由「什么时候被调用」决定**。

### 2.3 ★★ 两个 `0.0`：同一个数，含义相反

vLLM 的 IR 测试基础设施里有一条判据：

> **「dispatch 路径 vs 直接调用」的输出必须 `恰好一致`（`rtol=0, atol=0`）。**

也就是说，同一个实现通过两条路径被调用时，差必须是 **`0`**。

**这和本篇 §1 的 `0.0` 是同一个数值、相反的含义**：

| 场景 | `maxdiff == 0.0` 的含义 |
|---|---|
| dispatch 一致性（同一个实现的两条调用路径） | **正确**——两边本来就是同一个东西，差为 `0` 是**期望** |
| §1 的共享代码参考实现 | **测不出来**——两边共有一个错误的 `S`，差为 `0` 是**失效** |

> ★★ **所以看到 `maxdiff == 0.0` 时，第一个问题不是「通过了吗」，而是「两边是不是同一个东西」。**

这条把 §1 的定理从一个代数命题变成了**工程上每天都会遇到的判读错误**：一个测试报了 `0`，它可能是最好的结果，也可能是最坏的结果，而**输出长得一模一样**。

### 2.4 容差比对查不出的两件事

vLLM 的 op 测试基础设施还有一条独立检查 `opcheck`：**参数是否被就地修改**、**输出是否与输入别名**。

这两件事**容差比对一件都查不出**：一个把输入原地改掉的实现，输出可以完全正确。⇒ **验证矩阵里必须有一维不属于「数值比对」**（见 `02-verification-matrix` 的「对抗输入」维）。

## 3. 从「随手写个对照」到「独立参考 + 明确容差」

三步，每一步都有一个**可判定的完成条件**：

| 步 | 做什么 | 完成条件 |
|---|---|---|
| ① | 选参考实现的**来源** | 能指名它属于哪一档（见下），且**不是**「我自己再写一遍」 |
| ② | 证明它**独立** | 共享代码的调用计数为 `0`；且语句数不多于被测实现 |
| ③ | 定**明确的容差** | 能说出这个数从哪来（哪个 dtype 的 `u`、哪次标定），而不是「试出来的」 |

**参考实现的选取规则**（按**独立性**排序，不是按精度、也不是按速度）：

| 优先级 | 来源 | 独立性来自哪 | 本库的例子 |
|---|---|---|---|
| ① | **CPU 上的 fp64 / fp32 实现** | 与被测的 GPU 路径**机制不同** | `40-kernels/*/code/verify.py` 用 numpy 写参考 |
| ② | **框架已内置的等价 op** | **实现者不同** | `torch.<op>` / `numpy.<op>` |
| ③ | 手写**明显正确的朴素 NumPy 版** | **算法不同** | 分块 → 直接求和 |

> ⚠ **第三档是最弱的一档**：朴素版一旦与被测实现**共用同一个 helper**，就退化成 §1 的定理。
> ⚠ **「改用 CPU fp64」不会自动带来独立性**——如果你把 GPU 上的 layout 计算原样搬到 CPU，那仍然是共有的 `S`。

**外部对齐**：arXiv:2606.20128（**预印本，未确认同行评审**）用的正是 **fp64 CPU 参考 + 逐 (op,dtype) 容差**，与本库规则的第一档一致。⇒ 两处**独立**的做法指向同一个选择。

## 4. 踩坑与失败模式

### 4.1 参考实现调用被测实现的子函数

最直接的形态。它常常是「无意的」：被测实现里有一个写得挺清楚的 `_compute_offsets()`，参考实现顺手就用了。

**判据**：这是 §1 定理的最强形态——共享的是**整个** `S`。**后果**：`maxdiff` 恒为 `0.0`，一整个函数体的错误落在盲区里。

### 4.2 两者共用同一个 helper

例如同一个 padding 函数、同一个 dtype 转换、同一个索引映射表。

**判据**：这是 §1 定理的**最隐蔽**形态——因为「用一个 helper」在工程上是**好习惯**。共享的范围比 4.1 小，漏报的范围也小，但**仍然不是零**。

**处置**：不是「禁止共用 helper」，而是**知道共用了哪些、并为它们单独写测试**。本程序 §D.1 的调用计数器就是给这件事用的。

### 4.3 参考实现比被测实现还复杂

一旦如此，**出错时无法判断是哪边的错**。你会花时间 debug 一个其实是对的参考实现。

**判据**：语句节点数（或任何一致的复杂度代理）。本程序断言 `R_indep` 的语句数 **不多于** `F`。

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**（本机无 GPU，本域任何一篇都不得声称有实测数据）。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 参考实现调用了被测实现的任何函数 | **停**——共享了 `S`，对 `S` 里的错误捕获率为 0 |
| 2 | 两者共用一个 helper | 知道是哪一个，并**为它单独写测试**；不要以为差分测试覆盖了它 |
| 3 | 比对结果的 `maxdiff == 0.0` | 先问「**两边是不是同一个东西**」——是 ⇒ 可能是 §1 的失效；不是 ⇒ 才是正确 |
| 4 | 要给「独立性」一个判据 | 共享代码的**调用计数 == 0**；不是靠声明 |
| 5 | 参考实现比被测实现复杂 | **换一个**——出错时无法归因 |
| 6 | 注入的缺陷导致崩溃/异常 | 记成 **`false_capture`**，**不得**并进捕获数 |
| 7 | 要设计一个「测不出」的反例 | 缺陷必须**静默**：只改结果的值，不改控制流 |
| 8 | 选参考实现的来源 | 按独立性排序：CPU fp64/fp32 → 框架内置 op → 朴素 NumPy |
| 9 | 想用「我搬到 CPU 上重写了一遍」当理由 | **不算**独立——如果算法与数据排布没变，`S` 没变 |
| 10 | 要断言「native 是测试基线」 | 可以，但它解决的是**漂移**，**不是**共享部分的错误（P7） |
| 11 | 同一个实现经由两条路径调用 | 判据是 **`rtol=0, atol=0`**（必须逐位相同）——这时 `0` 意味着**正确** |
| 12 | 测试要查「参数被就地改」「输出与输入别名」 | 容差比对**查不出**，必须另写检查（vLLM 用 `opcheck`） |
| 13 | 要引用一条外部规则 | 先问**检索了几次**：两次独立一致 ⇒ 可写「逐字」；一次 ⇒ 只能写「经检索转述」 |
| 14 | 要举一个「参考实现漏报」的例子 | 先确认它**有出处**；没有 ⇒ **明写是本库构造的**并记进 `UNSOURCED` |
| 15 | 参考实现的注释只出现在注释里、没有任何断言 | 删除它——注释不会被任何测试钉住（本库 C6 教训） |

**闭合性检查**：读完这张表能把「这个参考实现算不算独立、这个 `0.0` 能不能信、这个缺陷算不算被测出」判完。**唯一的表外输入**是「被测实现与参考实现到底共享了哪些代码」——它取决于具体的实现，必须去读代码（本库不做具体 kernel 实现，回链 `40-kernels`）。

## 6. 小结与延伸

- ★ **参考实现必须与被测实现独立。** 共享代码的参考实现对「两者共有的那部分错误」的捕获率是 **`0`**，而且它给出的对照结果会**看起来完全正常**（`maxdiff = 0.0`，能通过最紧的容差）。
- ★ **零捕获是代数恒等，不是经验**：`F = S ∘ f`、`R = S ∘ r` ⇒ 比对 `S` 直接产出的量时，差值 = `S` 的错误 − `S` 的错误 ≡ `0`。
- ★ **前提必须一起写**：零捕获只在「比对 `S` 之后未经独立处理的输出」且「缺陷静默」时成立。**不得**写成「共享代码的参考实现一定测不出任何 bug」——本程序 §B 就是前提①的反例。
- ★ **「独立」有判据**：共享代码的调用计数必须为 `0`。这一条把独立性从自我声明变成可测试的性质。
- ★ **三态必须分开**：捕获 / 漏网 / **假捕获**（崩溃）。把第三态并进第一态是变异测试最常见的自欺方式。
- ★ **`maxdiff == 0.0` 有两种相反含义**：同一个实现的两条路径比 ⇒ **正确**；共享代码的参考实现比 ⇒ **测不出来**。输出长得一模一样。
- ★ **选取顺序的判据是独立性**：CPU fp64/fp32 → 框架内置 op → 朴素 NumPy。**「搬到 CPU 重写」不等于独立**。
- ★ **vLLM 的 native 三合一解决漂移，不解决本篇的问题**——作用域要写对（P7）。
- ★ **构造就是构造**：本库没有找到「共享参考实现漏掉真实缺陷」的公开案例，§C 是本库构造的仿真；外部论文自陈它的 buggy 变体也是作者播种的。

**延伸**：

- 容差怎么按 dtype 定（以及为什么「按 dtype 定」**不够**）：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- 结果不对时该按什么顺序查：`45-kernel-lifecycle/implementation/03-debug-order`。
- 契约与 cache key 的关系（「跑的其实是另一个 kernel」）：`45-kernel-lifecycle/operator-design/01-interface-contract`。
- 数值设计的误差预算（`u` 与 `γ_K` 从哪来）：`45-kernel-lifecycle/operator-design/02-numerical-design`。
- 各算子的具体实现与它们各自的 `verify.py`（本域**不讲**的边界）：`40-kernels/*`。

本篇对应的编号程序是 **`code/01_reference_independence.py`**。它**不 import torch**、不碰 GPU、**不含任何 kernel 实现代码**（`S`/`F`/`R_*` 都是数组变换）。

- **A 类**：无缺陷（对照组）时两个参考实现都报 `0.0`；补位个数恰好等于 `(-N) % 4`；三者输出长度一致。
- **B 类**：缺陷位于**独立部分**时两个参考实现**都能**捕获（本程序实测 `maxdiff = 7.0`）；并指出「把共享范围从 `S` 扩大到 `S∘f` 就都测不出来」。
- **C 类**（★★ 本篇最关键的 C 类）：缺陷位于**共享代码**时，共享版参考实现的**捕获数为 0**、报出的最大误差**恰好是 `0.0`**（能通过本库收录的最紧容差 `1e-8`），而同一次运行里独立版捕获到 **`3.0`**；再用 §C.5 演示**假捕获**（崩溃 → `ValueError`，必须记成 `false_capture`）；最后把**三个含义不同的 `0.0`** 并排断言。
- **D 类**：`specs.py` §1 的每条常量逐条被断言钉住；含两条**机械独立性判据**（共享代码调用计数、语句节点数）与一条 `ast` 的**跨程序常量覆盖检查**（三个程序的 `COVERED_*` 并集 == `specs.py` 的全部模块级常量，且两两不交）。
- **§L 结构守卫**（★ 在任何使用之前）：把本篇用到的**容器常量的逐格字面量**先钉住。
  粒度是**叶子**而不是常量名——元组/字典里**每一个字面量**都算一个待钉住的叶子。
  两个理由：① 字典的**键**被改错时，`SP.VLLM_DEFAULT_TOLERANCES[d]` 会抛 `KeyError`，
  那是 **harness 异常**（假捕获）而不是断言失败；② 只钉住「常量名」这一层，
  元组/字典**内部**的元素就没人管。本篇还额外有一条**跨程序引用的结构前置条件**：
  §C.3 索引的 `VLLM_DEFAULT_TOLERANCES` 的**归属是 02 篇**，所以这里只先验它的**键集合**，
  取值由 02 篇钉住（**引用 ≠ 归属**）。

判据若被改错，程序以**非零码**退出。
