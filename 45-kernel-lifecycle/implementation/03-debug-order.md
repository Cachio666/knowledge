# 调试顺序：依赖顺序在步数模型下最优，在成本模型下不是

> **调试顺序影响所需步数**，而且这个影响可以算出来。把 kernel 执行建模成**分层依赖** `layout → copy → compute → edges`，两个模型给出两个不同的答案：
>
> - **步数模型**（每查一层算 1 步）：依赖顺序 = 按先验降序排列，**恰好最优**（期望步数 `2.08`）；
> - **成本模型**（排除一层要花若干步）：依赖顺序**不是最优**（`6.16` vs 最优 `5.82`），最优序把便宜的 `edges` 提到昂贵的 `compute` 之前。
>
> **★ 一条确切的门限**：依赖顺序在成本模型下最优 ⟺ `c(compute)/p(compute) ≤ c(edges)/p(edges)`。解出 **`c(compute) ≤ 2 × 0.22 / 0.13 = 3.3846`**，而实际是 **`6`**。⇒ **正文不得写成「按依赖顺序检查总是最好」。**
>
> **★ 两条真的跑出来的错误结果**：缺陷在 `layout` 层时，按「compute 优先」的直觉顺序在 **8 步预算**内**定位成功 `0 / 200`**（预算被三个 `compute` 吃光，`layout` 在队尾），而依赖顺序 **`200 / 200`**（2 步）；一份**同一输入 200 次重复**的对照显示，顺序累加只有 **1** 个读数，`atomicAdd` 形态有 **71** 个 ⇒ 必须被**拒**。

## 0. 背景与动机

### 0.1 「结果不对」的第一反应，以及它的代价

结果不对时最常见的第一反应是**怀疑数学**：重读公式、手算一遍、加 `printf` 把中间值打出来。

这条直觉在多数时候是对的——但如果缺陷在 `layout`（地址算错了），你会**在 `compute` 层反复找问题**：因为你看到的症状（数值偏差）确实像数学问题，而 `compute` 层能解释这个症状的假设又特别多（索引、同步、精度、展开、指令选择……）。

**代价不是「找不到」，而是「找不到却一直在找」**。这有两种形态，第二种更贵：

| 形态 | 表现 |
|---|---|
| 找到了，但花了十倍时间 | 至少收敛 |
| **在预算内没找到** | 没有信号告诉你「方向错了」；只会持续消耗时间 |

### 0.2 分层：依据是**依赖**，不是「重要性」

```text
layout  →  copy  →  compute  →  edges
（地址）   （搬运）   （数学）    （边界）
```

**后面的层依赖前面的层正确**：`compute` 的输入是 `copy` 搬过来的，`copy` 的读地址是 `layout` 算出来的。

这个结构给出一个**可判定的定位方法**：

> 把上一层的输出替换成**手算的正确值**。若缺陷消失 ⇒ 缺陷在**上一层**。

它不是「重要性排序」——它是一个可以被检验的依赖关系。**这就是为什么顺序可以被讨论，而「重要性」不能。**

### 0.3 本篇在本域主线上的位置：它守的是**上界的前提**

| 主题 | 「上界」在这一环是什么 |
|---|---|
| `requirement-discovery` | roofline 给的理论上界——**上界在哪** |
| `operator-design` | 候选设计各自的上界——**怎么抬高上界** |
| **`implementation`** | **正确性门——上界只有在算对的前提下才有意义** |
| `convergence-and-tuning` | 剩余距离是工程能触及的，还是噪声 |

本篇守的是这一环的**「多快算对」**那一半，理由有三条：

1. **时间预算是有限资源，顺序决定它花在哪**。缺陷在 `layout` 时，一个把预算全部投向 `compute` 的顺序会**永远到不了 `layout`**——这不是「慢一点」，是**结构性地到不了**。
2. **顺序的优劣可以被算出来，不必靠经验**。下面两个模型的期望值都有解析解（其中一个还是一条经典调度规则），可以和穷举 24 个排列的结果逐位对照。
3. **但「固定顺序」不是免费的**。本篇量到它在成本模型下**不是最优**——**把它写成「总是最好」就是本篇要防的那句话**。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。分层模型、成本、先验都是**本库的建模输入**（`[E]`），不是实测。

## 1. 原理：两种顺序，两个模型，两个答案

### 1.1 模型

每一层有两个属性：

| 属性 | 含义 | 本篇取值 |
|---|---|---|
| **成本** `c_i` | 排除这一层**要花多少步**（= 这一层有多少个子假设要逐个排除） | `layout 2 · copy 3 · compute 6 · edges 2` |
| **先验** `p_i` | 缺陷位于这一层的概率 | `layout 0.40 · copy 0.25 · compute 0.22 · edges 0.13` |

**为什么 `compute` 的成本是 6**：数学层能解释「数值偏差」的假设最多（数学、索引、同步、精度、展开、指令选择）；而 `edges` 只要 2 个（尾部、退化形状）。

> ⚠ **这两个字典都是本库的建模输入 `[E]`，没有来源，也测不了**（「一次调试里先怀疑哪层」不是一个硬件量）。本篇的处置是**把它们标成建模输入**，并让程序断言**结论随它们变化**——而不是把它们当成事实（本库 `UNSOURCED` 第 5 项）。
>
> ⚠ **先验是刻意挑成对依赖顺序有利的**：`0.40 > 0.25 > 0.22 > 0.13` **严格递减**。这是**先给对手最有利的条件**，再看结论。

### 1.2 步数模型：每查一层算 1 步

```text
E_steps(顺序) = Σ_i p_i × (层 i 在顺序里的位次)
```

**解析解**：按 `p_i` **降序**排列。为什么——交换论证：若相邻两层的先验是 `p_a < p_b` 且 `a` 在前，把它们换过来，期望值变化 `p_a - p_b < 0`，即更小。⇒ 降序最优。

**本程序量到**：解析解 `(layout, copy, compute, edges)` == 穷举 24 个排列的 argmin，期望步数 **`2.080`**（手算 `0.40×1 + 0.25×2 + 0.22×3 + 0.13×4`）。

### 1.3 成本模型：排除一层要花 `c_i` 步

```text
E_cost(顺序) = Σ_i p_i × (排到第 i 层时累计花掉的步数)
```

**解析解**：按 `c_i / p_i` **升序**排列——这是**史密斯规则**（加权最短处理时间优先）。它是经典结果，本篇不重推（回链调度理论的任何一份讲义），只验证它：

```text
成本/先验 = layout 5.000 · copy 12.000 · edges 15.385 · compute 27.273
⇒ 最优顺序 = (layout, copy, edges, compute)
```

**本程序量到**：解析解 == 穷举 argmin，期望成本 **`5.820`**。

### 1.4 ★★ 两个答案不一样——这就是本篇最该写下来的一条

| | 最优顺序 | 期望值 |
|---|---|---|
| 步数模型 | `(layout, copy, compute, edges)` = **依赖顺序** | `2.080` |
| 成本模型 | `(layout, copy, edges, compute)` ≠ 依赖顺序 | `5.820` |

**同一组先验，两个模型给出两个不同的最优顺序。**

- 步数模型下，依赖顺序**赢了**（先验严格递减 ⇒ 它就是降序序）。
- 成本模型下，依赖顺序**输了**：固定顺序 `6.160` vs 最优 `5.820`。**在给了它最有利的先验的前提下**输的。

⇒ **结论不是「先验没挑好」，是模型本身的差别**：**「排除一层要花几步」不是常数。**

> ★★ **所以本篇的态度是**：依赖顺序是一个**好起点**，不是一条定理。要用它，先说清「每层的排除成本是不是差不多」；不是差不多时，先算一次 `c_i/p_i`。

### 1.5 ★★ 确切的门限：什么情况下依赖顺序不再占优

**依赖顺序成本最优 ⟺ `c/p` 沿依赖顺序升序** ⟺ 相邻两层的约束都成立。本题里真正绑定的是最后一对（`compute` vs `edges`）：

```text
c(compute)/p(compute) ≤ c(edges)/p(edges)
⇒ c(compute) ≤ c(edges) × p(compute)/p(edges) = 2 × 0.22 / 0.13 = 3.3846
```

**实际 `c(compute) = 6 > 3.3846`** ⇒ 依赖顺序不是成本最优。本程序在门限两侧各取一个探测值验证：

```text
c(compute) = 3.1846  → 依赖顺序**是**成本最优
c(compute) = 3.5846  → 依赖顺序**不是**成本最优
```

**另一个边界（步数模型）**：把先验改成 `compute > copy`（`0.40, 0.20, 0.27, 0.13`），步数模型的最优序变成 `(layout, compute, copy, edges)`——**不再是依赖顺序**。⇒ 步数模型下依赖顺序最优的充要条件正是**先验沿依赖顺序递减**。

### 1.6 随机顺序的分布

穷举 24 个排列之外，再看 20000 次随机排列（固定种子）：

| | 均值 | 最小 | 最大 |
|---|---|---|---|
| 期望步数 | `2.4976` | `2.0800`（= 依赖顺序） | `2.9200` |
| 期望成本 | `8.0522` | `5.8200`（= 成本最优序） | `10.3100` |

- 步数模型：依赖顺序的 `2.080` **等于最小值** ⇒ 它是 24 个排列里最优的之一。
- 成本模型：**`1687 / 20000`（`8.4%`）** 的随机排列**优于**依赖顺序 ⇒ 「随便排排」有 8.4% 的概率比固定顺序好，而**最优的那一个比它省 5.5%**。

> ★ 这两个数一起说明：**固定顺序不是「随便排排就行」的反面**，它是**一个有条件的局部最优**。

## 2. 执行映射：工具落点（**[A] 级 · NVIDIA 官方文档**）

### 2.1 `compute-sanitizer` 的**四档**，一档都不能漏

```text
compute-sanitizer --tool memcheck|racecheck|initcheck|synccheck ./app
```

| 档 | 查什么 | **它不查什么**（边界同样重要） |
|---|---|---|
| **`memcheck`**（**默认档**） | global/local/**shared** 的**越界与错位**、硬件异常、`malloc/free` 误用、CUDA API 错误、显存泄漏 | **不查竞争**——越界与竞争是两类缺陷 |
| **`racecheck`** | **仅共享内存**上的三种竞争型态：**WAW / WAR / RAW** | **不查全局内存别名**；**不查确定性** |
| **`initcheck`** | 未初始化就读——**只支持 device global memory** | **不查共享内存**⇒「共享内存未初始化」它报不出来 |
| **`synccheck`** | `__syncthreads()` / `__syncwarp()` 及其 Cooperative Groups 对应物：**块内分歧 / warp 内分歧 / 参数非法** | **不是性能工具**，是正确性工具 |

**三条必须写下来的限定**：

1. **默认档是 `memcheck`** ⇒ **不写 `--tool` 时你只查了一维**：共享内存竞争、未初始化读、同步分歧**都没查**。
2. **`initcheck` 只覆盖 device global memory** ⇒ 它是一句会被误读成「我查过了」的限定。
3. **四档合起来才是有边界的表**：`memcheck` 查越界 **≠** 竞争；`racecheck` 查共享内存竞争 **≠** 全局内存别名、**≠** 确定性；`initcheck` 只查 global **≠** 共享内存未初始化；`synccheck` 查同步分歧 **≠** 数据竞争（两者常同时出现，但检查器不同）。

> ★ **`synccheck` 不得漏，有两条理由**：① 它正对「共享内存同步分歧」这类**边界 bug**——本篇 §3 要定位的正是这一类；② **本库自己在用它**：`40-kernels/reduce-scan/code/verify.py:1255` 与 `40-kernels/reduce-scan/01-reduction-algorithms.md:327`（两处均已打开文件核对）。
>
> ★ **顺带一条可机械判定的判据**：`compute-sanitizer` 的前身 `cuda-memcheck` 在 **CUDA 12.0 起移除**。⇒「照着一篇提到 `cuda-memcheck` 的旧教程做」在 CUDA ≥ 12 的环境里**命令不存在**。这不是风格问题。

### 2.2 确定性：**多 seed 重复，非确定性则拒**（**[B] 级 · PyTorch 官方文档**）

`atomicAdd` 是**非确定性来源**：它让浮点加法的**到达顺序不确定**，而浮点加法不满足结合律 ⇒ 「每次求值可能引入不同的舍入误差」。官方把 `index_add_` / `scatter_add_` / `bincount` 等列为使用它的算子。

**本篇量到了这个现象**（同一份输入、`K = 4096`、fp32 累加、200 次重复）：

| 实现形态 | 200 次重复得到的不同读数 | 跨度 |
|---|---|---|
| **顺序累加**（固定顺序） | **`1`** | `-12147.4365` |
| **`atomicAdd` 形态**（随机到达顺序） | **`71`** | `-12147.4824 ~ -12147.3574` |

⇒ **确定性门**：跑 `n` 次，只要出现两个不同的读数就**拒**。

```text
顺序累加   → accept
atomic 形态 → reject
```

> ⚠ **判据必须是「多 seed 重复」，不是「跑一次看着对」**——单次运行**永远**看不出非确定性。
> ⚠ **但也不得外推**：
> - 「跑两次一样」可能是巧合（P5）。本篇展示的是**同一份输入的 200 次重复**。
> - PyTorch 的原话是「这类算子**目前没有简单办法**避免非确定性」，**不是**「所有 `atomicAdd` 都不可复现」。

**`torch.use_deterministic_algorithms(True)` 的三条限定**：

1. 算子无非确定性替代时**抛 `RuntimeError`**（不是静默降级）；
2. **`warn_only=True` 不会真的强制**——非确定性算子照跑，只发一条警告；
3. ⇒ **「我们开了确定性模式」不足以支撑「结果可复现」**：必须同时说 `warn_only` 的取值。

**与规范层的关系**（回链 `operator-design`，本主题不重推）：PTX ISA 明写 `wmma.mma` 的 **`accumulation order` 未规定** ⇒ 「逐位可复现」**不是规范保证的，必须自己保证**。

## 3. 从「打印大法」到分层排查

| 步 | 做什么 | 完成条件 |
|---|---|---|
| ① | 写出**层**与它们的**依赖** | 每一层能指出「它的输入是谁的输出」 |
| ② | 估每层的**成本**（子假设个数）与**先验** | 两个都写下来——它们是**建模输入**，不是事实 |
| ③ | 按 `c/p` 升序排一次 | 与依赖顺序比对；**不同就用算出来的那个** |
| ④ | 用「替换上一层输出为手算值」定位 | 缺陷消失 ⇒ 在上一层 |
| ⑤ | 每一层排除后**记一步** | 预算用完时你会知道「排除了几层」 |

**第 ③ 步是本篇的核心可操作内容**：它把「按什么顺序查」从一个习惯变成一个**可计算的决策**。

## 4. 踩坑与失败模式

### 4.1 先怀疑数学，实际是 stride

最常见的形态。**症状**（数值偏差）指向 `compute`，**原因**在 `layout`。

**代价可以量化**：本篇 §5 量到，在 `layout` 有缺陷时，一个「`compute` 优先」的顺序在 8 步预算内**定位成功 `0 / 200`**——因为 `compute` 一个层就要 6 步，而顺序里它出现了三次。

**处置**：先做**最小化输入**（`J = 65`、退化轴、全零），一个 `printf` 打印地址与索引，比在 `compute` 里找一轮便宜得多。

### 4.2 把 OOM 当内核数学 bug

显存不够常常来自**测试侧**：重复的 `.contiguous()`、忘记 `del` 中间张量、把整批数据一次性搬上卡。这些都不在内核里。

**判据**：OOM 是**资源**问题，不是**数值**问题。把它记进 `compute` 层会污染成本估计——**它是 `copy` 层的邻居**（也是本模型的边界：本模型只覆盖「结果不对」，不覆盖「跑不起来」）。

### 4.3 用单次运行判断确定性

**单次运行永远看不出非确定性。** 本篇 §2.2 的对照里，`atomicAdd` 形态的 200 次重复给出 71 个不同的读数——但你**任意挑一次**都会得到一个**看起来正常**的数。

**判据**：确定性必须用**重复**判；而且**重复次数要写出来**（200 次与 2 次是两回事）。

### 4.4 ★ 以为「按依赖顺序」是一条定理

**本篇量到的反例就在 §1.4**：在给出了最有利的先验的前提下，依赖顺序在成本模型下仍**不是最优**（`6.160` vs `5.820`）。

**处置**：把顺序当成**一个决策**，把它的**前提**写出来（成本是不是常数、先验是不是递减）。这也是本域「不许写正确的废话」那条纪律在调试上的形态——「按依赖顺序查」如果不带前提，就是一句无信息量的话。

### 4.5 把「四个工具跑一遍」当成「验证完了」

`memcheck` / `racecheck` / `initcheck` / `synccheck` 各查**互不覆盖**的东西（§2.1 的第三列）。更关键的是：**它们都查不出「容差吸收了一个静默的数值偏差」**——那是 `02-verification-matrix` 的事。

**判据**：工具报「干净」**不蕴含**「结果对」。两句话说的是两件事。

### 4.6 ★ 把「本库构造的仿真」写成「真实故障」

本篇的分层模型、成本、先验、缺陷位置**全部是本库构造的**。正文已明写。检索没有找到一份可引用的「先怀疑数学导致定位失败」的实测记录（与 `02` 篇共用 `UNSOURCED` 第 5 项）。

| 2 | 每层的排除成本**不同** | 按 **`c/p` 升序**排（史密斯规则）；先与依赖顺序比一次 |
| 3 | 依赖顺序是否成本最优 | 判据：`c/p` 沿依赖顺序**升序**；本题的绑定门限是 `c(compute) ≤ 3.3846`，实际是 `6` ⇒ **不是** |
| 4 | 先验**不**沿依赖顺序递减 | 步数模型下依赖顺序**不再最优**（最优序把先验大的提前） |
| 5 | 缺陷可能在某一层，且该层成本高、位置靠后 | 把**便宜且可能**的层提前，否则预算可能在到达它之前耗尽 |
| 6 | 预算耗尽（没找到答案） | **回头问「是不是顺序错了」**，不是「是不是还不够仔细」——这是个信号，不是「再努力一点」 |
| 7 | 要定位缺陷在哪一层 | 把上一层输出换成**手算的正确值**；缺陷消失 ⇒ 在上一层 |
| 8 | 只跑了不带 `--tool` 的 `compute-sanitizer` | 视为**只查了一维**（默认档是 `memcheck`） |
| 9 | 要查「共享内存未初始化就读」 | `initcheck` **不覆盖共享内存** ⇒ 换别的办法 |
| 10 | 要查 `__syncthreads()` 分歧 | `--tool synccheck`；这是**正确性**工具，不是性能工具 |
| 11 | 要判「这个实现确定吗」 | 用**重复**判（本文用 200 次）；单次运行看不出；**重复次数要写出来** |
| 12 | 一个算子用了 `atomicAdd` 且没有确定性替代 | **不得**纳入逐位比对的测试集；要么换实现，要么降级为容差比对**并明写它不查确定性** |
| 13 | 要说「我们开了确定性模式」 | 同时说 `warn_only` 的取值——`warn_only=True` **不会**真的强制 |
| 14 | 工具报「干净」 | **不蕴含**「结果对」；四档各查互不覆盖的东西，且都查不出「容差吸收了静默偏差」 |
| 15 | 把「跑不起来」（OOM）当成数值 bug | **停**——它是资源问题；本模型只覆盖「结果不对」 |
| 16 | 照一篇提到 `cuda-memcheck` 的旧教程做 | 在 CUDA ≥ 12.0 上**命令不存在**（前身已移除） |
| 17 | 要举一个「顺序错误导致定位失败」的例子 | 先确认它**有出处**；没有 ⇒ **明写是本库构造的** |

**闭合性检查**：读完这张表能把「该按什么顺序查、预算耗尽意味着什么、四档工具各查什么、这个实现算不算确定」判完。**唯一的表外输入**是「每层到底要花几步」——它必须**估**（并写下估计），不能查（本库不做具体 kernel 实现，回链 `40-kernels`）。

## 6. 小结与延伸

- ★ **调试顺序可以被算出来，而且两个模型给出两个答案**：步数模型下依赖顺序最优（`2.080`），成本模型下**不是**（`6.160` vs `5.820`）。
- ★ **确切的门限**：依赖顺序成本最优 ⟺ `c/p` 升序 ⟺ 本题 `c(compute) ≤ 3.3846`，而实际是 `6` ⇒ **不得写成「按依赖顺序总是最好」**。
- ★ **步数模型下依赖顺序最优的充要条件**是先验沿依赖顺序递减；把它改成 `compute > copy`，最优序就不再是依赖顺序。
- ★ **「排除一层要花几步」不是常数**——这是两个模型分歧的唯一来源，也是本篇最重要的一条前提。
- ★ **缺陷在 `layout` 时，「compute 优先」在 8 步预算内定位成功 `0 / 200`**，依赖顺序 `200 / 200`（2 步）。错误结果的形态是**没找到答案**，不是「找到了错答案」⇒ 它不会以「报错」的形式暴露。
- ★ **预算耗尽时必须回头问「是不是顺序错了」**，而不是「是不是还不够仔细」。
- ★ **确定性用重复判**：200 次重复下顺序累加 **1** 个读数、`atomicAdd` 形态 **71** 个 ⇒ `accept` / `reject`。**单次运行永远看不出**。
- ★ **`warn_only=True` 不会真的强制** ⇒「我们开了确定性模式」不足以支撑可复现。
- ★ **`compute-sanitizer` 四档，`synccheck` 不得漏**（本库 `40-kernels/reduce-scan` 两处在用）；默认档 `memcheck` ⇒ 不写 `--tool` 就只查了一维；`initcheck` **不查共享内存**。
- ★ **工具报「干净」不蕴含「结果对」**——四档都查不出「容差吸收了静默偏差」。

**延伸**：

- 容差怎么定、为什么要标定：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- 参考实现怎么选、独立性怎么判：`45-kernel-lifecycle/implementation/01-reference-first`。
- 为什么累加顺序**不是**规范保证的：`45-kernel-lifecycle/operator-design/02-numerical-design`。
