# 验证矩阵：容差不能是一个常数，但「按 dtype 定」也不够

> **一个容差走天下是错的**——同一个算子，fp32 路径与 fp16 路径的合理容差差三个数量级；但**「按 dtype 定一张表」也不够**。本篇用本库自己的程序量了这件事：**同一个算子、同一个 dtype，只把输入的动态范围从 1 个数量级换到 3 个数量级，实测的最大误差就跨了 `48.9` 倍（1.7 个数量级），而需要的 `rtol` 从 `0`（atol 就够）变成 `3.7e-3`。**
>
> **一条可机械判定的论断**：把测试矩阵当成**五个维度**上的覆盖问题，可以求出**最小覆盖集**——本程序给出一个**可证的下界**并构造出**恰好达到下界**的见证集：**3 个形状**覆盖 3 个轴 × 4 类共 9 个「(轴, 类别)」组合（逐维各测一遍要 9 个形状）。
>
> **★ 两个真的漏报**（都要跑出数字）：**只含 2 的幂形状的矩阵**对「尾部块不写」这个缺陷的**捕获数为 `0`**（尾块为空 ⇒ 那行代码根本没执行）；一个 `1.001` 倍的**静默偏置**在 D 级容差表下**通过**、在标定容差下被捕获——但标定容差也会**把正确的实现误报**。

## 0. 背景与动机

### 0.1 「测过了」的两种含义

| 说法 | 实际做了什么 | 覆盖了什么 |
|---|---|---|
| 「测过了」 | 跑过几个形状，容差内都过了 | 可能只覆盖了**一个点** |
| 「覆盖了维度」 | 每个维度上的每个类别都至少出现一次 | 可以**算出来**覆盖了什么、没覆盖什么 |

差别在**可计算性**：前者只能说「过了」，后者能说「覆盖了 9 个 (轴, 类别) 组合中的 9 个，代价是 3 个形状」。

### 0.2 三个「正确性幻觉」的来源（**[C] 级 · 预印本**）

arXiv:2606.20128 *The Correctness Illusion in LLM-Generated GPU Kernels*（**预印本，未确认同行评审**）独立指出，用固定形状、小样本、容差比对当 oracle 会**系统性地过于乐观**，来源有三个：

| 来源 | 论文的说法 | 本篇的对应节 |
|---|---|---|
| **shape** | 每个算子只测一个形状；带 tail masking、off-by-one 累加、block-size 假设的 kernel 在选中的形状上过、别处错 | §1.1 形状维 |
| **dtype** | 每个算子只测一个 dtype；混合精度溢出、下溢、累加误差都测不到 | §1.2 dtype 维 |
| **tolerance** | `atol`/`rtol` 通常比实测误差包络**松 1–3 个数量级**，把真错误吸收了 | §2 容差节 |

⇒ **五维不是本库编的清单，外部有一篇专门论证它缺一不可的工作**（论文自己的 caveat：它的语料是 LLM 生成的 kernel 与**作者播种**的转写错误，不是任何真实部署系统的缺陷率——本篇不把它外推）。

### 0.3 本篇在本域主线上的位置：它守的是**上界的前提**

| 主题 | 「上界」在这一环是什么 |
|---|---|
| `requirement-discovery` | roofline 给的理论上界——**上界在哪** |
| `operator-design` | 候选设计各自的上界——**怎么抬高上界** |
| **`implementation`** | **正确性门——上界只有在算对的前提下才有意义** |
| `convergence-and-tuning` | 剩余距离是工程能触及的，还是噪声 |

本篇守的是这一环的**「配得上」**那一半，理由有三条：

1. **错误的上界会被当成真的**。一个没被验证矩阵覆盖的缺陷不会自己宣告存在——它会安静地把 `AI`、把 roofline 判定、把「还有 3 倍空间」一起带偏。
2. **容差是一个**有代价**的选择**。紧 ⇒ 假失败（把对的判成错的，噪声淹没信号）；松 ⇒ 漏报（把错的放过去）。**两边的代价都要写出来**，只写一边就是选择性引用。
3. **「覆盖了什么」必须可计算**。否则「测过了」这句话没有信息量，而本域的头号风险就是无信息量的句子。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。下面的被测算子是**数组变换的仿真**：沿最后一维做加权行和，按固定块长分块累加——**尾部块的存在不依赖任何 GPU 细节**，它是分块算法本身的性质。

## 1. 原理：五个维度，以及每维的**最小覆盖集**

### 1.1 形状维：类别是**谓词**，不是取值清单

一个形状描述符（`B, M, J`）在三根轴上的取值会触发**不同的代码路径**。本主题按「触发了哪条路径」定义四个类别（不是按数学性质）：

| 类别 | 谓词 | 触发什么 |
|---|---|---|
| `pow2_ge_TILE` | `v ≥ TILE` 且 `v` 是 2 的幂 | 恰好切成若干个**完整**块，尾部块**为空** |
| `tail` | `v > TILE` 且 `v % TILE != 0` | 有一个**非空但不满**的尾部块 |
| `small` | `v < TILE` | 整个循环只跑一次，块比 `TILE` 小 |
| `mod4_ne0` | `v % 4 != 0` | 触发「`% 4` fallback」那条**防御性分支** |

> ★★ **本主题的第一版把 `pow2` 定义成「是 2 的幂」（不要求 `≥ TILE`）**，于是 `16`、`32` 同时落进 `pow2` 与 `small` 两类——**下界论证当场失效**（`J` 轴用 `{16, 65}` 两个取值就「覆盖」了四类）。
> ⇒ 正确的分法是**按「它在分块算法里触发了哪条路径」分**。这个教训与 `10-foundations` 反复强调的「口径先定清楚」是同一件事。

**每轴需要覆盖的类别不同**（这一步不能省）：

| 轴 | 角色 | 需要覆盖的类别 |
|---|---|---|
| `J` | 归约轴，被分块 | `pow2_ge_TILE` / `tail` / `small` / `mod4_ne0` |
| `M` | 非归约轴，不分块 | `pow2_ge_TILE` / `small` / `mod4_ne0` |
| `B` | 批轴 | `pow2_ge_TILE` / `small` |

把三轴当成同一个集合，会得出一个**偏大**的最小覆盖集，并因此以为「正交设计省不了多少」。

### 1.2 最小覆盖集：可证的下界 + 恰好达到下界的见证集

**下界（一句话的证明）**：每个形状在**每根轴**上只提供一个取值，所以某轴至少要出现 `k_A` 个**不同**取值才能覆盖该轴的类别 ⇒ **形状数 ≥ max_A k_A**。

本程序穷举候选池求出每个轴的最小取值数：

```text
J 轴：4 类 → 最少 3 个取值   [1, 64, 65]
M 轴：3 类 → 最少 2 个取值   [1, 64]
B 轴：2 类 → 最少 2 个取值   [1, 64]
⇒ 下界 = max(3, 2, 2) = 3
```

**见证集**（恰好达到下界）：

```text
(B=1,  M=1,  J=1)      覆盖 small（三轴）+ mod4_ne0（M、J）
(B=64, M=64, J=64)     覆盖 pow2_ge_TILE（三轴）
(B=1,  M=1,  J=65)     覆盖 tail（J）+ mod4_ne0（M、J）
```

覆盖 **9 / 9** 个 (轴, 类别) 组合，用了 **3** 个形状。逐维各测一遍要 **9** 个形状 ⇒ **省 3.0 倍**。

> ⚠ **上界也必须诚实**：这只保证每个 **(轴, 类别)** 组合被覆盖到，**不**保证轴与轴之间的**交互**（如「`M` 小 **且** `J` 恰好是尾部」）被覆盖——那是 strength-2 覆盖，规模会大得多。**本篇不声称做到了它。**

### 1.3 外部对齐：另一组边界形状

arXiv:2606.20128 用的边界值是 `H ∈ {1, 3, 7, 256, 1025}`。把它按本主题的四类判一遍：

| 类别 | 被外部集合覆盖的取值 |
|---|---|
| `pow2_ge_TILE` | `256` |
| `tail` | `1025`（`= 2^10 + 1`，「整块 + 1」） |
| `small` | `1, 3, 7` |
| `mod4_ne0` | `1, 3, 7, 1025` |

⇒ **两处独立的设计指向同一组类别**（`1/3/7` 是小的非 2 的幂，`1025` 是「整块 + 1」）。论文还量了更强的一件事：**去掉边界值后，shape-dependent 缺陷的召回率归零**——不是「某个缺陷漏了」，是**一整类缺陷的召回率归零**。

### 1.4 其余四维

| 维 | 取值集（本主题的声明） | 为什么需要 |
|---|---|---|
| **dtype** | `float16` / `bfloat16` / `float32` | 混合精度的溢出、下溢、累加误差只在换 dtype 时才出现 |
| **layout** | 连续行主序 / 末维带 stride / 转置视图 | 非连续输入会让**向量化路径失效**，走进另一条代码路径 |
| **边界** | 恰好是块整数倍 / 尾块小于块 / 尾块大于块 / 退化轴 | §1.1 的形状类别在执行侧的对应物 |
| **对抗输入** | 全零 / 全次正规 / 极大极小混合 / **参数被就地改·输出与输入别名** | ★ 最后一类**不属于数值比对**：容差比对**查不出**它（vLLM 用 `opcheck` 单独查） |

## 2. 容差：三张不同等级的版本，以及**按 dtype 定为什么不够**

### 2.1 三张表放在一起（**来源等级不同，必须分别标注**）

| 来源 | 等级 | 内容 | 口径 |
|---|---|---|---|
| vLLM `vllm/ir/tolerances.py` 的 `DEFAULT_TOLERANCES` | **[B]** | `float16: (1e-3, 1e-3)` · `bfloat16: (1e-3, 1.6e-2)` · `float32: (1e-5, 1.3e-6)` · `float64: (1e-8, 1e-8)` 等 7 个 dtype | `atol + rtol·|ref|` |
| arXiv:2607.16228 的标定 | **[C]** | 规则 = **正确 kernel 自身误差分布的 `p95 × 1.5`**；中位收紧 **100–200 倍**；极端例 `attention_triton` fp16 从手挑 `5.0e-2` 收到 `2.29e-5`（**2184 倍**） | **绝对** `atol`，逐 (op, dtype) |
| 本域规格 §Chunk3 的表 | **[D]** | `fp64_ref_vs_fp32: (1e-8, 1e-5)` · `fp64_ref_vs_fp16: (1e-3, 1e-2)` · `fp64_ref_vs_bf16: (1e-3, 5e-2)` | **未声明** |

> ⚠ **三张表口径不同，不可直接比大小**（P9 的同名不同指）：vLLM 用 `atol + rtol·|ref|`，论文与本篇程序用**绝对**口径，D 级表**没说**用哪个。同一个 `1e-3` 在两种口径下不是同一个界。

> ⚠ **D 级表的处置**：它来自**社区材料**，规格**没有给出处页面**，本实现者的两轮检索**也没找到**一张与之逐格吻合的公开页面（记进 `UNSOURCED`）。**本篇保留它的唯一目的是把它当靶子**——它的每个数字出现时必须写明「D 级、无出处页面、未被独立复现」。这也是本域硬规则 2（D 级不得单独支撑论断）的**具体执行**：本篇满足它的方式是**用更高等级的来源推翻它**。
>
> ⚠ **表里 fp64 vs int8 那一行本篇不收录**：规格原文写「以量化 scale 的比例度量（通常 `< 0.5 × scale`）」——「通常」无可核实的条件，且检索到的高等级材料给的是**另一种口径**（vLLM：`int8` 用 `rtol = 0`、绝对容差），二者不可比。**找不到出处的行直接不写，而不是「大概差不多」。**

### 2.2 本库的精度推导：三个格式的单位舍入误差

`u = 2^-p`，`p` = 有效二进制位数（含隐藏位）：

```text
u(fp16) = 2^-11 = 4.883e-04     p = 1+5+10  = 11
u(bf16) = 2^-8  = 3.906e-03     p = 1+8+7   = 8
u(fp32) = 2^-24 = 5.960e-08     p = 1+8+23  = 24
```

⚠ **与 `130-model-optimization` 的 `EPS` 不是同一个量，别混**：`130-model-optimization/quantization/code/specs.py:441` 的 `BF16_EPS = 2^-7` 是 **1.0 处的间距**（`finfo.eps`），而 `u = 2^-8` 是**它的一半**。⇒ 引用「本库 130-model-optimization 的精度推导」时必须说清引的是哪一个；本主题的误差界用 **`u`**（与 `10-foundations/floating-point/04-low-precision-formats` 的 `γ_K = K·u/(1-K·u)` 同口径）。

**方向也要写对**：`u(bf16) / u(fp16) = 8` ⇒ **bf16 比 fp16 粗 8 倍**（3 位，十进制 0.90 个数量级）。
> ★ 本主题的第一版把这个常量命名成 `U16_OVER_UBF16`（值为 `0.125`）——**比值方向反了**。`02_verification_matrix.py` 的 §A.2 当场把它抓了出来。这是 P9（同名不同指）在**常量命名**上的形态：一个反了的比值仍然「看起来是个数」。

**bf16 的两条独立实现**：numpy **没有** `bfloat16` 这个 dtype。本篇的处置是在程序里写**两条机制不同**的路径并交叉核对——位操作（取 fp32 位模式高 16 位 + RNE 偏置）与数值舍入（`spacing = 2^(e-7)`，四舍五入到最近偶数倍）。在 4008 个探针上**逐位一致**。这是本主题「参考实现必须独立」那条论断**在自己身上的应用**。

### 2.3 ★ 实测：**需要的 rtol** 是一个可测量，而它随**输入分布**变

「需要的 `rtol`」的定义：在固定的 `atol = 1e-3` 下，要让全部元素通过需要多大的 `rtol`。用被测算子在 `J ∈ {256, 1025, 4096}` 上测（fp32 累加 + 低精度**存储**，与 fp64 参考比）：

| 输入动态范围 | dtype | 需要的 `rtol` | 绝对 `max|err|` |
|---|---|---|---|
| 窄（1 个数量级） | fp16 | **0.000e+00** | 6.035e-04 |
| 窄 | bf16 | 8.860e-03 | 8.435e-03 |
| 中（2 个数量级） | fp16 | 1.873e-03 | 5.455e-03 |
| 中 | bf16 | 2.702e-02 | 5.030e-02 |
| 宽（3 个数量级） | fp16 | 3.715e-03 | 2.950e-02 |
| 宽 | bf16 | 4.932e-02 | 4.148e-01 |

**同一个算子、同一个 dtype、只换输入分布**：

- fp16 的**绝对最大误差**从 `6.035e-4` 到 `2.950e-2`，跨 **48.9 倍（1.7 个数量级）**；
- fp16 需要的 `rtol` 从 **`0`**（`atol` 就够）变成 **`3.7e-3`**；
- 两个 dtype 的所需 `rtol` 都随分布**单调上升**（方向可预测）。

> ★★ **这就是对本域规格那条断言的反驳。** 规格说「容差不能是一个常数……**必须按 dtype 定**」——测下来，**按 dtype 定也不够**。差别不在「一个常数」还是「一张表」，而在**这个量根本不是 dtype 的函数**。

### 2.4 ★ 逐行判定：三张表在三种分布下够不够

| 表（rtol） | 窄 | 中 | 宽 |
|---|---|---|---|
| **[D]** 规格 fp16 行（`1e-2`） | 通过（需 `0`） | 通过（需 `1.9e-3`） | 通过（需 `3.7e-3`） |
| **[D]** 规格 bf16 行（`5e-2`） | 通过（需 `8.9e-3`） | 通过（需 `2.7e-2`） | 通过（需 `4.9e-2`）——**余量只有 1.014 倍** |
| **[B]** vLLM fp16（`1e-3`） | 通过 | **不足** | **不足** |
| **[B]** vLLM bf16（`1.6e-2`） | 通过 | **不足** | **不足** |

- **[D] 级表的 `bf16` 行在宽分布下的余量是 `1.014×`**——形同没有余量。这是**偏高等级的来源**给出的判断，不是本库的偏好。
- **[B] 级 vLLM 的两行在「中」「宽」分布下都不足**。这不是说 vLLM 错了：它的容差是**故意松的**（官方注释：`intentionally conservative ... to avoid false failures across different hardware and kernel implementations`），松是为了**跨硬件不假失败**；代价是它兜不住宽动态范围的算子。
- **三张表没有一张在三种分布下同时有余量。**

### 2.5 `u` 给出的比例是**下界**，不是比例本身

| 量 | 值 |
|---|---|
| `u` 的比值（bf16/fp16） | **8.0×** ← 「粗多少倍」的**下界** |
| 实测需要的比值（中分布） | **14.4×** |
| 实测需要的比值（宽分布） | **13.3×** |
| [D] 规格表给的比值 | **5.0×** |
| [B] vLLM 给的比值 | **16.0×** |

三条结论（都是程序算出来的）：

1. **比值至少是 `u` 的 `8×`**——[D] 表给 `5×`，**连下界都没到**。这是**结构性**的：`bf16` 的 `u` 比 `fp16` 粗 8 倍，任何把 bf16 放得比 fp16 松不足 8 倍的比值，都必然在某些输入上把 bf16 卡死。
2. **实测需要 `13×–14×`**（> 8×）⇒ **`u` 只定「量级」，定不出比例**。为什么？因为「需要的容差」还取决于**输入的动态范围与抵消**，而 `u` 只说「一个数被表示得有多粗」。
3. ⇒ **唯一与测量自洽的做法是标定**：逐 (op, dtype) 从**累积的实测误差分布**里导出（`p95 × 1.5`），而不是查一张按 dtype 的表。这正是 [C] 级那篇论文的做法与结论。

### 2.6 标定不是免费的：它是一笔**交易**

用同一批 case（算子相同、规模与分布不同）比较三张表（fp16，`atol = 1e-3`）：

| 语料 | 容差表 | **捕获**（缺陷） | **误报**（正确实现） |
|---|---|---|---|
| `spread=0`（5 个 case） | [D] 规格 `(1e-3, 1e-2)` | **0 / 5** | 0 / 5 |
| | [B] vLLM `(1e-3, 1e-3)` | **0 / 5** | 0 / 5 |
| | **[C] 标定** `(9.32e-4, 0)` | **5 / 5** | **1 / 5** |
| `spread=1`（5 个 case） | [D] 规格 `(1e-3, 1e-2)` | 1 / 5 | 1 / 5 |
| | [B] vLLM `(1e-3, 1e-3)` | 5 / 5 | 3 / 5 |
| | **[C] 标定** `(5.14e-3, 0)` | **5 / 5** | **1 / 5** |

读法：

- `spread=0` 那一组：**D 级与 vLLM 两张表捕获数都是 `0`**——一个 `1.001` 倍的静默偏置**完全被吸收**。标定容差在**同一批 case** 上**全部捕获**。⇒ 这就是**容差造成的漏报**，跑出来了。
- `spread=1` 那一组：标定与 vLLM **捕获率相同（5/5）**，但标定的**误报只有 `1/5`**（vLLM 是 `3/5`）⇒ 在这批 case 上标定**占优**。
- **但标定也有假阳性**（`1/5`）⇒ 它是**一笔交易**，不是免费的改进。

**论文报告的正是同一笔交易**（[C] 级，语料 26 个算子，RTX 3060，采集窗口 2026-05-27 – 2026-06-11）：召回 `73.2% → 82.4%`（+9.3 个百分点），代价是控制组误报 `0.0% → 1.1%`。**两个方向都要写进正文**——只写收益就是选择性引用，只写代价就是否定一个已在用的做法。

### 2.7 一条「没有默认值」的判据

vLLM 的 `get_tolerance(dtype)` 在表里查不到那个 dtype 时**直接抛 `ValueError`**，**没有兜底默认值**；更紧或更松的界必须由一个显式的、按 `(op, dtype)` 的 `override_tolerance` 声明给出。

> ★★ 反直觉且可证伪：**一个「故意松」的表，却对没列的 dtype 直接报错**。两者是同一套设计的两面——**松是「已知格子的取值」，不是「未知格子的默认」**。它从来不假装自己是从精度推出来的。

## 3. 从「随机形状」到「按维度正交设计」

| 步 | 做什么 | 完成条件 |
|---|---|---|
| ① | 为每根轴列出**类别**（谓词，不是取值清单） | 每个类别能说清它触发哪条代码路径 |
| ② | 求出每轴的**最小取值数** `k_A` | 穷举候选池到最优（`k ≤ 4`，池子十几项，直接穷举） |
| ③ | 取 `max k_A` 个形状作见证集，并**逐条核对覆盖** | 覆盖数 == 全部 (轴, 类别) 对数 |
| ④ | 单独判定**防御性分支**是否被覆盖 | `M % 4 != 0` 的 fallback 至少被一个形状跑到 |
| ⑤ | 定容差 | 能说出这个数**从哪来**（标定 / 哪个 `u`），而不是「试出来的」 |

**第 ④ 步常被漏掉**：一个防御性设计（fallback 分支）如果没有被任何形状触发，它**一次都没跑过**——它和一个不存在的分支没有区别。本程序的见证集里 `M = 1` 覆盖了 `mod4_ne0` ⇒ fallback **被覆盖**。

## 4. 踩坑与失败模式

### 4.1 只测 2 的幂

**最贵的一个。** 2 的幂的形状让**尾部块为空**——所有「处理尾部」的代码路径**一次都不执行**。本程序 §C 量到了：4 个 2 的幂形状对「尾部块不写」的**捕获数为 `0`**；补上 `65 / 100 / 1025` 后捕获 `3 / 3`。

> ⚠ **这条漏报的性质要说准**：**不是容差松，是那段代码根本没跑**。⇒ 它无法靠「把容差调紧」修好——这是形状维与容差维的**本质区别**。外部论文量到的是更强的版本：边界值一去掉，**一整类**（shape-dependent）缺陷的召回率**归零**。

### 4.2 只测连续 layout

非连续输入（末维带 stride、转置视图）会让**向量化路径失效**，走进另一条代码路径。只测连续输入 ⇒ 那条路径从未被执行。

### 4.3 不测「最后一个不完整 tile」

与 4.1 同源，但更细：`J = 65`（尾块 1 个元素）与 `J = 100`（尾块 36 个元素）触发的是**同一条**路径的**不同取值**，而 `J < TILE`（整个循环只跑一次）是**另一条**路径——本程序量到，在 `J < TILE` 时「不写尾部」的缺陷表现为**输出恒为 0**（`J // TILE == 0` ⇒ 循环一次都不跑）。它同样是**静默**的（不崩、不越界）。

### 4.4 混合精度路径不验证累加是否真的在 fp32

这一条决定了 fp16 那行容差该按**哪个** `u` 推：

| 累加口径 | 误差随 `J` 的增长 | `J = 4096` 时的量级 | 对 `rtol = 1e-2` 的影响 |
|---|---|---|---|
| **fp32** 累加（硬件默认） | 基本不随 `J` 涨（存储舍入不累积） | 由 `u16` 定；实测 `6.0e-4`（窄分布）~ `3.0e-2`（宽分布） | 表**够** |
| **fp16** 累加 | 按 `√J · u16` | `3.125e-02` | 表**太紧、会漫天假失败** |

⇒ **同一个数（`1e-2`）在两种累加口径下，一个太松一个太紧。** 所以「容差表」必须与「累加口径」**一起读**，单看容差无法判定。

本库的既有事实（`130-model-optimization/quantization/code/specs.py:349` 的 `FP16_MM_CPU_ACCUM = "fp32"`，同一个文件里用 `[2048,1,1] @ ones → 4096.0` 的探针证明累加**不是** fp16）是本篇断言前提的依据。
> ⚠ **不得外推到 GPU**（那是 `130-model-optimization` 的原话）：PTX 里 `.ctype` 与 `.dtype` 都是 `.f16` 的累加变体**确实存在**，只是本库的 CPU 路径不走它。

### 4.5 把「按 dtype 定」当成终点

本篇 §2.3/§2.4 量到的事实：**它不是 dtype 的函数**。同一 dtype、同一算子，输入动态范围一变，需要的 `rtol` 从 `0` 变成 `3.7e-3`。

**处置**：不是「改用一张更细的表」，而是**承认它是标定出来的**——从累积的实测误差分布里导出，并且**把标定的代价（假阳性）一起记下来**。

### 4.6 ★ 把「本库构造的仿真」写成「真实故障」

本程序的两个缺陷（尾部块不写、`1.001` 倍偏置）**都是本库构造的**，语料也是。检索没有找到一份可引用的「尾部块不写」真实缺陷清单（记进 `UNSOURCED`）。**正文必须明写它们是构造的。**

这与外部论文的自陈纪律同源：arXiv:2606.20128 论文**开头就自陈**它的 buggy 变体是**作者播种**的。

## 6. 小结与延伸

- ★ **容差不能是一个常数，但「按 dtype 定」也不够**：同一算子、同一 dtype，输入动态范围从 1 档换到 3 档，实测最大误差跨 **48.9 倍**，需要的 `rtol` 从 **`0`** 变成 **`3.7e-3`**。
- ★ **两个 `u` 之间的比例有一个 `8×` 的下界**（`u(bf16)/u(fp16)`）：[D] 级表给 `5×`，**连下界都没到**；实测需要 `13×–14×`，说明 **`u` 只定量级、定不出比例**。
- ★ **D 级表在宽分布下的余量是 `1.014×`**——形同没有余量；[B] 级 vLLM 的两行在「中/宽」分布下**不足**（它的松是**故意**的，为跨硬件不假失败，代价是兜不住宽动态范围）。
- ★ **最小覆盖集是可算的**：形状维的**下界 = max_A k_A**，见证集 **3 个形状**覆盖 9 个 (轴, 类别) 组合（逐维各测一遍要 9 个）。
- ★ **只测 2 的幂 ⇒ 捕获数为 `0`**。而且**不是容差松，是那段代码根本没跑**——无法靠调紧容差修好。
- ★ **容差造成的漏报也跑出来了**：`spread=0` 的一批 case 上，[D] 与 [B] 两张表的捕获数都是 **`0 / 5`**，标定容差是 **`5 / 5`**。
- ★ **标定是一笔交易**，不是免费的改进：捕获 `73.2% → 82.4%` 的代价是误报 `0.0% → 1.1%`；**两个方向都要写**。
- ★ **混合精度路径必须先确认累加口径**：同一个 `1e-2` 在 fp32 累加下太松、在 fp16 累加下太紧。
- ★ **`numpy` 没有 `bfloat16`**：本主题写两条机制不同的舍入路径交叉核对（4008 个探针逐位一致）——这是本篇论断在自己身上的应用。
- ★ **`maxdiff` 之外还有检查**：参数就地修改、输出别名，容差比对一件都查不出。

**延伸**：

- 为什么容差不是规范保证的（累加顺序未规定）：`45-kernel-lifecycle/operator-design/02-numerical-design`。
- 误差界的推导（`u`、`γ_K`、`√K·u`）：`10-foundations/floating-point/04-low-precision-formats`、`130-model-optimization/quantization/03-bf16-fp16-tf32`。
- 参考实现怎么选、独立性怎么判：`45-kernel-lifecycle/implementation/01-reference-first`。
- 结果不对时按什么顺序查：`45-kernel-lifecycle/implementation/03-debug-order`。
- 各算子的具体测试写法（本域**不讲**的边界）：`40-kernels/*`。
