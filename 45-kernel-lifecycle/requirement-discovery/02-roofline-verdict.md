# roofline 判定：为什么「什么受限」不是算子的属性

> **「这个算子是什么受限」不是算子的属性，是「算子 × 精度路径」的联合属性。**
>
> H100 上，FP32 向量路径的 ridge 是 **20.0000**，FP16 张量核路径的 ridge 是 **295.3731**——两者相差 **14.77 倍**。算术强度落在这个区间内的算子，**换个精度路径就会得到相反的判定**。
>
> **但能翻转的只有落在 `(20, 295.37)` 这个窗口里的算子。** 本仓库实算（`code/02_roofline_verdict.py`）：5 个典型算子 × 2 条精度路径 = 10 次判定，**翻转的恰好 1 个**（prefill attention `S=512`）；3 个远低于窗口（`AI ≤ 1.25`）、1 个远高于窗口（`AI = 1365.33`）——**怎么换精度都不翻转**。

## 0. 背景与动机

### 0.1 三种手段，三种病

拿到一个「慢」的算子，能做的事只有三类。**选错手段的代价是「做完什么也没变」**：

| 手段 | 它治的病 | 它**治不了**的病 |
|---|---|---|
| **换精度**（fp32 → fp16/bf16/fp8 张量核） | 算力受限**且** `AI` 落在两条路径的 ridge 之间 | 访存受限——换精度后 `AI` 更低（见 §4.2），可能**更糟** |
| **加机器**（更多 SM / 更高带宽） | 带宽与算力**同步**涨，两条都受益 | 按件计的固定开销（launch、同步）**一分不减** |
| **改算法**（融合 / 减少数据移动） | 访存受限：降低分母 | 算力受限——分母已经无关紧要 |

**⇒ 「先判受限类型，再选手段」不是流程美学，是因为三种手段的适用范围**不相交**。** 这就是本篇要产出的那个判定。

### 0.2 一个具体的对照场景

同一个 attention，两个阶段：

| | `S` | 实际用的是哪个 | 判定 | 该做什么 |
|---|---|---|---|---|
| decode（`S=4096`，MHA） | 4096 | fp16 张量核 | **访存受限**（`AI = 1.0`） | 降字节：量化 KV、融合 |
| prefill（`S=512`） | 512 | fp16 张量核 | **访存受限**（`AI = 256`，仍 < 295.37） | ↑ 同上 |
| prefill（`S=512`） | 512 | **fp32 向量** | **计算受限**（`AI = 256 ≥ 20`） | 换精度路径 |

**同一份代码、同一个 `S`，只换精度路径，结论就反了。** 而 decode 那一行**怎么换都不反**——因为 `AI = 1.0` 已经在窗口之外。

## 1. 原理

### 1.1 三个式子

```
AI    = FLOPs ÷ 从 DRAM 读的字节数
ridge = 峰值算力 ÷ 峰值带宽
可达上界  P ≤ min(峰值算力, 带宽 × AI)
```

`AI < ridge` ⇒ **访存受限**（上界由带宽决定）；`AI ≥ ridge` ⇒ **计算受限**。

### 1.2 口径三件套（**不写死，同一张表内部就会混两种口径**）

| 项 | 本篇的取法 |
|---|---|
| FLOPs | **按 FMA 计 2 次**浮点运算 |
| 字节 | **只算必须往返 HBM 的唯一字节**（重复读的反例见 §4.1） |
| dtype | **fp16**，读写各 **2 B/element** |

### 1.3 H100 的两条 ridge（**E 级：本库推导值**）

代入本库 `specs.py` 的 **dense** 峰值与**标称**带宽：

```
FP16 张量核： 989.5e12 ÷ 3350.0e9 = 295.3731 FLOP/byte
FP32 向量  ：  67.0e12 ÷ 3350.0e9 =  20.0000 FLOP/byte
窗口宽度   ： 295.3731 ÷ 20.0000  =  14.7687 倍
```

> ★ **峰值必须用 dense 的 989.5，不是产品页上的 1979。** 本库 `specs.py` 的注释逐字警告：NVIDIA 产品页写的 H100 FP16 1979 TFLOPS **是带 2:4 稀疏的**，dense 只有 **989.5**。**程序把这一条写成了断言**——变异测试里把它换成 1979，ridge 变成 590.75，A.1 立即失败。

> ★ **「两个来源一致」不等于「两个独立来源一致」。** 外部材料（**[D]**）也算出 ≈295，与本库的 295.3731 一致。这**验证了算式与口径选择的一致性**（都取 dense、都用十进制 `10^9`、都在 SXM 档），**但不验证规格值本身**——两边的原始规格**都来自 NVIDIA 官方**。查证时必须追问**输入是不是同一个**。
>
> **对照**：B200 那一处（§4.4）两边**不一致**（281 vs 292.21），原因也是「输入是什么」——但那里输入**真的不同**（带宽 8.0 vs 7.7 TB/s）。**一处一致、一处不一致，原因都是「输入是什么」**——对照着看，比单看一处更能说明问题。

### 1.4 五个典型算子的 AI（**逐项推导**）

| 算子 | 算式 | AI |
|---|---|---|
| decode attention `S=4096, d=128`（**MHA**） | `4Sd ÷ (2Sd·2)` | **1.000000** |
| LayerNorm `d=4096` | `5d ÷ (2d·2)` | **1.250000** |
| GEMM `M=1, N=K=4096` | `2MNK ÷ ((MN+NK+MK)·2)` | **0.999512** |
| prefill attention `S=512, d=128`（**MHA**） | `4S²d ÷ (4Sd·2) = S/2` | **256.000000** |
| GEMM `4096³` | `2MNK ÷ ((MN+NK+MK)·2) ≈ N/3` | **1365.333333** |

**两处必须点明的推导步骤**：

- **LayerNorm 的 `5d`**：均值、方差、归一化、缩放、平移各 1 次/元素。**字节是 `2d·2`**（读 `x`、写 `y` 各 `d·2` 字节）——**这条约定是必须写死的**：用「读-改-写」或「只写其一」都会改变这个值。文档早期版本把这一格写成 `1.2`，实算是 **1.25**（`5d/4d`）。
- **prefill attention 的 `4S²d`**：两个核各 `2S²d`。**这个平方项的来源属于算子本体，回链** `40-kernels/attention/01-attention-as-a-kernel`，**正文在本域不复述**。

> ★ **这两行的「MHA」不是修饰，是口径。** 表里的 decode attention `AI = 1.0` **假设 `h_q = h_kv`（MHA）**。换成真实模型的 GQA，`AI = d_q/d_kv = h_q/h_kv`：

| `h_q/h_kv` | `AI` | fp32 路径判定 |
|---|---|---|
| 1:1（MHA） | 1.000 | 访存受限 |
| 4:1（Llama-3-8B） | 4.000 | 访存受限 |
| 8:1（Qwen3-30B-A3B） | 8.000 | 访存受限 |

**⇒ GQA 把 decode attention 的 AI 抬高 `h_q/h_kv` 倍，但即使 8:1 也只有 8.0，仍在 fp32 路径的 ridge（20.0）之下——判定不变。** 然而「AI 是多少」这个数变了 8 倍。**所以口径必须写在表的旁边，而不是脚注里。**

## 2. 执行映射

### 2.1 判定的落点一：L2 如何改变「DRAM 字节」

本节的口径来源是**本库已入库的量**：`L2_MB_H100_IN_REPO = 50`（H100 L2 容量 **50 MB**，**[E]**）。

> ⚠ **必须连同它的自陈一起搬**：该注释写明「**本仓库对 L2 容量这一项内部不一致**」——`20-gpu-architecture/architecture-evolution/code/specs.py` 只把 **B200** 的 L2 列为 UNSOURCED，并未给 H100 的值。**本节只做量级判断，不做精确结论。**

**量级**：50 MB ÷ 2 B = **2.6e7 个 fp16 元素**（≈ `2^24.6`）。这个数决定一件事：**中间张量装不装得进 L2**。

| 情形 | 会不会改变 DRAM 字节 |
|---|---|
| 中间张量 > 50 MB | **会**——第二次读它时已从 L2 驱逐，DRAM 字节 = 重复读次数 × 张量大小 |
| 中间张量 ≪ 50 MB 但被反复读 | **不一定**——取决于两次读之间的**其他流量**是否把它挤出去 |

**⇒ 这一条正是「唯一字节 vs 总读取字节」那个口径分歧的物理来源**（§4.1）：口径二（总读取字节）**假设一次都没命中**；口径一（唯一字节）**假设全部命中**。**两者都是极端，真实值在中间**——但这不改变判定的稳定性：本仓库实算的那个卷积里，两个极端给出的判定**相反**，所以**必须说清用的是哪个极端**。

### 2.2 判定的落点二：可达带宽与标称带宽的差，方向与直觉相反

本库记录的可达带宽缺口 `ACHIEVABLE_BW_SHORTFALL_PCT_IN_REPO = (5, 15)`（**[E]**，且带自陈：**本仓库对它的原始出处没有给出一手页面，引用值，本仓库不复核其测量口径**）。对应可达带宽系数 `η ∈ [0.85, 0.95]`。

```
η = 0.95 ⇒ 可达带宽 3182.5 GB/s ⇒ 可达 ridge = 310.92（标称的 1.05 倍）
η = 0.85 ⇒ 可达带宽 2847.5 GB/s ⇒ 可达 ridge = 347.50（标称的 1.18 倍）
```

> ★ **直觉会说「可达带宽更低 ⇒ 更容易计算受限」，这是反的。**
> `ridge = 峰值 ÷ 带宽`——**分母变小 ⇒ ridge 变大 ⇒ 更多的算子被判成访存受限**。
> **⇒ 用标称值做判定是保守方向**：它会把算子判得比实际更「算力受限」，也就是**低估**访存瓶颈的普遍性。程序把这条写成断言（§B.4）。

## 3. 从单算子到融合后的重新判定

融合会**同时**改变分子与分母：FLOPs 通常不变（融合不改算术），字节**减少**（中间张量不再往返 HBM）。**⇒ 融合把 `AI` 推高，方向是「从访存受限往计算受限走」。**

**这条的完整推导（融合如何改写 `AI`、以及为什么融合的收益会随算子链长度饱和）正文在 `40-kernels/elementwise-fusion/02-fusion-and-traffic`，此处回链，不重讲。** 本域只用它的**结论形态**：融合之后必须**重新判一次受限类型**——用融合前的 `AI` 去决定融合后的优化手段，会把结论用错地方。

## 4. 踩坑与失败模式

### 4.1 把重复读算进 DRAM 字节（**方向：压低 AI，不是抬高**）

**现象**：给一个直接卷积（3×3、不做 im2col、不做 shared memory 复用）报 `AI = 842.51`，然后说它「计算受限」，并按计算受限去优化它。

**成因**：`842.51` 是**算法的最小 DRAM 字节**算出来的——它假设每个权重、每个输入元素**只从 DRAM 取一次**。真实的朴素实现**每个输出元素都要重读 `K²·Cin` 个权重、`K²` 个输入**。

**规避（本程序 §C 实跑的具体数）**：同一个卷积（`N=1, Cin=Cout=256, H=W=56, K=3`，fp16，`FLOPs = 3,699,376,128`，两种口径下**相同**）

| 口径 | 分母（字节） | `AI` | 判定 |
|---|---|---|---|
| **唯一 DRAM 字节**（理想复用） | 4,390,912 | **842.51** | **计算受限** |
| **总读取字节**（无复用实现实际发出的流量） | 3,715,432,448 | **0.995678** | **访存受限** |

**两个分母的来历（算式必须写全，否则左边是元素数、右边是字节数）**：

```
口径一：输入 802,816 + 权重 589,824 + 输出 802,816 = 2,195,456 个元素
        × 2 B/element = 4,390,912 B
口径二：每个输出元素重读 K²·Cin = 2304 个权重元素、K² = 9 个输入元素，输出写 1 次
        = 1,857,716,224 个元素 × 2 B = 3,715,432,448 B
```

**⇒ 两种口径的判定相反。两个数都是对的，差在「分母问的是什么问题」**：口径一问「这个算法**最少**要搬多少」（上界）；口径二问「这个实现**实际**发出了多少」（roofline 要的就是这个）。

> ★ **方向容易写反。** 把重复读算进去，**分母变大 ⇒ `AI` 变小**——是**压低** `AI`，不是抬高。所以真实的失败模式是「**把理想的 AI 当实现的 AI 用**」，结论从**访存受限**错判成**计算受限**。反过来，说「算进重复读会虚高 AI」是错的。

> ★ **「重复读了 9 倍」这句话本身也不对。** 两者的比是 **846.2 倍**，而这个倍数由**两个不同的量**合成：权重每个元素被重读 `H·W = 3136` 次；输入每个元素被重读 `K² = 9` 次。**⇒ 这类算子上「重复读的倍数」没有单一值**，不能用一句「重读 9 次」概括。

**这条不是外部来源的发现**：本库已有同一翻转的实现——`40-kernels/gemm/code/verify.py` 的 `b2_naive_ai` 用「两套字节口径」对照同一道 GEMM（那里口径三写明「每个元素只从 HBM 取一次」并判为计算受限）；`10-foundations/performance-models/code/09_roofline_model.py` 的口径声明写死「Bytes 只统计必须往返 HBM 的字节」。**本域回链，不重讲。**

### 4.2 用错精度峰值

**现象**：拿 FP32 FFMA 峰值（H100 上是 67.0 TFLOPS）去判一个跑在 FP16 张量核上的算子。

**成因**：如 §0.2 的表，同一个 `AI = 256` 在两条路径上判定相反。**用错峰值等于用错整张判据表。**

**规避**：峰值、ridge、`AI` 三者必须来自**同一条路径**。判据表第 2 行。

**★ 一个附带的推论（容易被忽略）**：**换了精度路径，字节也变了**。fp16 的 `AI` 是 fp32 的 2 倍（每个元素 2 B 而不是 4 B）——**分子不变、分母减半**。

**⇒ 这引出本篇表里一处必须自己先说破的口径问题**：`AI` 列是 **fp16 字节**算的，而 fp32 路径的 ridge `20.00` 是 **fp32 字节**算的。严格地说，「把同一个算子放到 fp32 路径上」意味着**字节翻倍 ⇒ `AI` 减半**。程序（§B.5）把两种读法各算了一遍：

| 读法 | `AI` | 对照的 ridge | 翻转集合 |
|---|---|---|---|
| **A：字节翻倍** | `AI_fp16 ÷ 2` | `20.00` | `{prefill S=512}` |
| **B：字节不变**（fp16 数据 + fp16 向量速率 `2×67 = 134` TFLOPS） | `AI_fp16` | `40.00` | `{prefill S=512}` |
| 基准（表里直接把 fp16 的 `AI` 比两条 ridge） | `AI_fp16` | `20.00` / `295.37` | `{prefill S=512}` |

**三种读法的翻转集合相同**（程序写成断言）。**⇒ 这张表的判定不依赖口径约定，但翻转窗口的边界依赖它**：读法 A 的窗口在 fp16 口径下是 `(40, 590.75)`。**所以引用窗口时必须写明它是在哪条口径下的；口径无关的那个量是窗口的宽度 `14.77` 倍。**

### 4.3 把标称带宽当可达带宽

**现象**：用 3350 GB/s 算出 `ridge = 295.37` 之后，拿它去解释「为什么实测只到峰值的 60%」。

**成因**：`295.37` 是 `ridge`（拐点位置），不是「可达吞吐」。可达带宽低 ⇒ 可达 `ridge` **更高**（§2.2）⇒ **判据更严**。

**规避**：判据表第 5 行——用标称值判定是**保守**方向（把算子判得更偏计算受限），这是可以接受的；但**不要**把标称值当成「实测应该到达的值」。

### 4.4 B200 的 ridge：281 与 292.21 是**口径分歧**，不是算力争议

| 带宽口径 | 算式 | ridge |
|---|---|---|
| 本库 `HBM_BW_GBps_BY_GEN["B200"] = 7700` GB/s | `2250.0e12 ÷ 7700e9` | **292.2078** |
| 外部材料（**[D]**）的 8.0 TB/s | `2250.0e12 ÷ 8000e9` | **281.25** |

**两者都不是错的**，差的只是**分母上的带宽**。本主题**一律采用本库的 7.7 TB/s**（`specs.py` 口径一致性强），并在正文注明另一口径的存在。

**⇒ 写法要求**：不得把 281 与 292.21 并列成「B200 的 ridge 有两个值」就完事——**必须写出差异的成因**，否则读者会以为**算力**有争议。

### 4.5 把「attention 会翻转」当结论

**现象**：看到 prefill attention `S=512` 在两条路径上判定相反，就写成「attention 是那个会翻转的算子」。

**成因**：**翻转取决于 `S`，不取决于「是不是 attention」**。`S=4096` 的 prefill attention `AI = 2048`，**远高于 295.37，怎么换都不翻转**；decode attention `AI = 1.0`，**远低于 20.0，怎么换也不翻转**。

**规避**：报「翻转」时必须同时给出 `S` 与 `AI`；报「不翻转」时必须给出它离窗口有多远。判据表第 3、4 行。

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**（本机无 GPU，本域任何一篇都不得声称有实测数据）。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 算 `AI` 之前，口径三件套（FMA=2、唯一 DRAM 字节、dtype 及其 `esize`）未写在同一处 | **停**——数字不可比；先写口径 |
| 2 | 算子实际执行在 fp16/bf16 张量核上 | ridge 用 **295.3731**（H100）；**不得**用 FP32 向量峰值 67.0 |
| 3 | `AI < 20.0` | 两条路径**都**判访存受限；换精度**不会**翻转 |
| 4 | `AI > 295.3731` | 两条路径**都**判计算受限；换精度**不会**翻转 |
| 5 | `20.0 ≤ AI < 295.3731` | **落在窗口内**；必须**两条路径各判一次**，并给出两条结论 |
| 6 | 分母用的是「唯一 DRAM 字节」 | 得到的是**算法上界**（理想复用）；引用时必须同时给出实现的实际复用情况 |
| 7 | 分母用的是「总读取字节」 | 得到的是**某个具体实现**的 `AI`；换实现（加 shared memory / im2col）它就会变 |
| 8 | 一个算子的读者可能把它读成 MHA | **把 `h_q/h_kv` 写在 AI 旁边**——GQA 使 `AI` 变化 `h_q/h_kv` 倍 |
| 9 | 用的是标称带宽 | 判定方向**保守**（偏计算受限）；**不得**把这个 ridge 当作「实测应达到的吞吐」 |
| 10 | 想知道可达判据 | 可达 `ridge = 标称 ridge ÷ η`，`η ∈ [0.85, 0.95]`；**可达 ridge 更高、判据更严** |
| 11 | 想用 L2 减少 DRAM 字节 | 先比「中间张量大小 vs **50 MB**（本库口径，**内部不一致**，仅作量级）」；装不下就不改变字节 |
| 12 | 算子被融合了 | **重新判一次**受限类型——字节减少 ⇒ `AI` 被推高，方向是从访存受限往计算受限走 |
| 13 | 两个来源给出同一个 `AI`/`ridge` | 先问**它们的输入是不是同一个规格来源**；是，则不构成独立验证 |
| 14 | 两个来源给出不同的 `ridge` | 先比**带宽口径**（如 B200 的 7.7 vs 8.0 TB/s）；**多数ridge 分歧在分母上，不在算力上** |
| 15 | 一张表里既有 fp16 也有 fp32 的 `AI` | **必须**给每个 `AI` 标 dtype；否则「翻不翻转」这个问题本身无定义 |

**闭合性检查**：读完这张表能把「一个算子在一条给定精度路径上是什么受限、这个判定对口径有多敏感、换路径会不会翻转」判完。**唯一的表外输入**是「实现的实际复用情况」——它不在 roofline 里，在实现里（回链 `40-kernels`）。

## 6. 小结与延伸

- ★ **受限类型是「算子 × 精度路径」的联合属性**：H100 上两条 ridge 相差 **14.77 倍**；5 个典型算子 × 2 条路径，**翻转的恰好 1 个**。
- ★ **但翻转是有条件的**：只有落在 `(20, 295.37)` 窗口内的算子才翻转。**「attention 会翻转」是错的**——`S=512` 翻、`S=4096` 不翻、decode 不翻。
- ★ **可达带宽更低 ⇒ 可达 ridge 更高 ⇒ 判据更严**（与直觉方向相反）。
- ★ **把重复读算进 DRAM 字节是压低 `AI`**，错误的方向是「把理想的 `AI` 当实现的 `AI`」⇒ 从访存受限错判成计算受限。本仓库实算的 3×3 卷积：`842.51`（计算受限）vs `0.995678`（访存受限）。
- ★ **B200 的 281 vs 292.21 是带宽口径分歧**（8.0 vs 7.7 TB/s），不是算力争议；**写它必须写出成因**。
- **「两个来源一致」≠「两个独立来源一致」**——先追问输入是不是同一个。
- **GQA 让 decode attention 的 `AI` 变化 `h_q/h_kv` 倍**（8:1 时 8 倍），但**不改变判定**——它改变的是「`AI` 是多少」，所以口径必须写在表旁边。

**延伸**：

- 用这条判定排优化的先后，在 `45-kernel-lifecycle/requirement-discovery/03-optimization-priority`。
- 算子的 `AI` 怎么从 config 算出来，在 `45-kernel-lifecycle/requirement-discovery/01-model-to-operator-inventory`。
- **两套字节口径的既有实现**：`40-kernels/gemm/code/verify.py` 的 `b2_naive_ai`（口径三 = 唯一字节）与 `40-kernels/gemm/01-naive-gemm-and-roofline`。
- 访存受限算子的本体形态（为什么逐元素算子必然贴带宽上界）：`40-kernels/elementwise-fusion/01-memory-bound-limit`。
- 融合如何改写 `AI`：`40-kernels/elementwise-fusion/02-fusion-and-traffic`（**正文在该域，此处回链**）。
- roofline 模型的原理与推导、可达带宽的分解：`10-foundations/performance-models/01-roofline-model`、`03-measuring-roofline`。
