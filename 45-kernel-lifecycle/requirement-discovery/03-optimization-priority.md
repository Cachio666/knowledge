# 优化价值排序：为什么 17.9% 排在 50.4% 之前

> **优化的第一目标不是占比最大的算子。** 本仓库实跑（`code/03_optimization_priority.py`）用一份真实剖面的数据检验了三条数量规则——**① 按占比、② 占比 ÷ 工作量、③ 距离 × 占比 ÷ 工作量**——**三条都把 50.4% 的那个排在第一**，而实际决策先做了 **17.9%** 的那个。
>
> **⇒ 「17.9% 排在 50.4% 之前」不是从（占比、距离、工作量档名）算出来的。** 要让它成立，规则③ 需要 **工作量比 > 4.6606**，而那个比值**不来自任何来源**。能复现这个决策的是一条**布尔判据**：**要不要写新 kernel**。

## 0. 背景与动机

### 0.1 「按热点排序，优化第一个」什么时候给出错误的顺序

这条朴素规则**在大多数情况下是对的**——所以它危险。它错的条件是可以写出来的：

```
设两个候选 A、B，占比 s，到上界的距离 d，工作量 w。
规则③ 的排序量 = d·s/w。
「按占比」把 A 排第一，规则③ 把 B 排第一
   ⟺  d_A·s_A / w_A  <  d_B·s_B / w_B
   ⟺  w_A / w_B  >  (s_A·d_A) / (s_B·d_B)
```

**⇒ 「按占比排序会出错」这句话的精确形态是：当工作量之比超过某个由 `s` 与 `d` 决定的临界值时，两个排序必然相反。**

**反过来也成立**：**若所有候选的工作量相同（`w_A/w_B = 1`），按占比排序就是对的**。所以「不要按占比排」这句话本身也是错的——**错在把它当成无条件规则**。

### 0.2 一个具体的对照场景

| | 规则 | 第一目标 | 结果 |
|---|---|---|---|
| 路径甲 | 按占比 | 50.4% 那个 | 需要**新打包格式 + 新 kernel**；被推后 |
| 路径乙 | 按「要不要写新 kernel」 | 17.9% 那个 | **一个 loader flag**，同二进制 A/B，实测 prefill **1.090×** |

**两个目标都在清单里、都真实存在**。差别不在「哪个更大」，在**哪个能在这周做完**。

## 1. 原理

### 1.1 排序量

```
排序量 = 到上界的距离 × 占比 ÷ 工作量
```

三项各自回答一个问题：

| 项 | 问题 | 从哪来 |
|---|---|---|
| **到上界的距离** | 「做完了能拿多少」 | `02-roofline-verdict` 的判定 + Amdahl 上界 `1/(1−占比)` |
| **占比** | 「它能影响多少总时间」 | profile（分子与分母必须是同一个时间轴） |
| **工作量** | 「要付多少」 | **本篇最弱的一环**，见 §1.3 |

> ★ **`距离` 与 `占比` 不是一回事，两者缺一不可。** 占比大但距上界只有 `1.05×` 的算子，最多给你 5%；占比小但距上界 `2×` 的算子，可能给你更多。**「按占比排」等于把第二项当成唯一项。**

### 1.2 headroom gate：**声称的加速比不得超过该算子到其约束资源的距离**

这是一条**来自上游实现的闸**（**[B]**，NVIDIA/TensorRT-LLM PR #18805 的变更说明逐字记录：`headroom_verdict` 成为一道闸——「**一个 kernel 加速项声称的加速比不得超过该算子到其约束资源的距离**」）。

**它的边界是闭的**：距上界恰好 `1.300×` 时，声称 `1.300×` **通过**、声称 `1.301×` **被拒**（程序 §A.1）。

**用真实数据走一遍**（**[D]**，vllm.cpp 的 **CPU** prefill 剖面，条件见 §3）：

| 项 | 值 |
|---|---|
| `kMatmul` 的上界（Amdahl 完全消除） | `1/(1−0.179) = 1.2180×` |
| 实测（同二进制 CPU prefill A/B） | `1.090×` |
| 闸 | `1.090 ≤ 1.2180` ⇒ **通过** |
| 兑现率 | `1.090 / 1.2180 = 89.49%` |

**⇒ 这个闸把「声称」和「可证明」分开了。** 距上界 `1.2180×` 的算子说自己能快 `1.5×`，不需要跑就能否掉。

### 1.3 「工作量」是本篇最弱的一环——**说清楚它弱在哪**

`距离` 可以从 roofline 算，`占比` 可以从 profile 读。**`工作量` 没有这两个性质**：

- 它**不是**一个可从 config 或 profile 推出的量；
- 上游来源只给**档名**（`LOW` / `MEDIUM–HIGH`），**不给数值**；
- 任何把它变成数值的动作都是**本库的秩映射**（`code/specs.py` 的 `EFFORT_RANK_MAPPING`，标 **[E]**），不是来源值。

**⇒ 因此本篇的结论必须写成「**在什么工作量比值下，排序会翻转**」的形式**，而不是「按我们的公式就对」。程序 §B.3 算出了两个临界值：

| 规则 | 需要的 `工作量_A / 工作量_B` |
|---|---|
| ② 占比 ÷ 工作量 | **> 2.8156**（`= 50.4/17.9`） |
| ③ 距离 × 占比 ÷ 工作量 | **> 4.6606**（`= 50.4×2.0161 / (17.9×1.2180)`） |

**本库的秩映射给出 `2.5/1.0 = 2.50 < 4.6606`** ⇒ 规则③ 判 50.4% 的那个第一。**这就是「三条规则都没复现实际决策」的全部原因**——不是公式错，是**工作量不能用一档名字来定价**。

### 1.4 kernel 没覆盖的那部分份额，**不会被更快的 kernel 恢复**

这是一条**上界**，不是建议。来源同 **[B]** PR #18805，逐字：「**a launch-starved share is not recovered by a faster kernel**」。

**本库的算术（[E]）**：设 kernel 覆盖的份额为 `p`，把 kernel 加速到**无穷**，剩余时间 `= 1 − p`：

| `p` | 任何 kernel 优化的加速比上界 |
|---|---|
| 0.30 | 1.4286× |
| 0.50 | 2.0000× |
| 0.80 | 5.0000× |
| 0.95 | 20.0000× |

**⇒ `p = 0.5` 时，无论把 kernel 优化到什么程度都到不了 2×。** 所以**在做任何优化之前，先确认时间真的在 kernel 里**——这是 §2 的主题。

**一个正面对照**（**[B]**，vLLM 官方博客）：Kimi K3 的专用 metadata builder 把 metadata 准备从 **870 µs** 压到 **34 µs**（−96%），端到端只改善 **6%**。

**本库反解（[E]）**：省下的 `836 µs = 6%` ⇒ 被改善的那段总时长 ≈ **13.9 ms**；该 op 的原始占比 `= 870/13933 = 6.24%`，**兑现率 `6.0/6.24 = 96.1%`**——因为它被**基本消除了**。

**⇒ 两个数一起看才有意义**：`6.24%`（占比）与 `96.1%`（兑现率）。**只看占比会低估一个好改动，只看兑现率会高估一个小改动。**

## 2. 执行映射

### 2.1 先确认时间真的在 kernel 里

TensorRT-LLM 的做法（**[B]**，PR #18805）给出的理由，逐字：

> `nsys stats` 只回答「哪个 kernel 花掉的 GPU 时间最多」，「**those diverge the moment the GPU is not busy**」。按开销排序的 top-kernel 表「reads as a list of opportunities even when the iteration is mostly waiting on the host」。

它产出的是一份**按 iteration 的预算**：相对**检出的 anchor** 的时间、**三层嵌套的 busy rung 连同各自的 idle 补集**、**compute-absent 时间**拆成 **launch-starved / blocking / dependency-stalled**、kernel 类别分解、以及**暴露出来的集合通信时间**拆成 transfer 与 jitter wait。

**`share_pct` 的定义是 `analysis/nsys_analysis` 的 **interval-union time**——`kern_sum` 只作**显式兜底**。**（同一份说明里有一条必须引用的警告：**流之间重叠会同时改变排序与百分比**。**⇒ 按 `kern_sum` 排出来的顺序与按 interval-union 排出来的顺序可以不同，而且「谁占多少」也不同。这是 P7 的一个具体形态：**两个都叫「占比」的量，作用域不同。**）

**本条与 PR #18825 是两件事，不要合并引用**：PR #18825 给的是**每个 kernel 的四类处置**——`elimination`（能不能不做）、`faster execution`、`fusion`、`overlap`——每类都要带 evidence 与**数值化的 `gpu_busy_pct`**。

> ★ **`elimination` 被排在第一位**：先问能不能不做，再问怎么更快。这条与 §1.4 的上界是同一件事的两面——**消除一个算子拿到的收益不受 `p` 限制，加速它受限制**。

### 2.2 三条数量规则都没复现实际决策——这才是本篇要讲的

程序（§B）用实例数据把三条规则都跑了一遍：

| 规则 | `A`（50.4%） | `B`（17.9%） | 第一名 |
|---|---|---|---|
| ① 按占比 | 50.4000 | 17.9000 | **A** |
| ② 占比 ÷ 工作量 | 20.1600 | 17.9000 | **A** |
| ③ 距离 × 占比 ÷ 工作量 | 40.6446 | 21.8022 | **A** |
| ④ **要不要写新 kernel** | `True` | `False` | **B** |

**实际决策是 B**（`A` 被明确写成「the next lever」）。

> ★ **这不是公式的失败，它揭示了「工作量」在真实排序里是什么形态。**

文档逐字记录的理由（两句都是**引用**，不是本程序的推断）：

- **`B`（17.9%）的修复不需要写新 kernel**：它骑在既有的 `expand_nk` loader 策略上；`VT_GGUF_GDN_NK=0` 是**同二进制的 A/B 退出开关**，`VT_CPU_REF=1` 可复现历史行为——**构造上逐字节相同**。
- **`A`（50.4%）的修复需要一个新的打包格式**（q8_0 repack-at-load）**加一个新 kernel**。

**⇒ 「工作量」在这条决策里不是一档名字，是有没有跨过「要写新 kernel」这条线。**

**实测结果支持这个选择**：同二进制 prefill **1.090×**、decode **1.09×**，RSS 不变、token **逐字节相同**，`kMatmul` 在 prefill 里从 **72 次调用降到 0**。

### 2.3 top-3 Pareto：只看前 3 个桶

同一份剖面的占比（**[D]**）：

| 算子 | 占比 |
|---|---|
| `kMatmulBTQuant`（q8_0 量化 GEMM，i8mm 档） | **50.4%** |
| `kMatmul`（`[K,N]` 慢 kernel，无 M-blocking） | **17.9%** |
| `kMatmulBT`（`[N,K]` 快 kernel，f16 展开权重） | **14.9%** |
| `kGdnPrefill`（已线程化） | 5.2% |
| `kPagedAttention`（已线程化） | 3.2% |

**前 3 个桶合计 83.2%**，与原文记录的「GEMMs 占 prefill 的 **83%**」自洽（原表各留一位小数，程序把这条写成断言）。

> ★ **这条只支撑「在这一份数据上，前 3 个桶够了」**，**不**支撑「3 个桶总是够」。把 Pareto 当成一条**普适规则**就是 P10——它在这里成立，是因为**这份剖面的分布恰好长这样**。

## 3. 一个真实实例（★ **这是 CPU 剖面，不是 GPU**）

以下全部来自 `mudler/vllm.cpp` 的 `.agents/specs/` 文档，**来源等级 [D]**（**个人仓库**，未被独立复现）。

**测量条件（缺一不可，必须连在一起写）**：

> **aarch64 DGX** · **20 线程** · `--input-len 128 --output-len 1` · **q8_0** · **warm page cache** · 用临时的 `vt::GetOp` wall-time 钩子采集 · commit `bead27d` · **总计 1070 ms（这是 TTFT，不是吞吐）**。

**★ 本节的每一个数字都是 CPU 上的。** 正文若不把「CPU」写在数字旁边，读者会把它当成 GPU 案例——这是本篇最容易犯的 **P7（引文与断言作用域不匹配）**。

| 结论 | 值 |
|---|---|
| 最大占比的算子 | `kMatmulBTQuant`，**50.4%**，被明确写成「**the next lever**」 |
| 实际先做的算子 | `kMatmul`，**17.9%**，**LOW effort**（一个 loader flag） |
| 上界（Amdahl 完全消除） | `kMatmul`：**1.2180×**；`kMatmulBTQuant`：**2.0161×** |
| 实测（同二进制 A/B） | prefill **1.090×**、decode **1.09×** |
| 上界兑现率 | `1.090/1.2180 = 89.49%` |

> ★ **注意上界那一行的反直觉之处**：**占比大的那个上界更大**（`2.0161× > 1.2180×`），**而被选中的偏偏是上界小的那个**。
> **⇒ 「按上界排」和「按实测决策排」给出相反的顺序，差的正是「工作量能不能付得起」。**

> ⚠ **上界是「完全消除」才拿到的**。它对 `kMatmul` **是紧的**（真的做到了 `72 → 0` 次调用）；对 `kMatmulBTQuant` **不紧**——消除一个量化 GEMM 意味着换掉整条量化路径，那已经超出「优化」的范围。

## 4. 踩坑与失败模式

### 4.1 按占比排序

**现象**：拿到 profile，按 `share_pct` 降序，从第一个开始做。

**成因**：占比是**收益上界的估计**，而收益上界还需要「距上界多远」与「要付多少」两项。三者缺一，排序量就退化成占比。

**规避（可复现的判据）**：程序 §C 构造了一组候选，其中占比最高的那个在**两种**规则下都排第 1；**只**改它的工作量估计（`×4`，其余一律不动），排序**真的翻转**（第 1 名由 `op_hot` 变成 `op_mid`），而占比序列**一位都没变**。

**⇒ 判据**：`w_A/w_B > (s_A·d_A)/(s_B·d_B)` 时两个排序必然相反；**所有候选工作量相同时，按占比排序就是对的**（§0.1）。

### 4.2 忽略噪声地板去做 2% 的优化

**现象**：报一个 `+2%` 的改动，说它「有效」。

**成因**：`+2%` 落在测量噪声里。本库记录的两档**不同条件**的噪声（**[D]**，hipfire 的 `docs/methodology/perf-benchmarking.md`，平台 **gfx1100 / 7900 XTX**）：

| 条件 | 噪声带 |
|---|---|
| **同一会话内**做代码改动 A/B（受 DPM 状态、热余量、固件版本影响，**故要求换新进程跑**） | **±10–15%** |
| **graph capture 打开**时的读数离散度 | **1.5–3%** |
| **`HIPFIRE_VERIFY_GRAPH=0`（关掉 graph capture）** | **约 0.1%** |

> ★ **这三行是两个不同条件的数，不得混成一句「噪声带 ±1–3%」。** 合并后既不是 graph on 的档，也不是 graph off 的档，**而且丢掉了唯一的结论：条件决定档位**。
> ★ **方向也是反直觉的**：**关掉 graph capture 反而更稳**（`0.1% < 1.5–3%`）。「用 CUDA Graph 更确定」这个直觉在这一档数据上是**错的**。

**来源等级警告（P10 的本域最高风险处）**：上表**全部来自一个个人项目**，**未被独立复现**。**不得写成「业界经验表明噪声带是……」。** 同一份方法论文档另有一条**容差**规定：`speed-gate.sh` 相对**已提交基线**的容差是 **±5%**；「改变规范 bench 超过 5% 的 flag 才默认开启」。

> ⚠ **不要把它写成「收益 <5% 不值得做」。** 原文**没有**这句话。原文说的是「容差 ±5%」。**「不值得投入」是本库的推论（[E]）**，且它只在 gfx1100 那一档的测量条件上成立——换平台，噪声带不同，阈值就不同。

### 4.3 把「已有高度优化库可用」的算子当作自研目标

**现象**：清单里有一个 GEMM，占比不低，于是安排自研。

**成因**：距上界的距离那一项被算成了「峰值 ÷ 当前」，而不是「**该平台上可达到的最好实现** ÷ 当前」。如果 vendor 库已经在 90% 峰值上，自研能拿到的只有 10%。

**规避**：`距离` 这一项的分母**必须是「可达上界」而不是「标称峰值」**（`02-roofline-verdict` §2.2：可达带宽低于标称 ⇒ 可达 ridge 更高、可达上界更低）。判据表第 6 行。

### 4.4 跨阶段比较加速比（P9）

**现象**：说「这次优化让 prefill 快了 `1.1×`，decode 也快了 `1.09×`，所以整体快了约 `1.1×`」。

**成因**：prefill 与 decode 的**算子完全不同**（`01-model-to-operator-inventory` §4.3），而且**端到端时间轴不一样**。两个 `1.1×` 相乘/取平均都不对。

**规避**：**每个加速比必须带「分母是哪条时间轴」**。判据表第 8 行。本例里同一个改动对 prefill 是 `1.090×`、对 decode 是 `1.09×`——**两个数几乎相同，但那是巧合，不能推广**。

### 4.5 用 `kern_sum` 的占比去排 interval-union 的序

**现象**：把两个不同时间轴的占比混在一张排序表里。

**成因**：见 §2.1——`kern_sum` 与 `interval-union time` 是**两个分母**，而**流之间的重叠会同时改变排序与百分比**。

**规避**：判据表第 3 行——**profile 的分子与分母必须来自同一个时间轴**；用了兜底口径就把它标出来。

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**（本机无 GPU，本域任何一篇都不得声称有实测数据）。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 候选的排序只用 `share_pct` 一个量 | **不完整**；至少还要「到上界的距离」与「工作量」 |
| 2 | 有算子声称的加速比 > 「上界 ÷ 当前」 | **拒绝**该声称（headroom gate）；边界是闭的，恰好相等通过 |
| 3 | 占比来自 `kern_sum` 而排序表里还有 `interval-union` 的项 | **先统一时间轴**；两者会给出不同排序与不同百分比 |
| 4 | 一个算子的占比 ≥ 100% | 分母错了（很可能是把 `kern_sum` 与墙钟混用） |
| 5 | 候选的 `w`（工作量）全部相同 | **按占比排序就是对的**——此时不该提「别按占比排」 |
| 6 | 「到上界的距离」的分母用的是**标称峰值** | 换成**可达上界**；否则已高度优化的库会被当成自研目标 |
| 7 | 想做的优化收益 < 测量条件对应的噪声带 | **不做**（或先换测量条件）；阈值随条件变，见 §4.2 那三行 |
| 8 | 引用的加速比没写明分母是哪条时间轴 | **不可用**；prefill / decode / 端到端是三条不同的轴 |
| 9 | 优化对象是某个算子，但它落在「已有高度优化库可用」的集合里 | 距上界用「该库的实际水平 ÷ 当前」，不用标称峰值 |
| 10 | 排名前 3 的桶合计 ≥ 80% | 可以只看前 3 个——**但这是这份剖面的性质，不是普适规则** |
| 11 | 想先做「占比最大」的那个，而它的修复需要新 kernel | **先算 §B.3 的临界工作量比**；超过它就应改做不需要新 kernel 的那个 |
| 12 | 说「某改动使整体快 `X×`」，而 `X` 来自单算子实测 | **不成立**；单算子加速比必须乘以 Amdahl 上界 `1/(1−占比)` 才成为端到端上界 |
| 13 | kernel 覆盖份额 `p ≤ 0.5` | 任何 kernel 优化都到不了 `2×`；**先查时间是不是在 host 侧**（launch-starved 那一份不会被更快的 kernel 恢复） |
| 14 | 优化对象是「能不能不做」的候选（`elimination`） | **优先**——它拿到的收益不受 `p` 限制，而加速受 |
| 15 | 引用的噪声 / 门限量没有测量条件（平台、是否 graph capture、是否换新进程） | **不可用**；本域这类数字全是 **[D]** 级，条件即定义 |

**闭合性检查**：读完能把「先做哪个、某个声称能不能接受、这个收益值不值得做」判完。**唯一的表外输入**是「工作量」的数值——它在 §1.3 被明确标为最弱的一环，而**表里给的是临界比值（第 11 行）而不是一个数**，所以读者不需要接受任何本库自造的工作量定价。

## 6. 小结与延伸

- ★ **「17.9% 排在 50.4% 之前」不是算出来的**：三条数量规则（含「距离 × 占比 ÷ 工作量」）**都**把 50.4% 的排第一；能复现的是一条布尔判据——**要不要写新 kernel**。
- ★ **可判定的是临界值**：规则③ 需要 `工作量_A/工作量_B > 4.6606`；本库的秩映射给出 `2.50`，**不够**。所以**结论依赖工作量如何定价**——这一点必须写在正文，不能藏在公式里。
- ★ **headroom gate 是上游实现里真实存在的闸**（**[B]**）：声称的加速比**不得超过**该算子到其约束资源的距离；边界闭（`1.300` 通过、`1.301` 被拒）；实测 `1.090 ≤ 1.2180` 通过，兑现率 **89.49%**。
- ★ **kernel 未覆盖的份额不会被更快的 kernel 恢复**（**[B]** 逐字）：`p = 0.5 ⇒` 任何 kernel 优化的上界是 `2×`。
- ★ **两档噪声数不同条件，不得合并**：gfx1100 会话内 **±10–15%**；graph capture 开 **1.5–3%**、关 **约 0.1%**——**关掉反而更稳**。**全部 [D] 级，未被独立复现。**
- ★ **占比大的那个 Amdahl 上界更大**（`2.0161× > 1.2180×`），**而被选中的是上界小的那个**——差的正是工作量。
- **`elimination` 应该排在 `faster execution` 之前**：消除不受 `p` 限制。
- **§3 的全部数字是 CPU 剖面**（aarch64 DGX / 20 线程 / q8_0 / 1070 ms TTFT），**不是 GPU**。

**延伸**：

- 「到上界的距离」怎么算：`45-kernel-lifecycle/requirement-discovery/02-roofline-verdict`。
- 候选清单怎么来：`45-kernel-lifecycle/requirement-discovery/01-model-to-operator-inventory`。
- Amdahl 上界的通用形式与扩展性分析：`10-foundations/performance-models/02-amdahl-and-scaling`（**正文在该域，此处回链**）。
- 一个算子**怎么改**（而不是「先改哪个」）：`40-kernels/*`——例如 MoE 的 grouped GEMM 与 permute/unpermute，回链 `40-kernels/moe-kernels/01-moe-compute-pattern`。
- profiling 工具本身的用法（nsys / ncu / CUPTI）：**不在本域**，见 `50-performance`（**未建成**）。
- 收敛与停止条件（残差是噪声还是工程能触及的）：`45-kernel-lifecycle/convergence-and-tuning`（**未建成**）。
