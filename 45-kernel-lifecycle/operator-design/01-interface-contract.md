# 接口契约：凡改变「构建出哪个 kernel」的字段都是契约

> **一个算子的契约不只是「输入输出形状」。凡是会改变「编译出哪个 kernel」的东西都是契约的一部分**——包括可选参数**是否出现**、dtype、layout。漏掉任一项，缓存就会命中错误的 kernel。
>
> **这条规则是双向的、而且两个方向坏的方式不同**：**漏**一个改变构建的字段 ⇒ **静默**用错 kernel（没有异常、没有警告）；**多**一个不改变构建的字段 ⇒ 缓存**一次都不命中**（每次 rerun 都重编）。
>
> **一条可机械判定的论断**：一份契约里只要有一个必填字段的取值域被声明为 `unspecified`，这份契约就**不存在能失败的测试**——它的可测性是 **0**，不是「较弱」。`code/01_contract_check.py` 的 §A.3 把这个判据做成了断言。

## 0. 背景与动机

### 0.1 一个具体的对照场景：两个调用方，同一份假设，两种默认值

同一个 `layernorm` 算子，被两个调用方使用：

| | 调用方 A（推理服务） | 调用方 B（训练循环） |
|---|---|---|
| 它假设的**边界行为** | 越界就 `clamp`（推理侧不关心尾部） | 越界就 `raise`（训练侧希望早崩） |
| 它假设的**确定性** | `run_to_run_stable` 就够 | 需要 `bitwise_reproducible`（要复现实验） |
| 它**没有**声明的是 | 两者都没在契约里写这两项 | 同上 |

契约里如果**没有**这两个字段，A 与 B 都会**各自假设一个默认值**——而它们假设的默认值不相等。于是同一份代码在两个调用方手里**跑的不是同一个 kernel**，而**没有任何一方会看到错误**。

**⇒ 契约不完整的代价不是「文档不好看」，而是「同一份契约下，两个调用方对同一个名字理解不同」**——而这个名字会进 cache key、进 dispatch、进测试基线。

### 0.2 为什么「可选参数是否出现」也算契约

最容易被漏掉的一项不是 dtype，也不是 shape，而是**可选参数的存在性**。

理由：一个可选参数**出现**时，构建器可能走一条**完全不同的路径**（例如一条融合的 epilogue）。于是「传了它」与「没传它」是**两个不同的 kernel**。

**⇒ 如果 cache key 只记录字段的值、不记录字段是否出现，这两个调用会哈希到同一个键。** 这是本篇 §C 要真的构造出来的那个错误。

### 0.3 本篇在本域主线上的位置：它守的是**上界的前提**

本域的主线是「**到上界还有多远，以及那段距离值不值得走过去**」。三个主题各占一环：

| 主题 | 「上界」在这一环是什么 |
|---|---|
| `requirement-discovery` | roofline 给的理论上界——**上界在哪** |
| **`operator-design`** | 候选设计各自的上界——**怎么抬高上界**（02/03 篇）＋ **守住上界的前提**（本篇） |
| `implementation` | 正确性门——上界只有在算对的前提下才有意义 |
| `convergence-and-tuning` | 剩余距离是工程能触及的，还是噪声 |

**本篇站的是「守住前提」这一格**，理由有三条：

1. **上界必须挂在**一个**确定的**对象上。roofline 算出的 `AI` 与 ridge，描述的是「**哪个** kernel」；如果 cache 命中了另一个 kernel，那个上界描述的就**不是**你在跑的东西。**前提错了，后面每一步都白算。**
2. **契约的作用域是「构建期」，而它的后果出现在「测量期」**。契约漏字段时不会有任何即时反馈——错误会一路传导到性能数字上，那时已经**无法区分**「设计不好」与「跑的其实是另一个 kernel」。
3. **这一环的代价是非对称的**：写好契约是一次性的（几分钟），而漏一个字段可能让你用几天去优化一个**你没在跑**的 kernel。

**⇒ 契约是「一票否决」的**——与 `implementation` 的正确性门同构（那里是「算对之前不谈性能」，这里是「**确定跑的是哪一个之前不谈上界**」）。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。契约、字段、cache key 都是**声明**，不是实现。

## 1. 原理：契约的七个字段，以及「这一项为什么必须写」

### 1.1 七个字段

| # | 字段 | 取值域（本篇的声明） | **为什么必须写** |
|---|---|---|---|
| 1 | **形状规则** | `rank_2` / `rank_2_or_3` | 它决定**形状怎么算**（哪几维参与、是否广播）。**它是模式，不是每次调用的取值**——所以它**不进** cache key（见 §1.2） |
| 2 | **dtype** | `fp16` / `bf16` / `fp32` | 不同 dtype ⇒ **不同的 kernel**（张量核路径 vs 向量路径）。除了「构建哪个」，它还决定容差（→ 02 篇） |
| 3 | **layout 与 stride** | `row_major_contiguous` / `col_major_contiguous` / `strided` | 同一份逻辑数据按不同 layout 存，装载指令与 tile 划分**都不是同一个**。且 `strided` 会**打破对齐前提**（→ 03 篇） |
| 4 | **可选参数** | `absent` / `present` | **存在性**改变构建结果（§0.2）。这是最容易被当成「值」而不是「有无」的一项 |
| 5 | **输出精度** | `same_as_input` / `fp32_always` | 累积器与输出的 dtype 决定 kernel 的 epilogue 形态；也是**容差口径**的入口（→ 02 篇） |
| 6 | **确定性** | `bitwise_reproducible` / `run_to_run_stable` | 确定性归约与非确定性归约（顺序不固定 / 原子加）是**两个 kernel**。而 PTX **不保证**顺序（→ 02 篇 §2）⇒ 这一项**必须由实现方保证**，不能引用规范 |
| 7 | **边界行为** | `raise` / `clamp` / `pad_and_mask` | 越界处理方式决定是否要边界检查代码、决定尾块的写法（→ 03 篇 §3） |

**七项全部必填。** 缺任何一项，检查器都要报出来——**不是只报「确定性」那一个**（程序 §A.2、§A.4）。

### 1.2 「契约字段」与「调用级输入」是两类东西

这一节是关于 §1.1 表里第 1 行的一个**必须说清的区分**：

| | 契约字段 | 调用级输入 |
|---|---|---|
| 例子 | `shape_rule`（形状怎么算的**规则**） | `call_shape_MNK`（这次的**具体** M/N/K） |
| 每次调用是否改变 | **不改变** | **改变** |
| 是否进 cache key | **不进** | **进** |

**理由**：`shape_rule` 声明的是「形状怎么算」这条规则，每次调用都相同；而**具体的形状值**直接决定 tile 选择 ⇒ 它**必须**进 key。**把这两件事混为一谈会得到相反的错误**：把 `shape_rule` 放进 key ⇒ 无害但无用；把**具体形状**漏出 key ⇒ **静默用错 kernel**（同一个算子在不同 M/N/K 下会选到不同 tile）。

**同一个区分还有第三个成员**：像 `stream` / device context 这类**运行期**才定的值，**既不是**契约字段，**也不改变构建结果** ⇒ **不进 key**（进了就是反方向的错误）。

> ★ **一条来自某一实现的、反直觉的佐证**（**[B] 级，只支撑「vLLM 这么做」**，P10）：vLLM 的 `vllm.ir.op` 文档明确要求 `supports_args` **不应**检查 batch size，也不应加「基于取值」的守卫。⇒ **「运行期才定的值不进编译期决策」这条规则在实现里是被写下来的**，不是本库的推论。程序 §D.2 把它做成了断言。

### 1.3 可测性：`unspecified` 不是一个较弱的值，**是一个空集**

§1.1 的第 7 行给了「边界行为」三个**可选值**。如果契约把它声明成 `unspecified`，会发生什么？

**答：这份契约**不存在能失败的测试**。** 判据是机械的：

> 一个字段是**可测的** ⟺ 它的取值域承诺了**可观察的区别**。域为 `unspecified` ⇒ 无论实现怎么行为，契约都没有被违反 ⇒ **不存在任何能失败的测试**。

这不是「测试写得不够好」的问题，是**契约根本没有承诺任何东西**。而下游会**照样依赖它**——这就是 §4 坑 ②。

**⇒ 一条可证伪的论断**：把「边界行为」的域从三个具体值改成 `unspecified`，可测性从 **1（可测）** 直接掉到 **0（不可测）**，**中间没有连续的中间态**。程序 §A.3 断言了这一点。

### 1.4 一致性检查：契约也可以声明自己的互斥

契约里可以有**互斥对**。本篇的示例是：

```
determinism = bitwise_reproducible   ⊗   optional_params 含 use_atomics
```

**依据不是「原子加慢」，而是一条规范事实**（→ 02 篇 §2）：PTX ISA 明文规定 `wmma.mma` 的 **`accumulation order` 未规定**（逐字，见 `code/specs.py` 的 `PTX_WMMA_UNSPECIFIED_ASPECTS`）。**任何让累加顺序依赖调度或并发到达次序的实现，都不可能逐位可复现**——这是从 A 级规范事实**推出来**的互斥（本库推论 **[E]**），不是性能判断。

**⇒ 这条把 01 篇与 02 篇接上了**：契约里写 `bitwise_reproducible` 这三个字，等于对实现提了一个**规范不保证**的要求。程序 §A.4 断言了冲突被报出、且依据是那条规范事实。

## 2. 执行映射：契约在框架里落在哪

### 2.1 三层落点：注册 → dispatch → cache key

| 层 | 它做什么 | 契约在这里的作用 |
|---|---|---|
| **注册** | 声明「有这个算子」+ 它的语义 | 契约就是声明的对象 |
| **dispatch** | 决定「这次调用走哪份实现」 | 契约字段是 dispatch 的**输入** |
| **kernel cache key** | 决定「这次调用复用哪个已构建的 kernel」 | ★ **本节的焦点**：key 必须覆盖所有**改变构建结果**的字段 |

### 2.2 两层支持性检查（**[B] 级 · vLLM 的做法**）

> ★ **P10 标注**：以下是 **vLLM 一家**的做法（其 `vllm.ir.op` 文档与 `vllm/config/kernel.py`）。**不得**写成「业界通常」「主流做法」。

vLLM 的实现注册接口把「能不能用」拆成**两层**：

| 层 | 形态 | 求值时机 | 允许判什么 | **不允许**判什么 |
|---|---|---|---|---|
| `supported` | **静态布尔** | **import 时求值一次** | 平台 / 库是否存在 | 任何运行期状态 |
| `supports_args` | **动态谓词** | 编译期用 fake tensor、eager 路径用真 tensor | 类型与形状 | ★ **batch size**、任何「基于取值」的守卫 |

**三条可操作的结论**：

1. **两层不是一层**。「这个平台上有没有这个库」与「这次调用的参数支不支持」是两个不同的问题——混成一层就会得到「一会儿能一会儿不能」的行为。
2. **`supported` 在 import 时求值一次** ⇒ 它**不能依赖运行期状态**。把运行期才定的值放进去，行为会随 import 顺序变化。
3. **`supports_args` 不得查 batch size** ⇒ ★ 这与「凡改变构建结果的字段都要进 key」**不矛盾**，因为 batch size **不改变构建出哪个 kernel**，它只改变**同一个 kernel 的调用参数**。**两条规则是同一条规则的相反方向**。

**选择规则**：优先级列表中**第一个 `supported` 且 `supports_args` 通过的实现**。`register_impl` 的 provider 名里有**保留名**（`native` 是 `@register_op` 自带的那份）⇒ **列表永远有兜底**。配置入口是一个显式 CLI 前缀（`--ir-op-priority`）。

### 2.3 compile key 的规则是**双向**的

vLLM 的 `KernelConfig.compute_hash()` 的 docstring 写着一条**双向**规则（**经检索转述**，**不是逐字**——见 §4.3 的引用纪律）：

> 任何**影响编译**的新字段都应加进 hash；任何**不影响编译**的新字段都应排除。

**两个方向各自的后果**：

| 方向 | 后果 | 症状 |
|---|---|---|
| **漏**一个改变构建的字段 | 两个不同的 kernel 塌成**同一个 cache 条目** | **静默**用错 kernel（无异常、无警告） |
| **多**一个不改变构建的字段 | 每次调用算出**不同的 key** | 缓存**一次都不命中**，每次 rerun 都重编 |

**⇒ 「多放几个保险」是错的。** 这两种病都真实存在，且**第二种更容易被当成「正常」**（「慢一点而已」）。

### 2.4 现实里的形态不是「有人忘了写」，而是「机制上看不见它」

★ 这是本篇 B 类最值得记住的一条（**[B] 级 · vLLM**，经检索转述）：

vLLM 的 IR 实现有一个 `IrOpImpl.uuid()`，它是**实现源文件内容**的哈希。而代码注释里写着（**经检索转述**）：

> 实现被 Dynamo **隐藏**，所以它们**不会出现在被追踪的文件列表里**。

⇒ 结果：一个**真的会改变构建结果**的输入（实现源文件的内容），**在机制上不可见**，必须**手工**把它加进 hash factors（`IrOpPriorityConfig.compute_hash()` 里那份手工收集就是干这个的）。

**这条的意义**：**现实的失败形态不是「粗心」，而是「自动收集机制覆盖不到的那一部分」**。⇒ 判据不是「我有没有仔细检查」，而是「**我的 key 是自动收集的还是手工维护的；手工维护的那份，有没有一个检查**」。

### 2.5 反方向的对照（**[D] 级 · 单一社区项目 · 未被独立复现**）

> ⚠ **D 级标注**：以下来自**一个社区仓库的 issue**（ai-dynamo/dynamo #10119），是**单一主体、未被独立复现**的报告。**它不得单独支撑任何结论**——这里只把它与 §2.3 的 B 级规则**同向**印证。

该 issue 记录的是**反方向**的一次真实故障：一个**不改变构建结果**的运行期字段（worker id）进了 config hash ⇒ 每次 rerun 都算出新 hash ⇒ torch.compile 缓存**一次都不命中**。

**⇒ 与 §2.3 的规则方向一致**（那是一条 B 级官方规则，这是一例 D 级实际发生），两者对照才允许写进来。

### 2.6 `@register_op` 的三合一（**[B] 级 · vLLM 的做法**）

vLLM 的 `@register_op` 装饰器让「算子声明」与「native 实现」是**同一个函数**，而这个函数同时承担三件事：

| 它同时是 | 用途 |
|---|---|
| **语义定义** | 这个算子的**意思**是什么 |
| **默认实现** | 没有别的 provider 时跑它 |
| **测试基线** | 对照测试的**参考** |

**⇒ 「三合一」不是省事，而是把「语义」与「实现」的分歧**消灭在源头**：如果语义定义与默认实现是两份东西，它们可以漂移；是一份东西就漂移不了。

> ⚠ **与 `implementation` 主题的边界**：那里讲的是「参考实现必须与被测实现**独立**」。这里说的是**声明层的三合一**。两者的对象不同：这里是「语义 ↔ 默认实现」，那里是「被测实现 ↔ 参考实现」。**别混**。

## 3. 从「随手定」到「契约驱动」

| | 随手定 | 契约驱动 |
|---|---|---|
| 字段从哪来 | 写到哪想到哪 | 一张**必填清单**（§1.1 的七项） |
| 可测性 | 没想过 | 每个字段的域**承诺可观察的区别**（§1.3） |
| cache key | 「先放几个看看」 | **枚举所有改变构建的字段**，逐个比对（§2.3） |
| 冲突 | 运行期才发现 | 契约**声明互斥对**（§1.4） |
| 缺字段 | 下游各自假设默认值 | 检查器**报错**（§0.1） |

**落地形态**（vLLM 的做法，**[B] 级**）：把「声明语义 + 默认实现 + 测试基线」做成一个装饰器（§2.6），于是契约**不是**一份单独的文档，而是**代码里的一个对象**——它可以被检查器读、被 dispatch 读、被测试读。

**⇒ 「契约驱动」的可操作定义**：**契约是一个可以被程序读的对象**，而不是一段散文。本程序就是那个「读它的程序」。

## 4. 踩坑与失败模式

### 4.1 cache key 漏字段 ⇒ **静默**用错 kernel

**现象**：同一个算子在两个调用点返回了**同一个 kernel 对象**，但两个调用点要求的行为不同。

**成因**：某个**改变构建结果**的字段没进 key。

**本程序 §C 真的构造出来了这个错误**（**本库构造的仿真**，不是任何真实故障——见 §4.4）：

| 步骤 | 观测量 |
|---|---|
| 两个调用只在 `optional_params` 上不同 | 差异字段恰好 `['optional_params']` |
| 有缺陷的契约（key 漏该字段）下 | `key(A) == key(B)` ✓；**只发生 1 次构建**；两次拿到**同一个对象** |
| 而正确的构建本该产出 | 两个**不相等**的 kernel（`epilogue=plain` vs `epilogue=fused`） |
| 结论 | 返回给 B 的 kernel **≠** B 应得的那个 ⇒ **静默错误成立** |
| 反事实（把字段放回 key） | 发生 **2 次**构建、两个调用拿到**不同**的 kernel、各自**都等于**应得的那个 ⇒ 错误消失 |

**★ 反事实那一步是本 C 类的关键**：它使结论**可证伪**——如果加回字段而错误不消失，说明缺陷模型没抓住因果，前面的结论就不成立（程序 §C.4）。

**规避**：判据表第 3、4 行。

### 4.2 契约里写「未定义行为」，然后下游依赖它

**现象**：契约把某个字段声明成 `unspecified`，下游代码**照样按某个约定的行为写**。

**成因**：把 `unspecified` 当成了一个「较弱但仍有承诺」的值。**它不是**——它是一个**空集**（§1.3）：**不存在能失败的测试**。

**规避**：判据表第 1 行。**判据是机械的**：域为 `unspecified` ⇒ 可测性为 0 ⇒ 该字段必须被单独标出来，且下游**不得**依赖它。

### 4.3 ★ 引用纪律：本篇有一条引文**不够格**标「逐字」

本篇引用了 vLLM 的一条 docstring 规则（§2.3）。**它不够格标「逐字」**：

| 引文 | 检索次数 | 本篇的标注 |
|---|---|---|
| PTX ISA 的 `wmma.mma` 精度段（→ 02 篇 §2） | **两次独立检索一致**，出处到文档级 | **逐字**（`PTX_WMMA_UNSPECIFIED_QUOTE_IS_VERBATIM = True`） |
| vLLM `KernelConfig.compute_hash()` 的 docstring 规则 | **一次** | **经检索转述**（`VLLM_KERNELCONFIG_HASH_RULE_IS_VERBATIM = False`） |

**⇒ 这个对照本身就是纪律的执行记录**：不是「我引用了」就够，要**够格**才写成逐字。程序 §D.5 把这条标成了一个**会被断言的布尔**——改它 `make run` 就失败。

**为什么这条要写进「踩坑」**：上一轮（`requirement-discovery`）把一个**编出来的引文**标成了「逐字」，被独立检索抓到。**同一个错误最容易在「就差一点」的地方复发。**

### 4.4 把「本库构造的仿真」写成「真实故障」

**现象**：§4.1 那张表看起来很具体（有 key、有构建次数、有对象身份），于是被读成「某个框架真的这么坏过」。

**事实**：**检索没有找到任何一例**「key 漏字段 ⇒ 静默返回错 kernel」的公开案例（见 `code/specs.py` 的 `UNSOURCED` 第 5 项）。本篇的 §C **是本库构造的仿真**，`specs.py` 的 `UNSOURCED` 元组里专门记了这一项，程序 §D.8 断言它存在。

**规避**：写这类例子时，**在例子的旁边**（不是脚注里）写明「本库构造」。

### 4.5 把两层支持性检查做成一层

**现象**（vLLM 的语境下）：把「平台/库是否存在」与「这次调用的参数支不支持」放进同一个判断。

**后果**：判断结果会**随求值时机变化**——一次在 import 时被固化，一次在编译期被求值，混在一起就得到「一会儿能一会儿不能」。

**规避**：判据表第 6 行；**注意 `supported` 只在 import 时求值一次**。

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**（本机无 GPU，本域任何一篇都不得声称有实测数据）。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 某字段的取值域被声明为 `unspecified` | 该字段**可测性为 0**——不存在能失败的测试；**标出来**，且下游不得依赖它 |
| 2 | 一份契约缺了七项里的任意一项 | **停**——不补不写；缺项的后果是「两个调用方各自假设一个默认值」 |
| 3 | 一个字段的值不同 ⇒ 构建出**不同的 kernel** | 它**必须**进 cache key |
| 4 | 一个字段的值不同 ⇒ **同一个** kernel、只是调用参数不同 | 它**不得**进 key（进了就是「缓存永不命中」） |
| 5 | 想在 key 里「多加几个保险」 | **不许**——key 的规则是**双向**的：漏 ⇒ 用错 kernel；多 ⇒ 永远重编 |
| 6 | 判断「这次调用能不能走某个实现」 | 分两层：**平台/库存在性**用 import 时求值的静态布尔；**类型与形状**用动态谓词；**两者都不判 batch size** |
| 7 | 一个字段是「模式」（每次调用相同） | 它**不进** key；但**具体的形状值**必须进——**这两件事不能混** |
| 8 | 契约里出现 `bitwise_reproducible` | 实现方**必须自己保证**累加顺序——PTX 明文规定顺序**未规定**（→ 02 篇 §2） |
| 9 | 契约要声明两个选项互斥 | 互斥的**依据**必须能指到一条规范事实或一条实测；**不得**只写「一般不这么用」 |
| 10 | 一个改变构建结果的输入**在机制上不可见**（不在自动收集的范围内） | **手工**把它加进 hash，并**为它写一个检查**——现实的失败形态是「机制看不见」而不是「人粗心」 |
| 11 | 引用一条外部规则作依据 | 先问**检索了几次**：两次独立一致 ⇒ 可写「逐字」；一次 ⇒ 只能写「经检索转述」 |
| 12 | 要举一个「用错 kernel」的例子 | 先确认它**有出处**；没有 ⇒ **明写是本库构造的仿真**，并记进 `UNSOURCED` |
| 13 | 契约字段与调用级输入混在一张表里 | **分开**：契约字段是模式（跨调用不变），调用级输入是每次变的量 |
| 14 | 算子声明、默认实现、测试基线是三份东西 | 把它们合成**一份**（声明即实现即基线）——两份就会漂移 |

**闭合性检查**：读完这张表能把「一份契约缺什么、哪些字段该进 key、key 该用什么粒度、引文该怎么标」判完。**唯一的表外输入**是「某个字段是否真的改变构建结果」——它取决于**具体的构建器**，必须去读构建器（本库不做具体实现，回链 `40-kernels`）。

## 6. 小结与延伸

- ★ **契约的判据是「是否改变构建出哪个 kernel」**，不是「看起来重不重要」。⇒ dtype / layout / **可选参数是否存在** / 输出精度 / **确定性** / 边界行为**都算**。
- ★ **七项全部必填。** 缺项的代价不是文档不好看，而是**两个调用方各自假设一个默认值**，于是同一个名字指的是两个 kernel。
- ★ **`unspecified` 不是「较弱的值」，是空集**：可测性从 1 直接掉到 0，没有中间态。
- ★ **compile key 的规则是双向的**：漏一个改变构建的字段 ⇒ **静默**用错 kernel；多一个不改变构建的字段 ⇒ **永不命中**。两种病都真实（第二种只有 D 级佐证，见 §2.5）。
- ★ **「可选参数的存在性」是最容易漏的一项**：本程序 §C 真的构造出两个只在它上面不同的调用命中**同一个 cache 条目**、拿到**同一个对象**，而正确的构建本该产出两个不同的 kernel。
- ★ **现实里的漏字段不是粗心，是机制看不见**（vLLM 的实现源文件被 Dynamo 隐藏，必须手工进 hash）。
- ★ **`shape_rule` 不进 key，但具体的形状值必须进**——把这两件事混起来会得到相反的错误。
- **契约是可测性的载体**：一个字段的域决定**有没有测试能失败**。
- **引用纪律**：本篇有一条引文**只检索过一次** ⇒ 只能标「经检索转述」，程序把这条标成了一个会被断言的布尔。

**延伸**：

- 契约里 `bitwise_reproducible` 这条要求为什么**规范不保证**，以及容差预算怎么定：`45-kernel-lifecycle/operator-design/02-numerical-design`。
- 契约里第 3、7 两条如何变成**约束方程**（对齐 / 布局 / tile）：`45-kernel-lifecycle/operator-design/03-tiling-and-boundaries`。
- 上界在哪、以及「该不该做这个算子」：`45-kernel-lifecycle/requirement-discovery/02-roofline-verdict`、`03-optimization-priority`。
- 算子的具体实现（本域**不讲**的边界）：`40-kernels/*`。
- 编程接口本身的用法（本域**不讲**）：`30-gpu-programming/*`。

```bash
cd 45-kernel-lifecycle/operator-design/code
make 01_contract_check               # 或 make run，跑本主题全部三个编号程序
```

本篇对应的编号程序是 **`code/01_contract_check.py`**。它**只用标准库**（含 `ast`，用来读同目录另外两个程序里的常量覆盖表）、**不 import torch**、不碰 GPU。

- **A 类**：四份契约的检查报告与手判一致——完整契约的报告**必须为空**（四类发现全空）；缺 `determinism` 的报告**恰好**是 `['determinism']`；把 `boundary_behavior` 的域声明成 `unspecified` 的报告**恰好**是 `['boundary_behavior']` 且**不是** `missing`（两件事不能混）；互斥对同时被选中时报出冲突，且依据是 A 级规范事实。
- **B 类**：枚举**所有改变构建结果**的字段（6 个），正确契约的 cache key 缺失项**必须是空集**，漏一项的那份**恰好**报出那一项；并区分「契约字段」与「调用级输入」，含一个**反方向**的对照项（`stream_device_context` **不该**进 key）。
- **C 类**：构造两个只在 `optional_params` 上不同的调用，显示它们 **哈希到同一个 key**、**只发生一次构建**、**返回同一个对象**，而正确的构建本该产出**两个不相等的 kernel** ⇒ **静默错误**；再用**反事实**（把字段放回 key）证明错误**消失**；最后给出**反方向**的错误（把 `stream_device_context` 放进 key ⇒ 缓存一次都不命中）。
- **D 类**：`specs.py` §1 的每条常量逐条被断言钉住；含一条 **`ast` 的跨程序机械检查**——三个程序的常量覆盖表**并集 == `specs.py` 的全部模块级常量**，且**两两不交**。⇒ 在 `specs.py` 里加一个没人断言的常量，`make run` 立刻失败。

判据若被改错，程序以**非零码**退出。
