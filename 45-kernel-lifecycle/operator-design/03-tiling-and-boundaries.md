# 分块与边界：只测 2 的幂形状，对「最后一个 tile」零捕获

> **边界 bug 不会在第一块 tile 上暴露。只测 2 的幂形状的验证，对「最后一个不完整 tile」类 bug 零捕获。**
>
> **这条在本机被真的跑出来了**（`code/03_tiling_check.py` §C）：三个「**只在最后一 tile 出错**」的缺陷模型（丢 M 尾块 / 尾块起点夹回却写错位置 / 丢 K 尾块），用**只含 2 的幂形状**的测试集跑，**4 个形状 × 3 个缺陷 = 12 次比对，捕获数 0**；换成按 §1 约束推出的**边界形状集**后，三个缺陷**全部被捕获**。
>
> **第二条可证伪论断**：寄存器预算的真实上限是 **248**，**不是 255**——因为寄存器按 **8** 一档分配，`255` 向下取整到 **248**。⇒ 一个需求 **250** 个寄存器的 tile 是**非法**的，而「直接拿 250 ≤ 255 比」的朴素判据会接受它。

## 0. 背景与动机

### 0.1 为什么 tile 选型是「受约束的离散选择」，不是连续调参

「调参」的隐含前提是**参数可以连续变化、目标函数连续**。tile 选型**两条都不满足**：

| | 连续调参 | **tile 选型** |
|---|---|---|
| 参数空间 | 连续 | **离散且稀疏**：`M` 的粒度是 fragment 的边长，shape 只有少数几种合法组合 |
| 目标 | 连续函数 | 由**四条约束是否同时满足**决定 ⇒ 边界是一道道**闸门** |
| 「差一点」 | 有意义 | ★ **没有意义**：`TM = 48` 与 `TM = 47` 不是「接近」，后者**不合法** |

**⇒ 本程序 §B 的实跑**：在一个 `2,625` 组的穷举空间里，合法组合只有 **955** 组——**63.6% 的候选直接不合法**。

**★ 而且「谁在卡它」不是均匀分布的**：

| 最紧的那条约束 | 合法组合数 |
|---|---|
| **寄存器** | **820** |
| warp 数 | 128 |
| **共享内存** | **7** |

**⇒ 「四者取最紧」不是一句修辞**：寄存器是绝大多数合法配置的**实际限制**，而共享内存只卡住了 7 组。**如果把预算算错在寄存器上，影响面是共享内存的 100 倍以上。**

### 0.2 一个具体的对照场景：同一份代码，两种输入

```text
配置：tile (64, 64, 16)，fp16

输入 A：M = N = K = 512     ← 三个轴都是 64 / 64 / 16 的整数倍
输入 B：M = 513, N = 512, K = 512   ← 只多了一行
```

| | 输入 A | 输入 B |
|---|---|---|
| 不完整 tile 的个数 | **0** | **1**（M 方向多得的那一行） |
| 只在尾块出错的 bug 会不会触发 | ★ **不会** | ★ **会** |
| 一组「只跑 2 的幂」的测试能发现它吗 | — | **不能**（它只在 B 上出错） |

**⇒ 「测试通过」这句话在 A 上和在 B 上**含义完全不同**。** 而 A 是所有人写测试时的第一直觉。

### 0.3 本篇在本域主线上的位置：它**抬高上界**（另一条路）

01 篇守的是「上界的前提」（确定跑的是哪一个 kernel），02 篇抬高上界靠**精度档位**，**本篇抬高上界靠分块**：

1. **分块是把「装不下」变成「装得下」的唯一手段。** 一个问题的数据量远大于片上容量 ⇒ 必须切。**切法直接决定能走哪条路径**（能不能用张量核、能不能用多级流水）。
2. **约束方程给出的是「上界的可行域」。** 它不告诉你哪个 tile 最快，它告诉你**哪些 tile 根本不可能**——而**排除掉 63.6% 的候选**本身就是最大的信息量。
3. **边界是「上界能不能被守住」的关口。** 一个在 512³ 上贴着上界的实现，如果在 513×512×512 上算错，**那个上界对它毫无意义**——这就是本篇 §C 的意义。

> ⚠ **与 `implementation` 主题的边界**：那里讲「**验证**该测什么」（验证矩阵）。本篇讲「**设计**时怎么算出该测哪些形状」——**从约束方程推出来**，不是枚举出来的。两篇的接口是 §1.4 的那个形状集。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。约束方程、tile 参数、边界形状都是**声明与算式**，不是实现。

## 1. 原理：约束方程

### 1.1 四组约束，以及一个必须分开的类别

| # | 约束 | 形态 | 修复方式 |
|---|---|---|---|
| ① | **fragment 的离散性** | tile 各维必须是 fragment 边长的倍数；每个 warp 至少分到一个 fragment | 换 tile 参数 |
| ② | **寄存器预算** | 每线程 fragment 寄存器数（取整后）≤ 有效上限 | 换 tile 参数 / 换累加器档位 |
| ③ | **共享内存预算** | `(TM·TK + TK·TN)·esize·stages ≤ 上限` | 换 tile 参数 / 调 `stages` |
| ④ | **warp 数** | `WM·WN ≤ min(每 block 上限, 每 SM 上限)` | 换 warp 布局 |
| ⑤ | **对齐** | ★ **注意：它不是上面那种「预算」** | 见下 |

**★★ ⑤ 必须单独拿出来说，因为它的类别不同**：

| | ①–④（**tile 参数约束**） | ⑤（**问题形状约束**） |
|---|---|---|
| 判什么 | 我选的 tile 参数 | **问题自己的形状**（如行距 `N`） |
| 换 tile 参数能解决吗 | 能 | ★ **不能**——换遍所有合法 tile 结论都不变 |
| 修复方式 | 换参数 | **补 padding / 换布局 / 换算法** |

**本程序 §C.4 断言了这一点**：对 `N = 44`（fp16，`44 × 2 = 88` 字节，不是 32 的倍数），**换遍所有合法 tile，对齐判定一个都不变**。

**⇒ 把这两类混在一张表里，「不合法的原因」就无法定位了。** 判据表第 1 行。

### 1.2 ★ 寄存器预算的真实上限是 **248**，不是 255

这是本篇最容易被算错、且**有 A 级来源**的一条：

```
MAX_REGISTERS_PER_THREAD  = 255      （CUDA C++ Programming Guide §5.1）
REGISTER_ALLOC_GRANULARITY =   8      （同处：每线程寄存器数按 8 个一档向上取整）
⇒ 有效上限 = floor_to_8(255) = 248    （256 > 255 ⇒ 256 那一档不可达）
```

**★ 可证伪论断**：一个需求 **250** 个寄存器的配置**非法**——它会被取整到 **256**，超过 255。

| 判据 | 对 250 的结论 |
|---|---|
| 朴素（直接比 255） | 250 ≤ 255 ⇒ **合法** ❌ |
| **真实（按 8 取整）** | `ceil8(250) = 256 > 248` ⇒ **非法** ✓ |

**⇒ 程序 §B.2 给出了一对「**恰好**合法 / **恰好**非法」的参数**（都是**正好**落在档位上，不是「差不多到边界」）：

| | tile `(TM,TN,TK)` | warp 布局 | fragment 寄存器 | 结论 |
|---|---|---|---|---|
| **恰好不越界** | `(48, 112, 16)` | `1×1` | **248**（**正好**等于有效上限） | 合法 |
| **恰好越界** | `(32, 160, 16)` | `1×1` | **256**（**正好**比上限大一档） | 非法 |

**⇒ 「差一个粒度档」是这里最小的可分单位。** 判据表第 4 行。

### 1.3 共享内存：边界由 `stages` 决定，而且能算到「恰好」

共享内存的算式是 `(TM·TK + TK·TN) · esize · stages`。`stages` 是**唯一可以连续取值的量**这一事实让这一条特别好算：

```
tile (128, 128, 32)，fp16 ⇒ 每 stage = (128·32 + 32·128) × 2 = 16,384 B
上限 = 228 KB = 233,472 B
⇒ stages_max = floor(233,472 / 16,384) = 14
   stages = 14 → 229,376 B  ≤ 233,472  ✓ 合法（紧度 0.9825）
   stages = 15 → 245,760 B  > 233,472  ✗ 非法（紧度 1.0526）
```

**⇒ 程序 §B.1 给出这一对，并断言两者之差就是**恰好一个 stage**。** 判据表第 5 行。

> ⚠ **口径限定（必须一起搬）**：本程序把 `SMEM_PER_SM_MAX_KB = 228` 当作**每 block 的预算**用，这**忽略了两件真事**：carve-out 有保留量；每 SM 驻留多个 block 时预算被分摊。**⇒ 算出的 tile 上界是乐观上界**，真实可用的更小。

### 1.4 对齐要求落在哪：**三条规则、两个层级、一个不能做的换算**

> ★ **层级声明**：本节的约束方程写在 **CUDA C++ API 层**（设计者接触的是这一层），PTX 层的规则**单独列出**并标明层级。

| 规则 | 数值 | 层级 | 来源等级 |
|---|---|---|---|
| `mptr` 必须是 **32 字节（256 bit）** 的倍数 | 32 B | CUDA C++ API | **[A]** |
| `ldm` 必须是 **8**（`__half`）/ **4**（`float`）的倍数 | 8 / 4（**元素**） | CUDA C++ API | **[A]** |
| 起始地址按 **fragment 的字节大小**对齐 | **32 B** | PTX `wmma.load` | **[A]**（经检索转述） |

**★★ 这里有一个必须说清、否则一定会写错的换算**：

```
ldm 的单位是【元素】：8 个 __half × 2 B = 16 B
                      4 个 float  × 4 B = 16 B
⇒ 「ldm 是 8 或 4 的倍数」与「行距的【字节数】是 16 的倍数」是同一件事的两种写法
```

| 说法 | 对不对 |
|---|---|
| 「`ldm` 必须是 8 或 4 的倍数」 | ✓ |
| 「行距的**字节数**是 16 的倍数」 | ✓ |
| ★ 「**`ldm` 是 16 的倍数**」 | ❌ **错**——`8` 和 `4` **本身都不是** 16 的倍数 |

**⇒ 本程序 §A.2 把「16 ≠ 32 且 8 ≠ 16」写成了断言**——把两条规则钉成**不相等**，防止有人「顺手统一」成一个数。

**为什么这条值得单独写**：本库 `20-gpu-architecture/tensor-core/02-fragment-layout.md` 第 236 行**逐字警告**过这件事（「两个数都等于 16 字节，但不是同一条规则，别互相换算」）。**本域规格的初稿正是在这里写错的**（把 `ldm` 的「8 / 4」直接说成「均为 16 字节的倍数」）——**已订正**。

### 1.5 与 tile 参数无关的那一条：**问题形状**（cuDNN FP8）

> ★ **引用等级：经检索转述**；★ **本库此前未引用过这一条**（域规格标注「实施时须自行核到 cuDNN 文档原文」——本实现者做到了两处独立检索一致）。

cuDNN 对 Hopper 上的 FP8 卷积给出一条**问题形状**约束：

| 约束 | 值 |
|---|---|
| I/O **channels** 必须是 | **16** 的倍数 |
| `ConvolutionFwd` 的 **batch size** | **任意** |
| `ConvolutionBwFilter` / `ConvolutionBwData` 的 **batch size** 必须是 | **16** 的倍数 |

**★ 可证伪论断**：`channels = 15` 或 `17` 时，**换任何 tile 都不行**——这不是 tile 选型问题，是问题形状问题（程序 §C.5 断言了这一点）。

**★ 还有一处「方向不对称」**：**前向的 batch 任意，反向必须是 16 的倍数**。⇒ 与 02 篇的「FP8 累加：前向可用快档、反向需 `FLOAT`」是**两处独立的、同向的不对称**。

**⇒ 两条独立证据指向同一条结构性认识**：**「这个算子要满足什么」不是算子的属性，是「算子 × 方向」的联合属性。**（这与 `requirement-discovery/02` 的「受限类型是算子 × 精度路径的联合属性」**同构**。）

### 1.6 求解流程

```text
1. 定 dtype          → 得到 esize 与 ldm 的倍数要求（§1.4）
2. 枚举 tile 候选     → TM/TN/TK 取 fragment 边长的倍数（§1.1 ①）
3. 枚举 warp 布局     → WM×WN ≤ min(block 上限, SM 上限)（§1.1 ④）
4. 逐条算三组预算     → 寄存器（取整后 ≤ 248）/ 共享内存 / warp 数（§1.2、§1.3）
   取最紧的那条 = 它为什么合法/不合法
5. 单独过对齐闸门     → tile 侧：行距字节数 % 16 == 0
                       问题侧：N · esize % 32 == 0（§1.4、§1.5）
6. 从「合法集」里挑最优 → 本主题**不回答**这一步（那是 40-kernels 的边界）
```

**★ 第 5 步必须**单独**做**：它是**闸门**（合法/非法），不是一个可以和预算比值放进同一个 `max` 的量。

> ★★ **本实现者的初版在这里犯过一个错**（已订正，记在程序 §1 的 `tightness` docstring 里）：把对齐的紧度写成 `1.0`（布尔转比值），然后和其他三条预算一起取 `max` ⇒ **结果恒等于 `alignment`**，看起来像「对齐总是最紧的约束」。**那是度量错误，不是发现。** ⇒ 「四者取最紧」的正确读法是：**三条预算各自算比值取最大 + 一条前置闸门**。

## 2. 执行映射

### 2.1 落点一：约束方程的四个常量分别来自哪里

| 约束 | 用到的常量 | 来源等级 |
|---|---|---|
| 寄存器 | `MAX_REGISTERS_PER_THREAD = 255`、`REGISTER_ALLOC_GRANULARITY = 8` | **[A]** CUDA C++ Programming Guide |
| 共享内存 | `SMEM_PER_SM_MAX_KB = 228` | **[A]** H100 白皮书 |
| warp 数 | `MAX_THREADS_PER_BLOCK = 1024`、`WARP_SIZE = 32`、`MAX_WARPS_PER_SM = 64` | **[A]** CUDA C++ Programming Guide |
| 对齐 | `WMMA_MPTR_ALIGN_BYTES = 32`、`WMMA_LDM_ELEMENT_MULTIPLE = {fp16:8, fp32:4}`、`WMMA_FRAGMENT_BYTES = 32` | **[A]** CUDA C++ Programming Guide / PTX ISA |
| fragment | `FP16_FRAGMENT_SHAPES`、四个 `WMMA_*_FRAGMENT_REGS` | **[A]** PTX ISA |

**⇒ 四条约束的每个输入都有 A 级来源**；把它们**组合**成一个预算系统的那一层是**本库的建模 [E]**（见 §2.2）。

### 2.2 落点二：一个**明写的假设**，而不是一个编出来的数

寄存器模型要算「除 fragment 之外还要多少寄存器」（地址、索引、循环变量）。**这个数没有任何来源**——检索找不到「一个 `m×n×k` 的 tile 需要多少个非 fragment 寄存器」。

**⇒ 处置（这是本篇的一条纪律）**：**不编一个看起来真实的数，而是明写一个假设**：

```python
ADDRESS_AND_INDEX_REGS_ASSUMED = 0     # 本库的设计假设 [E]
```

**取 0 的后果**：算出的 tile 上界是**乐观上界**——真实能用的一定更小。**好处是结论不依赖一个编出来的数**：任何读者都能把它改成 40 重算一遍。

**⇒ 缺口被**标注**（进 `UNSOURCED`，程序 §D.5 断言它在那里），而不是被**填平**。**判据表第 10 行。**

### 2.3 落点三：`.f16` 累加器省一半寄存器——02 篇与 03 篇在这里**打架**

PTX 给出的 fragment 寄存器数（**三种 shape 相同，只有布局不同**）：

| fragment | `.f32` 累加器 | `.f16` 累加器 |
|---|---|---|
| A | 8 | — |
| B | 8 | — |
| C/D | **8** | **4** |

**⇒ 用 `.f16` 累加可以省一半累加器寄存器**——而累加器是寄存器预算里**最大的一块**（§0.1：820 组合法配置被寄存器卡住）。

**⇒ 于是两篇给出相反的倾向**：

| 篇 | 倾向 |
|---|---|
| 02 篇 | 用 `.f16` 累加 ⇒ `K` 只能到 **2048**（最坏界） |
| 03 篇 | 用 `.f16` 累加 ⇒ 累加器寄存器减半 ⇒ **更大的 tile 可行** |

**⇒ 这是同一个决定的两笔账，必须一起算。** 判据表第 11 行。

### 2.4 落点四：「冗余线程做空事」比 predication 更值得优先考虑

尾块的三种处理方式（**设计选择，不是实现细节**）：

| 方式 | 代价 | 什么时候用 |
|---|---|---|
| **predication**（越界线程跳过） | 每次访存都带一个判断 | 尾部**很小**、且分支可预测 |
| **mask**（越界处取单位元） | 多算但结果对；单位元选择错会**静默出错** | 归约类（加法取 0、乘法取 1、min 取 +∞） |
| **冗余线程做空事**（让尾块也跑满，结果丢弃） | 多算 | ★ 尾部**占比大**时最划算——**它把分支消掉了** |

**⇒ 判据不是「哪个更省」，而是「尾部的**占比**」**：尾部占比小 ⇒ 多算的代价小、消掉分支的收益大；占比大 ⇒ 反。**⇒ 这是一个可以从约束方程直接算出来的量**（尾块数 ÷ 总块数），不是经验。

## 3. 从「能跑」到「边界覆盖」

| | 能跑 | 边界覆盖 |
|---|---|---|
| 测试形状 | 「挑几个常见的」——往往是 2 的幂 | **从约束方程推出来**：每个轴 `tile 边长 + 1` |
| 覆盖的是什么 | ★ 只覆盖了**整除**的情形 | 覆盖**每个轴的不完整 tile** |
| 说「测过了」时的含义 | 「在整除的形状上对」 | 「在不完整 tile 上**也**对」 |

### 3.1 最小边界形状集**怎么推出来**

以 tile `(64, 64, 16)` 为例，三个轴各需要一个形状：

| 形状 | 余数 | 它抓什么 |
|---|---|---|
| `(65, 64, 16)` | M 余 1 | 尾块**被丢**（`M // TM` 而非 `ceil`） |
| `(64, 65, 16)` | N 余 1 | 尾块**起点夹回却写错位置** |
| `(64, 64, 17)` | K 余 1 | K 的余数**完全不参与累加** |

**★ 本程序 §C.3 的实跑结果（一条比初版**更弱但为真**的结论）**：

| 缺陷 | 被哪些形状捕获 |
|---|---|
| 丢 M 尾块 | `(65,64,16)`、`(129,64,16)`、`(65,65,17)` |
| 尾块写错位置 | `(64,65,16)`、`(64,129,16)`、`(65,65,17)` |
| 丢 K 尾块 | `(64,64,17)`、`(65,65,17)` |

**⇒ 每个缺陷被捕获 ⟺ **它那一轴有余数**。** 这条**成立**，而且很有用：**看到哪个形状红了就知道是哪个轴出了问题**（定位）。

**★★ 但下面这句话被实跑推翻了，本实现者初版就是这么写的**：

> ~~「三个轴各需要一个形状，**缺一不可**。」~~

**实跑**：形状 `(65, 65, 17)`（三轴各 +1）**一个**就捕获了全部三个缺陷。逐个删掉任一「单轴 +1」形状，**没有任何缺陷漏网**（程序 §C.3 把这两条断言和那段更正文字都保留在了输出里）。

**⇒ 更正后的表述**：

> **这组形状的作用是「定位」，不是「最小覆盖」。** 对本程序建模的三个缺陷，`(65,65,17)` 一个就够；per-axis 的形状让你知道**是哪个轴**坏了。

**⇒ 连带的一个诚实缺口**：`2·TM+1` 那一类形状（余数相同但跨两块）对本程序建模的三个缺陷是**冗余的**——**连续 tiling 下每个轴只会有一个不完整 tile**。它只在「余数自己还要再分块」时才有对象，而**那个场景本篇没有建模**（记进 `UNSOURCED` 第 6 项，程序 §D.5 断言它在那里）。

### 3.2 为什么 2 的幂形状是**结构性**覆盖不到

**这不是「测得不够多」，而是「那些形状上根本不存在那个对象」**：

> 一个「只在最后一 tile 出错」的缺陷，**在 2 的幂形状上不会出错**——因为那些形状**没有不完整 tile**。补再多 2 的幂形状，也永远不会有。

**⇒ 本程序 §C 的实跑**：

| 测试集 | 形状数 | 三个缺陷的捕获数 |
|---|---|---|
| 只含 2 的幂（64/128/256/512） | 4 | **0 / 0 / 0**（12 次比对，全 0） |
| §3.1 的边界形状集 | 6 | **3 / 3 / 2** |

**⇒ 这就是本篇的核心论断的直接证据**：**覆盖不足比写错更隐蔽**——因为「测试通过」四个字在两种测试集上**看起来一样**。

## 4. 踩坑与失败模式

### 4.1 只测 2 的幂

**现象**：测试形状是 `512³`、`1024×1024×1024`——「都是常见形状」。

**成因**：这些形状**三个轴都整除** tile ⇒ **不存在不完整 tile** ⇒ 尾块类缺陷**不可能被触发**。

**后果（本程序 §C.1 实跑）**：三个尾块缺陷的捕获数**全部为 0**。

**规避**：判据表第 12 行。**边界形状集要从约束方程推**（§3.1），不能靠枚举。

### 4.2 假设连续 / 对齐而未加保护

**现象**：kernel 假设输入是连续的行主序、行距是 16 字节的倍数。

**成因**：**真实数据常常不是**——一个 `N = 44` 的 fp16 张量，行距是 **88 B**，`88 % 16 = 8` ⇒ **不是 16 的倍数，更不是 32 的倍数**。

**后果**：**快路径非法**（装载指令会读到跨行的字节 ⇒ 整块 tile 行列错位）。

**规避**：判据表第 6、7 行。**注意：这一类换 tile 参数救不了**（§1.1 ⑤）——必须补 padding 或换布局。

### 4.3 用 `float4` 之类的向量化快路径，却没 gate 对齐与 `stride == 1`

**现象**：看到连续访存就上向量化路径。

**成因**：向量化路径的前提是**两个条件同时成立**——**地址对齐**与**步长为 1**。只 gate 了一个，另一个就会静默出错。

**规避**：判据表第 6 行。**两个条件都要 gate**，且**判据要在设计里写出来**（不是运行期才发现）。

### 4.4 输出与输入同 buffer（别名）

**现象**：为了省内存，让输出复用输入的内存。

**成因**：**这破坏了一个隐含前提**——尾块的处理依赖「输入还没被写过」。一旦别名，尾块读到的是**已经被部分写入的数据**。

**⇒ 这条的形态与前三者不同**：前三者是**形状/对齐**问题，这一条是**契约**问题（→ 01 篇）——「能不能别名」是**契约里的一个字段**（可选参数或边界行为），不是一个 tile 参数。

**规避**：判据表第 13 行。

### 4.5 ★ 把布尔闸门与预算比值放进同一个 `max`

**现象**：算「哪条约束最紧」时，把「对齐」也变成一个 0/1 的比值，然后四条一起取最大值。

**后果**：★ **结果恒等于对齐**——因为它的值恒为 `1.0`（`1.0` 恰好是最紧的比值），于是输出永远显示「对齐是最紧的约束」。

**这是本实现者的初版真实犯过的错**（不是假设）：程序 §1 的 `tightness` 函数把它改成了「**三条预算取最大 + 一条前置闸门**」，并在 docstring 里记下了这个错。**如果只看输出，它「看起来很合理」**——这正是本域反复强调的那类错误：**错误的结果比没有结果更难发现**。

**规避**：判据表第 2 行。**闸门与预算不能混进同一个比较。**

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 一条约束「换 tile 参数能解决」 | 它是 **tile 参数约束**；若换遍所有合法 tile 结论**不变** ⇒ 它是**问题形状约束**，要改 padding / 布局 / 算法 |
| 2 | 要算「哪条约束最紧」 | 只在**预算**之间取最大；**闸门（对齐）单独判合法/非法**——混进同一个 `max` 会得到恒等于闸门的结果 |
| 3 | 每线程寄存器需求为 `R` | 比的是 **`ceil8(R) ≤ 248`**，不是 `R ≤ 255`（分配粒度 8；255 那一档不可达） |
| 4 | 要判一个 tile 是否恰好到边界 | 用**正好落在档位上**的两组参数（248 / 256），不是「差不多」 |
| 5 | 要调 `stages` 到共享内存边界 | `stages_max = floor(上限 ÷ 每 stage 字节)`；`stages_max` 合法、`+1` 非法，**两者差恰好一个 stage** |
| 6 | 地址对齐与步长为 1 | **两个条件都要 gate**（向量化路径的前提是二者同时成立） |
| 7 | 用 `ldm` 的倍数要求 | `ldm` 是 **8（`__half`）/ 4（`float`）** 的倍数 ⇒ 是**行距的字节数**为 **16** 的倍数；**不要说「`ldm` 是 16 的倍数」** |
| 8 | 要引用 PTX 层的对齐 | PTX `wmma.load` 要求起始地址按 **fragment 的字节大小（m16n16k16 f16 = 32 B）** 对齐——**与 16 B 那条不是同一条规则，别互相换算** |
| 9 | FP8 卷积在 Hopper 上，`channels % 16 != 0` | **不合法**，且**换 tile 救不了**（问题形状约束）；`ConvolutionFwd` 的 batch 任意，**反向** batch 必须是 16 的倍数 |
| 10 | 约束方程里需要一个「非 fragment 寄存器」的数 | **无来源 ⇒ 明写一个假设并标 [E]**，不要编一个看起来真实的数；并说明它使结论成为**乐观上界** |
| 11 | 要选累加器档位（`.f16` vs `.f32`） | `.f16` 省一半累加器寄存器（8→4），代价是 02 篇的精度预算（`K` 只能到 2048）——**两笔账一起算** |
| 12 | 要设计边界测试形状 | 从约束方程推：**每个轴各取 `tile 边长 + 1`**；只测 2 的幂 ⇒ **零捕获**（结构性的，不是量不够） |
| 13 | 输出与输入可能同 buffer | 这是**契约字段**（别名），不是 tile 参数；尾块处理依赖「输入未被写过」⇒ 必须在契约层否决 |
| 14 | 尾块处理方式（predication / mask / 冗余线程） | 判据是**尾部的占比**，不是「哪个更省」；占比可由约束方程直接算出 |
| 15 | 报「边界测试通过了」 | 必须给出**测试形状集**；只给「形状数」不给形状 ⇒ 这句话不可核 |

**闭合性检查**：读完这张表能把「一个 tile 为什么合法/不合法、边界在哪、该测哪些形状、以及哪一类问题换 tile 救不了」判完。**唯一的表外输入**是「哪个 tile 最快」——本主题**不回答**（那是 `40-kernels` 的边界）。

## 6. 小结与延伸

- ★ **边界 bug 不会在第一块 tile 上暴露**：三个「只在最后一 tile 出错」的缺陷，在**只含 2 的幂**的测试集上（4 形状 × 3 缺陷 = **12 次比对）捕获数全部为 0**；换成从约束方程推出的边界形状集后**全部被捕获**。**这是结构性的——那些形状上没有不完整 tile。**
- ★ **寄存器预算的真实上限是 248，不是 255**（按 8 一档分配，256 那一档不可达）⇒ 需求 250 个寄存器的 tile **非法**。
- ★ **四者取最紧的分布极不均匀**：`2,625` 组穷举里 **955** 组合法，其中 **820** 组被**寄存器**卡住、128 组被 warp 数、**只有 7 组**被共享内存 ⇒ **寄存器算错的影响面是共享内存的 100 倍以上**。
- ★ **对齐的「8 / 4」不是「16 字节的倍数」**——是**字节积**才是 16；而 PTX 层的 fragment 字节数是 **32**，**两条规则不同层级，不能互相换算**。
- ★ **cuDNN FP8 的 channels % 16 是「问题形状」约束**，换 tile 救不了；且**前向 batch 任意、反向必须 16 的倍数**——与 02 篇的「反向需 `FLOAT` 累加」是**两处独立的同向不对称**。
- ★ **「余数自己还要再分块」的场景本篇没有建模** ⇒ `2·TM+1` 那类形状是**冗余**的。**一处本实现者初版写错、被实跑推翻的论断**（「三个轴缺一不可」）已更正为「这组形状的作用是**定位**」。
- ★ **闸门与预算不能放进同一个 `max`**（初版真实犯过：结果恒等于闸门）。
- **缺口要标注，不要填平**：`ADDRESS_AND_INDEX_REGS_ASSUMED = 0` 是明写的假设，使结论成为**乐观上界**。

**延伸**：

- `.f16` 累加器的寄存器节省与精度代价（两篇的交汇）：`45-kernel-lifecycle/operator-design/02-numerical-design` §1.4。
- 这些形状怎么进**验证矩阵**、容差怎么定：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- fragment 的布局规则与 `ldmatrix` 的字节算术（本库已有的推导，**本篇不重推**）：`20-gpu-architecture/tensor-core/02-fragment-layout`（尤其 §1 第六步与第 236 行的层级警告）。
- 共享内存的 bank 冲突、padding 与 swizzle（本域**不讲**）：`20-gpu-architecture/memory-system/03-shared-memory-bank-conflict`、`40-kernels/gemm/02-shared-memory-tiling`。
- 具体算子的 tile 参数怎么选到最快（本主题**不回答**）：`40-kernels/gemm/*`。

本篇对应的编号程序是 **`code/03_tiling_check.py`**。它需要 **numpy**（做整数矩阵乘与逐元素比对，整数使「相等」是**逐位**的），**不 import torch**、不碰 GPU。

- **A 类**：寄存器有效上限 **248**（并由「250 会被取整成 256」反证）；`ldm` 的 8/4 与**字节积 16**、以及 **PTX 层 32 ≠ 16** 这两条规则**不相等**；四组 tile 参数的逐条判定与**手算**一致（`(128,128,16) w2x2` → 192 寄存器合法；`(128,128,32) w2x2` → 256 非法；`(64,64,64) w2x2` → 160 合法；`(256,256,64) w2x4` → 640 非法）；共享内存算式与手算一致；warp 数的 block 侧 32 与 SM 侧 64 **取最紧 = 32**。
- **B 类**：共享内存的「**恰好不越界 / 恰好越界**」——tile `(128,128,32)` 时 `stages_max = 14`（229,376 B 合法）与 `15`（245,760 B 非法），**两者之差恰好一个 stage**；寄存器的同一对——`(48,112,16) w1x1` → **正好 248**（合法）与 `(32,160,16) w1x1` → **正好 256**（非法），并给出反驳点（朴素判据 `250 ≤ 255` 会接受一个取整后为 256 的需求）；穷举 `2,625` 组给出 **955** 组合法与「最紧约束」分布（寄存器 **820** / warp **128** / 共享内存 **7**）。
- **C 类**：★ ① 三个「只在最后一 tile 出错」的缺陷（丢 M 尾块 / 尾块起点夹回却写错位置 / 丢 K 尾块）—— **只含 2 的幂的 4 个形状上捕获数全部为 0**（12 次比对全 0），**换成边界形状集后 3 / 3 / 2**；② 每个缺陷被捕获 ⟺ **它那一轴有余数**（⇒ 这组形状能**定位**是哪个轴）；③ **反驳点**：换成整除形状 ⇒ 捕获数**全部退回 0**；④ **一处被实跑推翻的本库论断保留在输出里**——`(65,65,17)` 一个形状就捕获全部三个缺陷 ⇒ 初版的「缺一不可」**是错的**，已更正为「作用是定位」；⑤ 对齐是**问题形状**约束（`N=44` 时换遍所有合法 tile 判定不变）；⑥ cuDNN FP8 的 `channels % 16` 与前向/反向的 batch 不对称。
- **D 类**：`specs.py` §3 与 fragment 相关的每条常量逐条被断言钉住；含两个**自我更正**的落点（`ADDRESS_AND_INDEX_REGS_ASSUMED` 的假设性质、`UNSOURCED` 第 6 项）。
