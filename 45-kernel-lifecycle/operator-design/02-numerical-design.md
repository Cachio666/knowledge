# 数值设计：规范规定了「至少多少」，却没规定「什么顺序」

> **PTX 规定了累加精度「至少」是多少，但明确规定 `accumulation order`、`rounding`、`subnormal handling` 是 unspecified。** 也就是说，**同一个 kernel 的浮点结果不是规范保证的**——任何依赖逐位可复现的设计，都必须自己保证顺序。
>
> **这条论断在本机是可证的**（`code/02_error_budget.py` §C）：同一组 1000 个数，**只把累加顺序打乱**，fp32 顺序累加的结果差异达 **896 × u32**；K=100000 时达 **59,904 × u32**。**差异远超单次舍入单位**。
>
> **第二条可证伪论断**：把 fp16 换成 fp32 累加，可用的归约长度 `K` 相差 **8192 = 2^13 倍**（最坏界的临界值：**2048** vs **16777216**）。而且 **K 只要到 16，两边的差就已经超过 `u16` 的 2.98 倍**——「累加精度不是细节」不是修辞。

## 0. 背景与动机

### 0.1 「换个 tile 大小结果就变了」为什么不是 bug

现象：同一个算子、同一份输入，只把 tile 从 `64×64` 改成 `128×64`，输出**不再是逐位相同的数**。

**这不是 bug。这是一条规范事实的直接后果**（§2）：PTX 明文规定**累加顺序未规定** ⇒ 换个 tile 划分就是换一种累加顺序 ⇒ **结果不同是被允许的**。

**⇒ 它也不是「浮点误差」这种笼统的说法**，而是一个**精确**的陈述：

| 问题 | 规范的回答 |
|---|---|
| 累加**精度**至少是多少？ | **有规定**（`wmma.mma`：`.f32` 累加至少单精度；两侧都 `.f16` 时至少半精度） |
| 累加**顺序**是什么？ | **未规定** |
| **舍入**怎么做？ | **未规定** |
| **次正规**输入怎么处理？ | **未规定** |

**⇒ 前三行里只有第一行能引用规范。后三行必须由实现方自己保证。**

### 0.2 它对可复现性的影响：三种「确定性」，只有一种与浮点有关

| 说法 | 含义 | 由谁保证 |
|---|---|---|
| `run_to_run_stable` | 同样输入、同样配置，多次运行结果一致 | 通常由「不加非确定性并行归约」保证 |
| `bitwise_reproducible` | **跨 tile / 跨 block 划分 / 跨机器**逐位一致 | ★ **规范不保证**——必须自己固定累加顺序 |
| 「差不多就行」 | 有容差 | **容差必须有推导依据**（§1、§3），不能「试出来」 |

**⇒ 契约里写 `bitwise_reproducible` 这三个字，等于对实现提了一个规范不保证的要求**（→ 01 篇 §1.4）。本程序 §C.1 就是这条要求的可运行形态。

### 0.3 本篇在本域主线上的位置：它**抬高上界**

本域主线是「**到上界还有多远，以及那段距离值不值得走过去**」。本篇站在「**抬高上界**」这一格：

1. **累加精度档位直接决定算力上界。** fp16 张量核路径与 fp32 向量路径的峰值**不是同一个量级**（本库既有的 H100 ridgeline：**295.37 vs 20.00**，相差 **14.77 倍**——回链 `requirement-discovery/02-roofline-verdict`，此处不重推）。
2. **精度档位能不能用，由误差预算决定。** 如果 `K` 超过某个临界值，fp16 累加就**不再可用**（§1.4）⇒ 你被**退回**到算力低一个数量级的路径上。**这才是「抬高上界」在这里的具体含义**：预算算清楚了，你才**有资格**用高档位。
3. **容差是「上界能不能被验证」的接口。** 容差定得太松（拿最坏界定）⇒ 什么都测不出来 ⇒ 你**无法知道**自己有没有拿到那个上界。

> ⚠ **本篇与 `10-foundations/floating-point/04-low-precision-formats` 的边界**：那篇讲**累加误差本身**（同一格式算得越多、误差怎么涨）。本篇**不重推**那条推导，只讲两件事：**§1 的界如何变成容差预算**、以及 **§2 的「规定 vs 未规定」对照表**。误差随 `K` 增长的机制**回链**那一篇。

> ⚠ **本主题不出现任何 kernel 实现代码**（域 README 的硬边界）。

## 1. 原理：误差预算

### 1.1 三个界，以及一条必须写明的口径

设归约长度 `K`、单位舍入误差 `u`（`u = 2^-p`，`p` = 有效位数）：

| 界 | 表达式 | 它假设什么 |
|---|---|---|
| **最坏界**（简化式） | `K·u` | 每一次舍入都朝同一方向、且都取到最大 |
| **最坏界**（本库既有形式） | `γ_K = K·u / (1 − K·u)` | 同上，含高阶项；`K·u ≥ 1` 时**退化到 ∞** |
| **统计界** | `√K·u` | 部分和是**零均值随机游走**，误差按平方相加再开方 |

> ★ **`γ_K` 的形式照抄本库既有口径**（`10-foundations/floating-point/04`），本篇**不重推**。

**★ 可证伪论断一**：`K = 10000` 时，最坏界与统计界之比**恰好等于 `√K` = 100**（差**两个数量级**）。⇒ **「容差该定多少」没有无条件答案**——它取决于你**用哪一条界**。程序 §A.3 把这个比值断言成了 `√K`。

### 1.2 两个 `u`，以及一个被写错过两次的数

```
u_fp16 = 2^-11 = 4.8828125e-04
u_fp32 = 2^-24 = 5.960464477539063e-08
u16 / u32 = 8192 = 2^13
```

**★ 可证伪论断二**：`8192` 的**十进制数量级是 3.91**（`log10(8192) = 3.9134`）——**不是「三个数量级」**。写「三」是低估，写「四」是高估。

> ★★ **这一个数在本域被写错过两次**（域规格的逐篇表两次都写「容差相差约三个数量级」）。因此 `specs.py` 里专门放了一个 `U16_OVER_U32_ORDERS_OF_MAGNITUDE = 3.91` 常量，**它的唯一目的就是防止那个措辞错误回流**——程序 §A.1 断言它，改它 `make run` 就失败。

**⇒ 「容差按 dtype 定」这句话的量化形态**：同一段代码，累加精度从 fp32 换成 fp16，**容差要放宽 8192 倍**（近 4 个数量级）。

### 1.3 规范规定什么、不规定什么（**[A] 级，逐字**）

> ★ **引用等级：逐字。** 以下引文由本实现者**两次独立检索**读到同一段文字（PTX ISA 的 `wmma.mma` 条目，"Precision and rounding for .f16 floating point operations" 段；多个版本归档页一致）。程序 §D.4 把「够格标逐字」这个事实做成了一个**会被断言的布尔**。

| # | 规范的原话（`wmma.mma`） | 本篇的读法 |
|---|---|---|
| 1 | 元素乘法「**at least** single precision」 | ★ **下限**，**不是「恰好」**——允许更精确 |
| 2 | `.ctype` **或** `.dtype` 为 `.f32` 时，累加「**at least** single precision」 | 注意是**二者之一**，不是二者都 |
| 3 | 两者**都是** `.f16` 时，累加「**at least** half precision」 | 条件反过来；**只有这一档**允许半精度累加 |
| 4 | **`accumulation order`、`rounding`、`handling of subnormal inputs` 是 `unspecified`** | ★★ **本篇最重要的一条** |

**★ 「at least」被读成「恰好」是本篇的坑 ①（§4.1）**。第 1 行说乘法**至少**单精度 ⇒ 某个实现完全可以用**更高**的精度做乘法，而这不违反规范。**引用规范时只能引用它承诺的下限。**

**★ 第 4 行的三个未规定项是本节的重点**：它们不是「精度不够」，而是**「规范不说」**。这两件事的处置方式完全不同：

| | 「精度不够」 | **「规范不说」** |
|---|---|---|
| 处置 | 提高精度 / 换路径 | **自己保证**（固定顺序），或**明确声明不保证** |
| 能不能引用规范 | 能（规范给了下限） | **不能**——规范在这里什么都没说 |
| 静默出错的风险 | 低（误差可测） | ★ **高**——因为大家都以为「规范没说 = 随便」 |

> ⚠ **这是规范层的事实（P8）**：它说的是 **PTX 允许什么**，**不是**某块具体 GPU 的实际行为。实际行为可以被实测，但**实测结果不是规范**——换一代硬件就可能变。

### 1.4 三个天花板，**取最紧**

「`K` 增大到多少时 fp16 累加不再可用」这个问题有**三个**独立的答案：

| # | 天花板 | 推导 | fp16 的临界 `K` |
|---|---|---|---|
| ① | **最坏界失效** | `K·u ≥ 1` ⇒ `K ≥ 1/u16` | **2,048** |
| ② | **fp16 值域** | 对抗性输入（`K` 个数全为 1）下运行和 = `K` ≤ 65504 | **65,504** |
| ③ | **统计界失效** | `√K·u ≥ 1` ⇒ `K ≥ (1/u16)²` | **4,194,304** |

**⇒ 取最紧 = ①的 2048**（它比 ② 紧 **31.98 倍**，比 ③ 紧 **2048 倍**）。

**★ 可证伪论断三**：答案是 **2048**，**不是**统计界的 4.19e6。这个结论**反直觉**——通常人们会直觉地用统计界（「误差按 √K 涨」）来估，那会得出一个**宽松 2048 倍**的数字。

**同样的推导换到 fp32 累加**：最坏界的临界 `K = 1/u32 = 16,777,216`（= `2^24`）。**⇒ 两个精度可用的 `K` 相差 8192 倍**（§1.2 的同一个数）。程序 §B.1、§B.2 把这些都断言了。

### 1.5 从界到容差预算：拿最坏界定容差会**失去判别力**

**★ 可证伪论断四**：在 `K = 2048` 这一点上——

| 用哪条界 | 容差 | 判别力 |
|---|---|---|
| 最坏界 `K·u16` | **100%** 相对误差 | ★ **对任何输入都通过** ⇒ **等于没有容差** |
| 统计界 `√K·u16` | **2.21%** | 能测出问题 |

**⇒ 判据（进 §5 表）**：**容差必须写明它的依据是哪一条界**。写「最坏界」的容差在 `K ≳ 2048` 时**自动失去判别力**；写「统计界」的容差必须说明它假设了「部分和是零均值随机游走」——**输入有系统性偏置时这个假设不成立**。

**⇒ 这就是「精度预算」与「容差」之间的接口**：预算算出「最坏能差多少」，容差决定「差多少算错」。**两者必须来自同一条界**，否则验证是没有意义的。

### 1.6 规范之外的一层：**方向**也会决定档位（**[A] 级 · cuDNN FP8**）

> ★ **引用等级：经检索转述**（本实现者只读到检索摘要；**两次独立检索一致**，但**未逐字读到该表原文**）。

cuDNN 对 FP8 卷积的累加精度给了**两档** `compute type`：

| 档 | 什么时候够用 |
|---|---|
| `CUDNN_DATA_FAST_FLOAT_FOR_FP8` | **前向**与**推理**——更快、精度足够 |
| `CUDNN_DATA_FLOAT` | ★ **训练的反向**（算权重/激活梯度）——cuDNN 建议用这一档 |

**★ 可证伪论断五**：**「这个算子该用哪档累加」不是算子的属性，是「算子 × 方向」的联合属性**——同一个 FP8 卷积，前向可以用快的那档，反向**不行**。

**⇒ 这与 `requirement-discovery/02-roofline-verdict` 的结论同构**：那里是「**受限类型是「算子 × 精度路径」的联合属性**」，这里是「**累加档位是「算子 × 方向」的联合属性**」。**两条独立结论、同一个结构性认识**。

> ⚠ **本库此前未引用过 cuDNN 的这条约束**（域规格标注「实施时须自行核到原文」——本实现者做到了两处独立检索一致）。
> ⚠ **cuDNN 没有给出 `FAST_FLOAT_FOR_FP8` 的误差量级**（见 `code/specs.py` 的 `UNSOURCED` 第 3 项）⇒ 本篇**只说「允许哪一档」，不说「差了多」**。

## 2. 执行映射：这条事实在工程上落在哪

### 2.1 落点一：**跨 tile 的逐位一致性是不可能被规范背书的**

`bitwise_reproducible` 要成立，累加顺序就必须**固定**。而顺序由这些决定：

| 决定顺序的东西 | 会不会变 |
|---|---|
| tile 形状（`TM`/`TN`/`TK`） | ★ 会——它就是**设计变量** |
| warp 之间的分工 | 会 |
| 一个 warp 内部的 fragment 归约次序 | 会——PTX 未规定 |
| 硬件代际（同一份 PTX） | ★ **可能**会——规范只给下限 |

**⇒ 「换 tile 结果就变」不是实现有 bug，而是**设计上必须承认的事实**。要 `bitwise_reproducible`，就得在所有这四处都**固定**（或者换一条**顺序确定**的算法路径：例如固定顺序的串行归约、或成对求和树）。**代价通常是性能**——这是设计决策，不是正确性问题。

### 2.2 落点二：容差预算怎么按 dtype 定

| 设计决定 | 依赖的预算 |
|---|---|
| 用 fp16 还是 fp32 累加 | §1.4 的三个天花板**取最紧** ⇒ 2048 vs 16777216 |
| 容差取多少 | §1.5 —— 并**注明用的是哪条界** |
| `K` 超过 2048 之后怎么办 | ① 换 fp32 累加（**算力掉一个数量级**）；② **分块累加**（两级归约，把每段 `K` 压到 2048 以下）；③ 接受容差放宽 |

**⇒ 第三条是「精度预算」与「分块」的交汇点**（→ 03 篇 §1）：**两级归约不是性能技巧，它是把 `K` 压回预算内的手段。** 03 篇讲的是「`K` 方向怎么切」（tile 的 `TK`），本篇讲的是「切完之后每段的 `K` 是多少」。**两篇是同一次切分的两个面。**

### 2.3 落点三：这条事实**为什么在本机可证**

本机没有 GPU，但「累加顺序未规定」这条**规范事实的后果**是**纯算术**的，可以用宿主机的 fp16/fp32 标量累加复现：

- **仿真的是算术，不是硬件。** 程序用 numpy 的 `float16` / `float32` **标量顺序**累加，模拟一条归约链的舍入行为（刻意**不用** `np.sum`——它的成对求和会掩盖要展示的现象）。
- **⇒ 本程序不产出任何实测性能数字**，产出的是「同一组数、两种顺序、两个结果」。

## 3. 从「看起来对」到「误差有界」

| | 看起来对 | 误差有界 |
|---|---|---|
| 判据 | 「跑通了、结果像」 | 有一个**写出来的界**，且**界能拒绝错误的实现** |
| 容差 | 「试出来的」 | 按 dtype 的 `u` 与 `K` 推出来，并**注明用哪条界** |
| `K` 的上限 | 不知道 | §1.4 三个天花板**取最紧** |
| 可复现性 | 「应该没问题」 | 明确声明是 `bitwise_reproducible` 还是 `run_to_run_stable`（01 篇 §1.1 第 6 项） |

**⇒ 「误差有界」的可操作定义**：**能写出一个界，并且这个界足够紧、能拒绝一个错误的实现**。§1.5 那条判据就是它的守门人——容差若来自最坏界，在长 `K` 上**拒绝不了任何东西**。

## 4. 踩坑与失败模式

### 4.1 把「未规定」当成「保证」

**现象**：设计时假设「同一份输入 + 同一份代码 ⇒ 同一个输出」，于是在这个假设上盖了缓存、校验和、增量计算。

**成因**：把 §1.3 的第 4 行读成了「规范保证顺序是某个值」。**它不是**——规范**什么都没说**。

**规避**：判据表第 2 行。要逐位一致性 ⇒ **自己固定顺序**，或**把声明降级**为 `run_to_run_stable`（01 篇 §1.1 第 6 项）。

### 4.2 把「at least」读成「恰好」

**现象**：引用规范说「`.f16` 乘法**是**单精度」，然后据此写容差。

**成因**：`at least single precision` 是**下限**。某个实现完全可以用更高精度做乘法，而**这不违反规范** ⇒ 按「恰好单精度」推出的容差**可能比实际宽**（好方向）或**在另一代硬件上失效**（坏方向——硬件换了，实际精度下降了，只要不违反下限就不算错）。

**规避**：判据表第 3 行。**引用规范只能引用它承诺的下限。**

### 4.3 用 fp16 累加做长 `K` 归约

**现象**：数据以 fp16 存储（省带宽），累加**也用 fp16**（省寄存器——累加器的 `.f16` 档只要 `4` 个寄存器，是 `.f32` 档的一半，见 03 篇 §1）。

**成因**：把「**存储格式**」与「**累加格式**」混为一谈。**两者可以是不同的**——最常见的好做法正是 **fp16 存、fp32 累加**。

**后果（本程序 §C.2 实跑）**：两者**在小到 K=16 时就已经不是一个数**（差是 `u16` 的 2.98 倍）；到 K=65536 时，结果在**自己那个量级上**差了 **167 个 fp16 可表示步长**。

**规避**：判据表第 5、6 行。

### 4.4 容差没有推导依据，只是「试出来的」

**现象**：容差设成「跑通为止的最小值」。

**成因**：没有先把界写出来，于是容差**同时**承担了两个矛盾的职责——「够松以通过」与「够紧以拒绝错误实现」。**先试出来的那个值必然偏向「够松」。**

**规避**：判据表第 7、8 行。**先把 `K` 与 `u` 代进 §1.1 的公式**，再谈容差。

### 4.5 ★ 一个**自己先说破**的陷阱：单点测量不能支撑「误差随 K 增长」

**这是本篇最容易被写错的一句话**，而且**本实现者的初版就写错了**（程序 §C.3 把更正保留在了输出里）。

**现象**：跑一条随机序列，看到 `K` 增大时误差也在涨，于是写成「误差随 `K` 增长」。

**实跑的结果（程序 §C.3）**：**单条序列的相对误差** `|a16−a32| / |a32|` 在 `K` 上**不是单调的**：

| `K` | 64 | 256 | 1024 | 2048 | 4096 | 16384 |
|---|---|---|---|---|---|---|
|---|---|---|---|---|---|---|
| `÷ u16` | 2.82 | 1.76 | 4.71 | 1.72 | 23.70 | 15.17 |

**K=256 的值比 K=64 的**小**。** 成因是**相消**：相对误差的**分母**是结果本身，而结果量级在随机游走下**忽大忽小**——同一个绝对误差除以一个大的分母就变小。

**⇒ 更正后的表述**：

> **能断言的是「差 ÷ u16 随 K 单调上升」（差按 `K·u` 的量级长）；不能断言的是「相对误差单调上升」。** 前者是**绝对**量对 `u` 的比，后者被**结果量级**污染。

**⇒ 判据（进 §5 表）**：报误差时必须同时给出 **`K`、界的口径、以及测量次数**；**缺任何一个，那个数都不能用来支撑「误差随 K 增长」**。

> ★ **这与本库的元教训同构**（域 README 的元线索）：**过于干净的结果通常是采集方式的问题**。「K 越大误差越大」这个**看起来天经地义**的结论，在单次测量上**根本不成立**。

## 5. 判据表

> ★ 按本域约定，§5 的位置与编号保留，内容**不是实测数据**而是**判据表**。每一行必须是「**可机械判定的条件 → 结论**」。

| # | 可机械判定的条件 | 结论 |
|---|---|---|
| 1 | 要引用 PTX 的累加精度 | 只能引用**下限**：「至少单精度」/「至少半精度」；**「at least」≠「恰好」** |
| 2 | 设计里假设了「同一输入 ⇒ 逐位相同输出」 | **停**——`accumulation order` **未规定**；要么自己固定顺序，要么把声明降级为 `run_to_run_stable` |
| 3 | 契约/文档里出现「规范保证精度是 X」 | 先确认 X 是**下限**还是**精确值**；只有下限能引用 |
| 4 | 要判「这个结果的舍入是否合规」 | **不能判**——`rounding` 与 `subnormal handling` 未规定；只能判**精度下限** |
| 5 | 数据是 fp16 存储 | 累加**可以是** fp32；「存储格式」与「累加格式」**是两件事** |
| 6 | `K`（累加长度）是多少 | 与 `1/u` 比：`K ≥ 1/u` ⇒ **最坏界失效**（fp16：2048；fp32：16777216） |
| 7 | 要定容差 | 先写清**用哪条界**：最坏 `K·u`（或 `γ_K`）还是统计 `√K·u`；**两者在 K=10000 时差 100 倍** |
| 8 | 容差来自最坏界且 `K ≳ 1/u` | 容差 ≥ 100% ⇒ **失去判别力**，等于没有容差 |
| 9 | `K` 超过 §1.4 的临界值 | 三选一：换 fp32 累加（算力掉一个数量级）/ **分块两级归约**（把每段 `K` 压回预算内）/ 放宽容差并**写明** |
| 10 | 想断言「误差随 `K` 增长」 | 只能断言 **`差 ÷ u`** 随 `K` 增长；**相对误差不单调**（相消），单次测量**不能**支撑趋势 |
| 11 | 报一个误差数字 | 必须同时给出 **`K`、界的口径、测量次数**；缺任一项，那个数不可用 |
| 12 | 要算 `u16/u32` 的「数量级」 | 是 **8192 倍 = 10^3.91**——写「三个数量级」是低估，写「四」是高估 |
| 13 | 同一个算子的**前向**与**反向** | 累加档位**可能不同**（cuDNN FP8：前向可用 `FAST_FLOAT_FOR_FP8`，反向需 `FLOAT`）——**别用一个档位覆盖两个方向** |
| 14 | 要用 FP8 的快累加档 | 先确认**方向**；并且注意 cuDNN **没有给出**误差量级 ⇒ 不得编「差多少」 |
| 15 | 「换个 tile 结果就变」 | **不是 bug**，是规范后果；要消除它就固定顺序，**代价通常落在性能上** |

**闭合性检查**：读完这张表能把「这条浮点行为能不能引用规范、`K` 的上限是多少、容差该按哪条界定、以及能不能断言趋势」判完。**唯一的表外输入**是「结果量级有多大」（它决定相对误差的分母）——那要去看具体数据分布，不在本篇。

## 6. 小结与延伸

- ★ **PTX 规定了累加精度「至少」多少，却明确规定 `accumulation order`、`rounding`、`subnormal handling` 未规定**（**逐字**，两次独立检索一致）。⇒ **同一个 kernel 的浮点结果不是规范保证的。**
- ★ **这条在本机可证**：同一组 1000 个数**只打乱顺序**，fp32 结果差异达 **896 × u32**；K=100000 时 **59,904 × u32**。
- ★ **`u16/u32 = 8192 = 10^3.91`**——**不是三个数量级**（这个数在本域被写错过两次，`specs.py` 专门放了一个常量守着它）。
- ★ **`K` 的三个天花板取最紧 = 2048**（最坏界），不是统计界的 4.19e6，也不是值域的 65504。**fp32 的对应值是 16777216 ⇒ 相差 8192 倍。**
- ★ **拿最坏界定容差在 `K = 2048` 处要开到 100% ⇒ 等于没有容差。** 容差必须注明**依据哪条界**。
- ★ **cuDNN 的 FP8 累加档位由「方向」决定**（前向可用快档、反向需 `FLOAT`）——与「受限类型是算子 × 精度路径的联合属性」**同构**。
- ★ **一个自己先说破的陷阱**：**相对误差不是 `K` 的单调函数**（相消）⇒ 单次测量**不能**支撑「误差随 `K` 增长」。**能断言的是「差 ÷ u」的单调性。**
- **「换个 tile 结果就变」不是 bug**，是规范未规定累加顺序的直接后果。
- **「至少」不等于「恰好」**——引用规范只能引用它承诺的下限。

**延伸**：

- 误差**为什么**按 `√K·u` 而不是 `K·u` 增长（随机游走的推导）、三种格式遵循同一规律的证明：`10-foundations/floating-point/04-low-precision-formats`（**本篇不重推**）。
- 累加器档位与寄存器预算的**取舍**（`.f16` 累加器只要一半寄存器）：`45-kernel-lifecycle/operator-design/03-tiling-and-boundaries` §1。
- 容差如何进**验证矩阵**（按 dtype 定容差、参考实现必须独立）：`45-kernel-lifecycle/implementation/02-verification-matrix`。
- 契约里「确定性」这一项为什么必须写：`45-kernel-lifecycle/operator-design/01-interface-contract`。
- `wmma` / `mma.sync` 的 fragment 与精度语义：`20-gpu-architecture/tensor-core/01-mma-primitive`。

```bash

```

本篇对应的编号程序是 **`code/02_error_budget.py`**。它需要 **numpy**（做 fp16/fp32 的标量累加），**不 import torch**、不碰 GPU。

- **A 类**：三个界的公式与手算逐位一致（`K·u`、`γ_K = K·u/(1−K·u)`、`√K·u`）；`u16 = 2^-11`、`u32 = 2^-24` 逐位一致；**`u16/u32 = 8192` 且数量级是 `3.91`（不是 3）**；最坏界与统计界在 `K=10000` 时之比**恰好等于 `√K = 100`**。
- **B 类**：三个天花板各自推导并**取最紧**——最坏界 **2048**、值域 **65504**、统计界 **4194304**，最紧是 **2048**（比次紧的 65504 紧 **31.98 倍**）；fp32 的最坏界临界是 **16777216**，与 fp16 相差 **8192 倍**；固定种子下的**中位数**实测（差 ÷ `u16` 在 K=16 时已是 **2.98**，在 K=16384 时是 **2152.8**，**严格单调上升**）；以及「最坏界定容差在 K=2048 处退化到 100%」。
- **C 类**：★ ① **打乱顺序**后 fp32 顺序累加的结果差异 —— K=1000 时 **896 × u32**、K=10000 时 **7424 × u32**、K=100000 时 **59904 × u32**，**三个 K 上都远超单次舍入且随 K 单调增长**；② fp16 与 fp32 累加的差 —— **所有 K 上都 > `u16`**，K=65536 时在结果量级上差了 **167 个 fp16 步长**；③ 反驳点：同一组数改用 fp32 累加两次结果**逐位相同**（差异归零 ⇒ 差异确实来自累加格式）；④ 自己说破：**相对误差不是 `K` 的单调函数**（2.82 → 1.76 → 4.71 → 1.72 → 23.70 → 15.17），且最坏界与观测值**完全脱钩**；⑤ 与 fp64 对照：fp32 累加的相对误差只有 **8.49 × u32**，而 fp16 累加是 **122,324 × u32**——**高出四个数量级**。
- **D 类**：`specs.py` §2 的每条常量逐条被断言钉住；含**引用等级**的自我声明（PTX 那条**够格**标逐字 → 布尔为 `True`；而 01 篇引的 vLLM docstring **不够格** → 布尔为 `False`，**这一对照本身就是纪律的执行记录**）。
