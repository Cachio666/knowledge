# 45-kernel-lifecycle 算子全生命周期

从一次模型发布出发，走到一个算子的收敛。

本域不回答「这个算子**怎么写快**」（那是 `40-kernels`），回答「**为什么是它、写之前要定什么、写到什么程度算完**」。

## 本域覆盖什么

| 主题 | 内容 | 状态 |
|---|---|---|
| [requirement-discovery](requirement-discovery/) | 从模型规格读出算子清单 / roofline 判定 / 优化价值排序 | 未开始 |
| [operator-design](operator-design/) | 接口契约 / 数值设计 / 分块与边界 | 未开始 |
| [implementation](implementation/) | 参考实现先行 / 验证矩阵 / 调试顺序 | 未开始 |
| [convergence-and-tuning](convergence-and-tuning/) | 基准测量 / 显著性判定 / 收敛与停止 | 未开始 |

**统一主线**：

> **到上界还有多远，以及那段距离值不值得走过去。**

四个主题是这条主线的四次使用——需求发掘问「上界在哪」，设计问「怎么抬高上界」，实现守「上界的前提」（算对之前，上界没有意义），收敛问「剩下的距离是工程能触及的，还是噪声」。

一个直接推论贯穿全域：

> **「优化空间」不是「有多慢」，而是「离上界有多远」。** 一个跑得慢但紧贴上界的算子**没有优化空间**；一个跑得快但远离上界的才是目标。这一条同时否定两种常见做法——按「看起来慢」选目标，和按「占比大」选目标。

## 本域**不**做什么

本域横跨四个域，边界必须写死，否则会变成什么都说一点的大杂烩。

| 相邻域 | 它讲什么 | **本域不讲什么** |
|---|---|---|
| `40-kernels` | **具体算子**怎么做（gemm / attention / reduce / softmax / 融合 / MoE） | **本域不出现任何具体 kernel 的实现代码**。本域讲「做哪一个、按什么顺序、什么时候停」 |
| `50-performance` | **通用**性能方法论（profiling 工具、瓶颈定位、参数搜索） | 本域不重复讲**该域主题清单已覆盖的**工具。本域讲**一个算子**从开工到收敛的判断与停止条件 |
| `30-gpu-programming` | **怎么写**（CUDA / Triton / PTX-SASS / CUTLASS） | 本域不教任何编程接口的用法 |
| `80-model-architectures` | 模型结构**是什么**（transformer / 注意力变体 / MoE / 归一化 / 位置编码） | 本域不讲模型原理。本域讲怎么从模型规格**读出算子需求** |
| `10-foundations` | roofline 模型的**原理与推导**（在 `performance-models/`） | 本域不重推 roofline。本域用**已入库的口径**做判定，并回链 |

## 代码约定

本域的 12 个编号程序**全部在本机可跑**——纯 `python3` + `numpy`，**不 import `torch`**，不碰 GPU。

| 文件 | 性质 | 构建 |
|---|---|---|
| `NN_*.py` | 编号程序，**与文档一一对应** | `make run` |
| `specs.py` | 非编号辅助模块，**外部事实常量** | 被编号程序读 |
| `Makefile` · `requirements.txt` | 构建 | — |

**本域与其他域在代码形态上方向相反**：`40-kernels` 的编号程序是 `.cu`（要远程 GPU），本机只跑 `verify.py`；本域的编号程序**本身就是本机可跑的**，所以**没有 `verify.py`**。

### 每个程序必须可以被反驳

> 判据：如果文档里的论断是错的，脚本应当**报错或给出相反结论**。
> 一个无论论断对错都打印「✓ 通过」的脚本，视为**未实现**。

三类断言：**A 算法正确性**（与手算/独立实现对照）· **B 模型与公式**（按文档公式算并给判定）· **C 边界与反例**（文档声称「会出问题」的情形，**必须真的跑出问题**）。

**C 类是本域的重点**——本域的核心论断大多是「这么做会得出错误结论」，所以必须真的构造出那个错误结论。

## 数字口径：来源分级

本域的数字与前面几个域**性质不同**。前面几域的数字大量来自规范原文、厂商白皮书、本机实测，**可锚定**；本域的数字大量来自**别人的工程经验**，没有规范可依，来源强弱差异极大。

因此本域对每条外部常量标注**来源等级**：

| 等级 | 含义 |
|---|---|
| **A** | 厂商官方文档 / 规范（PTX ISA、CUDA C++ Programming Guide、NVIDIA 白皮书） |
| **B** | 产品官方文档（某一实现的规格，如 vLLM 文档、TensorRT-LLM 的 PR） |
| **C** | 论文 / 官方技术报告（**须注明是否确认同行评审**） |
| **D** | 社区项目文档（**个人或小团队仓库**） |
| **E** | 本库推导值（由本库已有常量算出） |

**硬规则**：

1. **D 级来源的数字，正文中必须写明它是 D 级**，不得以「研究表明」「业界经验表明」的口吻出现。
2. **D 级来源不得单独支撑一条论断**，须有 A/B/C 级佐证，或降级为「某个项目的经验值，未被独立复现」。
3. 凡引用外部数字，注释里必须写出**它是在什么条件下测的**（什么 GPU、什么 batch、什么精度）。写不出条件的，不写进来。
4. 口径不只区分 dense/sparse、标称/可达，还要区分**单 kernel / 端到端**。

## 文档的 §5 是「判据表」，不是「实测数据」

`CONTRIBUTING` 规定 §5 是「实测数据」（可选章节）。按同一份规范，`40-kernels` 因为「`.cu` 的运行结果本仓库没有」而**整节省略**了 §5。

本域有**同一个理由**（本机无 GPU，跑不出实测），但**结论不同**：本域有替代内容，且它是读者最需要的部分。

> **§5 的位置与编号保留，内容改为「判据表」。**

判据表每一行必须是**「可机械判定的条件 → 结论」**形式，**不得**写「根据情况判断」「视实际而定」；表要**闭合**——读完能照着做判断。

**本域任何一篇都不得声称有实测数据。**

## 与其他域的关系

- **上游**：`10-foundations`（roofline 的口径与推导）、`40-kernels`（各算子的代价模型与既有常量）、`80-model-architectures`（模型结构，**未建成**）。
- **下游**：`50-performance`（本域给出「什么时候停」，它给出「怎么测」，**未建成**）。
- **横切**：本域是**流程域**——它不产出新的硬件知识，而是给出「在什么条件下该做哪个判断」。所有具体知识**回链**到对应域，不在本域重复。

## 编号说明

本域编号 `45` **打破了「间隔 10」的约定**（现有 16 个一级域全部是 10 的倍数）。

**理由**：本域的知识对象是「从模型到算子再到调优」的流程，语义上必须落在 `40-kernels` 与 `50-performance` **之间**；放到 `160` 会让它与两个最相关的邻域隔开整个栈。

这是该约定的**第一处例外**，不追溯既有域。
