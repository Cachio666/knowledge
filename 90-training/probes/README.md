# 90-training/probes —— 探测脚本与它们的口径

这 3 个脚本是 `docs/superpowers/plans/2026-09-23-training-domain.md`
**§0.7-D「本机实测值」那张表（D1–D16）的唯一口径记录**。

它们原先只存在于 `/tmp`（**不入版本控制**，随时会被清掉），Chunk 0 把它们收进仓库。
**种子、初始化分布、重复次数、判据式都在脚本里** —— 读数字之前先读那一行是怎么算的。

- **不是编号程序**，不在任何主题的 `code/` 下，**不参与「文档数 = 编号程序数」的核对**
  （`CONTRIBUTING` §2：只有形如 `NN_*` 的文件才计入），也**不在**任何 `code/Makefile` 的扫描范围内。
- 它们是**探测**：**只打印、不断言、没有非零退出码**（三个脚本实跑 rc 均为 0）。
  可证伪的断言属于各主题 `code/` 下的编号程序，不属于这里。
- 运行环境（本机实测，即这些数字的测量条件）：**python3 3.13.5 + numpy 2.4.4**，macOS arm64，
  **无 GPU**。⇒ 本域的一切数值都是**玩具规模的真跑**，**不得支撑关于大规模训练的结论**。
- 三个脚本共用同一个种子：`np.random.default_rng(90)`。
  ⇒ `probe_90.py` 的 `A2` 与 `probe_90b.py` `A2` 表的「随机 N(0,0.1)」那一行
  **是同一组随机数**（两处都给 `0.149927 / 0.759138`），不是两次独立测量。

```sh
cd 90-training/probes
python3 probe_90.py        # 其余同理：probe_90b.py / probe_90c.py
```

## 入仓前的两处修正（计划 §0.7-D 的 D4b 与 §0.1 第一条）

1. **`probe_90.py` 的除法溢出（★ 两处，不是一处）。**
   原稿 `np.log10(F16_MAX/float(F16_TINY))` 实跑打印 `inf 个数量级` 并报
   `RuntimeWarning: overflow encountered in scalar divide`；**fp32 那一行同样溢出**。
   ★ 原因**不是**「两个操作数都是 `np.float16`」（`float(F16_TINY)` 是 Python float），
   而是 **NumPy 2.x 的 NEP 50 弱标量提升**（Python 标量**不提升**标量的 dtype）——
   证据（一行可复核，`probe_90.py` 的注释里也写着）：
   `(np.finfo(np.float16).max / float(np.finfo(np.float16).tiny)).dtype` → **`float16`**。
   现在**显式转 float64**，并把三个数的**口径各自标出来**。

2. **`probe_90b.py` 第 32 行的硬编码字符串 `⇒ 差 ≈ 7.5 个数量级` 已删除。**
   它是**自造真值**：`76.46 − 12.04 = 64.42`，而且那两个数**不是同一个口径**
   （fp16 那一行**含次正规**、fp32 那一行取**正规**下限）。
   替代它的是**三个各自标了口径的数**（`9.03 / 12.04 / 76.46`），
   以及由脚本自己算出的**同口径差 `67.43`** ——
   与库内已有的正确口径一致：`130-model-optimization/quantization/03-bf16-fp16-tf32.md:154`
   给的是「bf16 的量程跨度宽 **67.5** 个数量级（`76.5 vs 9.0`）」。

   ★ 这两处之外，脚本**未作任何改动**（起止行、打印格式、其余结论一律保留原样）。

## 缺口与不可用的数（**引用前必读**）

1. ★★ **D4b 原稿的「差 ≈ 7.5 个数量级」不可用 —— 那是自造真值。**
   理由两条：**数字不对**（`76.46 − 12.04 = 64.42`），**口径也不同**
   （fp16 含次正规 vs fp32 正规）。它原先的出处就是 `probe_90b.py:32` 的一个**硬编码字符串**，
   紧跟在那两行打印之后、**没有任何推导**；该字符串已删（见上）。
   ⇒ **引用动态范围时，只能用同口径的一组**：fp16 正规 `9.03` / fp16 含次正规 `12.04` /
   fp32 正规 `76.46`；**同口径的差是 `67.43`**。
   ★ 库内先例（`130-model-optimization/quantization/03-bf16-fp16-tf32.md:154`）**逐字警告过**
   `2^-126` vs `2^-14`「**两个数不是同一个量，不要混用**」。

2. ★★ **bf16 的 `eps` 有两处已知错误，本目录按纪律「只修控制者点名的两处」处置，未就地修正。**
   · `probe_90.py` 的 `F1` **回退分支**：打印 `eps = 2^-8 = 0.00390625`，
     并在小结里写「bf16 … 精度低（eps 0.0039）」；
   · `probe_90b.py` 的 `F1'` **末行**：`bf16 精度**低 4 倍**`。
   **正确的值/说法**：bf16 尾数 **7** 位 ⇒ `eps = 2^-7 = 0.0078125`，
   **比 fp16 低 8 倍**（`9.77e-4 → 7.81e-3`）。依据：计划 §0.7-B 的 **B-1** 与 §0.7-D 的 **D13**。
   ★★ **注意这两处是「结论行」错，不是计算错**：`probe_90b.py` 的 `F1'` 自己按 IEEE 定义
   算出来的 `eps = 2^-7 = 0.0078125` **是对的**（`bf16_finfo()` 里 `eps = 2**(-man_bits)`），
   错的只是它紧跟着的那句「低 4 倍」；`probe_90.py` 的 `F1` 则是**手工填的常数**填错了
   （同一个 `F1` 段里写着「尾数 7 位」却填 `2^-8`，自相矛盾）。
   ⇒ **引用 bf16 的 `eps` 时以计划 §0.7-D 的 D13 为准，不要引用这两行的输出。**

3. **`probe_90.py` 里的 `import ml_dtypes` 在本机不可用。**
   它写在 `try/except` 里，本机**没装** ⇒ 走的是手工分支（也正是第 2 条那处错误的所在）。
   ⇒ `ml_dtypes` **不是**本域的依赖（`code/requirements.txt` 里没有它）；
   ★ 换一台装了 `ml_dtypes` 的机器时，`F1` 会走真 `finfo` 分支，那一支的 `eps` 是对的。

4. **D2 的 `0.696466` 是单种子值。** 换种子会得到别的数（计划 §4 **T19** 记了另一个种子下的
   `1.127157`）⇒ 引用时只写「差 > 0.1」，**不要写单个数**。

5. **`probe_90b.py` 里的段标签 `A1/A2/A3` 与 `E2`/`G2` 是脚本自己的编号**，
   与计划 §0.7 的 **A 节（本机硬约束）/B 节/C 节/D 节**没有对应关系。
   ★ 原稿曾把 `A3` 当依据 ⇒ 那是**自造编号**（**M3**，与 P21 同源）。
   本 README 的 D 行 → 段标签对照表就是为了避免再读错。

6. **`probe_90.py` 的 `A2` 在 §0.7-D 里没有独立行。** 它（随机 `N(0,0.1)`、200 步）
   与 `probe_90b.py` `A2` 表的同名行**是同一组随机数**，值是 `0.149927 / 0.759138`；
   §0.7-D 的 **D2** 引的是 `probe_90b.py` 的 `N(0,1)` 那一行（`0.696466`）。

7. **`probe_90c.py` 的 `C1` 与计划 §3 表 A ⑦ 的判据不是同一个判据。**
   脚本打印的 `✓ == max_norm` 用的是 `abs(new_total - max_norm) < 1e-6`（一个**绝对**容差），
   而计划表 A ⑦ 要的是**相对**误差 `1e-6/T` **且 `T ≥ 1`**。
   ⇒ 计划那条才是有判据形状的那一条；**本脚本这一行只作演示**。

## 这些数**不能**支撑什么

- 一切数值都是 `python3` + `numpy` 的**玩具规模**真跑：**没有 GPU、没有训练任何真模型**
  ⇒ **不得**支撑关于真实训练系统的结论（`CONTRIBUTING` §2 的「本机实测值」限定语）。
- D11/D12 是**分段策略的一个模型**（「每段 `⌈√n⌉` 层、段内从头重算」），
  不是任何实现的实测；`√n` 与 `≈2n` 都是**这个模型**的结论。
  ★ 与论文（Chen 2016）的关系：原文只给 `O(·)` 与「`an extra forward pass`」；
  **精确的分段计数公式是本库推导**（`specs.py` 的 `UNSOURCED` 里记着这一条）。
